# 消息队列进阶语义

基础的“发消息、收消息”之外，生产环境真正决定消息队列好不好用的，是顺序、延迟、死信、幂等、投递语义这组进阶语义。本篇讲清每个语义的含义、代价和 Kafka / RocketMQ 的实现差异。

## 1. 顺序消息：分区顺序与全局顺序

- 分区顺序：同一分区（Kafka 的 Partition、RocketMQ 的 MessageQueue）内严格有序。实现方式是把同一业务键的消息固定路由到同一分区：Kafka 按消息 key 做分区，RocketMQ 按 key 做队列选择。代价小，是生产中最常用的顺序级别。
- 全局顺序：所有消息跨分区也有先后。实现方式只有一个：全局只用一个分区/队列。代价很大：并行度归零、单分区成为吞吐瓶颈和故障单点。除非业务强要求（如单账户资金流水全局定序），否则不要选全局顺序。
- 消费端保序的前提：同一分区在同一时刻只能被同一消费者实例消费，否则两个消费者并行处理同一分区的消息，顺序立刻被打乱。
- Kafka 的两个保序要点：第一，生产者开启幂等（`enable.idempotence=true`）后，靠生产者序列号保序，即使 `max.in.flight.requests.per.connection` 大于 1，重试也不会乱序；不开启幂等时，重试乱序只能把 `max.in.flight` 设为 1 来规避，代价是吞吐下降。第二，消费者端用“同一分区单线程处理”或按 key 分发到固定线程。
- RocketMQ 的顺序消费：发送端按 key 选择队列，消费端用顺序消费模式（`ConsumeMessageOrderlyService`），同一队列同一时刻只被一个消费者锁定消费，失败时挂起重试而不是跳过，保证“前一条没成功，后一条不处理”。

## 2. 延迟消息：到期才可见

- 典型场景：订单超时未支付自动关单、失败重试退避、定时提醒。共同点是“现在发、未来某个时刻才允许消费”。
- RocketMQ 4.x：固定 18 个延迟级别（1s、5s、10s、30s、1m、2m、3m、4m、5m、6m、7m、8m、9m、10m、20m、30m、1h、2h），发送时只能选级别，不能自定义任意时长。RocketMQ 5.x 提供定时消息，可指定任意未来时刻。
- Kafka：原生没有延迟消息。常见做法是业务层实现：延迟 topic + 定时扫描到期消息再转发，或者外部调度器到时再发送。不要把“消费端 sleep 等待”当作延迟消息，那会占住消费线程、拖垮吞吐。
- 选型提醒：延迟精度要求到秒级且量大时，优先用原生支持定时/延迟的消息产品；量小且精度要求低时，业务层延迟 topic 也够用。

## 3. 死信队列：重试耗尽后的归宿

- 含义：消息消费失败、重试次数耗尽后，不再原地重试，而是被路由到一个专门的死信队列（DLQ），等人工或自动程序后续处理。作用是把“毒消息”隔离出去，避免它无限阻塞正常消费。
- RocketMQ：非顺序消息默认最多重试 16 次，耗尽后进入 `%DLQ%` 开头的死信队列。顺序消息没有死信队列概念，失败会一直挂起重试，需要业务侧兜底。
- Kafka：原生没有死信队列。常见做法是框架或业务实现，例如 Spring Kafka 的错误处理器把失败消息转发到单独的 DLQ topic，或者消费端捕获异常后手动发送到 DLQ topic。实现时注意两点：死信消息要带上原始 topic、失败原因、重试次数；重放死信时要有次数上限，避免死信本身再次失败形成死循环。
- 死信处理流程：告警 → 定位原因（脏数据、Bug、下游故障）→ 修复后重放或丢弃。死信队列不是垃圾桶，长期无人处理的死信等于悄悄丢数据。

## 4. 幂等消费：重复投递下的保命手段

- 为什么需要：主流消息队列默认提供“至少一次”投递（见第 5 节），网络抖动、消费端崩溃、重试都会导致同一条消息被投递多次。消费逻辑如果不幂等，重复消费就是重复扣款、重复发货。
- 业务唯一键 + 消费记录表：用业务唯一键（如订单号）做去重键，消费时在同一个本地事务里同时写业务数据和消费记录；重复投递时先查消费记录，已处理则跳过。这是落地最稳的做法，代价是一张去重表和一次额外写入。
- Redis SETNX：消费前用 `SET key value NX EX 秒数` 抢锁式去重，成功才处理。注意过期时间与崩溃窗口：处理耗时超过过期时间，锁提前释放，重复投递可能再次通过；去重键还要定期清理，避免无限膨胀。
- 幂等键设计：键必须稳定（同一条业务消息每次重试的键相同）、可回查（能从键反查到原始业务单据）。用随机 UUID 做幂等键是常见错误：每次重试键都不同，去重永远失效。

## 5. 投递语义对照：至多一次、至少一次、恰好一次

| 语义 | 含义 | 代价与适用 |
|---|---|---|
| 至多一次 | 消息最多被处理一次，可能丢失 | 不重试、不确认，吞吐最高；只适合可丢的场景，如非关键日志采集 |
| 至少一次 | 消息至少被处理一次，可能重复 | 需要生产者重试 + 消费端幂等；是生产中的主流选择 |
| 恰好一次 | 消息恰好被处理一次，不丢不重 | 实现成本最高，且有边界（见下） |

- 恰好一次的边界要讲清：Kafka 通过幂等生产者 + 事务（`transactional.id`）可以在“消费—处理—生产”这个 Kafka 内部闭环里实现恰好一次（Kafka Streams 的 EOS 语义）。一旦闭环跨出 Kafka、涉及数据库等外部系统，严格的恰好一次就无法保证，工程上的等价做法是“至少一次投递 + 消费端业务幂等”，对外效果等同于一次。
- 选型口诀：能接受丢 → 至多一次；不能丢 → 至少一次 + 幂等；只有纯 Kafka 闭环才谈事务级恰好一次。

## 6. Kafka 与 RocketMQ 实现差异对照

| 语义 | Kafka | RocketMQ |
|---|---|---|
| 分区顺序 | 同一 Partition 内有序；key 决定分区 | 同一 MessageQueue 内有序；key 选择队列 |
| 全局顺序 | 单 Partition，代价大 | 单队列，代价大 |
| 延迟消息 | 原生不支持，业务层实现 | 4.x 固定 18 级；5.x 定时消息任意时刻 |
| 死信队列 | 原生不支持，框架/业务实现 | 非顺序消息默认 16 次重试后进 `%DLQ%` |
| 幂等生产者 | `enable.idempotence=true` + 序列号 | 消息 id 与业务去重键配合，业务层实现幂等消费 |
| 事务（恰好一次） | 事务 API + Streams EOS，限 Kafka 闭环 | 事务消息（半消息 + 回查），用于分布式事务场景 |

## 小技巧与冷知识

【小技巧】分区顺序的 key 一定要选业务主键且全程不变，比如订单号，千万别拿订单状态、下单时间这类会变的字段当 key。key 一变，消息就被路由到另一个分区，原来的顺序保证立刻失效；重试、重发时也要用同一个 key，否则同一笔订单的两条消息可能落在不同分区。

【小技巧】Kafka 增加分区数会打乱 key 到分区的映射：分区数变了，同一 key 的哈希取模结果可能落在新分区上，新消息的顺序起点就变了。已上线且依赖分区顺序的 topic，扩分区前要先评估影响，顺序要求强的 topic 宁可先扩副本、加消费者，也别轻易加分区。

【小技巧】RocketMQ 4.x 的延迟级别是固定档位，没有想要的时长就选“最接近且偏大”的一档，比如需要 25 分钟只能选 30 分钟那档，宁可晚到、不可早到。需要任意时长时再考虑 5.x 的定时消息或业务层调度，别在 4.x 里硬凑自定义时长。

【小技巧】死信重放前先修根因、再重放，而且要限流逐条放回：直接把 DLQ 整批倒回原 topic，根因没修好时等于把毒消息又喂回去一遍。重放时先在小流量下验证几条能正常消费，再逐步放大；重放也要设次数上限，避免死信二次失败又回到死信里打转。

【小技巧】给死信队列单独配消费组和告警，别让它只躺在控制台里：死信一有新增就告警、每天巡检一次积压量，长期无人处理的死信等于悄悄丢数据。告警阈值按业务定，关键链路的死信哪怕只有一条也值得立即看。

【小技巧】顺序消费里一条毒消息会挂起整个队列，所以要给挂起设上限：失败超过约定次数后转人工或记账跳过，不能无限挂起。否则队列永久卡住，后面所有正常消息都被堵住；跳过的消息要留档，事后能按业务键追回来补处理。

【小技巧】幂等键别拿消息 ID 充数：Kafka 没有业务稳定的消息 ID，RocketMQ 的 msgId 也是每次发送新生成的，应用层重发一次就换一个 ID。去重一定要用业务唯一键，比如订单号、支付流水号，只有业务键在重试、重发时始终不变。

【小技巧】Redis SETNX 去重的有效期就是去重窗口：过期时间要大于“单次处理耗时 + 可能的重试间隔”，否则锁先过期、重复投递又会通过。超过窗口的重复投递本来就防不住，所以去重键的过期时间要按业务能接受的最长重试周期来定，太短等于没去重。

【小技巧】去重记录别只记“处理过”，要记“处理结果”：重复投递时直接返回上次的结果，比“已处理就跳过”更稳，调用方拿不到结果会以为没成功、可能再发一次。去重表里存业务键、处理状态和结果摘要，重复投递直接按结果返回。

【小技巧】Kafka 事务的消费端要配 read_committed，否则 EOS 闭环不完整：默认的 read_uncommitted 会读到已中止事务的消息，等于把回滚掉的数据又消费了一遍。只要用了事务生产者，下游消费者就把隔离级别改成 read_committed，和事务配套使用。

【冷知识】Kafka 幂等生产者的去重键是“生产者 ID + 分区 + 序列号”三元组，序列号是按分区单独维护的。broker 收到重复序列号就直接丢弃，所以幂等只能防“同一生产者实例的同一分区重试”，换个生产者实例重发是新序列号，照样会写进去。

【冷知识】RocketMQ 的系统 topic 都用 % 开头，比如 %RETRY% 是重试队列、%DLQ% 是死信队列，业务 topic 不要用 % 开头命名。看到 % 开头的 topic 就知道它是系统保留的，控制台上按这个前缀一眼就能区分业务队列和系统队列。

【冷知识】Spring Kafka 的死信发布器默认把失败消息发到“原 topic 名 + .DLT”的 topic，而不是随便起一个名字。知道了这个约定，排障时不用到处找死信落在哪，直接去对应 .DLT topic 查，还能在消费端给 .DLT topic 单独配消费组做重放。

【冷知识】RocketMQ 顺序消费的队列锁在 broker 端：同一队列同一时刻只被一个消费者锁定，重平衡时锁会交接给新消费者，交接期间该队列暂停消费。所以顺序消费扩容、缩容时会出现短暂的队列停顿，这是保序的代价，不是消费卡住了。

【冷知识】RocketMQ 4.x 的 18 档延迟里最长一档是 2 小时，超过 2 小时的延迟在 4.x 里没有原生档位可选。需要更长延迟时，要么升级到 5.x 用定时消息指定任意时刻，要么在业务层用调度器到时再发，别指望 4.x 的延迟级别能覆盖。

【小技巧】“至少一次 + 幂等”落地的检查清单只有三项：生产者开重试、消费端做了业务幂等、重复投递有演练。上线前故意制造一次重复投递，看消费端是不是真的只生效一次；没演练过的幂等，等于没做。

## 面试与自测

1. 为什么全局顺序消息在生产中很少用？
2. Kafka 原生没有延迟消息和死信队列，工程上一般怎么实现？
3. “至少一次投递 + 幂等消费”和“恰好一次”是什么关系？

### 参考答案

1. 全局顺序只能用单个分区/队列，并行度归零，单分区成为吞吐瓶颈和故障单点；除非业务强要求全局定序，否则用分区顺序（同一业务键固定到同一分区）就够了。
2. 延迟消息用延迟 topic + 定时扫描到期转发，或外部调度器到时发送；死信用框架错误处理器或消费端手动转发到单独的 DLQ topic，并带上原始 topic、失败原因、重试次数，重放设次数上限防死循环。
3. 至少一次投递允许重复，靠消费端业务幂等把重复消费抹平，对外效果等同于一次；严格的恰好一次只在 Kafka 内部“消费—处理—生产”闭环里靠幂等生产者 + 事务实现，跨出 Kafka 涉及外部系统时无法严格保证。
