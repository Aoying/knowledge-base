# Kafka 与 RocketMQ 对比

## 1. 核心概念

Kafka 和 RocketMQ 都是分布式消息中间件，但出身决定了性格：

- **Kafka** 出身于 LinkedIn 的日志/数据管道场景，本质是**分布式提交日志**。强项是超高吞吐、流式处理生态（Kafka Streams、Connect、Flink 对接），消息默认按「流」消费，保留期内可反复回溯重放。
- **RocketMQ** 出身于阿里电商交易链路，是为**业务消息**设计的：事务消息、顺序消息、延迟消息、消息轨迹、按 key 查询都是原生能力，控制台和运维工具链对业务团队友好。

一句话定位：**Kafka 是数据流管道，RocketMQ 是业务消息总线**。选错了不是不能用，而是处处要自己补轮子。

## 2. 基础知识

### 架构对比

| 组件 | Kafka | RocketMQ |
|---|---|---|
| 元数据/协调 | 3.x 靠 ZooKeeper；4.x 起 KRaft 自治（去掉 ZK） | NameServer（轻量无状态，节点间不通信，各自广播） |
| 存储节点 | Broker，按 Topic-Partition 组织 | Broker，按 Topic-Queue 组织 |
| 服务端过滤 | 不支持，客户端拉全量自己过滤 | 支持 Tag/SQL92 属性过滤 |
| 消费模型 | 拉（Pull），消费组内分区独占 | 推拉结合（长轮询实现近推效果），队列负载均衡；5.x 增加 Pop 消费 |
| 客户端生态 | 多语言、社区生态最全 | Java 一等公民，其他语言以 5.x gRPC 客户端补齐 |

架构差异的实际影响：Kafka 的分区数决定消费并行度上限；RocketMQ 的服务端过滤能在消息量大、消费方只关心子集时省大量无效拉取。

### 消息模型对比

| 维度 | Kafka | RocketMQ |
|---|---|---|
| 消息保留 | 按时间/大小保留，消费后不删除 | 同左（CommitLog 顺序写，过期清理） |
| 消费位点 | offset 由客户端/消费组管理，可任意重置回溯 | offset 由 Broker/客户端管理，支持按时间重置 |
| 按 key 查消息 | 不支持，要靠外部索引 | 原生支持按 MessageId / Key 查询和轨迹追踪 |
| 死信处理 | 无原生死信队列，自己实现 | 重试耗尽自动进死信队列 `%DLQ%消费组` |
| 消息回溯 | 改 offset 即可重放 | 控制台/命令按时间重置位点 |

## 3. 进阶知识

### 顺序、事务、延迟三件套

| 能力 | Kafka | RocketMQ |
|---|---|---|
| 顺序消息 | 同一 Partition 内有序；靠相同 key 落同分区实现局部有序，全局有序只能单分区（吞吐塌方） | 分区（队列）内有序 + 提供顺序消息专用发送/消费模式（队列锁、顺序消费线程模型）；全局顺序同样要单队列 |
| 事务消息 | 有事务机制（幂等生产者 + 事务协调器），定位是 **exactly-once 流处理**（消费-处理-回写 Kafka 闭环），不是业务分布式事务 | **半消息 + 事务回查**机制专为业务分布式事务设计：先发半消息（消费者不可见）→ 执行本地事务 → 提交/回滚，Broker 定期回查本地事务状态。这是 RocketMQ 的招牌能力 |
| 延迟消息 | **原生不支持**。要自己造：时间轮、分级延迟 Topic、或外挂调度，无标准方案 | 4.x 固定 18 个延迟等级；5.x 支持任意精度定时消息（Timer Message），下单超时关单这类场景开箱即用 |

结论很硬：**业务系统需要事务消息或任意延迟，选 RocketMQ；Kafka 硬做这两件事就是自研半个 RocketMQ。**

### 可靠性与一致性

- Kafka：副本 + ISR 机制，`acks=all` + `min.insync.replicas=2` 可做到已确认消息不丢（RPO=0 级别）；幂等生产者防重复，事务保证流处理 exactly-once。
- RocketMQ：同步刷盘/异步刷盘、同步复制/异步复制可组合；默认异步刷盘 + 异步复制，极端宕机有丢消息窗口，金融场景要显式改同步双写并接受吞吐下降。
- 两边都只是「消息不丢」，**端到端不重复消费都要业务幂等兜底**，这点没有例外。

## 4. 原理剖析

### 吞吐差异的来源

Kafka 高吞吐靠三板斧：分区顺序写 + 页缓存 + **零拷贝（sendfile）**，批量和压缩（lz4/zstd）把网络和磁盘都喂满；单机百万级 TPS 的宣传数字来自大批量、顺序、少过滤的日志型负载。

RocketMQ 的存储是**所有 Topic 共用一份 CommitLog 顺序写**，再异步分发到各队列的 ConsumeQueue 索引。这个设计让写入吞吐不随 Topic 数衰减（Kafka 的分区文件多了随机写和句柄压力上升），代价是消费要多一次索引跳转。两个设计没有高下，是「按分区隔离」与「全局日志 + 索引」的路线之争。

### 堆积能力

消息堆积时看两个指标：写入还能不能扛、消费追赶速度。

- Kafka：堆积就是文件躺在磁盘上，写入几乎不受已堆积量影响；消费端按分区线性扩，追赶速度快。是业界公认的**堆积之王**，这也是日志、数仓同步链路清一色 Kafka 的原因。
- RocketMQ：CommitLog 顺序写同样不怕堆积，消费位点独立推进；但堆积量大时 ConsumeQueue 页缓存命中率下降，随机读放大，追赶速度不如 Kafka 平滑。业务消息的正常堆积量级（分钟到小时级）完全够用，TB 级囤积不是它的主场。

### 消费失败与重试

Kafka 没有 Broker 侧重试概念：消费失败靠应用自己处理（重试 Topic、死信 Topic 都是自己搭的模式），灵活但每家实现都不一样。RocketMQ 把重试做进产品：消费失败自动重试（默认 16 次、间隔递增），耗尽进死信队列，控制台可查可重投。业务团队用 RocketMQ 省的就是这套「失败治理」基建。

## 5. 实战应用

### 选型建议（结论先行）

| 场景 | 选择 | 理由 |
|---|---|---|
| 日志采集、行为埋点、数仓/实时计算数据管道 | **Kafka** | 吞吐与堆积能力、Flink/Streams 生态无可替代 |
| 订单、支付等交易链路异步解耦，需要事务消息保一致 | **RocketMQ** | 半消息事务回查是原生能力，别在 Kafka 上自研 |
| 定时/延迟触发（超时关单、延迟通知、对账提醒） | **RocketMQ** | 5.x 任意精度定时消息；Kafka 无原生方案 |
| 消息量不大、团队已熟 Kafka、只是普通异步通知 | 沿用 Kafka | 换中间件的迁移和运维成本大于收益 |
| 新业务系统、无历史包袱、国内团队 | **RocketMQ 优先** | 中文文档、控制台、轨迹查询对中小团队运维友好 |
| 跨国/多语言客户端、海外生态对接 | **Kafka 优先** | 客户端生态和云厂商托管支持占优 |

### 结合实际项目看

**翼安反诈平台同时用了 Kafka 和 RocketMQ**——这不是重复建设，是按负载分工：

- **Kafka 承接数据流**：话单、交易流水等大吞吐数据进入平台，走 Kafka 做采集管道，下游接实时计算做风险特征加工，看中的是吞吐、堆积和回放（模型复盘要重跑历史数据时 offset 回溯就是刚需）。
- **RocketMQ 承接业务消息**：风险处置通知、工单流转、跨系统状态同步这类交易型消息，要的是可靠投递、失败重试、死信可查、按单号查轨迹——出问题时运维能在控制台按 key 把一条消息的一生查清楚，这对政务/反诈场景的审计要求是实打实的加分。

**神农 e 贷场景**：银行信贷系统，消息量级不大（审批流状态变更、短信/推送通知、与外部征信和核心系统的异步交互），但一致性要求高——审批结果落库和发通知不能一成一败。这类场景的正解是 RocketMQ 事务消息（或本地消息表）保「落库 + 发消息」原子性，Kafka 在这里没有用武之地：吞吐优势用不上，缺的事务/延迟能力反而要自己补。银行内网还有个现实因素：RocketMQ 的运维控制台和国产化适配（TongWeb 环境、信创审查材料）比 Kafka 全家桶更容易过审。

### 共存时的纪律

一个系统里两套 MQ 并存是常态，但要立规矩：**新消息先按上表归类再选边，禁止同一业务消息双发两边**（对账和排障时会死人）；统一消息规范（命名、key 设计、幂等键）与中间件无关地执行；监控告警一套面板看两边，别让任何一套成为盲区。

## 6. 疑难杂症

- **Kafka 消费组频繁 Rebalance**：消费者处理超时（`max.poll.interval.ms` 内没拉下一批）、消费线程阻塞、心跳线程异常都会触发踢出重平衡。先把单批处理时间降下来（减小 `max.poll.records`、慢逻辑异步化），别盲目调大超时掩盖问题。
- **Kafka 分区倾斜**：发送端没指定 key 时老版本黏性分区策略已缓解；自定义分区器把热点 key 全打到一个分区是常见人为事故，监控要到分区级 lag 和流量。
- **RocketMQ 消息重复投递**：重试、Rebalance、Broker 切换都会造成重复，这是设计内行为，消费端必须幂等（业务唯一键 + 去重表/状态机校验），在 Broker 侧找「不重复」的开关是找错了地方。
- **RocketMQ 堆积报警但消费端没报错**：先查是不是单个队列被一条毒消息卡住顺序消费、或消费线程池被慢 SQL/慢调用占满。用控制台看分队列 lag 分布，定位到具体队列和消息再处理，不要无脑扩容消费者（队列数是并行度上限，扩了也不并行）。
- **事务消息回查风暴**：本地事务状态表查不到结果时 Broker 会反复回查直到上限。回查逻辑必须能凭半消息里的业务键查到确定状态，查不到要返回明确回滚而不是抛异常拖成超时。

## 7. 常见误区

- **拿 Kafka 做业务消息还要事务和延迟**：最后自研的时间轮 + 本地消息表 + 回查逻辑，复杂度和 bug 率都超过直接上 RocketMQ。
- **以为 RocketMQ 吞吐不行**：普通业务负载两边都绰绰有余，吞吐差距只在极限日志场景才显现；用压测数字给业务系统选型是拿错考卷。
- **顺序消息理解成全局有序**：两边全局有序都只有「单分区串行」一条路，吞吐直接掉到单线程量级。真实需求 99% 是局部有序（同一订单/账户内有序），按业务 key 分区就够。
- **消息中间件当存储用**：把 MQ 当长期数据仓库（尤其 Kafka 永久保留）会让清理、合规删除、数据修正全部变难；该落库落库，MQ 只管传递。
- **忽视客户端版本与 Broker 版本的匹配**：RocketMQ 5.x 的 gRPC 客户端与 4.x 协议客户端能力不同，Kafka 4.x 砍掉了老版本协议兼容，升级前都要查官方兼容矩阵。

## 8. 性能优化

- **发送端**：批量 + 压缩是最大杠杆。Kafka 调 `batch.size`/`linger.ms` 并用 zstd；RocketMQ 开启消息压缩、批量发送，发送超时和重试次数按链路重要性分级，不要全用默认值。
- **分区/队列规划**：Kafka 分区数按目标吞吐和消费并行度估算后留 2–3 倍余量，分区只增不减（减分区不支持），宁多勿少但别上万（元数据和选举开销）。RocketMQ 队列数同理，且读写队列数保持一致。
- **消费端**：并行度上限 = 分区/队列数，消费者数超过它纯属浪费；消费慢先定位是 CPU、IO 还是下游调用，批量消费/批量落库通常比加机器有效。
- **存储**：Kafka 用独立磁盘或 RAID、保留策略按磁盘水位算好；RocketMQ 刷盘方式按可靠性等级选择，CommitLog 与 ConsumeQueue 所在盘的高峰 IO 要监控。
- **堆积预案**：预先验证「临时扩分区 + 扩消费者 + 只转发不处理」的紧急消费通道，大促和活动前演练，不要等堆积了再想办法。

## 9. 版本差异

- **Kafka 2.x → 3.x**：KRaft 逐步替代 ZooKeeper（3.3 起生产可用），幂等生产者成为默认。
- **Kafka 4.x（2025 年发布）**：彻底去掉 ZooKeeper，只支持 KRaft，要求 Java 17；新消费组协议（KIP-848）正式可用，Rebalance 更平滑；4.2 起 Share Groups（队列语义）生产可用。**已持有 ZK 版老集群的要在 3.9 桥接版本上完成迁移才能升级 4.x**。
- **RocketMQ 4.x → 5.x**：架构云原生化：新增 Proxy 组件实现存算分离、客户端改走 gRPC、Pop 消费模型解决消费倾斜和慢消费者拖累；定时消息从固定等级升级为任意精度；5.3/5.4 持续补 RocksDB 存储与可观测。4.x 的客户端和运维经验大体可平移，但部署拓扑要按 5.x 重做。

## 10. 面试与自测

1. Kafka 的事务和 RocketMQ 的事务消息解决的问题有什么本质不同？
2. 为什么 Kafka 堆积不影响写入、RocketMQ 大堆积时消费追赶会变慢？从存储结构解释。
3. 业务需要「下单 30 分钟未支付自动关单」，分别用 Kafka 和 RocketMQ 怎么实现？代价各是什么？
4. 同一订单的消息必须有序，两边分别怎么配？消费者扩到队列数的 2 倍会发生什么？
5. `acks=all` 为什么还要配 `min.insync.replicas`？只配一个的风险是什么？
6. 一个平台同时用 Kafka 和 RocketMQ 是浪费还是合理？给出你的分工判断标准。

### 参考答案

1. 本质不同：Kafka 的事务定位是 exactly-once 流处理，即消费、处理、回写 Kafka 的闭环（幂等生产者加事务协调器），不是业务分布式事务；RocketMQ 的事务消息是半消息加事务回查机制，专为业务分布式事务设计，即本地 DB 事务加发消息的原子性。选错方向就是在 Kafka 上自研半个 RocketMQ，或拿 RocketMQ 去干流处理的老本行。
2. Kafka 堆积不影响写入：堆积就是文件躺在磁盘上，写入几乎不受已堆积量影响，消费端按分区线性扩，追赶速度快，是业界公认的堆积之王。RocketMQ 的 CommitLog 顺序写同样不怕堆积，但大堆积时 ConsumeQueue 页缓存命中率下降、随机读放大，消费追赶速度不如 Kafka 平滑；业务消息的正常堆积量级（分钟到小时级）完全够用，TB 级囤积不是它的主场。
3. 业务需要下单 30 分钟未支付自动关单时，RocketMQ 用 5.x 任意精度定时消息（4.x 是固定 18 个延迟等级）开箱即用，几乎零开发。Kafka 原生不支持延迟消息，要自己造时间轮、分级延迟 Topic 或外挂调度，无标准方案；代价是自研一套延迟系统的开发与运维成本，以及延迟精度与可靠性自己兜底。结论很硬：业务系统需要事务消息或任意延迟，选 RocketMQ。
4. 同一订单的消息必须有序时，Kafka 靠相同 key 落同分区实现局部有序，RocketMQ 靠同队列局部有序加顺序消息专用发送与消费模式（队列锁、顺序消费线程模型）；全局有序两边都只有单分区或单队列一条路，吞吐直接掉到单线程量级，真实需求 99% 是局部有序。消费者扩到队列数的 2 倍时，多余的消费者纯属浪费：并行度上限就是分区或队列数，超过它的消费者分不到队列、处于闲置。
5. acks=all 只保证 ISR（同步副本集）都确认；如果 min.insync.replicas 保持默认 1，ISR 可能只剩 leader 一个，leader 一挂，已确认消息照样丢。所以还要配 min.insync.replicas=2（副本因子建议大于等于 3），已确认消息才不丢。只配一个的风险：只配 acks=all 时 ISR 缩水无保护，只配 min.insync.replicas 而生产者不等确认时，发送端同样可能丢。
6. 不是浪费，是合理：判断标准是按负载与场景归类选边，而不是一个系统只许一种。数据流（日志采集、行为埋点、数仓与实时计算管道）走 Kafka，看中的是吞吐、堆积和回放；业务消息（订单、支付等交易链路异步解耦、事务消息、延迟触发、按 key 查轨迹）走 RocketMQ。翼安反诈平台就是先例：Kafka 承接话单与交易流水的数据流，RocketMQ 承接风险处置通知与工单流转。纪律是新消息先归类再选边，禁止同一业务消息双发两边，统一消息规范与监控面板。
