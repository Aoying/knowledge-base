# 编码、字符集、内存与文件系统

## 字符集

|  | 说明 |
|---|---|
| ASCII | 128 个，英文 + 符号，1 字节 |
| GBK | 中文 Windows 默认，2 字节，不兼容就乱码 |
| UTF-8 | 变长 1-4 字节，英文 1 字节中文 3 字节，互联网标准 |
| UTF-16 | Java String 内部，2/4 字节 |

## 乱码排查三问

1. 文件是什么编码存的？（`file -i xxx` 看）
2. 程序按什么编码读的？（Java `-Dfile.encoding=UTF-8`，Python `open(encoding='utf-8')`）
3. 终端/页面按什么编码显示的？

- MySQL 经典坑：`utf8` ≠ 真 UTF-8（存不了 emoji），建表用 `utf8mb4`，见 [03-数据与消息/MySQL-数据库.md](03-数据与消息/MySQL-数据库.md)。

## 大小端

- 小端（x86/ARM 默认）：低字节存低地址；网络传输统一大端（网络字节序）。
- Java 里基本碰不到，写二进制协议 / 解析 pcap 时才需要。

## 内存布局（进程视角）

```
高地址
[栈]  局部变量，向下增长，函数返回自动回收
  ↓
[堆]  new/malloc，向上增长，GC 管
[数据段] 全局 / 静态变量
[代码段] 只读
低地址
```

- 栈溢出：递归没出口；堆溢出：泄漏 / 一次加载太多数据。
- `dmesg | grep -i oom` 看谁被 OOM killer 干掉了。
## 内存对齐与填充

- CPU 按字长（64 位 = 8 字节）取内存：变量地址是"自然对齐"的倍数时一次取完，否则跨两次取，变慢。
- C 结构体：编译器自动在字段间插 padding。`struct { char a; int b; }` 不是 5 字节而是 8 字节（a 后面补 3 字节）。
- Java 对象：对象头 12 字节（64 位 + 压缩指针）+ 实例数据 + padding 补到 8 的倍数；`new Object()` 占 16 字节。小对象数组的内存开销常被低估：`Long[10000]` 是 10000 个引用（8 万字节）+ 10000 个 Long 对象。
- 经验：缓存行 64 字节；伪共享（false sharing）是高并发计数器的隐形杀手，`@Contended` 或手动 padding 隔离。


## 文件系统

- inode：存元数据（权限/大小/块指针），文件名只是目录项指向 inode。
- 软链 vs 硬链：软链是快捷方式（删源就断），硬链是同一 inode 的别名。
- ext4（Linux）/ NTFS（Windows）/ APFS（macOS）。
- `df -i` 看 inode 用量：小文件太多会先耗尽 inode，磁盘还有空间也写不进。

## 磁盘 IO 基础

- 随机 IO 比顺序 IO 慢 1-2 个数量级（SSD 缩小了差距但还在）。
- LSM 树（RocksDB/LevelDB）：写放大换读性能，顺序写 + 后台合并。
- B+ 树：读优化，MySQL InnoDB 的选择。
