# 计算机网络：TCP/IP 与 HTTP/HTTPS

## 五层模型（TCP/IP）

物理 → 数据链路 → 网络（IP）→ 传输（TCP/UDP）→ 应用（HTTP/DNS）。
OSI 七层面试背一下就行，工程按五层理解。

## TCP：三次握手四次挥手

```
SYN →          # 我想连
    ← SYN+ACK  # 好，我也想连
ACK →          # 确认
```

- 为什么三次：双方都要确认对方的收发能力，少一次就有人是"单向以为连上了"。
- 四次挥手：数据可能还没发完，FIN 要各发各的。
- 半连接队列满 = SYN Flood 攻击，`netstat -an | grep SYN_RECV` 看。

## TCP 可靠性

- 序号 + 确认 + 重传；滑动窗口流量控制；慢启动 + 拥塞避免。
- 工程体感：跨洋专线 RTT 200ms，小文件走 TCP 光握手就占大头 → 长连接/连接池。

## UDP

- 无连接、不可靠、快。场景：DNS、视频会议、游戏、QUIC（HTTP/3 底层）。
- 要可靠自己加：序号 + 重传（QUIC 就是这么干的）。

## HTTP 演进

| 版本 | 关键 |
|---|---|
| 1.1 | 长连接；管道化有队头阻塞 |
| 2 | 多路复用、头部压缩 HPACK、Server Push |
| 3 | QUIC over UDP，0-RTT，移动网络切换不掉线 |

## HTTPS / TLS

- 握手：非对称加密换对称密钥（ECDHE），之后全走对称加密（快）。
- 证书链：根 CA → 中间 → 服务器；浏览器不认自签证书。
- TLS 1.3 握手 1-RTT，1.2 是 2-RTT；Nginx 配 `ssl_protocols TLSv1.2 TLSv1.3`。
- 实战见 [04-运维与工具/Nginx.md](04-运维与工具/Nginx.md) HTTPS 章节。

## DNS

- 递归 → 根 → 顶级 → 权威，层层缓存；`dig +trace` 看全过程。
- 切流量靠 DNS（TTL 调小），但客户端/运营商缓存不听话；紧急切流用 IP 直连 + Host 头。

## 状态码速查

- 200 / 201 / 204：成功三件套。
- 301 / 302：永久/临时重定向；304：协商缓存命中。
- 400 参数错；401 没登录；403 没权限；404 没这个资源。
- 500 服务端炸了；502 网关连不上后端；503 过载/维护；504 后端超时。

## 抓包排障

- `curl -v` 看握手和头；`curl -w` 统计各阶段耗时。
- Wireshark / tshark 看三次握手和重传；`ss -s` 看 socket 统计。


## 长连接与连接池（后端必修）

- HTTP/1.1 默认 Keep-Alive：`Connection: keep-alive`，一个 TCP 连发多个请求，省掉握手开销。
- 微服务/网关调下游必须用连接池（Apache HttpClient / OkHttp 池），否则每次建连：TCP 握手 + TLS 握手 ≈ 几十 ms，高并发下端口和 TIME_WAIT 爆炸。
- TIME_WAIT 是谁的锅：主动关闭方进入 TIME_WAIT（2MSL）；服务端主动关 → 服务端堆积 TIME_WAIT。用 `ss -tan | grep TIME-WAIT | wc -l` 看。
- 缓解：客户端复用连接（池）+ 服务端 `keepalive_timeout` 调大；调内核 `net.ipv4.tcp_tw_reuse` 是最后手段。

## WebSocket vs SSE vs 长轮询

| 方案 | 方向 | 场景 |
|---|---|---|
| 长轮询 | 客户端→服务端问 | 老系统兼容，实现简单但费连接 |
| SSE | 服务端→客户端推 | 日志流、通知推送，基于 HTTP |
| WebSocket | 全双工 | 聊天、协同编辑、游戏 |

- 选型口诀：只推不用回 → SSE；要双向 → WebSocket；老古董系统 → 长轮询。
- WebSocket 握手是 HTTP Upgrade，之后走 ws 帧；Nginx 反向代理要加 `Upgrade`/`Connection` 头转发。

## TCP 粘包/拆包

- TCP 是字节流，没有"包"的概念；一次 `read` 可能拿到半条或多条业务消息。
- 解法三选一：定长协议、分隔符（如 `\n`）、**长度头 + Body**（最常用）。
- Netty 里 `LengthFieldBasedFrameDecoder` 就是干这个的；自己写 socket 一定要先处理粘包再谈业务。

## 代理：正向 vs 反向

- 正向代理：替**客户端**出网（翻墙、公司上网网关）；反向代理：替**服务端**接请求（Nginx 在后端前面）。
- 实战见 [04-运维与工具/Nginx.md](04-运维与工具/Nginx.md) 反向代理章节；内网穿透见 [11-计算机基础/Linux与Shell.md](11-计算机基础/Linux与Shell.md) SSH 端口转发。

## 抓包进阶

```bash
tcpdump -i eth0 'tcp port 8080' -w cap.pcap   # 线上抓包存文件，拉回本地 Wireshark 看
tcpdump -i any -A 'port 3306' | grep -i select # 看发往 MySQL 的 SQL（测试环境用）
```

- 怀疑网络问题时三板斧：`ping` 看通不通、`telnet ip port` 看端口开不开、`tcpdump` 看包到底发没发出去。
- TLS 加密后 tcpdump 只能看到握手和密文，排查应用层问题用 `curl -v` 或服务端日志。
