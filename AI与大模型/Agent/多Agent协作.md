# 多 Agent 协作

> 先说立场：多 Agent 不是单 Agent 的升级版，而是**最后手段**。单 Agent + 好工具能解决的问题，拆成多 Agent 只会更贵、更慢、更难调。多 Agent 的合理动机只有三个：上下文装不下（必须分工分窗口）、角色口径冲突（写的人不能自己审自己）、可并行（子任务彼此独立）。不满足这三条，别拆。单 Agent 的构成见 [Agent](AI与大模型/Agent/Agent.md)。

## 1. 核心概念

- **角色分工**：每个 Agent 只负责一类事，有自己的系统提示、工具集和输出契约。分工的切法按「认知口径」切，不按人类岗位名称切——叫「经理 Agent」没有任何工程意义。
- **编排者（Orchestrator）**：负责拆任务、派活、验收、汇总的角色，可以是另一个 LLM Agent，也可以干脆是普通代码/状态图。能用代码编排的不要用 LLM 编排：代码的分支是确定的，LLM 的分支是概率的。
- **交接物**：Agent 之间只传结构化产物（JSON、文档、状态增量），不传「聊天感觉」。交接物没有 schema，协作就是传话游戏，误差逐跳放大。

## 2. 基础知识：编排模式

| 模式 | 结构 | 适合 | 风险点 |
|---|---|---|---|
| 流水线 | A 的输出是 B 的输入，线性接力 | 步骤固定、每步口径不同（如 分析 → 校验 → 落库） | 前一步的错会被后一步当事实放大 |
| 主从（编排者-工人） | 编排者拆分并分发，工人执行后回交验收 | 子任务同质、可批量（如逐章做同一种分析） | 编排者的拆分质量决定全局 |
| 评审制 | 执行者产出，独立评审者按固定清单挑错，不合格打回 | 质量敏感、错误代价高（如矛盾检测、终裁） | 评审口径要成文，否则打回标准漂移 |
| 并行汇聚 | 多个 Agent 同时处理互不依赖的子任务，结果合并 | 大批量、子任务独立 | 合并阶段的冲突处理要预先设计 |

组合比单选常见：主从管分发、每个工人内部是小流水线、最后过一道评审——但每加一层，调试面就多一层。

### 在 LangGraph 里的落点

[LangGraph](AI与大模型/Agent/LangGraph.md) 的图模型天然承载这几种模式：每个 Agent 是一个节点（或子图），交接物就是 State 里传递的结构化字段，条件边负责打回与分支，Checkpointer 让任何一步可断点重跑。子图封装是拆分复杂度的关键手段：主图只看得见每个子图的输入输出契约，子图内部怎么折腾互不干扰。这也是有 Flowable 背景的人最顺手的映射：子图 ≈ 子流程，State ≈ 流程变量，评审打回 ≈ 驳回节点。

### 2.1 第五种模式：对等交接（Swarm / 点对点）

上面四种都有中心节点（编排者、评审者、汇聚者）或固定顺序。对等交接去掉中心节点：任何 Agent 判断任务超出自己范围时，直接调用交接工具把控制权交给另一 Agent，交接后新 Agent 接着干，不必回中心节点汇报。

- **源头**：OpenAI Swarm（2024-10 发布，定位是教学实验框架，不是生产框架；现已被 OpenAI Agents SDK 取代，但「例程（Routine）+ 交接（Handoff）」的思路延续下来）。LangGraph 侧的对应实现是 `langgraph-swarm`：`create_swarm` 建图，`create_handoff_tool` 生成交接工具，交接时返回 `Command(goto=..., graph=Command.PARENT)` 切到父图中的目标节点。
- **适用**：路由意图明确、来回少的分诊场景（客服 triage → 账单/退款专科 Agent）；任务流向事先说得清、不需要中心验收。
- **与主从模式的取舍**：主从（Supervisor）每轮多一次路由调用——supervisor 先分类再派活，控制权每步都回中心，路由更准、链路更可追踪，但更慢、更贵；Swarm 跳过中转，更快、调用更少，但路由准确率略低、且没有统一的验收点。一组同场景实测对照（Focused，客服场景，2026 年）：单域任务 supervisor 平均 4.2s / 2 次 LLM 调用 / 路由准确率 94%，Swarm 为 2.8s / 1 次 / 91%；需要交接时 supervisor 9.1s / 4 次，Swarm 5.4s / 2 次。数字是单一场景实测，不是通用结论；选型前应先写路由准确率评测再定模式。
- **边界条件（容易踩的三处）**：
  - **交接默认带走全部历史**：Swarm 与 Agents SDK 默认把完整对话历史交给下一个 Agent，低权限分诊 Agent 拾到的注入文本会原样到达高权限 Agent；要用 `handoff()` 的 `input_filter` 裁剪历史，只给下游必需的上下文。身份与授权必须来自调用方上下文（`context_variables`），在工具内复核，绝不能取模型填的参数。
  - **没有收敛点**：无中心节点意味着没有统一的打回上限与验收，乒乓循环（A 交给 B、B 又交回 A）更容易发生；必须配确定性跳数上限、循环检测、超限升级人工的出口（与 §3 的收敛条件同理，但这里更关键，因为没人兜底）。
  - **失败与成本无兜底**：Swarm 不统计各 Agent 的 token 用量、不做失败恢复，链上一个 Agent 失败整链失败；生产用要自己在外层补预算、超时与重试。
- **LangChain 当前推荐写法**：supervisor 模式推荐 tool-based 写法——每个 worker 包成工具，supervisor 以 `create_agent` 调用这些工具；`langgraph-supervisor` 库仍可用，但其 README 已指向新写法（据 LangChain 生态文档，2026-09-28 核验）。

> 来源：OpenAI Cookbook《Orchestrating Agents》、LangGraph 多 Agent 模式文档、OpenAI Agents SDK 安全说明；核验日期 2026-10-30。

## 3. 进阶知识：失控与成本风险

- **成本乘数**：N 个 Agent 不是 N 倍成本，是「每跳都要重读上下文」的连乘——每个 Agent 的输入里都含任务描述和上游产物，长链路下 token 消耗增长很快。本地部署虽然零 API 费用，但时间和显存同样是成本，账算在 [本地部署与Ollama](AI与大模型/本地部署与Ollama.md) 那一篇的框架里。
- **误差放大**：单步 95% 可靠、串 10 步只剩约 60%。对策不是「相信模型」，而是每跳设校验门（结构化校验、规则校验），让错误死在出厂前，而不是靠终端 Agent 擦屁股。
- **循环与推诿**：两个 Agent 互相打回、反复改同一处，是没有收敛条件的典型症状。每个循环必须有硬上限（最多打回 K 次）和超限出口（升级人工 / 接受当前最优并记录分歧）。
- **记忆共享的边界**：协作不等于共享一切记忆。各 Agent 共用同一份**权威状态**（见 [Agent-记忆系统](AI与大模型/Agent/Agent-记忆系统.md) 的状态外置原则）没问题，但各自的中间推测不能直接写进共享区，否则一个 Agent 的幻觉会成为全体 Agent 的「事实」。
- **可观测性先行**：单 Agent 还能通读日志，多 Agent 必须给每次交接留痕（谁、何时、输入摘要、输出摘要）。没有留痕的多 Agent 系统出问题时无法归因，等于不可维护。

## 4. 实战应用

映射到小说引擎这类创作链路（项目见 [小说创作引擎](项目沉淀/小说创作引擎.md)），一个合理的多角色设想是：生成（按世界状态上下文写章节）→ 分析（抽取状态变化、回写结构）→ 矛盾检测（对照事实与规则挑冲突）三者分工，正是「写的人不审自己」的评审制；模型分工上，高频的分析用常驻小模型、低频的矛盾检测与终裁用大模型按需调用，与 [本地部署与Ollama](AI与大模型/本地部署与Ollama.md) 的双层部署账正好咬合。此设想目前属架构演进方向，**尚未落地验证，标待验证**——落地前要先回答的问题包括打回上限、矛盾判定的成文口径、以及整链跑一章的耗时是否可接受。

## 5. 常见误区

- **按人类组织架构拆 Agent**：分工依据是口径与上下文，不是拟人。
- **用多 Agent 掩盖单步质量问题**：单步不可靠，拆多少步都不可靠；先把单步做稳。
- **编排也交给 LLM 自由发挥**：流程骨架用图/代码定死，LLM 只在节点内发挥。

## 面试与自测

1. 拆成多 Agent 的合理动机只有哪三个？不满足时应该怎么做？
2. 单步 95% 可靠、串 10 步只剩约 60%，这个误差放大问题应该怎么对付？
3. 两个 Agent 互相打回、反复改同一处，说明系统缺了什么？对策是什么？
4. 什么时候选主从（Supervisor），什么时候选对等交接（Swarm）？Swarm 交接时最容易忽略的风险是什么？

### 参考答案

1. 只有三个：上下文装不下（必须分工分窗口）、角色口径冲突（写的人不能自己审自己）、可并行（子任务彼此独立）。不满足这三条就别拆——单 Agent 加好工具能解决的问题，拆成多 Agent 只会更贵、更慢、更难调。
2. 对策不是相信模型，而是在每跳设校验门（结构化校验、规则校验），让错误死在出厂前，而不是靠终端 Agent 擦屁股；同时要记住成本也是连乘的，每跳都要重读上下文，长链路下 token 消耗增长很快。
3. 说明没有收敛条件。每个循环必须有硬上限（最多打回 K 次）和超限出口（升级人工，或接受当前最优并记录分歧），否则打回循环会一直转下去。
4. 路由意图明确、来回少、分诊式场景可选 Swarm（更快、调用更少）；需要中心验收、路由准确率优先、链路可追踪时选 Supervisor。Swarm 交接默认带走全部对话历史，低权限 Agent 拾到的注入文本会原样到达高权限 Agent，须用 input_filter 裁剪历史；身份与授权来自调用方上下文、在工具内复核，不取模型参数；同时要配跳数上限与超限升级出口，防止乒乓循环。
