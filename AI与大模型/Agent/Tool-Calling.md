# Tool Calling（工具调用）

> 让模型从「只会说话」变成「能动手」：模型负责决定调哪个工具、传什么参数，你的代码负责真正执行，再把结果喂回去。这条链路的工程质量，决定了 Agent 的可靠性上限。

## 1. 核心概念

一次工具调用的完整回合（所有框架、所有厂商，骨架都一样）：

```text
1. 你把工具清单（名称 + 描述 + 参数 JSON Schema）连同对话一起发给模型
2. 模型不直接回答，而是返回一个 tool_calls 结构：要调的工具名 + JSON 参数
3. 你的代码校验参数 → 真正执行工具（查库、调 API、算数）
4. 执行结果作为一条 tool 角色的消息追加回对话
5. 模型看着结果继续：再调工具，或给出最终答复
```

三个必须分清的事实：

- **模型从不真正执行任何东西**：它只会「提议」调用。执行权、权限、副作用全在你的代码侧——这也是安全控制能成立的前提。
- **工具清单是给模型看的说明书**：模型对工具的全部认知来自名称、描述和参数 schema（源自 Agent 篇「工具」一节）。写得含糊，模型必然用错。
- **这不是模型的特殊能力魔法**：支持 tool calling 的模型经过专门训练/微调，会在该调工具时输出结构化的调用意图；不支持的模型硬套，只会把 JSON 当普通文本吐出来让你自己猜。

## 2. 基础知识

**工具定义**：一个工具给模型看的是 function schema（Agent 篇给了完整示例，这里给最小形态）：

```json
{
  "type": "function",
  "function": {
    "name": "get_character_state",
    "description": "查某人物在指定章节时的状态（位置、伤势、已知信息）。只在需要确认人物当前状态时调用；查剧情梗概用 get_chapter_summary，不要用这个。",
    "parameters": {
      "type": "object",
      "properties": {
        "name": { "type": "string", "description": "人物姓名" },
        "chapter": { "type": "integer", "description": "章节序号" }
      },
      "required": ["name", "chapter"]
    }
  }
}
```

描述的写法是全部要点里最重要的一条：**写清什么时候用、什么时候别用，并点名容易混淆的替代工具**。参数定义越严越好——类型、必填、枚举都在 schema 里卡住，少留自由发挥空间。

**本地 Ollama 调用**（OpenAI 兼容风格的请求结构，`/api/chat` 原生接口同理）：

```python
import requests

tools = [ ... ]  # 上面的 schema 列表

resp = requests.post("http://127.0.0.1:11434/api/chat", json={
    "model": "qwen3:14b",
    "messages": [{"role": "user", "content": "第 40 章时苏晚在哪？"}],
    "tools": tools,
    "stream": False,
})
msg = resp.json()["message"]
if msg.get("tool_calls"):
    for call in msg["tool_calls"]:
        fn = call["function"]["name"]
        args = call["function"]["arguments"]  # 已是 dict（个别模型给的是 JSON 字符串，要兼容解析）
        result = dispatch(fn, args)           # 你自己的分发函数
        # 把结果以 tool 消息追加，再发一轮，模型才会给出最终答复
```

注意：拿到 tool_calls **不等于任务完成**，必须把执行结果回填再请求一轮，模型才能基于结果说话。少了这一步是新手最常见的「调用了但没下文」。

## 3. 进阶知识

**并行调用**：模型可能在一轮里提议多个互不依赖的工具调用（如同时查人物状态和时间线）。并发执行能省轮次，但写操作、或后一步依赖前一步结果的调用必须串行——是否并行由你的代码根据工具性质决定，不要无条件全并发。

**参数校验分两层**：

```python
from pydantic import BaseModel, ValidationError

class GetCharacterState(BaseModel):
    name: str
    chapter: int

def dispatch(fn_name: str, raw_args: dict) -> str:
    try:
        args = GetCharacterState(**raw_args)   # 第一层：schema/类型校验
    except ValidationError as e:
        return f"参数错误: {e.errors()}。请修正后重试。"  # 错误喂回模型自修
    # 第二层：业务校验（人物是否存在、章节是否越界）
    ...
```

- schema 对不上就**拒掉并把错误信息喂回模型**让它自己改参数重试（Agent 篇定的工程要点），而不是你的代码替它猜。
- 业务校验在代码侧：模型给的人物名不存在、章节超出范围，这类错误同样以文本结果返回，让模型换个查法或向用户澄清。

**失败处理总原则**：

- 工具执行异常 → 不要抛给最外层崩掉整个会话；把「工具名 + 失败原因」作为 tool 消息返回，模型多数能换参数或换路径重试。
- 重试必须有**预算**：同一工具连续失败 N 次（建议 2–3 次）就停，把问题上抛给人或走降级路径，避免模型换个姿势无限重试烧 token。
- **幂等**：模型重试是常态，工具被执行两遍不能产生两份副作用。写类工具用业务键去重（请求 ID、章节+版本），查询类天然幂等不用管。

## 4. 原理剖析

- **模型怎么知道有工具**：工具清单被序列化后拼进请求的专门字段（或等价的提示模板段），模型在训练中学过「看到这种清单 + 用户意图匹配时，输出调用结构而不是自然语言」。所以模型与接口模板必须配套：Ollama 里模型卡片标注支持 tools 的才真正可靠，聊天模板（chat template）不对，输出格式会整体跑偏。
- **约束解码与严格模式**：部分云端接口支持 strict 模式，强制参数严格符合 schema；本地链路一般没有这层保障，因此本地 Agent 的参数校验代码要写得比调云 API 时更认真。
- **工具结果的地位**：tool 消息和其他上下文一样只是文本。结果里夹带的文字（网页内容、第三方返回）**可能包含提示注入**，模型未必能分辨——敏感动作不能只凭工具返回就放行，要在代码侧复核。

## 5. 实战应用

落到小说引擎的抽取 Agent：

- 工具集按任务裁剪：抽取任务只给「查人物、查时间线、查伏笔、写抽取结果」四个工具，不要把全库二十个工具一股脑塞进去（工具越多，选错率越高，清单本身也吃 token）。
- 写库工具（写抽取结果）单独设确认策略：批量落库前先dry-run 出统计（新增/修改条数），异常比例过高就停下报警。
- 二层模型分工：常驻 14B 模型负责常规抽取的工具调用；终裁环节换大模型时，**工具清单保持一致**，换的只是推理核心，这样两层的结果可对比、可回放。

**危险操作确认清单**（ Agent 篇定的红线，具体化到工具层）：删数据、对外发送、花钱、批量改写——这四类工具执行前必须人工确认，确认逻辑写在分发层，不依赖模型自觉。


## 工具失败恢复：先分类，再选恢复手段

原篇 §3 定的是总原则，本节补的是操作层：失败分哪几类、每类走哪条恢复路、预算怎么算到头。恢复手段按代价从低到高排，够用就停，不要一上来就上抛给人，也不要在低层死磕。

### 失败分类：同一种“失败”，恢复动作完全不同

| 失败类型 | 典型表现 | 首选恢复动作 |
|---|---|---|
| 参数错误 | schema 校验失败、业务校验失败（人物不存在、章节越界） | 把错误喂回模型自修（§3 已定），不重试原参数 |
| 工具异常 | 下游服务报错、返回格式非预期、依赖不可用 | 换参数或换工具重试；偶发异常可原样重试一次 |
| 超时 | 工具迟迟不返回，不知道执行成没成 | 先查状态再定，禁止盲重试（见“结果未知”一节） |
| 权限拒绝 | 无权调用、被确认拦截、配额用尽 | 不重试、不绕过，澄清或上抛给人 |
| 结果不可解析 | 返回了，但字段缺失、格式损坏、无法落到下一步 | 降级解析（取可用字段+标注缺失）或换个查法 |
| 循环打转 | 同一参数反复调同一工具 | 停并换路径；检测机制见 §6，本节不重复 |

分类先行是因为恢复动作互斥：参数错误重试原参数必败，权限拒绝换个姿势重试是绕过安全边界，超时盲重试可能造出两份副作用。分不清类型就选不对手段。

### 恢复手段分层：按代价从低到高

1. **原样重试**：只用于瞬时故障（偶发异常、限流）。同一工具连续失败 2–3 次就停——沿用 §3 的预算口径，本节不另定数字。
2. **换参数 / 换工具**：参数错误改参数，工具异常换等价工具。换的前提是失败原因已明确，否则换也是盲试。
3. **降级**：拿不到完整结果时退而求其次——只读替代、缓存的旧结果（须标注时效）、部分结果加缺失标注。降级结果进上下文时必须带“已降级”标记，否则模型会把残缺结果当完整事实用。
4. **澄清追问**：缺关键信息、意图边界不清时问用户，而不是替用户猜。追问要具体（缺哪个字段、两个选项选哪个），笼统的“请补充信息”等于把问题踢回给用户。
5. **人工确认 / 上抛**：危险操作（§5 的确认清单）、预算耗尽、权限拒绝，一律上抛。上抛时带上已试过的手段和失败记录，不要只抛一句“失败了”。
6. **中止并保留现场**：不可恢复、或继续执行有害时停下，保留轨迹和中间结果供人事后查，不要为“把任务跑完”而硬跑。

### 重试预算：次数、退避、总耗时三条线

§3 定了次数线（连续失败 2–3 次停），完整预算还有两条线：

- **退避**：失败后不要立即连发。瞬时故障连发只会把下游打得更糟，退避（间隔逐次拉长）是标准做法；退避期间预算照计，不因“等了一会儿”重置次数。
- **总耗时与步数上限**：单步工具设超时，整任务设总时限和总步数上限（Agent 篇“超时和步数上限要双设”）。次数没用完但总时限到了，同样停——无限重试的变体是“每次换个参数无限试”，步数上限防的就是这个。
- **预算分两层计**：单工具连续失败次数和整任务累计失败次数分开算。单工具没超预算，但整任务失败已多，说明不是某个工具的问题，是任务本身或模型决策跑偏，该停下复盘而不是继续试下一个工具。

预算耗尽不是报错走人：耗尽后按分层走降级或上抛，并把“已试手段 + 失败原因”写进轨迹，留给下一节的排障用。

### 幂等补全：超时后“结果未知”是最难的情形

§3 的业务键去重是事前防重，解决“执行两遍”的问题；超时补的是事后情形——工具可能已执行、只是回包丢了，这时连“成没成”都不知道：

- **先读后写**：重试写操作前，先读状态再决定——查订单/记录/版本号是否存在。已存在就返回旧结果，不再执行；不存在才补写。
- **读不到状态时不上盲重试**：状态查不到（读接口也没有），宁可上抛给人裁决，也不要赌一把重执行。写类工具最忌“可能已执行”状态下的第二次执行。
- **查询类不受此限**：查询天然幂等，超时直接重试即可，不用先查状态。

一句话收口：**失败恢复的顺序是分类 → 按层选手段 → 预算内执行 → 结果写进轨迹**。跳过分类直接重试，是原篇 §7 “失败了就无限自动重试”的另一种写法。

## 执行轨迹：记什么、用来干什么

Agent 篇给轨迹下过定义（一次任务完整的 Thought / Action / Observation 序列日志，没有轨迹出问题无法复盘），本节补 Tool-Calling 侧的记录口径：一条轨迹记哪些字段、轨迹分几级、三个用途各自怎么用。

### 一条轨迹记什么

每一步记一行，字段固定，不要想到什么记什么：

| 字段 | 记什么 | 为什么必须有 |
|---|---|---|
| 步骤号 | 第几步 | 定位跑偏点、算步数预算 |
| 模型决策 | 本步的意图摘要（想查什么、为什么调这个工具） | 只看工具名不知道模型为什么调它 |
| 工具名 | 实际调用的工具 | 归因到工具 |
| 参数摘要 | 关键入参（非全文） | 复现时能重放同一步 |
| 返回摘要 | 成功/失败 + 关键字段或错误原因 | 失败归因的第一现场 |
| 耗时 | 本步耗时 | 超时、慢步骤定位 |
| 错误码 / 原因 | 失败类型（按上一节分类） | 恢复手段选型、失败统计的口径 |
| 重试次数 | 本步已重试几次 | 预算审计 |

记摘要不记全文：参数和返回的全文进原始日志，轨迹只记可读摘要。全文塞进轨迹，轨迹本身就成了上下文负担——与 §7 “返回值不要整坨塞回”同一个道理。

### 轨迹分级：完整轨迹落盘，上下文内只留最近 N 步

- **完整轨迹**：全量步骤落盘保存，是排障和审计的权威记录，不截断。
- **上下文内轨迹**：模型可见的部分只留最近 N 步，旧步截断或摘要压缩（管理方法见 Agent 篇“基础知识补强”）。长任务里模型不需要、也不应该看到全部历史步骤。

两级分开的好处：排障时有全量可查，运行时上下文不被历史步骤撑爆。

### 轨迹的三个用途

- **复现排障**：按步骤号重放，定位“哪一步开始跑偏”——是模型决策错（选错工具）、参数错，还是工具本身返回错。三类根因的修法完全不同，没有步骤级记录只能靠猜。
- **效果评估**：评估时逐题明细的原料就是轨迹：成功率、失败归因到步骤、重试次数分布，都从轨迹里统计。评估口径见 [模型评测方法](AI与大模型/模型评测方法.md)，本节不展开评测框架。
- **审计**：危险操作（§5 的确认清单）留痕——谁确认的、调了什么工具、参数是什么、结果如何。事后追责问“这条数据怎么被删的”，轨迹就是答案。

### 轨迹里的敏感信息：脱敏后记，轨迹本身按敏感数据管

参数和返回里常带密钥、token、个人数据：记轨迹前先脱敏或截断（密钥只留后几位标识、长文本截断），不要把原始秘密写进轨迹文件。轨迹文件本身按敏感数据管理——访问控制、留存期——否则排障用的日志就成了新的泄露口。工具回传内容的分级与隔离是安全篇的活，本节只定轨迹侧的脱敏底线。

## 6. 疑难杂症

- **模型该调工具时却直接编了个答案**：先查三件事——模型是否真的支持 tool calling；请求里 tools 字段有没有传对；描述里有没有写清触发条件。本地小模型对长清单的遵循度差，削减工具数往往立刻见效。
- **参数 JSON 解析失败**：个别模型把 arguments 给成字符串而非对象，解析层要兼容两种形态；仍失败就把解析错误喂回让它重出，不要自己正则硬抠。
- **参数幻觉**：模型编造不存在的人物名、订单号。根源是上下文里没给足线索——在系统提示里给出合法取值范围（或先调一个「列出候选」工具），比事后校验更治本。
- **工具循环打转**：模型反复用同样参数调同一工具。多为工具返回的信息不足以推进（如只回「失败」不回原因）；返回信息写具体 + 分发层做「相同入参重复调用」检测，双管齐下。
- **本地模型时好时坏**：同一模型不同量化/模板表现差异大；固定一套已验证的「模型 + 模板 + 参数（温度）」组合，升级时用固定测试集回归，不要裸奔上线。

## 7. 常见误区

- 描述只写功能不写边界：模型会在不该用的场合乱调、该用时不敢用。反例场景必须写进描述。
- 返回值把数据库大对象整坨塞回：撑爆上下文且全是噪声。只返回模型下一步决策需要的字段。
- 把工具调用当 RPC 用：它是「模型提议、代码裁决」的协作协议；校验、权限、确认都是代码的责任，不是模型的自觉性能替代的。
- 失败了就无限自动重试：没有预算的重试是烧钱和放大事故的标准姿势。
- 一次给几十个工具还指望选得准：按任务分集是基本功，不是优化项。

## 8. 性能优化

- 工具清单长度直接换算成每轮的固定 token 成本，长会话里尤其明显：按任务动态组装清单，而不是全量常驻。
- 只读查询类工具可并行、可缓存：同一会话内相同入参的查询结果短时复用。
- 让工具一次返回够用的信息（人物状态 + 所在时间线片段），减少模型为了拼图反复多轮调用。
- 模型侧：工具调用密集型任务对模型「指令遵循」的要求高于文采，选型时用真实工具集做成功率测试，不要只看通用榜单分数。

## 9. 版本差异

- 各家接口的请求/返回字段名不完全一致（OpenAI 的 `tool_calls`、Anthropic 的 `tool_use` 内容块、Ollama 原生 `/api/chat` 的 `tool_calls`），抽象一层自己的分发接口，换模型时只改适配层。
- Ollama 侧：支持工具调用的模型清单以官方模型库标注为准；同一模型的新旧版本模板可能不同，升级 Ollama 或模型后要回归工具调用测试。
- MCP 出现后工具多了一条「被发现」的路径，但发现≠调用规范变化：最终落到模型面前的仍是同一套 schema 与调用回合（见 MCP 篇）。

## 10. 面试与自测

1. 完整描述一次 tool calling 回合的五步，并指出每一步的责任方（模型/代码）。
2. 参数校验为什么要分 schema 层和业务层？校验失败后为什么把错误喂回模型而不是直接抛异常结束？
3. 哪四类工具必须人工确认？确认逻辑应该写在哪一层，为什么不能靠模型自觉？
4. 工具被重复执行会产生副作用，你在工具设计上如何防？（答：幂等键/业务键去重）
5. 模型不调工具直接编答案，你的排查顺序是什么？

### 参考答案

1. 五步：①代码把工具清单（名称+描述+参数 JSON Schema）连同对话发给模型（责任方：代码）；②模型不直接回答，返回 tool_calls 结构（工具名+JSON 参数）（责任方：模型）；③代码校验参数后真正执行工具（责任方：代码）；④执行结果作为一条 tool 角色消息追加回对话（责任方：代码）；⑤模型看着结果继续：再调工具，或给出最终答复（责任方：模型）。关键点：模型从不真正执行任何东西，它只提议调用。

2. schema 层卡格式问题（类型、必填、枚举），业务层卡语义问题（人物是否存在、章节是否越界），两类错误性质不同，混在一层会互相掩盖。校验失败要把错误喂回模型而不是直接抛异常结束：让模型自己修正参数重试，能保持会话连续、利用模型的自修能力；直接抛异常等于放弃整轮任务。但重试必须有预算，同一工具连续失败 2–3 次就停，走降级或上抛给人。

3. 四类：删数据、对外发送、花钱、批量改写。确认逻辑必须写在分发层（代码侧）：模型只提议、不执行，校验、权限、确认都是代码的责任；靠模型自觉等于把裁决权交给不可信方——模型可能被注入诱导，也可能在描述不清时误判。分发层是模型意图与真实副作用之间唯一的裁决点。

4. 写类工具按业务键去重：请求 ID、章节+版本这类业务键，执行前先查重，已执行过的直接返回旧结果，不产生第二份副作用；查询类天然幂等，不用管。因为模型重试是常态，工具被执行两遍是预期行为而非异常，防重必须做在工具设计里，不能指望模型不重试。

5. 按正文排查顺序：①模型是否真的支持 tool calling（模型卡片标注为准）；②请求里 tools 字段有没有传对；③描述里有没有写清触发条件；④本地小模型对长清单遵循度差，削减工具数往往立刻见效。另外两类常见根因顺带查：参数幻觉（上下文里没给合法取值范围，或先调「列出候选」工具）；工具循环打转（返回信息不足以推进，或分发层没做相同入参重复调用检测）。

## 11. 关联知识

- Agent：Tool Calling 是 Agent 四部件中「工具」的具体机制，循环控制在 Agent/LangGraph 侧。
- LangGraph：ToolNode 把第 2 节的手写回合标准化；自己先写过一遍裸循环，再用框架不迟。
- MCP：工具的另一种供给方式——通过协议发现的工具，最终仍以同样的 schema 进入本篇的调用回合。
- 前置知识：JSON Schema 基础、HTTP 接口调用；延伸：结构化输出（让模型直出 JSON）与工具调用的取舍。
