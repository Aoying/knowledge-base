# Agent

> 每晚 20:30 自动补充完善。

## 核心概念

一个 Agent = **LLM（推理）+ Tools（行动）+ Memory（记忆）+ 循环控制**。

最经典的循环是 **ReAct**：Thought（思考下一步）→ Action（调工具）→ Observation（看结果），循环直到任务完成。绝大多数 Agent 框架都是这个循环的变体。

## 四个关键部件

### 1. 推理（LLM）
负责做决策：下一步调哪个工具、传什么参数。本地可用 Ollama 跑支持 tool calling 的模型（如 qwen3 系列），云端按需用大模型做复杂裁决。**二层架构**是实用套路：小模型常驻处理高频常规任务，大模型按需处理复杂推理——和你"14B 常驻 + 30B 按需"的规划一致。

### 2. 工具（Tools / Tool Calling）
- 每个工具给 LLM 的是一个 **function schema**：名称、一句话描述（写清楚触发条件）、参数定义。
- 工程要点：参数校验（schema 对不上就拒掉重问）、错误重试（工具报错把报错信息喂回 LLM 让它自己修参数）、最小权限（工具只能做它该做的事）。
- 危险操作（删库、发消息、花钱）必须走人工确认，不能让 Agent 自己决定。

### 3. 记忆（Memory）
- **短期**：当前对话的上下文窗口，放最近的 Thought/Action/Observation。
- **长期**：结构化存（SQLite/向量库）——实体、关系、事件、待办。你的小说引擎 Entity/Relation/Event/Timeline 就是长期记忆的一种实现。
- 经验：长期记忆的关键不是"存得多"，而是"检索得准"——检索策略（关键词 + 向量混合）比存储格式更重要。

### 4. 循环控制
- 什么时候停：任务完成 / 步数上限 / LLM 明确说做完了。三者缺一不可，否则 Agent 会空转烧 token。
- **Human-in-the-loop**：关键节点停下来问人，确认后再继续。你的"高风险操作先确认"就是这个思想。

## LangGraph（状态机式 Agent 框架）

核心只有四个概念，适合你这种有后端/流程引擎背景的人：

- **State**：流程中传递的状态对象（类似 Flowable 的流程变量）。
- **Node**：一个处理步骤（调 LLM、调工具、写库）。
- **Edge**：步骤之间的流转，支持条件分支（类似排他网关）。
- **Checkpointer**：状态持久化，支持断点续跑和"回到某一步重来"——这是 LangGraph 相对裸写循环最大的工程价值。

心智映射：Node≈服务任务节点，Edge≈顺序流/条件流，State≈流程变量，Checkpointer≈流程实例持久化。有 Flowable 经验学这个很快。

## MCP（Model Context Protocol）

一句话：**Agent 调外部能力的统一插头标准**。Server 提供 tools/resources/prompts，Client（你的 Agent）按标准去发现和调用。不用再为每个 API 手写一套对接胶水。

## Hermes Agent

你在研究的方向。Hermes 系模型以 tool calling / function calling 见长，适合做本地 Agent 的推理核心。NVIDIA 官方把 nemotron 系列接入了 Hermes、OpenClaw 生态——本地 Agent 这条线可以持续跟。

## 落到你的项目

- 小说引擎的 EventEngine → 可以 Agent 化：把"抽取实体/关系/事件"做成带校验和重试的 Agent 循环，而不是一次性 LLM 调用。
- 沙盒推演 → 本质是"分支 + 并行跑多个 Agent + 对比结果"，LangGraph 的分支能力正好对上。
- 冲突检测 → 二层架构：小模型常驻扫全量章节，大模型按需做最终裁决。


## Agent 设计模式（四种常用）

1. **ReAct**：Reason + Act 循环，"想一步 → 调一个工具 → 看结果 → 再想"。最通用，LangChain 默认就是这个。
2. **Plan-and-Execute**：先让 LLM 出完整计划，再一步步执行，执行偏离时重计划。适合长流程（如你的小说多章生成）。
3. **Reflection**：做完自己评审一遍，"这段剧情有没有矛盾？"，有问题就改。对应你的 ChapterAnalysisService → 修正循环。
4. **Multi-Agent**：分工，一专多能不如多专：抽取 Agent、矛盾检测 Agent、文风 Agent 各干各的，最后汇总。LangGraph 的 supervisor 模式就是干这个的。

- 小说引擎现在用的是"单 Agent + 结构化输出"，下一步可以试 ReAct（抽取时主动查时间线）+ Reflection（生成后自检矛盾）。


## Human-in-the-Loop（人机回路）

Agent 自主跑不等于没人看，关键节点必须有人拍板：

1. **计划确认**：Plan-and-Execute 出完计划先给人看，OK 才执行（小说引擎生成大纲时用）。
2. **高风险工具确认**：删数据、发请求、写库这类操作执行前弹窗（Muse 的审批卡就是这个思想）。
3. **结果抽查**：抽取 Agent 跑完 50 章，人工抽 5 章看 JSON 质量，不对就回炉。

- 落到小说引擎：章节生成（高风险）→ 人确认；章节分析抽取（低风险）→ 自动跑 + 抽查。
- 别走极端：全自动=翻车没人知道，全人工=Agent 白做了。

## 记忆系统设计（三层）

1. **工作记忆**：当前窗口内的上下文，用完即弃（就是 prompt 里那堆）。
2. **情景记忆**：历史会话/章节的摘要，RAG 按需召回（小说引擎的 Chapter 摘要就是）。
3. **语义记忆**：长期事实库，"林溯怕黑""源石能改记忆"，结构化存（StoryFact 表）。

- 写入：每次会话结束抽 3-5 条事实入库，去重（embedding 判重）。
- 读取：先语义（事实）→ 再情景（相关章节摘要）→ 拼进工作记忆，三层漏斗。
- 遗忘：事实带 `confidence`，被 contradict 次数多了降权，定时清 <0.3 的。
- claude-mem（见 Agent-开发-Skills 第 5 条）就是这套思想的现成实现。

## 基础知识补强

### 核心概念与术语

- Agent（智能体）：能自己决定下一步做什么、并通过行动影响环境的程序；核心不是模型大，而是"决策权在程序手里"。
- 聊天机器人 vs 工作流 vs Agent：聊天机器人只答不做；工作流的每一步是人预先写死的；Agent 的步骤是运行时由模型决定的。
- 环境（Environment）：Agent 活动范围的统称——文件系统、数据库、网页、业务系统都是环境。
- 动作（Action）：Agent 能对环境做的事，一般等于它可调用的工具集合；动作空间就是这个工具清单。
- 观察（Observation）：动作执行后环境返回的结果，被喂回模型作为下一步决策的依据。
- 轨迹（Trace）：一次任务完整的 Thought/Action/Observation 序列日志；没有轨迹，出问题无法复盘。
- 系统提示（System Prompt）：开场就定死的角色、规则和边界，全程优先级最高，用户中途的话改不动它。
- 上下文工程：决定每一步往上下文里放什么、不放什么的手艺，和提示工程的区别是它管的是动态组装而非单句措辞。
- 护栏（Guardrail）：包在 Agent 外面的规则层——输入检查、输出检查、权限拦截，与模型本身无关。
- 编排器（Orchestrator）：在多 Agent 或复杂流程里负责分发任务和汇总结果的角色，可以是代码，也可以是一个专门的模型。

### 基础知识与用法

先用感知-决策-行动循环给所有 Agent 建模，这是最稳的心智框架：

```text
感知：把环境现状整理成模型能读的文字（状态摘要、工具返回）
决策：模型在给定目标和现状下，挑下一个动作
行动：代码真正执行动作，拿到结果
循环：结果成为新的感知材料，直到目标达成或触发停止条件
裸写 Agent 的本质就是这个 while 循环加停止条件，框架只是把它工程化。
```

自主程度是一条谱系，选档位先于选框架：

```text
低自主：固定步骤，模型只填参数            （结构化抽取、表单填充）
中自主：模型在限定工具集内自己选下一步    （多数实用 Agent 在这档）
高自主：模型自己拆任务、选工具、纠偏      （研究型 Agent，护栏要最重）
档位每升一级，不确定性、成本和翻车半径都涨一级，先从低档做起。
```

一个工具定义的完整长相（JSON 示意），原文讲了要点，这里补实体：

```json
{
  "name": "query_order",
  "description": "按订单号查询订单状态。只在需要确认某笔订单当前状态时调用，不要用它查用户信息。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "description": "订单编号" }
    },
    "required": ["order_id"]
  }
}
```

- 描述写给模型看：重点写"什么时候用、什么时候别用"，比写实现细节重要得多。
- 参数定义越严越好：类型、必填、枚举值都在 schema 里卡住，少给模型自由发挥的空间。
- 返回值也要设计：返回模型能直接用的精简结果，不要把数据库原始大对象整坨塞回去。

上下文管理的三个基础手法（窗口有限，迟早要用）：

- 截断：只保留最近 N 步轨迹，简单粗暴，适合短任务。
- 摘要压缩：把旧轨迹总结成一段话替换原文，信息有损但能续跑长任务。
- 外置笔记：中间结论写进外部存储，需要时再检索回来，本质是把记忆和上下文分开管。

Agent 的成本与效果，立项前先算三本账：

```text
成本账：步数 × 每步 token，失控的循环是成本失控的主因
效果账：任务成功率（端到端跑完且结果对的比例），比单步准确率更有意义
延迟账：每步都要等一次模型生成，十步任务天然慢于一次问答
评估方法：备一批固定测试任务，每改一版提示或工具就整批重跑，看成功率涨跌。
```

### 关键机制速览

- 模型并不知道工具的存在与否之外的世界：它看到的一切都是你拼给它的文字，拼错了它就在错误的前提下认真推理。
- 工具调用结果的可信度分级：自家代码的确定性返回可信；外部网页、第三方接口返回的文字一律当不可信输入处理。
- 幂等设计对 Agent 尤其重要：模型重试一次是常事，工具执行两遍不能产生两份副作用（重复下单、重复发信）。
- 超时和步数上限要双设：单步工具可能挂死，整体循环也可能打转，任何一层缺失都会放大成事故。
- 沙盒思维：给 Agent 的文件、网络、数据库权限按任务现开现收，别图省事长期挂着大权限。
- 确定性环节尽量用代码不用模型：格式校验、数值计算、权限判断写成普通函数，模型只做真正需要语义判断的部分。
- 可观测性先于优化：先有完整轨迹日志，才能知道它在哪一步开始跑偏；没有日志的调优等于蒙眼开车。
- 失败恢复的默认姿势：失败步可重试、已完成步不重跑、整体可从检查点续——和批处理作业的断点续跑是同一套思想。

### 新手易错点

- 工具一股脑全给：工具越多模型越容易选错、描述互相干扰；按任务分工具集，一次只给它用得上的。
- 工具描述只写功能不写边界：模型会在不该用的场合乱调，或者该用的时候不敢用，描述里必须有反例场景。
- 拿模型输出直接拼命令或查询语句执行：输出是不可信文本，未经校验就执行等于把注入风险请进门。
- 不验工具返回值就往下走：工具返回错误或空结果时模型常会假装成功继续编，每步都要做结果校验。
- 没有轨迹日志还想调优：只看到最终答错，不知道错在哪一步，只能靠猜改提示，越改越乱。
- 把长任务全塞进一个 Agent 硬跑：任务越长越容易目标漂移，该拆成"计划、执行、验收"分段，段间留确认点。
- 测试只测顺利路径：真实翻车都在异常分支——工具超时、返回空、模型格式跑偏，测试用例要专挑这些场景造。
