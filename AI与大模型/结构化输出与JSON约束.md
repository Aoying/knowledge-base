# 结构化输出与 JSON 约束

> 只要输出要进程序，目标就不是「模型大概会给 JSON」，而是「给不出合规 JSON 就当场失败、可重试、可定位」。约束分三层：提示层（求它给）→ 解码层（逼它给）→ 程序层（验它给的）。三层都上，才叫工程方案。提示怎么写见 [Prompt-工程](AI与大模型/Prompt-工程.md)，本篇讲约束与兜底。

## 1. 核心概念

- **JSON Mode**：接口级开关（如 OpenAI 兼容接口的 `response_format: {"type": "json_object"}`、Ollama 的 `format: "json"`）。作用是保证输出**语法**是合法 JSON，仅此而已——字段缺没缺、类型对不对，它不管。
- **Schema 约束输出**：把 JSON Schema 直接给到接口（Ollama 原生接口支持在 `format` 里传 schema），解码时按 schema 限制可选 token，能保证字段与类型结构合规。这是目前本地链路里最强的一层约束，支持程度因接口而异，接入前实测。
- **程序侧校验**：拿到输出后用 schema / pydantic 再验一遍。解码层保证的是「形状」，业务规则（如「引用的实体必须存在」）只能在这一层查。
- 与 [Tool-Calling](AI与大模型/Agent/Tool-Calling.md) 的关系：tool_calls 的参数就是一次结构化输出，约束思想完全相通；能用工具调用承载的结构化任务，优先用工具调用，白拿一层框架校验。

## 2. 基础知识：一条可靠的解析管线

```text
请求（低温度 + JSON mode / schema）
  → 提取（剥掉代码块围栏、前后闲话，只取 JSON 主体）
  → json.loads 解析
  → Schema / pydantic 校验字段与类型
  → 业务校验（枚举值、外键存在性、数值范围）
  → 任一环节失败：带着错误信息重试（见第 3 节）
```

提取环节的现实主义：即使开了 JSON mode，也要防模型偶尔包一层 ```json 围栏或加一句「好的，结果如下：」。提取逻辑（找第一个 `{` 到最后一个 `}` 做兜底切片）要写，但要清楚这是兜底，不是正道——正道是解码层约束 + 低温度。

Schema 设计的三条经验：

- **字段宁少勿多**：每个字段都是模型要分心填的东西，非必要不加；能由程序推导的字段（如序号、时间戳）不要让模型填。
- **枚举收口**：状态、类型这类字段一律 `enum` 列死候选值，自由文本是最常见的口径漂移来源。
- **给「不知道」留合法出口**：允许 `null` 或空数组，并明确语义；没有出口，模型会用编造来填满必填字段。

## 3. 进阶知识：解析失败的重试策略

重试不是把同一请求再发一遍，那只是碰运气。有效的重试是**把错误喂回去**：

```python
for attempt in range(MAX_RETRY):  # 上限一般 2–3 次
    raw = llm_call(messages)
    try:
        data = parse_and_validate(raw)   # 解析 + schema + 业务校验
        return data
    except ValidationError as e:
        messages.append({"role": "assistant", "content": raw})
        messages.append({"role": "user",
            "content": f"上面的输出不符合要求：{e}。只修正格式问题，重新输出完整 JSON，不要解释。"})
raise StructuredOutputError(...)  # 超限：落盘原始输出 + 报错，人工介入
```

要点：

- **错误信息要具体**：哪个字段、什么问题、期望什么。把校验器的原始报错给模型，比「格式不对，请重试」有效得多。
- **只修格式不改内容**：重试提示要防止模型借重试之机把内容也重写一遍——对抽取类任务，这等于二次幻觉。
- **超限必须硬失败**：重试耗尽就抛错并保存原始输出供排查，绝不允许「解析失败就当空结果继续跑」。静默吞掉坏输出，下游会出现无源之水的数据，这在长链路里是最难查的污染。
- 温度：重试时保持低温度；靠升温度「换个运气」对格式问题基本无效。

## 4. 实战应用

小说引擎的章节分析链路就是这条管线的使用方（项目全貌见 [小说创作引擎](项目沉淀/小说创作引擎.md)）：LLM 分析一章后输出 entities / entity_changes / relations / events / facts / rules 六类结构，直接回写 SQLite。这类「输出即入库」的场景里，业务校验尤其关键——比如 entity_changes 引用的实体必须已在 Entity 表中存在、relations 两端必须可解析，查不过就不许落库，宁可整章分析失败重跑，不让半份脏数据进去。长篇是几百章累积的，一章的脏数据会在几十章后才以矛盾形式爆出来。

## 5. 常见误区

- **开了 JSON mode 就以为万事大吉**：它只管语法，不管字段。
- **用正则从自然语言里「抠」数据**：能约束输出就别事后抠，抠取逻辑会随模型措辞漂移不断打补丁。
- **校验失败静默返回空**：把失败伪装成「没有数据」，是长链路里最贵的 bug 形态。
- **Schema 写得比业务还复杂**：嵌套过深、字段过多会反噬模型准确率；先拆任务，再简化 schema。

## 小技巧与冷知识

【小技巧】`additionalProperties: false` 要显式写在每个对象上：OpenAI 的 Structured Outputs 强制要求每个对象都加这一项，否则请求会被拒；llama.cpp 把 schema 转文法时默认也是 false。它的作用是堵住“模型多吐一个没定义的字段”——不写的话，解码层拦不住多余字段，只能靠程序层事后剔除，等于白白浪费一层约束。

【冷知识】JSON mode 和 Structured Outputs 不是一回事：OpenAI 在 2024 年 8 月 6 日推出 Structured Outputs，`response_format` 用 `{"type": "json_schema", ...}` 加 `strict: true`，保证输出按 schema 来；原来的 `json_object` 只保证语法合法，不管字段。原文只提了 json_object 这一档，本地链路里 Ollama 的 `format` 传 schema 走的是 Structured Outputs 同类思路，选接口时要分清自己要的是“合法 JSON”还是“合规 JSON”。

【冷知识】本地链路的 schema 约束底层是文法：llama.cpp 会把 JSON Schema 先转成 GBNF 文法，再在采样时逐个 token 限流，不合规的 token 根本进不了输出。但它只支持 JSON Schema 的一个子集，不支持的关键字会被静默跳过——写 schema 前先看转文法的支持清单，别以为 schema 里写了什么就一定生效了。

【小技巧】schema 里的 `description` 是写给模型的字段说明，不是给人看的注释：每个字段写清“从原文抄原词、不要改写”“只填章节里出现过的实体”，格式和内容能同时收住。description 空着等于白白浪费一次免费的约束机会，模型填字段时只能靠字段名猜口径，猜错的概率比有说明时高得多。

【小技巧】Python 的 `json.loads` 默认会悄悄吞掉 NaN：严格 JSON 里 NaN、Infinity、尾逗号都不合法，但 `json.loads('{"a": NaN}')` 默认不报错、直接解析成 `float('nan')`。入库前要么关掉宽容解析，要么在校验层拒掉 NaN，否则一个非法值就这么进了 SQLite，后面查出来时已经不知道是哪一章的输出了。

【小技巧】校验层要开 strict，别让类型“宽容”过去：字符串 `"123"` 填进 int 字段，宽松校验会悄悄转成 123，类型漂移就是从这种小事开始的。pydantic 严格模式下 `"123"` 填 int 字段会直接报错，宁可触发一次重试，也不要让一次悄悄转换把脏类型带进库。

【小技巧】重试时只带最后一次的错误，别把历次错误全堆进去：原文说把错误喂回去，但错误越堆上下文越乱，模型越容易修偏——前一次的错和这一次的错可能根本不是同一个字段。每次重试只给最新一次的字段、问题、期望，历史错误只留在日志里供人查，不进提示词。

【冷知识】模型常犯的错，都是 JSON 语法本来就不允许的东西：JSON 没有注释、没有尾逗号、key 必须用双引号，单引号、`NaN`、尾逗号全是非法语法。`json.loads` 报错会直接报出行列号，排障先看报错位置再决定是修提取逻辑还是重试，别一上来就怀疑模型“又幻觉了”——很多时候只是语法层面的小毛病。

## 面试与自测

1. JSON mode 保证什么、不保证什么？原文说本地链路里最强的一层约束是什么？
2. 原文说有效的重试不是把同一请求再发一遍，那是什么？重试耗尽后必须怎么做？
3. Schema 设计的三条经验是什么？为什么要给“不知道”留合法出口？

### 参考答案

1. JSON mode 是接口级开关（如 OpenAI 兼容接口的 `response_format: {"type": "json_object"}`、Ollama 的 `format: "json"`），作用是保证输出语法是合法 JSON，仅此而已——字段缺没缺、类型对不对，它不管。本地链路里最强的一层约束是 Schema 约束输出：把 JSON Schema 直接给到接口（Ollama 原生接口支持在 `format` 里传 schema），解码时按 schema 限制可选 token，能保证字段与类型结构合规，但支持程度因接口而异，接入前要实测。
2. 有效的重试是把错误喂回去：解析 + schema + 业务校验任一环节失败后，把校验器的原始报错（哪个字段、什么问题、期望什么）附在重试提示里发回去，只修正格式问题、重新输出完整 JSON，不要解释；重试上限一般 2–3 次，且重试时保持低温度，靠升温度“换个运气”对格式问题基本无效。重试耗尽必须硬失败：抛错并保存原始输出供排查，绝不允许“解析失败就当空结果继续跑”，静默吞掉坏输出会在长链路里造成无源之水的数据污染。
3. 一是字段宁少勿多：每个字段都是模型要分心填的东西，非必要不加，能由程序推导的字段（如序号、时间戳）不要让模型填；二是枚举收口：状态、类型这类字段一律用 `enum` 列死候选值，自由文本是最常见的口径漂移来源；三是给“不知道”留合法出口：允许 `null` 或空数组并明确语义，没有出口，模型会用编造来填满必填字段。
