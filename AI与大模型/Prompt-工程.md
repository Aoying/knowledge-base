# Prompt 工程

> Prompt 不是「咒语」，是给模型的**接口契约**：说清角色、任务、输入、输出格式和边界。契约越明确，输出越稳定；凡是要进程序处理的输出，格式约束比文采重要一个数量级。输出格式的机器级约束见 [结构化输出与JSON约束](AI与大模型/结构化输出与JSON约束.md)，本篇讲提示词本身怎么写。

## 1. 核心概念

一条可维护的提示词由五段构成，缺哪段补哪段，不要整段文学创作：

1. **角色与目标**：你是谁、这轮任务算什么（抽取 / 判断 / 生成，三者不要混在一轮里）。
2. **上下文**：完成任务所需的事实材料，与指令分开放。
3. **任务指令**：动词明确的步骤，说清做什么、不做什么。
4. **输出格式**：字段、顺序、长度、语言；进程序的输出在这段下死命令（「只输出 JSON」）。
5. **边界与兜底**：信息不足时怎么办（输出固定标记、留空、说明缺什么），禁止编造什么。

核心认知：模型对提示词的服从是**概率性**的。提示写得好是把出错概率压低，不是归零；关键链路永远要在代码侧再校验一遍。

## 2. 基础知识

### 结构化提示的写法

- **用分隔符圈定材料**：上下文用 ```` ``` ````、XML 标签或明确标题与指令隔开，避免模型把材料里的文字当成给它的新指令（材料越长越重要，叙事文本里尤其常见——章节正文中出现一句「请注意……」不该改变任务）。
- **一条指令一个意思**：复合要求拆成编号步骤，按执行顺序排。
- **给「不许做」配「改做」**：只写「不要编造」效果有限，写「原文没有的信息，字段填 null，不要推测」才可执行。
- **长度与粒度说死**：「简要总结」是玄学，「用 3 句话、每句不超过 30 字」是契约。

### Few-shot（示例教学）

给 2–5 个「输入 → 期望输出」的示例，让模型照着模式走。适用：输出格式刁钻、分类口径主观（如什么算「伏笔」、什么算「状态变化」）、风格要统一的任务。

- 示例要覆盖典型情况和一个边界情况，边界示例的价值最高。
- 示例的输出必须彼此格式完全一致——示例本身不一致，模型学会的就是不一致。
- 示例占上下文且会「锚定」口径，口径变化时先改示例，不要在指令里打补丁。

### 思维链（Chain-of-Thought）

让模型先写推理过程、再给结论（「先逐项分析，最后给结论」）。适用：多步判断、矛盾检测、复杂裁决。不适用：纯抽取、格式化转换——这类任务加思维链只是多烧 token、还多出解析干扰。

工程上的折中：**推理与结论分区**——要求模型先在分析区自由写，最后在固定标记后只放结构化结论，程序只解析结论区。这样既享受思维链的准确率，又保住下游可解析性。

## 3. 进阶知识：调试方法

Prompt 调试和代码调试同构，别靠感觉：

1. **建固定测试集**：攒一批典型输入 + 期望输出（含已知会翻车的），每次改提示先全量回归。
2. **一次只改一处**：同时改三处，变好变坏都归因不了。
3. **先看失败样本再改**：把失败模式归类（格式错 / 口径错 / 漏抽 / 幻觉），对症下药；格式错优先上机器约束（见 [结构化输出与JSON约束](AI与大模型/结构化输出与JSON约束.md)），别用更长的提示去求模型别犯格式错。
4. **温度分工**：抽取、判断类任务低温度求稳定；创意生成类才放开。同一条链路的不同环节可以不同温度。

## 4. 常见失效模式

| 失效 | 表现 | 对策 |
|---|---|---|
| 指令稀释 | 提示越堆越长，后半段要求被「忘掉」 | 精简；关键约束放开头和结尾各一次；拆任务 |
| 材料串指令 | 被处理的文本里的祈使句被当成命令执行 | 分隔符隔离 + 明确声明「材料仅是数据」 |
| 格式漂移 | 前几次合规，批量跑时逐渐变形 | few-shot 锚定 + 代码侧校验重试，不要指望提示根治 |
| 过度迎合 | 模型顺着问题里的暗示给结论（问「是不是 A 导致的」就答是） | 指令中性化；判断类任务先让它列证据再下结论 |
| 编造补全 | 信息不足时用「合理推测」填空 | 兜底条款：缺信息填 null / 输出固定标记 |
| 口径漂移 | 同一标准前后判定不一致 | 把口径写成可判定的规则 + 边界示例，而不是形容词 |

## 5. 实战应用

以小说引擎的章节分析为例（详见 [小说创作引擎](项目沉淀/小说创作引擎.md)）：输入是一章正文 + 世界状态上下文，输出是 entities / entity_changes / relations / events / facts / rules 的 JSON。这个任务把上面几条全用上了：角色段限定「只做分析不续写」；材料段用标题隔离正文与状态上下文；口径段定义什么事件值得记录；兜底段规定「无法确定归属的变化填 null 不许猜」；输出段下死命令只给 JSON——而 JSON 的机器级保障不在提示层，交给结构化输出那一篇的 schema 校验与重试。

## 小技巧与冷知识

【小技巧】不变的契约放系统提示，每轮变化的材料放用户提示。角色、任务口径、输出格式这些每轮都一样的东西写进系统提示，只让用户提示带本轮的输入材料；这样换任务只换用户段，契约不会被材料里的文字带偏，调试时也一眼能看出改的是哪一段。

【小技巧】否定句改写成肯定句再写进提示。模型对“不要……”的服从比肯定指令弱，“不要用表格”不如直接写“用纯文本段落输出”，“不要太长”不如写“控制在 200 字以内”。肯定句直接给出目标行为，模型不用先理解禁令、再反推该做什么，出错的环节少一步。

【小技巧】把提示词当代码做版本管理：提示模板、测试集、期望输出一起进仓库，改提示就跑一遍回归。原文只要求建固定测试集、一次改一处，版本管理再往前一步：哪次改动让哪类样本变好变坏都有记录，回滚也有据可查，而不是凭印象觉得“上次那个版本更好”。

【冷知识】温度设为 0 也不保证每次输出完全相同。采样之外的浮点计算、并行批处理等因素会带来微小波动，同一条提示跑两次也可能在个别词上不同；所以关键链路不能只靠低温求稳定，仍要在代码侧校验、重试、兜底，这和原文“关键链路永远要在代码侧再校验一遍”是一个道理。

【冷知识】示例的顺序本身会影响输出，模型对靠后的示例更敏感。Few-shot 里把最难、最容易判错的边界示例放在最后，往往比放在中间更能锚定口径；调换示例顺序也是一种调试手段，口径没变但结果变了时，先别急着改指令，试试换一下示例顺序。

【冷知识】换模型要重测提示，不要直接迁移。同一条提示在不同模型、甚至同一模型的不同版本上表现可能不同，有的模型对分隔符敏感、有的对示例格式敏感；换模型等于换了一套“口径”，原测试集要全量重跑一遍，过了才能算这条提示在新模型上可用。

## 面试与自测

1. 一条可维护的提示词由哪五段构成？各段管什么？
2. 思维链适用于哪些任务、不适用于哪些任务？工程上的折中做法是什么？
3. 只写“不要编造”为什么效果有限？可执行的写法是什么？

### 参考答案

1. 角色与目标（你是谁、这轮任务算什么，抽取、判断、生成三者不要混在一轮里）、上下文（完成任务所需的事实材料，与指令分开放）、任务指令（动词明确的步骤，说清做什么、不做什么）、输出格式（字段、顺序、长度、语言，进程序的输出在这段下死命令，如“只输出 JSON”）、边界与兜底（信息不足时怎么办，禁止编造什么）。
2. 适用多步判断、矛盾检测、复杂裁决；不适用纯抽取、格式化转换，这类任务加思维链只是多烧 token、还多出解析干扰。工程折中是推理与结论分区：要求模型先在分析区自由写，最后在固定标记后只放结构化结论，程序只解析结论区，既享受思维链的准确率，又保住下游可解析性。
3. 因为只写禁令没有给可执行的替代动作。有效的写法是给“不许做”配“改做”：原文没有的信息，字段填 null，不要推测；这正是边界与兜底段的规定——信息不足时输出固定标记、留空或说明缺什么，而不是用“合理推测”填空。
