# 本地部署与 Ollama

> 为什么本地部署：零 API 成本、数据不出本机、随时可用。代价是硬件上限就是能力上限——所以本篇的重点不是「哪个模型最强」，而是**估算方法**：给定显存/内存，先算清一个模型能不能装、装下后上下文能开多大，再谈效果。具体型号的实测结论变化快，一律以本机实测为准，未实测的标「待验证」。

本地环境基线：Windows，48GB 内存，12GB 独立显存 + 约 24GB 共享显存；Ollama 提供 OpenAI 兼容接口 `http://127.0.0.1:11434/v1`。

## 1. 核心概念

- **Ollama 的定位**：本地模型运行时 + 模型仓库。负责下载权重、按需加载/卸载、多模型切换，并同时暴露原生 API（`/api/chat`、`/api/embed`）和 OpenAI 兼容 API（`/v1`），让已有代码改个 base_url 就能从云端切到本地。
- **GGUF**：llama.cpp 生态的单文件权重格式，Ollama 的模型本质上就是 GGUF + Modelfile 的封装。理解 GGUF 的量化命名，就能看懂任何本地模型的体积与精度取舍。
- **量化**：把权重从 FP16 压到低比特存储。精度降一点，体积和显存占用降一大截，是消费级硬件跑大模型的前提。

## 2. 基础知识

### 常用命令

```powershell
ollama list            # 本地已有模型（标签以此为准，网上教程的标签可能已改名）
ollama pull <模型:标签>
ollama run <模型:标签>  # 交互对话，顺带验证能加载
ollama ps              # 当前驻留内存/显存的模型
ollama rm <模型:标签>
```

### 量化格式怎么读（GGUF 命名）

形如 `Q4_K_M`、`Q5_K_M`、`IQ2_M`、`IQ4_XS`：

- 数字 = 平均每权重比特数（粗略）：Q8≈8、Q5≈5、Q4≈4、IQ 系是带重要性矩阵的非均匀量化，同比特下通常优于普通 Q。
- 经验换算：**权重文件体积 ≈ 参数量(B) × 比特数 / 8**。如 14B × Q4 ≈ 8–9GB，14B × Q5 ≈ 10–11GB（另有少量结构性开销）。
- 取舍：同尺寸下比特越高越接近原模型；硬件紧张时宁可大一号模型的低量化，也别选小一号的高量化——但这只是通用经验，具体到某个模型要实测，标「待验证」。

### Modelfile：给模型定默认行为

```dockerfile
FROM qwen3:14b
PARAMETER temperature 0.3
PARAMETER num_ctx 32768
SYSTEM 你是章节分析助手，只输出约定的 JSON，不输出解释文字。
```

`ollama create mymodel -f Modelfile` 后即得到一个带默认参数与系统提示的本地模型。适合把「信息抽取」「JSON 输出」这类固定任务固化下来，与代码里的临时参数分工。

## 3. 进阶知识：显存/内存估算方法（本篇核心）

能不能跑，分三笔账，缺一不可：

**第一笔：权重**。按上节公式估体积。权重能全部进显存最理想；装不下时 Ollama 会把一部分层 offload 到内存，**能跑 ≠ 跑得动**——走内存的层会显著拖慢生成速度。

**第二笔：KV Cache**。上下文越长越大，且与层数、隐藏维度成正比。粗估方法：先按短上下文（如 4K）跑通，再逐步加大 `num_ctx` 观察显存增量，用增量反推每 1K token 的 KV 占用，不要直接按模型标称的最大上下文开满——标称值是「架构支持」，不是「你的硬件装得下」。

**第三笔：运行时开销**。计算图缓冲、系统占用、其他程序（IDE、浏览器）都要留余量。实操原则：**显存预算 = 独显容量 − 2GB 左右余量**；内存同理，别按 48GB 满打满算。

套到本地环境（12GB 独显 + 48GB 内存）的方法论结论（非具体型号结论）：

- 约 14B 级 Q4/Q5 量化可望全量进显存或仅少量 offload，适合常驻高频任务（信息抽取、JSON、RAG 问答）。
- 约 30B 级只能部分 offload，适合按需调用的低频重活（复杂推理、最终裁决），接受它慢。
- 双层分工「常驻 + 按需」正是 [Agent](AI与大模型/Agent/Agent.md) 篇的二层架构在本机的落地形态；两模型同时驻留时，总账 = 两份权重 + 两份 KV，别只算单个。

### OpenAI 兼容 API 的接入约定

代码侧统一走 `/v1` 兼容口，只换 base_url 与 model 名，业务代码不感知本地/云端差异。注意两个坑：

- 兼容层对高级参数（如某些采样参数、tool calling 的细节行为）的支持程度与原生 `/api/chat` 不完全一致；工具调用链路建议用原生接口实测一次再定，见 [Tool-Calling](AI与大模型/Agent/Tool-Calling.md)。
- embedding 走 `/api/embed`，与生成接口是两条路，别拿 chat 模型名去调 embed。

## 4. 疑难杂症

- **`ollama pull` 报模型不存在（404）**：多半是标签改名或教程过期。先查官方库页面与 `ollama list` 的实际标签，不要凭记忆写死模型名。
- **模型加载后奇慢**：先看 `ollama ps` 的处理器分布（GPU/CPU 占比），确认是不是大部分层被 offload 到 CPU；再考虑降量化档位或减上下文。
- **两个模型来回切换时反复加载**：驻留策略与显存上限决定，常用模型可调大 keep-alive，非常用的随用随卸。

## 5. 常见误区

- **只看参数量选模型**：量化档位、上下文长度、KV 占用都决定实际占用，参数量只是第一笔账。
- **按标称上下文开满**：长上下文先吃显存（KV），再谈模型能不能「理解」那么长。
- **把网上跑分当本机结论**：速度与质量都依赖硬件与量化档位，别人机器上的数字只作参考，本机未实测的标「待验证」。

## 小技巧与冷知识

【小技巧】模型默认只在内存里待 5 分钟，闲置超时就卸载，下次调用又要重新加载：常驻的高频模型（抽取、JSON、RAG）要把驻留时间调长，服务端环境变量 `OLLAMA_KEEP_ALIVE=-1` 是最稳的做法，`ollama run` 也可以加 `--keepalive 24h`。`ollama ps` 的 UNTIL 列能直接看到每个模型还剩多久被卸载，排障时先看它，别只凭感觉猜是不是被卸载了。

【小技巧】`ollama stop <模型>` 可以主动卸载模型，不用等 5 分钟自然超时：大模型按需跑完重活后，立刻停掉它把显存还给常驻模型，下一次高频任务就不用重新加载。两个模型来回切换时，先停不用的、再起要用的，比让 Ollama 自己按显存上限挤掉要可控得多。

【小技巧】模型默认存在用户目录下，Windows 是 `C:\Users\%username%\.ollama\models`，几个大模型一拉 C 盘就满了：提前用环境变量 `OLLAMA_MODELS` 把模型目录指到空间大的盘（例如 `D:\OllamaModels`），设好后重启 Ollama 服务再生效，之后再 pull 的模型才会进新目录。已经下好的模型要搬家，得先停服务、把整个目录搬过去再改变量，直接改变量不搬文件等于丢了已下载的模型。

【小技巧】排障先看 `ollama show --modelfile <模型>`：它能打出模型真实的默认参数、模板和系统提示，比凭记忆猜“这个模型默认温度是多少”可靠。自己用 Modelfile 改过参数的模型尤其要看——`ollama list` 只告诉你它存在，`show` 才告诉你它到底被配成了什么样。

【小技巧】交互对话里不用退出重建就能临时改参数：`ollama run` 的对话中输入 `/set parameter num_ctx 4096`，当场就把上下文窗口改成 4096，适合临时验证“上下文开大一点会不会变慢”；想永久生效再写进 Modelfile 用 `ollama create` 固化。临时改和永久改分开，试参数时不用反复建模型。

【小技巧】模型慢的时候先用 `ollama run --verbose` 看耗时分解：它会在回答后打出加载耗时、提示处理速度（token/s）、生成速度（token/s）三段数字。加载慢说明模型在反复卸载重载，去调 keep-alive；生成慢才是显存 offload 或量化档位的问题，两类慢的修法完全不同，别一上来就降量化。

【冷知识】`ollama run` 第一次跑某个模型会自动先 pull，不用先 `pull` 再 `run`：`ollama run qwen3:14b` 在本地没有这个标签时，会直接下载再开对话。反过来，`ollama pull` 只是下载不加载，想验证能不能跑、跑多快，还是要 `ollama run` 一次或调一次 API 才算数。

【小技巧】想确认 Ollama 服务活着，不用跑一次完整对话：`curl http://127.0.0.1:11434/api/tags` 返回已下载的模型列表就说明服务正常，返回不了先查服务有没有启动、端口有没有被占。写代码前先用这条命令探一下，比在代码里调一次 chat 再看报错要快得多，也更容易分清是“服务没起”还是“模型名写错”。

## 面试与自测

1. 14B 模型用 Q4 量化时，权重文件大约多大？换算公式是什么？
2. 模型能加载但生成奇慢，第一步应该查什么？接下来怎么处理？
3. 为什么不要直接按模型标称的最大上下文开 `num_ctx`？正确的做法是什么？

### 参考答案

1. 约 8–9GB。公式：权重文件体积 ≈ 参数量(B) × 比特数 / 8，14 × 4 / 8 ≈ 7GB，再加少量结构性开销；同理 14B Q5 约 10–11GB。注意这只是权重这一笔账，KV Cache 和运行时开销另算。
2. 先看 `ollama ps` 的处理器分布，确认是不是大部分层被 offload 到内存/CPU——能跑不等于跑得动，走内存的层会显著拖慢生成。确认后降量化档位或减小上下文；两个模型来回切换反复加载时，常用模型可调大 keep-alive。
3. 标称值是架构支持，不是你的硬件装得下：KV Cache 随上下文增长，且与层数、隐藏维度成正比。正确做法是先按短上下文（如 4K）跑通，再逐步加大 `num_ctx` 观察显存增量，用增量反推每 1K token 的 KV 占用；显存预算按独显容量减约 2GB 余量来算。
