# Embedding 与向量数据库

> RAG 的地基：embedding 决定「语义距离怎么量」，向量数据库决定「按这个距离能多快找回来」。分块与评测方法见 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md)，本篇只讲向量这一层：模型怎么选、维度意味着什么、换模型为什么必须重建库。

## 1. 核心概念

- **Embedding（向量化）**：用一个专门的 embedding 模型把一段文本映射成定长浮点向量。语义相近的文本，向量在空间里距离近。生成模型（LLM）和 embedding 模型是两类东西：前者生成文字，后者只产向量，不能混用。
- **相似度度量**：余弦相似度（只看方向，最常用）、内积、欧氏距离。入库和查询必须用同一种度量，中途换度量等于换了一套排序规则。
- **向量数据库**：存向量 + 元数据，并提供近似最近邻（ANN）检索。数据量小（万级以内）时精确暴力检索也够用；向量库真正的价值在元数据过滤、持久化和增量更新。
- **召回 ≠ 排序**：向量检索只负责「按语义距离捞一批候选」，捞得准不准还要靠评测，方法见 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md)。

## 2. 基础知识

### Embedding 模型的选择维度

| 维度 | 说明 |
|---|---|
| 输出维度 | 常见 384 / 768 / 1024 / 2048，维度越高单条向量越大、索引越占空间 |
| 最大输入长度 | 超长文本会被截断，长章节必须先分块再向量化 |
| 中文支持 | 必须确认模型明确支持中文；只训英文语料的模型对中文语义距离判断不可靠 |
| 部署方式 | 本地（Ollama / sentence-transformers）零 API 成本，或云端 embedding API 按量计费 |
| 指令前缀 | 部分模型区分 query / document 两种输入，要按文档要求加前缀，否则效果打折 |

### Chroma 的基本模型（本地原型在用）

- **Collection**：一个集合 = 一套向量 + 对应文档 + 元数据，集合内向量维度必须一致。
- 写入：`add(ids, documents, embeddings, metadatas)`——embedding 可以自己算好传入，也可以让 Chroma 用内置函数算；原型里自己调 Ollama 出向量，便于换模型时可控。
- 查询：`query(query_embeddings, n_results, where)`，`where` 是元数据过滤（如按项目、章节号过滤），这是叙事类 RAG 的关键能力：先按结构化条件圈范围，再按语义排序。
- 持久化：指定 `persist_directory` 落盘，重启不丢；集合本身没有「改一列」的概念，元数据要改就是按 id 删除重写。

## 3. 进阶知识

### 维度与重建：换 embedding 模型 = 重建整个库

这是最容易踩的坑，必须记牢：

- 一个集合里的向量维度由入库时用的模型决定。换了输出维度不同的模型（例如从 768 维换到 2048 维），新旧向量**根本不在同一个空间**，混写会直接报错或静默给出垃圾排序。
- 即使维度相同、换了模型，向量空间的语义分布也不同，旧向量与新查询向量不可比，同样要全量重算。
- 结论：**换 embedding 模型的操作规程 = 新建集合 → 全部文档重新向量化入库 → 评测回归 → 切换查询指向 → 删除旧集合**。没有捷径。
- 工程防护：在集合元数据里记录入库用的「模型名 + 维度」，查询启动时校验当前配置与库内记录一致，不一致就拒绝启动并报警——把「维度对不上」从线上事故变成启动期报错。

### 向量检索的定位：只是检索手段之一

纯向量检索对专有名词、人名、地名这类精确词不敏感（它找的是「意思像」，不是「字面有」）。叙事文本里大量查询恰恰是人名 + 事件的精确组合。实用做法是混合检索：**结构化过滤（元数据）+ 关键词 + 向量**三路召回再合并，而不是迷信单路向量。小说引擎里已有 Entity / Timeline 等结构化数据，天然适合「先结构化圈定、再语义排序」。

## 4. 实战应用（本地原型现状）

当前原型（2026-10 落地，先放着、暂未切换）：单后端版 `rag_chroma_eg2.py` 走 Ollama `/api/embed` 出向量，向量模型标签为 `embeddinggemma-2:270m`（注意：旧标签 `embeddinggemma2` 已 404，拉模型前先以 `ollama list` / 官方库为准核对标签名）；切片用 chunk + overlap，异常统一收敛为 `RAGError`，不让检索层把主流程带崩。

已备好但未启用的双后端版支持用环境变量在 Ollama 与另一本地 embedding 方案之间切换，并带「后端 + 维度」双重守卫——正对应本篇第 3 节的重建问题：守卫只能拦住带元数据的新库，**旧库若没写元数据，守卫覆盖不到，切换时要手动删旧 `chroma_db` 重建**。

更高维度的本地候选模型（如 2048 维一档）是否比现方案更适合中文长叙事检索，**待验证**：需要按 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md) 的评测集做召回对比后再下结论，不凭参数表拍板。

## 5. 常见误区

- **拿生成模型当 embedding 模型**：chat 模型的隐藏状态不是为语义检索训练的，效果没有保证。
- **以为向量库越大越智能**：检索质量上限由 embedding 模型和分块决定，换库不换模型，效果基本不变。
- **入库不存元数据**：只存文本和向量，事后无法按章节、人物、时间过滤，等于把结构化优势扔掉。
- **查询和入库用了不同模型/不同预处理**：两边必须同模型、同截断、同前缀规则，否则距离没有意义。

## 小技巧与冷知识

【小技巧】入库和查询必须走同一条向量化封装：模型、前缀、截断规则、归一化开关有一处不同，距离就失去意义。做法是只写一个 embed(texts, kind) 函数，入库传 kind="document"、查询传 kind="query"，两边的前缀差异收在函数内部，代码里别出现第二处直接调 embedding 模型的调用，改规则时只改一处。

【小技巧】入库前先做一对冒烟查询再全量灌库：准备两对文本——同一句话换个说法，以及完全无关的两句——灌进空集合查一次排序，符合预期再灌全库。模型选错、前缀配反、截断配错，这类问题几分钟内就能暴露，比灌完几千条再跑评测集便宜得多。

【小技巧】元数据字段名要先定表再入库：Chroma 的 where 过滤只认入库时写进元数据的字段，事后想按新维度过滤，只能全量删除重写。入库前先把项目、章节号、人物、时间这类过滤维度列成一张固定字段表，字段名一经定下就别改，改字段名等于改 schema，也要重建。

【小技巧】查询时先用 where 把范围圈小再做向量检索：叙事查询大多自带人物、章节条件，先按元数据过滤把候选从几千条压到几十条，再算向量距离，既快又准。反过来先全库向量检索、事后按条件过滤，真正相关的结果可能根本进不了 Top-K，过滤发生在排序之后就晚了。

【冷知识】向量维度不是越高越好：维度上去之后，不同文本之间的距离会越来越“挤在一起”，区分度反而可能下降；再加上单条向量更大、索引更占空间，高维未必等于高召回。原文说高维候选要“待验证”正是这个道理——选型看评测集的召回对比，不看参数表上的维度数字。

【冷知识】ANN 检索是“近似”的，结果会随数据量悄悄变化：为了快，向量库只在候选子集里找最近邻，数据量变大、分布变了之后，同一查询的 Top-K 可能换内容。需要精确结果时要回退暴力检索，或先多捞一批候选再重排，别把 ANN 的某次结果当成唯一真值。

【冷知识】最大输入长度的单位是 token 不是字数：中文、英文、代码换算成 token 的比例各不相同，直接按字数估算很容易低估。长章节分块时按 token 数留余量；截断是静默发生的，超出的部分直接丢掉不报错，关键情节落在截断处就等于没入库。
