# Embedding 与向量数据库

> RAG 的地基：embedding 决定「语义距离怎么量」，向量数据库决定「按这个距离能多快找回来」。分块与评测方法见 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md)，本篇只讲向量这一层：模型怎么选、维度意味着什么、换模型为什么必须重建库。

## 1. 核心概念

- **Embedding（向量化）**：用一个专门的 embedding 模型把一段文本映射成定长浮点向量。语义相近的文本，向量在空间里距离近。生成模型（LLM）和 embedding 模型是两类东西：前者生成文字，后者只产向量，不能混用。
- **相似度度量**：余弦相似度（只看方向，最常用）、内积、欧氏距离。入库和查询必须用同一种度量，中途换度量等于换了一套排序规则。
- **向量数据库**：存向量 + 元数据，并提供近似最近邻（ANN）检索。数据量小（万级以内）时精确暴力检索也够用；向量库真正的价值在元数据过滤、持久化和增量更新。
- **召回 ≠ 排序**：向量检索只负责「按语义距离捞一批候选」，捞得准不准还要靠评测，方法见 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md)。

## 2. 基础知识

### Embedding 模型的选择维度

| 维度 | 说明 |
|---|---|
| 输出维度 | 常见 384 / 768 / 1024 / 2048，维度越高单条向量越大、索引越占空间 |
| 最大输入长度 | 超长文本会被截断，长章节必须先分块再向量化 |
| 中文支持 | 必须确认模型明确支持中文；只训英文语料的模型对中文语义距离判断不可靠 |
| 部署方式 | 本地（Ollama / sentence-transformers）零 API 成本，或云端 embedding API 按量计费 |
| 指令前缀 | 部分模型区分 query / document 两种输入，要按文档要求加前缀，否则效果打折 |

### Chroma 的基本模型（本地原型在用）

- **Collection**：一个集合 = 一套向量 + 对应文档 + 元数据，集合内向量维度必须一致。
- 写入：`add(ids, documents, embeddings, metadatas)`——embedding 可以自己算好传入，也可以让 Chroma 用内置函数算；原型里自己调 Ollama 出向量，便于换模型时可控。
- 查询：`query(query_embeddings, n_results, where)`，`where` 是元数据过滤（如按项目、章节号过滤），这是叙事类 RAG 的关键能力：先按结构化条件圈范围，再按语义排序。
- 持久化：指定 `persist_directory` 落盘，重启不丢；集合本身没有「改一列」的概念，元数据要改就是按 id 删除重写。

## 3. 进阶知识

### 维度与重建：换 embedding 模型 = 重建整个库

这是最容易踩的坑，必须记牢：

- 一个集合里的向量维度由入库时用的模型决定。换了输出维度不同的模型（例如从 768 维换到 2048 维），新旧向量**根本不在同一个空间**，混写会直接报错或静默给出垃圾排序。
- 即使维度相同、换了模型，向量空间的语义分布也不同，旧向量与新查询向量不可比，同样要全量重算。
- 结论：**换 embedding 模型的操作规程 = 新建集合 → 全部文档重新向量化入库 → 评测回归 → 切换查询指向 → 删除旧集合**。没有捷径。
- 工程防护：在集合元数据里记录入库用的「模型名 + 维度」，查询启动时校验当前配置与库内记录一致，不一致就拒绝启动并报警——把「维度对不上」从线上事故变成启动期报错。

### 向量检索的定位：只是检索手段之一

纯向量检索对专有名词、人名、地名这类精确词不敏感（它找的是「意思像」，不是「字面有」）。叙事文本里大量查询恰恰是人名 + 事件的精确组合。实用做法是混合检索：**结构化过滤（元数据）+ 关键词 + 向量**三路召回再合并，而不是迷信单路向量。小说引擎里已有 Entity / Timeline 等结构化数据，天然适合「先结构化圈定、再语义排序」。

### 度量一致性：余弦相似度 = 归一化后的内积

余弦、内积、欧氏距离不是三套互不相干的排序规则，归一化后前两者是同一回事：

- 余弦相似度只看方向：`cos(a, b) = (a·b) / (‖a‖‖b‖)`；内积 `a·b` 同时受方向和模长影响。把两个向量都做 L2 归一化（除以各自的模长）之后，内积就等于余弦相似度。
- 手算一例（本地 Python 复算）：`a = [1, 2, 3]`，`b = [4, 5, 6]`，内积 `1×4 + 2×5 + 3×6 = 32`；`‖a‖ ≈ 3.741657`，`‖b‖ ≈ 8.774964`，余弦 `32 / (3.741657 × 8.774964) ≈ 0.974632`；欧氏距离 `√[(3² + 3² + 3²)] ≈ 5.196152`。把 a、b 各自归一化后再算内积，得到 `0.974632`，与余弦完全一致。
- 工程含义有三条：①入库和查询必须用**同一种度量 + 同一套归一化**，一边归一化、一边不归一化，排序就失真；②用内积度量时，未归一化的向量会偏向模长大的长文本——长章节天然占优，不是因为它更相关；③ EmbeddingGemma 输出本身已做 L2 归一化（均值池化后归一化），所以对它来说余弦与内积等价，**但截断维度后必须重新归一化**（见下一节），截出来的前 N 维不再是单位向量，直接算距离会系统性偏小。

### 维度定量：768 维的账与 Matryoshka 截断

维度不是玄学，是一笔能算的账。单精度 float32 每维 4 字节：

| 维度 | 每条向量 | 1 万条 | 2.4 万条（约 600 章 × 40 chunk） |
|---|---|---|---|
| 768 | 3072 B | 约 29.3 MiB | 约 70.3 MiB |
| 512 | 2048 B | 约 19.5 MiB | 约 46.9 MiB |
| 256 | 1024 B | 约 9.8 MiB | 约 23.4 MiB |
| 128 | 512 B | 约 4.9 MiB | 约 11.7 MiB |

（本地 Python 复算；只计向量本身，不含 HNSW 索引结构与元数据，索引开销见 [向量检索深水](AI与大模型/RAG/向量检索深水.md)。）

关键变量是模型本身支持**截断**：EmbeddingGemma 2（Google，2026-10-06 发布，Apache-2.0；Ollama 标签 `embeddinggemma-2:270m` 对应其 270M 纯文本配置，输出 768 维，以 `ollama list` / 官方库为准核对）用 Matryoshka 表示学习（MRL）训练，768 维输出可以只取前 512 / 256 / 128 维使用，因为训练时就把最具区分度的信号压进了靠前的维度。Google 开发者指南给出：256 维约保留 95% 的多模态检索性能；MTEB 多语言 v2 榜单：768 维 61.36 → 256 维 60.41（约 98.5%）→ 128 维 57.89（约 94.3%）。256 维时 2.4 万条纯向量约 23.4 MiB，是 768 维的三分之一。

三条边界，缺一不可：

- **截断只省存储与检索算力，不省 embedding 计算**：模型推理仍跑满 768 维输出，截断发生在出向量之后，入库速度不会因此变快。
- **换截断维度 = 换向量空间**：256 维向量与 768 维向量不在同一空间，切换截断维度同样要按本节第一节的操作规程重建库，不能混写。
- **通用榜单 ≠ 小说语料结论**：上面 95% / 98.5% 是 Google 发布的通用榜单数字，未在小说引擎语料上实测。是否截到 256 维，要按 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md) 的评测集做召回对比后再定，**待验证**，不凭参数表拍板。

来源：Google EmbeddingGemma 2 开发者指南与模型卡（2026-10-06 发布）、MTEB 多语言 v2 榜单数字，核验日期 2026-11-04。

## 4. 实战应用（本地原型现状）

当前原型（2026-10 落地，先放着、暂未切换）：单后端版 `rag_chroma_eg2.py` 走 Ollama `/api/embed` 出向量，向量模型标签为 `embeddinggemma-2:270m`（注意：旧标签 `embeddinggemma2` 已 404，拉模型前先以 `ollama list` / 官方库为准核对标签名）；切片用 chunk + overlap，异常统一收敛为 `RAGError`，不让检索层把主流程带崩。

已备好但未启用的双后端版支持用环境变量在 Ollama 与另一本地 embedding 方案之间切换，并带「后端 + 维度」双重守卫——正对应本篇第 3 节的重建问题：守卫只能拦住带元数据的新库，**旧库若没写元数据，守卫覆盖不到，切换时要手动删旧 `chroma_db` 重建**。

更高维度的本地候选模型（如 2048 维一档）是否比现方案更适合中文长叙事检索，**待验证**：需要按 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md) 的评测集做召回对比后再下结论，不凭参数表拍板。

## 5. 常见误区

- **拿生成模型当 embedding 模型**：chat 模型的隐藏状态不是为语义检索训练的，效果没有保证。
- **以为向量库越大越智能**：检索质量上限由 embedding 模型和分块决定，换库不换模型，效果基本不变。
- **入库不存元数据**：只存文本和向量，事后无法按章节、人物、时间过滤，等于把结构化优势扔掉。
- **查询和入库用了不同模型/不同预处理**：两边必须同模型、同截断、同前缀规则，否则距离没有意义。

## 原理剖析

本节只把原文已有章节给出的结论拆开讲清机制：不引入新概念，不补新数字，数字一律复用 §3 已核验的定量算例；凡原文没展开的点，文中明确标注，不作定论。

### 向量为什么能表示语义距离

原文 §1 给出的定义是：embedding 模型把一段文本映射成定长浮点向量，语义相近的文本在空间里距离近；生成模型只产文字，embedding 模型只产向量，生成模型与 embedding 模型不能混用。检索时做的事，就是按这个距离把候选排出来：距离近的排在前面，距离远的排在后面。向量数据库提供的近似最近邻检索，找的也是按同一距离度量的最近邻；数据量小时，原文 §1 说精确暴力检索也够用。

这里有一处原文未展开：embedding 模型在内部怎样把文本映射成向量、语义相近为什么会在空间里距离近，原文没有讲训练过程与映射机制，本文不作定论，只复述原文给出的定义与用法。同样原文未展开：近似最近邻检索在索引内部怎样圈定候选子集，原文 §3 只说索引开销见向量检索深水篇，本文不展开。

### 余弦与内积为什么归一化后等价

原文 §3 给出的关系是：余弦相似度只看方向，内积同时受方向和模长影响；把两个向量都做 L2 归一化（除以各自的模长）之后，内积就等于余弦相似度。手算一例（原文 §3，本地 Python 复算）：`a = [1, 2, 3]`，`b = [4, 5, 6]`，内积 `1×4 + 2×5 + 3×6 = 32`；`‖a‖ ≈ 3.741657`，`‖b‖ ≈ 8.774964`，余弦 `32 / (3.741657 × 8.774964) ≈ 0.974632`；欧氏距离 `√[(3² + 3² + 3²)] ≈ 5.196152`。把 a、b 各自归一化后再算内积，得到 `0.974632`，与余弦完全一致（以上数字均出自原文 §3）。

机制拆开是：余弦公式 `cos(a, b) = (a·b) / (‖a‖‖b‖)` 的分母恰好就是两个模长的乘积，除以模长就是归一化；归一化后的向量模长均为单位长度，内积里的模长因素被消掉，剩下的只有方向因素，所以内积退化为余弦。由此得到原文 §3 的工程含义：入库和查询必须用同一种度量加同一套归一化，一边归一化、一边不归一化，排序就失真；用内积度量时，未归一化的向量会偏向模长大的长文本，长章节天然占优，不是因为它更相关。

还有一处与归一化直接相关：原文 §3 说 EmbeddingGemma 输出本身已做 L2 归一化，所以对它来说余弦与内积等价，但截断维度后必须重新归一化，因为截出来的前 N 维不再是单位向量，直接算距离会系统性偏小。至于模型输出归一化的具体实现位置，原文未展开，不作定论。

### 维度、存储与截断的账怎么算

原文 §3 给出的算法是单精度 float32 每维 4 字节，存储只计向量本身，不含 HNSW 索引结构与元数据。按该算法复算（数字均出自原文 §3）：768 维每条向量 3072 B，1 万条约 29.3 MiB，2.4 万条约 70.3 MiB；512 维每条向量 2048 B，1 万条约 19.5 MiB，2.4 万条约 46.9 MiB；256 维每条向量 1024 B，1 万条约 9.8 MiB，2.4 万条约 23.4 MiB；128 维每条向量 512 B，1 万条约 4.9 MiB，2.4 万条约 11.7 MiB。其中 2.4 万条约等于 600 章 × 40 chunk（原文 §3）。

截断的机制是原文 §3 给出的：EmbeddingGemma 2 用 Matryoshka 表示学习训练，768 维输出可以只取前 512 / 256 / 128 维使用，因为训练时就把最具区分度的信号压进了靠前的维度。性能保留数字（原文 §3，Google 开发者指南与 MTEB 多语言 v2 榜单）：256 维约保留 95% 的多模态检索性能；768 维 61.36 → 256 维 60.41（约 98.5%）→ 128 维 57.89（约 94.3%）。256 维时 2.4 万条纯向量约 23.4 MiB，是 768 维约 70.3 MiB 的三分之一（原文 §3）。

边界同样按原文 §3 复述：截断只省存储与检索算力，不省 embedding 计算，模型推理仍跑满 768 维输出，截断发生在出向量之后，入库速度不会因此变快；通用榜单数字不等于小说语料结论，上面 95% / 98.5% 是 Google 发布的通用榜单数字，未在小说引擎语料上实测，是否截到 256 维要按评测集做召回对比后再定，原文标注待验证。此处原文未展开：Matryoshka 表示学习在训练时怎样把信号压进靠前维度，原文没有讲训练细节，本文不作定论。

### 换模型、换截断为什么等于换空间

原文 §3 给出的结论是：一个集合里的向量维度由入库时用的模型决定；换了输出维度不同的模型，新旧向量根本不在同一个空间，混写会直接报错或静默给出垃圾排序；即使维度相同、换了模型，向量空间的语义分布也不同，旧向量与新查询向量不可比，同样要全量重算。换截断维度同理：256 维向量与 768 维向量不在同一空间，切换截断维度同样要按操作规程重建库，不能混写。

操作规程按原文 §3 复述：新建集合 → 全部文档重新向量化入库 → 评测回归 → 切换查询指向 → 删除旧集合，没有捷径。工程防护按原文 §3 复述：在集合元数据里记录入库用的模型名与维度，查询启动时校验当前配置与库内记录一致，不一致就拒绝启动并报警。

此处原文未展开：不同模型向量空间的语义分布为什么不同、分布差异在数学上如何刻画，原文没有展开，本文不作定论；只复述原文给出的可操作结论，即换模型或换截断维度都要重建。

## 实战案例

### 案例一

**现象：** 切换截断维度后，同一查询返回的候选与切换前明显不同，排序看起来不再可信。

**排查：** 先核对集合元数据里记录的模型名与维度是否与当前配置一致（原文 §3 的工程防护做法）；再核对切换时是否走了原文 §3 的操作规程，即新建集合、全部文档重新向量化入库、评测回归、切换查询指向、删除旧集合；若旧库没有写模型名与维度元数据，原文 §4 说双后端版的守卫覆盖不到，切换时要手动删旧 `chroma_db` 重建。排查时对照的存储量级只用原文 §3 已核验的数字：768 维 2.4 万条纯向量约 70.3 MiB，256 维 2.4 万条纯向量约 23.4 MiB，是 768 维的三分之一——该数字只说明截断省存储，不说明截断后排序仍可比。

**结论：** 按原文 §3，256 维向量与 768 维向量不在同一空间，切换截断维度等于换向量空间，必须重建库，不能把新截断向量混写入旧集合；存储上省下来的量级不能作为不重建的理由。至于切换后召回具体变化多少，原文未在小说引擎语料上实测，本文不作定论，须按原文 §3 要求用评测集做召回对比后再定。

### 案例二

**现象：** 用内积度量排序时，长章节在结果里系统性占优，短而相关的片段排在后面。

**排查：** 先核对入库与查询是否用了同一种度量加同一套归一化（原文 §3）；再用原文 §3 的手算例复核公式本身：`a = [1, 2, 3]`，`b = [4, 5, 6]`，内积 `1×4 + 2×5 + 3×6 = 32`，`‖a‖ ≈ 3.741657`，`‖b‖ ≈ 8.774964`，余弦 `32 / (3.741657 × 8.774964) ≈ 0.974632`，欧氏距离 `√[(3² + 3² + 3²)] ≈ 5.196152`，归一化后内积为 `0.974632`，与余弦一致（以上数字均出自原文 §3）。该手算例只验证公式关系，不验证真实语料上的排序；再核对是否在截断维度后重新归一化，原文 §3 说截出来的前 N 维不再是单位向量，直接算距离会系统性偏小。代码层面只复用原文已出现的写法核对调用是否一致：

```
add(ids, documents, embeddings, metadatas)
query(query_embeddings, n_results, where)
```

**结论：** 按原文 §3，未归一化的向量在内积度量下会偏向模长大的长文本，长章节占优不是因为它更相关；入库与查询必须统一度量与归一化，截断维度后必须重新归一化。至于本次排序失真中有多少来自归一化、多少来自其他因素，原文未展开，本文不作定论，须逐项核对后再下结论。

## 小技巧与冷知识

【小技巧】入库和查询必须走同一条向量化封装：模型、前缀、截断规则、归一化开关有一处不同，距离就失去意义。做法是只写一个 embed(texts, kind) 函数，入库传 kind="document"、查询传 kind="query"，两边的前缀差异收在函数内部，代码里别出现第二处直接调 embedding 模型的调用，改规则时只改一处。

【小技巧】入库前先做一对冒烟查询再全量灌库：准备两对文本——同一句话换个说法，以及完全无关的两句——灌进空集合查一次排序，符合预期再灌全库。模型选错、前缀配反、截断配错，这类问题几分钟内就能暴露，比灌完几千条再跑评测集便宜得多。

【小技巧】元数据字段名要先定表再入库：Chroma 的 where 过滤只认入库时写进元数据的字段，事后想按新维度过滤，只能全量删除重写。入库前先把项目、章节号、人物、时间这类过滤维度列成一张固定字段表，字段名一经定下就别改，改字段名等于改 schema，也要重建。

【小技巧】查询时先用 where 把范围圈小再做向量检索：叙事查询大多自带人物、章节条件，先按元数据过滤把候选从几千条压到几十条，再算向量距离，既快又准。反过来先全库向量检索、事后按条件过滤，真正相关的结果可能根本进不了 Top-K，过滤发生在排序之后就晚了。

【冷知识】向量维度不是越高越好：维度上去之后，不同文本之间的距离会越来越“挤在一起”，区分度反而可能下降；再加上单条向量更大、索引更占空间，高维未必等于高召回。原文说高维候选要“待验证”正是这个道理——选型看评测集的召回对比，不看参数表上的维度数字。

【冷知识】ANN 检索是“近似”的，结果会随数据量悄悄变化：为了快，向量库只在候选子集里找最近邻，数据量变大、分布变了之后，同一查询的 Top-K 可能换内容。需要精确结果时要回退暴力检索，或先多捞一批候选再重排，别把 ANN 的某次结果当成唯一真值。

【冷知识】最大输入长度的单位是 token 不是字数：中文、英文、代码换算成 token 的比例各不相同，直接按字数估算很容易低估。长章节分块时按 token 数留余量；截断是静默发生的，超出的部分直接丢掉不报错，关键情节落在截断处就等于没入库。

## 面试与自测

1. 换 embedding 模型时为什么必须重建整个库？原文给出的操作规程是哪几步？
2. 纯向量检索对哪类查询不敏感？叙事文本里原文推荐的实用做法是什么？
3. 旧库若没写模型名与维度元数据，双后端版的“后端 + 维度”守卫会有什么盲区？切换时怎么办？
4. 余弦相似度与内积是什么关系？为什么截断维度后必须重新归一化？256 维省的是什么、不省什么？

### 参考答案

1. 因为一个集合里的向量维度由入库时用的模型决定：换了输出维度不同的模型，新旧向量根本不在同一个空间，混写会直接报错或静默给出垃圾排序；即使维度相同、换了模型，向量空间的语义分布也不同，旧向量与新查询向量不可比，同样要全量重算。操作规程是：新建集合 → 全部文档重新向量化入库 → 评测回归 → 切换查询指向 → 删除旧集合，没有捷径。
2. 对专有名词、人名、地名这类精确词不敏感——它找的是“意思像”，不是“字面有”，而叙事文本里大量查询恰恰是人名 + 事件的精确组合。实用做法是混合检索：结构化过滤（元数据）+ 关键词 + 向量三路召回再合并，小说引擎里已有 Entity / Timeline 等结构化数据，天然适合“先结构化圈定、再语义排序”。
3. 守卫只能拦住带元数据的新库，旧库若没写元数据，守卫覆盖不到；切换时要手动删旧 `chroma_db` 重建。工程防护是：在集合元数据里记录入库用的“模型名 + 维度”，查询启动时校验当前配置与库内记录一致，不一致就拒绝启动并报警，把“维度对不上”从线上事故变成启动期报错。

4. 把两个向量都做 L2 归一化之后，内积就等于余弦相似度（手算例：`[1,2,3]` 与 `[4,5,6]` 内积 32、余弦约 0.974632，归一化后内积同样是 0.974632）。截断维度后必须重新归一化，因为截出来的前 N 维不再是单位向量，直接算距离会系统性偏小。256 维省的是向量存储（2.4 万条约 23.4 MiB，为 768 维的三分之一）与检索算力，不省 embedding 计算——模型仍跑满 768 维输出；且换截断维度等于换向量空间，同样要重建库。
