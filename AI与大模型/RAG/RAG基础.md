# RAG 基础

> RAG（Retrieval-Augmented Generation，检索增强生成）是「先查资料、再让模型回答」的一套做法：模型回答前，先从你的知识库里把相关片段找出来塞进上下文，模型照着这些片段答。本篇是 RAG 的入口：讲清全链路、每个环节解决什么问题、深挖去哪篇找。分块、向量、检索、评测的细节分别在 RAG 目录下的 6 篇进阶笔记里，本篇不重复讲。

## 1. 核心概念

- **RAG 是什么**：回答问题时，先检索（Retrieval）出相关资料，再把资料作为上下文交给模型生成（Generation）答案。模型本身不改，改的是「每次调用给它看什么」。名字来自 2020 年 Lewis 等人的论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》（arXiv:2005.11401）。
- **为什么需要 RAG**：大模型有三个天生短板，RAG 正好补上——① 知识有截止时间，训练数据之后的事它不知道，只能靠检索去查（见 [大模型基础](AI与大模型/大模型基础.md)）；② 私有知识（你的笔记、项目文档、小说世界设定）根本不在训练语料里，不检索模型无从得知；③ 直接问容易幻觉，给了依据片段，答案有出处可查。
- **全链路**：切分 → 向量化 → 召回 → 重排 → 生成 → 评测，缺一不可（见 [大模型基础](AI与大模型/大模型基础.md)「RAG 全链路」一节）。每一环出问题，最终答案都会变差，而且三段要分开测（见 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md) §1）：答案不好，可能是没切好、没召回、或召回了但模型乱编，混在一起调永远不知道该改哪。
- **RAG 不是微调**：微调改模型权重，RAG 改每次调用的上下文。换资料不用重新训练，改知识库里的文档就行；代价是每次回答都要多做一次检索。

## 2. 基础知识

### 四个环节各解决什么

| 环节 | 做什么 | 出问题时的症状 | 深挖去哪篇 |
|---|---|---|---|
| 文档处理与切分 | 把长文档解析成文本、切成可独立向量化的小段（块） | 答案正好横跨切口、整段召不回来 | [文档处理与解析](AI与大模型/RAG/文档处理与解析.md)、[RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md) |
| 向量化 | 用 embedding 模型把每块文本变成定长向量，存进向量库 | 语义相近的文本距离却很远 | [Embedding与向量数据库](AI与大模型/RAG/Embedding与向量数据库.md) |
| 检索与重排 | 按问题向量捞一批候选，再重排取最相关的 TopK | 捞回来的全是沾边的、真正有用的排在后面 | [混合检索与Rerank](AI与大模型/RAG/混合检索与Rerank.md)、[向量检索深水](AI与大模型/RAG/向量检索深水.md) |
| 生成 | 把 TopK 片段拼进提示词，让模型照着回答 | 召回对了，模型还是凭空编 | [上下文工程](AI与大模型/RAG/上下文工程.md) |

### 分块（chunking）

- **块是检索的最小单位**：块切错，后面 embedding 再好也召不回来。切分策略有四种——固定长度、按段落/结构、递归切分、语义切分，各自的取舍见 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md) §2。
- **overlap（重叠）**：相邻块之间留一段重叠，一般取块长的 10%–20%，解决「答案正好横跨切口」的问题；overlap 不是越大越好，它会等比例放大索引体积和重复召回。
- **切分单位用 Token 而非字符数**，更贴近模型与 embedding 的实际处理方式，中英文混排时差异尤其明显。

### 向量化与向量库

- **Embedding 模型只产向量、不生成文字**，和生成模型（LLM）是两类东西，不能混用。常见输出维度 384 / 768 / 1024 / 2048，维度越高单条向量越大、索引越占空间。
- **相似度度量**：余弦相似度（只看方向，最常用）、内积、欧氏距离。入库和查询必须用同一种度量，中途换度量等于换了一套排序规则。
- **向量库真正的价值**在元数据过滤、持久化和增量更新；数据量小（万级以内）时精确暴力检索也够用。
- **换 embedding 模型必须重建库**：向量是模型算出来的，换模型等于换了一套坐标系，旧向量全部作废。

### 检索与生成

- **向量检索只负责「按语义距离捞一批候选」**，捞得准不准还要靠评测；关键词检索（BM25）按字面匹配，和向量检索互补，两路融合再重排是主流做法，见 [混合检索与Rerank](AI与大模型/RAG/混合检索与Rerank.md)。
- **生成时只喂 TopK 相关片段，别把整库倒进窗口**；长文档先摘要再问。RAG 问答的 temperature 一般取低值（本库口径：小说引擎抽取用 0，RAG 问答用 0.1–0.3），减少模型自由发挥。

### RAG、微调、长上下文怎么选

| 方案 | 适合 | 不适合 |
|---|---|---|
| RAG | 知识常变、私有资料、要给出处 | 模型本身能力不够（如不会某种推理范式） |
| 微调 | 改模型的行为风格、格式、特定任务能力 | 知识更新频繁（每次更新都要重新训） |
| 长上下文直塞 | 文档很少、一次问完 | 文档量大、每次都烧 token、中间信息召回差 |

三者可以叠加：微调定行为，RAG 供知识，长上下文兜底。

### 评测分两段

- **检索评测**：给定一批带标准答案的问题，看正确片段有没有被召回、排得靠不靠前。与生成质量无关，先单独测这一段。
- **生成评测**：给定召回结果，看最终回答是否只依据上下文（忠实度）、是否真的答到了点上（相关性）。
- 评测要有一套人工标注的评测集（golden set）：「问题 → 应命中的片段 → 参考答案」，一次建好、长期复用、每次改动后回归。指标与建法见 [RAG-评测与分块策略](AI与大模型/RAG/RAG-评测与分块策略.md) §3、§5。

## 4. 原理剖析

- **向量相似为什么能代表语义相近**：embedding 模型训练的目标就是让语义相近的文本在向量空间里距离近。检索本质上是在这个空间里找「离问题最近的几块文本」。模型换了，空间就换了，所以换模型必须重建库。
- **块为什么是检索的最小单位**：向量是对整块文本算出来的，一块混多个主题，向量会被平均，召回谁都不像；块太小，上下文不完整，模型答不全。块的目标大小要在「单块信息完整」和「召回精度」之间权衡。
- **TopK 为什么不能贪多**：上下文窗口是稀缺资源，给多了模型反而抓不住重点（长上下文的中部信息召回率会掉），还烧 token。先靠检索与重排把候选筛到最相关的几条，再生成。
- **RAG 为什么能降幻觉、不能根治**：有依据片段时，模型照着答，出错率明显下降；但召回错了、片段本身有错、或模型无视上下文，照样会编。所以评测要分检索与生成两段，定位错在哪一段。

## 5. 实战应用：从零跑通一条最小链路

以下为最小链路的步骤（以本库小说引擎的 RAG 原型思路为准，原型见 `rag_chroma_eg2.py`，Chroma + Ollama 本地 embedding 模型；该原型目前先放着、暂不切换，见本库相关记录）：

1. **准备文档**：先拿 10–20 篇已经结构化的笔记当语料，别一上来倒整个库。
2. **解析与切分**：按段落/标题切，超长段再兜底硬切；块之间留 10%–20% overlap。
3. **向量化入库**：每块算一个向量，连同原文与来源路径一起存进向量库（Chroma）。
4. **提问检索**：把问题同样向量化，捞回 Top 5，看正确片段在不在里面、在第几位——这一步先不生成，只看检索。
5. **生成回答**：把 TopK 片段拼进提示词，temperature 取 0.1–0.3，让模型照着回答，并让它标出依据。
6. **建评测集**：人工写 20–30 个「问题 → 应命中片段 → 参考答案」，每次改切分、换模型、调 TopK 后都回归跑一遍。

**先跑通、再放大**：最小链路跑通前，不要加混合检索、不要加 Rerank、不要调参。链路不通时加的每个环节都会让定位更难。

## 6. 疑难杂症

- **提问后什么都召不回来**：先定位三段中的哪一段——切分：问题里的关键句是不是正好被切口切开了？向量化：查询与文档用的是否为同一模型、同一度量？检索：TopK 是不是设得太小？逐段查，别一起改。
- **召回来的全是沾边的**：块可能太大、主题太杂，向量被平均了；或只有向量一路在干活，没加关键词一路融合。先看 [混合检索与Rerank](AI与大模型/RAG/混合检索与Rerank.md)，再看分块。
- **召回对了，模型还是乱编**：生成环节的问题——提示词有没有写明「只依据给出的片段回答，不知道就说不知道」；temperature 是不是太高；片段是不是给多了、模型抓不住重点。
- **换了 embedding 模型效果反而变差**：先确认旧库重建了没有；再确认查询与入库用的是同一模型、同一度量；最后确认新模型是否明确支持中文。

## 7. 常见误区

- **「上了 RAG 就不会幻觉了」**：RAG 降低幻觉，不根治。召回错、片段错、模型无视上下文，照样编。
- **「块越大，信息越全，效果越好」**：块太大，一个块混多个主题，向量被平均，召回谁都不像。
- **「TopK 越大越保险」**：给多了模型抓不住重点，还烧 token；先筛到最相关的几条再生成。
- **「向量库越大越准」**：库大但切分与检索没做好，召回照样差；先做评测集，再谈规模。
- **「不用评测，凭感觉调」**：感觉调参等于蒙。先建评测集、跑出基线数字，再改一个变量、再测一次。

## 8. 性能优化

- **先测再优化**：评测集跑出基线（召回率、忠实度）之前，不要动参数；每次只改一个变量。
- **TopK 与块大小联动调**：块切小了，TopK 要相应放大才够信息量；块切大了，TopK 可以收小。
- **数据量小别急着上 ANN 索引**：万级以内精确暴力检索也够用；HNSW、IVF、PQ 是数据量上去之后才划算的取舍，见 [向量检索深水](AI与大模型/RAG/向量检索深水.md)。
- **overlap 控制在 10%–20%**：再大就是等比例放大索引体积和重复召回。

## 9. 版本差异

- **RAG 是架构模式，不是某个框架的某个版本**：切分 → 向量化 → 召回 → 重排 → 生成 → 评测这条链路不随框架版本变；变的是各环节的默认实现（如某框架默认切分器的参数）。
- **embedding 模型在换代**：新模型出来，先看中文支持、输出维度、最大输入长度三项，再决定要不要换；换了就必须重建库。
- **长上下文模型变长，不等于 RAG 没用了**：窗口变长解决「塞得下」，不解决「找得准」和「知识截止」；RAG 的价值从「塞进窗口」转向「精准找、给出处」。

## 小技巧与冷知识

- RAG 这个名字是 2020 年论文起的，「检索增强」的「增强」指的是增强生成时的上下文，不是增强模型本身——模型权重一点没动。
- 调 RAG 先问一句「错在哪一段」：切分、召回、生成三段分开测，定位快十倍；最常见的坑是三段混在一起调。
- 评测集不用大：20–30 条人工标注的「问题 → 应命中片段 → 参考答案」，够跑出基线、够回归，就够起步了。
- 小说文本切分有个天然优势：章、场景是天然语义边界，应作为切分的第一优先级，而不是一上来按固定长度横切。

## 10. 面试与自测

1. RAG 是什么？它解决大模型的哪三个短板？
   - 参考答案：RAG 是检索增强生成：回答前先从知识库检索相关片段，再把片段作为上下文交给模型生成。补的短板：① 知识有截止时间，之后的事只能靠检索查；② 私有知识不在训练语料里；③ 直接问容易幻觉，给了依据片段答案有出处。
2. RAG 全链路是哪六步？哪一步出问题会导致「答案横跨切口召不回来」？
   - 参考答案：切分 → 向量化 → 召回 → 重排 → 生成 → 评测。切分步：块是检索的最小单位，答案正好被切口切开就召不回来；overlap 取块长 10%–20% 可缓解。
3. 向量检索和关键词检索（BM25）各擅长什么？为什么主流做法是两路融合再重排？
   - 参考答案：向量检索按语义距离找，擅长同义、换说法；BM25 按字面匹配，擅长专有名词、编号、精确词。单一路都有盲区，两路融合（RRF 等）再用 cross-encoder 重排，互补。
4. 为什么换 embedding 模型必须重建向量库？
   - 参考答案：向量是模型算出来的，换模型等于换了一套坐标系，旧向量全部作废；入库和查询还必须用同一种相似度度量。
5. RAG、微调、长上下文直塞分别适合什么场景？
   - 参考答案：RAG 适合知识常变、私有资料、要给出处；微调适合改模型行为风格与特定任务能力，不适合知识频繁更新；长上下文适合文档很少、一次问完，文档量大时烧 token 且中部召回差。三者可叠加。
