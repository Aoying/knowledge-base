# RAG 评测与分块策略

> RAG 的效果由三段决定：**切得对不对（分块）→ 找得准不准（检索评测）→ 答得忠不忠（生成评测）**。没有评测集，所有调参都是玄学；本篇的目标是把小说引擎那套 RAG 原型从「能跑」推进到「可量化对比」。
>
> 说明：本篇涉及与小说引擎原型绑定的效果结论，凡未经实测的一律标注「待验证」，不拿通用经验冒充项目结论。

## 1. 核心概念

- **分块（chunking）**：入库前把长文档切成可独立向量化的小段。块是检索的最小单位——块切错，后面 embedding 再好也召不回来。
- **检索评测**：给定一批带标准答案的问题，看正确片段有没有被召回、排得靠不靠前。与生成质量无关，先单独测这一段。
- **生成评测**：给定召回结果，看最终回答是否只依据上下文（忠实度）、是否真的答到了点上（相关性）。
- **评测集（golden set）**：人工标注的「问题 → 应命中的片段 → 参考答案」集合，是全部指标的计算基准，一次建好、长期复用、每次改动后回归。

三段要分开测：最终答案不好，可能是没切好、没召回、或召回了但模型乱编。混在一起调，永远不知道该改哪。

## 2. 基础知识：四种分块策略

| 策略 | 切法 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| 固定长度 | 每 N 字符/Token 一刀，带 overlap | 实现最简单，行为可预期 | 在句子/段落中间硬切，语义破碎 | 快速原型、无结构文本 |
| 按段落/结构 | 沿空行、标题、Markdown 层级切，超长段再兜底硬切 | 块即自然语义单元 | 段落长度不均，超短段信息量不足 | 有明确结构的文档 |
| 递归切分 | 按分隔符优先级（标题→段落→句子→词）逐级递归切到目标大小 | 兼顾结构与长度上限，主流框架默认 | 参数组合多，要调 | 通用文档，默认起点 |
| 语义切分 | 用 embedding 相似度找话题转折点再切 | 块内主题最纯 | 成本最高（切分本身要算向量），稳定性依赖模型 | 长叙事文本 |

通用经验（非本项目实测）：

- overlap 一般取块长的 10%–20%，解决「答案正好横跨切口」的问题；overlap 不是越大越好，它会等比例放大索引体积和重复召回。
- 块的目标大小要在「单块信息完整」和「召回精度」之间权衡：块太小，上下文不完整，模型答不全；块太大，一个块混多个主题，向量被平均，召回谁都不像。
- 切分单位用 Token 而非字符数更贴近模型与 embedding 的实际处理方式，中英文混排时差异尤其明显。

小说文本的特殊性（结构事实，非效果结论）：

- 章、场景是天然语义边界，应作为切分的第一优先级，而不是一上来按固定长度横切；原型 `rag_chroma_eg2.py` 目前是「段落粗分 + 超长硬切 + overlap」，与递归切分的思路接近。
- 人物对话和心理描写跨段连续，按段落切容易把一个回合的问答切开——是否需要「对话回合」级别的合并策略，**待验证**。

## 3. 进阶知识：评测指标

**检索段指标**（只需标注「问题 → 正确片段」，不用跑模型，便宜，应高频跑）：

- **Recall@k**：前 k 个结果里命中的正确片段占全部正确片段的比例。RAG 最看重的底线指标——正确片段根本没进上下文，生成再强也白搭。
- **Hit Rate@k**：至少命中一个正确片段的问题占比，比 Recall 更粗，适合快速看趋势。
- **MRR**：第一个正确片段排名的倒数均值。衡量「对的排得够不够靠前」，影响模型实际用不用得上（排在第 9 位的片段很容易被忽略或截断）。
- **Precision@k / nDCG**：Precision 看前 k 里有多少是噪声；nDCG 综合考虑相关程度与位置。调 rerank 时主要看这两个和 MRR。

**生成段指标**（要跑模型 + 需要评判，成本高，低频跑）：

- **忠实度（Faithfulness）**：回答里的每个论断能否在上下文中找到依据。小说引擎场景下这是防「模型编造剧情事实」的核心指标。
- **答案相关性（Answer Relevancy）**：回答有没有正面答问题，而不是复述上下文。
- **上下文精度/召回（Context Precision/Recall）**：喂给模型的上下文里有用信息的比例与覆盖——RAGAS 一类框架把上述几项打包实现，思路可借鉴，不必迷信某个框架的分数口径。

**端到端任务指标**（最终裁判）：脱离 RAG 单项指标，用业务结果验收。例如小说引擎：拿一批人工埋了矛盾的测试章节，看「矛盾检出率」和「误报率」——RAG 改造（换分块、换 embedding）后这两个数有没有变好。单项指标涨但任务指标不涨，就是白改。

## 4. 原理剖析

- **为什么分块和 embedding 必须一起评**：向量是块内全部内容的语义平均。块的主题越杂，向量越「谁都不像」；同一 embedding 模型在不同分块下召回率可以差出一个量级，所以报召回数字时必须同时报分块配置，否则数字不可比。
- **维度与模型切换的影响**：embedding 换模型（如从 768 维换到 2048 维）等于换了一套坐标系，向量库必须全量重建，新旧结果不可直接混排比较；双后端版原型为此做了「后端+维度」守卫，防的就是拿旧库跑新模型还不自知。
- **评测集的统计意义**：二三十条样本的指标波动极大，Recall 差 5 个百分点可能纯属噪声；起步不少于 50 条，关键对比拉到 100 条以上再下结论。指标要带样本量一起报。

## 5. 实战应用：评测集怎么建（小说引擎）

构建步骤（一次投入，长期复用）：

1. **选题**：从已有章节里挑真实会问的问题类型——人物状态（「第 40 章苏晚知道哪些秘密」）、伏笔追踪（「源石第一次出现在哪一章」）、时间线（「林溯到尼泊尔之前发生了什么」）、关系（「江衡和白言何时决裂」）。每类 10–20 条。
2. **标片段**：每条问题人工标注应命中的章节/片段 ID（可多个），标注人就是你自己，别让模型标——模型标的「标准答案」会把评测变成自问自答。
3. **标参考答案**：一两句话的事实性答案，供生成段评测对照；顺带记录「绝不能出现的编造点」（如人物当时还不知道某秘密），专门用来抓忠实度问题。
4. **留难样本**：故意放进需要跨章拼接的问题（单章查不到答案）、和「库里根本没有」的问题（正确行为是答不知道），这两类最能暴露系统短板。

最小评测脚本骨架（检索段，不跑生成模型）：

```python
def recall_at_k(retrieved_ids: list[str], gold_ids: set[str], k: int) -> float:
    hits = len(set(retrieved_ids[:k]) & gold_ids)
    return hits / len(gold_ids) if gold_ids else 0.0

def mrr(retrieved_ids: list[str], gold_ids: set[str]) -> float:
    for i, doc_id in enumerate(retrieved_ids, start=1):
        if doc_id in gold_ids:
            return 1.0 / i
    return 0.0

# 遍历评测集：对每题调检索 → 累计 Recall@5、MRR → 输出均值 + 逐题明细
# 逐题明细必须留：均值只告诉你好不好，明细才告诉你坏在哪类问题上
```

**待验证清单**（以下结论只能由原型实测得出，跑完评测后回填本篇）：

- 《残契者》语料上，递归切分 vs 现有「段落+硬切」在 Recall@5 上的差距——待验证。
- 按「章/场景」切分是否优于纯文本策略、对哪类问题（人物状态/伏笔/时间线）收益最大——待验证。
- embeddinggemma-2（768 维）与 Nemotron-3.5-Embed-1B（2048 维）在本评测集上的召回对比——待验证（双后端版已备好，切换即可同集对比）。
- overlap 取 10% 与 20% 对伏笔类长跨度问题的实际影响——待验证。


## 检索评测集构建

前文「实战应用」一节讲的是小说引擎建集的四步（选题、标片段、标参考答案、留难样本），那是“做什么”。本节讲“怎么做才可信”：问题集、标注、负样本、防泄露。两节是互补关系，不重复。

### 问题集构造：分布先对齐，措辞要多样

- **分布对齐真实提问**：评测集的问题类别比例应接近真实问题分布，而不是每类平均配。按真实提问日志的类别比例配；上线前没有日志时，按预期用途估计比例并把假设记下来，日后有日志再校准。只测高频问题会高估系统，因为高频问题往往也最容易召回。
- **同一意图多种问法**：同一信息需求写出两三种问法（正式问法、口语问法、关键词式问法），防止评测集只测到一种措辞、系统换个说法就失效。统计时注意权重：同一意图的不同问法按意图组看结果，避免一个意图刷多条、无形中抬高权重。
- **长尾问题专门留比例**：低频实体、早期内容、冷门类别要有名额。系统在高频题上全对、在长尾题上全错，均值依然好看，但真实用户体验是坏的。
- **边界问题单独成类**：
- 指代不明：同名实体、多义指代，标注时写明本题指哪一个，系统答到另一个不算对。
- 多跳拼接：需要跨多处片段才能回答的题，标注每一跳的 gold 片段；只命中其中一跳不算全对（前文已提跨章拼接，此处是标注口径的补全）。
- 时效性问题：答案随语料版本变化的题，标注时写明适用版本，语料更新后复核这类题。
- 无答案问题：库里根本没有答案的题，正确行为是答不知道（前文留难样本已提）。计分口径要单列：无答案题不计入 Recall 分母，单独统计拒答率与误答率，否则会把“诚实说不知道”算成召回失败。

### 答案标注：人工是基准，模型只能提候选

- **人工标注是基准**：前文已定“标注人就是你自己，别让模型标”，本节不推翻这条，只补效率与一致性做法。
- **模型辅助标注的取舍**：模型可以提候选（给出它认为相关的片段排序），人做裁决（确认、否决、补标）。模型省的是“找片段”的时间，不能定“什么是标准”。凡模型提名、人未复核的条目不进 gold 集；辅助标注的比例要记录在案，口径变了要能追溯。
- **标注指南先行**：动笔前先写半页指南，至少定三条：什么算 gold（直接回答问题的片段与仅起背景支撑作用的片段分两级——核心片段与支撑片段，Recall 只算核心，分析时再看支撑）；一个问题 gold 片段的上限（太多说明问题太宽，应该拆题）；同名实体、时间表述的判定规则。指南不清，两个人标同一题会标出两套标准。
- **一致性抽查**：隔一段时间重标一小批旧题（或换人复标），看前后是否一致；不一致率高先修指南、再修标注，不要直接改分数口径。

### 负样本构造：没有负样本，看不出排序的好坏

- **为什么需要**：Recall 只看“对的找没找到”；Precision、nDCG 和 rerank 效果要靠负样本才能看出。系统把“看起来相关、实际答非所问”的片段排前面时，Recall 全绿也发现不了。
- **难负样本为主**：同一主题但答非所问——同一人物不同时期、同一事件不同视角、同一术语不同含义。这类最能检验排序质量，应占负样本大头。
- **易负样本保底**：随机抽的无关片段。系统连无关片段都排前面，说明检索本身已经坏了，先修检索再谈排序。
- **负样本不进 gold 集**：只用于分析误召回类型（哪类负样本最容易被误排前面），不计入 Recall 分母。

### 数据泄露防护：评测集一旦污染，分数全部作废

- **评测问题不能进索引**：不要把评测集的问题与参考答案以文档形式写进知识库或语料库（例如别为评测题专门建一篇问答文档入库）。一旦问题原文进了索引，召回测的就是“背诵”不是“检索”。
- **评测问题不能进微调数据**：embedding 微调、生成模型微调、rerank 训练都不能用评测题。用评测题调过参的方案，要换一版未见过的留出集重测才能报数。
- **开发集与留出集分离**：日常调参用开发集，定稿验收用留出集；留出集只在关键对比时跑，平时不动。拿着留出集反复调参，等于把它也变成了开发集，验收分数不再可信。
- **索引版本隔离**：评测时冻结索引版本，跑批中不写库。前文疑难杂症已有“增量写脏”一条，此处是制度版：评测跑批前记录索引版本，跑批中任何写入都要等评测结束。

## 6. 疑难杂症

- **评测分数很好，实际用着很差**：评测集太简单或与真实问题分布不符。把实际使用中答错的问题持续回填进评测集，它应该越用越「难」。
- **换了 embedding，分块没动，分数反而降**：先怀疑评测口径——新模型对块长、语言分布的敏感点不同，可能要连带调整块大小；也可能是旧库没重建干净、新旧向量混排（见第 4 节守卫）。
- **生成答案编造但检索指标全绿**：问题在生成段不在检索段——查提示词有没有「只依据上下文回答、无依据就说不知道」的硬约束，以及拼进上下文的片段顺序与截断策略。
- **同一评测两次跑分数不同**：生成段评测天然有随机性（温度、评判模型波动），固定温度与种子、检索段指标应保持完全可复现，对不上先查索引是否被增量写脏。

## 7. 常见误区

- 不建评测集，靠「感觉这个回答不错」调参：感觉样本量等于 1，且专挑顺眼的看。
- 只测检索不测生成，或反之：前者漏掉编造问题，后者出了错不知道锅在哪一段。
- 拿公开 benchmark 的分数推断自己语料的效果：小说叙事文本和新闻/百科语料分布差很远，公开分数只能当选型参考，结论必须在自己的评测集上复现。
- 分块、embedding、rerank 一次全换：分数变了也不知道是谁的功劳/锅。一次只动一个变量，是评测的基本纪律。
- 评测集一成不变用到老：语料在长（新章节、新人物），评测集要跟着扩，否则优化的是昨天的分布。


## 消融实验

前文「常见误区」只给了一条纪律（一次只动一个变量），「原理剖析」给了样本量口径（起步不少于 50 条，关键对比 100 条以上）。本节是完整操作法：基线怎么定、四个变量怎么做对照、差异怎么判、结论怎么写。

### 对照设计：一次只改一个因素

- **基线先冻结**：先定一套基线配置（分块、embedding、召回路数、rerank 开关）并跑出基线分数；之后每次实验只改一处，改完与基线比。基线配置要随结果一起记录（模型名＋维度＋分块配置，前文「版本差异」一节已有此要求），没有配置头的结果不可比。
- **四个变量的消融示例**（每个都是独立实验，不是一次全做）：
- 切分大小：其余全不动，只换块大小方案；看 Recall@k 与 MRR 的变化，顺带记索引体积变化（块数×维度，前文「性能优化」一节有此关系）。
- 召回路数：单路向量召回 vs 向量＋关键词混合召回（见混合检索与Rerank）；只改路数，不动分块与 rerank。
- 重排开关：rerank 开 vs 关；只看排序指标（MRR、nDCG、Precision@k）是否变化。Recall@k 不应变——rerank 只改变顺序，不改变召回集合；如果 Recall 变了，说明重排实现偷偷改了召回范围，先查实现再谈结论。
- 嵌入模型：模型甲 vs 模型乙；必须全量重建索引（前文「原理剖析」：换模型等于换坐标系），新旧向量混排的对比结果作废。
- **交互效应要单列**：单因素消融只能回答“这个因素单独有没有用”。两个因素联动才有效果时（例如大块与 rerank 联合），单因素实验会漏掉。重要联动要补做组合实验，但结论要写明是“组合效应”，不能归功于其中一个因素。

### 结果显著性判断：先看样本量，再看逐题差异

- **样本量不够先按“看不出”处理**：沿用前文口径，起步不少于 50 条，关键对比 100 条以上。样本量不够时，任何差异都先按“看不出”处理，不写“略优／略差”。
- **看逐题差异，不只看均值**：新方案均值高，要看是“多数题小幅变好”，还是“少数题大幅变好、多数题持平或变差”；后者不可轻信，可能是个别题型的偶然收益。前文评测脚本骨架要求留逐题明细，明细就是干这个用的。
- **检索段与生成段区别对待**：检索段指标可完全复现，重复跑同一配置分数不变——重复跑不能用来“刷显著性”。生成段有随机性（温度、评判波动），同一配置要固定温度与种子、多跑几轮取平均；轮次间波动大于方案间差异时，结论写“未见显著差异”。
- **差异小时的决策**：差异小到在噪声范围内时，不采纳、不写“微优”；要么扩大样本量重测，要么直接放弃该改动。为噪声级别的提升付出维护成本不值。

### 消融结论的写法：改动—指标变化—是否采纳

- **固定句式**：改动（改了什么、基线是什么）—指标变化（哪个指标、变化方向与幅度、样本量）—是否采纳（采纳／不采纳／待扩大样本重测）。句式示例（占位写法，不是实测数字）：
- 基线配置 A，单改因素 B；评测集 N 条，检索指标变化方向、生成指标变化方向、端到端任务指标变化方向；采纳／不采纳／待扩大样本重测，理由一句话。
- **采纳标准以端到端为准**：前文「评测指标」一节已定，单项指标涨但任务指标不涨就是白改；单项指标涨、任务指标不动的改动不采纳。
- **负结果也要记录**：不采纳的改动写进“已试过”清单（改了什么、为什么没采纳），防止半年后有人重试同一条路。消融记录与评测结果一起归档，配置头与版本号同前文「版本差异」一节。

## 8. 性能优化

- 检索段评测不跑生成模型，成本低、速度快，应作为每次改动的默认回归；生成段评测贵，只在大改或定期跑。
- 索引体积由「块数 × 维度」决定：减小块尺寸、加大 overlap、换高维 embedding 都会放大体积与检索延迟，调参时和质量指标一起看。
- 父子块（小块检索、返回其所属大块/整段上下文）是兼顾召回精度与上下文完整的常用折中，是否适合小说语料——待验证。
- 评测脚本本身做缓存：同一评测集 + 同一索引版本，检索结果落盘，改生成提示时不用重跑检索段。

## 9. 版本差异

- 评测框架（RAGAS 等）的指标定义与实现细节随版本变化，跨版本比分数前先确认口径一致；本篇指标定义以第 3 节的文字定义为准，不绑定某框架版本。
- embedding 模型与索引强绑定：模型版本一换就重建索引并重跑全量评测，版本号（模型名+维度+分块配置）应作为每次评测结果的固定标注头。

## 小技巧与冷知识

【小技巧】评测时的 k 要和上线实际喂给模型的片段数对齐：上线只喂 5 条、评测却报 Recall@10，分就虚高了，正确片段排在第 6 到 10 位在评测里算命中、上线根本进不了上下文。评测 k 应等于上线 top_k 的上限，想看排序潜力再另报一个更大的 k 做对照，别拿它当主指标。

【小技巧】overlap 有没有生效，要靠“接缝处问题”来验收：专门挑答案正好横跨两个块切口的问题放进评测集，这类题 Recall 上不去，就是 overlap 没起作用或切口位置不对。只测普通问题看不出 overlap 的价值，因为答案在块中间时有没有 overlap 都能召回。

【小技巧】overlap 区被两个块同时召回时，拼上下文前先去重合并：同一段话占了两份上下文窗口不说，模型还会把它当成两个独立证据重复加权，本来只有一份来源的说法看起来像被多方印证。做法是按来源位置把重叠块合并成一段再拼进提示词，合并后仍要算进 token 预算。

【冷知识】ChromaDB 默认的距离不是余弦相似度，而是平方 L2 距离（`hnsw:space` 默认 `"l2"`），想用余弦要建集合时显式传 `metadata={"hnsw:space": "cosine"}`。对单位归一化的向量两者排序结果一致，但返回的距离数值含义不同；直接拿默认 L2 距离当“相似度分数”设阈值过滤，会筛掉一批本该留下的结果，阈值口径要和距离度量一起记。

【冷知识】MRR 对第一名特别敏感：第一个正确片段排第 2 位，MRR 只有 0.5；排第 1 位就是 1.0。调 rerank 时 MRR 涨 0.05，可能只是少数题从第 2 名升到第 1 名，不代表整体排序变好了；看 MRR 变化时一定要配逐题明细，确认是多数题小幅前移还是个别题跳变。

【小技巧】生成段评测开跑前，先把同一配置原样连跑两次，量出“波动带宽”：两次分数的差就是这套评测的噪声底线，之后方案间差异小于这个带宽一律按“未见显著差异”处理。原文要求固定温度与种子，这条补上前提——不先量噪声，固定温度也分不清“方案变好了”还是“这次运气好”。

【小技巧】父子块召回后返回父块时，要按展开后的 token 数重新算预算：top-5 小块展开成 5 个大块，上下文很容易超窗，模型实际只看到前两三个，排在后面的等于白召回。做法是先定上下文总预算，再按父块大小反推小块的 top_k，或者只展开得分最高的一两个父块，其余只给小块原文。

## 10. 面试与自测

1. Recall@k 和 MRR 分别回答什么问题？为什么 RAG 先保 Recall 再谈其他？
2. 固定长度、递归、语义三种分块的取舍是什么？给小说文本选分块，你的第一直觉是什么、要靠什么验证它？
3. 最终答案出现编造，但 Recall@5 很高，你判断问题出在哪一段、怎么验证？
4. 为什么说「换 embedding 模型必须重建索引」？新旧向量混排会发生什么？
5. 一个只有 20 条样本的评测集得出「新方案 Recall 高 10%」，你信不信，为什么？

### 参考答案

1. Recall@k 回答「正确片段找没找到」：前 k 个结果里命中的正确片段占全部正确片段的比例；MRR 回答「对的排得够不够靠前」：第一个正确片段排名的倒数均值。RAG 先保 Recall，因为正确片段根本没进上下文，生成再强也白搭——它是底线指标，排位问题要在找得到的前提下再谈。

2. 固定长度实现最简单、行为可预期，但会在句子/段落中间硬切，语义破碎；递归切分按分隔符优先级（标题→段落→句子→词）逐级切，兼顾结构与长度上限，是主流默认起点，但参数组合多、要调；语义切分按 embedding 相似度找话题转折点，块内主题最纯，但成本最高、稳定性依赖模型。给小说文本的第一直觉是章、场景是天然语义边界，应优先按章/场景切；但这只是直觉，必须靠评测集上的 Recall@5/MRR 实测对比验证——本篇把这类结论都标为待验证，不拿通用经验冒充项目结论。

3. 问题在生成段，不在检索段：Recall@5 高说明正确片段已经召回。验证分两步：①查提示词有没有「只依据上下文回答、无依据就说不知道」的硬约束；②查拼进上下文的片段顺序与截断策略（关键片段是否被截断、是否排在模型注意不到的位置）。同时用忠实度指标核对：回答里的每个论断能否在上下文中找到依据。

4. 向量是块内容在某个 embedding 模型坐标系下的表示；换模型等于换了一套坐标系，维度也可能变（如 768 维换 2048 维），旧向量与新向量不在同一空间，距离完全不可比。新旧混排会使排序失真、召回不可信，还会让「换模型后分数下降」无法定位（可能是旧库没重建干净）。所以换模型必须全量重建索引，双后端版原型为此做了后端+维度守卫。

5. 不信。20 条样本的指标波动极大，Recall 差 5 个百分点可能纯属噪声，10% 的差距在这么小的样本上很可能也在噪声范围内。本篇的口径是：起步不少于 50 条，关键对比拉到 100 条以上再下结论；而且指标要带样本量一起报，不带样本量的提升数字不可比。
