# Godot

开源免费的 2D/3D 游戏引擎（MIT 协议，真免费无抽成），轻量（几十 MB、免安装解压即用），适合碎片时间做小 demo。对 Java 后端的额外价值：游戏循环、状态机、事件驱动的设计思想，和流程引擎/ Agent 状态机是相通的。

> 时效性：版本信息 2026-10-17 已验证（godotengine.org 下载页、官方文档 release policy）。

## 版本（2026-10）

- 当前稳定：**Godot 4.7.2**（2026-08 发布）；4.8 在开发中。学 4.x 系列即可，核心概念跨小版本稳定。
- 两个渲染器：Forward+（桌面高画质，需 Vulkan）和 Compatibility（OpenGL，低端机/网页导出用）。
- C# 版需另装 .NET SDK；纯 GDScript 版开箱即用。

## 核心概念

- **节点（Node）**：一切皆节点。精灵、碰撞体、计时器、UI 按钮都是节点。
- **场景（Scene）**：节点组成的树，可保存复用。做游戏 = 拼场景 + 给节点挂脚本。
- **GDScript**：Python 风格的动态语言，缩进定代码块，上手极快。示例：

```gdscript
extends CharacterBody2D

@export var speed := 200.0

func _physics_process(delta):
    var dir := Input.get_vector("ui_left", "ui_right", "ui_up", "ui_down")
    velocity = dir * speed
    move_and_slide()
```

- **信号（Signal）**：Godot 的观察者模式，节点间解耦通信。按钮被点 → 发出 `pressed` 信号 → 任意节点连接处理。理解成事件总线即可。
- **游戏循环**：`_process(delta)` 每帧调用（渲染相关）、`_physics_process(delta)` 固定步长（物理/移动，防帧率差异）。

## 5 个常见坑

1. **`@onready` 之前访问节点**：节点在 `_ready()` 前可能还没进树，用 `@onready var x = $Node` 声明，别在成员初始化时直接 `$Node`。
2. **物理写在 `_process` 里**：帧率一变速度就变，移动/碰撞必须用 `_physics_process(delta)`。
3. **信号连重了**：编辑器里连一次、代码里又 `connect` 一次，回调执行两遍；统一一种方式。
4. **导出网页白屏**：十有八九是 `file://` 直接打开或用了 Forward+ 渲染器，切 Compatibility + 起 HTTP 服务。
5. **资源路径用绝对路径**：项目换机器就炸，统一用 `res://` 开头的项目相对路径。

## 疑难杂症

### 1. 中文显示全是方框
- **现象**：Label 写中文，运行出来是口口口。
- **原因**：默认字体不含 CJK 字形。
- **解决**：导入一个中文字体（ttf/otf），在主题或 Label 的 Font 里指定；注意字体文件体积，移动端用子集化字体。

### 2. 大版本升级后项目打不开
- **现象**：3.x 项目用 4.x 打开，报错或场景全乱。
- **原因**：Godot 大版本不保证兼容（3→4 改动极大）。
- **解决**：升级前完整备份；用官方迁移工具走一遍；新项目直接定一个 LTS 版本别中途换。

### 3. 导出预设突然丢失
- **现象**：昨天还能导出，今天导出预设没了。
- **原因**：`export_presets.cfg` 没进版本控制，或换了机器/重装 Godot。
- **解决**：`export_presets.cfg` 提交进 git；导出模板（export templates）按版本装好，别和编辑器版本搞混。

## GDScript 进阶

```gdscript
# await：等信号/等一帧，不用回调地狱
await get_tree().create_timer(1.0).timeout
await $Button.pressed

# signal 带参数 + 动态连接
signal hp_changed(old, new)
hp_changed.emit(100, 80)
$Enemy.hp_changed.connect(_on_hp_changed)

# Callable 存起来当回调
var cb: Callable = _on_hp_changed
cb.call(100, 80)

# 上下文无关的工具函数放 static
static func clamp_hp(v): return clampi(v, 0, 100)
```

- `await` 后面跟信号是最常用的写法（等动画播完、等网络回来），比 `_process` 里轮询干净。
- 信号连重了会触发多次，连接前 `if not is_connected(...)` 判一下。
- 性能敏感处（每帧跑的）别频繁 `get_node`，`@onready` 缓存引用。

## 2D 实战：TileMap + 碰撞层

```gdscript
# TileMapLayer（4.x 写法）+ CharacterBody2D 移动模板
extends CharacterBody2D
@export var speed := 200.0
func _physics_process(_delta):
    var dir := Input.get_vector("ui_left", "ui_right", "ui_up", "ui_down")
    velocity = dir * speed
    move_and_slide()
```

- 地形画在 TileMapLayer 上，碰撞用"物理层"单独画，别和美术层混一起。
- 碰撞层（Layer）vs 监测掩码（Mask）：Layer 是"我是谁"，Mask 是"我撞谁"；玩家 Layer=1、Mask=2（墙），子弹 Layer=4、Mask=2。
- 调物理手感三个数：`speed`、`acceleration`（用 `velocity.move_toward` 做平滑）、跳跃的 `gravity`。

## 基础知识补强

### 核心概念与术语

- 游戏引擎：一套现成的游戏地基，管渲染、物理、音频、输入、资源加载；你只写玩法逻辑，不用从画像素开始造轮子。
- 渲染：把场景数据变成屏幕像素的过程；引擎每帧重画一次，帧率就是一秒画多少次。
- 帧（Frame）：一帧就是画面的一次完整更新；程序里说的"每帧执行"就是随这个节拍执行。
- delta：上一帧到这一帧的真实秒数。一切"按时间"的移动都要乘 delta，帧率变了速度才不变。
- 场景树：运行中的游戏就是一棵活的节点树，父节点移动/旋转/隐藏，子节点整体跟着变，这是 Godot 最核心的心智模型。
- 变换（Transform）：位置、旋转、缩放三件套；子节点的实际位置是"父变换叠自己的变换"，不是自己填的那个数。
- 资源（Resource）：与节点分离的数据资产，如图片、音频、自定义数据文件；多个节点可引用同一份资源，改一处全生效。
- 输入映射（Input Map）：给按键起逻辑名（如 jump、move_left），代码只认逻辑名；换键位改映射即可，不用改代码。
- 分组（Group）：给节点贴的标签，运行时可按组批量找节点（如所有敌人），相当于给场景树加的索引。
- 自动加载（Autoload）：挂为全局单例的场景或脚本，任何地方可直接访问，常用来放全局状态、音频管理、存档。

### 基础知识与用法

2D 坐标系先钉死，这是所有位置 bug 的总源头：

```text
Godot 2D：原点在屏幕左上角，X 向右增，Y 向下增（和屏幕像素一致，与数学课相反）
单位默认是像素。节点 position 表示它相对父节点原点的偏移。
角度：正角度顺时针转（因为 Y 朝下）；向量 (0, -1) 是"向上"，(0, 1) 是"向下"。
3D 约定：Y 向上，角色面朝 -Z 方向，地面是 XZ 平面。
```

向量的四个基本操作（GDScript 示例，移动、瞄准全靠它们）：

```gdscript
var a := Vector2(3, 4)
a.length()            # 长度 = 5（勾股定理）
a.normalized()        # 单位化，只保留方向，长度变 1
var dir := (target_pos - my_pos).normalized()   # 朝向目标的方向
a.dot(b)              # 点积：判断夹角，>0 同向，=0 垂直，<0 反向
velocity = dir * speed  # 方向 × 速率 = 速度，游戏里最常见的一行
```

三种 2D 物理体怎么选（原文讲了碰撞层，这里补身体本身的区别）：

| 类型 | 谁驱动 | 典型用途 |
|---|---|---|
| StaticBody2D | 不动，谁也推不动 | 墙、地面、平台 |
| CharacterBody2D | 代码驱动，自己写速度 | 玩家、可控角色 |
| RigidBody2D | 物理引擎驱动，吃重力和力 | 掉落物、箱子、弹跳球 |
| Area2D | 不挡人，只监测谁进来 | 触发区、拾取物、伤害区 |

- 选错典型症状：让 RigidBody 当玩家，控制手感全是物理反馈，调不动；让 CharacterBody 模拟掉落，又得自己写重力。

节点生命周期顺序，记这条链就够了：

```text
实例化 → _init（对象刚造出来，节点还没进树，别碰别的节点）
      → 进入场景树 → 子节点先 _ready，父节点后 _ready
      → 逐帧 _process / _physics_process
      → 移出树时 _exit_tree（收尾、断信号放这里）
_ready 只跑一次；反复进出树的节点别把一次性初始化假设写死在别处。
```

GDScript 基础语法补充一小段（进阶节之外的地基部分）：

```gdscript
var hp := 100               # := 表示类型由右边推断
var names: Array[String] = ["a", "b"]   # 数组，可带元素类型
var cfg := {"speed": 200, "jump": -400}  # 字典，键值对

for i in range(3):          # 循环 0,1,2；也可以直接 for x in names
    print(i)
if hp > 50 and not names.is_empty():    # 条件与逻辑运算，写法近 Python
    print("hp=%d" % hp)     # % 做字符串格式化
```

动画与音频只记两个基础抓手：

- AnimationPlayer：把"属性随时间变化"录成动画片段，代码里按名 play；角色跑跳切换本质是切片段加混合。
- 音频分总线（Bus）管理：背景音乐、音效、语音各走一条总线，音量、静音统一调，别在每个音效节点上散调。

### 关键机制速览

- 父子变换叠加：子节点填的是相对坐标，父节点一动子节点跟着动，UI 和角色挂点（武器挂手上）都靠这条。
- 树的处理顺序与层级无关的还有 Canvas 层：UI 和世界分属不同画布层，UI 永远压在游戏画面之上，不受相机影响。
- 信号是单向通知：发出方不知道谁在听；在编辑器里连和代码里连是同一份连接关系，重复连接就会重复触发。
- 资源引用是共享的：两个敌人引用同一份属性资源时，运行时改了一个的资源值，另一个可能跟着变，需要独立副本时记得复制资源。
- 实例化场景就是"把一份场景模板克隆成活节点塞进树"，预加载保证克隆时不卡顿，适合频繁生成的子弹、敌人。
- 物理帧与渲染帧解耦：物理固定步长保证手感稳定，渲染帧率浮动不影响物理结果，卡顿严重时物理会追帧补算。
- 帧率与耗时换算：60 帧约等于每帧 16.7 毫秒预算，单帧逻辑超过这个数就开始掉帧，定位卡顿先看哪帧超时。

### 新手易错点

- 方向不归一化就乘速度：手写方向时右加下得到斜向向量，长度是直向的约 1.4 倍，斜着跑明显更快，对比时以为是错觉。
- 整数相除丢小数：两个整数相除结果仍是整数，需要小数结果时先把一侧写成浮点（如 5.0 / 2），比例计算最常中招。
- 把计时写成"每帧加一"：帧率一变计时就全错，计时一律用 delta 累加秒数，或直接用计时器节点。
- 全局到处找节点：跨场景用长路径取节点，树一改名就全线报空；固定协作走信号或分组，少写死路径。
- 误以为改资源等于改单个实例：共享资源被多处引用时改一处影响全局，调数值前先确认这份资源是不是独享的。
- 在 _init 或成员变量初始化里访问场景树：此时节点还没进树，取子节点必然为空，凡是依赖树的引用统一放 _ready 之后。
- 3D 里拿 2D 直觉套坐标：2D 是 Y 向下，3D 是 Y 向上、前方是 -Z，两套约定来回切项目时最容易在这里栽。

## 小技巧与冷知识

【小技巧】删节点用 `queue_free()`，别直接用 `free()`：`free()` 是立即释放，在信号回调或遍历子节点时调用很容易让正在执行的代码拿到已释放的节点而崩溃；`queue_free()` 只是把节点排进删除队列，等当前帧结束才真正释放。凡是“在别的节点触发的回调里删自己/删别人”，一律用 `queue_free()`。

【小技巧】判断角色是否落地，用 `move_and_slide()` 之后的 `is_on_floor()`：它只在刚执行过 `move_and_slide()` 的同一物理帧内有效，跳跃、落地音效、二段跳的判断都要紧跟在它后面写。把它写在 `_process` 里、或者在 `move_and_slide()` 之前调用，读到的都是上一帧的旧状态，跳跃手感会莫名其妙地时灵时不灵。

【小技巧】游戏里的鼠标点击用 `_unhandled_input` 而不是 `_input`：`_input` 是最先收到的，UI 按钮还没来得及消费事件，游戏逻辑就已经先响应了，结果就是点按钮的同时也触发了场景里的点击。`_unhandled_input` 只在 UI 都没处理这个事件时才触发，点按钮和点场景就能干净分开。

【小技巧】在物理回调里改碰撞体必须用 `set_deferred`：比如受伤无敌期间想临时关闭碰撞，在 `_on_body_entered` 里直接写 `$CollisionShape2D.disabled = true` 会报错，因为物理引擎正在遍历碰撞体。写成 `$CollisionShape2D.set_deferred("disabled", true)`，等物理步结束再改，就不会触发这个错误；同理，物理回调里改节点树结构要用 `call_deferred`。

【小技巧】暂停游戏别只写 `get_tree().paused = true`：默认模式的节点会停，但 `get_tree().create_timer()` 建的计时器默认是不受暂停影响的（`process_always` 为 true），倒计时、敌人生成计时会在暂停界面继续跑。建计时器时显式传 `create_timer(1.0, false)` 让它跟随暂停，或者把暂停菜单的节点 `process_mode` 设为“Always”，菜单按钮才能在暂停时继续响应。

【小技巧】跨层级取节点用 `%唯一名`，别写死长路径：把节点勾上“Access as Unique Name”后，全场景任何地方用 `%Player` 就能拿到它，中间加一层父节点、改个名字都不会断。长路径 `$World/Level1/Player` 是原文易错点里“全局到处找节点”的重灾区，`%` 语法就是官方给的解药。

【小技巧】调试只跑当前场景按 F6，跑整个项目按 F5：改一个小场景时没必要每次都从主场景进，F6 直接运行当前打开的场景，启动快得多。F6 的场景如果依赖自动加载的全局单例也能正常跑，因为 Autoload 是随项目启动的，不依赖从主场景进入。

【小技巧】`load()` 和 `preload()` 分工不同：`preload()` 在脚本解析时就把资源读进内存，适合开场就用的主角、主场景；`load()` 是运行时按需加载，适合关卡切换、按需生成的敌人。把所有资源都 `preload` 会拖慢启动，把高频生成的子弹、敌人写成 `load()` 又会在生成瞬间卡顿，启动资源与动态资源要分开。

【小技巧】点按和长按要分开判断：`Input.is_action_pressed("jump")` 只要按住就一直为真，适合持续奔跑、蓄力；`Input.is_action_just_pressed("jump")` 只在按下的那一帧为真，适合跳跃、开火这种“按一下触发一次”的动作。跳跃写成 `is_action_pressed` 会导致按住空格连跳，用错一个函数手感全变。

【小技巧】取鼠标位置分清屏幕坐标和世界坐标：`get_viewport().get_mouse_position()` 拿到的是屏幕像素位置，相机一动就对不上场景里的东西；`get_global_mouse_position()`（CanvasItem 的方法）已经换算成世界坐标，瞄准、点击地面移动直接用它。相机跟随角色时还用屏幕坐标算瞄准，准星会跟着相机漂。

【小技巧】相机跟随开平滑、加边界：`Camera2D` 的 `position_smoothing_enabled` 能让相机平滑追上角色，而不是死死粘在角色身上，跑动时画面不抖；再把 `limit_left/right/top/bottom` 设成地图边缘，相机就不会拍到地图外的黑边。两个开关都在检查器里，十分钟就能让一个 demo 的观感上一个台阶。

【小技巧】俯视角游戏的遮挡关系开 Y 排序：把父节点的 `y_sort_enabled` 打开后，子节点按 Y 坐标自动排前后，走到树后面的角色会被树挡住，走到前面则挡住树。没开 Y 排序时遮挡只看节点在树里的先后顺序，角色绕到树后还是画在树前面，立体感全无。

【小技巧】场景和脚本文件是纯文本，放进 git 非常友好：`.tscn` 场景文件是人类可读的文本格式，改了什么、谁改的，`git diff` 一眼就能看出来，合并冲突也能直接打开文本修。别把场景当二进制黑盒，版本控制、代码审查那套流程对 Godot 项目同样适用。

【小技巧】只用一次的回调连信号时加 `CONNECT_ONE_SHOT`：`$Button.pressed.connect(_on_pressed, CONNECT_ONE_SHOT)` 会在第一次触发后自动断开，不用再手写 disconnect。开场动画播完切场景、一次性对话触发这类“只跑一次”的连接最适合，省掉“忘了断开导致回调重复执行”的坑。

【冷知识】Godot 的名字来自贝克特的戏剧《等待戈多》（Waiting for Godot）：作者 Juan Linietsky 觉得这个名字很贴切——引擎就像剧中那个永远在等待、从未现身的戈多，而开发者就是在等待中把游戏做出来的人。读音是 go-DOH，重音在后。

【冷知识】Godot 最初是阿根廷 OKAM 工作室的内部引擎：Juan Linietsky 和 Ariel Manzur 在 2000 年代为自家游戏开发，2014 年以 MIT 协议开源。这也是它“真免费无抽成”的由来——从一开始就不是商业公司用来卖授权的产品，而是做游戏的人顺手开源的工具。

【冷知识】Godot 4.0 历时三年多才发布（2023 年 3 月）：3.x 到 4.0 是一次彻底重写，渲染器换成 Vulkan、GDScript 换成静态类型优先、物理引擎换掉，改动大到官方专门写了迁移指南。这也是原文“大版本升级后项目打不开”的历史根源——3→4 不是常规升级，是一次换代。

【冷知识】GDScript 的 `await` 在 4.0 才真正成为语言级特性：3.x 时代等信号要靠 `yield` 函数，写法啰嗦还容易漏恢复；4.0 把 `await` 做进语法后，等计时器、等动画、等信号都变成一行代码。原文进阶节里的 `await get_tree().create_timer(1.0).timeout` 就是这套新写法的典型用法。

【冷知识】Godot 编辑器本身也是用 Godot 做的：编辑器界面就是一个运行在 Godot 场景树上的 Godot 程序，编辑器的很多面板、控件用的都是引擎自带的 UI 节点。想给编辑器加功能时，写编辑器插件和写游戏用的其实是同一套节点与信号机制。

## 面试与自测

1. `_process(delta)` 和 `_physics_process(delta)` 各管什么？为什么移动/碰撞必须写在后者里？
2. 信号连重了会发生什么？`@onready` 之前访问节点为什么会取到空？
3. Godot 2D 坐标系与数学课有什么不同？方向向量不归一化就乘速度会出什么问题？计时为什么不能“每帧加一”？

### 参考答案

1. `_process(delta)` 每帧调用，管渲染相关；`_physics_process(delta)` 固定步长，管物理/移动，防帧率差异。物理写在 `_process` 里帧率一变速度就变，所以移动/碰撞必须用 `_physics_process(delta)`。
2. 编辑器里连一次、代码里又 `connect` 一次，回调会执行两遍；要统一一种方式，连接前可用 `if not is_connected(...)` 判一下。节点在 `_ready()` 前可能还没进树，用 `@onready var x = $Node` 声明，别在成员初始化时直接 `$Node`；在 `_init` 或成员变量初始化里访问场景树时节点还没进树，取子节点必然为空，依赖树的引用统一放 `_ready` 之后。
3. Godot 2D 原点在屏幕左上角，X 向右增，Y 向下增（和屏幕像素一致，与数学课相反）；3D 则是 Y 向上、前方是 -Z。方向不归一化就乘速度时，右加下得到的斜向向量长度是直向的约 1.4 倍，斜着跑明显更快。一切“按时间”的移动都要乘 delta，计时一律用 delta 累加秒数或直接用计时器节点，“每帧加一”帧率一变计时就全错。
