# 分布式系统理论

## 1. 核心概念

分布式系统难，不是因为节点多，而是三件事同时成立：**网络会断、节点会挂、各台机器没有共同的时钟**。单机上天然成立的假设（调用非成即败、数据只有一份、时间单调递增）全部失效，后面所有理论都是在给这三件事打补丁。

本篇只讲理论框架：CAP、一致性谱系、共识、故障模型、时钟、分布式 ID。事务协议细节见 [分布式事务](数据库/分布式事务.md)——那篇讲协议怎么做，本篇讲为什么只能这么做。

- **副本**：同一份数据存多份，是高可用和读扩展的前提，也是一致性问题的源头。
- **分区（Partition）**：节点间网络不通。分区不等于宕机，两边都活着、都在服务，才是最危险的形态。
- **共识（Consensus）**：一组节点对同一个值达成一致且不再反悔，是选主、多副本一致的地基。

## 2. 基础知识：CAP 与 BASE

**CAP**：分区（P）发生时，一致性（C，读必得最新写）和可用性（A，请求必有响应）只能选一个。P 不是选项——跨机器部署，分区迟早发生，真正的选择只有分区时保 C 还是保 A：

| 选择 | 分区时行为 | 代价 | 典型 |
|---|---|---|---|
| CP | 少数派一侧拒写/拒服务 | 牺牲可用性 | OceanBase、ZooKeeper、银行账务 |
| AP | 两边继续读写 | 产生冲突，恢复后合并/对账 | Redis Cluster、消息通知 |

两个误读先排除：CAP 的 C 不是 ACID 的 C；也没有「三选二」——无分区时 C、A 可兼得，定理只约束分区那一刻。

**BASE** 是 AP 路线的工程化表述：基本可用（降级也算可用）、软状态（允许「处理中」中间态）、最终一致（停写后副本收敛）。它不是协议，是柔性方案的底座，与本地消息表、Saga 同源。

## 3. 进阶知识：一致性模型谱系

一致性不是二选一，是一条谱系。每往弱走一档，可用性和吞吐上一台阶，业务多付一份心智成本：

| 档位 | 保证 | 实例 |
|---|---|---|
| 强一致 / 线性一致 | 写完所有人立刻可见，像单机 | OceanBase 单租户内读写 |
| 顺序一致 | 全局操作顺序一致，不保证实时 | 共识系统内部语义 |
| 因果一致 | 有因果的操作不乱序 | 回复必在原文之后、审批意见链 |
| 读己之写 / 单调读 | 自己写的能读到，版本不倒退 | 读写分离的最低配置 |
| 最终一致 | 只保证最终收敛 | Redis 主从、Kafka 消费、通知 |

选型判断表——本篇的核心结论，先问「读到旧数据是资金错误还是体验问题」，再问「冲突能否自动合并」：

| 场景 | 档位 | 代价 |
|---|---|---|
| 审批状态、额度、账务 | 强一致（CP） | 可用性让步、吞吐最低、靠共识兜底 |
| 刚提交后自己回查 | 读己之写 | 关键路径读主或等 LSN 追平 |
| 评论、计数、搜索索引 | 最终一致 | 容忍秒级旧数据，要对账兜底 |
| 短信/站内通知 | 最终一致 + 重试 | 晚到可接受，强一致纯属白付性能税 |

中间档最实用：MySQL 主从读写分离（见 [MySQL 主从复制](数据库/MySQL-主从复制与读写分离.md)）做不到全量强一致，但至少要保「读己之写」——刚提交的审批单刷新就消失，用户会以为数据丢了。

## 4. 原理剖析：共识算法

共识一句话：**多节点对一串操作的顺序达成一致，且定下的不许反悔**（状态机复制：同序回放，状态自然一致）。难点是节点会挂、消息会丢会乱序时，仍保证值唯一且系统能继续走。

- **Paxos**：两阶段（Prepare 抢编号、Accept 定值）+ 多数派交叉保证唯一。正确但难实现，工程多用变体：OceanBase 多副本日志同步就是 Paxos 系——多数派确认才算提交，少数派分区自动停写，正是 CP 的落地。
- **Raft**：拆成选主、日志复制、安全性三块。强 Leader 制，写全过 Leader，过半确认即提交；Leader 挂了任期（term）加一重选。etcd、TiKV 用它。抓三点够用：term 是逻辑时钟、日志只从 Leader 流向 Follower、多数派保证不选出两个合法 Leader。
- **多数派为什么是底线**：任意两个多数派必有交集，新 Leader 必看得到已提交数据。代价是副本取奇数（3/5）：偶数不增容错只增成本。

共识之上怎么做原子提交，看 [分布式事务](数据库/分布式事务.md) 与 [OceanBase](数据库/OceanBase.md)。

## 5. 实战应用：故障模型与脑裂

设计前先声明你假设世界能坏到什么程度：

| 模型 | 假设 | 说明 |
|---|---|---|
| 崩溃故障 | 节点只停机不作恶 | 多数内部系统只需防这个 |
| 遗漏故障 | 消息可丢、延迟无上限 | 超时区分不了「挂了」和「很慢」 |
| 拜占庭故障 | 节点会撒谎发矛盾消息 | 区块链/跨机构场景才需要，成本极高 |

第二行最要命：**超时 ≠ 宕机**。下游超时，它可能没处理、可能回包丢了、可能正在处理，对应完全不同的重试策略。所以跨系统调用必须配幂等键 + 状态查询，不能傻重试。

分区的典型事故是**脑裂**：Redis Cluster 靠 gossip 探活和故障转移，但分区把主节点与多数派隔开时，少数派侧旧主可能继续写，恢复后这批数据被覆盖丢弃。`min-replicas-to-write` 本质是给 AP 打 CP 补丁：副本不够就拒写。Kafka 同理，ISR 收缩时若开不干净选主，会选出最落后的副本当 Leader 丢数据，见 [Kafka 消息队列](消息队列/Kafka-消息队列.md)。

系统对号入座——一条业务链上两档混用才是常态：

| 系统 | 理论落点 |
|---|---|
| OceanBase（神农 e 贷） | Paxos 强一致；审批/额度/台账同租户同库靠引擎共识，不在应用层自造分布式事务 |
| Flowable 审批流 | 强一致：流程状态不可事后合并且要可审计 |
| Kafka（翼安反诈） | `acks=all` + 最小 ISR 才是金融级可靠；消费端靠幂等收成效果上的恰好一次 |
| Redis Cluster | 缓存可最终一致；借它做锁/库存要开写门槛，接受脑裂丢数风险 |
| 短信/消息通知 | 最终一致 + 本地消息表 + 日终对账，拆出主链路异步走 |

一句话：**核心账务向左（CP、共识兜底），周边触达向右（AP、对账兜底）。**

## 6. 疑难杂症

- **主从延迟读到旧数据**：本质是最终一致窗口，不是 bug。先在档位上承认延迟，解法是关键路径读主或等从库追平 LSN。
- **Redis 脑裂后数据回滚**：分区期少数派写入在恢复后被覆盖。事前靠副本写门槛预防，事后只能业务对账捞，Redis 自己不合并。
- **时钟与排序**：物理时钟靠 NTP 同步，误差毫秒到秒级还会回拨，两台机器的 `now()` 定不了先后。跨节点定序一律用逻辑序号——Raft 的 term、Kafka 的 offset、数据库 LSN 都是逻辑时钟变体；审批判先后看流程历史表，对账按流水号，都不按时间戳。用时间戳做「最后写入者胜」，等于把裁决权交给时钟误差。
- **雪花 ID 重复**（分布式 ID 见下节）：十有八九是时钟回拨或机器号重复分配，先查 NTP 记录和机器号分配表，不要先怀疑算法。

## 7. 常见误区

- 误区：CAP 是三选二。P 不能选，选的只有分区时保 C 还是保 A。
- 误区：最终一致 = 不一致。它是有收敛保证的弱档位；没有对账和幂等配套的才叫裸奔。
- 误区：上了分布式数据库就不用懂理论。OceanBase 屏蔽实现不屏蔽选型——副本数、读写档位定错照样出事。
- 误区：副本越多越可靠。偶数副本不增容错，跨机房副本还拉高提交延迟。

## 8. 性能优化

- **一致性降档是最便宜的优化**：读能容忍秒级旧数据就走副本，别全压主库；账务类不降。
- **批量摊薄共识**：Kafka 批量发送、OB 日志组提交，把多次共识合成一次。
- **超时与重试设预算**：无退避重试在分区时会把活节点也压死，退避 + 上限 + 熔断配套用。

## 9. 版本差异

理论不分版本，实现口径在变：Kafka 早期靠 ZooKeeper 选主，新版 KRaft 把共识收进 Raft 自实现；其余系统的判据细节随版本演进，参数查当前版本官方文档。

## 10. 面试与自测

- 分区发生时 CP 与 AP 分别发生什么？各举一个你项目里的例子。
- 多数派为什么要奇数副本？3 副本和 4 副本容错差在哪？
- Raft 的 term 起什么作用，为什么说它是逻辑时钟？
- 超时为什么推不出对方宕机？这对接口设计提出什么硬要求？
- 分布式 ID 除了雪花还有什么方案？雪花（时间戳 + 机器号 + 序列，见 [分库分表](数据库/分库分表.md)）的命门是什么，号段模式和 UUID 各适合做哪类 ID？
- 设计「放款成功后的多渠道通知」：一致性选哪档，兜底是什么？

### 参考答案

1. 分区时 CP 侧少数派拒写/拒服务，保一致性、牺牲可用性；AP 侧两边继续读写，保可用性，恢复后合并/对账。项目里的例子：CP 如 OceanBase 上的神农 e 贷审批状态、额度、账务（同租户同库靠引擎共识，少数派分区自动停写）；AP 如 Redis Cluster 缓存、短信/站内通知（晚到可接受，恢复后对账）。注意 P 不是选项——跨机器部署分区迟早发生，选的只是分区时保 C 还是保 A。

2. 多数派是底线，因为任意两个多数派必有交集，新 Leader 必看得到已提交数据，多数派保证不选出两个合法 Leader。奇数是因为偶数不增容错只增成本：3 副本容 1 个故障，4 副本同样只容 1 个，多花的副本白付了成本和提交延迟；要容 2 个故障得上 5 副本。

3. term 是任期编号：Leader 挂了，term 加一重选。它是逻辑时钟，因为它用单调递增的编号定序和裁决新旧——选主时比较 term，旧 Leader 在新 term 下的写不再合法；而不依赖物理时钟（NTP 同步有毫秒到秒级误差还会回拨，两台机器的 now() 定不了先后）。Raft 的 term、Kafka 的 offset、数据库 LSN 都是逻辑时钟变体。

4. 超时区分不了「挂了」和「很慢」：遗漏故障模型下消息可丢、延迟无上限，下游超时可能是没处理、回包丢了、也可能正在处理，三种情况对应完全不同的重试策略。这对接口设计提出的硬要求是：跨系统调用必须配幂等键 + 状态查询，不能傻重试——否则一次超时重试就可能造成重复放款、重复通知这类重复副作用。

5. 除了雪花，还有号段模式和 UUID。雪花的命门是时钟回拨（以及机器号重复分配）：时间戳回拨会使新 ID 小于已发 ID，十有八九的雪花重复都是先查 NTP 记录和机器号分配表，不要先怀疑算法。号段模式适合需要大致有序、数据库索引友好的业务单号（批量取号、顺序性要求高）；UUID 适合去中心化生成、无需协调、无需顺序、只要全局唯一的场景（如无业务含义的随机主键、去重键）。

6. 一致性选最终一致：通知晚到可接受，强一致纯属白付性能税。兜底是本地消息表 + 日终对账：放款成功先把通知写本地消息表、拆出主链路异步发送，重试保证最终送达，日终对账捞出漏发的补发。主链路只保证放款本身强一致，通知走 AP 路线——核心账务向左（CP、共识兜底），周边触达向右（AP、对账兜底）。
