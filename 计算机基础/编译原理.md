# 编译原理

> 骨架篇：先建立整体地图，各阶段细节按需再展开。

## 1. 核心概念

编译器把源代码翻译成目标代码，同时做检查与优化。经典流程五段：

```
源码 → 词法分析 → 语法分析 → 语义分析 → 优化 → 代码生成 → 目标代码
       字符流     Token流     AST       带类型标注的AST   中间代码   机器码/字节码
```

理解编译流程的现实价值：看懂编译报错的位置与含义、理解 AST 后能读懂各种代码工具（格式化、Lint、代码生成、SQL 解析器）的工作原理。

## 2. 基础知识：各阶段做什么

| 阶段 | 输入→输出 | 典型产物/报错 |
|---|---|---|
| 词法分析 | 字符流 → Token 流 | 关键字、标识符、字面量、运算符；非法字符报错 |
| 语法分析 | Token 流 → AST | 按文法递归下降/LL/LR 构建树；括号不配、语法错误 |
| 语义分析 | AST → 带符号表的 AST | 类型检查、作用域解析；未定义变量、类型不匹配 |
| 中间代码与优化 | AST → IR | 常量折叠、死代码删除、循环优化 |
| 代码生成 | IR → 目标代码 | 寄存器分配、指令选择 |

## 3. AST 是核心数据结构

抽象语法树（Abstract Syntax Tree）把代码的语法结构变成树：节点是运算/语句，子节点是操作数。`1 + 2 * 3` 的 AST 是 `+(1, *(2,3))`——树的形状本身就编码了优先级，所以后续阶段不再处理括号问题。

几乎所有代码工具都工作在 AST 上：IDE 的重构、ESLint/Checkstyle 的规则、MyBatis 把 XML/SQL 模板解析成节点树、规则引擎解析表达式。能"把一段代码画成 AST"，编译原理就入了门。

## 4. 与日常开发的关联

- **JDK 编译**：`javac` 把 `.java` 编译为字节码 `.class`（前端，止步于代码生成）；运行期 JIT（C1/C2）再把热点字节码编译为机器码，属于"二次编译"，这也是 Java 预热慢、跑久了更快的原因。
- **注解处理器**（Lombok、MapStruct）在语法/语义分析阶段介入，修改或生成 AST——Lombok 的"魔法"本质是编译期改树。
- **SQL 解析**：数据库执行 SQL 前同样走词法→语法→语义（表/列校验）→优化（生成执行计划）→执行；看执行计划就是在看数据库的"优化阶段"产物。Druid 的 WallFilter、ShardingSphere 的分片改写都基于 SQL 的 AST。
- **模板与 DSL**：Flowable 的表达式、规则引擎、小说引擎里若要做剧情规则表达式求值，都会遇到"自己写一个小编译器/解释器"的问题，套路都是这五段的子集。

## 5. 解释器与编译器

- 编译型：先整体翻译再执行（C、Rust）；解释型：逐句翻译执行（早期脚本语言）。
- 现代语言多为混合：Python 编译为字节码再由虚拟机解释执行（所以有 `.pyc`），Java 是字节码 + JIT。分类的关键不在语言，而在实现。
- 还有一类转译（transpile）：TypeScript → JavaScript、各种 SQL 方言互转，流程与编译完全相同，只是目标仍是高级语言。

补充两个高频概念：

- **符号表**：语义分析阶段维护的"名字 → 类型/作用域"登记表，未定义变量、重复定义都在查这张表时发现。
- **语法制导**：很多工具（表达式求值、配置解析）不建完整 AST，而在语法分析动作里顺手计算或生成代码，简单 DSL 常用。

## 6. 常见误区

- 把"编译慢"等同于编译器差：大型项目编译慢多在依赖解析与增量失效，原理层面的阶段划分有助于定位。
- 以为报错行就是出错行：语法分析是"发现无法继续"时才报错，真正的错误常在前一行（如少分号、括号错位从上一处开始）。

## 9. 一句话总结

编译器 = 把代码变树、对树做检查与加工、再把树变回代码；看懂这条线，报错、工具、SQL 与表达式引擎都不再是黑盒。
