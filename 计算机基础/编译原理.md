# 编译原理

## 1. 核心概念

编译器把源代码翻译成目标代码，同时做检查与优化。经典流程五段：

```
源码 → 词法分析 → 语法分析 → 语义分析 → 优化 → 代码生成 → 目标代码
       字符流     Token流     AST       带类型标注的AST   中间代码   机器码/字节码
```

理解它的现实价值：看懂编译报错的位置与含义，并读懂各种代码工具（Lint、代码生成、SQL 解析器）的工作原理。

## 2. 词法分析：把字符流切成 Token

词法分析器（Lexer）按模式扫描源码，切出最小语义单位 Token：关键字、标识符、字面量、运算符、界符。每个 Token 带类型和值，如 `chapter` → `IDENT("chapter")`。

- Token 的模式用**正则表达式**描述，识别引擎是**有限自动机**（DFA）：状态转移表驱动，扫一遍字符串即完成，所以极快。
- 词法层只管"切得对不对"：`3x` 不是合法 Token 在这层报错；而 `int x = ;` 每个 Token 都合法，要到语法层才报错。定位错误时先分清是哪一层。空白与注释在此被丢弃（Python 例外，缩进产生 INDENT/DEDENT Token）。

## 3. 语法分析：把 Token 流组成 AST

语法分析器（Parser）按**文法**（通常写成 BNF）把 Token 流组织成抽象语法树。两大流派：

- **递归下降（LL 家族）**：每个非终结符写一个解析函数，靠向前看几个 Token 决定走哪条规则。手写解析器几乎都是它，直观、报错友好；运算符优先级靠分层函数（expr → term → factor）表达。
- **LR 家族**：查表驱动，能处理更宽的文法；yacc/bison、ANTLR 等生成器吃一份文法文件吐一个解析器，适合规模较大的语言/DSL。

**优先级与结合性**就发生在这层：`1 + 2 * 3` 的 AST 是 `+(1, *(2,3))`——`*` 子树更深、先算，树的形状本身编码了优先级，后续阶段不再处理括号。

几乎所有代码工具都工作在 AST 上：IDE 重构、ESLint 规则、MyBatis 的 SQL 模板、规则引擎表达式。能"把一段代码画成 AST"，编译原理就入了门。

## 4. 语义分析：在树上查"合不合法"

语法对 ≠ 语义对。语义分析遍历 AST 做静态检查：

- **符号表**：维护"名字 → 类型/作用域/声明位置"的登记表，通常是带作用域栈的哈希表（进代码块压栈、退出弹栈）。未定义变量、重复定义、作用域外引用都在查它时发现。
- **类型检查**：给表达式节点标注类型并校验运算合法——`String + int` 在 Java 里合法（拼接）、在另一些语言里报错，就是这层的规则不同。类型不匹配、方法签名对不上都在此拦截。
- **注解处理器**（Lombok、MapStruct）在此阶段介入修改或生成 AST——Lombok 的"魔法"本质是编译期改树。

产出是一棵"带类型标注的 AST"，优化与代码生成不再回头查名字。

## 5. 中间代码与优化

- **中间表示（IR）**：与机器无关的中间语言（三地址码、SSA 等）。前端只管"源码→IR"、后端只管"IR→机器码"，LLVM 生态就是靠它组合多语言多平台；JVM 字节码也是 IR 的一种。
- **典型优化**：常量折叠（编译期先算 `3 * 24 * 60`）、死代码删除、循环不变量外提、函数内联——大多是 IR/AST 上的等价变换，做之前必须证明不改变语义，这也是优化最容易引入 bug 的地方。
- **代码生成**：IR → 目标代码，核心难题是寄存器分配（变量多、寄存器少，谁进寄存器谁溢出到栈）。javac 止步于字节码，机器码生成留给运行期 JIT。

## 6. 与日常开发的关联

- **JDK 编译与 JIT**：`javac` 是前端（到生成字节码为止）；运行期 JIT 把热点字节码再编译为机器码，属"二次编译"，这也是 Java 预热慢、跑久了更快的原因。
- **SQL 解析与执行**：数据库执行 SQL 走同一条流水线：词法→语法→语义（表/列校验）→优化（生成执行计划）→执行，看执行计划就是看"优化阶段"的产物；Druid 的 WallFilter 防注入、ShardingSphere 的分片改写都基于 SQL 的 AST——注入能被识别，是因为改写后的 AST 形状变了。
- **规则引擎与表达式**：Flowable 的流程条件、审批规则、小说引擎的剧情规则（如"林溯不知道父母已死亡时禁止引用这条信息"）若要做成可配置表达式，就会遇到"自己写一个小编译器/解释器"的问题：定义 Token、写文法、递归下降建 AST、遍历求值，套路是五段的子集。SpEL、MVEL、Aviator 内部都是这套结构。
- **DSL 与模板**：接口文档生成、构建工具配置语言本质都是"小语言"，判断值不值得自己造，先看要不要类型检查与报错定位——要，就得老实走完前三段。FreeMarker 等模板引擎同样是先把模板解析成节点树再渲染。

## 7. 解释器与编译器

- 编译型先整体翻译再执行（C、Rust）；现代语言多为混合：Python 编译为字节码再由虚拟机解释执行（所以有 `.pyc`），Java 是字节码 + JIT。分类关键不在语言，而在实现。
- 转译（transpile）：TypeScript → JavaScript、SQL 方言互转，流程与编译相同，只是目标仍是高级语言。
- **语法制导**：简单工具（表达式求值、配置解析）不建完整 AST，而在语法分析动作里顺手计算，简单 DSL 常用。

## 8. 常见误区

- 把"编译慢"等同于编译器差：大型项目编译慢多在依赖解析与增量失效，按阶段划分有助于定位。
- 以为报错行就是出错行：语法分析是"发现无法继续"时才报错，真正的错误常在前一行（如少分号、括号错位从上一处开始）。
- 以为学编译原理只是为了造语言：多数人一辈子不造语言，但每周都在用它的产物——报错、Linter、SQL、表达式引擎都是这条流水线的变体。

## 小技巧与冷知识

【小技巧】写递归下降解析器前，先把文法的左递归改掉：expr → expr + term 这种规则会让解析函数无限递归下去。改写成循环形式 expr → term (('+' | '-') term)*，一次循环吃掉一串同级运算符，解析函数就不会再自己调自己。LL 解析器处理不了左递归不是实现问题，是方法本身的限制，改文法是唯一出路。

【小技巧】词法切分遵循“最长匹配”：源码里的 == 要切成一个等号 Token，不能切成两个赋值 Token；写 Lexer 时先按最长匹配取 Token，再处理关键字与标识符的冲突——关键字先查表，查不到才是普通标识符。顺序写反了，if、while 这些关键字会被当成变量名，语法层再也救不回来。

【小技巧】报错信息里除了行号，还要带上源码片段和指向符号：Token 除了类型和值，再记一个起始偏移，报错时把出错行原文截出来、在出错位置画个 ^。javac、rustc 的报错之所以好读，关键就在这一步；自己写小解析器时先把位置信息打通，后面所有报错都受益，IDE 的跳转和高亮也靠同一份位置数据。

【小技巧】运算符一多就别再加解析函数层，改用 Pratt 解析（优先级攀登）：一张表定义每个二元运算符的优先级和结合性，解析循环按优先级决定“当前运算符要不要先算”。加一个新运算符只需在表里加一行，不用再拆一层 expr/term/factor；这是 Vaughan Pratt 在 1973 年提出的办法，很多语言的表达式解析器内部都是它。

【小技巧】调试语法问题时先把 AST 按缩进打印出来：优先级、结合性、括号嵌套在树形打印里一眼可见，比对着文法空想快得多。树打出来发现 * 挂在了 + 上面，说明优先级分层写反了；发现括号里的子树跑到外面去了，说明括号的解析函数没把子表达式包住。看树，不看代码，是定位语法 bug 最短的路。

【小技巧】文法歧义的经典例子是悬空 else：if (a) if (b) s1; else s2; 里 else 归属内层 if 还是外层 if，文法本身没说清楚。多数语言约定 else 归属最近的 if，生成器遇到这种文法会报移进-归约冲突；自己写文法时要显式写清这个约定，否则冲突会一直跟着项目走。

【小技巧】写计算器类小工具可以先上调度场算法：Dijkstra 在 1961 年提出的 shunting-yard 算法把中缀表达式转成后缀表达式，优先级和括号在转换过程里一次处理完，不用写完整文法。表达式求值、配置里的简单算式用它就够了；等到要加变量、函数、类型检查时，再升级成完整 AST 方案。

【小技巧】读 LLVM IR 时看到 %1、%2 这种只赋值一次的变量名，就是 SSA 形式：每个变量只被赋值一次，要“改值”就产生一个新变量。SSA 让数据流分析变得简单——一个变量的定义点唯一，找“谁给它赋值”不用再翻整段代码。现代优化器大多先把 IR 转成 SSA 再做优化，Cytron 等人在 1991 年的论文里系统化了这套做法。

【小技巧】分清“编译期能算的”和“运行期才知道的”，常量折叠才不会用错：3 * 24 * 60 是字面量，可以在编译期先算；final 变量、配置文件里的值，要看编译器能不能在编译期确定它的值——Java 的常量表达式判定规则就是这条线。优化的前提永远是“语义不变”，死代码删除、循环不变量外提之前，先确认被移动的代码没有副作用，有打印、IO 的调用不能随便外提或删除。

【小技巧】符号表查名字时按作用域从内到外找：先查当前代码块，再查外层，最后查全局；内层同名变量盖住外层同名变量，就是影子变量（shadowing）。查表顺序写错，语义分析就全错——内层变量会被当成外层变量，外层变量又可能被误判为未定义；作用域栈“进块压栈、出块弹栈”这个结构，就是为了保证这个查找顺序。

【小技巧】想理解 JIT 的行为，先看 -XX:+PrintCompilation 的日志：JVM 的 C1、C2 两级编译会在日志里留下方法被编译的记录，能看到哪个方法先被 C1 快速编译、热点方法又被 C2 重新编译优化。预热慢、跑久了变快不是玄学，日志里看得见编译发生的时机；调优之前先跑一次日志，再决定是代码问题还是预热问题。

【小技巧】寄存器分配难，本质是图着色问题：变量之间“同时存活”就不能共用一个寄存器，把变量画成节点、同时存活的连边，分配寄存器就等于给图着色，颜色不够就把变量溢出到栈上。Chaitin 在 1982 年把这套方法系统化，现代编译器的寄存器分配器大多是它的变体；理解了图着色，就理解了为什么“变量多、寄存器少”时编译器要往栈上 spill。

【冷知识】Lex 和 Yacc 都是 1975 年贝尔实验室的产物：Lex（Mike Lesk、Eric Schmidt）负责词法分析，Yacc（Stephen Johnson）负责语法分析，名字里的 lex 是 lexical analyzer、yacc 是 Yet Another Compiler-Compiler。Unix 上一代代编译器工具链都从它俩起步，今天的 Flex 和 Bison 就是它们的开源后代。

【冷知识】编译领域的“龙书”《Compilers: Principles, Techniques, and Tools》第一版是 1986 年，作者 Aho、Sethi、Ullman，封面画着一位骑士与一条龙——骑士代表编译器、龙代表复杂性。这本书之后再版封面换成了紫龙，但“龙书”这个叫法一直留了下来，是编译原理领域最常被引用的教材。

【冷知识】GCC 最初是 GNU C Compiler，1987 年由 Richard Stallman 发布，最初只支持 C 语言；后来支持的语言越来越多，才改名为 GNU Compiler Collection。LLVM 则是 Chris Lattner 在 2000 年于伊利诺伊大学厄巴纳-香槟分校启动的研究项目，名字原本是 Low Level Virtual Machine 的缩写，后来官方不再展开这个缩写。

【冷知识】Ken Thompson 在 1984 年的图灵奖演讲《Reflections on Trusting Trust》里证明：编译器可以在编译 login 程序时悄悄植入后门，而源码里完全看不出来——后门藏在编译器自身里，连重新编译都洗不掉。这篇演讲揭示了自举编译器的信任链问题：你信任的不是源码，是编译它的那个编译器。

【冷知识】Go 和 Rust 都经历过“换语言重写自己”：Go 1.5（2015 年）把编译器从 C 重写为 Go，完成了自举；Rust 编译器最初是用 OCaml 写的，2011 年完成了自举，之后一直用 Rust 自己编译自己。编译器自举是语言成熟的标志——能用自己编译自己，说明语言已经够表达编译器这种复杂程序了。

【冷知识】ANTLR 的作者 Terence Parr 从 1989 年就开始做解析器生成器，ANTLR 这个名字是 ANother Tool for Language Recognition 的缩写。它和 Yacc 最大的区别是生成递归下降解析器而不是查表解析器，生成的代码可读、报错信息友好，是手写解析器和生成器之间的一条中间路线。

## 9. 面试与自测

1. 五个阶段的输入输出各是什么？
2. AST 相比源码字符串多解决了什么问题？
3. javac 与 JIT 分工是什么？为什么 Java 程序跑久了变快？
4. 数据库执行一条 SQL 前经历了哪些与编译类似的步骤？
5. 递归下降为什么要分 expr/term/factor 三层函数？

### 参考答案

1. 词法分析：字符流→Token 流；语法分析：Token 流→AST；语义分析：AST→带类型标注的 AST；优化：带类型标注的 AST/中间代码→优化后的中间代码；代码生成：中间代码→目标代码（机器码/字节码）。定位报错先分清是哪一层：词法层只管切得对不对（如 3x 不是合法 Token），int x = ; 要到语法层才报错。

2. AST 多解决的是结构：树的形状本身编码了优先级、结合性、嵌套关系（如 1+2*3 的 AST 是 +(1,*(2,3))，* 子树更深、先算），后续阶段遍历树就能直接操作结构；源码字符串只是线性字符，看不出结构。几乎所有代码工具（IDE 重构、ESLint、MyBatis SQL 模板、规则引擎表达式）都工作在 AST 上；能把一段代码画成 AST，编译原理就入了门。

3. javac 是前端：词法→语法→语义→生成字节码，止步于字节码；JIT 是运行期的二次编译，把热点字节码再编译为机器码。Java 程序跑久变快，是因为热点代码被 JIT 编译成本地机器码并做了内联等优化，预热后执行的是优化过的机器码而非解释执行。

4. 数据库执行 SQL 走同一条流水线：词法→语法→语义（表/列校验）→优化（生成执行计划）→执行。看执行计划就是看优化阶段的产物；Druid 的 WallFilter 防注入、ShardingSphere 的分片改写都基于 SQL 的 AST——注入能被识别，是因为改写后的 AST 形状变了。

5. 分层函数就是优先级分层：expr 处理加减（最低优先级）、term 处理乘除、factor 处理原子（数字、括号、变量）；解析时低优先级函数调用高优先级函数，形成的 AST 里高优先级子树更深、先算。这样树的形状本身编码了优先级，后续阶段不再处理括号；不分层的话，解析器无法仅靠向前看几个 Token 决定运算顺序。

## 11. 一句话总结

编译器 = 把代码变树、对树做检查与加工、再把树变回代码；看懂这条线，报错、工具、SQL 与表达式引擎都不再是黑盒。
