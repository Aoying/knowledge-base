# 操作系统：进程与线程

## 进程 vs 线程 vs 协程

|  | 进程 | 线程 | 协程 |
|---|---|---|---|
| 资源 | 独立内存空间 | 共享进程内存 | 用户态调度 |
| 切换成本 | 高（内核态） | 中 | 低 |
| 通信 | 管道/socket/共享内存 | 共享内存（要加锁） | 让出执行权 |
| 例子 | Chrome 每个标签页 | Java 线程池 | Python asyncio、Go goroutine |

## 上下文切换

- 切的是：寄存器、程序计数器、栈指针、虚拟内存映射。
- 线程数远超 CPU 核数且都是计算密集型时，CPU 全在"搬运"，越切越慢。
- 排查：`top` 看 `%sy`（内核态占比）高就是切换/锁竞争重。

## 上下文切换（深化补充）

原篇已有切换内容清单（寄存器、程序计数器、栈指针、虚拟内存映射）、线程超配的危害和 top %sy 的判断，本节只补开销的构成、量级感知和减少手段。

### 开销分直接和间接两部分

- 直接开销：保存/恢复寄存器组、程序计数器、栈指针和内核栈；进程切换还要换页表和地址空间（同进程内的线程切换不换页表，这是线程切换比进程切换便宜的根本原因）；调度器本身的决策和队列操作；进出内核态的往返。
- 间接开销：切换后新任务的 TLB 表项和 CPU 缓存亲和性丢了，要把工作集重新载入缓存和 TLB，这部分往往比寄存器搬运本身更贵。高频切换时，间接开销会把总成本放大到远超单次切换的账面值。
- 进程、线程、协程三档的开销差异由此而来：进程切换最重（换地址空间加 TLB 处理），线程切换省掉换页表，协程切换在用户态完成、不进内核，最轻。原篇的成本表（高/中/低）对应的就是这条原因链。

### 量级感知与观测

- 量级上只记一条：单次切换本身通常是微秒量级，随 CPU 和内核而异，不必记具体数字；真正要警惕的是切换频率，一秒几万次切换时，间接开销和调度器本身就成了 CPU 的主要消费者。
- 观测时把两个信号放一起看：原篇的 top %sy（内核态占比高）加 vmstat 的 cs 列（每秒上下文切换次数），%sy 高且 cs 高，才指向切换/锁竞争重；只看一个容易误判。

### 减少切换的工程手段

- 线程数有界：线程池定长加队列削峰，计算密集任务的线程数向核数靠拢（原篇易错点已讲多线程不一定更快，本节只给手段）。
- IO 密集不要“一连接一线程”：用本篇新增的 IO 多路复用或异步模型，让一个线程管一批连接，从根上减少为等 IO 而存在的线程数。
- 绑核与亲和性：把关键线程固定在少数核上，减少跨核迁移带来的缓存和 TLB 重建。
- 减少无谓唤醒：锁竞争和条件变量用精确通知、批量处理代替频繁唤醒，唤醒一次就切换一次，唤醒本身也是切换的来源。
- 用户态调度兜底：协程或虚拟线程把切换留在用户态，见原篇进程 vs 线程 vs 协程一节和 Java 对应一节，原理是切换不进内核、不换页表。

插入位置：接在原篇“## 上下文切换”节末尾，即“排查：top 看 %sy 那条”之后、“## 同步原语”之前。

## 同步原语

- Mutex：同一时间只许一个进（synchronized 底层）。
- 信号量：允许 N 个进（限流、连接池）。
- 条件变量：等某个条件成立再继续（生产者-消费者）。
- 读写锁：读多写少，读不互斥、写互斥。

## 死锁 4 条件（缺一不可）

互斥、占有且等待、不可剥夺、循环等待。
解法：按固定顺序加锁（最常用）、tryLock 超时放弃、死锁检测。

## 虚拟内存与分页

- 每个进程以为自己独占内存，MMU 做虚拟→物理映射。
- 缺页异常：访问了不在内存的页，OS 从磁盘换进来；频繁缺页 = 抖动，机器卡死。
- Java 堆太大时 Full GC 停顿 + swap 是双重灾难：堆设保守点、关 swap。

## 虚拟内存与分页（深化补充）

原篇已有 MMU 映射、缺页与抖动、TLB 定义、地址转换示意和置换三兄弟的点名，本节只补原篇没展开的三块。

### 多级页表：为什么不止一级

- 单级页表的问题是地址空间稀疏：64 位地址空间下，一张平铺的页表本身就会大到不可接受，而进程实际只用了其中很小一部分地址段。
- 多级页表只为实际用到的地址段建下级表，没用到的段连表都不建，用“表里套表”换内存。以 x86-64 常见的 4 级页表为例，虚拟地址被切成多段索引加页内偏移，逐级查下去才定位到页框。
- 代价是查表要走多级，单靠查表会很慢，这正是 TLB 存在的理由；页表本身也占内存，页表项里除了页框号，还带存在位、读写位、用户/内核位、访问位、脏位、执行禁用位等标志，权限检查和置换决策都靠它们。

### TLB：未命中之后发生什么

- 原篇已讲 TLB 是页表的高速缓存、查地址先查 TLB。补一条链路：TLB 未命中时要做页表遍历（page walk），按多级页表逐级查到页框号，再把结果填回 TLB，后续访问同一页就命中。
- 进程切换时的 TLB 处理：地址空间换了，旧进程的 TLB 表项不能再用。朴素做法是切换时刷新 TLB，现代 CPU 用进程上下文标识（x86 的 PCID、ARM 的 ASID）给不同进程的表项打标记，让多个进程的表项共存，切换时不必全刷。
- 多核下的补充：一个核改了页表，其他核上缓存的旧映射也要失效，靠核间中断通知对方刷新相关 TLB 表项（TLB shootdown），这是页表修改必须考虑的跨核成本。

### 缺页中断的完整流程

按顺序走六步，缺页和 TLB 未命中是两回事（原篇已点明，本节展开前者）：

```text
1. 访问触发缺页异常，CPU 切进内核态
2. 内核先查地址合法性：非法访问直接报段错误，不走到换页
3. 找空闲页框；没有空闲时按置换算法选一个牺牲页，脏页先回写磁盘
4. 从磁盘或交换区把需要的页读进页框
5. 更新页表、建立 TLB 映射
6. 重新执行触发缺页的那条指令，这次命中
```

### 页面置换：原篇三兄弟之外的工程要点

- 原篇已列 FIFO、LRU、OPT 三兄弟，工程上真正常用的是 LRU 的近似：时钟算法（Clock）。用一个环形指针加访问位扫一圈，扫到访问位为 1 的先清零放过，扫到为 0 的换出，相当于给每个页一次“第二次机会”，实现代价远低于精确 LRU。
- OPT 只作理论上限对比，实际系统不知道未来访问序列，不可能实现。
- 两条选型直觉：换出干净页比脏页便宜（脏页要先回写），置换倾向先换干净页；抖动是工作集超过物理内存的系统性问题，换置换算法救不了纯粹的内存不足，只能加内存或缩小工作集。

## IO 多路复用：一个线程等多个连接

先说它解决什么问题：原篇易错点已讲过，连接数上万时“一连接一线程”会死在线程数和上下文切换上。IO 多路复用是另一条路：一个线程向内核登记一批 fd（文件描述符），内核告诉它“这几个就绪了”，它只处理就绪的，不用为每个连接各起一个线程干等。

### select、poll、epoll 的机制对比

|  | select | poll | epoll |
|---|---|---|---|
| 监听方式 | 每次调用把 fd 位图全量传进内核，返回时集合被改写，下次要重建 | 每次调用把 pollfd 数组全量传进内核，返回后遍历找 revents | epoll_create 建实例，epoll_ctl 增量注册/修改/删除，epoll_wait 只取就绪的 |
| 扫描代价 | 每次都要把全部监听 fd 过一遍，随监听总数走 | 同 select，随监听总数走 | 只返回就绪 fd，耗时随就绪数走，不随监听总数走 |
| fd 上限 | 受 FD_SETSIZE 限制（默认 1024），改大也不推荐 | 无 FD_SETSIZE 式硬上限，上限是进程可开 fd 数 | 同 poll，上限是进程可开 fd 数 |
| 触发语义 | 只有水平触发语义 | 只有水平触发语义 | LT（默认）与 ET 可选，见下 |

一句话记住选型：连接数少、逻辑简单时 select/poll 够用；连接数大、且大部分连接平时不活跃时，epoll 的“只返回就绪”才划算。epoll 的优势不在单次调用更快，而在监听规模上去之后不随总数线性变差。

### epoll 的 LT 与 ET

- LT（水平触发，默认）：只要 fd 上还有未处理完的就绪状态，下一次 epoll_wait 还会通知你。可以一次只处理一部分，剩下的下次再来，写起来宽容，高频通知时效率低一些。
- ET（边缘触发）：状态从“未就绪”变“就绪”时只通知一次。收到通知后必须用非阻塞 fd 循环读/写到返回 EAGAIN 为止，否则剩下的数据不会再触发通知，会滞留在内核缓冲里。
- ET 的使用注意三条：fd 必须设非阻塞；一次事件要处理干净（读到 EAGAIN、写到 EAGAIN）；一个 fd 长期可读会占住事件循环，要给单次处理加量上限或做公平调度，否则别的连接被饿住。
- 常见误区：ET 不是“性能一定更好”，它只是减少通知次数；处理逻辑没按“读到 EAGAIN”写，ET 反而会丢事件。

### Reactor 模型与 Java NIO 的对应

- Reactor 模式一句话：一个事件分发器等就绪事件，事件到了就回调对应的 handler，线程不用在每个连接上干等。
- 三种经典形态：单 Reactor 单线程（Redis 的模型）；单 Reactor 多线程（分发与业务处理分开）；主从 Reactor（一个 Reactor 只管 accept，另一个管已建立连接的读写，对应 Netty 的 boss/worker 分工）。
- Java NIO Selector 就是多路复用器的 Java 封装：Linux 上默认基于 epoll 实现，Selector.select() 对应 epoll_wait，SelectionKey 的 OP_ACCEPT/OP_READ/OP_WRITE 对应 epoll 关注的事件类型。
- 两点对应关系要讲清：第一，Java NIO Selector 只暴露水平触发语义，不提供 ET 模式，按 LT 的写法用即可；第二，一个 Selector + 一个线程 + 任务处理就是 Reactor 单线程模型，对应 Netty 篇里 EventLoop 的定义（一个线程 + 一个 Selector + 一个任务队列），Netty 细节见 Netty、Java-IO与NIO，本篇不展开。

## 进程调度

- CFS（Linux 默认）：按"虚拟运行时间"公平调度，`nice` 值调优先级。
- 实时任务用 FIFO/RR，别和普通进程抢。

## 僵尸进程与孤儿进程

- 僵尸（Z 状态）：子进程退出了，父进程没 `wait()` 回收——占着进程表项，杀不掉（已经死了），只能杀父进程或让父进程回收。
- 排查：`ps aux | awk '$8 ~ /Z/'`；找到 Z 进程的 PPID，处理父进程。
- 孤儿进程：父进程先退了，子进程被 init（PID 1，现在一般是 systemd）收养——正常现象，守护进程就是这么来的（double fork）。
- Java 相关：`ProcessBuilder` 起的子进程，记得 `process.waitFor()` 并消费输出流，否则子进程变僵尸、还可能因为管道缓冲写满卡死。

- Java 平台线程 1:1 内核线程；Java 21 虚拟线程 = JVM 里的"协程"，见 [开发语言/Java/Java.md](开发语言/Java/Java.md)。
- `jstack` 看线程状态：RUNNABLE / BLOCKED / WAITING，死锁直接搜 "deadlock"。

## 基础知识补强

### 核心概念与术语

- 操作系统：管硬件、给应用提供统一接口的系统软件。核心职责四件：进程管理、内存管理、文件管理、设备（IO）管理。
- 内核：操作系统最核心的部分，常驻内存，特权最高；其余部分都围着它转。
- 用户态 vs 内核态：CPU 的两种权限级别。应用跑用户态，碰硬件、改内存映射必须进内核态。
- 系统调用：应用请求内核办事的唯一正门，如读文件、建进程、发网络包，都要过这一关。
- 中断：硬件或软件发来的"先停一下"信号。键盘敲击、网卡收包、时钟滴答都是中断。
- 进程控制块（PCB）：内核给每个进程建的档案，存状态、寄存器快照、打开的文件、优先级等。
- 临界区：一段访问共享资源的代码，同一时刻只允许一个执行流进入。
- 竞态条件：多个执行流同时改共享数据，结果取决于谁先谁后——并发 bug 的总根源。
- 原子性：一个操作不可分割，要么全做完，要么没做；`i++` 不是原子的（读、改、写三步）。
- 饥饿：某个进程长期抢不到资源一直等；活锁：双方不断互相礼让，谁也推进不了。两者都区别于死锁（死等不动）。

### 基础知识与用法

进程五种状态与转换，先建立这张心智图：

```text
新建 ──→ 就绪 ──被调度──→ 运行 ──时间片用完──→ 就绪
                        运行 ──等 IO/等锁──→ 阻塞
                        阻塞 ──事件完成──→ 就绪
                        运行 ──执行结束──→ 终止
就绪 = 万事俱备只差 CPU；阻塞 = 在等事件，给它 CPU 也没用。
```

CPU 调度先看四个基础算法和三个评价指标：

- 先来先服务（FCFS）：按到达顺序，简单公平，长任务会堵住后面所有人（护航效应）。
- 短作业优先（SJF）：平均等待最短，但作业时长事先不知道，且长作业可能饥饿。
- 时间片轮转（RR）：每人跑一个小片，响应快；片太小切换开销大，片太大全退化成 FCFS。
- 优先级调度：按优先级跑，要防低优先级饿死，常用"老化"（等得越久优先级越高）补救。
- 评价指标：周转时间（提交到完成）、等待时间（在就绪队列里干等）、响应时间（首次被调度）。

进程间通信（IPC）五种基本方式，按场景选：

```text
管道：半双工字节流，适合父子进程之间，最简单
消息队列：内核维护的消息链表，按消息类型收发，进程可不相关
共享内存：同一块内存多方直接读写，最快，但同步要自己加
信号：异步通知，只有"发生了什么事"，不带数据，如 Ctrl+C 的 SIGINT
Socket：可跨机器，其余四种基本限本机
```

分页机制补两个原文没展开的概念：

- 页与页框：虚拟内存切成等大的页（常见 4KB），物理内存切成同样大的页框，页表记录页到页框的对应。
- TLB：页表的高速缓存，放最近用过的映射。查地址先查 TLB，命中就不走多级页表，缺页和 TLB 未命中是两回事。
- 地址转换示意：虚拟地址 = 页号 + 页内偏移；偏移不翻译，只换页号对应的页框号再拼回去。
- 页面置换三兄弟：先进先出（FIFO，最朴素）、最近最久未用（LRU，效果好近似实现）、最优（OPT，只作理论上限对比）。

IO 的两种等法和一个加速器：

- 中断驱动：设备干完活发中断叫醒 CPU，CPU 不用干等，适合慢设备。
- 轮询：CPU 反复查状态，浪费算力，只适合响应极快、等待极短的场景。
- DMA：数据在设备和内存之间直达搬运，不经 CPU，只在开始和结束时打扰 CPU 一次。

阻塞/非阻塞与同步/异步，两组最常被混为一谈的概念：

```text
阻塞/非阻塞：说"等的时候要不要卡住当前线程"（调用方视角）
同步/异步：说"结果由谁来通知你"——自己回来看 = 同步，回调/信号通知 = 异步
四种组合都存在：阻塞同步（普通 read）、非阻塞同步（轮询 read）、异步 IO（完成才回调）
```

### 关键机制速览

- 一次系统调用的代价：切内核态、查参数、干活、切回来，比普通函数调用贵得多，所以批量读写才划算。
- fork 的心智模型：复制出一个子进程，父子从 fork 返回处分道扬镳，靠返回值区分身份（父拿到子 PID，子拿到 0）。
- 写时复制（COW）：fork 不真复制内存，父子先共享同一批页，谁写谁才复制那一页，建进程因此很便宜。
- 线程的实现分工：用户级线程库管调度、内核不知情，一线程阻塞可能拖住全部；内核级线程由 OS 调度，Java 平台线程走这条。
- 自旋 vs 挂起：等的时间短就自旋（空转几下不切换），等的时间长就挂起让出 CPU；锁实现常是两者混合。
- 生产者-消费者是同步问题的总模板：有界缓冲区 + 两个条件（不满才能放、不空才能取），信号量和条件变量都能解。
- 时间片和时钟中断是一对：没有周期性的时钟中断，调度器就没机会抢回 CPU，多任务无从谈起。
- 内存抖动的本质：置换算法选错页或内存实在不够，CPU 大部分时间在等换页而不是算题。
- 中断处理要快进快出：中断里只做最紧急的记录工作，重活留给普通线程慢慢干，否则高频中断会把正常任务饿住。
- 信号量可以先记成"带计数的门票"：票数就是允许同时进入的个数，Mutex 是票数恰好为 1 的特例。
- 文件在操作系统眼里只是一串字节加一份元数据：格式、结构全是应用层自己的约定，OS 不关心内容。

### 新手易错点

- 以为多开线程必然更快：线程数超过核数后，计算密集任务只增加切换开销；IO 密集才适合多线程等 IO。
- 把死锁、饥饿、活锁混为一谈：死锁是环路死等，饥饿是总被插队，活锁是双方动态让步却原地打转，解法各不相同。
- 以为加锁就没竞态：锁只保护临界区，忘了给某条路径加锁、检查后再操作（check-then-act）不在锁内，一样出问题。
- 分不清进程隔离的边界：同进程线程共享堆和全局变量；进程之间默认互不可见，共享必须走 IPC。
- 认为阻塞 IO 就是性能差：线程数可控、业务简单时，阻塞 IO 模型反而最好维护，复杂的是连接数上万的场景。
- 忽略系统调用和上下文切换的隐形税：无谓的频繁小 IO、无锁不成的细粒度加锁，都会把这笔税放大。
- 把虚拟内存当免费午餐：地址空间大不等于物理内存够用，工作集超过物理内存就抖动。
- 以为线程共享一切：栈和寄存器是每个线程私有的，共享的只有堆和全局数据，给线程传参数别指望它自带一份副本。
- 拿 sleep 当同步手段：睡多久全靠猜，机器负载一变就时序错乱；等条件就用条件变量或信号量，别用延时凑。
- 忽略优先级反转：低优先级拿着锁，高优先级被迫等，中优先级的反而先跑——实时系统的大坑，普通业务了解概念即可。
