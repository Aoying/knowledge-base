# B 树与 B+ 树

数据库索引为什么用 B+ 树而不是二叉树、哈希表？答案藏在磁盘 IO、范围查询和树高这三个点里。本篇先讲清两种树的结构，再讲清它们和数据库索引的对应关系。

## 1. B 树结构

- 定义：一棵 m 阶 B 树，每个节点最多 m 个孩子、最多 m-1 个关键字；除根节点外，每个节点最少有 ⌈m/2⌉ 个孩子；所有叶子节点在同一层；节点内的关键字有序，孩子节点按关键字区间划分。
- 关键特征：关键字和数据一起存在所有节点里（包括内部节点），每个关键字只出现一次；查找时从根向下按区间逐层定位，时间复杂度 O(log n)。
- 阶的含义：阶 m 就是节点的最大孩子数。阶越大，节点越宽，树越矮；阶越小，树越高。数据库场景里阶通常很大（几百到上千），因为节点对应磁盘页，页越大、一次 IO 能带回的关键字越多。

## 2. B+ 树结构

B+ 树是 B 树的变体，改动有三处，每一处都是为数据库查询服务的：

- 数据只存在叶子节点：内部节点只存关键字（分界值），不存数据记录。这样内部节点能塞下更多关键字，扇出更大，树更矮。
- 叶子节点按顺序用链表连起来：范围查询时先定位到起点叶子，然后沿链表顺序扫描，不用回到树上逐个查找。
- 内部节点的关键字是分界值的副本：同一个关键字可能在内部节点和叶子节点同时出现，内部节点只负责“导航”，不负责“存数据”。

## 3. 页分裂与合并：树怎么长大和缩小

- 插入导致节点满了：把节点分裂成两个，中间关键字上提到父节点；如果父节点也满了，继续向上分裂；分裂传到根节点时，树高加一。这是 B+ 树高度增长的唯一方式，所以所有叶子永远同层，高度稳定。
- 删除导致节点关键字过少：先向兄弟节点借一个关键字；借不到就和兄弟节点合并，父节点的分界关键字随之下移；合并向上传播时，树高可能减一。
- 工程含义：分裂与合并是写放大的来源之一。顺序插入（如自增主键）时分裂集中在最右端，随机插入（如 UUID 主键）时分裂分散在全树，还会产生页碎片，这是“自增主键优于随机主键”的底层原因。

## 4. 为什么数据库索引用 B+ 树

- 范围查询快：`WHERE age BETWEEN 20 AND 30` 这类查询，B+ 树定位到起点叶子后沿链表扫描即可；B 树要反复回树查找，哈希索引根本不支持范围查询。
- 顺序访问友好：`ORDER BY` 索引列时，叶子链表本身就是有序的，不用额外排序。
- 高度稳定：所有叶子同层，任何一次点查的 IO 次数都等于树高，可预测、可估算。以扇出 1000 估算，3 层约可存 10 亿条记录（1000³），所以生产中的 B+ 树索引通常只有 3–4 层，一次点查只需 3–4 次 IO。
- 契合磁盘页式存储：节点大小对齐磁盘页（如 InnoDB 默认 16KB 一页），一次 IO 读一页，页内关键字越多，IO 效率越高；二叉树节点太小，同样数据量要多很多次 IO。

## 5. 与 MySQL 索引的对应关系

- InnoDB 聚簇索引：叶子节点存整行数据，表数据本身就是按主键组织的一棵 B+ 树；主键查询不需要回表。
- InnoDB 二级索引：叶子节点存主键值，查到主键后再回聚簇索引取整行，这一步叫回表；覆盖索引（查询列全在索引里）可以避免回表。
- 索引选择与最左前缀：复合索引按从左到右的列顺序组织，查询条件跳过左边的列时，后面的列就用不上索引（最左前缀原则的来源）。
- 页的含义：InnoDB 一页默认 16KB，B+ 树的一个节点就是一页；页分裂就是上面第 3 节的分裂，频繁随机插入会导致页分裂和碎片。

## 6. 对比表：B+ 树、红黑树、哈希索引

| 维度 | B+ 树 | 红黑树 | 哈希索引 |
|---|---|---|---|
| 点查 | O(log n)，3–4 次 IO | O(log n)，内存友好 | O(1)，最快 |
| 范围查询 | 叶子链表顺序扫描，最擅长 | 需中序遍历，尚可 | 不支持 |
| 排序输出 | 叶子天然有序 | 中序遍历有序 | 无序 |
| 磁盘友好度 | 节点对齐页，IO 次数少 | 节点小、树高大，IO 次数多 | 依赖内存，磁盘场景弱 |
| 适用场景 | 数据库索引默认选择 | 内存数据结构（如 Java TreeMap） | 内存缓存点查、等值查询 |

## 7. Python 演示：B+ 树查找路径模拟

下面是教学简化模型：3 个叶子加内部节点分界键，演示一次点查走过的路径和一次范围扫描。真实实现还要处理分裂、合并和并发，这里只保留“导航”这一核心过程。

```python
# 简化版 B+ 树：3 个叶子，内部节点存分界键
leaves = [[1, 3, 5], [7, 9, 11], [13, 15, 17]]
separators = [7, 13]  # 第 i+1 个叶子的最小键

def find_path(key):
    idx = 0
    while idx < len(separators) and key >= separators[idx]:
        idx += 1
    return idx, key in leaves[idx]

def range_scan(lo, hi):
    out = []
    for leaf in leaves:
        out.extend([k for k in leaf if lo <= k <= hi])
    return out

print(find_path(9))       # (1, True)：分界键导航到第 1 个叶子，命中
print(find_path(6))       # (0, False)：6 < 7，落入第 0 个叶子，未命中
print(find_path(13))      # (2, True)：13 >= 13，落入第 2 个叶子，命中
print(range_scan(5, 13))  # [5, 7, 9, 11, 13]：沿叶子顺序扫描
```

## 小技巧与冷知识

【小技巧】点查要几次 IO 可以自己估：树高大约是 log(扇出)(数据量) 再加一层叶子，扇出 1000、10 亿行数据时约 3 层，点查就是 3 次 IO。估算时先看主键长度——主键越短，单页能塞的关键字越多，扇出越大，树越矮，这也是整型主键比长字符串主键省 IO 的原因之一。

【小技巧】别把“3 次 IO”当成“3 次读盘”：根节点和上层内部节点几乎常驻 InnoDB 缓冲池，真正落到磁盘的往往只有叶子那一次。排障时看到点查慢，先看缓冲池命中率和叶子页是不是在磁盘上，别只盯着树高算账。

【小技巧】范围查询的起点只定位一次：`BETWEEN` 先二分定位到左端点所在的叶子，之后沿叶子链表顺序扫到右端点为止，中间的叶子不用再回树上找。写范围条件时把“能定位起点的列”放在前面，起点定不准，链表扫描的范围就变大。

【小技巧】范围跨度太大时优化器可能放弃索引改走全表扫描：返回行数占表比例一高，逐页沿链表扫的随机 IO 反而不如顺序全表扫划算。遇到“加了索引却没走”的情况，先看查询的选择性，别急着怀疑索引建错了。

【小技巧】批量插入前先把数据按主键排好序：顺序写入时页分裂只发生在最右端，新页按顺序填满；乱序写入会在全树到处分裂，还会留下大量半满页。导数、ETL 入库这类批量场景，排序后再插是成本最低的优化。

【小技巧】删了很多行后表文件不一定会变小：InnoDB 的删除多是标记删除，页内留空洞，页合并只在关键字过少时才发生。删完大批数据想回收空间，可以用 `OPTIMIZE TABLE` 重建表整理碎片，但它会锁表，大表要在低峰期做。

【小技巧】复合索引的列顺序按“等值查询在前、范围查询在后”排：等值列先定位到一个窄区间，范围列再在这个区间里扫；反过来排，范围列一出现，后面的列就用不上索引。原文最左前缀讲的是“能不能用上”，这一条讲的是“排成什么顺序最划算”。

【小技巧】InnoDB 的叶子链表是双向的：`ORDER BY 索引列 DESC` 不用额外排序，直接从右端叶子往回扫就行。看到“倒序查还要 filesort”的情况，先确认是不是走了索引列的倒序扫描，而不是默认倒序就等于要排序。

【小技巧】想验证一棵索引到底几层，不用猜：MySQL 里可以用 `SHOW INDEX` 看基数、用执行计划看访问方式，再结合页大小和主键长度估算扇出。树高是算出来的，不是背出来的，面试时现场估算比报“3–4 层”更有说服力。

【小技巧】B+ 树怕的不是数据量大，而是“写得乱”：读多写少的表用 B+ 树很稳，写入全是随机主键、高频更新的场景，分裂和碎片会持续吃掉性能。这类场景可以考虑换 LSM 树结构的存储（如 RocksDB、LevelDB），它把随机写先攒成顺序写，代价是读时要多查几层。

【冷知识】B 树出自 1972 年的一篇论文：Rudolf Bayer 和 Edward M. McCreight 发表《Organization and Maintenance of Large Ordered Indexes》，最初就是为磁盘、磁带这类外存设备设计的索引结构。B 树的“矮胖”不是偶然，是为了让一次磁盘寻道带回尽可能多的数据。

【冷知识】B 树里的 B 到底指什么，至今没有定论：有人说是 Bayer 的首字母，有人说是作者当时所在的波音（Boeing），也有人说是 balanced（平衡）的缩写。Bayer 本人从未正式确认过，教科书里写哪个版本都有。

【冷知识】B+ 树这个名字是后来才定下来的：Douglas Comer 在 1979 年的综述《The Ubiquitous B-Tree》里系统梳理了 B 树家族，把“数据只存叶子、叶子连成链表”这一变体称为 B+ 树，名字由此流行开来。

【冷知识】红黑树和 B 树是亲戚：红黑树可以看作 2-3-4 树（二叉化表示的 B 树变体）的二叉形态，两者在结构上等价。原文对比表说红黑树适合内存、 B+ 树适合磁盘，根源就在这里——同一种平衡思想，节点大小不同，适用的存储介质就不同。

【冷知识】B* 树是 B+ 树的一个变体：分裂时不急着一分为二，先向兄弟节点借空间，兄弟也满了才分裂，分裂后两个节点各约 2/3 满，比 B+ 树分裂后一半满的空间利用率更高。代价是分裂逻辑更复杂，工程上用得少，但理解它能帮你看清“分裂策略就是空间利用率和实现复杂度的 trade-off”。

【冷知识】B+ 树的叶子链表还有一个冷门用途：数据库做“全表顺序扫描”时，有时不是扫表数据文件，而是沿叶子链表扫一遍，因为叶子里的行是按主键排好序的。覆盖索引的范围扫描走的也是这条链表，理解了这一点，就能明白为什么“索引覆盖 + 范围”常常比想象中更快。

## 面试与自测

1. B+ 树相对 B 树改了哪三处？每一处是为了解决什么问题？
2. 为什么数据库索引默认用 B+ 树而不用红黑树或哈希索引？
3. 随机主键（如 UUID）相对自增主键，对 B+ 树写入有什么不利影响？

### 参考答案

1. 数据只存叶子（内部节点扇出更大、树更矮）；叶子按顺序链表相连（范围查询沿链表扫描）；内部节点关键字是分界值副本（只导航不存数据）。三处改动分别服务于“更矮”和“范围查询更快”。
2. 红黑树节点小、树高大，同样数据量磁盘 IO 次数多；哈希索引不支持范围查询和排序输出。B+ 树同时满足点查 O(log n) 且 IO 次数少、范围查询沿链表扫描、叶子天然有序，是磁盘场景下的综合最优。
3. 随机主键的插入位置分散在全树，页分裂分散发生，还会产生页碎片和频繁的页合并；自增主键的插入集中在最右端，分裂可预测、碎片少，所以写入更友好。
