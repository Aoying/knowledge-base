# 编码、字符集、内存与文件系统

## 字符集

|  | 说明 |
|---|---|
| ASCII | 128 个，英文 + 符号，1 字节 |
| GBK | 中文 Windows 默认，2 字节，不兼容就乱码 |
| UTF-8 | 变长 1-4 字节，英文 1 字节中文 3 字节，互联网标准 |
| UTF-16 | Java String 内部，2/4 字节 |

## 乱码排查三问

1. 文件是什么编码存的？（`file -i xxx` 看）
2. 程序按什么编码读的？（Java `-Dfile.encoding=UTF-8`，Python `open(encoding='utf-8')`）
3. 终端/页面按什么编码显示的？

- MySQL 经典坑：`utf8` ≠ 真 UTF-8（存不了 emoji），建表用 `utf8mb4`，见 [数据库/MySQL/MySQL-数据库.md](数据库/MySQL/MySQL-数据库.md)。

## 大小端

- 小端（x86/ARM 默认）：低字节存低地址；网络传输统一大端（网络字节序）。
- Java 里基本碰不到，写二进制协议 / 解析 pcap 时才需要。

## 内存布局（进程视角）

```
高地址
[栈]  局部变量，向下增长，函数返回自动回收
  ↓
[堆]  new/malloc，向上增长，GC 管
[数据段] 全局 / 静态变量
[代码段] 只读
低地址
```

- 栈溢出：递归没出口；堆溢出：泄漏 / 一次加载太多数据。
- `dmesg | grep -i oom` 看谁被 OOM killer 干掉了。
## 内存对齐与填充

- CPU 按字长（64 位 = 8 字节）取内存：变量地址是"自然对齐"的倍数时一次取完，否则跨两次取，变慢。
- C 结构体：编译器自动在字段间插 padding。`struct { char a; int b; }` 不是 5 字节而是 8 字节（a 后面补 3 字节）。
- Java 对象：对象头 12 字节（64 位 + 压缩指针）+ 实例数据 + padding 补到 8 的倍数；`new Object()` 占 16 字节。小对象数组的内存开销常被低估：`Long[10000]` 是 10000 个引用（8 万字节）+ 10000 个 Long 对象。
- 经验：缓存行 64 字节；伪共享（false sharing）是高并发计数器的隐形杀手，`@Contended` 或手动 padding 隔离。


## 文件系统

- inode：存元数据（权限/大小/块指针），文件名只是目录项指向 inode。
- 软链 vs 硬链：软链是快捷方式（删源就断），硬链是同一 inode 的别名。
- ext4（Linux）/ NTFS（Windows）/ APFS（macOS）。
- `df -i` 看 inode 用量：小文件太多会先耗尽 inode，磁盘还有空间也写不进。

## 磁盘 IO 基础

- 随机 IO 比顺序 IO 慢 1-2 个数量级（SSD 缩小了差距但还在）。
- LSM 树（RocksDB/LevelDB）：写放大换读性能，顺序写 + 后台合并。
- B+ 树：读优化，MySQL InnoDB 的选择。

## 基础知识补强

### 核心概念与术语

- 位（bit）：信息的最小单位，只能是 0 或 1；字节（byte）：8 个 bit，是内存寻址和文件大小的基本单位。
- 字（word）：CPU 一次能处理的数据宽度，和机器字长绑定，64 位机器一个字是 8 字节。
- 字符集 vs 编码：字符集是"有哪些字符、各编什么号"的字典；编码是"号码怎么落成字节"的规则。Unicode 是字符集，UTF-8/UTF-16 是它的两种编码。
- 码点（code point）：字符在字符集中的编号，写作 U+ 加十六进制，如汉字"中"是 U+4E2D。
- 有符号/无符号：同样的字节，按补码解释可为负，按无符号解释全是非负；类型选错，比较和算术全错。
- 补码：正数就是原码，负数是"取反加一"；用补码表示后，加法器可以同时干加减法，这是它胜出的根本原因。
- 栈帧：一次函数调用在栈上的一块记录，含参数、局部变量、返回地址；调用链多深，栈帧就叠多高。
- 页缓存（page cache）：内核把读过的文件内容缓存在内存里，下次读直接命中内存；内存看着"被吃满"很多时候是它。

### 基础知识与用法

整数的范围公式，先记这一组，选类型时直接套：

```text
n 个字节的有符号整数：-2^(8n-1) ~ 2^(8n-1) - 1
  1 字节：-128 ~ 127        4 字节（int）：约 ±21 亿
  8 字节（long）：约 ±9.2×10^18
无符号：0 ~ 2^(8n) - 1
溢出不会报错：超过上限会绕回最小值（回绕），计数和金额尤其要防。
```

手工算一遍补码（以 1 字节的 -5 为例）：

```text
+5 的二进制：0000 0101
取反：      1111 1010
加一：      1111 1011   ← 这就是 -5 的补码存储形态
验证：5 + (-5) 按 8 位加法 = 1 0000 0000，丢掉进位正好是 0。
```

浮点数为什么不能直接比相等：

```text
浮点数按 符号 + 指数 + 尾数 存储，只能近似表示大多数小数。
0.1 在二进制里是无限循环小数，存下来必然带微小误差。
0.1 + 0.2 == 0.3 结果为 false，是表示误差累积，不是语言 bug。
正确做法：比差的绝对值小于一个小量（如 1e-9）；钱的计算用整数分或十进制定点类型。
```

UTF-8 编码规则表（原文只说了变长，这里补齐字节形态）：

```text
码点范围            字节数  字节形态（x 为有效位）
U+0000 ~ U+007F     1       0xxxxxxx
U+0080 ~ U+07FF     2       110xxxxx 10xxxxxx
U+0800 ~ U+FFFF     3       1110xxxx 10xxxxxx 10xxxxxx
U+10000 ~ U+10FFFF  4       11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
规律：后续字节都以 10 开头，所以从任意字节都能判断自己处在字符的第几字节，
     解码容错和"按字节截断不裂字符"的处理都靠这条自同步特性。
BOM：文件开头的 EF BB BF，是某些编辑器写 UTF-8 时加的标记，解析器不跳过它就会在首字段藏一个怪字符。
```

Base64 与 URL 编码，两种最常见的"传输编码"别和加密混淆：

- Base64：把任意字节按 3 字节一组拆成 4 个可打印字符，体积膨胀约三分之一，目的是让二进制安全穿过只认文本的通道（邮件、JSON、URL 参数）。
- URL 编码：空格、中文等特殊字符转成 %XX 形式，如空格变 %20；不转的话 URL 解析直接出错。
- 两者都是公开可逆的格式转换，不提供任何保密性。

大小端判断的一行代码（C 语言示意，理解原理即可）：

```c
int x = 1;
char *p = (char *)&x;   // 取最低地址处的字节
*p == 1 → 小端；*p == 0 → 大端
// 小端：低位字节 01 在低地址；大端：高位字节在低地址，01 会在高地址处。
```

文件权限的数字表示法（Linux）：

```text
r=4, w=2, x=1，每三位一组：属主 / 属组 / 其他人
chmod 755 = 属主可读写执行，同组和其他人可读可执行
chmod 644 = 属主可读写，其余只读（普通文件的常见配置）
目录的 x 表示"能进入"，没有 x 光有 r 只能看到文件名列表却进不去、读不了内容。
```

### 关键机制速览

- 字符数不等于字节数：一个汉字在 UTF-8 里 3 字节，emoji 常是 4 字节；按字节截断字符串可能把字符截成两半。
- 程序里的字符串长度语义各语言不同：有的是字节数，有的是码元数，跨语言传数据先对齐口径。
- 判断一段字节的编码没有万能法：靠 BOM、协议声明、统计特征猜；声明与实际不一致就是乱码的源头。
- 硬盘上删文件删的是目录项和引用计数：文件被进程打开时删掉名字，数据仍在、空间不释放，进程关了才真回收，"磁盘满但 df 与 du 对不上"多半是这个。
- fsync 才是落盘保证：write 返回成功只代表进了页缓存，断电仍可能丢；数据库的可靠性都建立在正确调用 fsync 上。
- 内存映射文件（mmap）：把文件当内存数组访问，读写由缺页机制代劳，大文件随机读和进程间共享常用它。
- 字节序只在跨机器/跨语言传二进制时才要管：纯文本协议（JSON 一类）天然没这个问题，这也是文本协议流行的原因之一。
- 栈向低地址长、堆向高地址长是常见布局而非铁律，重点是理解两者生命周期不同：栈随调用自动回收，堆靠手动或 GC。

### 新手易错点

- 读写文件不指定编码，靠系统默认"碰运气"：本地中文环境能跑，换台英文服务器立刻乱码，编码要写死在代码里。
- 拿字符长度当字节长度去截断或校验：数据库字段长度、协议长度字段多按字节算，中文一多就超限或截裂。
- 用浮点存钱：0.1 的误差乘上交易量就是对不上的账，金额一律用最小单位整数或定点小数类型。
- 混淆 KB 的两种口径：内存和文件系统常用 1024 进制，厂商标硬盘常用 1000 进制，"买的盘比标称小"多是口径差不是缺斤少两。
- 以为删除文件空间立刻回来：进程还持有已删除文件的句柄时空间不释放，要重启或关闭持有进程。
- 有符号和无符号混算：负数和无符号数比较会被提升成无符号大数，结果反直觉；比较前先统一类型。
- 把 Base64 当加密：任何人都能一键解回来，敏感数据该加密加密、该脱敏脱敏，别指望编码。

## 字节与对齐定量：字符、对象与 inode 算一算

口径先定死：UTF-8 按 RFC 3629，ASCII 1 字节、汉字 3 字节、辅助平面字符（含常见 emoji）4 字节；Java 按 64 位 HotSpot + 压缩指针（堆 ≤ 32 GB）、对象头 12 字节、8 字节对齐；C 结构体按 x86-64 典型对齐；ext4 按默认块 4 KB、默认每 16,384 字节一个 inode。换口径，数字全要重算。

### 字符字节数：先数码点，再乘字节

换算表：ASCII 字符 1 字节，汉字（U+0800 ~ U+FFFF）3 字节，emoji 等辅助平面字符（U+10000 ~ U+10FFFF）4 字节。字符数、码点数、字节数是三个数，别混用。

【算例 1】`"Hi你好😀"` 共 5 个码点：`H`、`i` 各 1 字节，`你`、`好` 各 3 字节，`😀`（U+1F600）4 字节，合计 2 + 6 + 4 = 12 字节。Python 复算：`len("Hi你好😀".encode("utf-8"))` = 12。10 万条这样的短文本共 12 × 100,000 = 1,200,000 字节，约 1.14 MiB。

同口径再算三组，便于估行宽时直接套：纯 ASCII 文本 1,000 字符 = 1,000 × 1 = 1,000 字节；纯汉字文本 1,000 字 = 1,000 × 3 = 3,000 字节；100 个单码点 emoji = 100 × 4 = 400 字节。同样 1,000 个字符，纯英文 1 KB、纯汉字约 2.93 KiB、纯 emoji 约 0.39 KiB，纯汉字约是纯 emoji 的 7.5 倍。

| 文本 | 字符数 | 字节数 |
|---|---|---|
| 1,000 个 ASCII 字符 | 1,000 | 1,000 |
| 1,000 个汉字 | 1,000 | 3,000 |
| 100 个单码点 emoji | 100 | 400 |
| `"Hi你好😀"` | 5 | 12 |

按 1 MiB（1,048,576 字节）反推容量：纯 ASCII 可装 1,048,576 个字符，纯汉字约 1,048,576 / 3 ≈ 349,525 个，纯单码点 emoji 约 262,144 个。同一份 1 MiB 预算，汉字文本的字符容量只有英文的约三分之一。

MySQL `utf8mb4` 下按最坏情况留行宽：每字符最多 4 字节。`VARCHAR(100)` 最坏 100 × 4 = 400 字节，再加 2 字节长度前缀（最坏 400 字节 > 255 字节，长度字段占 2 字节）；上面那串 12 字节的实际内容只占 12 字节 + 前缀。`CHAR(100)` 是定长，最坏按 400 字节算。`VARCHAR(255)` 最坏 255 × 4 = 1,020 字节，超过旧版 InnoDB 767 字节索引上限，这就是 191 的来历：191 × 4 = 764 字节，刚好塞进 767。

### 对齐填充：字段顺序决定 padding

算式只用两条：字段起始偏移要是自身大小的倍数，结构体总大小要是最大字段大小的倍数。

【算例 2】`struct { char a; int b; }`：`a` 占偏移 0（1 字节），`b` 要 4 字节对齐，偏移 1 ~ 3 补 3 字节，`b` 占偏移 4 ~ 7，合计 1 + 3 + 4 = 8 字节。推广到三字段：`struct { char a; double d; char c; }` 是 1 + 7 + 8 + 1 + 7（尾部补齐到 8 的倍数）= 24 字节；调换顺序成 `struct { double d; char a; char c; }` 是 8 + 1 + 1 + 6 = 16 字节，只改顺序就省 8 字节，省三分之一。数组按 stride 算：8 字节的结构体 10,000 个占 80,000 字节，24 字节的结构体 1,000 个占 24,000 字节。

再算两个常见排列：`struct { int a; char b; char c; }` 是 4 + 1 + 1 + 2（尾部补齐到 4 的倍数）= 8 字节；`struct { char a; char b; int c; }` 也是 1 + 1 + 2 + 4 = 8 字节，两个 `char` 挤进 `int` 前面的空位就不产生额外填充。含 `double` 的结构体总大小按 8 对齐，含 `int` 的按 4 对齐，最大字段决定尾部补齐的步长。

数组 stride 直接决定缓存行占用：64 字节缓存行能装 8 个 8 字节结构体，只能装 2 个 24 字节结构体（余 16 字节）；1,000 个 24 字节结构体占 24,000 字节，约 23.44 KiB。

### Java 对象体量：头 12 字节是固定成本

公式：对象大小 = 向上取整到 8 的倍数（12 字节头 + 实例数据）；数组再加 4 字节长度字段；引用在压缩指针下 4 字节。

【算例 3】`new Object()`：12 + 0 = 12，补到 8 的倍数是 16 字节；100 万个就是 16 × 1,000,000 = 16,000,000 字节，约 15.26 MiB。含一个 `int` 和一个 `long` 的对象：HotSpot 按字段大小重排，`long` 优先排在前面——头 12 字节后补 4 字节（`long` 要 8 字节对齐，偏移 12 不够），`long` 占偏移 16 ~ 24，`int` 占偏移 24 ~ 28，合计 28，补到 8 的倍数是 32 字节，声明顺序写反了也是 32 字节；100 万个是 32,000,000 字节，约 30.52 MiB。一个 `Integer` 也是 12 + 4 = 16 字节，`Long` 是头 12 字节 + 4 字节填充 + 8 字节 = 24 字节。

数组对象：`int[1000]` 是 12（头）+ 4（长度）+ 1,000 × 4 = 4,016 字节，已是 8 的倍数，不用补。`Object[10000]` 本身是 12 + 4 + 10,000 × 4 = 40,016 字节，只是 10,000 个引用；`Long[10000]` 还要加 10,000 个 `Long` 对象：40,016 + 10,000 × 24 = 280,016 字节，约 0.27 MiB，引用只占其中约七分之一。

`int` 与 `Integer` 的价差也按头算：`int[10000]` 是 12 + 4 + 10,000 × 4 = 40,016 字节；`Integer[10000]` 的数组本身同样是 40,016 字节（10,000 个引用），但每个 `Integer` 对象另占 16 字节，10,000 个共 160,000 字节，合计 200,016 字节，约是 `int[]` 的 5 倍。`boolean` 字段占 1 字节，`short`/`char` 占 2 字节，`long`/`double` 占 8 字节，引用占 4 字节（压缩指针下），都先加进 12 字节头再按 8 对齐。

空数组也不为零：`int[0]` 是 12（头）+ 4（长度）+ 0 = 16 字节，`Object[0]` 同样 16 字节；只建数组不填元素，每个空数组先占 16 字节。

### inode 与块：小文件贵在块，不在内容

公式：磁盘占用 = 文件数 × 块大小（每文件至少一个块），inode 消耗 = 文件数。

【算例 4】100 万个 100 字节的小文件：逻辑大小 100 万 × 100 = 100,000,000 字节，约 95.37 MiB；块占用 100 万 × 4,096 = 4,096,000,000 字节，约 3.81 GiB；浪费 4,096,000,000 − 100,000,000 = 3,996,000,000 字节，约 3.72 GiB，浪费率约 97.6%。同时耗掉 100 万个 inode：按默认每 16,384 字节一个 inode，16 GiB 文件系统默认约 16 × 2^30 / 16,384 = 1,048,576 个 inode，刚够装；10 GB（十进制）的盘默认约 610,351 个 inode，装到约 61 万个文件就先耗尽 inode，盘还剩空间也写不进。

对照两组：10 万个 100 字节文件逻辑约 9.54 MiB，块占用 10 万 × 4,096 = 409,600,000 字节，约 390.63 MiB，浪费约 97.6%；1 万个 1 KB 文件逻辑 10,000,000 字节，约 9.54 MiB，块占用 10,000 × 4,096 = 40,960,000 字节，约 39.06 MiB，浪费约 75%。单个 1 字节文件也要占一整块，浪费 4,095 字节，浪费率约 99.98%。

上面只算了数据块和 inode，未计目录项本身占的块：目录也是文件，成千上万个文件挤在一个目录里，目录项还要另占块；算容量时把目录块单独留出来，生产值以 `du` 实测为准。

### 边界条件

- Java 的数字只在 64 位 HotSpot + 压缩指针（堆 ≤ 32 GB）下成立：关掉压缩指针，对象头变 16 字节，引用变 8 字节；`new Object()` 仍是 16 字节（头 16 + 无实例数据），但含字段的对象会变大，上面所有 Java 算式重算；不同 JDK 大版本以 JOL 实测为准。
- “一个 emoji 4 字节”只对单个码点的 emoji 成立：带肤色修饰符、零宽连接的组合 emoji 是多个码点，字节数按码点逐个加，总数超过 4 字节；估算行宽时按最坏 4 字节 × 字符数留量，别按表情个数估。
- C 结构体的数字跟编译器和 ABI 走：`#pragma pack`、32 位平台、ARM 与 x86-64 的对齐规则都可能改结果；跨平台代码以本机 `sizeof` 实测为准，本文数字是 x86-64 典型值。
- inode 与块的数字是 ext4 默认口径（4 KB 块、16,384 字节/inode、无 inline_data、无压缩）：XFS 的 inode 是动态分配的，没有固定上限；btrfs、NTFS、APFS 的分配方式不同，数字不能直接套用；生产值以 `df -i`、`du`、`dumpe2fs` 实测为准。

## 原理剖析

本节只把原文已有章节给出的结论拆开讲清机制：不引入新概念，不补新数字，数字一律复用定量节已核验的算例；凡原文没展开的点，文中明确标注，不作定论。

### 字符集、编码与乱码：三处口径必须一致

原文的结论是：字符集是“有哪些字符、各编什么号”的字典，编码是“号码怎么落成字节”的规则，Unicode 是字符集，UTF-8 与 UTF-16 是它的两种编码。乱码排查的三问，正是把这条链路拆成三处口径来对：文件是什么编码存的、程序按什么编码读的、终端或页面按什么编码显示的。

机制是这样串起来的：存的时候按一种编码把码点落成字节，读的时候必须按同一种编码把字节还原成码点，显示的时候又要按同一种编码去解释。原文给出的排查写法就是这三处的抓手：存的一侧用 `file -i xxx` 看，读的一侧 Java 用 `-Dfile.encoding=UTF-8`、Python 用 `open(encoding='utf-8')`。三处中任何一处口径不同，同一串字节就会被解释成另一组字符，这就是乱码；原文没有展开某一串字节在两种编码下具体会被错读成什么样子，原文未展开，此处不作定论。

同一条机制也能解释原文的 MySQL 经典坑：MySQL 的 `utf8` 不等于真 UTF-8，存不了 emoji，建表要用 `utf8mb4`。定量节把这条结论落成了可算的数：UTF-8 按 RFC 3629 的口径，ASCII 字符 1 字节、汉字 3 字节、辅助平面字符（含常见 emoji）4 字节（出处：定量节口径与【算例 1】）。`"Hi你好😀"` 共 5 个码点，`H`、`i` 各 1 字节，`你`、`好` 各 3 字节，`😀`（U+1F600）4 字节，合计 2 + 6 + 4 = 12 字节（出处：定量节【算例 1】）。也就是说，一个 emoji 在字节数上就占了 4 字节的份额，编码口径把它排除在外，存入时就会出问题；原文没有展开 `utf8` 与 `utf8mb4` 在 MySQL 内部具体如何区分这 4 字节字符，原文未展开，此处不作定论。

行宽的算法也是同一条机制的延伸：定量节按最坏情况留行宽，每字符最多 4 字节，`VARCHAR(100)` 最坏 100 × 4 = 400 字节，再加 2 字节长度前缀（出处：定量节【算例 1】）；上面那串 12 字节的实际内容只占 12 字节加前缀。长度字段按字节算、而不是按字符数算，这与原文“字符数不等于字节数”的结论是一回事：一个汉字在 UTF-8 里 3 字节，emoji 常是 4 字节，按字节截断字符串可能把字符截成两半。

### 大小端：同一串字节，两种读法

原文的结论是：小端是低字节存低地址，x86 与 ARM 默认小端；网络传输统一大端，即网络字节序；Java 里日常基本碰不到，写二进制协议或解析 pcap 时才需要。

机制是：字节序只决定多字节数据在内存里按什么顺序排布，不改变字节本身。原文“基础知识补强”里给出的判断写法正是利用这一点：

```c
int x = 1;
char *p = (char *)&x;   // 取最低地址处的字节
*p == 1 → 小端；*p == 0 → 大端
// 小端：低位字节 01 在低地址；大端：高位字节在低地址，01 会在高地址处。
```

读最低地址处的那个字节，就能反推出整台机器的排布方式：小端时低位字节落在低地址，大端时低位字节落在高地址。跨机器或跨语言传二进制时，双方必须先对齐这一条，否则同一串字节会被读成另一个数；原文也说了，纯文本协议天然没有这个问题，这也是文本协议流行的原因之一。原文没有展开网络字节序在具体协议里如何约定、以及 pcap 解析时除字节序外还要对齐哪些字段，原文未展开，此处不作定论。

### 内存对齐与对象体量：填充不是浪费，是取数方式决定的

原文的结论是：CPU 按字长（64 位 = 8 字节）取内存，变量地址是“自然对齐”的倍数时一次取完，否则跨两次取，变慢；C 结构体由编译器自动在字段间插 padding；Java 对象是对象头 12 字节（64 位加压缩指针）加实例数据，再补到 8 的倍数。

定量节把这条结论落成了两条算式：字段起始偏移要是自身大小的倍数，结构体总大小要是最大字段大小的倍数（出处：定量节“对齐填充”节）。以【算例 2】为例，`struct { char a; int b; }` 中 `a` 占偏移 0（1 字节），`b` 要 4 字节对齐，偏移 1 ~ 3 补 3 字节，`b` 占偏移 4 ~ 7，合计 1 + 3 + 4 = 8 字节（出处：定量节【算例 2】）。这 3 字节填充不是多占的空间，而是让 `b` 落在 4 的倍数上、一次取完的代价；不补，`b` 就会跨两次取。

同一条算式也解释了为什么字段顺序能省空间：`struct { char a; double d; char c; }` 是 1 + 7 + 8 + 1 + 7（尾部补齐到 8 的倍数）= 24 字节，调换顺序成 `struct { double d; char a; char c; }` 是 8 + 1 + 1 + 6 = 16 字节，只改顺序就省 8 字节，省三分之一（出处：定量节【算例 2】）。两个 `char` 挤进 `int` 前面的空位就不产生额外填充，`struct { int a; char b; char c; }` 与 `struct { char a; char b; int c; }` 都是 8 字节（出处：定量节“对齐填充”节）。数组按 stride 算，8 字节的结构体 10,000 个占 80,000 字节，24 字节的结构体 1,000 个占 24,000 字节（出处：定量节【算例 2】）；64 字节缓存行能装 8 个 8 字节结构体，只能装 2 个 24 字节结构体（余 16 字节）（出处：定量节“对齐填充”节）。原文提到伪共享是高并发计数器的隐形杀手、可用 `@Contended` 或手动 padding 隔离，但原文没有展开伪共享在什么访问模式下触发、以及 padding 隔离具体要补多少，原文未展开，此处不作定论。

Java 一侧的机制是同一条对齐规则换了一套口径：对象大小等于向上取整到 8 的倍数（12 字节头加实例数据），数组再加 4 字节长度字段，引用在压缩指针下 4 字节（出处：定量节“Java 对象体量”节）。【算例 3】中 `new Object()` 是 12 + 0 = 12，补到 8 的倍数是 16 字节，100 万个就是 16 × 1,000,000 = 16,000,000 字节，约 15.26 MiB（出处：定量节【算例 3】）。含一个 `int` 和一个 `long` 的对象，头 12 字节后补 4 字节（`long` 要 8 字节对齐，偏移 12 不够），`long` 占偏移 16 ~ 24，`int` 占偏移 24 ~ 28，合计 28，补到 8 的倍数是 32 字节，100 万个是 32,000,000 字节，约 30.52 MiB（出处：定量节【算例 3】）。一个 `Integer` 也是 12 + 4 = 16 字节，`Long` 是头 12 字节加 4 字节填充加 8 字节 = 24 字节（出处：定量节【算例 3】）。所以原文说“小对象数组的内存开销常被低估”，落到数上就是：`Object[10000]` 本身是 12 + 4 + 10,000 × 4 = 40,016 字节，只是 10,000 个引用；`Long[10000]` 还要加 10,000 个 `Long` 对象，40,016 + 10,000 × 24 = 280,016 字节，约 0.27 MiB，引用只占其中约七分之一（出处：定量节“Java 对象体量”节）。`int[10000]` 是 12 + 4 + 10,000 × 4 = 40,016 字节，`Integer[10000]` 的数组本身同样是 40,016 字节，但每个 `Integer` 对象另占 16 字节，10,000 个共 160,000 字节，合计 200,016 字节，约是 `int[]` 的 5 倍（出处：定量节“Java 对象体量”节）。空数组也不为零，`int[0]` 与 `Object[0]` 同样是 12 加 4 加 0 = 16 字节（出处：定量节“Java 对象体量”节）。这些数字只在定量节定死的口径下成立，即 64 位 HotSpot 加压缩指针（堆 ≤ 32 GB）、对象头 12 字节、8 字节对齐；关掉压缩指针后对象头与引用的数字会变，原文边界条件节已说明，上面所有 Java 算式要重算，原文未展开重算后的具体数值，此处不作定论。

### 文件系统、inode 与块：文件名、元数据与数据块是三回事

原文的结论是：inode 存元数据（权限、大小、块指针），文件名只是目录项指向 inode；软链是快捷方式（删源就断），硬链是同一 inode 的别名；`df -i` 看 inode 用量，小文件太多会先耗尽 inode，磁盘还有空间也写不进。

机制是把一个文件拆成三层：目录项只记名字到 inode 的指向，inode 只记元数据与块指针，真正的内容存在数据块里。删文件删的是目录项和引用计数，文件被进程打开时删掉名字，数据仍在、空间不释放，进程关了才真回收；`write` 返回成功只代表进了页缓存，断电仍可能丢，`fsync` 才是落盘保证——这些都是原文“关键机制速览”里已给出的结论，本节只是把它们按三层关系串起来：名字、元数据、数据块各管各的，任何一层先耗尽，写操作都会失败。

定量节把“小文件贵在块，不在内容”落成了数：公式是磁盘占用等于文件数乘块大小（每文件至少一个块），inode 消耗等于文件数（出处：定量节【算例 4】）。【算例 4】中 100 万个 100 字节的小文件，逻辑大小 100 万 × 100 = 100,000,000 字节，约 95.37 MiB；块占用 100 万 × 4,096 = 4,096,000,000 字节，约 3.81 GiB；浪费 4,096,000,000 − 100,000,000 = 3,996,000,000 字节，约 3.72 GiB，浪费率约 97.6%（出处：定量节【算例 4】）。同时耗掉 100 万个 inode：按默认每 16,384 字节一个 inode，16 GiB 文件系统默认约 16 × 2^30 / 16,384 = 1,048,576 个 inode，刚够装；10 GB（十进制）的盘默认约 610,351 个 inode，装到约 61 万个文件就先耗尽 inode，盘还剩空间也写不进（出处：定量节【算例 4】）。对照的两组也是同一条公式：10 万个 100 字节文件逻辑约 9.54 MiB，块占用 10 万 × 4,096 = 409,600,000 字节，约 390.63 MiB，浪费约 97.6%；1 万个 1 KB 文件逻辑 10,000,000 字节，约 9.54 MiB，块占用 10,000 × 4,096 = 40,960,000 字节，约 39.06 MiB，浪费约 75%；单个 1 字节文件也要占一整块，浪费 4,095 字节，浪费率约 99.98%（出处：定量节【算例 4】）。定量节同时说明，上面只算了数据块和 inode，未计目录项本身占的块，成千上万个文件挤在一个目录里，目录项还要另占块，算容量时要把目录块单独留出来，生产值以 `du` 实测为准；原文没有展开目录项占块的具体算法，原文未展开，此处不作定论。同样，inode 与块的数字是 ext4 默认口径（4 KB 块、16,384 字节一个 inode），XFS 的 inode 是动态分配的、没有固定上限，btrfs、NTFS、APFS 的分配方式不同，数字不能直接套用，生产值以 `df -i`、`du`、`dumpe2fs` 实测为准（出处：定量节“边界条件”节）。

## 实战案例

### 案例一

现象：建表时用 MySQL 的 `utf8` 存 emoji 存不进；另有一张表把字段定成 `VARCHAR(255)`，在 `utf8mb4` 下建索引时撞上旧版 InnoDB 的索引上限报错。两处现象指向同一条原文结论：`utf8` 不等于真 UTF-8，存不了 emoji，建表用 `utf8mb4`。

排查：先按原文乱码排查三问对口径——文件是什么编码存的，用 `file -i xxx` 看；程序按什么编码读的，Java 用 `-Dfile.encoding=UTF-8`，Python 用 `open(encoding='utf-8')`；再看终端或页面按什么编码显示。口径对齐后，再按定量节的数算行宽：UTF-8 按 RFC 3629 的口径，ASCII 字符 1 字节、汉字 3 字节、辅助平面字符（含常见 emoji）4 字节（出处：定量节口径与【算例 1】）。`"Hi你好😀"` 共 5 个码点，合计 2 + 6 + 4 = 12 字节（出处：定量节【算例 1】），其中 emoji 一个就占 4 字节。按最坏情况留行宽，每字符最多 4 字节，`VARCHAR(255)` 最坏 255 × 4 = 1,020 字节，超过旧版 InnoDB 767 字节索引上限（出处：定量节【算例 1】）。

结论：字符集改成 `utf8mb4` 只是第一步，行宽与索引长度要跟着最坏 4 字节重算：191 × 4 = 764 字节，刚好塞进 767（出处：定量节【算例 1】），所以把字段缩短到 191 是一条原文定量节已给出的出路。原文没有展开除缩短字段之外的其他解法在此处是否适用，原文未展开，此处不作定论。

### 案例二

现象：磁盘明明还有空间，写文件却写不进；`ls -l` 看到的逻辑大小不大，`du` 看到的实际占用却大得多。两处现象指向同一条原文结论：小文件太多会先耗尽 inode，磁盘还有空间也写不进；`ls -l` 是逻辑大小，`du` 是实际占用的块数。

排查：先用 `df -i` 看 inode 用量，再用 `du` 与 `ls -l` 对同一批文件各算一遍。按定量节【算例 4】的数对：100 万个 100 字节的小文件，逻辑大小 100 万 × 100 = 100,000,000 字节，约 95.37 MiB；块占用 100 万 × 4,096 = 4,096,000,000 字节，约 3.81 GiB；浪费 4,096,000,000 − 100,000,000 = 3,996,000,000 字节，约 3.72 GiB，浪费率约 97.6%（出处：定量节【算例 4】）。同时耗掉 100 万个 inode：按默认每 16,384 字节一个 inode，16 GiB 文件系统默认约 16 × 2^30 / 16,384 = 1,048,576 个 inode，刚够装；10 GB（十进制）的盘默认约 610,351 个 inode，装到约 61 万个文件就先耗尽 inode，盘还剩空间也写不进（出处：定量节【算例 4】）。对照组也符合同一条公式：10 万个 100 字节文件逻辑约 9.54 MiB，块占用 10 万 × 4,096 = 409,600,000 字节，约 390.63 MiB，浪费约 97.6%（出处：定量节【算例 4】）。

结论：这不是磁盘空间不够，而是每文件至少占一个 4 KB 块、每文件耗一个 inode，两层开销先到了上限；`df -i` 与 `du` 是定位这类故障的抓手，`ls -l` 只看到逻辑大小，看不到块占用与 inode 消耗。定量节同时说明，上面只算了数据块和 inode，未计目录项本身占的块，生产值以 `du` 实测为准；原文没有展开目录项占块与 inode 耗尽之外的其他写不进原因，原文未展开，此处不作定论。

## 小技巧与冷知识

【小技巧】Java 18 开始默认字符集就是 UTF-8（JEP 400），新项目不用再写 `-Dfile.encoding=UTF-8`；但跑在 Java 8/11/17 上的老代码仍要显式指定，升级 JDK 后顺手把启动参数里的 `-Dfile.encoding` 删掉，别留着两份口径打架。

【小技巧】UTF-8 文件带 BOM 时，Python 用 `encoding='utf-8-sig'` 读会自动去掉开头的 BOM，写时则会补一个；Java 没有这个待遇，读到的第一个字符会是 `\uFEFF`，首字段解析前要手动 strip 掉，或者用 Apache Commons IO 的 BOMInputStream，否则第一列的列名总对不上。

【小技巧】MySQL 从 `utf8` 改 `utf8mb4` 时别只改字符集，还要看索引长度：`varchar(255)` 在 utf8mb4 下占 255×4=1020 字节，旧版 InnoDB 的 767 字节索引上限会直接报错；要么把字段缩短到 191，要么确认行格式是 DYNAMIC 且开了大前缀（上限 3072 字节），改完用 `SHOW CREATE TABLE` 验一遍再上线。

【小技巧】按字节截字符串前，先想想会不会把字符截裂：UTF-8 的后续字节都以 `10` 开头，截断后从末尾往回找，遇到不完整的字符就把末尾几个字节一起丢掉；更稳妥的是先 decode 成字符串再切，长度校验也按字符数和字节数各算一遍，数据库字段和协议长度字段多半按字节算。

【小技巧】Java 的 `String.length()` 数的是 UTF-16 码元，不是字符数：一个 emoji 占 2 个码元，`length()` 会多算 1；要真实字符数用 `codePointCount(0, length())`，遍历字符串用 `codePoints()` 而不是 `charAt`，否则按字符切 emoji 会切出半个代理对。

【小技巧】写二进制协议时把字节序写死在代码里：Java 的 `ByteBuffer` 默认大端，正好就是网络字节序，解析 x86 的小端协议要显式 `order(ByteOrder.LITTLE_ENDIAN)`；原文说 Java 里基本碰不到大小端，意思是日常开发碰不到，写协议解析时它就是第一要确认的事。

【小技巧】看文件大小用 `ls` 还是 `du`，先想清楚要的是哪个数：`ls -l` 是逻辑大小，`du` 是实际占用的块数；ext4 默认一个块 4KB，1 字节的小文件也要占满一个块，所以 `du` 永远比 `ls` 看着大，小文件成堆时差距能到几十倍，容量评估用 `du` 才准。

【小技巧】文件名大小写在 macOS 和 Linux 上表现不一样：macOS 默认的 APFS 大小写不敏感，`Readme.md` 和 `README.md` 是同一个文件，Linux 上却是两个；本地 Mac 跑得好好的代码，一上 Linux 就报文件找不到，先对一遍文件名的大小写，别先怀疑路径拼错了。

【小技巧】删了文件磁盘空间不释放，先查谁还攥着句柄：`lsof | grep deleted` 能列出已删除但仍被进程打开的文件，重启或关闭那个进程空间才回来；不想重启进程时，可以用 `: > /proc/<pid>/fd/<fd>` 把那个句柄指向的文件截断，空间立刻释放，日志文件轮转就靠这一招救急。

【小技巧】mmap 适合大文件随机读，但文件被截短后访问映射区会收到 SIGBUS：映射建立后文件大小变了，超出的部分再访问就直接崩进程；只读场景优先用 mmap，写场景要把文件大小管理好，或者在截断前先解除映射，别让映射区悬在已被截掉的区域上。

【小技巧】内存看着满了先看 `free` 的 available 那一列：Linux 把空闲内存都拿去做页缓存，used 很高不代表不够用，available 才是真正能分配的；`echo 3 > /proc/sys/vm/drop_caches` 能清页缓存，但只适合测试环境验证，在生产机上清缓存等于主动把热数据赶出内存。

【小技巧】硬链接不能跨文件系统，也不能链目录：inode 编号只在单个文件系统内有效，跨盘 `ln` 会报 Invalid cross-device link，目录只能靠软链接；备份脚本里想用硬链接省空间（`cp -al` 快照那套），源和目标必须在同一个文件系统里。

【冷知识】UTF-8 是 Ken Thompson 和 Rob Pike 在 1992 年一张餐垫上设计出来的：两人在新泽西一家小餐馆里花一晚上定下了变长编码方案，第二天就有了能跑的实现；如今超过 98% 的网页都用 UTF-8，它赢在和 ASCII 完全兼容、又没有字节序问题。

【冷知识】"大小端"这个词来自《格列佛游记》：Danny Cohen 在 1980 年的论文《On Holy Wars and a Plea for Peace》里借用了书里"大端派和小端派为鸡蛋该磕哪头打仗"的典故；网络字节序定为大端，也是这场"圣战"里少数真正达成共识的结果。

【冷知识】ASCII 在 1963 年定型，只有 128 个字符；emoji 是 1999 年栗田穣崇为 NTT DoCoMo 的 i-mode 服务画的 176 个 12×12 像素小图，2010 年才随 Unicode 6.0 正式进入字符集——表情符号从运营商私货变成世界标准，只用了十一年。

【冷知识】GB2312（1980 年）、GBK（1995 年）、GB18030（2000 年）是三代中文编码：GB2312 只覆盖常用汉字，GBK 扩到两万多，GB18030 是覆盖全部 Unicode 的强制性国家标准；Windows 中文版默认 GBK，就是这套标准一路沿用下来的结果。

【冷知识】inode 是 index node（索引节点）的缩写，这个概念从早期 Unix 一直沿用至今；文件系统本身也在换代：NTFS 在 1993 年随 Windows NT 3.1 发布，ext4 在 2008 年随 Linux 2.6.28 稳定，APFS 在 2017 年随 macOS High Sierra 接替 HFS+。

【冷知识】UTF-8 文件开头的 EF BB BF，本质上是一个字符 U+FEFF：它原名是"零宽不换行空格"，被借来当编码签名的 BOM 用；UTF-16 的 BOM 是 FE FF 或 FF FE，还能顺带标明字节序，UTF-8 的 BOM 只剩"这是 UTF-8"一个作用。

## 面试与自测

1. 出现乱码时按哪三问排查？MySQL 里 `utf8` 有什么经典坑？
2. C 结构体 `struct { char a; int b; }` 为什么是 8 字节而不是 5 字节？Java 里 `new Object()` 为什么占 16 字节？
3. 软链接和硬链接有什么区别？`df -i` 是在看什么，什么情况下“磁盘还有空间也写不进”？

4. 100 万个 100 字节的小文件存在 ext4（默认块 4 KB、默认每 16,384 字节一个 inode）上：逻辑大小多少？实际占多少磁盘？浪费多少、浪费率多少？inode 够不够用，16 GiB 和 10 GB 的盘各是什么结论？

### 参考答案

1. 三问：文件是什么编码存的（`file -i xxx` 看）；程序按什么编码读的（Java `-Dfile.encoding=UTF-8`，Python `open(encoding='utf-8')`）；终端/页面按什么编码显示的。MySQL 经典坑：`utf8` ≠ 真 UTF-8，存不了 emoji，建表要用 `utf8mb4`。
2. CPU 按字长（64 位 = 8 字节）取内存，变量地址是“自然对齐”的倍数时一次取完；编译器自动在字段间插 padding，`a` 后面补 3 字节，所以是 8 字节。Java 对象是对象头 12 字节（64 位 + 压缩指针）+ 实例数据 + padding 补到 8 的倍数，`new Object()` 没有实例数据，12 字节补到 8 的倍数就是 16 字节。
3. 软链是快捷方式，删源就断；硬链是同一 inode 的别名。`df -i` 看 inode 用量：小文件太多会先耗尽 inode，磁盘还有空间也写不进。inode 本身存元数据（权限/大小/块指针），文件名只是目录项指向 inode。

4. 逻辑 100 万 × 100 字节 = 100 MB，约 95.4 MiB；实际 100 万 × 4 KB ≈ 3.81 GiB，浪费约 3.72 GiB，约 97.6%。耗 100 万 inode：16 GiB 盘默认约 1,048,576 个，刚够；10 GB 盘默认约 61 万个，先耗尽。
