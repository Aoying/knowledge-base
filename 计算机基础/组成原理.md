# 组成原理

## 1. 核心概念

冯·诺依曼结构：程序与数据同存于一个存储器，CPU 按"取指 → 译码 → 执行"循环，五大部件是运算器、控制器、存储器、输入、输出。现代计算机在其上加了缓存、流水线、多核与向量指令，主干未变。

一条指令的生命周期：PC（程序计数器）指向的地址取指 → 译码 → 执行 → PC 自增或按跳转改写。理解这条线，就能理解分支预测、流水线气泡、上下文切换为什么有成本。

## 2. 存储层次：性能优化的根

| 层级 | 容量量级 | 访问延迟量级 | 备注 |
|---|---|---|---|
| 寄存器 | KB | <1 ns | 编译器/JIT 分配 |
| L1 缓存 | 32–64 KB/核 | ~1 ns | 指令与数据分开 |
| L2 缓存 | 256 KB–数 MB/核 | ~3–5 ns | |
| L3 缓存 | 数 MB–数百 MB | ~10–20 ns | 多核共享 |
| 内存（DRAM） | GB–TB | ~100 ns | |
| SSD | TB | ~100 μs | 比内存慢约千倍 |
| 机械盘/网络 | — | ms 级 | |

每往下一层慢一个数量级左右。"数据在哪一层"几乎直接决定性能：缓存以 64 字节的缓存行（cache line）为单位搬运，顺序访问能整批命中，随机指针跳转则次次 miss——这是连续数组优于链表的根本原因。

两个常被忽略的细节：**预取**（CPU 检测到顺序访问会提前搬后续缓存行，随机访问则帮不上忙）；**写回**（写命中只改缓存、择机回写内存，"写进缓存"≠"数据已到内存"——这正是需要一致性协议与内存屏障的根源）。

## 3. CPU 执行的几个关键机制

- **流水线**：取指/译码/执行/访存/写回并行重叠提升吞吐；分支猜错要冲刷流水线，所以有了**分支预测**——启示：可预测的分支（已排序数据、稳定条件）明显更快。
- **乱序执行与超标量**：CPU 一周期可发射多条指令并按数据依赖乱序调度——重排不只在编译器层，硬件也在重排。这是 JMM 存在的深层原因：内存屏障最终要落成硬件指令。
- **多核与 NUMA**：多核各有 L1/L2、共享 L3；服务器还有 NUMA——访问本节点内存比跨节点快，大堆 JVM/数据库部署会遇到绑核与 NUMA 感知分配问题。
- **缓存一致性（MESI 等协议）**：两个线程频繁写同一缓存行的不同变量会互相使对方缓存失效，叫**伪共享**（false sharing），Java 里用 `@Contended` 填充解决，计数器拆分（LongAdder）同理。
- **虚拟内存**：每进程独立地址空间，MMU 按页（4 KB）经 TLB 翻译到物理内存；TLB miss 是真实开销，JVM 大页、堆大小设置都与之有关。
- **SIMD 向量指令**：一条指令并行算多个数据（AVX 等）。向量检索的距离计算、numpy 之所以快，很大程度靠它。

## 4. IO：中断、DMA 与总线

- **中断**：外设完成后通知 CPU，避免轮询空转；但每次中断都要保存现场，高频小包下中断本身成开销，于是有中断合并、NAPI 等折中。
- **DMA**：大块数据由 DMA 控制器在外设与内存间直接搬运，不经 CPU。"零拷贝"的本质是减少这条通路上多余的 CPU 拷贝，如 NIO 的 `transferTo` 落在 sendfile 上。
- **存储接口与带宽总账**：NVMe 走 PCIe、多队列并行，远超 SATA 单队列；CPU、GPU、NVMe 又共享内存/PCIe 带宽——本地推理 offload 到内存后变慢，账就出在这条总线上。

## 5. 数据的表示

- 补码：负数用补码表示，减法变加法；溢出是静默的（Java int 溢出不报错）。
- 浮点 IEEE 754：符号 + 阶码 + 尾数的取舍决定了 `0.1 + 0.2 != 0.3`；钱用 BigDecimal 本质是避开二进制浮点。
- 字节序：大端/小端影响协议与文件格式解析，跨语言传二进制时必须约定。

## 6. 与 JVM 和性能调优的关联

- **对象布局与对齐**：对象头（Mark Word + 类型指针）加字段要 8 字节对齐，实际占用往往大于字段之和，算容量时别按字段裸加。
- **数组 vs 链表**：数组连续内存、缓存友好，遍历远快于链表，与"链表插入 O(1)"的纸面结论常相反——`ArrayList` 胜 `LinkedList` 的绝大多数场景，根源在此。
- **volatile 与内存屏障**：volatile 写要插入屏障指令，逼缓存行刷到对其他核可见——成本不在指令本身，而在破坏流水线与缓存状态，所以高频写路径上要谨慎，能用 LongAdder 分段就别用单个 volatile 计数。
- **GC 与 JIT**：GC 扫描/复制对象是大量内存遍历，存活对象越散、缓存 miss 越多、停顿越长，对象布局紧凑同样是 GC 友好；JIT 的机器码产物放 Code Cache，方法内联还顺带提高指令缓存命中。
- **数据库与推理**：B+ 树索引（扇出大、节点对齐页大小）是为存储层次量身定做的，Buffer Pool 命中率就是数据库版缓存命中率；本地大模型推理的瓶颈同样是权重搬运，量化减少搬运字节数所以直接提速。
- **排查工具**：`perf`、火焰图看 CPU 周期花在哪条指令上；上下文切换贵，是因为要保存/恢复寄存器与刷新 TLB。

## 7. 数字速记（排查时随手估算用）

- L1 ~1 ns，内存 ~100 ns，SSD 随机读 ~100 μs，磁盘寻道 ~10 ms。
- 一次上下文切换 ~1–10 μs 直接成本 + 缓存/TLB 失效的间接成本，往往后者更大。

## 8. 常见误区

- 只看时间复杂度不看数据布局：同为 O(n)，顺序扫数组与跳着追指针可差几倍到几十倍。
- 认为多核等于线性提速：缓存一致性、内存带宽、伪共享都会让加速比提前见顶。
- 把 SSD 延迟当内存考虑：miss 去内存是百纳秒、去磁盘是百微秒，差三个数量级，系统设计对"是否落盘"必须敏感。

## 小技巧与冷知识

【小技巧】怀疑伪共享时，先用 perf c2c 验证再动代码：`perf c2c record` 加 `perf c2c report` 能直接定位哪两个地址落在同一缓存行、被哪些核反复互相失效。别凭感觉加 @Contended 或填充——先确认是真伪共享还是锁竞争、带宽瓶颈，否则填充白加，问题还在。

【小技巧】多线程各写数组不同下标时，让步长按缓存行对齐：8 个线程各写一个 long 数组元素，相邻元素同处一个 64 字节行，写冲突和单线程差不多；把每个线程负责的元素隔开 8 个 long（64 字节），冲突立刻消失。这就是 LongAdder 分段思想的手工版，写并发计数器时直接套用。

【小技巧】分支密集的循环，先把数据排好序再跑：原文只说“可预测的分支更快”，落到代码上就是先 sort 再进循环——排序本身要 O(n log n)，但循环里分支预测命中率上去后，省下的流水线冲刷往往能抵回来。数据本来就有序、只是没排过时，这招最划算。

【小技巧】只用结构体里一两个字段时，改成“字段分开存”：数组里每个元素带十个字段、循环只读其中一个，缓存行 64 字节里大部分是白搬的；把常用字段抽成单独的数组（结构体数组改成数组结构体，SoA），一次搬运全是有效数据。游戏引擎和数据库列存用的就是这招。

【小技巧】大堆 JVM 先看 TLB 再调堆大小：堆越大、页表项越多，TLB 覆盖不住就频繁 miss；开大页（-XX:+UseLargePages，x86-64 上一般是 2 MB，一项覆盖的内存是 4 KB 页的 512 倍）能让同样的 TLB 项覆盖更多内存。改之前用 perf stat 看 dTLB-load-misses 占比，确认真是 TLB 瓶颈再开，别盲目加参数。

【小技巧】用 JOL 看对象到底占多大：org.openjdk.jol 的 `ClassLayout.parseInstance(obj).toPrintable()` 能打印对象头、字段偏移和填充字节，算容量时不再凭字段裸加。怀疑“这个对象怎么这么大”时先跑 JOL，看到对齐填充再决定要不要拆字段、换类型。

【小技巧】批量写计数器时先在线程本地攒着、最后一次性合并：每个线程攒够一批再往共享计数器写一次，共享缓存行的失效次数从每次写变成每批一次。LongAdder 是这招的现成实现，自己手写时用局部变量或 ThreadLocal 攒着也一样，高频写路径上先想“能不能少写”，再想“怎么写更快”。

【小技巧】读大文件只读不写时优先 mmap 而不是反复 read：mmap 让文件页直接进页缓存，缺页时才按需搬运，省掉用户态与内核态之间的拷贝；随机读小块时配合 madvise 预取效果更好。原文的零拷贝讲的是网卡到磁盘，mmap 是磁盘到内存的同类思路。

【小技巧】NUMA 机器上先绑核再谈性能：`numactl --hardware` 能看到每个节点的内存与 CPU 归属，跨节点访存比本节点慢得多；线程绑到固定核、内存分配在同节点（numactl --cpunodebind / --membind），能先排除“线程在节点间漂移”这个变量。没绑核就测出来的性能抖动，很可能只是调度器在捣乱。

【小技巧】分不清瓶颈在算力还是内存搬运时，看 perf 的两个数：cache-misses 占比高、IPC（每周期指令数）远低于 1，基本是内存墙；反过来 IPC 明显高于 1 且缓存命中高，才是算力瓶颈。先定性再优化，别在算力瓶颈上调数据结构、也别在内存瓶颈上调算法常数。

【冷知识】缓存是 1968 年 IBM System/360 Model 85 首次商用的：它在 CPU 和主存之间加了一小块高速缓冲存储器，这就是缓存的雏形。冯·诺依曼 1945 年的 EDVAC 草案里并没有这一层，存储层次是后来为“CPU 越来越快、内存跟不上”硬生生长出来的。

【冷知识】“内存墙”这个词来自 1995 年 Wulf 和 McKee 的论文《Hitting the Memory Wall》：论文指出 CPU 性能年增速远高于内存，差距只会越拉越大，预言缓存层次会越来越深。三十年过去，L1/L2/L3、NUMA、大页这些补丁，全是这篇论文预言的注脚。

【冷知识】L1 指令缓存和数据缓存分开，是“改良哈佛结构”：程序和数据在主存里仍是同一片（冯·诺依曼），但到了 L1 这一层，指令和数据各走各的缓存。原文表里 L1 注明的“指令与数据分开”，就是这条分界线。

【冷知识】多核提速的上限定律叫阿姆达尔定律：Gene Amdahl 在 1967 年指出，程序里串行部分的占比决定了并行加速比的天花板，串行部分占 5% 时再多核也超不过 20 倍。原文说“多核不等于线性提速”，阿姆达尔定律就是把这句话量化了的公式。

【冷知识】缓存行不全是 64 字节：x86-64 常见 64 字节，但 Apple M1 的 L1 缓存行是 128 字节。写跨平台的高性能代码时，填充和对齐不能把 64 写死，跨架构要按目标平台的缓存行大小取数。

【冷知识】IEEE 754 浮点标准背后是 William Kahan：他主导了 1985 年标准的制定，因此被称为“浮点数之父”，还因此获得 1989 年图灵奖。原文说“钱用 BigDecimal 是避开二进制浮点”，根源是这套标准当初为科学计算设计，压根没考虑十进制金额。

## 9. 面试与自测

1. 从寄存器到磁盘，每一层的延迟量级是多少？差多少倍？
2. 什么是缓存行？为什么顺序访问数组比链表快？
3. 伪共享是什么？Java 里怎么解决？
4. 分支预测失败为什么慢？
5. 浮点数为什么不能表示金额？
6. volatile 为什么慢？它的开销落在哪一层硬件机制上？

### 参考答案

1. 寄存器 <1 ns；L1 约 1 ns；L2 约 3–5 ns；L3 约 10–20 ns；内存约 100 ns；SSD 约 100 μs；机械盘/网络 ms 级。每往下一层慢一个数量级左右：内存到 SSD 差约 1000 倍（100 ns→100 μs），SSD 到磁盘寻道（约 10 ms）又差约 100 倍。速记：L1~1 ns、内存~100 ns、SSD 随机读~100 μs、磁盘寻道~10 ms。

2. 缓存行是缓存搬运的单位，64 字节。顺序访问数组时，连续内存能整批命中缓存行，CPU 检测到顺序访问还会预取后续行；链表是随机指针跳转，次次 miss，预取帮不上忙。所以同为 O(n) 遍历，数组远快于链表——这也是 ArrayList 胜 LinkedList 绝大多数场景的根源。

3. 伪共享是两个线程频繁写同一缓存行的不同变量，缓存一致性协议（MESI）不断使对方缓存失效，互相拖慢。Java 里的解法：用 @Contended 填充把变量隔到不同缓存行（独占一行），或把计数器拆分（LongAdder 分段），从根上减少同一行的写冲突。

4. 流水线把取指/译码/执行/访存/写回并行重叠，分支预测猜错要冲刷整条流水线——丢弃已取指译码的指令、重新取指，浪费的周期就是代价。所以可预测的分支（已排序数据、稳定条件）明显更快，随机分支则反复冲刷流水线。

5. 浮点按 IEEE 754 表示：符号+阶码+尾数，二进制无法精确表示 0.1 这类十进制小数，0.1+0.2≠0.3，舍入误差还会累积。金额要求精确十进制，不能容忍这种误差，所以用 BigDecimal 本质是避开二进制浮点。

6. volatile 写要插入内存屏障指令，逼缓存行刷到对其他核可见。开销不在指令本身，而在破坏流水线与缓存状态：屏障阻止重排优化、使其他核的缓存行失效。所以高频写路径上要谨慎，能用 LongAdder 分段就别用单个 volatile 计数。
