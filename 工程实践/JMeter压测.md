# JMeter 压测

## 1. 核心概念

压测回答三个问题：系统能扛多少并发、瓶颈先出在哪、退化拐点在哪。JMeter 是客户端施压工具：模拟并发用户按脚本发请求，统计响应时间、吞吐与错误率。它测的是「被压系统的表现」，不是「JMeter 能发多快」——施压机自己先成为瓶颈是最常见的乌龙。

四种测试别混：

| 类型 | 做法 | 回答的问题 |
|---|---|---|
| 基准测试 | 单用户/低并发跑通脚本 | 脚本对不对、单请求基线耗时 |
| 负载测试 | 目标并发持续一段时间 | 目标量级下延迟与错误率是否达标 |
| 压力测试 | 并发阶梯上升直到拐点/崩溃 | 容量上限与退化形态 |
| 稳定性测试 | 目标负载长跑（数小时级） | 内存泄漏、连接泄漏、长尾恶化 |

## 2. 基础知识

### 脚本骨架

```text
测试计划
└─ 线程组（并发数、Ramp-Up、持续时间）
   ├─ HTTP 请求默认值（域名、端口、协议统一配置）
   ├─ CSV 数据文件设置（参数化数据）
   ├─ HTTP 请求（各接口采样器）
   │   ├─ 响应断言（状态码/关键字段）
   │   └─ 提取器（JSON 提取器取 token/业务 id 给后续请求）
   ├─ 聚合报告 / 查看结果树（调试期）/ 汇总报告
   └─ 察看结果树只在调试脚本时开，正式跑要关掉：它逐条存响应，最吃内存
```

线程组三参数：

- **线程数**：并发用户数，不是 QPS；QPS 由响应时间反推（并发 ≈ QPS × 平均响应时间）。
- **Ramp-Up**：线程在多少秒内全部起来。瞬间全起会制造不真实的冲击且容易把系统打进假死；按业务到达形态给平滑爬升。
- **循环/持续时间**：正式负载用持续时间控制（如稳压 15 分钟），别用固定循环次数——快慢接口的循环节奏完全不同，不可比。

### 参数化与关联

- **参数化**：登录账号、查询条件等从 CSV 读取，每线程取不同行，避免所有线程打同一条数据（同一行记录的行锁、同一缓存键，会测出假瓶颈或假流畅）。
- **关联（提取器）**：登录返回的 token、上一步创建的业务 id 必须用 JSON 提取器/正则提取器取出传给后续请求；写死 token 测的是鉴权失效路径，不是业务链路。
- **思考时间**：真实用户操作有间隔，用定时器模拟；审批类系统按真实操作节奏加，别用零思考时间的极限狂打冒充业务模型。

## 3. 进阶知识

### 结果判读

| 指标 | 看法 |
|---|---|
| 平均响应时间 | 只能看趋势，判断达标用分位数 |
| P90/P95/P99 | 核心判读：P99 恶化而平均平稳 = 长尾问题（GC 停顿、慢 SQL、锁等待） |
| 吞吐量（TPS/QPS） | 随并发上升的曲线形状最重要：线性上升→进入平台→下降，平台起点附近就是容量 |
| 错误率 | 区分 5xx、超时、断言失败（业务码错误）；错误率陡升点往往早于吞吐拐点 |
| 施压机自身 CPU/网络 | 必须同步监控，施压机 CPU 打满时所有数据作废 |

判读顺序：先看错误率是否在目标内 → 再看 P95/P99 是否达标 → 最后看吞吐量是否到目标。吞吐很高但错误率 30% 是系统在快速失败，不叫性能好。

### 瓶颈定位方法

响应时间随并发涨而吞吐不再涨时，瓶颈在服务端某个串行点：同步去被压机看四件事——应用 CPU（满了查热点方法，走 [JVM 故障排查](开发语言/Java/JVM/JVM-故障排查.md) 的 CPU 流程）、GC（停顿与 P99 毛刺对齐，看 GC 日志）、数据库（慢 SQL、连接池等待、OceanBase 侧会话与活跃 SQL）、下游接口（耗时占比看链路/日志）。配合 [监控告警](工程实践/运维/监控告警.md) 的黄金信号大盘同步看，单看 JMeter 报告定位不到层。

连接池是审批系统最常见的隐藏上限：Tomcat 线程、Druid `max-active`、数据库最大连接三者要成套核算，任一处小了，压测曲线就会在该点提前进入平台且应用 CPU 还很闲。

## 4. 实战应用

### 场景设计（以审批类系统为例，只在测试环境执行）

1. **脚本先行**：单线程跑通全链路（登录 → 列表 → 提交 → 审批），断言与提取器齐全后才谈并发。
2. **阶梯加压**：并发按 10 → 30 → 50 → 100 分段，每段稳压 10–15 分钟，记录每段的 P95/错误率/应用与 DB 指标。
3. **配比按业务**：读接口与写接口按真实流量比混合（列表查询多、提交审批少），纯写压测会高估锁竞争，纯读会漏掉事务与流程引擎的开销（如 Flowable 每次命令的表写入）。
4. **数据准备**：压测专用客户/账号数据成批预置，量级接近生产分布；测完按标记清理，不与功能测试数据混用。

### 压测纪律（红线）

- **不在生产乱压**：生产压测必须有正式审批、明确窗口（业务低谷）、限流与熔断预案、随时可停的开关，并提前通知相关方；没有这些条件一律只在测试/预发环境做。
- 测试环境结论要标注与生产的差异（机器规格、数据量、网络），别把测试环境的 TPS 直接当生产容量承诺；数量级参考可以，精确外推不行。
- 压测造的数据（申请单、流程实例）按批次标记，测后清理或整库重置，避免污染后续功能测试与统计报表。
- 压测期间不做无关变更（不发版、不改配置），一次只动一个变量，否则拐点归因说不清。

## 5. 疑难杂症

- **压不出量、应用还很闲**：按顺序查——施压机瓶颈（CPU/带宽/单机端口耗尽）、连接池与 Tomcat 线程上限、被测接口里有串行锁或单线程组件、参数化没做对（所有线程等同一行数据的行锁）。
- **响应时间锯齿状周期性飙高**：先对时间点——与 Full GC 停顿、定时任务（如 Quartz 批量作业）、日志切割周期对齐排查。
- **错误全是连接重置/超时但服务端日志干净**：多半是施压端或中间网络（负载均衡连接数、防火墙会话表）先到上限，换分布式施压并查中间设备计数。
- **每次压测结果差很多**：数据状态不一致（上次残留数据未清）、缓存冷热不同、脚本思考时间被改；固定数据基线与预热流程（先低并发预热 3–5 分钟再计正式数据）。

## 6. 常见误区

- 用 GUI 模式跑正式压测：GUI 本身吃资源且官方明确只用于调试，正式跑一律命令行 `jmeter -n -t plan.jmx -l result.jtl -e -o report/` 出 HTML 报告。
- 只看平均值与最大 TPS 宣布达标：达标线永远是「目标并发下 P99 与错误率同时达标」。
- 一次压测同时改代码、调参数、扩连接池：结果变好也不知道是谁的功劳，回归时参数被改回问题立刻复现。

## 小技巧与冷知识

【小技巧】分布式压测时，CSV 数据文件要每台 slave 各放一份（或放在所有 slave 都能访问的共享路径），JMeter 不会自动分发数据文件。只在 master 上放 CSV，slave 读不到文件会直接报错或跑空；分发脚本前先核对每台 slave 的文件路径与内容一致，别等跑起来才发现有一台在用旧数据。

【小技巧】施压机自己的堆内存默认只有 1GB（启动脚本里 `HEAP=-Xms1g -Xmx1g`），大并发压测前先改大：编辑 `jmeter.bat`（Windows）或 `jmeter` 启动脚本里的 HEAP 一行，按施压机内存调到够用的值。堆不够时 JMeter 会在中途报 OutOfMemoryError 崩掉，跑了半场的 JTL 作废，比提前调大要贵得多。

【小技巧】想把 QPS 钉在目标值，别只靠调线程数硬凑，用 Constant Throughput Timer：目标值按“每分钟”填，也就是目标 QPS 乘以 60，再配够线程数兜底。注意单位是每分钟不是每秒——想要 10 QPS 得填 600，填成 10 实际只有约 0.17 QPS，差了 60 倍，这是最常见的填错。

【小技巧】HTTP 请求勾上 Use KeepAlive 复用连接：不勾时每个请求都要新建一条 TCP 连接，施压机端口很快被 TIME_WAIT 占满，原文第 5 节说的“单机端口耗尽”多半就是这么来的。KeepAlive 让同一线程的请求复用连接，端口消耗立刻降下来；压测前先确认这项是勾上的，而不是等端口耗尽再去调系统参数。

【小技巧】用 `-J` 传参让同一份 jmx 跑不同并发，不用为每档并发另存一份脚本：脚本里线程数写成 `${__P(threads,10)}`，命令行用 `-Jthreads=100 -Jrampup=60` 覆盖。阶梯加压的 10、30、50、100 四档全用同一份脚本跑，改并发不改脚本，回归时也不会拿错版本。

【小技巧】CSV 数据文件设置的 Sharing Mode 别一直用默认：默认 All threads 是所有线程按顺序共享取行，多线程可能抢到同一行数据；改成 Current thread 后每个线程各取各的行，互不干扰。原文第 2 节要求“每线程取不同行”，这个开关就是落地的具体做法，压测前先确认它配的是哪一档。

【冷知识】JMeter 最初不是为测 Web 应用写的，而是为测 Apache JServ：Stefano Mazzocchi 在 1998 年写它是为了给 Apache JServ 做性能测试，JServ 后来被 Tomcat 取代，JMeter 1.0 也在 1998 年 12 月发布；它 2011 年 11 月才成为 Apache 顶级项目。知道这段历史就明白，它骨子里是个通用施压框架，HTTP 只是最常用的采样器，不是全部。

【冷知识】命令行生成的 HTML 报告（`-e -o`）是 JMeter 3.0 才加入的功能，在此之前只能靠监听器或自己解析 JTL。报告里的 Apdex、响应时间随时间变化图、错误 Top 5 都是现成的，跑完直接打开看，比在聚合报告里一行行翻分位数快得多；正式压测的习惯动作应该是“跑完先看 HTML 报告，再决定要不要下钻 JTL”。

## 7. 面试与自测

1. 并发数与 QPS 是什么关系？为什么不能直接把线程数设成目标 QPS？
2. P99 已恶化但平均响应时间平稳，说明什么？先查什么？
3. Ramp-Up 设为 0 会测出什么假象？
4. 吞吐进入平台、应用 CPU 不满、错误率上升，你的排查顺序是什么？
5. 为什么生产压测要单独审批？测试环境数据外推到生产要注意什么？

### 参考答案

1. 线程数是并发用户数，不是 QPS；QPS 由响应时间反推，并发约等于 QPS 乘以平均响应时间。直接把线程数设成目标 QPS 是错的：响应时间一变，实际 QPS 就跟着变，还忽略了思考时间和参数化，测出来的量级与业务模型对不上。
2. 说明是长尾问题：平均值被大多数正常请求拉平，掩盖了少数慢请求，常见根源是 GC 停顿、慢 SQL、锁等待。先对时间点：把 P99 毛刺与 Full GC 停顿、定时任务、日志切割周期对齐，再查慢 SQL 与锁等待；判读顺序是先看错误率是否在目标内，再看 P95/P99 是否达标，最后看吞吐。
3. Ramp-Up 为 0 意味着所有线程瞬间全起，会制造不真实的冲击，容易把系统打进假死，测出的数据既不是容量也不是业务形态。Ramp-Up 应按业务到达形态给平滑爬升，正式负载用持续时间（如稳压 15 分钟）而不用固定循环次数。
4. 排查顺序：先区分错误类型（5xx、超时、断言失败），错误率陡升点往往早于吞吐拐点；再查施压机自身是否先到瓶颈（CPU、带宽、单机端口耗尽，施压机打满时数据全部作废）；再查连接池与 Tomcat 线程上限三者是否成套（Tomcat 线程、Druid max-active、数据库最大连接，任一处小了都会提前进入平台）；最后查串行锁、单线程组件和参数化问题（所有线程等同一行数据的行锁）。
5. 生产压测是红线操作：必须有正式审批、明确窗口（业务低谷）、限流与熔断预案、随时可停的开关，并提前通知相关方，缺一不可，否则只在测试/预发环境做。测试环境结论外推到生产时要标注差异（机器规格、数据量、网络），数量级可以参考，精确外推不行，不能把测试环境的 TPS 直接当生产容量承诺。
