# 安全架构

安全架构不是堆安全工具，而是回答三个问题：攻击者从哪进（威胁建模）、已知的坑怎么防（OWASP 清单）、身份怎么验（OIDC）。最后用一张纵深防御清单收口，缺哪层补哪层。

## 1. OWASP Top 10（2021 版）：Java 后端视角

OWASP Top 10 是按真实风险排出来的最常见 Web 安全问题清单，2021 版共 10 项。下面每项给 Java 后端场景和防法，具体实现以所用框架的官方文档为准。

### 01 破坏访问控制（Broken Access Control）

最常见的一类。典型场景：

- 水平越权：用户 A 改 URL 里的 id 就看到了用户 B 的订单。防法：每次访问资源时，服务端按当前登录身份校验资源归属，别信前端传来的 id。
- 垂直越权：普通用户调了管理员接口。防法：接口级权限注解 + 服务端二次校验，别只靠前端菜单隐藏。
- 正确做法是默认拒绝：没明确授权的访问一律拒绝，再按需放开。

### 02 加密失败（Cryptographic Failures）

以前叫敏感数据泄露。典型场景：敏感数据明文存库、明文传输、用了弱加密或自研加密算法。

- 传输：全站 HTTPS，别留 HTTP 口子。
- 存储：密码只存哈希（加盐、慢哈希），卡号、身份证这类敏感字段按需加密，密钥和数据分开存。
- 别自研加密算法：用标准库和业界算法，国密场景见关联篇《国密与加密体系》。

### 03 注入（Injection）

SQL 注入、命令注入、EL 表达式注入都算。防法就一条：不把用户输入拼进解释器。

- SQL：用预编译（PreparedStatement / MyBatis 的 `#{}`），别用字符串拼接，更别用 `${}` 拼用户输入。
- 命令执行：别把用户输入拼进 shell 命令；必须调系统命令的，用参数数组 + 白名单。
- 表达式：别让用户输入进 EL、OGNL、SpEL 这类模板表达式。

### 04 不安全设计（Insecure Design）

不是实现 bug，是设计时就没考虑安全：比如无限次试密码、不限流的短信接口、没有业务风控的转账流程。防法：设计评审时就列威胁（见第 2 节），把限流、风控、审计当成需求写进去，而不是事后打补丁。

### 05 安全配置错误（Security Misconfiguration）

默认密码没改、调试接口留在生产、错误信息把堆栈和 SQL 打给用户、目录遍历能下载配置文件。防法：生产配置清单化（默认账号、调试开关、错误页、目录权限逐项检查），配置变更走评审。

### 06 易受攻击和过时的组件（Vulnerable and Outdated Components）

依赖库有已知漏洞。防法：依赖清单 + 定期漏洞扫描（比如 OWASP Dependency-Check、Maven 插件、CI 里的扫描步骤），高危漏洞定升级时限，别无限期拖着。

### 07 认证失败（Identification and Authentication Failures）

弱密码策略、暴力破解无限制、会话固定、退出后会话仍可用。防法：密码强度策略 + 登录失败限流 + 验证码、会话 ID 登录后重新生成、退出即失效服务端会话。

### 08 软件和数据完整性失败（Software and Data Integrity Failures）

反序列化漏洞、CI 流水线被篡改、用了没校验签名的第三方包。防法：别反序列化不可信数据（Java 原生反序列化尤其危险）、CI 产物签名校验、依赖只从可信源拉。

### 09 安全日志和监控失败（Security Logging and Monitoring Failures）

出了事查不到：登录失败、越权尝试、敏感操作没有审计日志，或者日志记了没人看。防法：关键操作（登录、授权变更、敏感数据访问）记审计日志，日志集中收集，异常行为告警，别只记成功不记失败。

### 10 服务端请求伪造（SSRF）

服务端拿着用户提供的 URL 去请求，结果请求到了内网服务（元数据接口、内网管理后台）。防法：用户提供的 URL 先解析、校验 host 白名单、禁内网地址段（10/8、172.16/12、192.168/16、169.254/169.254），重定向也要跟进校验，别只验第一次。

## 2. 威胁建模：上线前先画出来

威胁建模不是写文档，是在动手前把“攻击者能从哪进”想清楚。轻量流程四步：

### 2.1 画数据流图

画出系统的数据流：外部用户、前端、网关、服务、数据库、第三方接口，标出信任边界（哪些在边界外不可信）。每个跨边界的数据流都是一个潜在攻击面。图不用画得多精美，能标出“数据从哪来、到哪去、经过谁”就行。

### 2.2 按 STRIDE 列威胁

STRIDE 是微软的威胁分类法，每个数据流、每个组件按六类过一遍：

| 类别 | 含义 | 典型问题 |
|---|---|---|
| S 假冒（Spoofing） | 冒充别人身份 | 会话伪造、接口未鉴权 |
| T 篡改（Tampering） | 改数据 | 请求参数被改、传输中被改 |
| R 否认（Repudiation） | 做了不认账 | 关键操作无审计日志 |
| I 信息泄露（Information Disclosure） | 不该看的被看到 | 越权读数据、错误信息泄露 |
| D 拒绝服务（Denial of Service） | 服务被打垮 | 无限流接口、无资源限制 |
| E 权限提升（Elevation of Privilege） | 低权限干高权限的事 | 垂直越权、配置错误提权 |

### 2.3 排优先级

威胁列出来要排序，别平均用力。排序看两点：资产价值（这条链路背后是什么数据、多少钱）和可利用性（攻击者能不能远程利用、要不要登录）。远程可利用 + 高价值资产的先修，需要内网条件 + 低价值资产的往后排。

### 2.4 定措施、复查

每个排上号的威胁写一条应对措施（是防住、缓解、还是接受风险并记录原因），措施落到具体改动（代码、配置、流程），上线前复查一遍有没有漏。威胁建模的产物不是图本身，是这张“威胁-措施”清单。

## 3. OIDC：身份层

### 3.1 OIDC 和 OAuth2 的关系

OAuth2 只解决授权（“我允许这个应用访问我的资源”），不解决认证（“你是谁”）。OIDC（OpenID Connect）就是在 OAuth2 上面加了一层身份：认证完除了发 Access Token，还发一个 ID Token，里面就是用户身份信息。记住这句：OAuth2 是授权协议，OIDC 是身份协议。

### 3.2 授权码流程

最常用的流程，走五步：

1. 用户访问应用，应用把用户重定向到身份提供方（IdP）的授权页。
2. 用户在 IdP 登录并同意授权，IdP 把用户重定向回应用，带上一个授权码（code）。
3. 应用拿授权码去 IdP 的 token 端点换 token（这一步是服务端对服务端，不经过浏览器）。
4. IdP 返回 ID Token 和 Access Token。
5. 应用校验 ID Token 签名和关键字段（签发方、受众、过期时间），确认用户身份，建立自己的会话。

### 3.3 ID Token 和 Access Token 的区别

| | ID Token | Access Token |
|---|---|---|
| 用途 | 证明“你是谁”，给客户端验身份 | 调 API 的凭证，给资源服务器验权限 |
| 格式 | JWT，里面有用户身份字段 | 不一定是 JWT，别假设里面有用户信息 |
| 给谁看 | 客户端（应用） | 资源服务器（API） |
| 常见误用 | 拿 ID Token 当 API 凭证 | 拿 Access Token 当身份证明、解析里面的用户信息做登录判断 |

### 3.4 实践要点

- state 参数：防 CSRF，授权请求带随机 state，回调时比对，不一致拒绝。
- nonce 参数：防重放，ID Token 里带回 nonce，校验一致才认。
- PKCE：移动端和单页应用没有安全的客户端密钥，用 PKCE（code_verifier / code_challenge）代替密钥换 token。
- Token 存储：别把 token 放 localStorage（XSS 一偷一个准），优先 httpOnly Cookie 或安全的服务端会话，具体按应用形态定。
- 签名与密钥比较：别用 `==` 比 token 或签名，时序差异会泄露信息。用恒定时间比较：

```python
import hmac
# 恒定时间比较：不管第几位不同，耗时都一样，防时序攻击
print(hmac.compare_digest("s3cret-token", "s3cret-token"))  # True
print(hmac.compare_digest("s3cret-token", "s3cret-tokem"))  # False
```
- 退出：应用退出时除了清自己的会话，能调 IdP 的登出端点就调上，别只清本地。

## 4. 纵深防御清单

单点防不住，层层设防。按这张清单自查，缺哪层补哪层：

- 身份认证：强密码策略、登录限流、MFA（管理员和高敏感操作必开）、会话管理（登录后换会话 ID、退出即失效）。
- 授权：最小权限、接口级权限校验、服务端二次校验资源归属（防 01）。
- 输入与输出：所有外部输入白名单校验、SQL 预编译、输出编码防 XSS、文件上传类型与大小限制。
- 传输与存储：全站 HTTPS、敏感字段加密、密钥与数据分离存储、密码慢哈希加盐。
- 依赖与配置：依赖漏洞定期扫描、生产配置清单化、默认账号清理、错误信息不泄露堆栈。
- 日志与监控：关键操作审计日志、日志集中收集、异常行为（暴力破解、越权尝试）告警。
- 应急：密钥泄露轮换流程、漏洞响应时限、安全事件复盘机制。

没有哪一层是银弹：认证再强也防不住 SQL 注入，加密再好也防不住越权。清单的意义就是防止只补一层、其他层全空。

## 面试与自测

1. OAuth2 和 OIDC 是什么关系？为什么说“拿 Access Token 当身份证明”是误用？
2. 水平越权和垂直越权各举一个场景，服务端应该怎么防？
3. 威胁建模里 STRIDE 的 R（否认）对应什么问题？怎么防？

### 参考答案

1. OAuth2 只解决授权（允许应用访问资源），不解决认证（确认用户是谁）；OIDC 是在 OAuth2 上加的身份层，认证完额外发 ID Token 证明身份。Access Token 是调 API 的凭证，不一定是 JWT、里面不一定有可靠的用户信息，拿它解析用户信息做登录判断等于把授权凭证当身份证明用，格式和语义都不保证。
2. 水平越权：用户 A 改 URL 里的订单 id 看到了用户 B 的订单；垂直越权：普通用户直接调管理员接口。防法都是服务端校验：每次访问资源时按当前登录身份校验资源归属，接口级权限注解 + 服务端二次校验，不依赖前端隐藏。
3. R 是否认：做了关键操作却不认账、事后无法追溯。防法是记审计日志：登录、授权变更、敏感数据访问、资金操作都要记“谁、什么时候、做了什么”，日志集中存储、防篡改，出事时能还原。
