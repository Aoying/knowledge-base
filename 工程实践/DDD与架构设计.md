# DDD 与架构设计

## 1. 核心概念

DDD（领域驱动设计）解决「复杂业务怎么切、规则放哪」：把业务概念直接变成代码结构，不让规则散在 Controller、SQL 和流程图里。

两层：**战略设计**划边界（统一语言、限界上下文、上下文映射、子域分类）；**战术设计**落代码（实体、值对象、聚合根、领域服务、仓储、工厂、领域事件）。

架构是另一维：DDD 管建模，分层/整洁/六边形管依赖方向。要不要上看一条：**改一个规则是否要翻五个文件**，是才值得。

## 2. 基础知识

### 战略设计

子域分类决定投入：核心域（竞争优势，如授信、额度模型）自研、全套 DDD；支撑域（必需不独特，如进件材料）简化版；通用域（短信、文件）直接用中间件。

**统一语言**：业务、产品、开发用同一套词进类名/方法名，如「进件、授信、用信」，别另造译法混用。

**限界上下文**：一个模型只在一个边界内成立。「客户」在授信上下文是「有额度、有评级的借款人」，在贷后是「有还款计划的还款人」，是两个模型，不要合成一个大 `Customer`。上下文对应可独立演进的模块，也是拆微服务的边界。

**上下文映射**：合作伙伴（同进退）、客户-供应商（上游优先满足下游，如风控供评级）、**防腐层 ACL**（边界加翻译层把外部模型转成本域语言，接征信、核心系统必用）、开放主机服务（标准接口，如支付网关）。

### 战术设计速览

| 构件 | 要点 |
|---|---|
| 实体 / 值对象 | 实体有标识、按 ID 判等（贷款申请）；值对象无标识、不可变、按值判等（金额=数额+币种） |
| 聚合根 | 一组实体的入口与一致性边界，外部只能经它改内部 |
| 领域服务 | 不属于单个实体的规则，如额度试算同看评级与在贷余额 |
| 仓储 / 工厂 | 仓储按聚合根存取（一聚合一个，不是一表一个）；工厂封装复杂创建校验 |
| 领域事件 | 已发生的事实：「审批通过」「放款成功」 |

### 架构形态

- **经典分层**：接口 → 应用 → 领域 → 基础设施，简单够用；风险是领域层被 MyBatis 实体带跑成贫血模型。
- **整洁/六边形**：领域在中心，DB、MQ、第三方经端口（接口）接入，领域层不 import MyBatis、Flowable、Redis，换引擎不动规则；代价是转换代码多，只在核心域用。

## 3. 进阶知识

### 聚合三原则

1. **聚合是事务与一致性边界**：一个事务只改一个聚合；内强一致，聚合间用领域事件最终一致（见 [分布式事务](数据库/分布式事务.md)）。
2. **聚合要小**：只放必须一起校验的对象。客户连同全部历史贷款塞进一个聚合，改一行锁全量，必爆。
3. **聚合间只用 ID 引用**：`LoanApplication.customerId`，不挂另一个聚合的对象图。

### 充血模型

规则写进聚合本身，不在 Service 里操作裸字段：

```java
public class LoanApplication {   // 聚合根；amount 是值对象
    public void submit() {       // 状态迁移规则收在聚合内
        if (status != ApplyStatus.DRAFT)
            throw new BizException("LOAN_1001", "只有草稿状态可提交");
        if (amount.isGreaterThan(Money.yuan(5_000_000)))
            throw new BizException("LOAN_1002", "法人版单笔上限 500 万");
        this.status = ApplyStatus.SUBMITTED;
    }
}
```

值对象在 Java 8 下用 `final` 字段 + 无 setter + 按值重写 `equals/hashCode` 做不可变。

### 领域事件

聚合内攒事件，事务提交后才发布。事件是「事实通知」不是命令：消费方失败不回滚发布方，靠消息可靠性兜底（见 [消息可靠性](消息队列/消息可靠性.md)）。

### 架构演进

单体（包按业务分）→ 模块化单体（上下文=模块，只走接口/事件）→ 微服务（只拆独立扩缩的上下文）。拆分边界复用限界上下文，这也是 [Spring-Cloud概览](开发语言/Java/Spring/Spring-Cloud概览.md)「先算拆分的账」的前提：边界没划清就拆，得到分布式单体。

## 4. 原理剖析

**聚合根为什么能守规则**：变更必经聚合根方法，不变量集中校验；字段全开 setter，规则必然散落各调用方。

**ACL 为什么能防污染**：外部模型语义不稳，ACL 做一次翻译（码值 → 本域枚举、DTO → 本域值对象），外部升级只改 ACL；没有 ACL，外部字段会渗进实体与表结构，换供应商等于重构。

**流程引擎为什么不等于领域层**：流程图是编排，天然易变；领域规则相对稳定。规则写进 BPMN，等于把最稳定的东西绑在最易变、且没法单测的载体上。

## 5. 实战应用

### 神农 e 贷法人版上下文划分（示例）

| 上下文 | 类型 | 核心概念 |
|---|---|---|
| 客户准入 | 支撑 | 法人客户、股东、实控人（工商/征信走 ACL） |
| 授信 | **核心** | 额度、评级、额度占用/释放（全套 DDD） |
| 贷款申请 | **核心** | 进件、申请、担保 |
| 审批 | 支撑 | 审批任务、审批意见（Flowable 驱动） |
| 合同与放款 | 支撑 | 合同、借据、放款指令（核心系统 ACL + 幂等） |
| 贷后 | 支撑 | 还款计划、逾期、催收（只引借据 ID） |
| 消息通知 | 通用 | 短信、站内信（消费事件） |

跨上下文只走接口或事件，不许直连对方的表，模块化单体用 ArchUnit 卡依赖。

### Flowable 与领域层的边界

[Flowable](工程实践/Flowable.md) 是**应用层编排工具**：

- **流程图放**：节点顺序、审批人/角色、会签与网关路由、超时、驳回路径。
- **领域层放**：额度够不够、状态迁移是否合法、担保是否足值——能算出对错的规则做成领域服务/聚合方法，可单测。
- **监听器只转发**：只调应用服务一个方法，不写判断、不拼 SQL；流程变量只存 `applicationId` 这类 ID。「金额 > 100 万走总行审批」这类路由条件放网关表达式可以，但「是否超可用额度」必须回领域层，不许在流程图复制一份。

监听器就一行转发：`approvalAppService.onApproved((Long) e.getVariable("applicationId"))`，内部再调领域服务校验。

### 系统设计自查清单

- **容量与分表**：日单量、峰值 QPS、单表年增量与分表线（[分库分表](数据库/分库分表.md)）。
- **缓存/MQ/限流落点**：读多写少才上缓存（[Redis-缓存问题与分布式锁](数据库/Redis/Redis-缓存问题与分布式锁.md)）；能异步才进 MQ，想清不丢不重与幂等；入口与外部出口都有限流闸（[限流熔断与降级](开发语言/Java/限流熔断与降级.md)）。
- **事务与可测**：本地事务只含一个聚合，跨上下文用事件最终一致；规则要能不启 Spring 单测（[单元测试与Mock](工程实践/单元测试与Mock.md)）。

## 6. 疑难杂症

- **贫血模型**：实体只剩 getter/setter，同一校验在三个 Service 各写一份。把校验与状态迁移搬回聚合，Service 只编排。
- **仓储泛滥**：每表一个 Repository 等于给 Mapper 改名，仓储只按聚合根建。
- **改规则要发新流程版本**：规则写进了 BPMN 表达式，抽回领域服务，流程按服务结果路由。

## 7. 常见误区

- **CRUD 硬套 DDD**：后台管理就是增删改查，硬套只得到三倍代码量。事务脚本（Service 直调 Mapper）就是正确解法，DDD 只投核心域。
- **战术先行**：没做战略划分就建实体、值对象，边界就是包边界。顺序永远是子域分类 → 划上下文 → 谈聚合。
- **DDD = 四层包结构**：包建了、里面仍是贫血实体加过程式 Service，是换皮。看两条：规则在不在模型里、依赖有没有隔离。
- **领域事件当同步调用**：发事件还等消费结果决定主流程成败，是把强一致伪装成异步。事件只做事后解耦。

## 8. 性能优化

- **聚合粒度即锁粒度**：聚合越小冲突面越小；额度余额等高冲突字段单独成聚合或用乐观锁版本号。
- **避免 N+1 与读模型**：集合别用 MyBatis 嵌套查询逐条拼装（批量一次查询 + 内存组装）；列表、统计直接查宽表出 DTO（轻量 CQRS）。通知、建贷后计划放事件消费端异步化。

## 9. 版本差异

- Boot 2.7 / Java 8 下值对象不能用 record（Java 16+），用不可变类手写；模块约束不能用 Spring Modulith（需 Boot 3），替代包约定 + ArchUnit。升 Boot 3 时领域层基本不动，只改基础设施适配层。
- Flowable 6.7.2 监听器接口在 `org.flowable.engine.delegate.*`，与 7.x 包路径有别，抄代码先对包名。

## 小技巧与冷知识

【小技巧】聚合根划不准时，问一句“删掉它，剩下的对象还有没有独立意义”：如果剩下的对象离开聚合根就没法单独存在、没人会单独查它改它，它们就是同一聚合；反过来，删掉它之后剩下的对象照样有独立生命周期，就该拆成两个聚合。这个判断比“它们经常一起出现”更准，经常一起出现不等于必须一起改。

【小技巧】统一语言先落地成一张术语表再进代码：每个业务词写一行——词、含义、对应的类名或枚举名，放在仓库里随代码一起评审。新词进代码前先查表，没有就先补表再写类；同词异义（比如“客户”在授信和贷后是两个意思）直接在表里分开写两行，比事后在代码里靠包名区分要可靠得多。

【小技巧】防腐层（ACL）先写翻译测试再写翻译代码：外部 DTO 进来、转成本域值对象或枚举的每一条映射，先写成一张测试用例表，外部系统升级、码值变了，先跑这张表——哪条映射断了立刻知道。没有翻译测试的 ACL，外部字段改个名字就会悄悄渗进实体，防腐层等于没建。

【小技巧】领域事件的名字用过去时写业务事实，命令式命名是误用信号：“审批通过”“放款成功”是对的，“请审批”“去放款”是命令。事件名一写成命令，就说明有人在拿事件当同步调用使唤，消费方会被迫等结果，主流程的成败又被异步链路绑住了；命名一改，误用在评审时就藏不住。

【小技巧】依赖方向别靠约定，靠构建时测试卡住：ArchUnit 一类工具可以在测试里写一条规则——领域层不许 import 基础设施包（如 MyBatis、Flowable、Redis 的包）。规则一违例构建就失败，比“大家注意别在领域层引 Mapper”的口头约定管用；原文说的“用 ArchUnit 卡依赖”，落到代码里就是这一条测试，写进持续集成。

【冷知识】DDD 这个词有明确出处：Eric Evans 在 2003 年出版的《Domain-Driven Design: Tackling Complexity in the Heart of Software》里系统提出，统一语言、限界上下文、聚合、仓储这些概念都出自这本书。它不是某个框架的配套方法论，而是一套建模思想——所以“上了 Spring Boot 就是 DDD”这种说法，从一开始就搞错了层次。

【冷知识】六边形架构（端口与适配器）比 DDD 的书晚两年：Alistair Cockburn 在 2005 年提出，核心是把业务逻辑放在中心、外部系统经端口接入。DDD 管“模型怎么切”，六边形管“依赖往哪指”，两者解决的是不同维度的问题；原文把它们并列讲，正是因为一个项目里往往两个都要用，而不是二选一。

【冷知识】“贫血模型”这个词是 Martin Fowler 在 2003 年的文章《AnemicDomainModel》里定名的，他批评的正是“实体只剩 getter/setter、规则全在 Service 里”的写法。Fowler 当时就指出，这种模型的问题不是代码量，而是规则散落在各处、改一处要翻多处——和原文判断“改一个规则是否要翻五个文件”说的是同一件事。

## 10. 面试与自测

- 限界上下文和微服务什么关系？没有微服务能不能用 DDD？
- 聚合根怎么划？为什么说聚合是事务边界？
- 实体与值对象判等规则有何不同？金额为什么必须是值对象？
- 防腐层用在什么场景？审批规则放流程图还是领域层？
- 什么系统不该用 DDD？代价是什么？

### 参考答案

1. 限界上下文是一个模型成立的边界，也是可独立演进的模块，拆微服务时直接复用它当边界。没有微服务也能用 DDD：先走模块化单体，上下文等于模块、只走接口或事件，边界没划清就拆只会得到分布式单体。
2. 聚合只放必须一起校验的对象，聚合要小；聚合是事务与一致性边界，一个事务只改一个聚合，聚合内强一致、聚合间用领域事件最终一致。聚合间只用 ID 引用（如 LoanApplication.customerId），不挂另一个聚合的对象图，否则改一行锁全量。
3. 实体有标识、按 ID 判等（如贷款申请）；值对象无标识、不可变、按值判等。金额必须是值对象：它由数额加币种共同决定相等，没有独立身份，不可变才能防止中途被改，Java 8 下用 final 字段加无 setter、按值重写 equals/hashCode 实现。
4. 防腐层（ACL）用在接外部系统时，如征信、核心系统：边界加一层翻译，把外部模型转成本域语言，外部升级只改 ACL，否则外部字段会渗进实体与表结构。审批规则分两边：流程图放节点顺序、审批人、会签与网关路由、超时与驳回路径；领域层放能算出对错的规则，如额度够不够、状态迁移是否合法、担保是否足值。
5. 增删改查为主的后台管理系统不该用 DDD，事务脚本（Service 直调 Mapper）就是正确解法。硬套的代价是三倍代码量却没带来规则收敛；判断标准是：改一个规则是否要翻五个文件，是才值得上 DDD，且只投核心域。
