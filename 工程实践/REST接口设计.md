# REST 接口设计

## 1. 核心概念

REST 不是协议，而是一套以**资源**为中心的接口组织风格：URL 定位资源，HTTP 方法表达动作，状态码表达结果。本篇管**设计侧**——接口长什么样、语义怎么定；文档怎么自动生成、怎么维护见 [OpenAPI 接口文档](工程实践/OpenAPI接口文档.md)，两篇分工不要混。

设计的目标是可预期：调用方不用逐个接口读文档猜行为——增删改查都长一个样，错误都一个格式，分页都一种翻法。一致性比「某个接口设计得多精巧」更重要。

## 2. 资源命名

- URL 用**名词、复数**：`/customers`、`/customers/{id}`、`/loans/{id}/approvals`。层级表达从属关系，但别超过 2–3 层，更深的关系拆成独立资源加查询参数。
- 动词是反模式：`/createCustomer`、`/getLoanList`、`/approveLoan` 都不对，动作交给 HTTP 方法。实在是动作而非资源的操作（如审批通过、发起重算），两种务实处理：子资源化（`POST /loans/{id}/approvals` 表示「新增一条审批」），或在资源下挂明确动作端点（`POST /loans/{id}:approve` 风格）并写进团队约定，全库统一，不要每个接口自创。
- 路径用 kebab-case（`/loan-applications`），字段名风格（camelCase）与团队 JSON 约定保持一致，全局只选一种。
- 过滤、排序、分页一律走查询参数：`GET /loans?status=PENDING&sort=createdAt,desc&page=0&size=20`，不要为筛选条件发明新路径。

## 3. 方法与状态码

| 方法 | 语义 | 幂等 | 典型状态码 |
|---|---|---|---|
| GET | 查 | 是 | 200；查不到 404 |
| POST | 新建/触发 | 否（要业务补幂等） | 201 Created（带 Location 头指新资源） |
| PUT | 整体替换 | 是 | 200 |
| PATCH | 局部更新 | 约定上按幂等设计 | 200 |
| DELETE | 删除 | 是 | 204 No Content |

状态码使用纪律：

- **不要全用 200 再在 body 里包错误**。协议层失败就给协议层状态码，监控、网关、前端拦截器都靠它工作：参数校验不过 400、未登录 401、无权限 403、资源不存在 404、状态冲突（如重复审批、版本冲突）409、参数格式对但业务规则不通过 422、服务端异常 500。
- 401 与 403 别混：前者是「没证明你是谁」，后者是「知道你是谁但不许」，与安全框架的划分一致，见 [Spring Security](开发语言/Java/Spring-Security.md)。
- 500 只给未预期异常；业务可预期的失败都要有明确状态码 + 业务码，不要拿异常栈当错误信息返回。

## 4. 版本管理

| 方式 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| URL 路径 | `/api/v1/loans` | 直观、调试和网关路由最省事 | URL 不「纯」，但工程上代价最小 |
| 请求头 | `Accept: application/vnd.app.v1+json` | URL 干净 | 不可见、联调和排障成本高 |

企业项目实务直接选 URL 版本，且只保留「大版本」粒度：兼容性变更（加字段、加可选参数）不升版，直接上线；破坏性变更（删字段、改语义）才开新大版本并双版本并行一段迁移期。不要出现 `/v1.1`、`/v2beta` 这种把版本号当发布号用的做法。

## 5. 幂等设计

重复提交在业务系统里是常态：前端连点、网关重试、消息重投。幂等要靠设计，不能靠用户手速。

- 天然幂等的 GET/PUT/DELETE 直接用好；POST 是要重点补的：创建类接口用**幂等键**——调用方带 `Idempotency-Key`（或直接用业务单号）+ 服务端唯一索引兜底，重复请求命中已有记录直接返回首次结果，而不是再建一条。
- 状态流转类接口（审批、确认、发货）用**状态机前置校验**：`WHERE status = 'PENDING'` 带条件更新，影响行数为 0 说明已被处理过，返回 409 或当前状态。ao 的审批流场景里，同一个待办被两人同时点、或一人连点，靠的就是这条而不是前端按钮置灰。
- 幂等实现放在服务端，前端防重复点击只是体验优化，一个都不能少、但不能互相替代。

## 6. 统一响应与错误码

统一信封结构，全库一套：

```json
{
  "code": "0",
  "msg": "success",
  "data": { },
  "traceId": "a1b2c3"
}
```

- 分工定死：**HTTP 状态码管协议层结果，业务 code 管业务层结果**。业务失败（如额度不足）用 200 + 业务码，还是直接 4xx？两种流派都成立，但必须全库统一并写进约定；混合着来是联调事故的最大来源。
- 业务错误码分段管理（如 1xxxx 参数类、2xxxx 业务类、3xxxx 外部系统类），码表集中一处维护，错误消息给人看、错误码给程序分支，两者都要有。
- `traceId` 必带：与日志 MDC 里的链路 ID 同源，客诉和排障时靠它把一次请求的前后端日志串起来。信封里不放异常栈、不放内部类名和 SQL。

## 7. 分页约定

| 方式 | 适用 | 注意 |
|---|---|---|
| 页码分页 `page/size` + total | 后台管理、要跳页要总数 | 深翻页性能差；查 total 有额外成本，大表慎用每页都查 |
| 游标分页 `cursor/limit` | 信息流、导出、对接拉取 | 不支持跳页；游标字段必须稳定唯一 |

两条铁律：**分页必须带排序，且排序键要以唯一字段收尾**（如 `createdAt desc, id desc`），否则同一行在两次翻页间会重复或丢失；`size` 必须设上限，防止一次拉全表把接口打成导出工具还不走导出通道。

## 8. 常见误区

- GET 请求带 body 传参：网关、缓存、日志系统都可能把 body 丢掉或不识别，查询条件一律走查询参数。
- 一个接口干两件事：「保存并提交」「查询并导出」这类复合动作拆开，失败语义和重试语义完全不同，揉在一起两边都做不好。
- 返回结构随接口心情：有的包信封有的裸返、列表有的给数组有的给对象。统一信封 + 全局异常处理（`@RestControllerAdvice`）收口，新增接口不允许自创格式。
- 错误消息直接透传下游系统原文：外部系统的报错含内部细节且口径不一，对外要映射成自家错误码，下游原文只进日志。

## 9. 面试与自测

- PUT 和 PATCH 的语义差别？POST 为什么需要幂等键？
- 409 和 422 分别用在什么场景？
- URL 版本和请求头版本怎么选？小版本变更要不要升版？
- 分页为什么要求排序键唯一收尾？
- 业务错误到底走状态码还是走业务 code？你的项目里约定是哪种、为什么？

### 参考答案

1. PUT 是整体替换，天然幂等；PATCH 是局部更新，约定上按幂等设计。POST 本身不幂等，所以创建类接口需要幂等键：调用方带 Idempotency-Key（或直接用业务单号），服务端用唯一索引兜底，重复请求命中已有记录直接返回首次结果，而不是再建一条；状态流转类接口则用状态机前置校验（WHERE status='PENDING'，影响行数为 0 说明已被处理过）。
2. 409 用于状态冲突，如重复审批、版本冲突；422 用于参数格式对但业务规则不通过。两者分工是：409 是资源当前状态不允许这个操作，422 是请求本身合法但业务上无法接受。
3. 企业项目实务直接选 URL 版本（如 /api/v1/loans），优点是直观、调试和网关路由最省事；请求头版本 URL 干净，但不可见、联调和排障成本高。只保留大版本粒度：兼容性变更（加字段、加可选参数）不升版直接上线，破坏性变更（删字段、改语义）才开新大版本并双版本并行一段迁移期，不要出现 /v1.1、/v2beta 这种把版本号当发布号的做法。
4. 因为不带唯一收尾的排序是不稳定的：同一行在两次翻页之间可能重复或丢失。铁律是分页必须带排序，且排序键要以唯一字段收尾，如 createdAt desc, id desc；同时 size 必须设上限，防止一次拉全表把接口打成导出工具。
5. 本篇没有定死项目用哪一种，它定死的是分工与统一：HTTP 状态码管协议层结果，业务 code 管业务层结果，两种流派（业务失败走 200 加业务码，或直接走 4xx）都成立，但必须全库统一并写进约定，混合着来是联调事故的最大来源。选型时看调用方与网关是否依赖状态码做拦截与监控，再全库落到一种并在团队约定里写明。
