# Maven 与依赖管理

> Maven 做两件事：**按约定组织构建生命周期**，**按坐标管理依赖图**。翻车大多不在编译，而在依赖图——同一库两个版本共存、传递进来不想要的版本、私服拉不到包。与 [CI/CD](工程实践/运维/CICD.md) 篇的分工：那篇讲流水线整体，本篇讲 `mvn` 这一步内部发生了什么。

## 1. 核心概念

- **坐标（GAV）**：`groupId:artifactId:version` 唯一确定一个构件，仓库里的物理路径就是坐标的展开。
- **仓库分三层**：本地仓库（`~/.m2/repository`，缓存）→ 私服（内网 Nexus/Artifactory 一类，代理中央仓库 + 托管自研包）→ 中央仓库。查找先本地、再私服、最后才出网。
- **pom 是声明式模型**：`dependencies` 只声明「要什么坐标」，实际拿到哪个版本由调解规则决定（第 3 节）——这是「我明明写的是 A 版本，跑起来却是 B」的根源。

## 2. 基础知识：生命周期与常用命令

三套生命周期互相独立：**clean**（清理）、**default**（构建部署，主线）、**site**（站点文档）。default 的阶段按序排列（compile → test → package → verify → install → deploy），执行某个 phase 时它之前的 phase 一起执行；分工上 surefire 在 test 阶段跑单元测试、failsafe 在 verify 阶段跑集成测试，install 把产物装进本地仓库，deploy 才推私服。

```bash
mvn clean install               # 全量构建并装本地仓库（多模块在根目录执行）
mvn clean package -DskipTests   # 打包不跑测试（救急可用，别成习惯）
mvn test -Dtest=FooServiceTest  # 只跑指定测试类（排错常用）
mvn -pl module-a -am package    # 只构建 module-a 及它依赖的上游模块（第 4 节）
mvn -o package                  # 离线模式，验证本地缓存是否完整
```

跳过测试分两档：`-DskipTests`（编译但不执行）与 `-Dmaven.test.skip=true`（连编译都跳）。**Wrapper（mvnw）**把 Maven 版本随项目走，流水线里优先用 `./mvnw` 而非机器自带的 `mvn`，避免版本不一致翻车。

## 3. 进阶知识：依赖范围与传递规则

### scope（依赖范围）

| scope | 生效范围 | 打进产物 | 典型例子 |
|---|---|---|---|
| compile（默认） | 编译/测试/运行 | ✓ | Spring、MyBatis |
| provided | 编译/测试 | ✗ | servlet-api（容器提供） |
| runtime | 测试/运行 | ✓ | 数据库驱动、日志实现 |
| test | 仅测试 | ✗ | JUnit、Mockito |
| system | 指向本地文件路径 | — | **不要用**，见第 6 节 |
| import | 仅 dependencyManagement 导入 BOM | — | 见下文 |

### 传递依赖的三条调解规则

1. **最近定义优先**：离根越近的版本胜出。A→B→C(1.0) 与 A→C(2.0) 冲突时，深度更浅的 2.0 赢（与 Gradle 的「最高版本胜出」不同，跨生态时容易记混）。
2. **先声明优先**：深度相同时，先声明的路径胜出，声明顺序不是随便写的。
3. **可选与排除**：`<optional>true</optional>` 让依赖不向外传递；`<exclusions>` 在引入点剪掉传递路径。两者是防御手段，治本靠版本统一。

### dependencyManagement 与 BOM

`dependencyManagement` 只声明版本、**不实际引入**；各模块在 `dependencies` 里只写坐标不写版本，版本以它为准，父 pom 统一全工程版本靠这一节。**BOM** 是只含 dependencyManagement 的 pom，用 `scope=import` 导入——Spring Boot 的 `spring-boot-dependencies` 即 BOM，导入后它管理的那批库全不用写版本。注意：`dependencies` 里显式写死的版本会盖过 dependencyManagement，「统一不生效」先搜散落的硬编码版本。

## 4. 实战应用：冲突排查与多模块

### 冲突排查流程

症状多在运行时才爆：`NoSuchMethodError`、`ClassNotFoundException`——编译能过、跑起来缺方法，九成是类被加载成了错误版本。

```bash
mvn dependency:tree                       # 全量依赖树，看目标库有几个版本、从哪进来
mvn dependency:tree -Dincludes=组id:构件id  # 只看某个库的路径（排查主力）
mvn dependency:tree -Dverbose              # 连被调解掉的版本也显示（omitted 标注）
```

处理顺序：定位期望版本应走的路径 → 引入点 `exclusions` 剪掉错误路径，或在 dependencyManagement 钉死版本 → 重跑 `dependency:tree` 确认只剩一个版本 → 跑测试验证。团队项目可加 `maven-enforcer-plugin` 的依赖收敛规则，让冲突在构建期报错而非运行时。

### 多模块：聚合与继承是两件事

- **聚合**：父 pom 用 `<modules>` 组织一次构建，反应堆（reactor）按模块间依赖自动排序，解决「构建顺序」。
- **继承**：子 pom 用 `<parent>` 继承 dependencyManagement 与插件配置，解决「配置复用」。
- 两者常同时出现但概念独立。部分构建用 `-pl` 选模块、`-am` 连带上游、`-amd` 连带下游；发布前仍要在根目录全量跑一遍。

## 5. 私服与 settings.xml

- **私服的双重角色**：代理缓存中央仓库（内网出不了外网、直连慢）+ 托管自研公共模块的分发。
- **settings.xml**（`~/.m2/settings.xml`，不进版本库）：配镜像（mirror 把 central 流量导向私服）与凭据（`servers` 节的 id 要与 pom/镜像配置对应）。凭据只放这里或 CI 的 Secrets，**绝不写进 pom**。
- **SNAPSHOT 与 RELEASE**：SNAPSHOT 可变，Maven 默认按更新策略定期检查（`-U` 可强制刷新）；RELEASE 发布后不可覆盖。「同事更新了公共包我却没生效」先确认是不是 SNAPSHOT，再试 `-U`。高频混淆：`install` 只装进**自己**的本地仓库，`deploy` 才推私服——只 install，同事永远拉不到。

## 6. 疑难杂症与常见误区

- **依赖下不下来**：按序查——settings.xml 镜像地址 → 私服上该版本是否真实存在 → 本地仓库是否有下载失败的残留（`*.lastUpdated` 是失败标记，删掉对应目录重试）→ 网络/代理。
- **本地能构建、CI 挂在依赖上**：CI 是干净环境。用 `-Dmaven.repo.local=/tmp/m2test` 换空仓库跑一遍，能复现就是某个包只存在于你的本地（忘了 deploy 或私服上没有）。
- **误区**：用 system scope 或把 jar 拷进项目（绕过依赖图，CI 立刻不一致；闭源 jar 应入私服）；用 LATEST/RELEASE 当版本（构建随时间漂移、不可复现）；在每个子模块重复声明同一版本（升级漏改一处即冲突源）。

## 7. 性能优化与版本差异

- 并行构建 `mvn -T 1C`：模块无依赖时并行，个别老插件线程不安全会翻车，遇问题退回串行定位；缩小范围（`-pl/-am`）通常比提速更有效。
- 3.8.x 起默认屏蔽不安全的 HTTP 仓库（http blocker）：老私服若仍是 http 地址，升级 Maven 后会突然全线下不动包，先查这条。3.9.x 为当前主流稳定线，插件兼容性以各插件官方说明为准。

## 8. 构建规模定量：模块数、依赖树与并行构建算一算

本节只做定量换算，不重复第 7 节的定性建议。以下数字均为估算口径：模块耗时、依赖数量、jar 大小都取项目实测值代入同一算式，生产值以实测为准。

### 8.1 串行总耗时：模块数 × 单模块耗时

多模块全量构建的串行总耗时，先按最简单的乘法估算：

```text
串行总耗时 ≈ 模块数 × 单模块平均耗时
```

单模块平均耗时取 `compile → test → package` 一轮的实测均值，不同模块差别大时按最慢的几个模块单独加权，不要只取平均值。

【算例 1】20 个模块，单模块平均 30 秒，串行总耗时约为 20 × 30 秒 = 600 秒 = 10 分钟。若其中 5 个模块各需 60 秒、其余 15 个各需 20 秒，则总耗时为 5 × 60 秒 + 15 × 20 秒 = 600 秒，结果相同但瓶颈分布完全不同：前者均匀，后者集中在 5 个慢模块上。


### 8.2 并行加速：-T 线程数与 Amdahl 上限

`-T` 只并行构建无依赖关系的模块。官方文档的写法是：`-T 4` 为固定 4 个线程，`-T 1C` 为每核 1 个线程，`-T 1.5C` 为每核 1.5 个线程。8 核机器上 `-T 1C` 即 8 个线程，4 核机器上即 4 个线程，线程数随核数变化。

加速比用 Amdahl 定律估算。设可并行部分占比为 p，线程数为 N，则理论加速比为：

```text
加速比 = 1 / ((1 - p) + p / N)
```

p 不是线程数决定的，而是模块依赖图决定的：能同时开工的模块越多，p 越大；链式依赖越多，p 越小。

【算例 2】取 p = 0.8（80% 的工作可并行），N = 4 时加速比为 1 / (0.2 + 0.8 / 4) = 1 / 0.4 = 2.5 倍；N = 8 时为 1 / (0.2 + 0.8 / 8) = 1 / 0.3 ≈ 3.33 倍；N = 16 时为 1 / (0.2 + 0.8 / 16) = 1 / 0.25 = 4.0 倍。线程数翻倍，加速比只从 2.5 倍涨到 3.33 倍，再翻倍也只到 4.0 倍：串行部分 20% 是天花板，p = 0.8 时加速比永远到不了 5 倍。

把算例 1 的 600 秒代入：N = 4 时并行总耗时约为 600 / 2.5 = 240 秒，省 360 秒；N = 8 时约为 600 / 3.33 ≈ 180 秒，只比 N = 4 再省约 60 秒。线程数继续加，收益递减得很快。

### 8.3 依赖链决定加速上限：关键路径

并行构建还有第二重上限：模块间的最长依赖链（关键路径）。链上的模块必须一个接一个构建，再多线程也并行不了。

```text
并行总耗时 ≥ 关键路径长度 × 链上单模块平均耗时
最大加速比 ≤ 串行总耗时 / 关键路径耗时
```

【算例 3】沿用算例 1 的 20 个模块、600 秒串行总耗时。若最长依赖链为 5 个模块、每模块 30 秒，则关键路径耗时为 5 × 30 秒 = 150 秒，并行总耗时再低也不能低于 150 秒，最大加速比为 600 / 150 = 4 倍。此时 Amdahl 算出的 4.0 倍（N = 16、p = 0.8）与链上限 4 倍恰好重合：两者取小值，才是真实上限。


### 8.4 依赖树规模：直接依赖与传递依赖的数量级

`mvn dependency:tree` 的输出行数，约等于依赖图中去重后的节点数加少量树形缩进与省略行。先估节点数：

```text
依赖节点总数 ≈ 直接依赖数 + 直接依赖数 × 每个直接依赖平均带来的传递依赖数
```

传递依赖要去重：多个直接依赖共用同一个传递依赖时只计一次，上式是未去重上限，实际节点数只会更小。

【算例 4】某模块声明 12 个直接依赖，每个平均带来 6 个传递依赖，则未去重上限为 12 + 12 × 6 = 84 个节点，`dependency:tree` 输出约 80 多行。若换成 20 个直接依赖、每个平均带来 4 个传递依赖，则上限为 20 + 20 × 4 = 100 个节点，输出约 100 行。直接依赖从 12 涨到 20，树规模不是线性涨 8 行，而是按“直接依赖 × 平均传递数”放大。

数量级判断：单模块树在几十行属常规；过百行说明传递依赖已占大头，调解与排除的排查成本随之上升；过千行时先用 `-Dincludes=组 id:构件 id` 只看目标库的路径，不要通读全树。

### 8.5 本地仓库体积：单个 jar 大小 × 数量

本地仓库体积按构件数乘单个体积估算，一个构件通常含 jar、pom、校验文件等多份文件，jar 本身占大头：

```text
本地仓库体积 ≈ 构件数 × 单个 jar 平均大小
```

例如 200 个构件、单个 jar 平均 1 MB 时，体积约为 200 × 1 MB = 200 MB；平均 5 MB 时约为 200 × 5 MB = 1000 MB ≈ 0.98 GB；150 个构件、平均 2 MB 时约为 150 × 2 MB = 300 MB。

### 8.6 SNAPSHOT 更新检查：updatePolicy 的次数换算

`updatePolicy` 决定 Maven 多久检查一次远程 SNAPSHOT 更新，官方可选值为 `always`、`daily`（默认值）、`interval:X`（X 为分钟数）、`never`。`-U` 可强制刷新一次，不受该策略限制。

换算成每天检查次数：

```text
每天检查次数：daily = 1 次；interval:X = 1440 / X 次；always = 每天构建次数
```

`daily` 每天只检查 1 次；`interval:60` 每天检查 1440 / 60 = 24 次；`interval:30` 每天检查 1440 / 30 = 48 次；`interval:15` 每天检查 1440 / 15 = 96 次。`always` 每次构建都检查，每天构建 20 次即检查 20 次。`never` 只在本地不存在时才下载。


### 边界条件

- 单模块平均耗时不均匀时，乘法估算要按慢模块单独加权；只取全体平均值会低估关键路径，算出的加速比偏高。
- Amdahl 换算只适用于模块级并行，p 应按实测的可并行模块占比取值，取 1 会高估；依赖链上限按最长链计算，链上慢模块按实际耗时计，不能全按平均值。
- 依赖树节点数估算为未去重上限：多个直接依赖共用传递依赖时实际节点数更小，`dependency:tree` 的 `omitted for conflict` 行不计入有效节点；本地仓库体积估算只计 jar 本体，pom、校验文件与旧版本残留另计，磁盘占用以 `du` 实测为准。
- `updatePolicy` 的次数换算按自然日计：`daily` 的“每天”以 Maven 上次检查时间为准，不是按日历零点重置；`interval:X` 的计时从上次检查开始算。

## 原理剖析

本节只把原文已有章节给出的结论拆开讲清机制：不引入新命令，不补新数字，数字一律复用 §8 已核验的定量算例；凡原文没展开的点，文中明确标注，不作定论。

### 生命周期三套与插件绑定：为什么跑 package 会先跑前面所有阶段

本节只综合原文 §2 的结论。

- default 生命周期的阶段是一条按序排列的固定链：compile → test → package → verify → install → deploy。Maven 执行某个阶段时，会把该阶段之前的所有阶段按顺序执行一遍——这不是“顺带”，而是生命周期本身的定义：后面的阶段默认前面的阶段已经完成。所以 `mvn package` 一定先编译、再跑测试、最后才打包；想跳过测试只能用原文 §2 给出的两档跳过参数，而不是“只跑 package 这一步”。
- 三套生命周期（clean、default、site）互相独立：执行 clean 不会触发 default 的任何阶段，执行 site 也不会先构建。`mvn clean install` 实际上是先后跑了两套生命周期——先 clean 清理，再按 default 的链一路跑到 install。
- 插件的工作方式是把目标（goal）绑定到某个阶段上：原文 §2 只点出了两个例子——surefire 绑定在 test 阶段跑单元测试，failsafe 绑定在 verify 阶段跑集成测试。正因为绑定关系是按阶段挂的，阶段一执行，该阶段上挂着的插件目标就跟着执行；这也是“执行一个阶段等于执行它之前所有阶段上挂着的全部插件目标”的另一面。至于每个插件具体绑定了哪个目标、默认配置是什么，原文未展开，仅作概念提示，以本机实测为准。

### 依赖调解三条规则：冲突时到底按哪条

本节只综合原文 §3 与 §4 的结论。

- 三条规则有明确的先后次序，不是并列投票：先看深度（最近定义优先），深度相同再看声明顺序（第一声明优先），最后才是防御手段（optional 与 exclusions）。原文 §3 的例子就是这个次序的体现：A→B→C(1.0) 与 A→C(2.0) 冲突时，先比深度，深度更浅的 2.0 直接胜出，根本走不到“谁先声明”那一步；只有两条路径深度相同时，才轮到声明顺序裁决。
- 最近定义优先这样定，是因为离根越近的声明越能代表项目自己的意图：项目在自己的 pom 里直接写明的版本，是显式选择；经由两三层传递带进来的版本，只是某个上游库当时的默认值。调解时优先采纳离根更近的，等于优先采纳“离项目更近的决定”。这也是它与 Gradle“最高版本胜出”的根本差别：Maven 认的是声明位置，不是版本号大小。
- 第一声明优先是深度相同情况下的确定性兜底：两条路径谁也压不过谁时，按 pom 里先出现的声明裁决，保证同一份 pom 每次解析出同一版本。原文 §3 特意强调“声明顺序不是随便写的”，原因正在这里——调换两行声明的顺序，可能直接改变冲突的胜出者。
- scope（依赖范围）是调解之外的另一层过滤：原文 §3 的表只说明了每个 scope 自身的生效范围（compile 默认三阶段都生效，provided 只在编译与测试生效，runtime 只在测试与运行生效，test 仅测试生效），即一个依赖能不能进入某个阶段的类路径。至于某个 scope 的依赖经过传递之后，传到下游时 scope 会变成什么（例如 compile 依赖的 compile 依赖、test 依赖的 compile 依赖分别如何传递），原文未展开，仅作概念提示——排查时以 `mvn dependency:tree` 的实测结果为准，不要凭印象推断。
- optional 与 exclusions 不参与“选哪个版本”的裁决，它们的作用是剪掉整条传递路径：optional 让依赖不向外传递，exclusions 在引入点剪掉不需要的路径。原文 §3 说两者是防御手段、治本靠版本统一，意思是：剪路径能去掉不想要的传递依赖，但解决“同一库两个版本共存”仍要靠在 dependencyManagement 里钉死版本（§3）或在引入点排除后重跑 `dependency:tree` 确认（§4）。

### 仓库解析顺序与 SNAPSHOT 更新检查

本节只综合原文 §1、§5、§6 的结论。

- 查找顺序是固定的三层：本地仓库（`~/.m2/repository`，缓存）→ 私服（代理中央仓库并托管自研包）→ 中央仓库。先本地、再私服、最后才出网。这个顺序决定了两件事：其一，本地仓库一旦有某个版本的构件，Maven 不会再去远程确认它是不是最新的——RELEASE 版本一旦装进本地，就以本地为准；其二，找不到时才逐层向外找，所以“依赖下不下来”的排查（§6）也是按这个顺序倒查：先查 settings.xml 的镜像地址，再查私服上该版本是否真实存在，再查本地有无下载失败的残留（`*.lastUpdated`）。
- SNAPSHOT 是这条顺序的例外：因为 SNAPSHOT 可变，Maven 会按更新策略定期检查远程有没有更新的 SNAPSHOT，而不是只认本地缓存。原文 §5 只给了结论——默认按更新策略定期检查，`-U` 可强制刷新一次；§8.6 给了次数换算：`daily`（默认值）每天只检查 1 次，`interval:60` 每天检查 1440 / 60 = 24 次，`always` 每次构建都检查。换句话说，“同事更新了公共包我却没生效”在机制上只有几种可能：对方只 install 没 deploy（§5：install 只装进自己的本地仓库，deploy 才推私服）、本地还在更新策略的间隔期内、或者本地仓库里有下载失败的残留标记。至于 updatePolicy 具体配在 settings.xml 还是 pom 的哪一节、以及 daily 的“每天”以哪次检查为计时起点，原文只在 §8 边界条件里提了一句“以 Maven 上次检查时间为准，不是按日历零点重置”，其余未展开，以本机实测为准。
- install 与 deploy 的分工也是这条顺序的直接推论：install 只写本地仓库，deploy 才推私服。本地联调改了公共模块只 clean 不 install，别人拉到的还是旧版（小技巧节已有同样结论），因为 clean 只清 target，不动本地仓库里已装好的旧 SNAPSHOT。

### 聚合与继承：同一个父 pom，两种关系

本节只综合原文 §4 的结论。

- 聚合解决的是“构建顺序”：父 pom 用 `<modules>` 把若干模块组织成一次构建，反应堆（reactor）按模块间的依赖关系自动排序，保证被依赖的模块先构建。聚合不传递任何配置，它只决定“哪些模块一起构建、按什么顺序构建”。
- 继承解决的是“配置复用”：子 pom 用 `<parent>` 继承父 pom 的 dependencyManagement 与插件配置，子模块在 `dependencies` 里只写坐标不写版本，版本以父 pom 的统一声明为准（§3）。继承不决定构建顺序——一个子模块即使继承了父 pom，也可以单独构建。
- 两者概念独立，但常同时出现：同一个父 pom 既可以是聚合的组织者（列出 modules），又可以是继承的来源（被子模块用 parent 引用）。原文 §4 的提醒正在于此：不要因为它们常写在同一个 pom 里就把两者混为一谈——“一次构建哪些模块”是聚合的事，“版本与配置从哪继承”是继承的事。父 pom 的打包方式、`<parent>` 里相对路径的查找细节等，原文未展开，仅作概念提示，以本机实测为准。
- 部分构建参数（`-pl` 选模块、`-am` 连带上游、`-amd` 连带下游）操作的是聚合关系：它们在反应堆里划出一个子集来构建，继承关系不受影响。原文 §4 要求发布前仍要在根目录全量跑一遍，原因也在这里：局部构建验证的是子集，聚合的完整顺序与继承的完整配置只有全量构建才能覆盖。

### 并行构建为什么受关键路径限制

本节只综合原文 §7 与 §8.2、§8.3 的结论。

- `-T` 只并行构建无依赖关系的模块：模块之间没有依赖才能同时开工，有依赖的必须等上游先构建完。这是并行构建的第一重限制，也是 Amdahl 定律里“可并行部分占比 p”的来源——p 不是线程数决定的，而是模块依赖图决定的：能同时开工的模块越多，p 越大；链式依赖越多，p 越小。
- Amdahl 上限是第二重限制的算式化：原文 §8.2 的算例取 p = 0.8，N = 4 时加速比为 2.5 倍，N = 8 时约 3.33 倍，N = 16 时为 4.0 倍。线程数翻倍，加速比只从 2.5 倍涨到 3.33 倍，再翻倍也只到 4.0 倍——串行部分 20% 是天花板，p = 0.8 时加速比永远到不了 5 倍。把 §8.1 的 600 秒串行总耗时代入：N = 4 时并行总耗时约为 600 / 2.5 = 240 秒，N = 8 时约为 600 / 3.33 ≈ 180 秒，只比 N = 4 再省约 60 秒。线程数继续加，收益递减得很快。
- 关键路径是第三重、也是最硬的限制：模块间的最长依赖链必须一个接一个构建，再多线程也并行不了。原文 §8.3 的算例：20 个模块、600 秒串行总耗时，最长依赖链为 5 个模块、每模块 30 秒，则关键路径耗时为 5 × 30 秒 = 150 秒，并行总耗时再低也不能低于 150 秒，最大加速比为 600 / 150 = 4 倍。此时 Amdahl 算出的 4.0 倍（N = 16、p = 0.8）与链上限 4 倍恰好重合：两者取小值，才是真实上限。
- 三个限制叠加起来，就是原文 §7 那句“缩小范围（`-pl/-am`）通常比提速更有效”的原理：加线程只能压榨 Amdahl 公式里的 p / N 一项，压不动串行部分，也压不动关键路径；而缩小构建范围直接减少了总工作量与链长度。反过来，个别老插件线程不安全时退回串行定位（§7），也是同一逻辑：并行只在模块无依赖的前提下安全，插件层面的线程问题不在 Amdahl 公式与关键路径的覆盖范围内，原文未展开，以本机实测为准。

## 小技巧与冷知识

【小技巧】依赖树看完冲突还不够，跑一次 `mvn dependency:analyze` 查“声明了没用 / 用了没声明”的两类隐患：代码直接用了某个类、但 pom 里没声明它（靠传递依赖偷渡进来），升级上游一剪传递路径就编译失败；反过来声明了却没用到的依赖，白白拉大构建图。它是按字节码分析的，只靠注解、只在运行时起作用的依赖（如 Spring Boot starter 里的自动配置）会被误报成“未使用”，删之前先确认，别照单全删。

【小技巧】`mvn dependency:analyze-dep-mgt` 专门对照 dependencyManagement 与实际解析结果：它会列出哪些依赖的解析版本和 dependencyManagement 里写的不一致，专治原文说的“统一不生效”。查到不一致时先搜子模块里有没有显式写死的版本——显式版本盖过统一管理，统一管理的版本只是默认值，不是强制值。

【小技巧】版本到底从哪来，别靠猜，用 `mvn help:effective-pom` 看最终生效的 pom：父 pom、import 的 BOM、激活的 profile 叠加之后，某个依赖的版本、某个插件的配置到底是多少，这一条命令全摊开。依赖冲突查到最后发现“版本不知从哪冒出来”，先打 effective-pom，比一层层翻父 pom 快得多。

【小技巧】弱网或断网环境先 `mvn dependency:go-offline` 预下载，再用原文的 `-o` 离线跑：go-offline 会把项目依赖、插件及插件的依赖一次性全部解析进本地仓库，之后 `-o package` 就不再碰网络。只 `mvn -o` 不预下载，缺一个包就中途停下；先 go-offline 再离线，等于把“下载”和“构建”两个动作拆开，出问题也分得清是哪一步。

【小技巧】升级前先列清单，别一个个翻仓库：`mvn versions:display-dependency-updates` 列出所有有新版本的依赖，`versions:display-plugin-updates` 列出插件的。先看清单再决定升哪个、一次升几个，配合 dependencyManagement 钉版本，升级才是有计划的动作，而不是“看到提示就顺手改一个版本号”。

【小技巧】多模块只跑某个测试类时，加上 `-DfailIfNoTests=false`：`mvn test -Dtest=FooServiceTest` 会在所有模块里找这个测试类，没有它的模块默认直接报错中断，加上这个参数后无匹配测试的模块跳过不报错。只想验证某一个模块时再配 `-pl`，两个参数配合才是“只跑我想跑的测试”的完整写法。

【小技巧】settings.xml 里的私服密码别写明文，用环境变量引用：`<password>${env.MAVEN_REPO_PASSWORD}</password>`，密码只存在本机环境变量或 CI 的 Secrets 里。settings.xml 不进版本库只是第一层，凭据本身也不该以明文躺在磁盘文件里；换机器时只改环境变量，配置文件原样拷走就能用。

【小技巧】`mvn clean` 只清 target，不清本地仓库里已装好的旧 SNAPSHOT：改了公共模块的代码，只 clean 不 install，别人拉到的还是旧版——install 才把新产物装进本地仓库，deploy 才推私服。本地联调“改了代码却没生效”时，先确认公共模块有没有重新 install，再怀疑缓存和版本。

【冷知识】Maven 的名字来自意第绪语，意思是“知识的积累者”（accumulator of knowledge）：它最初是 Jakarta Turbine 项目里简化构建流程的尝试，名字取的就是“把构建知识攒起来”这个意思。理解这一点就明白它为什么坚持约定大于配置——整个工具的设计目标，就是让构建知识沉淀在 pom 和约定里，而不是散落在每个人的脚本里。

【冷知识】子 pom 找父 pom 时，`<parent>` 里的 `<relativePath>` 默认就是 `../pom.xml`：Maven 先按这个相对路径在磁盘上找，找不到才去仓库里按坐标找父 pom。多模块改目录结构、把子模块挪了位置后构建报“找不到父 pom”，先查 relativePath 对不对，而不是先怀疑仓库和坐标；不写 relativePath 时它就是默认的 `../pom.xml`，不是“不查磁盘直接去仓库”。

## 9. 面试与自测

1. Maven 依赖调解规则是什么？深度相同冲突时谁胜出？
2. `dependencyManagement` 与 `dependencies` 的区别？BOM 如何导入？
3. 运行时报 `NoSuchMethodError` 但编译通过，排查步骤是什么？
4. install 与 deploy 的区别？SNAPSHOT 为什么同事更新了你却拉不到？
5. 聚合与继承有什么区别？

6. 某项目 20 个模块、单模块平均 30 秒，串行总耗时多少？取可并行占比 0.8、用 `-T 4` 时 Amdahl 加速比与并行耗时是多少？若最长依赖链为 5 个模块，最大加速比是多少？另估算 12 个直接依赖、每个平均带来 6 个传递依赖时的依赖树节点数，以及 SNAPSHOT 用 `daily` 与 `interval:60` 时每天各检查几次？

### 参考答案

1. 传递依赖调解规则是最近定义优先：离根越近的版本胜出，如 A→B→C(1.0) 与 A→C(2.0) 冲突时，深度更浅的 2.0 赢。深度相同时先声明优先，先声明的路径胜出，声明顺序不是随便写的。注意这与 Gradle 的最高版本胜出不同，跨生态时容易记混。
2. dependencyManagement 只声明版本、不实际引入；各模块在 dependencies 里只写坐标不写版本，版本以它为准，父 pom 靠它统一全工程版本。BOM 是只含 dependencyManagement 的 pom，用 scope=import 导入，如 spring-boot-dependencies，导入后它管理的那批库全不用写版本。注意 dependencies 里显式写死的版本会盖过 dependencyManagement。
3. 排查步骤：先用 mvn dependency:tree 看目标库有几个版本、从哪条路径进来，必要时加 -Dincludes 只看某个库、-Dverbose 看被调解掉的版本；再在引入点用 exclusions 剪掉错误路径，或在 dependencyManagement 里钉死版本；重跑 dependency:tree 确认只剩一个版本；最后跑测试验证。团队项目可加 maven-enforcer-plugin 的依赖收敛规则，让冲突在构建期报错而非运行时。
4. install 只把产物装进自己的本地仓库，deploy 才推私服，所以只 install 同事永远拉不到。SNAPSHOT 是可变版本，Maven 默认按更新策略定期检查更新，同事更新了你却拉不到时，先确认对方是不是 SNAPSHOT，再用 -U 强制刷新；还要查对方是否只 install 没 deploy，以及本地仓库有无下载失败的 *.lastUpdated 残留。
5. 聚合与继承是两件事：聚合是父 pom 用 modules 组织一次构建，反应堆按模块间依赖自动排序，解决构建顺序；继承是子 pom 用 parent 继承 dependencyManagement 与插件配置，解决配置复用。两者概念独立，常同时出现；部分构建用 -pl 选模块、-am 连带上游、-amd 连带下游，发布前仍要在根目录全量跑一遍。

6. 串行 20×30=600 秒=10 分钟；p=0.8、N=4 加速比 2.5 倍，并行约 240 秒；最长链 5×30=150 秒，最大加速比 4 倍；依赖树上限 84 个；SNAPSHOT 检查 daily 每天 1 次，interval:60 每天 24 次。
