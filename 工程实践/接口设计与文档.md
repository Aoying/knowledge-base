# 接口设计与文档

本篇分两部分：第一部分讲设计侧（REST 接口怎么定），第二部分讲文档侧（OpenAPI 文档怎么自动生成与维护），两部分分工不要混。

## 第一部分：REST 接口设计

### 1. 核心概念

REST 不是协议，而是一套以**资源**为中心的接口组织风格：URL 定位资源，HTTP 方法表达动作，状态码表达结果。本篇管**设计侧**——接口长什么样、语义怎么定；文档怎么自动生成、怎么维护见本篇第二部分，两部分分工不要混。

设计的目标是可预期：调用方不用逐个接口读文档猜行为——增删改查都长一个样，错误都一个格式，分页都一种翻法。一致性比「某个接口设计得多精巧」更重要。

### 2. 资源命名

- URL 用**名词、复数**：`/customers`、`/customers/{id}`、`/loans/{id}/approvals`。层级表达从属关系，但别超过 2–3 层，更深的关系拆成独立资源加查询参数。
- 动词是反模式：`/createCustomer`、`/getLoanList`、`/approveLoan` 都不对，动作交给 HTTP 方法。实在是动作而非资源的操作（如审批通过、发起重算），两种务实处理：子资源化（`POST /loans/{id}/approvals` 表示「新增一条审批」），或在资源下挂明确动作端点（`POST /loans/{id}:approve` 风格）并写进团队约定，全库统一，不要每个接口自创。
- 路径用 kebab-case（`/loan-applications`），字段名风格（camelCase）与团队 JSON 约定保持一致，全局只选一种。
- 过滤、排序、分页一律走查询参数：`GET /loans?status=PENDING&sort=createdAt,desc&page=0&size=20`，不要为筛选条件发明新路径。

### 3. 方法与状态码

| 方法 | 语义 | 幂等 | 典型状态码 |
|---|---|---|---|
| GET | 查 | 是 | 200；查不到 404 |
| POST | 新建/触发 | 否（要业务补幂等） | 201 Created（带 Location 头指新资源） |
| PUT | 整体替换 | 是 | 200 |
| PATCH | 局部更新 | 约定上按幂等设计 | 200 |
| DELETE | 删除 | 是 | 204 No Content |

状态码使用纪律：

- **不要全用 200 再在 body 里包错误**。协议层失败就给协议层状态码，监控、网关、前端拦截器都靠它工作：参数校验不过 400、未登录 401、无权限 403、资源不存在 404、状态冲突（如重复审批、版本冲突）409、参数格式对但业务规则不通过 422、服务端异常 500。
- 401 与 403 别混：前者是「没证明你是谁」，后者是「知道你是谁但不许」，与安全框架的划分一致，见 [Spring Security](开发语言/Java/Spring/Spring-Security.md)。
- 500 只给未预期异常；业务可预期的失败都要有明确状态码 + 业务码，不要拿异常栈当错误信息返回。

### 4. 版本管理

| 方式 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| URL 路径 | `/api/v1/loans` | 直观、调试和网关路由最省事 | URL 不「纯」，但工程上代价最小 |
| 请求头 | `Accept: application/vnd.app.v1+json` | URL 干净 | 不可见、联调和排障成本高 |

企业项目实务直接选 URL 版本，且只保留「大版本」粒度：兼容性变更（加字段、加可选参数）不升版，直接上线；破坏性变更（删字段、改语义）才开新大版本并双版本并行一段迁移期。不要出现 `/v1.1`、`/v2beta` 这种把版本号当发布号用的做法。

### 5. 幂等设计

重复提交在业务系统里是常态：前端连点、网关重试、消息重投。幂等要靠设计，不能靠用户手速。

- 天然幂等的 GET/PUT/DELETE 直接用好；POST 是要重点补的：创建类接口用**幂等键**——调用方带 `Idempotency-Key`（或直接用业务单号）+ 服务端唯一索引兜底，重复请求命中已有记录直接返回首次结果，而不是再建一条。
- 状态流转类接口（审批、确认、发货）用**状态机前置校验**：`WHERE status = 'PENDING'` 带条件更新，影响行数为 0 说明已被处理过，返回 409 或当前状态。ao 的审批流场景里，同一个待办被两人同时点、或一人连点，靠的就是这条而不是前端按钮置灰。
- 幂等实现放在服务端，前端防重复点击只是体验优化，一个都不能少、但不能互相替代。

### 6. 统一响应与错误码

统一信封结构，全库一套：

```json
{
  "code": "0",
  "msg": "success",
  "data": { },
  "traceId": "a1b2c3"
}
```

- 分工定死：**HTTP 状态码管协议层结果，业务 code 管业务层结果**。业务失败（如额度不足）用 200 + 业务码，还是直接 4xx？两种流派都成立，但必须全库统一并写进约定；混合着来是联调事故的最大来源。
- 业务错误码分段管理（如 1xxxx 参数类、2xxxx 业务类、3xxxx 外部系统类），码表集中一处维护，错误消息给人看、错误码给程序分支，两者都要有。
- `traceId` 必带：与日志 MDC 里的链路 ID 同源，客诉和排障时靠它把一次请求的前后端日志串起来。信封里不放异常栈、不放内部类名和 SQL。

### 7. 分页约定

| 方式 | 适用 | 注意 |
|---|---|---|
| 页码分页 `page/size` + total | 后台管理、要跳页要总数 | 深翻页性能差；查 total 有额外成本，大表慎用每页都查 |
| 游标分页 `cursor/limit` | 信息流、导出、对接拉取 | 不支持跳页；游标字段必须稳定唯一 |

两条铁律：**分页必须带排序，且排序键要以唯一字段收尾**（如 `createdAt desc, id desc`），否则同一行在两次翻页间会重复或丢失；`size` 必须设上限，防止一次拉全表把接口打成导出工具还不走导出通道。

### 8. 常见误区

- GET 请求带 body 传参：网关、缓存、日志系统都可能把 body 丢掉或不识别，查询条件一律走查询参数。
- 一个接口干两件事：「保存并提交」「查询并导出」这类复合动作拆开，失败语义和重试语义完全不同，揉在一起两边都做不好。
- 返回结构随接口心情：有的包信封有的裸返、列表有的给数组有的给对象。统一信封 + 全局异常处理（`@RestControllerAdvice`）收口，新增接口不允许自创格式。
- 错误消息直接透传下游系统原文：外部系统的报错含内部细节且口径不一，对外要映射成自家错误码，下游原文只进日志。

## 第二部分：OpenAPI 接口文档

### 1. 核心概念

手写接口文档必过期：字段改了文档没跟，前后端联调靠口头对齐。OpenAPI 方案是从代码（路由 + 注解 + DTO）自动生成标准描述（JSON/YAML），再渲染成交互页面（Swagger UI），文档与代码同源、随版本发布。

Boot 2.7 的选型结论：用 **springdoc-openapi**，不要再上 springfox——springfox 已多年不维护、与新版本 Spring 的路径匹配策略冲突是经典启动报错来源。springdoc 1.7.x 是对应 Boot 2.7 的版本线（Boot 3 要换 springdoc 2.x + Jakarta，别混装）。

### 2. 基础知识

引入依赖（版本由 1.7.x 管理，勿在 Boot 2.7 上用 2.x）：

```xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-ui</artifactId>
    <version>1.7.0</version>
</dependency>
```

启动后默认地址：文档 JSON `/v3/api-docs`，页面 `/swagger-ui.html`（自动跳 `/swagger-ui/index.html`）。基础信息配置：

```java
@Configuration
public class OpenApiConfig {
    @Bean
    public OpenAPI appOpenAPI() {
        return new OpenAPI().info(new Info()
                .title("神农 e 贷法人版 API")
                .version("v1")
                .description("客户、额度、进件、审批接口"));
    }
}
```

常用注解（都在 `io.swagger.v3.oas.annotations` 包）：

| 注解 | 位置 | 作用 |
|---|---|---|
| `@Tag(name, description)` | Controller 类 | 接口分组名与说明 |
| `@Operation(summary, description)` | 方法 | 接口标题与详细说明 |
| `@Parameter(description, required)` | 方法参数 | 路径/查询参数说明 |
| `@Schema(description, example)` | DTO 字段 | 字段含义与示例值 |
| `@ApiResponse` | 方法 | 补充非默认响应码说明 |

```java
@Tag(name = "进件管理", description = "贷款申请提交与查询")
@RestController
@RequestMapping("/api/applies")
public class ApplyController {

    @Operation(summary = "提交进件", description = "校验通过后落库并启动审批流程")
    @PostMapping
    public Result<Long> submit(@RequestBody @Valid ApplySubmitDTO dto) { ... }

    @Operation(summary = "按编号查询进件")
    @GetMapping("/{id}")
    public Result<ApplyVO> get(
            @Parameter(description = "进件编号", required = true) @PathVariable Long id) { ... }
}
```

### 3. 进阶知识

#### 与 Bean-Validation 的配合

springdoc 会自动把 DTO 上的校验注解翻译成 Schema 约束，前后端对字段规则有一份共同事实，不用在文档里再手写一遍：

| 校验注解 | 生成的约束 |
|---|---|
| `@NotNull` / `@NotBlank` / `@NotEmpty` | `required: true` |
| `@Size(max = 32)` / `@Length` | `maxLength` / 数组 `maxItems` |
| `@Min` / `@Max` / `@DecimalMin` 等 | `minimum` / `maximum` |
| `@Pattern` | `pattern` 正则 |
| `@Email` | `format: email` |

口径注意：校验注解是**运行时事实**（见 [Bean-Validation](开发语言/Java/Bean-Validation.md)），文档只是它的投影；只在 `@Schema` 里写「必填」而不加校验注解，文档好看但接口照样放行非法数据，别把顺序弄反。

#### 文档分组

多组接口按业务域拆组，页面顶部可切换，前端按组对接：

```java
@Bean
public GroupedOpenApi applyGroup() {
    return GroupedOpenApi.builder()
            .group("进件与审批")
            .pathsToMatch("/api/applies/**", "/api/approvals/**")
            .build();
}

@Bean
public GroupedOpenApi customerGroup() {
    return GroupedOpenApi.builder()
            .group("客户与额度")
            .packagesToScan("com.example.customer.controller")
            .build();
}
```

分组维度二选一（路径或包），团队内统一一种，别混用导致接口重复出现或漏组。

#### 全局鉴权声明

接口要带 Token 时在配置里声明安全方案，页面上出现 Authorize 按钮，联调时填一次全局生效：

```java
new OpenAPI().components(new Components().addSecuritySchemes("bearerAuth",
        new SecurityScheme().type(SecurityScheme.Type.HTTP).scheme("bearer").bearerFormat("JWT")))
    .addSecurityItem(new SecurityRequirement().addList("bearerAuth"));
```

网关统一鉴权的系统也要照此声明：文档描述的是调用契约，不是鉴权实现位置。

### 4. 实战应用

- **环境开关**：生产与对外环境关掉页面或加访问控制——`springdoc.swagger-ui.enabled` 与 `springdoc.api-docs.enabled` 按 profile 配置；内网生产至少限制到运维网段，接口文档等于把系统地图公开，别裸奔。
- **DTO 别偷懒**：入参出参用独立 DTO/VO 并写 `@Schema` 说明与示例；直接拿 Entity 当出参，字段语义不清还会把内部字段（逻辑删除标志、审计字段）暴露给前端。
- **枚举与字典**：枚举字段在 `@Schema` 里写清每个取值的业务含义（如审批状态 0 待审 / 1 通过 / 2 驳回），这是联调吵架最多的地方。
- **导出给前端**：`/v3/api-docs` 的 JSON 可导入 Apifox/Postman 生成用例与 Mock；接口变更评审时 diff 这份 JSON，比口头通知可靠。

### 5. 疑难杂症

- **页面 404 或打开空白**：先直连 `/v3/api-docs` 看 JSON 是否正常——JSON 正常而页面打不开多是静态资源被网关/拦截器拦了（放行 `/swagger-ui/**`、`/v3/api-docs/**`）；JSON 都没有则查依赖是否引入成功、是否被 profile 开关关掉。
- **接口没出现在文档里**：Controller 没被组件扫描到、方法不是公开映射、或分组的路径/包规则没覆盖它。
- **泛型与嵌套对象展开不对**：返回包装类（如统一 `Result<T>`）要保证泛型实参明确；实在展开不了的复杂结构用 `@Schema(implementation = ...)` 指定呈现模型，别为了文档改业务结构。
- **文件上传接口**：参数用 `MultipartFile` 并声明 `consumes = MediaType.MULTIPART_FORM_DATA_VALUE`，否则 UI 上没有文件选择框。

### 6. 常见误区

- 注解写满整个 Controller，把业务代码淹没：说明文字保持短句，复杂业务规则写在项目 Wiki/需求文档里并在 `description` 放链接。
- 为了「文档好看」在 `@Schema` 里写与校验注解不一致的约束（文档说必填、实际不校验），联调必翻车。
- 生产环境开着文档还无鉴权，且示例值里带真实客户数据——示例一律用虚构值。

4. 分页为什么要求排序键唯一收尾？
5. 业务错误到底走状态码还是走业务 code？你的项目里约定是哪种、为什么？

7. 校验注解是怎么变成文档约束的？为什么不能只写 `@Schema` 不写校验？
8. 文档分组有哪两种维度？混用会出什么问题？
9. 生产环境接口文档应该怎么处理？风险是什么？

### 参考答案

1. PUT 是整体替换，天然幂等；PATCH 是局部更新，约定上按幂等设计。POST 本身不幂等，所以创建类接口需要幂等键：调用方带 Idempotency-Key（或直接用业务单号），服务端用唯一索引兜底，重复请求命中已有记录直接返回首次结果，而不是再建一条；状态流转类接口则用状态机前置校验（WHERE status='PENDING'，影响行数为 0 说明已被处理过）。
2. 409 用于状态冲突，如重复审批、版本冲突；422 用于参数格式对但业务规则不通过。两者分工是：409 是资源当前状态不允许这个操作，422 是请求本身合法但业务上无法接受。
3. 企业项目实务直接选 URL 版本（如 /api/v1/loans），优点是直观、调试和网关路由最省事；请求头版本 URL 干净，但不可见、联调和排障成本高。只保留大版本粒度：兼容性变更（加字段、加可选参数）不升版直接上线，破坏性变更（删字段、改语义）才开新大版本并双版本并行一段迁移期，不要出现 /v1.1、/v2beta 这种把版本号当发布号的做法。
4. 因为不带唯一收尾的排序是不稳定的：同一行在两次翻页之间可能重复或丢失。铁律是分页必须带排序，且排序键要以唯一字段收尾，如 createdAt desc, id desc；同时 size 必须设上限，防止一次拉全表把接口打成导出工具。
5. 本篇没有定死项目用哪一种，它定死的是分工与统一：HTTP 状态码管协议层结果，业务 code 管业务层结果，两种流派（业务失败走 200 加业务码，或直接走 4xx）都成立，但必须全库统一并写进约定，混合着来是联调事故的最大来源。选型时看调用方与网关是否依赖状态码做拦截与监控，再全库落到一种并在团队约定里写明。
6. springfox 已多年不维护，且与新版本 Spring 的路径匹配策略冲突，是经典启动报错来源；springdoc 是当前主流。Boot 2.7 该选 springdoc 1.7.x 版本线，Boot 3 要换 springdoc 2.x 加 Jakarta，两条线别混装。
7. springdoc 会自动把 DTO 上的校验注解翻译成 Schema 约束，如 @NotNull/@NotBlank 对应 required、@Size 对应 maxLength、@Min/@Max 对应 minimum/maximum、@Pattern 对应 pattern。不能只写 @Schema 不写校验：校验注解是运行时事实，文档只是它的投影；只在 @Schema 里写必填而不加校验，文档好看但接口照样放行非法数据，顺序不能反。
8. 两种维度：按路径（pathsToMatch）或按包（packagesToScan）。团队内必须统一一种，二选一；混用会导致接口重复出现或漏组。
9. 生产与对外环境应关掉页面或加访问控制，用 springdoc.swagger-ui.enabled 与 springdoc.api-docs.enabled 按 profile 配置，内网生产至少限制到运维网段。风险是接口文档等于把系统地图公开，裸奔等于把接口、字段、枚举含义全部暴露；示例值一律用虚构值，不能带真实客户数据。
