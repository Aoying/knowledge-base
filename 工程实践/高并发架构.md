# 高并发架构

## 1. 核心概念

高并发不是“堆机器”，而是“让每一层只承担它该承担的量”。一句话模型：**流量先被削峰和分流，剩下的量再被缓存、异步和拆分消化，实在扛不住的部分靠降级保住核心**。手段之间有先后顺序，乱序上手段等于白花钱：没做缓存就扩容，是用机器替缓存还债；没做限流就做降级，是等系统被打垮了才认输。

并发量先算清楚再动手：峰值 QPS、平均响应时间、并发数怎么互相推导，见 [容量估算](工程实践/容量估算.md)，不要凭感觉定机器数。

## 2. 分层手段全景

| 层 | 手段 | 解决什么 | 典型代价 |
|---|---|---|---|
| 入口层 | 限流、负载均衡 | 挡住超预期流量、把流量摊开 | 限流阈值要随容量复核，见 [限流熔断与降级](开发语言/Java/限流熔断与降级.md) |
| 缓存层 | 本地缓存、分布式缓存、多级缓存 | 把读请求挡在数据库之外 | 一致性与失效策略，见缓存相关篇 |
| 异步层 | 消息队列削峰填谷 | 把峰值摊到时间轴上 | 消费延迟、顺序与幂等，见 [Kafka-消息队列](消息队列/Kafka-消息队列.md) |
| 服务层 | 拆分、读写分离、无状态化 | 单点变多点、读压力分流 | 分布式事务与调用链变复杂 |
| 数据层 | 分库分表、索引优化 | 单库单表扛不住的量 | 跨库查询与事务，见分库分表篇 |
| 兜底层 | 降级、熔断、回滚 | 保住核心链路，其余可舍 | 降级策略要事先排练，不是现写 |

缓存算术（不是性能承诺，只是量级关系）：总读 QPS 10000、缓存命中率 90%，回源 QPS = 10000 × (1 − 0.9) = 1000。命中率每掉 10 个点，回源压力就翻一倍左右，所以缓存失效、热点 Key、大 Key 这三件事要当事故隐患管。

```python
total_qps, hit_rate = 10000, 0.9
print(round(total_qps * (1 - hit_rate)))  # 1000，回源 QPS
```

### 线程池定量：线程数不是拍出来的

服务层最常见的定量问题是「线程池开多大」。Brian Goetz 在《Java Concurrency in Practice》里给的公式是起点：

**线程数 = CPU 核数 × 目标利用率 × (1 + 等待时间 / 计算时间)**

- **CPU 密集型**：等待时间 ≈ 0，线程数 ≈ 核数；再多线程只会增加切换开销。
- **IO 密集型**：等待时间远大于计算时间，线程数远超核数。算例：8 核机器，任务调下游接口平均等 100ms、处理 20ms，目标利用率取 1 → 8 × (1 + 100/20) = 48 线程。

```python
cores, wait_ms, compute_ms = 8, 100, 20
print(cores * (1 + wait_ms / compute_ms))  # 48，Goetz 公式算例
```

三个边界，公式算完再看：

1. **公式是起点不是答案**：等待/计算比要靠实测（压测看 CPU 利用率、队列深度、P99），不能只算一次就定死；混合负载不要共用一个池——CPU 密集和 IO 密集任务放一起会互相拖垮，分池隔离。
2. **虚拟线程改变游戏规则**：Java 21+ 的虚拟线程每个任务一个线程、阻塞时不占平台线程，池大小不再是瓶颈，公式基本失去意义；新服务优先考虑虚拟线程，见 [虚拟线程](开发语言/Java/虚拟线程.md)。线程池本身的构造与拒绝策略见 [线程池](开发语言/Java/并发/线程池.md)。
3. **队列是公式之外的另一半**：线程数定下来后，队列长度和拒绝策略决定超载时发生什么——这就是背压，见下节。

### 连接池定量与背压：超载时谁先说“不”

**数据库连接池同理定量**：连接数不是越大越好。并发占用 ≈ QPS × 单请求占用连接时长（Little's law 思路）：QPS 500、单请求持连接 20ms → 并发占用 ≈ 500 × 0.02 = 10 个连接，池设 20 留有余量。连接数超过数据库能并行处理的量，只会增加锁等待和切换，不会增加吞吐。

**背压是「逐层传递的拒绝」**：入口限流 → 线程池有界队列 + 拒绝策略 → 消息队列堆积告警，任何一层「无限接收」都会把压力传到下一层，最终在数据库或内存上炸开。

- **有界队列 + 拒绝策略是背压的落地形态**：队列无界等于把背压推迟到 OOM；拒绝策略三选一——抛错（调用方立刻知道失败，可重试或降级）、调用线程自己执行（`CallerRunsPolicy`，变相给上游限流，会拖慢上游）、丢弃（只适用于可丢的任务，如埋点）。选之前想清楚谁来扛这份延迟。
- **背压信号要看得见**：队列深度、拒绝次数、消息堆积量要进监控和告警，而不是等用户报障才发现；堆积告警的阈值按「消费速度能追上」来定，不是拍一个数。

## 3. 典型场景

- **秒杀**：流量特征是瞬时尖峰 + 库存竞争。顺序是：入口限流 → 库存预扣减（缓存层）→ 异步下单（消息队列）→ 数据库只做最终落库。不要让数据库直接面对尖峰，也不要用“先查库存再扣减”这种两步操作去抢库存。
- **审批流高峰**：流量特征是白天集中 + 长链路（表单、附件、流程引擎、通知）。顺序是：读写分离（列表查询走从库）→ 流程推进异步化（通知、归档走消息队列）→ 核心链路（提交、审批动作）优先保障，非核心（统计、报表）降级或延后。审批动作本身要幂等，重复提交、重复审批靠状态机前置校验挡，见接口幂等相关篇。
- **报表与导出**：流量特征是少量请求、单个请求很重。不要和在线链路抢资源：独立服务或独立连接池、异步导出、结果文件化，禁止在线接口直接扫全表。

## 4. 组合顺序与适用边界

推荐的上手段顺序：

1. **先算数**：容量估算出峰值 QPS、带宽、存储、机器数，再决定缺口在哪一层。
2. **先缓存**：读多写少的系统，缓存是性价比最高的手段；缓存解决不了的再往下走。
3. **再异步**：能接受延迟的写操作（通知、日志、归档、统计）一律异步化，核心写链路保持同步。
4. **再拆分**：单服务、单库成为瓶颈时拆分；拆分引入的分布式问题（事务、一致性、调用链）要同步有解法，不要为拆而拆。
5. **最后降级**：降级是兜底，不是常规手段。降级策略、降级开关、降级后的用户提示要事先定好并演练，细节见限流与降级篇，本篇不重复抄。

适用边界：

- 读多写少 → 缓存优先；写多读少 → 异步与拆分优先；强一致要求 → 不要用“最终一致”那套手段硬套，先确认业务能不能接受延迟。
- 小系统不要上全套：日活几千的系统做分库分表和全链路降级，是提前支付大系统的复杂度。

## 5. 常见误区

- 机器数拍脑袋：不算 QPS、不算单机容量就扩容，扩完还是不知道瓶颈在哪。
- 缓存当银弹：缓存只挡读流量，写尖峰、库存竞争、长事务一概挡不住。
- 异步当万能：异步引入延迟、顺序、幂等、死信一串新问题，核心链路该同步的别异步。
- 降级现写现用：故障时才想降级策略，开关没经过演练等于没有开关。

## 原理剖析

本节只把原文已有章节给出的结论拆开讲清机制：不引入新概念，不补新数字，数字一律复用原文第 1、2 节已核验的定量算例；凡原文没展开的点，文中明确标注，不作定论。

### 手段的上线顺序

原文第 1 节与第 4 节：手段之间有先后顺序，乱序上手段等于白花钱。推荐顺序是先算数（容量估算出峰值 QPS、带宽、存储、机器数，再决定缺口在哪一层），先缓存（读多写少的系统，缓存是性价比最高的手段），再异步（能接受延迟的写操作一律异步化，核心写链路保持同步），再拆分（单服务、单库成为瓶颈时拆分，拆分引入的分布式问题要同步有解法，不要为拆而拆），最后降级（降级是兜底，不是常规手段，策略与开关事先定好并演练）。没做缓存就扩容，是用机器替缓存还债；没做限流就做降级，是等系统被打垮了才认输。

### 缓存算术

原文第 2 节：总读 QPS 10000、缓存命中率 90%，回源 QPS = 10000 × (1 − 0.9) = 1000。命中率掉到 80% 时回源 QPS = 10000 × (1 − 0.8) = 2000，翻一倍；命中率每掉 10 个点，回源压力就翻一倍左右。所以缓存失效、热点 Key、大 Key 这三件事要当事故隐患管。热点 key 过期瞬间大量请求同时打到数据库叫缓存雪崩，解法是给 TTL 加随机抖动（如基础 10 分钟再加 0–60 秒随机量），把过期时间打散。

### Goetz 线程池公式

原文第 2 节：线程数 = CPU 核数 × 目标利用率 × (1 + 等待时间 / 计算时间)。CPU 密集型等待时间约等于 0，线程数约等于核数，再多线程只会增加切换开销；IO 密集型等待时间远大于计算时间，线程数远超核数。算例：8 核机器，任务调下游接口平均等 100ms、处理 20ms，目标利用率取 1，线程数 = 8 × (1 + 100/20) = 48。公式是起点不是答案：等待与计算比要靠实测（压测看 CPU 利用率、队列深度、P99），混合负载不要共用一个池；Java 21+ 的虚拟线程每个任务一个线程、阻塞时不占平台线程，池大小不再是瓶颈，公式基本失去意义。

### 连接池定量与背压

原文第 2 节：数据库连接池同理定量，并发占用约等于 QPS × 单请求占用连接时长（Little's law 思路）：QPS 500、单请求持连接 20ms，并发占用约等于 500 × 0.02 = 10 个连接，池设 20 留有余量。连接数超过数据库能并行处理的量，只会增加锁等待和切换，不会增加吞吐。背压是「逐层传递的拒绝」：入口限流、线程池有界队列加拒绝策略、消息队列堆积告警，任何一层「无限接收」都会把压力传到下一层，最终在数据库或内存上炸开。队列无界等于把背压推迟到 OOM；拒绝策略三选一——抛错、调用线程自己执行（`CallerRunsPolicy`，变相给上游限流）、丢弃（只适用于可丢的任务，如埋点）。

## 实战案例

以下两则只用原文已给出的写法与数字，不引入原文之外的事实。

### 案例一：没做缓存就扩容，扩完瓶颈还在

现象：读多写少的系统扛不住，扩了机器还是慢，瓶颈一点没动。

排查：先算数——总读 QPS 10000、缓存命中率 90% 时回源 QPS 只有 1000，缓存把九成读请求挡在数据库之外；没做缓存就扩容，是用机器替缓存还债。读多写少场景下缓存是性价比最高的手段，先上缓存再谈扩容。

结论：先上缓存，再看缺口在哪一层。缓存失效、热点 Key、大 Key 要当事故隐患管；小系统不要上全套，日活几千的系统做分库分表和全链路降级，是提前支付大系统的复杂度。

### 案例二：秒杀库存超卖

现象：秒杀时库存扣成负数，超卖了。

排查：不要用「先查库存再扣减」这种两步操作去抢库存。秒杀的流量特征是瞬时尖峰加库存竞争，顺序是入口限流、库存预扣减（缓存层）、异步下单（消息队列）、数据库只做最终落库，不要让数据库直接面对尖峰。

结论：库存竞争靠预扣减加异步下单，数据库只做最终落库。审批流高峰是另一套顺序（读写分离、流程推进异步化、核心链路优先保障、非核心降级或延后），特征不同、瓶颈层不同，顺序也不同。

## 小技巧与冷知识

【小技巧】缓存过期别让所有 key 同一秒失效：热点 key 过期瞬间，大量请求同时打到数据库叫缓存雪崩，解法是给 TTL 加随机抖动（如基础 10 分钟再加 0–60 秒随机量），把过期时间打散。原文只算了命中率掉 10 个点回源翻倍，雪崩是“命中率瞬间归零”的极端版——抖动 TTL 是成本最低的预防，落地时先看缓存 key 的过期时间是不是批量对齐的。

【小技巧】热点 key 失效时只放一个请求回源：缓存击穿时上千个请求同时穿透，只让第一个拿到锁的去查库、其余等它把结果写回缓存再读，这就是互斥回源（singleflight 思路）。没锁的版本是“每个请求都查一次库”，热点 key 一失效就等于直接把库打穿；加锁的代价只是一次等待，比全量回源便宜得多，落地时锁的粒度按 key 设，别全库一把大锁。

【小技巧】缓存穿透别只靠“查不到就返回空”：不存在的 key 每次都打到数据库，攻击者拿随机 ID 轮询就能把库刷爆。落地做法是查不到也写一条带短 TTL 的空值缓存，或者在前面加一层布隆过滤器先判“这个 key 可能存在吗”；空值缓存简单但要防“刚写入的真实数据被旧空值挡住”，TTL 给短一点（如几十秒）是折中。

【小技巧】限流阈值别写死一个数，要跟着容量复核：机器扩了一倍、单机容量上去了，旧阈值还在按老容量挡流量，等于自己给自己限流。原文表里写了“限流阈值要随容量复核”，落地动作是：每次扩容、压测、换机型后，把阈值和单机容量重新对一遍表；阈值是容量派生出来的数，不是写进配置就一劳永逸的常量。

【小技巧】线程池满了别只看“任务被拒绝”，先看队列在干嘛：队列无界时任务越积越多，内存先爆；队列有界时拒绝策略决定是抛错还是让调用线程自己跑。压测前先确认三件事——核心线程数、队列长度、拒绝策略，拒绝策略选 `CallerRunsPolicy` 时调用线程会自己执行任务，等于变相给上游限流，比直接抛错温和、但会拖慢上游，选之前想清楚谁来扛这份延迟。

【小技巧】高峰期先降采样、后降功能：日志、埋点、监控上报这类“写放大”的辅助流量，高峰时先把采样率从全量降到 1%，省下的磁盘和带宽比砍一个业务功能还多。原文的降级讲的是业务功能降级，辅助流量降级是更早一步——它不影响用户看到的功能，却能实打实腾出资源；压测报告里先看日志量占了多少带宽，再决定降级顺序。

【小技巧】读写分离后“刚写完就查不到”是预期行为，不是 bug：写走主库、读走从库，从库复制有延迟，提交完立刻刷新列表可能看不到自己的数据。落地时关键读（提交后跳回详情页）强制走主库，列表、统计这类可接受延迟的读再走从库；把“写后立刻读”当成一致性 bug 去修复制延迟，是拿错了药方。

【冷知识】高并发有个专门的名字叫 C10K 问题：1999 年 Dan Kegel 提出“一台服务器同时处理一万个连接”，当时主流做法是一个连接一个线程、一万个线程直接把内存和调度拖垮。这个问题逼出了事件驱动模型——Nginx、Node.js 都是这个思路的产物：一个线程靠 epoll 这类机制轮询大量连接，而不是一个连接配一个线程；今天的“单机扛多少并发”争论，根子还是它。

【冷知识】“Slashdot 效应”是最早的高并发事故名片：上世纪 90 年代，Slashdot 网站一推荐某个小网站，涌入的流量几分钟内就能把对方服务器冲垮，后来这类“被大站链接后瞬间涌入流量致服务不可用”就被叫作 Slashdot 效应。今天的秒杀、热搜冲榜、直播带货，本质上是同一件事换了个名字——流量不是匀速来的，是被某个事件突然点燃的，架构设计要按尖峰而不是按平均值算。

### 参考答案

1. 因为每一层手段都有代价和适用面：不算数就不知道缺口在哪一层；缓存是读多写少场景性价比最高的手段，先上；能接受延迟的写操作异步化，核心写链路保持同步；单服务、单库成为瓶颈时再拆分，拆分引入的分布式问题要同步有解法；降级是兜底不是常规手段，策略和开关要事先定好并演练。
2. 秒杀是瞬时尖峰加库存竞争，顺序是入口限流、库存预扣减、异步下单、数据库最终落库，不能让数据库直接面对尖峰；审批流高峰是白天集中加长链路，顺序是读写分离、流程推进异步化、核心链路优先保障、非核心降级或延后。特征不同，瓶颈层不同，所以顺序不同。
3. 总读 QPS 10000 时，90% 命中回源 1000，80% 命中回源 2000，回源压力翻一倍。命中率每掉 10 个点，回源压力大约翻一倍，所以缓存失效、热点 Key、大 Key 要当事故隐患管。

4. 8 × (1 + 100/20) = 48 线程。公式只是起点：等待/计算比要靠实测（压测看 CPU 利用率、队列深度、P99），混合负载要分池隔离；Java 21+ 虚拟线程每个任务一个线程，池大小不再是瓶颈，公式基本失去意义；队列长度和拒绝策略（背压）是公式之外的另一半，超载时由它们决定谁先说“不”。
