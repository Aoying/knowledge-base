# 高并发架构

## 1. 核心概念

高并发不是“堆机器”，而是“让每一层只承担它该承担的量”。一句话模型：**流量先被削峰和分流，剩下的量再被缓存、异步和拆分消化，实在扛不住的部分靠降级保住核心**。手段之间有先后顺序，乱序上手段等于白花钱：没做缓存就扩容，是用机器替缓存还债；没做限流就做降级，是等系统被打垮了才认输。

并发量先算清楚再动手：峰值 QPS、平均响应时间、并发数怎么互相推导，见 [容量估算](工程实践/容量估算.md)，不要凭感觉定机器数。

## 2. 分层手段全景

| 层 | 手段 | 解决什么 | 典型代价 |
|---|---|---|---|
| 入口层 | 限流、负载均衡 | 挡住超预期流量、把流量摊开 | 限流阈值要随容量复核，见 [限流熔断与降级](开发语言/Java/限流熔断与降级.md) |
| 缓存层 | 本地缓存、分布式缓存、多级缓存 | 把读请求挡在数据库之外 | 一致性与失效策略，见缓存相关篇 |
| 异步层 | 消息队列削峰填谷 | 把峰值摊到时间轴上 | 消费延迟、顺序与幂等，见 [Kafka-消息队列](消息队列/Kafka-消息队列.md) |
| 服务层 | 拆分、读写分离、无状态化 | 单点变多点、读压力分流 | 分布式事务与调用链变复杂 |
| 数据层 | 分库分表、索引优化 | 单库单表扛不住的量 | 跨库查询与事务，见分库分表篇 |
| 兜底层 | 降级、熔断、回滚 | 保住核心链路，其余可舍 | 降级策略要事先排练，不是现写 |

缓存算术（不是性能承诺，只是量级关系）：总读 QPS 10000、缓存命中率 90%，回源 QPS = 10000 × (1 − 0.9) = 1000。命中率每掉 10 个点，回源压力就翻一倍左右，所以缓存失效、热点 Key、大 Key 这三件事要当事故隐患管。

```python
total_qps, hit_rate = 10000, 0.9
print(round(total_qps * (1 - hit_rate)))  # 1000，回源 QPS
```

## 3. 典型场景

- **秒杀**：流量特征是瞬时尖峰 + 库存竞争。顺序是：入口限流 → 库存预扣减（缓存层）→ 异步下单（消息队列）→ 数据库只做最终落库。不要让数据库直接面对尖峰，也不要用“先查库存再扣减”这种两步操作去抢库存。
- **审批流高峰**：流量特征是白天集中 + 长链路（表单、附件、流程引擎、通知）。顺序是：读写分离（列表查询走从库）→ 流程推进异步化（通知、归档走消息队列）→ 核心链路（提交、审批动作）优先保障，非核心（统计、报表）降级或延后。审批动作本身要幂等，重复提交、重复审批靠状态机前置校验挡，见接口幂等相关篇。
- **报表与导出**：流量特征是少量请求、单个请求很重。不要和在线链路抢资源：独立服务或独立连接池、异步导出、结果文件化，禁止在线接口直接扫全表。

## 4. 组合顺序与适用边界

推荐的上手段顺序：

1. **先算数**：容量估算出峰值 QPS、带宽、存储、机器数，再决定缺口在哪一层。
2. **先缓存**：读多写少的系统，缓存是性价比最高的手段；缓存解决不了的再往下走。
3. **再异步**：能接受延迟的写操作（通知、日志、归档、统计）一律异步化，核心写链路保持同步。
4. **再拆分**：单服务、单库成为瓶颈时拆分；拆分引入的分布式问题（事务、一致性、调用链）要同步有解法，不要为拆而拆。
5. **最后降级**：降级是兜底，不是常规手段。降级策略、降级开关、降级后的用户提示要事先定好并演练，细节见限流与降级篇，本篇不重复抄。

适用边界：

- 读多写少 → 缓存优先；写多读少 → 异步与拆分优先；强一致要求 → 不要用“最终一致”那套手段硬套，先确认业务能不能接受延迟。
- 小系统不要上全套：日活几千的系统做分库分表和全链路降级，是提前支付大系统的复杂度。

## 5. 常见误区

- 机器数拍脑袋：不算 QPS、不算单机容量就扩容，扩完还是不知道瓶颈在哪。
- 缓存当银弹：缓存只挡读流量，写尖峰、库存竞争、长事务一概挡不住。
- 异步当万能：异步引入延迟、顺序、幂等、死信一串新问题，核心链路该同步的别异步。
- 降级现写现用：故障时才想降级策略，开关没经过演练等于没有开关。

## 6. 面试与自测

1. 高并发手段的上线顺序为什么是“先算数、先缓存、再异步、再拆分、最后降级”？
2. 秒杀和审批流高峰的流量特征有什么不同？各自的手段顺序为什么不一样？
3. 缓存命中率从 90% 掉到 80%，回源压力会怎么变？

### 参考答案

1. 因为每一层手段都有代价和适用面：不算数就不知道缺口在哪一层；缓存是读多写少场景性价比最高的手段，先上；能接受延迟的写操作异步化，核心写链路保持同步；单服务、单库成为瓶颈时再拆分，拆分引入的分布式问题要同步有解法；降级是兜底不是常规手段，策略和开关要事先定好并演练。
2. 秒杀是瞬时尖峰加库存竞争，顺序是入口限流、库存预扣减、异步下单、数据库最终落库，不能让数据库直接面对尖峰；审批流高峰是白天集中加长链路，顺序是读写分离、流程推进异步化、核心链路优先保障、非核心降级或延后。特征不同，瓶颈层不同，所以顺序不同。
3. 总读 QPS 10000 时，90% 命中回源 1000，80% 命中回源 2000，回源压力翻一倍。命中率每掉 10 个点，回源压力大约翻一倍，所以缓存失效、热点 Key、大 Key 要当事故隐患管。
