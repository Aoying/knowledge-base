# 国密与加密体系

## 1. 核心概念

加密体系先分清五件工具，各解决一个问题：

| 工具 | 解决什么 | 典型算法 |
|---|---|---|
| 对称加密 | 保密性，快，密钥分发难 | AES、SM4 |
| 非对称加密 | 密钥分发、签名，慢 | RSA、ECC、SM2 |
| 哈希 | 完整性、指纹，不可逆 | SHA-256、SM3 |
| 数字签名 | 身份可信 + 不可抵赖 | RSA 签名、SM2 签名 |
| 证书 | 公钥与身份绑定，CA 背书 | X.509 |

常见组合是混合加密：非对称协商/封装会话密钥，对称加密批量数据，哈希 + 签名保完整性和身份。TLS、落库加密、接口签名都是这套骨架的不同拼法。国密就是把骨架里的算法换成国产系列，动机是自主可控与金融合规；角色不变，换的是实现与标准。

## 2. 基础知识：国密四件套

- **SM2**：非对称算法，基于椭圆曲线，对位 RSA/ECC。用于数字签名、密钥交换、公钥加密；曲线参数与签名流程有自己的规范，不能拿普通 EC 密钥直接当 SM2 用。
- **SM3**：哈希算法，输出 256 位，对位 SHA-256。用于完整性校验、签名前的摘要、HMAC。
- **SM4**：对称分组算法，分组和密钥都是 128 位，对位 AES。只定义分组本身，安全性很大程度取决于工作模式（见第 3 节）。
- **SM9**：基于标识的密码算法，身份字符串直接当公钥、省掉证书管理，场景窄，日常项目基本碰不到。
- **ZUC（祖冲之）**：流密码，用于通信领域的加密与完整性保护，普通后端只在特定通信系统里遇到。

选型速记：加解密走 SM4；签名、验签、密钥协商走 SM2；摘要走 SM3。「全站国密改造」的落点通常是传输层换国密 TLS + 敏感数据 SM4 落库 + 签名换 SM2/SM3。

## 3. 进阶知识：模式与组合取舍

分组密码必须选工作模式，选错等于没加密：

- **ECB**：同明文出同密文，轮廓都藏不住，**禁止用于业务数据**。
- **CBC**：链式依赖，需要随机 IV；不带完整性校验，要自己配 HMAC/签名防篡改；IV 必须随机、不可预测，不能复用或写死。
- **GCM**：加密同时出认证标签（AEAD），自带防篡改，新项目首选；代价是同一密钥下 nonce 绝不能重复，重复直接击穿安全性。

其他组合口径：

- **填充**：CBC 等模式需 PKCS#7 填充补齐分组；填充报错别原样回给调用方（填充预言攻击靠区分报错逐字节试）。
- **签名组合**：SM2 是「先 SM3 摘要再签」，且要混入用户标识（ID），两端 ID 不一致验签必失败。
- **密钥分开用**：加密、签名、校验各用各的，一把包打天下出事时无法单独轮换。

## 4. 原理剖析

**SM2 签名为什么和 ECDSA 不能互换**：SM2 把公钥、曲线参数和用户 ID 一起杂凑成值 Z 再参与签名，验签端必须用同样的 ID 和参数重算。ID 默认值不同是联调最常见的验签失败原因。

**SM2 密文的组成**：公钥加密结果由三段拼成——曲线点 C1、密文 C2、校验段 C3。历史上存在两种拼接顺序（见第 7 节），不协商好就是「算法都对、数据解不开」。

**证书与双证书**：一张做签名验身份，另一张做密钥交换/解密，对应「签名私钥绝不出设备、加密私钥可托管备份」的口径，也是国密 TLS 用双证书的原因（见第 6 节）。

## 5. 实战应用：Java 落地

JDK 自带 JCE 对国密支持不完整，Java 侧事实标准是 BouncyCastle（BC）。Maven 引 `org.bouncycastle:bcprov-jdk18on`，启动时注册一次：

```java
static {
    Security.addProvider(new BouncyCastleProvider());
}
```

**SM4 加解密（CBC，密钥与 IV 从密钥管理处取，不写死）**：

```java
public static String sm4Encrypt(String plain, byte[] key, byte[] iv) throws Exception {
    Cipher cipher = Cipher.getInstance("SM4/CBC/PKCS7Padding", "BC");
    cipher.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(key, "SM4"), new IvParameterSpec(iv));
    return Base64.getEncoder().encodeToString(cipher.doFinal(plain.getBytes(StandardCharsets.UTF_8)));
}
public static String sm4Decrypt(String base64, byte[] key, byte[] iv) throws Exception {
    Cipher cipher = Cipher.getInstance("SM4/CBC/PKCS7Padding", "BC");
    cipher.init(Cipher.DECRYPT_MODE, new SecretKeySpec(key, "SM4"), new IvParameterSpec(iv));
    return new String(cipher.doFinal(Base64.getDecoder().decode(base64)), StandardCharsets.UTF_8);
}
```

新项目优先 `SM4/GCM/NoPadding`：nonce 随机生成后与密文一起存，解密时一并取出。

**SM2 签名与验签（SM3withSM2）**：

```java
KeyPairGenerator kpg = KeyPairGenerator.getInstance("EC", "BC");
kpg.initialize(new ECGenParameterSpec("sm2p256v1"), new SecureRandom());
KeyPair kp = kpg.generateKeyPair();
Signature signer = Signature.getInstance("SM3withSM2", "BC");
signer.initSign(kp.getPrivate());
signer.update(data);
byte[] sign = signer.sign();
Signature verifier = Signature.getInstance("SM3withSM2", "BC");
verifier.initVerify(kp.getPublic());
verifier.update(data);
boolean ok = verifier.verify(sign);
```

联调口径：密钥对、曲线、算法名三处与对端对齐；验签失败先查用户 ID 与签名编码格式，不要先怀疑算法。

## 6. 实战应用：银行场景

**敏感字段落库加密（AOP 模式）**。身份证号、手机号、银行卡号这类字段，口径是「库里存密文、日志不打明文、查询按需解密」。ao 在重庆文旅项目里用过 AOP 切面加解密，这套模式可直接复用：注解标字段、切面统一处理，业务代码不感知。

```java
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface SensitiveField { }   // 标在实体/DTO 的敏感字段上
// 切面：入库前遍历参数对象，标注字段 -> SM4 加密；查询返回后解密回明文。
// 密钥从配置中心/加密机取，不进代码。
```

注意：加密后模糊查、排序都废，精确查另存 SM3 摘要列做索引；密文比明文长，列宽预留；解密失败抛异常并告警。

**传输层：国密 TLS 与双证书**。握手时服务端出示两张证书——签名证书验身份、加密证书协商会话密钥，其余与普通 TLS 无异，差别在算法套件与证书体系。Java 侧原生支持有限，实际项目多靠国密浏览器、专用网关或密码厂商中间件终结握手，后端通常不直接处理。

**加密机 / HSM 为什么银行不用纯软件存密钥**：软件存密钥，密钥躺在应用服务器内存和配置里，主机失陷即全盘皆输；加密机是专用硬件，私钥在设备内生成、使用不出设备，只对外提供运算接口，并满足审计与合规要求。开发口径：本地与测试用 BC 跑通逻辑，生产走加密机，两套配置分开管。

## 7. 密钥管理：KMS、信封加密与轮换

本篇第 2–5 节讲了算法与落地代码，这一节补算法之外的另一半：密钥本身怎么生成、存、分发、轮换、作废。算法再对，密钥躺在代码里等于没加密；第 5 节代码里“密钥与 IV 从密钥管理处取，不写死”指的就是本节的机制。

### 7.1 KMS 与信封加密

密钥分两层，职责分开：

- **KEK（密钥加密密钥，主密钥）**：只用来加密别的密钥，不直接加密业务数据；存在 KMS 或加密机里，应用服务器上不出现 KEK 明文。
- **DEK（数据加密密钥）**：真正加密业务数据的密钥；可以每个字段、每条记录不同，泄露一个 DEK 只影响局部。

信封加密流程（“信封”指 DEK 被 KEK 加密后像装进信封一样随数据走）：

1. 向 KMS 申请 DEK：KMS 生成 DEK 明文，同时用 KEK 加密出一份密文 DEK，一并返回。
2. 用 DEK 明文加密业务数据，用完立即丢弃 DEK 明文（内存里短暂存在，不落盘、不记日志）。
3. 存储时把业务密文和密文 DEK 一起存；解密时反向走：拿密文 DEK 找 KMS 解出 DEK 明文，解密数据，再丢弃。
4. 好处：KEK 不动，DEK 可频繁更换；KMS 只见 DEK，不见业务数据；业务系统扩容时不用同步分发密钥。

国密算法在这里的位置（原理见本篇第 2 节，这里只讲分工）：DEK 用 SM4（对称、快，适合批量数据）；KEK 的封装、协商用 SM2（非对称，适合包密钥）；完整性校验用 SM3。与第 6 节加密机的关系：KMS 可以是软件服务加 HSM 托管 KEK，生产口径是 KEK 进 HSM、应用只调 KMS 接口。

### 7.2 轮换流程与注意事项

轮换分两类，别混为一谈：

- **KEK 轮换**：主密钥换代；旧 KEK 保留解密能力，直到所有密文 DEK 完成重封装，确认无旧封装残留后再作废。
- **DEK 轮换**：数据重加密；量大，分批跑、可断点续跑，别停服全量重写。

标准流程四步：新密钥生成 → 双轨期（新旧并存，新写用新密钥、旧读仍可用）→ 存量重加密／重封装（后台分批）→ 旧密钥标记作废（先禁用、观察期后再删除，删除不可逆）。

注意事项：

- **版本字段必备**：每份密文要带密钥版本（密钥 id），解密时靠它选密钥；没有版本标记，轮换后一半数据不知道用哪把解。
- **触发条件双轨**：定期轮换（周期按数据敏感度定）加事件触发（人员离职、疑似泄露、审计要求），只定周期不定事件等于泄露了还按表走。
- **轮换前备好回滚**：备份旧密钥与映射关系，轮换失败能按版本回退；最怕的是一半数据用新密钥加密、一半旧密钥且无版本标记，进退两难。
- 与安全架构的呼应：安全架构纵深防御清单里的“密钥泄露轮换流程”指的就是本节流程，轮换不是删密钥，是走完双轨、重加密、作废三步才算完。

### 7.3 密钥与配置分离

三条线，违反任何一条都等于把密钥公开：

- **代码里不出现密钥**：密钥、IV、口令都不硬编码；第 5 节示例代码的参数来自密钥管理处，不是写在源码里。
- **配置文件里不出现生产密钥明文**：配置文件只放 KMS 地址、密钥 id／别名；敏感值走密钥服务或加密配置，配置文件本身进版本库也不怕。
- **日志与异常里不打密钥明文**：与本篇第 8 节（疑难杂症）“报错不透传细节”同一口径，密钥明文一旦进日志就等于进了所有能看日志的系统。

检查方法：提交前扫描密钥模式（高熵字符串、私钥头、访问密钥样式）；泄露应急是立即轮换加评估泄露窗口内的数据影响加吊销旧密钥，不要只删代码里的密钥就当解决。

### 7.4 保管分级

- **环境隔离**：开发、测试、生产三套密钥，互不通用；测试数据用测试密钥加密，生产密钥不出生产网络；第 6 节“本地与测试用 BouncyCastle 跑通逻辑、生产走加密机，两套配置分开管”就是这一条的落地。
- **人员分离**：管密钥的人（创建密钥、审批轮换）与用密钥的业务账号分离；生产 KEK 的每次使用要审批并记审计日志（谁、何时、调了哪个密钥操作）。
- **备份与 KEK 本身同等重要**：KEK 备份要加密后异地存，备份的访问控制与 KEK 一致；丢了 KEK 等于丢了所有用它封装的数据，备份不是“有就行”，是“丢了能恢复、偷了打不开”才算合格。

## 8. 疑难杂症

- **SM2 密文死活解不开**：先查拼接顺序。老顺序 C1C2C3、新规范推荐 C1C3C2，不一致直接失败。BC 的 SM2 引擎有对应模式可切换，联调先把顺序写进接口文档，别靠试。
- **验签总失败但密钥无误**：查用户 ID。BC、硬件设备、各厂商 SDK 的默认 ID 可能不同，必须显式设成两端约定的同一个值。
- **密文存库后解出乱码**：编码层问题。密文字节流必须统一一种编码（Hex 或 Base64 二选一），常见翻车是中途被当 UTF-8 字符串转了一道，不可逆地丢字节。
- **同一明文每次密文不同被当 bug**：CBC/GCM 带随机 IV 本就该每次不同；拿密文做等值判断的需求改走摘要列。
- **解密报错透传前端**：填充错误、格式错误分开报等于给攻击者递梯子（填充预言攻击）。对外统一文案，细节留日志。

## 9. 性能优化

量级判断即可：对称加密（SM4/AES）最便宜，字段级加解密对接口耗时的影响通常在噪声范围内，慢先怀疑网络和数据库。非对称运算（SM2）比对称贵一到两个数量级，只用它做签名与密钥封装，不加密大字段。哈希（SM3）成本接近对称，可放心用在摘要索引上。优化先看两点：`Cipher`、`Signature` 不要在高频路径反复初始化；批量数据走流式。生产走加密机时，设备吞吐和网络往返才是上限，压测要带真实链路。

## 10. 版本差异

- **BouncyCastle 版本线**：`bcprov-jdk15on` 是老坐标，新项目用 `bcprov-jdk18on`；不同版本 SM2 引擎的默认密文顺序有差异，升级后必须回归与对端的互通，不能当无痛升级。
- **国密标准本身**：SM2 密文顺序的推荐做法新旧规范不同（见第 7 节），对接老系统以对端实际格式为准。
- **运行环境**：国产化环境（国产 JDK、TongWeb 等）可能自带国密提供者，与 BC 同时注册时注意优先级，避免同名算法被静默换了实现。

## 小技巧与冷知识

【小技巧】SM4 密钥必须是 16 字节，报错先数密钥长度：128 位密钥等于 16 字节，密钥从配置里取出来少一位、多一位，`Cipher.init` 直接抛 `InvalidKeyException`。联调时密钥常以 Hex 或 Base64 字符串形态流转，32 个 Hex 字符等于 16 字节、24 个 Base64 字符也等于 16 字节，解码前先数清字符数，比盯着算法名排查快得多。

【小技巧】固定 IV 只许出现在单元测试里：测试时用写死的 IV 和密钥，密文每次都一样，才能对加密结果做断言；生产代码一律用 `SecureRandom` 现场生成 IV。最容易翻车的写法是把测试代码里的固定 IV 复制进生产——原文第 3 节说了 IV 不能复用，测试用的确定性恰恰是生产要避开的坑，两套代码的 IV 来源要分开写。

【小技巧】IV/nonce 别另开字段存，直接拼在密文前面：GCM 的 nonce 一般 12 字节、CBC 的 IV 是 16 字节，加密时把这段随机值放密文最前面、解密时先按固定长度切出来再解密。原文第 5 节只说了“nonce 与密文一起存”，拼在同一字段是最省事的存法——字段数不增加，解密方也不用猜 nonce 藏在哪个配置里。

【小技巧】GCM 解密失败别当普通异常重试：认证标签对不上时抛的是 `AEADBadTagException`，意思是“密文被改过或密钥不对”，不是网络抖动能修好的问题。重试只会原样再失败一次，正确动作是记日志告警、按原文第 8 节的口径对外只给统一文案；把它和普通解密失败混在一起，等于把“数据被篡改”的信号当成偶发故障放过去了。

【小技巧】密文要进 URL 或 JSON 时别用标准 Base64：标准 Base64 里的 `+`、`/`、`=` 在 URL 里会被转义或截断，拼进查询参数就变了样。要么改用 URL 安全的 Base64 变体（`+`/`/` 换成 `-`/`_`、去掉末尾 `=`），要么像原文第 8 节说的那样统一用 Hex；编码方式是接口约定的一部分，联调前先写进文档，别等乱码了再猜是哪一端转了码。

【小技巧】SM2 签名跨语言对接先对齐编码格式：同样一对 r、s，BouncyCastle 默认打成 DER 编码的 ASN.1 结构，有些语言或硬件设备却要 raw 格式（r 和 s 各 32 字节直接拼接）。原文第 5 节只提了“签名编码格式”要对齐，落到实处就是先问对端要 DER 还是 raw——格式不对，签名值本身再正确也验不过。

【冷知识】国密算法名字里的 SM 是“商密”两个字的拼音首字母：SM2、SM3、SM4 分别对应商用密码行业标准 GM/T 0003、GM/T 0004、GM/T 0002，ZUC 则对应 GM/T 0001。标准号本身就是速查表——对接时说不清算法细节，先报标准号，对端就知道你在说哪一份规范。

【冷知识】SM4 原名 SMS4，2006 年公开，2012 年以 SM4 之名写入商密行业标准 GM/T 0002：SMS4 里的 SMS 就是“SM4”的旧写法，算法本身没变，改的是名字和标准身份。老系统文档里看到 SMS4 别当成另一种算法，它和 SM4 是同一个分组密码，只是叫法停在 2012 年之前。

- SM2 密文解不开、验签失败，排查顺序是什么？
- 落库加密后精确查询怎么做？密钥为什么不能跟应用放一起？

### 参考答案

1. 对称加密解决保密性（快、密钥分发难，如 AES、SM4）；非对称加密解决密钥分发与签名（慢，如 RSA、ECC、SM2）；哈希解决完整性与指纹（不可逆，如 SHA-256、SM3）；数字签名解决身份可信与不可抵赖（如 RSA 签名、SM2 签名）；证书解决公钥与身份绑定（CA 背书，如 X.509）。TLS 要组合用是因为单件工具只解决一个问题：非对称协商或封装会话密钥，对称加密批量数据，哈希加签名保完整性和身份，这就是混合加密骨架。
2. SM2 对位 RSA/ECC，是基于椭圆曲线的非对称算法，用于数字签名、密钥交换、公钥加密；SM3 对位 SHA-256，是输出 256 位的哈希算法，用于完整性校验、签名前的摘要、HMAC；SM4 对位 AES，是分组和密钥都是 128 位的对称分组算法，用于加解密。速记：加解密走 SM4，签名、验签、密钥协商走 SM2，摘要走 SM3。
3. ECB 同明文出同密文，轮廓都藏不住，禁止用于业务数据。CBC 是链式依赖，需要随机 IV，不带完整性校验，要自己配 HMAC 或签名防篡改，IV 必须随机、不可预测、不能复用或写死。GCM 加密同时出认证标签（AEAD），自带防篡改，新项目首选；代价是同一密钥下 nonce 绝不能重复，重复直接击穿安全性。
4. 排查顺序：密文解不开先查拼接顺序，老顺序 C1C2C3、新规范推荐 C1C3C2，不一致直接失败，BC 的 SM2 引擎有对应模式可切换，联调先把顺序写进接口文档。验签失败先查用户 ID（BC、硬件设备、各厂商 SDK 的默认 ID 可能不同，必须显式设成两端约定的同一个值），再查曲线、算法名与签名编码格式；不要先怀疑算法。密文存库后解出乱码则查编码层，密文字节流必须统一一种编码（Hex 或 Base64 二选一）。
5. 加密后精确查询不能直接对密文做等值判断（CBC/GCM 带随机 IV 时同一明文每次密文都不同），做法是另存 SM3 摘要列做索引；模糊查与排序同样废掉，要提前跟业务确认。密钥不能跟应用放一起：软件存密钥时密钥躺在应用服务器内存和配置里，主机失陷即全盘皆输；生产应走加密机（私钥在设备内生成、使用不出设备，只对外提供运算接口），本地与测试用 BouncyCastle 跑通逻辑，两套配置分开管。
