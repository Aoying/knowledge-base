# 事件驱动架构与 CQRS、事件溯源

三个概念常一起出现，但解决的问题不同：事件驱动架构解决服务间怎么通信，CQRS 解决读写模型怎么分工，事件溯源解决状态怎么存储。三者可以独立采用，也可以组合。

## 1. 事件驱动架构（EDA）

核心就一句话：已经发生的事，以事件的形式广播出去，谁关心谁消费。

### 1.1 基本角色

- 事件：已经发生的事实，用过去时命名，如 `OrderCreated`、`PaymentSucceeded`。事件一旦发出就不可变，错了只能再发一个纠正事件，不能改历史。
- 生产者：只负责发事件，不关心谁在消费，也不知道消费者的数量。发完即走，不等消费结果。
- 事件总线 / Broker：Kafka、RocketMQ 这类消息中间件，负责存储与投递事件。生产者和消费者都只跟 Broker 打交道，彼此不直连。
- 消费者：订阅自己关心的事件类型，独立部署、独立扩容。

### 1.2 好处与代价

好处：

- 解耦：新增一个消费者（比如加个短信通知服务）不用改生产者代码。
- 削峰：消费速度跟不上时事件先在 Broker 里排队，生产者不受影响。
- 可回放：事件有留存，出了问题可以重放事件复现、修复下游状态。

代价：

- 最终一致性：事件投递有延迟，下游状态不是实时一致的。要求强一致的场景（比如扣库存后立刻要读到结果）不能只靠事件。
- 调试变难：一次业务操作散成多条事件，排查要跨服务串事件链路，事件里必须带全局追踪 ID 和业务主键。
- 顺序与重复：见第 5 节，消费端必须自己处理。

### 1.3 什么时候不用

- 简单的请求-响应：查个用户信息、调个校验接口，直接同步调用，别绕事件。
- 强一致事务：跨服务必须同时成功或同时失败的，用分布式事务或 Saga 的补偿思路，别指望事件本身保证原子性。
- 内部模块通信：同一个服务内的模块调用，走函数调用，别为了“事件化”而事件化。

## 2. CQRS：命令与查询分离

CQRS 是 Command Query Responsibility Segregation 的缩写：写操作和读操作用不同的模型。

### 2.1 为什么分

一个模型同时服务读写，迟早顾此失彼：写模型要承载业务规则、聚合不变性；读模型要服务各种查询（列表、统计、多表拼接），两者对数据结构的要求正好相反。分开后：

- 写模型：以聚合为中心，只处理命令（CreateOrder、CancelOrder），保证业务规则，结构贴近领域。
- 读模型：以查询为中心，可以是宽表、物化视图、搜索引擎索引，怎么查得快就怎么建，不用顾及写规则。
- 同步：写侧产生变更后，通过事件投影（Projection）更新读模型。投影可以重建：读模型坏了，删了重跑一遍事件就能恢复。

### 2.2 代价

- 两套模型，两份维护成本，还有投影逻辑本身。
- 读模型有滞后：写完立刻读可能读到旧数据，调用方要能接受这个窗口，或者对关键查询走写侧直读。
- 不是所有系统都需要：读写负载差不多、查询也不复杂的 CRUD 系统，上 CQRS 是纯负担。

### 2.3 适用判断

同时满足两条再考虑：第一，读的压力或查询复杂度明显高于写；第二，业务上能接受读模型短暂滞后。只满足一条的，先只做读写分离（主从）或只做读模型缓存，别全套上。

## 3. 事件溯源（Event Sourcing）

传统做法只存当前状态；事件溯源反过来：只存事件序列，当前状态是把事件按顺序折叠（Fold）出来的。

### 3.1 关键点

- 事件日志是事实来源：状态可以丢，事件不能丢；状态丢了重放事件就能重建。
- 重放的用途：修复下游 bug 后重算、生成新的读模型、审计（谁在什么时候做了什么，事件序列本身就是审计日志）。
- 快照：事件攒到几千上万条后，每次重放都从头算太慢。定期存一个快照（某个版本号对应的状态），重放时从快照往后算。快照只是加速手段，不是事实来源，丢了可以重建。

### 3.2 版本演进

事件结构会变，处理办法：

- 只加字段，不改旧字段语义；消费者读事件时容忍未知字段。
- 每个事件带版本号，消费端按版本分支处理，或者写一个 Upcaster：读到旧版事件先升级成新版再处理。
- 绝不原地修改已入库的事件。实在要改语义，发一个新版本事件，旧事件保留。

### 3.3 代价

- 查询当前状态要重放，简单查询也变复杂，通常要配合 CQRS 的读模型一起用。
- 事件量会膨胀：高频变更的聚合，事件表增长很快，要有归档与快照策略。
- 团队要适应“状态是算出来的”这个思维转变，排错方式也变了（查事件序列而不是查当前行）。

## 4. 三者组合关系

| 组合 | 含义 |
|---|---|
| 只用 EDA | 服务间用事件通信，状态仍用传统表存。最常见，成本最低。 |
| EDA + CQRS | 写侧发事件，读侧投影成读模型。读写分离，状态仍传统存。 |
| EDA + CQRS + 事件溯源 | 写侧只存事件，读侧由事件投影出来。全套，成本最高，收益也最大。 |

记住：CQRS 不要求事件溯源（写侧可以用传统表 + 变更事件）；事件溯源也不要求 CQRS（可以重放后直接对外服务，但通常很慢）。按需组合，别全套照搬。

## 5. 落地注意

### 5.1 幂等消费

Broker 至少投递一次（At-least-once）是常态，消费者一定会收到重复事件。做法：事件带全局唯一 ID，消费端用一张已处理事件表（事件 ID 做唯一键）去重，先落库去重记录再执行业务，或者业务写操作本身用唯一键保证重复执行无副作用。

```python
# 幂等消费示意：已处理事件 ID 表（生产用数据库唯一键，不要用内存 set）
processed_ids = set()

def consume(event):
    if event["id"] in processed_ids:
        return "duplicate, skipped"
    processed_ids.add(event["id"])
    # ... 执行业务逻辑 ...
    return "processed"

events = [
    {"id": "evt-001", "type": "OrderCreated", "order_id": 101},
    {"id": "evt-001", "type": "OrderCreated", "order_id": 101},  # 重复投递
    {"id": "evt-002", "type": "PaymentSucceeded", "order_id": 101},
]
print([consume(e) for e in events])
# 输出：['processed', 'duplicate, skipped', 'processed']
```

### 5.2 顺序

- 同一个聚合（同一个订单）的事件顺序必须保证：做法是按聚合 ID 做分区键，同一分区内的事件按序投递、按序消费。
- 跨聚合不保证全局顺序：别写依赖“订单事件一定先于库存事件到达”的逻辑。
- 消费端并发会破坏顺序：一个分区只能一个消费者实例在处理，想提速靠加分区，不靠同分区内多线程。

### 5.3 死信队列

消费失败不要无限重试：重试几次（比如 3 次，带退避间隔）仍失败的，扔进死信队列（DLQ），同时告警。死信要有人看：定期巡检、定位原因（脏数据、版本不兼容、下游挂了）、修复后手动重投。死信无人看等于静默丢数据。

### 5.4 事件版本兼容

- 生产者：只加字段，不删字段、不改字段含义；大改就发新版本事件。
- 消费者：解析时忽略未知字段，别因为多了一个字段就报错。
- 事件命名与 Schema 要有治理：事件名、字段含义、版本号集中登记，改动先评审，别让各服务各发各的。

### 5.5 常见坑

- 事件里只带 ID 不带数据：消费者每次都要回查生产者，生产者一挂全链路都卡。事件里带消费端需要的关键数据快照，ID 回查只做补充。
- 事件当命令用：事件是“已经发生的事”，不是“请你做某事”。把命令伪装成事件，消费者改名、改语义都会炸。
- 没有追踪 ID：事件跨服务流转，排查全靠业务主键和时间戳，效率极低。事件信封里固定带 traceId。

## 面试与自测

1. 事件驱动架构带来最终一致性，什么场景不能只靠事件？
2. CQRS 的读模型为什么会有滞后？调用方怎么应对？
3. 事件溯源里快照丢了怎么办？为什么说快照不是事实来源？

### 参考答案

1. 要求强一致的场景不能只靠事件，比如扣库存后必须立刻读到最新库存、支付成功后必须立刻放行订单。事件投递有延迟，下游状态在窗口期内是旧的，这类场景要走同步调用或分布式事务，事件只做后续通知。
2. 读模型由写侧事件投影生成，投影是异步的，写完到投影完成之间有窗口期。应对办法：关键查询走写侧直读，或者调用方接受短暂旧数据（比如列表页），或者前端用写操作的返回结果先行展示。
3. 快照丢了可以重建：从头重放事件序列就能算出最新状态，只是慢一点。快照只是某个版本号的状态缓存、用来加速重放，事实来源始终是事件日志本身，所以快照不是事实来源。
