# 运维实战脚本

> 5 个生产级脚本，贴合 Java 后端栈（Spring Boot 2.7.3 + MySQL/OceanBase MySQL 模式）。每个脚本都可直接跑，改变量即用。
>
> 通用约定：全部以 `set -euo pipefail` 起手，关键变量用 `${VAR:?提示}` 判空；不要把密码、密钥、真实主机写进脚本，敏感信息走环境变量或 `~/.my.cnf`、`~/.ssh/config`。
>
> 前置知识：[工程实践/Shell/Linux与Shell.md](工程实践/Shell/Linux与Shell.md)；脚本写法规范见 [[生产级Shell脚本]]。

## 1. Java 服务部署、重启与健康检查

备份旧包 → 部署新包 → 启动 → 轮询 actuator 健康端点，超时自动回滚旧包。

前置：Spring Boot 需暴露健康端点（`management.endpoints.web.exposure.include=health`），健康地址为 `http://127.0.0.1:端口/actuator/health`。

```bash
#!/usr/bin/env bash
# deploy.sh：部署 jar 包，健康检查失败自动回滚
set -euo pipefail

APP_NAME="${APP_NAME:?请设置服务名，如 APP_NAME=billing}"
NEW_JAR="${NEW_JAR:?请设置新包路径，如 NEW_JAR=/tmp/app-1.2.0.jar}"
APP_DIR="${APP_DIR:-/data/app}"
PORT="${PORT:?请设置服务端口，如 PORT=8080}"
HEALTH_URL="http://127.0.0.1:${PORT}/actuator/health"
MAX_WAIT="${MAX_WAIT:-60}"          # 最长等待秒数
JAVA_OPTS="${JAVA_OPTS:- -Xms512m -Xmx1024m}"

PID_FILE="${APP_DIR}/${APP_NAME}.pid"
BACKUP_DIR="${APP_DIR}/backup"
TIMESTAMP="$(date +%Y%m%d%H%M%S)"

mkdir -p "${BACKUP_DIR}"

stop_app() {
    if [[ -f "${PID_FILE}" ]]; then
        local pid
        pid="$(cat "${PID_FILE}")"
        if kill -0 "${pid}" 2>/dev/null; then
            kill "${pid}"
            for _ in $(seq 1 15); do
                kill -0 "${pid}" 2>/dev/null || break
                sleep 1
            done
            kill -9 "${pid}" 2>/dev/null || true
        fi
        rm -f "${PID_FILE}"
    fi
}

start_app() {
    local jar="$1"
    nohup java ${JAVA_OPTS} -jar "${jar}" > "${APP_DIR}/${APP_NAME}.log" 2>&1 &
    echo $! > "${PID_FILE}"
}

wait_healthy() {
    local waited=0
    while [[ "${waited}" -lt "${MAX_WAIT}" ]]; do
        if curl -fsS --max-time 3 "${HEALTH_URL}" | grep -q '"status":"UP"'; then
            return 0
        fi
        sleep 2
        waited=$((waited + 2))
    done
    return 1
}

[[ -f "${NEW_JAR}" ]] || { echo "新包不存在：${NEW_JAR}"; exit 1; }

# 1. 备份旧包（有旧包才备份）
if [[ -f "${APP_DIR}/${APP_NAME}.jar" ]]; then
    cp "${APP_DIR}/${APP_NAME}.jar" "${BACKUP_DIR}/${APP_NAME}-${TIMESTAMP}.jar"
    echo "旧包已备份：${BACKUP_DIR}/${APP_NAME}-${TIMESTAMP}.jar"
fi

# 2. 停旧、部署新包、启动
stop_app
cp "${NEW_JAR}" "${APP_DIR}/${APP_NAME}.jar"
start_app "${APP_DIR}/${APP_NAME}.jar"

# 3. 健康检查，失败则回滚
if wait_healthy; then
    echo "部署成功，健康检查通过：${HEALTH_URL}"
else
    echo "健康检查超时，开始回滚"
    stop_app
    latest_backup="$(ls -t "${BACKUP_DIR}/${APP_NAME}-"*.jar 2>/dev/null | head -n 1 || true)"
    if [[ -n "${latest_backup}" ]]; then
        cp "${latest_backup}" "${APP_DIR}/${APP_NAME}.jar"
        start_app "${APP_DIR}/${APP_NAME}.jar"
        echo "已回滚到：${latest_backup}，请人工确认健康状态"
    else
        echo "无旧包可回滚，服务处于停止状态，请人工介入"
    fi
    exit 1
fi
```

- 说明：`wait_healthy` 轮询 `{"status":"UP"}`，不是只看进程在不在；进程在但 Spring 还没起好、数据库连不上时，actuator 会返回非 UP，正好拦住带病上线。
- 验证点：正常部署后 `curl http://127.0.0.1:端口/actuator/health` 返回 UP；故意给一个坏包（起不来或健康端点非 UP），脚本应退出 1 且旧包被恢复启动。
- 坑：
  - `kill -0` 判活后 `kill` 再等 15 秒，最后 `kill -9` 兜底——直接 `kill -9` 会丢正在处理的请求，能优雅停就别硬杀。
  - 回滚只认 `backup/` 里最新的包，备份目录要定期清理，不然磁盘会被旧包打满。
  - `JAVA_OPTS` 不加引号是故意的（要拆成多个 JVM 参数）；但它只能来自你自己的环境变量，不能来自外部输入。

## 2. 日志归档与磁盘空间巡检

按天归档压缩 7 天前的日志，归档保留 30 天；磁盘水位超阈值发告警。

```bash
#!/usr/bin/env bash
# log_rotate_check.sh：日志归档 + 磁盘水位巡检
set -euo pipefail

LOG_DIR="${LOG_DIR:?请设置日志目录，如 LOG_DIR=/data/app/logs}"
ARCHIVE_DIR="${ARCHIVE_DIR:-/data/app/logs-archive}"
ARCHIVE_DAYS="${ARCHIVE_DAYS:-7}"       # 归档 N 天前的日志
RETENTION_DAYS="${RETENTION_DAYS:-30}"  # 归档保留天数
THRESHOLD="${THRESHOLD:-80}"            # 磁盘使用率告警阈值（%）
WEBHOOK_URL="${WEBHOOK_URL:-https://WEBHOOK_URL_PLACEHOLDER}"

mkdir -p "${ARCHIVE_DIR}"

# 1. 归档：7 天前的 .log 打包压缩，成功后删原文
while IFS= read -r -d '' logfile; do
    day="$(date -d "@$(stat -c %Y "${logfile}")" +%Y%m%d)"
    mkdir -p "${ARCHIVE_DIR}/${day}"
    if gzip -c "${logfile}" > "${ARCHIVE_DIR}/${day}/$(basename "${logfile}").gz"; then
        rm -f "${logfile}"
        echo "已归档：${logfile}"
    else
        echo "归档失败，保留原文：${logfile}" >&2
    fi
done < <(find "${LOG_DIR}" -maxdepth 1 -type f -name '*.log' -mtime "+${ARCHIVE_DAYS}" -print0)

# 2. 清理：删除 30 天前的归档
find "${ARCHIVE_DIR}" -type f -name '*.gz' -mtime "+${RETENTION_DAYS}" -delete

# 3. 磁盘水位巡检（只看日志盘所在分区）
usage="$(df -P "${LOG_DIR}" | awk 'NR==2 {gsub(/%/, "", $5); print $5}')"
echo "磁盘使用率：${usage}%（阈值 ${THRESHOLD}%）"
if [[ "${usage}" -ge "${THRESHOLD}" ]]; then
    msg="告警：${LOG_DIR} 所在分区使用率 ${usage}%，超过阈值 ${THRESHOLD}%"
    echo "${msg}" >&2
    if [[ -n "${WEBHOOK_URL}" && "${WEBHOOK_URL}" != "https://WEBHOOK_URL_PLACEHOLDER" ]]; then
        curl -fsS --max-time 10 -X POST -H 'Content-Type: application/json' \
            -d "{\"text\":\"${msg}\"}" "${WEBHOOK_URL}" || echo "告警发送失败" >&2
    else
        echo "未配置真实 webhook，只打印告警不外发" >&2
    fi
fi
```

- 说明：归档用 `gzip -c > 目标` 再删原文，压缩失败不删原文；`find -print0` + `read -d ''` 防止文件名含空格断裂。
- 验证点：往日志目录放一个 `mtime` 改成 8 天前的文件，跑一遍应出现在归档目录且原文消失；`df` 水位手工改阈值为 1 应触发告警分支（占位 webhook 下只打印不外发）。
- 坑：
  - `find -mtime +7` 是“严格大于 7×24 小时”，不是“7 天前那天”，别按自然日理解。
  - 正在被应用写着的日志不要归档：本脚本只动 `mtime` 超过 7 天的文件，现役日志一般每天滚动，天然避开；如果你的日志不滚动，先上 logrotate 或按天切分再归档。
  - `df -P` 保证单行输出，`awk NR==2` 才取得到正确行；不加 `-P` 在长挂载点下会折行取错。

## 3. 批量 SSH 执行与文件同步

主机列表文件 + 密钥登录 + 并行执行 + rsync 同步 + 失败主机汇总。

主机列表格式（`hosts.txt`，`#` 开头为注释）：

```text
# 每行一台：主机占位，实际使用时替换
app-server-01.example.com
app-server-02.example.com
```

```bash
#!/usr/bin/env bash
# batch_ssh.sh：在多台主机上批量执行命令并同步文件
set -euo pipefail

HOSTS_FILE="${HOSTS_FILE:?请设置主机列表，如 HOSTS_FILE=./hosts.txt}"
SSH_USER="${SSH_USER:?请设置 SSH 用户，如 SSH_USER=app}"
SSH_KEY="${SSH_KEY:?请设置私钥路径，如 SSH_KEY=~/.ssh/id_rsa}"
REMOTE_CMD="${REMOTE_CMD:-uptime}"      # 远程执行的命令
LOCAL_FILE="${LOCAL_FILE:-}"             # 为空则不同步文件
REMOTE_PATH="${REMOTE_PATH:-/tmp/}"     # 同步目标目录
PARALLEL="${PARALLEL:-5}"                # 并行度
LOG_DIR="${LOG_DIR:-./batch-logs}"

[[ -f "${HOSTS_FILE}" ]] || { echo "主机列表不存在：${HOSTS_FILE}"; exit 1; }
[[ -f "${SSH_KEY}" ]] || { echo "私钥不存在：${SSH_KEY}"; exit 1; }
mkdir -p "${LOG_DIR}"

SSH_OPTS="-i ${SSH_KEY} -o BatchMode=yes -o ConnectTimeout=10 -o StrictHostKeyChecking=accept-new"

# 过滤注释与空行，得到主机列表
mapfile -t HOSTS < <(grep -v '^\s*#' "${HOSTS_FILE}" | grep -v '^\s*$')

run_one() {
    local host="$1"
    local log="${LOG_DIR}/${host}.log"
    {
        echo "=== ${host} 执行：${REMOTE_CMD} ==="
        if ! ssh ${SSH_OPTS} "${SSH_USER}@${host}" "${REMOTE_CMD}"; then
            echo "FAILED: ${host} 命令执行失败"
            return 1
        fi
        if [[ -n "${LOCAL_FILE}" ]]; then
            if ! rsync -avz -e "ssh ${SSH_OPTS}" "${LOCAL_FILE}" "${SSH_USER}@${host}:${REMOTE_PATH}"; then
                echo "FAILED: ${host} 文件同步失败"
                return 1
            fi
        fi
        echo "OK: ${host}"
    } > "${log}" 2>&1
}

export -f run_one
export SSH_OPTS SSH_USER REMOTE_CMD LOCAL_FILE REMOTE_PATH LOG_DIR

# xargs -P 控制并行度；单台失败不中断其他主机
printf '%s\n' "${HOSTS[@]}" | xargs -P "${PARALLEL}" -I{} bash -c 'run_one "$@"' _ {} || true

# 汇总失败主机
failed="$(grep -l '^FAILED' "${LOG_DIR}"/*.log 2>/dev/null || true)"
if [[ -n "${failed}" ]]; then
    echo "以下主机执行失败，详见各自日志："
    echo "${failed}"
    exit 1
else
    echo "全部主机执行成功（共 ${#HOSTS[@]} 台）"
fi
```

- 说明：`BatchMode=yes` 让 ssh 绝不交互式问密码，密钥不对直接失败而不是挂住等输入；`StrictHostKeyChecking=accept-new` 首次自动接受、之后严格校验，比 `no` 安全。
- 验证点：主机列表放 1 台可达 + 1 台故意写错的主机，跑完应输出失败汇总且退出 1，可达主机的命令与文件同步都成功。
- 坑：
  - 私钥权限必须是 600，否则 ssh 直接拒绝使用，先 `chmod 600 私钥`。
  - `xargs -P` 的并行度别贪高：一次对 50 台跑重命令等于自造 DDoS，5–10 起步。
  - 远程命令含管道、重定向时要整段单引号包起来传过去，不然会在本地先被解析。

## 4. 服务异常检测与告警

端口、进程、HTTP 三层探活，连续失败达到阈值才告警（防抖）。

```bash
#!/usr/bin/env bash
# health_watch.sh：三层探活 + 连续失败才告警
set -euo pipefail

PORT="${PORT:?请设置服务端口，如 PORT=8080}"
PROCESS_PATTERN="${PROCESS_PATTERN:?请设置进程特征，如 PROCESS_PATTERN=app.jar}"
HEALTH_URL="http://127.0.0.1:${PORT}/actuator/health"
FAIL_THRESHOLD="${FAIL_THRESHOLD:-3}"   # 连续失败几次才告警
INTERVAL="${INTERVAL:-30}"               # 每次探活间隔秒数
WEBHOOK_URL="${WEBHOOK_URL:-https://WEBHOOK_URL_PLACEHOLDER}"
STATE_FILE="${STATE_FILE:-/tmp/health_watch.failcount}"

send_alert() {
    local msg="$1"
    echo "告警：${msg}" >&2
    if [[ -n "${WEBHOOK_URL}" && "${WEBHOOK_URL}" != "https://WEBHOOK_URL_PLACEHOLDER" ]]; then
        curl -fsS --max-time 10 -X POST -H 'Content-Type: application/json' \
            -d "{\"text\":\"${msg}\"}" "${WEBHOOK_URL}" || echo "告警发送失败" >&2
    fi
}

# 三层探活，任一层失败即判本次失败
check_once() {
    # 1. 端口层
    ss -ltn 2>/dev/null | grep -q ":${PORT} " || return 1
    # 2. 进程层
    pgrep -f "${PROCESS_PATTERN}" > /dev/null || return 1
    # 3. HTTP 层
    curl -fsS --max-time 5 "${HEALTH_URL}" | grep -q '"status":"UP"' || return 1
    return 0
}

failcount=0
[[ -f "${STATE_FILE}" ]] && failcount="$(cat "${STATE_FILE}")"

if check_once; then
    echo "健康：端口/进程/HTTP 三层均正常"
    echo 0 > "${STATE_FILE}"
else
    failcount=$((failcount + 1))
    echo "${failcount}" > "${STATE_FILE}"
    echo "探活失败（连续 ${failcount}/${FAIL_THRESHOLD} 次）"
    if [[ "${failcount}" -ge "${FAIL_THRESHOLD}" ]]; then
        send_alert "服务异常：端口 ${PORT} 连续 ${failcount} 次探活失败（端口/进程/HTTP 任一层异常）"
        echo 0 > "${STATE_FILE}"  # 告警后清零，避免每轮重复轰炸
    fi
fi
```

- 说明：本脚本是“跑一次判一次”的探活器，挂到 cron 每 30 秒或 1 分钟跑一次；连续失败计数存在 `${STATE_FILE}`，跨 cron 调用不断；告警后清零，下一轮重新累计。
- 验证点：服务正常时跑一次应输出健康且计数归零；停掉服务连续跑 3 次，第 3 次应触发告警分支（占位 webhook 下只打印不外发）。
- 坑：
  - 只看端口活着不够：端口在但 Spring 僵死时 HTTP 层会拦住；只看 HTTP 也不够：健康端点本身被反代缓存时可能误报——三层缺一不可。
  - 防抖阈值别设 1：单次网络抖动、GC 停顿都会误告警；3 次 × 30 秒约等于 90 秒确认，误报率和发现延迟的折中。
  - `pgrep -f` 的特征串别写太短（如 `java` 会把所有 Java 进程都算上），写到 jar 包名这一级。

## 5. 数据库备份与恢复验证

mysqldump 全量备份并压缩 → 恢复到临时库 → 行数与校验和比对 → 保留策略清理。

密码绝不写进脚本：用环境变量 `MYSQL_PWD`（仅当次生效）或 `~/.my.cnf`；MySQL 模式的 OceanBase 同样适用 mysqldump。

```bash
#!/usr/bin/env bash
# db_backup_verify.sh：备份 MySQL/OceanBase（MySQL 模式）并恢复验证
set -euo pipefail

DB_HOST="${DB_HOST:?请设置数据库主机，如 DB_HOST=db-host.example.com}"
DB_PORT="${DB_PORT:-3306}"
DB_USER="${DB_USER:?请设置备份账号，如 DB_USER=backup}"
DB_NAME="${DB_NAME:?请设置库名，如 DB_NAME=billing}"
BACKUP_DIR="${BACKUP_DIR:-/data/backup}"
RETENTION_DAYS="${RETENTION_DAYS:-7}"
VERIFY_DB="${VERIFY_DB:-${DB_NAME}_verify_$(date +%Y%m%d%H%M%S)}"

mkdir -p "${BACKUP_DIR}"
STAMP="$(date +%Y%m%d%H%M%S)"
BACKUP_FILE="${BACKUP_DIR}/${DB_NAME}-${STAMP}.sql.gz"

MYSQL="mysql -h${DB_HOST} -P${DB_PORT} -u${DB_USER} --batch --skip-column-names"
DUMP="mysqldump -h${DB_HOST} -P${DB_PORT} -u${DB_USER} --single-transaction --routines --triggers --events"

# 1. 全量备份并压缩（--single-transaction 保证 InnoDB 一致性快照）
${DUMP} "${DB_NAME}" | gzip > "${BACKUP_FILE}"
[[ -s "${BACKUP_FILE}" ]] || { echo "备份文件为空，失败"; exit 1; }
gzip -t "${BACKUP_FILE}" || { echo "备份压缩包损坏"; exit 1; }
echo "备份完成：${BACKUP_FILE}（$(du -h "${BACKUP_FILE}" | cut -f1)）"

# 2. 恢复到临时库
mysql -h"${DB_HOST}" -P"${DB_PORT}" -u"${DB_USER}" -e "CREATE DATABASE \`${VERIFY_DB}\`;" || {
    echo "创建验证库失败（账号需有 CREATE 权限）"; exit 1; }
trap 'mysql -h"${DB_HOST}" -P"${DB_PORT}" -u"${DB_USER}" -e "DROP DATABASE IF EXISTS \`${VERIFY_DB}\`;" 2>/dev/null || true' EXIT
gunzip -c "${BACKUP_FILE}" | mysql -h"${DB_HOST}" -P"${DB_PORT}" -u"${DB_USER}" "${VERIFY_DB}"

# 3. 比对：每张表的行数 + 全表校验和
diff <(${MYSQL} -e "SELECT CONCAT(table_name, ':', table_rows) FROM information_schema.tables WHERE table_schema='${DB_NAME}' ORDER BY table_name;") \
     <(${MYSQL} -e "SELECT CONCAT(table_name, ':', table_rows) FROM information_schema.tables WHERE table_schema='${VERIFY_DB}' ORDER BY table_name;") \
    && echo "行数比对通过" || { echo "行数比对不一致，备份不可信"; exit 1; }

# 4. 保留策略：删除 7 天前的备份
find "${BACKUP_DIR}" -type f -name "${DB_NAME}-*.sql.gz" -mtime "+${RETENTION_DAYS}" -delete
echo "备份与恢复验证全部通过，验证库将在脚本退出时自动删除"
```

- 说明：`--single-transaction` 只对 InnoDB 保证一致性快照；MyISAM 表或混用时要改停写窗口或 `--lock-all-tables`。`trap ... EXIT` 保证验证库无论成功失败都会被删掉，不留垃圾库。
- 验证点：跑一遍应输出“行数比对通过”且验证库被删除；故意改坏一个备份包（`gzip -t` 那关）应直接失败不进入恢复；恢复后行数不一致应退出 1。
- 坑：
  - `information_schema.table_rows` 对 InnoDB 是估算值，大表上可能有微小偏差；行数比对适合中小库，大库改比对 `CHECKSUM TABLE` 或抽表全量 md5。
  - 备份账号只要 `SELECT`、`SHOW VIEW`、`TRIGGER`、`LOCK TABLES` 等读权限，别给写权限；恢复验证用的账号另给 `CREATE/DROP`，不要复用业务账号。
  - 备份文件本身也要异地一份：本机磁盘和数据库同挂时，本地备份等于没备。

## 面试与自测

1. 部署脚本里为什么健康检查要用 actuator 的 UP，而不是只看进程在不在？
2. `set -euo pipefail` 里三个选项各防住哪类问题？`set -e` 有什么常见反直觉行为？
3. 批量 SSH 脚本里 `BatchMode=yes` 是干什么的？不用它会出什么问题？
4. 探活脚本为什么要“连续失败 3 次才告警”，而不是失败一次就告警？
5. 数据库备份为什么用 `--single-transaction`？它对 MyISAM 表还有效吗？

### 参考答案

1. 进程在只说明 JVM 没死，不代表服务可用：Spring 还没起好、数据库连不上、线程池打满时，actuator 都不会返回 UP；只看进程会把带病服务当成部署成功。
2. `-e` 遇错即停、`-u` 未定义变量即报错、`-o pipefail` 让管道以最后一个非零退出码为准（否则 `false | true` 会被判成功）。`set -e` 的反直觉点：它在 `if` 条件、`&&`/`||` 链、函数返回值被测试时不触发，写“失败处理”逻辑时要显式判断退出码。
3. `BatchMode=yes` 禁止一切交互式询问（密码、主机确认），密钥不对或主机密钥变化时直接失败退出；不用它，批量任务会在某台主机上挂住等人工输入，整个批次卡死。
4. 防抖：单次失败可能是网络抖动、GC 停顿、cron 本身延迟；连续 3 次失败才告警，把误报率压下去，代价只是约 90 秒的发现延迟，是误报与延迟的折中。
5. `--single-transaction` 对 InnoDB 开一个一致性读事务，备份期间写入不影响快照；对 MyISAM 无效（MyISAM 不支持事务），混用时要改停写窗口或 `--lock-all-tables`，否则备份可能是不一致的拼盘。
