# 小说创作引擎

## 项目概述

一个通用小说创作引擎，目标不止是「让 LLM 写小说」，而是建成**小说世界状态数据库 + AI 推理系统 + 沙盒推演系统**：世界状态（人物、关系、事件、事实、规则）以结构化形式存在数据库里，LLM 在状态的约束下生成与分析，使长篇连载在几百章尺度上保持连贯。

当前服务对象是都市悬疑长篇《残契者》（又名《谁改写了我的记忆》），规划约 600 章、7 卷。引擎本身按通用设计：支持多部小说、多项目、模板，不与任何一部作品的具体剧情耦合。

## 技术栈

- 语言与框架：Python + SQLAlchemy
- 存储：SQLite（世界状态与章节的唯一权威数据源）
- 模型：Ollama 本地 LLM（OpenAI 兼容接口），零 API 成本；规划为小模型常驻处理高频分析、大模型按需做复杂推演与终裁，部署方法论见 [本地部署与Ollama](../AI与大模型/本地部署与Ollama.md)
- 向量检索（原型阶段）：Chroma，见下文 RAG 原型

## 架构

### 数据模型

| 模型 | 职责 |
|---|---|
| Project | 一部作品一个项目，隔离各自的世界状态 |
| Entity | 人物及其他实体（地点、物品、组织等） |
| EntityState | 实体当前状态 |
| StateHistory | 状态变更历史流水（不覆盖式记录，支持回溯任意时刻的状态） |
| Relation | 实体间关系 |
| Timeline | 故事时间线 |
| Event | 剧情事件 |
| Snapshot | 世界状态快照 |
| Sandbox | 沙盒推演分支（与主线状态隔离） |
| Rule / StoryRule | 剧情规则：把事实结构化成可检测的约束（如某人不知道某事、某物能改写记忆） |
| StoryFact | 已确立的剧情事实 |
| Chapter | 章节：status 默认 draft、version 默认 1，正文修改递增 version |

### 服务层

- **ChapterService**：章节 create / get / list / update_content / update_summary / publish。
- **ChapterContextService**：写章前聚合上下文——章节信息、Timeline、人物 Entity 与 EntityState、Sandbox 状态、Relation、Event、StoryRule，拼成给 LLM 的结构化世界状态上下文。
- **ChapterAnalysisService**：章节写完后跑 LLM 分析，把正文里的变化抽回结构化数据。
- **ContradictionService**：矛盾检测，对照事实与规则检查新内容是否与既有状态冲突。
- 其余：ProjectService、EntityService、EntityStateService、RelationService、TimelineService、EventEngine、SnapshotService、SandboxService、RuleService、StoryRuleService。

## 核心机制

**1. 章节数据流（生成—分析—回写闭环）**

```text
Chapter 正文 → ChapterAnalysisService → LLM → JSON
（entities / entity_changes / relations / events / facts / rules）
→ 校验后回写 SQLite
```

LLM 只产出结构化增量，落库由程序校验后执行——约束方法见 [结构化输出与JSON约束](../AI与大模型/结构化输出与JSON约束.md)。写下一章时，ChapterContextService 再从库里聚合最新世界状态喂回去，闭环成立。

**2. 伏笔台账**

独立的 Hook 表 + HookService 管理伏笔全生命周期：`planted`（埋设）→ `developed`（推进）→ `paid_off`（回收）/ `dropped`（弃置）。伏笔不再靠模型「记得」，而是可查、可统计账龄、到期未回收可预警的显式数据。台账（Step 1）已落地。

**3. 沙盒推演**

分支式剧情模拟：在 Sandbox 分支里让关键节点走不同选择（例：某角色存活 / 死亡 / 逃脱），观察各分支的后果与矛盾，主线状态不受污染，选定方向后再合并回主线。推演结论属于「方案」而非「事实」，与正式状态分开存放，对应 [Agent-记忆系统](../AI与大模型/Agent-记忆系统.md) 里推测与事实分级的原则。

**4. RAG 原型**

已落地原型（放在引擎目录下，先行验证、尚未正式切换进主链路）：`rag_chroma_eg2.py` 通过 Ollama `/api/embed` 出向量（模型 `embeddinggemma-2:270m`），chunk + overlap 切片，Chroma 持久化 DocStore，异常统一收敛为 RAGError。目标形态是「结构化检索（世界状态库）+ 语义检索（向量）+ LLM 推理」三层组合，原理与选型见 [Embedding与向量数据库](../AI与大模型/Embedding与向量数据库.md)，分块与评测见 [RAG-评测与分块策略](../AI与大模型/RAG-评测与分块策略.md)。

## 当前最大挑战

连续生成多章时的连贯性——直白说，不如直接让大模型一口气连写几十章顺。拆开看是几个记忆与规划问题，不是单点生成质量问题：

- **长期剧情记忆**：几百章尺度上，哪些旧状态该进每章上下文、过期事实如何降权（见 [Agent-记忆系统](../AI与大模型/Agent-记忆系统.md) 的 Anti-Persistence）。
- **伏笔管理**：埋了要记得推进、到期要回收，跨越上百章的伏笔靠台账 + 提醒机制，不能靠模型记忆。
- **人物目标与事件因果**：人物行为要有前因，事件之间要有因果链，而不是每章孤立成立。
- **主线/支线推进与节奏**：冲突推进速度、多线并行时的配比，需要章节级的规划层，而不只是逐章生成。

## 演进方向

- RAG 正式接入：结构化检索与语义检索合并排序，向量方案按评测结果（而非参数表）定型。
- 章节规划层：在逐章生成之上加「章节契约」——本章必须推进什么、回收什么、埋什么，先规划后生成。
- 记忆淘汰与降权：给世界状态上下文的聚合策略加时效与相关性筛选。
- 角色分工的多 Agent 形态（生成 / 分析 / 矛盾检测分离）作为候选架构，落地前先验证打回与耗时，见 [多Agent协作](../AI与大模型/多Agent协作.md)。
