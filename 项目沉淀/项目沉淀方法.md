# 项目沉淀方法

> 项目沉淀是把做项目的经验写成可复用的知识：一个项目一篇笔记，写「这个项目里技术是怎么落地的、难在哪、怎么解决的」。技术知识点笔记讲通用方法（比如 Flowable 怎么用），项目沉淀讲「这个项目里 Flowable 是怎么用的」。两者分工不同，互相挂链接。本篇是项目沉淀的入口：讲怎么写一篇沉淀、写什么、不写什么。

## 1. 核心概念

- **项目沉淀是什么**：以项目为单位的经验记录。一项目一笔记，放在 `项目沉淀/` 目录下；全部项目的索引与对照在 [项目沉淀地图](知识地图/项目沉淀地图.md)，本页只做方法说明，不做索引。
- **和技术知识点笔记的分工**：技术篇讲通用方法（一个技术点一篇，面向「下次遇到同类问题怎么解」）；项目篇讲一次真实落地（面向「这个项目当时是怎么回事」）。项目篇里遇到通用技术点，只写「当时怎么用的、坑在哪」，通用细节分流到技术篇、挂链接，不在项目篇里重讲一遍。
- **沉淀的读者**：首先是未来的自己（复盘、面试、接手类似项目时翻）；其次是能看到这个公开仓库的人。所以写法上只写技术做法与业务背景，不写客户内部数据、账号、金额细节与个人信息。
- **什么时候算一篇合格的沉淀**：别人读完能回答三个问题——这个项目是干什么的、你负责了什么、最难的技术点是怎么解决的。

## 2. 基础知识：案例笔记的五段结构

本库 9 篇项目沉淀用的都是同一套五段结构（以 [神农-e贷-法人版](项目沉淀/神农-e贷-法人版.md)、[督办系统](项目沉淀/督办系统.md) 为例）：

| 段 | 写什么 | 注意 |
|---|---|---|
| 项目概述 | 项目背景、业务目标、客户/单位、你的任职时间与公司 | 只写公开可讲的背景；时间以简历与实际为准，记不清的写「在职期间」、不臆测 |
| 软件环境 | 后端/前端/数据库/相关技术栈（带版本号）/开发工具 | 版本号写实际用的，如 Spring Boot 2.7.3、Flowable 6.7.2；别写「最新版」这种会过期的说法 |
| 本人职责 | 你负责了哪些事，按条列 | 写你实际做的事，别把整个团队的工作都算成自己的 |
| 核心工作与技术点 | 最难的 2–4 个技术点：问题、做法、结果 | 这是沉淀的核心；只列名字不算沉淀，要写清难在哪、怎么解决的 |
| 关联知识 | 挂到相关的技术篇与专题深挖篇 | 用仓库根路径链接或 `[[双链]]`，与技术篇双向挂 |

- **时间线与技术栈矩阵不在各项目篇里重复写**：统一放在 [项目沉淀地图](知识地图/项目沉淀地图.md)（时间线表 + 技术栈矩阵 + 与知识点的对应），新项目落成后去地图页补一行。
- **技术栈版本以各项目篇的「软件环境」为准**，本篇不汇总版本号，避免两处不一致。

## 3. 进阶知识：沉淀的三种深度

- **概述级（默认）**：五段结构写全，核心技术点各写一段。这是 9 篇沉淀目前的深度，够复盘、够面试讲。
- **专题深挖级**：某个技术点值得单独成篇时，从项目篇里拆出去单写一篇，再从项目篇挂链接。例子：[神农-e贷-法人版](项目沉淀/神农-e贷-法人版.md) 的审批流（会签、驳回、超时、补偿）单独沉淀为 [神农-e贷-审批流](项目沉淀/神农-e贷-审批流.md)，法人版篇只留一句话加链接。
- **反哺技术篇级**：项目里踩出的通用坑，值得写成通用技术篇时，在技术篇里写通用方法，在项目篇里挂过去。例子：督办系统的 Flowable 流程模型做法，对应通用篇的 Flowable 方法；法人版的 OceanBase 注意点，对应 MySQL-数据库篇。

拆不拆的判断标准：**这个技术点离开这个项目还有没有人要看**。有，就拆出去单写；没有，就留在项目篇里。

## 4. 原理剖析

- **为什么「一项目一笔记」**：项目是检索单位。面试按项目讲、复盘按项目查、接手类似项目时按项目翻；把多个项目混在一篇里，三种场景都难用。
- **为什么职责与技术点要分开写**：职责回答「你做了什么」（范围），技术点回答「怎么做的、难在哪」（深度）。混在一起写，容易变成只列事项、不讲做法的流水账。
- **为什么关联知识要双向挂**：项目篇挂技术篇，读者能从项目找到通用方法；技术篇挂项目篇，读者能从方法找到真实落地。单向挂，另一头的读者就找不到。
- **为什么通用细节不写进项目篇**：同一个技术会在多个项目里出现，细节写两份就会出现两份不一致。通用细节只写在技术篇一份，项目篇只写「当时怎么用的、坑在哪」，再挂链接。

## 5. 实战应用：写一篇沉淀的六步

以 [神农-e贷-法人版](项目沉淀/神农-e贷-法人版.md) 为例：

1. **定项目与时间范围**：项目名、客户/单位、起止时间。法人版：交通银行上海市分行「神农 e 贷」法人版，任职法本期间（2024/4 至今）的主力项目。
2. **列技术栈**：后端 JUMP + OceanBase + MyBatis；相关技术栈 Spring Boot 2.7.3、MyBatis-Plus 3.5.3.2、Flowable 6.7.2、Redis、Quartz、Docker、TongWeb；开发工具 IDEA + Git。
3. **写职责**：按条列——业务逻辑梳理、征信数据字段收集与建表入库、预核额/预审/正式审批/放款通知、第三方接口联调、增量同步脚本、需求讨论与发版上线。
4. **挑核心技术点**：只挑 2–4 个最难的。法人版挑了征信数据链路（字段梳理 → 建表 → 入库 → 报告查询）和审批主链路（预核额 → 预审 → 正式审批 → 放款通知），每点写清链路与难处。
5. **拆专题、挂关联**：审批流的会签、驳回、超时、补偿值得单写，就拆成 [神农-e贷-审批流](项目沉淀/神农-e贷-审批流.md)；关联知识挂审批流专题、Flowable、MySQL-数据库。
6. **去地图页补一行**：在 [项目沉淀地图](知识地图/项目沉淀地图.md) 的时间线表与技术栈矩阵里补上这个项目。

**写不下去时**：先把五段标题搭好、把能确定的技术栈与职责填上，空着技术点细节；细节等翻提交记录、翻需求文档、或口述补齐后再填，别凭印象编数字与时间。

## 6. 疑难杂症

- **写了一半没素材**：先写骨架（五段标题 + 确定的技术栈与职责），技术点细节标注待补；素材来源按序找——提交记录、需求文档、联调记录、口述回忆。没把握的数字与时间宁可不写。
- **项目涉密怎么办**：只写技术做法与业务背景，不写客户内部数据、账号、金额细节、未公开的业务数字。拿不准能不能写的，写通用做法、不写客户特指信息。
- **老项目时间记不清**：地图页写「在职期间」，不臆测起止时间；各项目篇以实际为准，记不清就不写具体月份。
- **项目还没做完**：可以先写骨架加已完成部分，标题与时间范围写明「至今/持续中」；做完再补。例子：[小说创作引擎](项目沉淀/小说创作引擎.md) 就是持续中的个人项目。

## 7. 常见误区

- **写成流水账**：只列「做了什么」，不写「难在哪、怎么解决的」。沉淀的核心是技术点，不是事项清单。
- **简历复制粘贴**：把简历里的项目描述原样贴过来。简历是给招聘方看的，沉淀是给未来的自己看的——要写做法、写坑、写取舍。
- **把通用技术细节全塞进项目篇**：同一个技术在多个项目出现，细节写两份就会出现两份不一致。通用细节写技术篇，项目篇只写当时怎么用的、再挂链接。
- **堆个人信息**：仓库是公开的，简历电话/邮箱/生日等个人信息一律不入库；项目篇只写技术与业务，不写个人联系方式。
- **一个技术点到处写、处处都浅**：值得深挖的点就拆成专题篇（如神农-e贷-审批流），别在项目篇里写一半、技术篇里又写一半。

## 8. 性能优化

- **维护成本要低**：沉淀写完不是一劳永逸，但也不用频繁改——项目有新进展才改；技术细节变了，改技术篇，不改项目篇。
- **关联断了及时修**：技术篇改名时，同步改项目篇里的链接；地图页的时间线与矩阵随新项目补，别攒着。
- **别给沉淀加「性能优化」式的硬指标**：沉淀的质量标准是「三个月后自己读还能复现当时的思路」，不是字数、不是篇数。

## 9. 版本差异

- 本篇讲方法，不随技术版本变；各项目技术栈的版本号以各项目篇的「软件环境」为准，不在本篇汇总。
- 案例笔记的五段结构是本库 9 篇沉淀的既有结构（2026-10-22 起陆续落成），新项目沿用同一结构；如需调整结构，先改本篇、再逐篇同步，不要单篇各行其是。

## 小技巧与冷知识

- 地图页有个很实用的标注法：时间记不清的项目写「在职期间」，并注明「以各项目笔记为准，不臆测」——诚实比精确重要。
- 审批流专题的拆分是本库最好的例子：法人版篇只留一句话「审批流实现细节单独沉淀在神农-e贷-审批流」，想深挖的人点过去，想看全貌的人不用被细节淹没。
- 个人项目也进沉淀：小说创作引擎是个人项目，照样有一篇沉淀（技术栈矩阵里有 Chroma、SQLite、Ollama），沉淀不只属于公司项目。
- 写沉淀最划算的时机是项目刚结束、记忆还热的时候；拖三个月，细节就得翻提交记录才能想起来。

## 10. 面试与自测

1. 项目沉淀是什么？它和技术知识点笔记的分工是什么？
   - 参考答案：项目沉淀是以项目为单位的经验记录，讲「这个项目里技术是怎么落地的、难在哪、怎么解决的」；技术篇讲通用方法。项目篇遇到通用技术点，只写当时怎么用的、坑在哪，通用细节分流到技术篇、挂链接。
2. 案例笔记的五段结构是哪五段？每段写什么？
   - 参考答案：项目概述（背景、业务目标、任职时间）、软件环境（技术栈带版本号、开发工具）、本人职责（实际做的事，按条列）、核心工作与技术点（最难的 2–4 个点，写清难处与做法）、关联知识（挂技术篇与专题篇）。
3. 什么情况下要把技术点从项目篇拆出去单写一篇？
   - 参考答案：这个技术点离开这个项目还有没有人要看。有，就拆成专题篇（如神农-e贷-审批流），项目篇只留一句话加链接；没有，就留在项目篇里。
4. 项目涉密、时间记不清时分别怎么处理？
   - 参考答案：涉密只写技术做法与业务背景，不写客户内部数据、账号、金额细节与未公开数字；时间记不清写「在职期间」，不臆测起止时间，以各项目笔记为准。
5. 为什么通用技术细节不写进项目篇？关联知识为什么要双向挂？
   - 参考答案：同一技术会在多个项目出现，细节写两份会不一致，通用细节只写技术篇一份；双向挂让读者既能从项目找到通用方法，也能从方法找到真实落地。
