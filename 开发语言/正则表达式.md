# 正则表达式

### 核心概念与术语

- **正则表达式（regex）**：用一串特殊符号描述"文本长什么样"的微型语言，用来在文本里查找、校验、切分、替换。
- **模式（pattern）**：你写的那串规则本身，如手机号规则就是一段模式；被检查的文本叫目标串。
- **匹配（match）**：模式在目标串里找到符合规则的一段，就算匹配成功；成功不等于整串都符合，要看是否用了锚点。
- **字面量字符**：普通字母数字在模式里就表示它本身，`abc` 匹配的只有连续的 abc 三个字符。
- **转义**：元字符想当普通字符用就加反斜杠，如 `\.` 只匹配小数点本身；反过来，普通字母加反斜杠常变成字符类（如 `\d`）。
- **字符类**：表示"这一位可以是这些字符之一"，有速记式（`\d \w \s`）和方括号自选式两大类。
- **量词**：紧跟在某个元素后面，表示它能重复几次；量词只作用于紧挨着它前面的那一个元素（或一组）。
- **锚点**：不匹配任何字符，只限定位置，如开头、结尾、单词边界；是"隐形条件"。
- **单词边界 \b**：单词字符（`\w`）与非单词字符交界处就是边界，`"cat"` 里的开头与结尾处各有一个。
- **分组**：用小括号把几个元素绑成一个整体，量词、或运算就能作用于整组。
- **或运算的优先级最低**：`ab|cd` 是"ab 或 cd"，不是"a 后跟 b 或 d"；拿不准就加括号圈范围。
- **标志（flags）**：写在模式外的开关，改引擎行为：`i` 忽略大小写、`g` 全局找全部、`m` 多行、`s` 让点号能匹配换行、`u` Unicode 模式（具体支持以官方文档为准）。
- **引擎心智模型**：主流引擎按"从左到右、逐位尝试、失败就回退重试"的方式工作，所以模式写法的顺序与具体程度会影响速度与结果。

## 元字符速查

| 符号 | 含义 |
|---|---|
| `.` | 任意单个字符（除换行） |
| `\d` / `\D` | 数字 / 非数字 |
| `\w` / `\W` | 单词字符（字母数字下划线）/ 非单词字符 |
| `\s` / `\S` | 空白 / 非空白 |
| `^` / `$` | 字符串开头 / 结尾 |
| `*` `+` `?` | 0 次以上 / 1 次以上 / 0 或 1 次 |
| `{n}` `{n,}` `{n,m}` | 恰好 n 次 / 至少 n 次 / n 到 m 次 |
| `[]` `[^]` | 字符集 / 取反 |
| `|` | 或 |
| `()` | 分组（捕获） |
| `\` | 转义 |

## 分组与捕获

- `(abc)`：捕获分组，模式内用 `\1` 按编号反向引用
- `(?:abc)`：非捕获分组，只分组不记住，性能更好
- 命名分组：Python 写 `(?P<name>abc)`，Java 与 JS 写 `(?<name>abc)`；长模式用命名组就不用数数字

| 引用位置 | Python | Java | JavaScript |
|---|---|---|---|
| 模式内反向引用 | `(?P=name)`（也可写 `\1` 按编号） | `\k<name>` | `\k<name>` |
| 替换侧引用 | `\g<name>`（`\1` 按编号） | `${name}` | `$<name>` |

## 贪婪 vs 懒惰

- 默认贪婪：`.*` 尽量多吃
- 加 `?` 变懒惰：`.*?` 尽量少吃
- 例：`<.*>` 会匹配整个 `<a>1</a>`，`<.*?>` 只匹配 `<a>`
- 引号内容：`".*"` 对 `"a" and "b"` 一口吃掉整串，`".*?"` 则逐个取出 `"a"`、`"b"`
- 数字提取：`\d+` 对 "价格100元200块" 取出 `100`、`200`；`\d+?` 每次只吃 1 位，取出 `1`、`0`、`0`、`2`、`0`、`0`

## 量词三形态对照表

| 形态 | 写法 | 吃多少 | 回吐吗 | 例子 |
|---|---|---|---|---|
| 贪婪 | `a*` | 尽量多 | 回吐 | `<.*>` 吃掉整个 `<a>1</a>` |
| 懒惰 | `a*?` | 尽量少 | 回吐 | `<.*?>` 只吃 `<a>` |
| 占有 | `a*+` | 尽量多 | 不回吐 | `a*+ab` 对 `aaab` 匹配失败（见下） |

- 占有量词吃下去就不还：`a*+ab` 匹配 `aaab` 时，`a*+` 一口吃掉 `aaa`，后面只剩 `b`，凑不出 `ab`，又不许回吐，于是整体失败；换成贪婪的 `a*ab` 则能成功（回吐一个 `a` 凑出 `ab`）。
- 占有量词与原子组 `(?>...)` 是一回事：`a*+` 等价于 `(?>a*)`；回溯节的优化讲的就是它。
- 支持情况：Java 早已支持；Python 3.11+ 支持；JS 不支持，占有需求改写成等价形式（如先收紧字符集、或用锚点限定范围）。

## 三语言写法差异

| | Java | Python | JavaScript |
|---|---|---|---|
| 字面量 | `"\\d+"`（双反斜杠） | `r"\d+"`（推荐 raw string） | `/\d+/g` |
| 匹配 | `Pattern.compile().matcher()` | `re.search` / `re.match` / `re.findall` | `str.match` / `regex.test` |
| 替换 | `replaceAll` | `re.sub` | `str.replace` |
| 命名分组 | `(?<name>...)` | `(?P<name>...)` | `(?<name>...)` |
| 标志 | `Pattern.CASE_INSENSITIVE` 等作编译参数 | `re.I` 等作 `flags` 参数 | `/i` `/g` 等写在结尾斜杠外 |

Java 里反斜杠要写两遍，是最常见的报错来源。

## 标志（flags）全表

| 含义 | Python | Java | JavaScript |
|---|---|---|---|
| 忽略大小写 | `re.I` | `Pattern.CASE_INSENSITIVE` | `/i` |
| 多行（`^$` 按行算） | `re.M` | `Pattern.MULTILINE` | `/m` |
| 点号匹配换行 | `re.S` | `Pattern.DOTALL` | `/s` |
| 忽略模式内空白与注释 | `re.X` | `Pattern.COMMENTS` | ——（不支持） |
| Unicode 模式 | 默认即 Unicode；`re.A` 反向收紧为 ASCII | `Pattern.UNICODE_CHARACTER_CLASS` 等 | `/u` |
| 全局查找全部 | `findall` / `finditer`（无 g 标志概念） | `Matcher.find()` 循环 | `/g` |

- 行内写法：Python 与 Java 支持写在模式开头，如 `(?i)`、`(?m)`、`(?s)`；JS 不支持行内标志，标志只能写在结尾斜杠外。
- 组合用 `|`：Python 写 `re.I | re.M`，Java 写 `Pattern.CASE_INSENSITIVE | Pattern.MULTILINE`。
- `g` 只在 JS 里是标志：Python 用 `findall`/`finditer` 拿全部，Java 用 `find()` 循环；三者不要混着记。
- JS 还有 `/y`（粘连，从 `lastIndex` 处开始匹配）与 `/d`（返回下标），不常用，查文档即可。

## 替换与切分

### re.sub：替换

```python
import re
# 替换文本里的 \1 按编号引用分组，\g<name> 按名字引用
re.sub(r"(\d{4})-(\d{2})-(\d{2})", r"\2/\3/\1", "2026-10-22")  # '10/22/2026'
re.sub(r"(?P<year>\d{4})-(?P<mon>\d{2})", r"\g<mon>/\g<year>", "2026-10")  # '10/2026'
# 回调替换：替换逻辑写不进一串文本时，用函数算
re.sub(r"\d+", lambda m: str(int(m.group(0)) * 2), "a3b5")  # 'a6b10'
# 注意：替换文本里的 \g<0> 是整个匹配；\1 在普通字符串里会被字符串层先转义，替换文本务必用 raw string
```

### re.split：切分

```python
import re
re.split(r"[,;]", "a,b;c")          # ['a', 'b', 'c']
re.split(r"(,)", "a,b")             # ['a', ',', 'b']：分组里的分隔符会保留
re.split(r"\s+", "a  b\tc", maxsplit=1)  # ['a', 'b\tc']：maxsplit 限切分次数
```

### 跨语言替换写法

| | Python | Java | JavaScript |
|---|---|---|---|
| 替换函数 | `re.sub` | `replaceAll` | `str.replace` / `replaceAll` |
| 编号引用 | `\1`、`\g<1>` | `$1` | `$1` |
| 命名引用 | `\g<name>` | `${name}` | `$<name>` |
| 特殊引用 | `\g<0>` 整个匹配 | `$0` 整个匹配 | `$&` 整个匹配；$` 匹配前部分；$' 匹配后部分 |
| 回调 | 传函数 | `Matcher.replaceAll` 传 lambda（Java 9+） | 传函数 |

- JS 的 `$&`、`$``、`$'` 只在替换文本里有效，模式里没有这个写法；Java 替换文本里的 `$`、`\` 有特殊含义，字面量要先 `Matcher.quoteReplacement` 处理。

## 5 个常见坑

1. **贪婪匹配吃多**：想取标签内容用 `<.*?>` 而不是 `<.*>`。
2. **特殊字符没转义**：`.`、`(`、`[` 在模式里有含义，匹配字面量要写 `\.` `\(` `\[`。
3. **灾难性回溯**：`(a+)+$` 这类嵌套量词在长字符串上能卡死；能确定边界就用具体字符集。
4. **`^$` 和多行的误会**：默认 `^$` 是整个字符串的开头结尾；要按行匹配才加多行模式（`re.MULTILINE` / `(?m)`）。
5. **`\d` 不等于 `[0-9]`**：Unicode 模式下 `\d` 能匹配全角数字等；严格校验用 `[0-9]`。

## 疑难杂症

### 1. 环视断言在旧环境直接报语法错
- **现象**：`(?<=@)\w+` 在新版 Chrome/Node 正常，老浏览器或旧 Java 报 `invalid regex`。
- **原因**：后行断言 `(?<=)` / `(?<!)` 是 ES2018 才进标准的，各语言支持时间不一。
- **解决**：要兼容就别用后行断言，改用捕获组取第 1 组；或先检测环境再降级。

### 2. \p{Script=Han} 匹配中文的前提
- **现象**：`\p{Script=Han}` 写出来没效果或报错。
- **原因**：Unicode 属性转义需要 `u` 标志（JS）或对应语言的 Unicode 模式；Python 的 `re` 不支持，得用 `regex` 第三方库。
- **解决**：JS 写成 `/\p{Script=Han}/u`；Python 要么用 `regex` 库，要么退回 `[\u4e00-\u9fa5]`。

### 3. 捕获组编号错乱
- **现象**：加了个 `(?:...)` 或嵌套分组后，`$2` 取到的内容变了。
- **原因**：只有捕获组才占编号，非捕获组不占；数编号时容易把 `(?:)` 算进去。
- **解决**：复杂模式用命名分组 `(?<name>...)`，引用时按名字取，不再数数字。

### 4. JS 的 g 标志正则反复 test 结果忽真忽假
- **现象**：同一个带 `/g` 的正则连续调用 `.test()`，结果 true、false 交替出现。
- **原因**：带 `g`（或 `y`）的正则对象自带 `lastIndex` 状态，`test`/`exec` 每次从 `lastIndex` 处开始找；找到后 `lastIndex` 推进到匹配末尾，找不到时才重置为 0。
- **解决**：只做真假判断就别加 `g`；必须复用带 `g` 的正则时，每次调用前手动置 `regex.lastIndex = 0`，或每次新建一个正则对象。

## Unicode 说明

- Unicode 属性转义 `\p{...}`：Java 原生支持（如 `\p{L}` 字母、`\p{Script=Han}` 汉字）；JS 要加 `/u` 标志才生效；Python 的 `re` 不支持，要用第三方 `regex` 库，或退回显式范围 `[\u4e00-\u9fa5]`。
- emoji：分布在多个区块，没有一段连续范围能全覆盖；JS/Java 可用 `\p{Extended_Pictographic}`（加 `/u`），Python `re` 只能列举常用区块（如 `[\U0001F300-\U0001F64F]`），完整处理用专门的 emoji 库。
- 大小写折叠：`i` 标志在 Unicode 模式下会按 Unicode 规则折叠大小写，但各语言折叠表不完全一致；土耳其语 `I/ı` 这类语言特例不在引擎折叠规则内，涉及 locale 的大小写转换先用字符串方法处理，别指望正则。
- `\d`、`\w` 的范围也随 Unicode 模式变：Python `re` 默认 Unicode，`\d` 能匹配全角数字；要严格 ASCII 就用 `re.A` 或显式写 `[0-9]`（见常见坑第 5 条）。

## 何时不用正则：选型对照

| 场景 | 正则够不够 | 推荐方案 |
|---|---|---|
| 解析 HTML/XML 整体 | 不够：嵌套结构超出正则表达能力 | 解析器（BeautifulSoup / lxml / DOMParser） |
| 解析 JSON | 不够：同上，且转义规则多 | `json.loads` / `JSON.parse` |
| 取 URL 各部分 | 能取但易错 | `urllib.parse` / `new URL()` |
| 日期是否真实存在 | 只验形状 | 日期库（datetime / dayjs） |
| 邮箱是否真实有效 | 只验形状 | 发一封验证邮件 |
| 简单包含/前后缀判断 | 杀鸡用牛刀 | `in` / `startswith` / `includes` |
| 括号配对、嵌套注释 | 正则做不到（个别引擎的平衡组除外） | 手写解析器或递归下降 |

- 判断标准：结构有嵌套、要算语义（日期合法、邮箱真实、数值大小），就别只用正则；正则只管"长什么样"，不管"对不对"。

## 环视断言实战

不消耗字符、只看前后文的"隐形条件"：

| 写法 | 含义 | 例子 |
|---|---|---|
| `(?=...)` | 前面是…（肯定顺序环视） | `\d+(?=元)` 匹配"100元"里的 100 |
| `(?!...)` | 前面不是… | `\d+(?!元)` 匹配不带"元"的数字 |
| `(?<=...)` | 后面是…（肯定逆序环视） | `(?<=@)\w+` 取 @ 后面的用户名 |
| `(?<!...)` | 后面不是… | `(?<!\$)\d+` 排除 $ 开头的金额 |

```python
import re
re.findall(r'\d+(?=元)', '100元和200块')      # ['100']
re.sub(r'(?<=\d),(?=\d)', '', '1,000,000')  # 去千分位逗号 -> '1000000'
```

- 逆序环视 `(?<=)` 里大多语言要求定长（如 `(?<=ab|abc)` 非法定长会报错），写之前确认。
- 密码强度校验是环视的经典场景：`^(?=.*[A-Z])(?=.*\d).{8,}$`。

## 回溯优化：从灾难性回溯说起

```python
# 灾难版：(a+)+$ 遇到 "aaaaaaaaaaaaaab" 直接卡死
# 优化1：占有量词（Java/PCRE）/ 原子组
# (?>a+)$          # 原子组：匹配了就不回吐
# 优化2：改写成等价的无嵌套形式
# a+$             # 本来就这么简单
```

- 嵌套量词 `(x+)+`、`(a|ab)*` 是重灾区，review 正则时先扫这个形状。
- 在线验证：regex101.com 有"debugger"看步数，步数爆炸就别上线。
- 日志清洗这种高频场景，宁可写两遍简单正则，也别写一遍炫技的。

## 测试与调试方法论

### regex101 怎么用
- 左侧选 flavor（PCRE2 / Python / JavaScript / Java），先把语言选对再写模式，flavor 不对测了也白测。
- TEST STRING 里同时放正例与反例；右侧 Explanation 逐段解释模式在干什么，看不懂的段就是写错的段。
- 疑似灾难回溯时开 debugger 看步数：步数随输入长度爆炸式增长就别上线，先改写法（见回溯优化一节）。

### 正反例表与边界值清单
- 每段模式至少准备 3 个正例、2 个反例；正例要覆盖各分支，反例要覆盖"差一点就对"的情况（如手机号 10 位、11 位但第 2 位是 2）。
- 边界值清单：空串、超长串、首尾空白、含换行、含 Unicode（中文/emoji）、大小写混写、特殊字符（`.` `*` `(` `[` `$`）。
- 校验类模式先跑整串（`fullmatch` / `^$`），提取类模式先跑片段（`search` / `findall`），两类不要用同一套测试。

### 分步拆解流程
1. 先写字面量部分跑通（如先写 `2026-` 再写后面的）。
2. 再逐个换上字符类与量词，每换一处跑一次测试。
3. 再加锚点、分组、环视，每加一层跑一次测试。
4. 最后把正反例表固化成单测（Python `assert`、JS 测试文件），模式一改就重跑。

## 基础知识补强

### 基础语法与用法

```python
import re

text = "订单 2026 号, 金额 88 元, 电话 13812345678"

# 三个最常用的动作：找、校验、全找
print(re.search(r"\d+", text).group())      # 找到第一处数字 -> '2026'
print(re.fullmatch(r"\d{11}", "13812345678"))  # 整串校验 -> 匹配对象（不是 None 即通过）
print(re.findall(r"\d+", text))              # 全部找出 -> ['2026', '88', '13812345678']

# match 只从开头试，search 从任意位置试：新手最常混的一对
print(re.match(r"\d+", "abc123"))    # None：开头不是数字
print(re.search(r"\d+", "abc123").group())   # '123'
```

```python
# 字符类方括号：自选范围、取反、连字符位置
print(re.findall(r"[aeiou]", "regex"))        # ['e', 'e'] 元音
print(re.findall(r"[^0-9]+", "a1b22c"))       # ['a', 'b', 'c'] 非数字段
print(re.findall(r"[a-z0-9_]+", "Hi_2026"))    # 小写字母数字下划线段
# 注意：方括号里 . * + 等元字符大多失去特殊含义，不用再转义
# 连字符想表示字面量就放最后，如 [a-z-]；放中间表示范围
```

```python
# 单词边界：避免把长单词里的一截误匹配出来
print(re.findall(r"\bcat\b", "cat scatter cat"))  # ['cat', 'cat']
print(re.findall(r"cat", "cat scatter cat"))       # 3 处，scatter 里的也算

# 分组加量词：重复的是整组
print(re.fullmatch(r"(ab)+", "ababab"))   # 通过：ab 重复 3 次
print(re.fullmatch(r"ab+", "ababab"))      # 不通过：+ 只管前面的 b

# 或运算写具体分支，别写万能点号
print(re.findall(r"猫|狗|鸟", "我家有猫和狗"))   # ['猫', '狗']
```

### 关键机制速览

- **先写需求再写模式**：固定四步——目标串长什么样、要整串还是找一段、有没有必须排除的情况、拿 3 个正例 2 个反例自测。
- **最左最长倾向**：引擎从最左边的位置开始尝试，该位置能匹配多长就先吃多长（懒惰量词除外），所以结果常是"第一处且尽量长"。
- **量词的作用范围**：量词只绑定它前面的单个元素；想重复多个字符必须先用括号分组，这也是分组最朴素的用途。
- **字符类减法做不到**：想表达"除了某几个的其他数字"这类需求，方括号只能对字符取反（如 `[^5]`），其余靠分支或环视（原文已述）。
- **点号的边界**：默认 `.` 不匹配换行符，跨行文本要用 `s` 标志或显式写 `[\s\S]`（空白与非空白的并集等于任意字符）。
- **空匹配陷阱**：模式能匹配空串时（如 `a*` 对 "bbb"），全局查找会在每个位置都报一处空匹配，结果一堆空字符串，先想清楚是否允许零次。
- **锚点与多行**：没有 `m` 标志时 `^` 只认整串开头；按日志逐行筛必须开多行模式，否则只有第一行能中。
- **预编译**：同一模式反复用时先编译再复用（Python 的 `re.compile`、Java 的 `Pattern`），既可读错又少重复解析（各语言细节以官方文档为准）。
- **校验与提取写法不同**：校验整串必须加 `^...$` 或用整串匹配函数；提取片段反而不加锚点，加了反而找不到中间内容。
- **调试手法**：写不对时把模式拆小逐段验证，先固定字面量部分跑通，再逐个换上字符类和量词，比盯着整串猜快得多。

### 新手易错点

- **拿正则解析 HTML/JSON**：嵌套结构不是正则能完整描述的，取一两个简单字段可以，解析整体请用专门解析器。
- **在模式里写空格求好看**：多数引擎默认空格是字面空格，会悄悄匹配失败；想分组排版就用注释模式（具体开关以官方文档为准）或老实写紧凑。
- **忘记原始字符串**：在代码里直接写 `"\d"` 时，字符串层先吃掉一层反斜杠，常变成别的意思；各语言有各自的免转义写法（原文对照表已给）。
- **量词叠在量词后面**：`a**` 不是"更贪"，多数引擎直接报语法错；`a*?` 才是懒惰量词，别混。
- **范围写反**：`[z-a]` 这类起止颠倒的范围会报错或无结果，写范围时起小终大。
- **方括号里乱放 `^`**：`^` 只在方括号第一个位置才是取反，写到中间就是普通的脱字符本身。
- **用 \w 校验中文名等场景**：`\w` 默认含字母数字下划线（及部分 Unicode 字母），它不是"英文字母"的同义词，严格场景写明确的方括号范围。
- **日期只验形状不验合法性**：`\d{4}-\d{2}-\d{2}` 会放行 2026-13-40，正则管形状，月份天数合不合法交给日期库判断。
- **手机号邮箱抄宽松版当严格校验**：速查表里的模式多为"够用版"，注册、支付等强校验场景要走业务校验或发送验证，不能只靠一段模式。
- **对用户输入直接拼模式**：把外部输入原样拼进模式，括号、星号会改变语义甚至触发回溯；拼前先做字面量转义处理。

## 回溯与匹配体量定量：步数、长度与组合数算一算

本节只算数。原文“回溯优化”一节已讲定性结论与改法，这里只把步数、长度、组合数算出来，帮你判断一个模式离“爆炸”还有多远。

口径先说清：**切分种数**是纯组合数，用 Python 就能复算，与引擎无关；**步数**是某个调试器数出来的引擎动作数，随引擎、版本、工具而变，不同工具只认量级、不认绝对值；凡标“估算口径”的数字，生产值以实测为准。

### 灾难性回溯：切分种数先算，步数再看

- `(a+)+$` 匹配 n 个 `a` 时，内层 `a+` 与外层 `+` 都能认领同一批 `a`，n 个 `a` 有 `2^(n-1)` 种切成若干组的方式，失败时引擎要把这些方式走完才认输。
- 切分种数随 n 翻倍：

| n（a 的个数） | 切分种数 2^(n-1) |
|---|---|
| 3 | 4 |
| 5 | 16 |
| 10 | 512 |
| 20 | 524288 |
| 25 | 16777216 |
| 30 | 536870912 |

- n 从 10 加到 20，切分种数从 512 涨到 524288，是 1024 倍，即 `2^10` 倍；n 从 20 加到 30 再涨 1024 倍，到 536870912 种。
- 步数量级用 regular-expressions.info 公布的 RegexBuddy debugger 实测值锚定：`(x+x+)+y` 对 10 个 `x` 且无 `y` 的输入要 2557 步，11 个 `x` 要 5117 步，12 个 `x` 要 10237 步；每多 1 个 `x`，步数约翻一倍（5117 / 2557 ≈ 2.00，10237 / 5117 ≈ 2.00）。
- 注意切分种数不等于步数：12 个 `x` 的切分种数是 `2^11 = 2048` 种，但实测步数是 10237 步，约 5 倍于切分种数，因为每种切分内部还有多次“吃字符、试锚点、回吐”的动作。
- 同一个 `(x+x+)+y`，19 个 `x` 时 debugger 步数超过 100 万，工具不再完整展示；20 个 `x` 的切分种数已是 524288 种，步数只会更高。
- 指数只发生在**失败**输入上：输入是 n 个 `a` 后跟一个 `b`（或缺了 `y`），`$` 永远对不上，引擎才被迫走完全部切分；输入本身就能匹配成功时，贪婪量词第一口就吃对，几步就结束。
- 线性引擎作对照：RE2 / Go `regexp` 这类自动机引擎把模式一次编译成状态机，n 个字符约走 n 步，30 个 `a` 约 30 步量级，与回溯引擎的 536870912 种切分不在一个量级；代价是不支持反向引用与环视。

【算例 1】`(a+)+$` 对 10 个 `a` 后跟 `b` 的输入：切分种数 `2^9 = 512`；把 `a` 加到 20 个，切分种数 `2^19 = 524288`，是 10 个时的 1024 倍；再加到 30 个是 `2^29 = 536870912` 种。每多 1 个 `a`，工作量约翻一倍，这就是“看着只长了几个字符，突然就卡死”的算术原因。

### 贪婪 vs 懒惰：同一输入，吃掉的字符数

- `<a>1</a>` 全长 8 个字符：贪婪 `<.*>` 一口吃掉 8 个，懒惰 `<.*?>` 只吃 3 个（`<a>`），相差 5 个字符。
- `"a" and "b"` 全长 11 个字符：贪婪 `".*"` 吃掉整串 11 个，懒惰 `".*?"` 分两次各吃 3 个（`"a"`、`"b"`），两次合计 6 个字符，剩下 5 个字符（` and `）不在任何一次匹配里。
- `"价格100元200块"`：贪婪 `\d+` 匹配 2 次，每次 3 位，合计吃掉 6 位数字；懒惰 `\d+?` 匹配 6 次，每次只吃 1 位，合计也是 6 位——总数相同，次数从 2 次变成 6 次。
- 长度差只在“有多个可停位置”时出现：输入里只有一个 `>`，贪婪与懒惰吃得一样多；差 5 个字符的前提是输入里有两个 `>` 可供选择。

【算例 2】`<a>1</a>`：贪婪 8 − 懒惰 3 = 5 个字符的差；换成 `<a>12</a>`（全长 9 个字符），贪婪吃 9 个，懒惰仍吃 3 个，差扩大到 6 个字符——差值等于贪婪多吃掉的中间内容长度，每多 1 个中间字符，差就多 1。

### 捕获组与组合数：分组数与分支数

- 分组数按左括号数：`(\d{4})-(\d{2})-(\d{2})` 有 3 个捕获组；`^1[3-9]\d{9}$` 有 0 个；邮箱宽松版 `^[\w.-]+@[\w-]+(\.[\w-]+)+$` 有 1 个。
- `(ab)+` 对 `"ababab"`：1 个分组重复 3 次，匹配总长 6 个字符；写成 `ab+` 时 `+` 只管 `b`，同一输入按全串匹配（`fullmatch`）就失败——分组数差 1 个括号，全串匹配结果从 6 个字符变成 0 个（只按 `search`/`match` 则仍能命中开头的 `ab`，2 个字符）。
- 分支数是乘法：`(a|b)(c|d)` 每组 2 个分支，合计 `2 × 2 = 4` 种组合；`(a|b){n}` 是 `2^n` 种，n=3 时 8 种，n=10 时 1024 种。
- 量词 `{m,n}` 的长度档数是 `n − m + 1`：`a{2,4}` 能匹配 2、3、4 个 `a`，共 3 档；`a{0,5}` 是 6 档。
- 手机号 `^1[3-9]\d{9}$` 的号码空间：第 1 位固定是 1，第 2 位 7 种（3–9），后 9 位每位 10 种，合计 `1 × 7 × 10^9 = 7000000000` 个号码，约 70 亿。
- 日期形状 `\d{4}-\d{2}-\d{2}` 的形状空间是 `10^4 × 10^2 × 10^2 = 100000000` 种，即 1 亿种；但一年只有 365 天（闰年 366 天），形状空间是真实日期数的约 27 万倍——这就是“只验形状不验合法性”的数量含义。

【算例 3】`(a|b){10}` 有 `2^10 = 1024` 种组合；再套一层外层量词写成 `((a|b){10})+`，每多一次外层重复就多 1024 倍的组合可能——嵌套的代价是乘法，不是加法。

### 常见模式的长度与步数对照

| 模式 | 输入 | 步数 / 量级 | 口径 |
|---|---|---|---|
| `(x+x+)+y` | 10 个 x，无 y | 2557 步 | regular-expressions.info / RegexBuddy debugger 实测值 |
| `(x+x+)+y` | 12 个 x，无 y | 10237 步 | 同上；比 10 个 x 时约 4 倍 |
| `(x+x+)+ +y`（占有量词，外层 `+` 写成 `++`） | 21 个 x，无 y | 7 步 | 同上；该来源口径为 6 步匹配全部 x，1 步确认 y 失败 |
| `(a+b+\|c+d+)+y` | `aaaabbbbccccdddd`（16 字符） | 54 步 | 同上；分支互斥，步数线性 |
| `^1[3-9]\d{9}$` | 11 位手机号 | 约 12 步 | 估算口径：每位 1 步加锚点，生产值以实测为准 |
| `(a+)+$`（RE2 / Go regexp） | 30 个 a 后跟 b | 约 30 步 | 估算口径：线性引擎 n 步量级；回溯引擎同期是 2^29 种切分 |

- 读表方法：先看量级是指数、线性还是常数，再看 n=10 与 n=12 两行的倍数；步数绝对值只在同一工具、同一引擎下可比，跨工具比数字没有意义。
- regex101 的 debugger 步数同样是“该工具实测值”：换 flavor（PCRE2 / Python / JavaScript）或换版本，同一模式同一输入的步数会变；上线前以你实际用的引擎实测为准。

【算例 4】`(x+x+)+y` 步数翻倍验证：10 个 `x` 是 2557 步，按“每多 1 个 x 翻一倍”推算，12 个 `x` 应为 `2557 × 2^2 = 10228` 步；实测 10237 步，相差 9 步，约 0.09%，吻合翻倍规律。反推 11 个 `x`：`2557 × 2 = 5114` 步，实测 5117 步，相差 3 步。

### 边界条件

1. 空串与下限：`(a+)+` 至少要 1 个 `a`，空串没有可切分的前缀，引擎第一步就失败，不产生回溯；指数爆炸的前提是“有足够长的可切分前缀”。
2. 成功输入不爆炸：输入是 30 个 `a` 且以 `$` 结尾时，`(a+)+$` 贪婪第一口就吃完并一次通过；只有尾部多个 `b`、缺 `y` 这类“差一点就对”的失败输入才会走完全部切分。
3. 懒惰不治灾难回溯：`(a+?)+$` 只是把切分从“先长后短”改成“先短后长”，失败时同样要遍历 `2^(n-1)` 种切分；想截断回溯要用占有量词或原子组，不是换懒惰。
4. 步数口径不可跨工具比较：2557 步、10237 步是 RegexBuddy debugger 的值，regex101 与 Python `re` 没有公开的同口径步数，换工具要重测；本节所有“约多少步”的估算口径数字，生产值以实测为准。

## 原理剖析

本节只把原文已有章节给出的结论拆开讲清机制：不引入新概念，不补新数字，数字一律复用定量节已核验的算例；凡原文没展开的点，文中明确标注，不作定论。

### 贪婪与懒惰：先吃多少，再回吐多少

原文「贪婪 vs 懒惰」一节的结论是：默认贪婪，`.*` 尽量多吃；加 `?` 变懒惰，`.*?` 尽量少吃。机制是同一套“先吃、再按需回吐”：贪婪先把能吃的全吃掉，再为让后续模式对上而逐个回吐；懒惰先只吃最少的一点，再为让后续模式对上而逐个多吃。两者最后都可能停在同一个位置，差别在于出发点不同——贪婪从“最多”往回退，懒惰从“最少”往前进。

定量节把这个差别算成了字符数（出处：定量节「贪婪 vs 懒惰」小节）：`<a>1</a>` 全长 8 个字符，贪婪 `<.*>` 一口吃掉 8 个，懒惰 `<.*?>` 只吃 3 个（`<a>`），相差 5 个字符。` "a" and "b"` 全长 11 个字符，贪婪 `".*"` 吃掉整串 11 个，懒惰 `".*?"` 分两次各吃 3 个（`"a"`、`"b"`），两次合计 6 个字符，剩下 5 个字符（` and `）不在任何一次匹配里。数字提取同理：`"价格100元200块"` 里，贪婪 `\d+` 匹配 2 次，每次 3 位，合计吃掉 6 位数字；懒惰 `\d+?` 匹配 6 次，每次只吃 1 位，合计也是 6 位——总数相同，次数从 2 次变成 6 次。

同一个差别只在“有多个可停位置”时出现（出处：定量节同小节）：输入里只有一个 `>`，贪婪与懒惰吃得一样多；差 5 个字符的前提是输入里有两个 `>` 可供选择。【算例 2】也只算了长度差：`<a>1</a>` 是贪婪 8 − 懒惰 3 = 5 个字符；换成 `<a>12</a>`（全长 9 个字符），贪婪吃 9 个，懒惰仍吃 3 个，差扩大到 6 个字符——差值等于贪婪多吃掉的中间内容长度，每多 1 个中间字符，差就多 1。

原文未展开：贪婪回吐时每一步具体走多少步，定量节只给了总步数与长度差，未给单次回吐的步数分解，不作定论。

### 量词三形态：回吐的有无决定成败

原文「量词三形态对照表」的结论是：贪婪 `a*` 尽量多、回吐；懒惰 `a*?` 尽量少、回吐；占有 `a*+` 尽量多、不回吐。机制差别只在最后一步——前两种吃下去之后还可以还回去，第三种吃下去就不还。

原文给出的分界例子是 `a*+ab` 对 `aaab`（出处：原文「量词三形态对照表」）：`a*+` 一口吃掉 `aaa`，后面只剩 `b`，凑不出 `ab`，又不许回吐，于是整体失败；换成贪婪的 `a*ab` 则能成功，因为贪婪回吐一个 `a` 凑出 `ab`。同一个输入、同一串字符，成败只由“允不允许回吐”决定，而不是由“吃多吃少”决定。

原文还给出等价关系：占有量词与原子组 `(?>...)` 是一回事，`a*+` 等价于 `(?>a*)`；回溯节的优化讲的就是它。支持情况原文已述：Java 早已支持；Python 3.11+ 支持；JS 不支持，占有需求改写成等价形式（如先收紧字符集、或用锚点限定范围）。

原文未展开：占有量词在 Python 3.11+ 与 Java 下的步数是否与定量节的 RegexBuddy 实测值相同，定量节的步数口径已声明随引擎、版本、工具而变，不作定论。

### 回溯：切分种数为什么翻倍

原文「回溯优化」一节的结论是：嵌套量词 `(x+)+`、`(a|ab)*` 是重灾区，灾难性回溯的根源在嵌套量词。机制是：内层量词与外层量词都能认领同一批字符，同一串字符有多少种“切成若干组”的分法，引擎在失败时就要把这些分法走完才认输。

定量节把分法算成了切分种数（出处：定量节「灾难性回溯」小节，`(a+)+$` 匹配 n 个 `a` 时切分种数为 `2^(n-1)`）：n=3 时 4 种，n=5 时 16 种，n=10 时 512 种，n=20 时 524288 种，n=25 时 16777216 种，n=30 时 536870912 种。n 从 10 加到 20，切分种数从 512 涨到 524288，是 1024 倍，即 `2^10` 倍；n 从 20 加到 30 再涨 1024 倍，到 536870912 种。每多 1 个 `a`，工作量约翻一倍，这就是“看着只长了几个字符，突然就卡死”的算术原因（出处：定量节【算例 1】：`(a+)+$` 对 10 个 `a` 后跟 `b` 的输入切分种数 `2^9 = 512`；加到 20 个是 `2^19 = 524288`，是 10 个时的 1024 倍；再加到 30 个是 `2^29 = 536870912` 种）。

步数是另一个口径，定量节用 regular-expressions.info 公布的 RegexBuddy debugger 实测值锚定（出处：定量节同小节）：`(x+x+)+y` 对 10 个 `x` 且无 `y` 的输入要 2557 步，11 个 `x` 要 5117 步，12 个 `x` 要 10237 步；每多 1 个 `x`，步数约翻一倍（5117 / 2557 ≈ 2.00，10237 / 5117 ≈ 2.00）。切分种数不等于步数：12 个 `x` 的切分种数是 `2^11 = 2048` 种，但实测步数是 10237 步，约 5 倍于切分种数，因为每种切分内部还有多次“吃字符、试锚点、回吐”的动作。同一个 `(x+x+)+y`，19 个 `x` 时 debugger 步数超过 100 万，工具不再完整展示；20 个 `x` 的切分种数已是 524288 种，步数只会更高。【算例 4】验证了翻倍规律：10 个 `x` 是 2557 步，按“每多 1 个 x 翻一倍”推算，12 个 `x` 应为 `2557 × 2^2 = 10228` 步，实测 10237 步，相差 9 步，约 0.09%；反推 11 个 `x` 为 `2557 × 2 = 5114` 步，实测 5117 步，相差 3 步。

指数只发生在失败输入上（出处：定量节同小节与「边界条件」第 2 条）：输入是 n 个 `a` 后跟一个 `b`（或缺了 `y`），`$` 永远对不上，引擎才被迫走完全部切分；输入本身就能匹配成功时，贪婪量词第一口就吃对，几步就结束。输入是 30 个 `a` 且以 `$` 结尾时，`(a+)+$` 贪婪第一口就吃完并一次通过；只有尾部多个 `b`、缺 `y` 这类“差一点就对”的失败输入才会走完全部切分。

对照是线性引擎（出处：定量节同小节与「常见模式的长度与步数对照」表）：RE2 / Go `regexp` 这类自动机引擎把模式一次编译成状态机，n 个字符约走 n 步，30 个 `a` 约 30 步量级，与回溯引擎的 536870912 种切分不在一个量级；代价是不支持反向引用与环视。

原文未展开：懒惰版嵌套量词在同一失败输入上的具体步数表，定量节「边界条件」第 3 条只给了定性结论——`(a+?)+$` 只是把切分从“先长后短”改成“先短后长”，失败时同样要遍历 `2^(n-1)` 种切分——未给懒惰版的实测步数，不作定论。

### 环视断言：不吃字符，只看前后文

原文「环视断言实战」一节的结论是：环视断言不消耗字符、只看前后文，是“隐形条件”。机制是：断言本身不吃掉任何字符，它只在当前位置检查前面或后面的文本是否符合条件，符合才放行、让后面的模式继续，不符合就让当前位置失败、换下一个位置再试。

原文的四种写法（出处：原文「环视断言实战」表）：`(?=...)` 肯定顺序环视，如 `\d+(?=元)` 匹配“100元”里的 100；`(?!...)` 否定顺序环视，如 `\d+(?!元)` 匹配不带“元”的数字；`(?<=...)` 肯定逆序环视，如 `(?<=@)\w+` 取 @ 后面的用户名；`(?<!...)` 否定逆序环视，如 `(?<!\$)\d+` 排除 $ 开头的金额。原文给出的代码只复用这两行：`re.findall(r'\d+(?=元)', '100元和200块')` 得 `['100']`；`re.sub(r'(?<=\d),(?=\d)', '', '1,000,000')` 去千分位逗号得 `'1000000'`。密码强度校验是环视的经典场景，原文写法为 `^(?=.*[A-Z])(?=.*\d).{8,}$`。

原文还给了一个限制：逆序环视 `(?<=)` 里大多语言要求定长（如 `(?<=ab|abc)` 非法定长会报错），写之前确认。疑难杂症一节也补充了兼容性：后行断言 `(?<=)` / `(?<!)` 是 ES2018 才进标准的，各语言支持时间不一，旧环境会直接报语法错。

原文未展开：环视断言内部失败时是否回溯、走多少种组合，原文与定量节均未给出环视的切分种数或步数算例，不作定论。

## 实战案例

### 案例一：想取标签内容，`<.*>` 一口吃掉整串

- 现象：原文「贪婪 vs 懒惰」一节给出的例子是：`<.*>` 会匹配整个 `<a>1</a>`，`<.*?>` 只匹配 `<a>`。想取的是第一个标签，实际拿到的是从第一个 `<` 到最后一个 `>` 的整串。
- 排查：按定量节的字符数核对（出处：定量节「贪婪 vs 懒惰」小节）：`<a>1</a>` 全长 8 个字符，贪婪 `<.*>` 一口吃掉 8 个，懒惰 `<.*?>` 只吃 3 个（`<a>`），相差 5 个字符。差 5 个字符的前提是输入里有两个 `>` 可供选择，贪婪先吃到最后一个 `>` 再回吐，懒惰先停在第一个 `>`。同理可核对引号内容：`"a" and "b"` 全长 11 个字符，贪婪 `".*"` 吃掉整串 11 个，懒惰 `".*?"` 分两次各吃 3 个（`"a"`、`"b"`），两次合计 6 个字符。原文「5 个常见坑」第 1 条的结论与此一致：想取标签内容用 `<.*?>` 而不是 `<.*>`。
- 结论：取第一个标签、第一个引号内容这类“到第一个结束符就停”的需求，用懒惰写法 `<.*?>`、`".*?"`；原文未展开该输入在某个具体引擎下的步数，不作定论。

### 案例二：`(a+)+$` 在失败输入上卡死，改写比换懒惰管用

- 现象：原文「回溯优化」一节给出的灾难版是：`(a+)+$` 遇到原文所举的长串加尾部字符的输入直接卡死；原文「5 个常见坑」第 3 条的结论相同：`(a+)+$` 这类嵌套量词在长字符串上能卡死，能确定边界就用具体字符集。
- 排查：先算切分种数（出处：定量节「灾难性回溯」小节与【算例 1】）：`(a+)+$` 对 10 个 `a` 后跟 `b` 的输入，切分种数 `2^9 = 512`；把 `a` 加到 20 个，切分种数 `2^19 = 524288`，是 10 个时的 1024 倍；再加到 30 个是 `2^29 = 536870912` 种。再看步数量级（出处：定量节同小节，regular-expressions.info / RegexBuddy debugger 实测值）：`(x+x+)+y` 对 10 个 `x` 且无 `y` 的输入要 2557 步，11 个 `x` 要 5117 步，12 个 `x` 要 10237 步，每多 1 个 `x` 约翻一倍；19 个 `x` 时步数超过 100 万。失败是前提：输入本身就能匹配成功时，贪婪第一口就吃对，几步就结束；只有“差一点就对”的失败输入才会走完全部切分（出处：定量节「边界条件」第 2 条）。换懒惰不治本（出处：定量节「边界条件」第 3 条）：`(a+?)+$` 只是把切分从“先长后短”改成“先短后长”，失败时同样要遍历 `2^(n-1)` 种切分。
- 结论：按原文「回溯优化」一节的改法走：能改写成等价的无嵌套形式就改写，原文给出的例子是 `a+$`；或用占有量词 / 原子组截断回吐，原文写法为 `(?>a+)$`，并说明占有量词与原子组是一回事。定量节的对照表也给出量级对比（出处：定量节「常见模式的长度与步数对照」表）：`(x+x+)+ +y`（占有量词，外层 `+` 写成 `++`）对 21 个 `x` 且无 `y` 的输入只要 7 步，该来源口径为 6 步匹配全部 x、1 步确认 y 失败；而线性引擎 RE2 / Go `regexp` 对 30 个 `a` 后跟 `b` 约 30 步。原文未展开：该灾难版输入在 Python `re` 下的具体步数，定量节已声明步数口径随引擎、版本、工具而变、不同工具只认量级、不认绝对值，不作定论。

## 小技巧与冷知识

【小技巧】校验整串时 `re.fullmatch` 比 `^...$` 更严：Python 里 `$` 还会在末尾换行符之前匹配，所以 `re.search(r"^\d+$", "123\n")` 是能通过的，字符串末尾偷偷多个换行符都发现不了；`fullmatch` 要求整个字符串从头到尾都符合，多一个换行符就失败。写"整串校验"类模式时优先用 `fullmatch`，`^$` 只留给确实要兼容多行或旧代码的场合。

【小技巧】`re.findall` 里一旦出现捕获组，返回的就不是整段匹配：`re.findall(r"(\d+)-(\d+)", "2026-10")` 拿到的不是 `["2026-10"]`，而是 `[("2026", "10")]` 这样的元组列表，整段匹配本身被丢掉了。只想要整段匹配时把分组改成非捕获 `(?:...)`；想同时要整段和分组时改用 `finditer`，再对每个 Match 对象调 `.group(0)`、`.group(1)`。

【小技巧】`re.I` 会让字符范围也跟着忽略大小写：`re.findall(r"[a-z]+", "AbC", re.I)` 能匹配到 `AbC`，因为 `i` 标志下 `[a-z]` 等价于 `[a-zA-Z]`。想"只匹配小写字母、但别的标志还要开"时，别指望靠大小写敏感的范围来收紧，要么不用 `re.I`、要么把范围显式写成不区分大小写的反向逻辑，用 `(?-i:[a-z])` 在局部关掉它。

【小技巧】方括号里想写字面的 `]`，把它放在第一个位置：`[]]` 匹配的就是一个 `]`，`[^]]` 表示"不是 `]` 的任意字符"。同理连字符想当字面量就放最后（原文已提 `[a-z-]`），`^` 只在第一个位置才是取反——方括号内部这三个符号的"特殊位置"记住了，写字符类时就不用每次都翻文档。

【小技巧】写 `|` 分支时把更长的分支放前面：引擎按从左到右的顺序试分支，第一个能匹配的就胜出，`re.search(r"a|ab", "ab")` 匹配到的只是 `a`，而不是更长的 `ab`。写"GET|POST"这类枚举、或"全称|简称"这类长短并存的分支时，先排长的再排短的；否则短分支先赢，长分支永远没机会。

【小技巧】全局查找的匹配不会重叠：`re.findall(r"aa", "aaa")` 只返回一个 `"aa"`，剩下的一个 `a` 不够再凑一次，引擎不会回头从第二个字符重新开始找。想找重叠出现的位置，要用环视把"位置"和"内容"分开，比如 `re.findall(r"(?=(aa))", "aaa")` 能找到两处；数"出现次数"之前先确认你要的是不重叠匹配还是重叠匹配。

【小技巧】Python 里写 `"\b"` 不是单词边界，是退格符：普通字符串里 `\b` 会被字符串层先转成 `\x08`（退格），模式拿到手时单词边界已经没了，这是比 `"\d"` 更隐蔽的坑——`"\d"` 只是原样保留反斜杠，`"\b"` 则直接变了意思。写模式一律用 raw string `r"\b"`，或者把反斜杠写双份；凡是模式里出现 `\b`、`\n`、`\t` 这类在字符串层也有含义的转义，raw string 不是习惯问题，是正确性问题。

【小技巧】`re.sub` 的 `count` 参数可以只替换前 N 处：`re.sub(r"\d+", "#", "a1b2c3", count=1)` 只把第一个数字换掉，后面的原样保留。日志脱敏"只打码第一处"、模板替换"只换第一个占位符"这类场景不用先 `search` 再切片拼接，一行 `count=1` 就够；默认 `count=0` 才是全部替换。

【小技巧】大文本上找全部匹配用 `finditer` 而不用 `findall`：`findall` 会先把所有结果攒成一个列表再返回，几十万行日志能一次吃掉大量内存；`finditer` 返回惰性迭代器，一次只产一个 Match 对象，边找边处理。逐行清洗日志、流式抽取字段时，`for m in re.finditer(...)` 是默认写法，`findall` 只留给结果集很小的场合。

【小技巧】多行模式下想锚定"整串开头结尾"用 `\A` 和 `\Z`：开了 `re.M` 之后 `^`、`$` 会变成"每行开头结尾"，`re.search(r"^ERROR", text, re.M)` 会在每一行都试；而 `\A` 只认整个字符串的开头、`\Z` 只认整个字符串的结尾，不受 `re.M` 影响。校验"整段文本必须以某标记开头"时写 `\A`，比"开多行又想办法排除行首"可靠得多。

【小技巧】行内标志 `(?i)` 只能写在模式最开头：Python 3.11 起，`re.compile(r"a(?i)b")` 会直接报错（global flags not at the start of the expression），旧版本只是悄悄接受。想让标志只对模式的一部分生效，改写成作用域形式 `(?i:...)`，比如 `r"(?i:abc)def"` 只对 `abc` 忽略大小写，后面的 `def` 仍区分大小写。

【小技巧】`[^a]` 能匹配换行符，但 `.` 不能：取反字符类表示"除了 a 之外的任意字符"，换行符也在其中，所以 `re.findall(r"[^x]+", "a\nb")` 会把换行符一起吃掉；而 `.` 默认不匹配换行符，想跨行取任意字符才要写 `[\s\S]` 或开 `re.S`。跨行文本切分时这个差别很关键：用取反字符类当"分隔符之外的一切"时，换行符会被悄悄吞进结果里。

【冷知识】`grep` 这个名字本身就是一段正则操作：它来自 ed 编辑器的命令 `g/re/p`，意思是"全局搜索（global）符合正则表达式（re）并打印（print）"。所以 `grep`、`grep -E`（扩展正则）、`grep -P`（Perl 兼容正则）这三个命令的区别，本质是三种正则方言的区别，不是三个工具的区别。

【冷知识】正则表达式是 1950 年代的形式语言理论产物：数学家 Kleene 在 1951 年提出用它描述"正则语言"，1968 年 Ken Thompson 在论文《Regular Expression Search Algorithm》里把它变成可执行的搜索算法，并写进了 QED 编辑器——今天几乎所有语言的正则引擎，都是这条线的后代。

【冷知识】Python 里同一个分组名不能定义两次：`(?P<year>\d+)-(?P<year>\d+)` 会直接报 `redefinition of group name`，即使两个分组长得一模一样。想在模式里复用同一个名字，要么用反向引用 `(?P=year)` 引用前面已定义的组，要么改用编号；这是命名分组"按名引用"的代价——名字在模式里是唯一的。

【冷知识】`[[:digit:]]` 这种 POSIX 字符类在 Python 和 JS 的正则里不存在：它是 POSIX 规范（grep/sed/awk）里的写法，`[[:alpha:]]`、`[[:space:]]` 这类方括号套方括号的语法，拿到 Python 的 `re` 或 JS 里会被当成嵌套字符类解析，结果完全不是你想要的。跨工具抄模式时先认方言，POSIX 的写法不能直接粘贴进 Python/JS。

## 面试与自测

1. 想取标签内容时为什么要用 `<.*?>` 而不是 `<.*>`？两者在 `<a>1</a>` 上各匹配出什么？
2. 同一个带 `/g` 的正则连续调用 `.test()`，结果为什么会 true、false 交替出现？三种解法各是什么？
3. 哪些场景正则不够用、必须换专门工具？判断标准是什么？

4. `(a+)+$` 对 20 个 `a` 后跟 `b` 的输入有多少种切分？比 10 个 `a` 时翻了多少倍？`(x+x+)+y` 从 10 个 `x` 的 2557 步涨到 12 个 `x` 的 10237 步，符合什么规律？为什么把量词改成懒惰救不了灾难性回溯？

### 参考答案

1. 默认贪婪：`.*` 尽量多吃，`<.*>` 会匹配整个 `<a>1</a>`；加 `?` 变懒惰，`<.*?>` 尽量少吃，只匹配 `<a>`。同理，引号内容用 `".*"` 会对 `"a" and "b"` 一口吃掉整串，`".*?"` 则逐个取出 `"a"`、`"b"`。
2. 带 `g`（或 `y`）的正则对象自带 `lastIndex` 状态，`test`/`exec` 每次从 `lastIndex` 处开始找；找到后 `lastIndex` 推进到匹配末尾，找不到时才重置为 0。解法：只做真假判断就别加 `g`；必须复用带 `g` 的正则时，每次调用前手动置 `regex.lastIndex = 0`，或每次新建一个正则对象。
3. 解析 HTML/XML 整体、解析 JSON（嵌套结构超出正则表达能力）、括号配对与嵌套注释（个别引擎的平衡组除外）都不能只用正则，改用解析器（BeautifulSoup / lxml / DOMParser、json.loads / JSON.parse）或手写解析器。判断标准：结构有嵌套、要算语义（日期合法、邮箱真实、数值大小），就别只用正则；正则只管「长什么样」，不管「对不对」——日期是否真实存在交给日期库，邮箱是否真实有效靠发一封验证邮件。

4. 20 个 a 有 2^19=524288 种切分，是 10 个 a 时 512 种的 1024 倍，每多 1 个 a 翻一倍。(x+x+)+y 从 10 个 x 的 2557 步涨到 12 个 x 的 10237 步，4 倍，符合指数翻倍。懒惰只改顺序，失败时仍遍历全部切分才认输，救不了灾难回溯。
