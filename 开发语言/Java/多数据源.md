# 多数据源（dynamic-datasource）

## 1. 核心概念

一个应用连多个数据库时，需要解决「这次操作走哪个库」。`dynamic-datasource`（baomidou 出品，与 MyBatis-Plus 同门）的做法是：把每个数据源注册进一个路由 `DataSource`，调用前通过 `ThreadLocal` 里的 key 决定取哪一个连接。`@DS("oceanbase")` 注解本质就是在方法执行前把 key 推入一个栈，执行完弹出，所以它天然支持嵌套切换（查主库的方法里调查 OB 的方法，各查各的）。

依赖：`com.baomidou:dynamic-datasource-spring-boot-starter`（和 MyBatis-Plus 同门）。版本要和 Boot 对齐：Boot 2.7 用 3.5.x 线的 starter，上了 Boot 3 要换 spring-boot3-starter，别引错。

```yaml
spring:
  datasource:
    dynamic:
      primary: master          # 默认数据源，方法上没标 @DS 时走它
      strict: true             # 找不到指定数据源直接报错，而不是悄悄走默认（建议开，防写错名字）
      datasource:
        master: { url: jdbc:mysql://.../db1, username: root, password: xxx }
        oceanbase: { url: jdbc:mysql://.../db2, username: root, password: xxx }
```

```java
@DS("oceanbase")   // 方法/类上一个注解就切库
public List<Order> listFromOb() { return mapper.selectList(null); }
```

`strict: true` 是经验上强烈建议开的：默认 false 时 `@DS` 名字拼错会静默回退到主库，查错库还不报错，是最难查的那类 bug。

## 2. 切换的粒度与原理

- `@DS` 可标在类上（整个 Service 走这个库）或方法上（方法优先）。标在 Mapper 接口上也可以，但经验上标 Service 层更清晰：事务边界在 Service，数据源和事务在同一层才对得齐。
- 切换靠 AOP + ThreadLocal 栈实现，所以和 `@Async`、`@Transactional` 一样有**同类自调用失效**的问题：同类内 `this.method()` 调带 `@DS` 的方法，注解不生效。解法同样是拆 Bean 或注入自己。
- 异步线程里 ThreadLocal 不跟随：`@Async` 方法里要切库，`@DS` 标在异步方法本身上（新线程执行时 AOP 会重新入栈），不能指望调用方标的那个传过去。

## 3. 事务注意（最重要的一节）

事务注意：`@DS` + `@Transactional` 混用时，Spring 的事务管理器在事务开启时就从路由数据源取定了一个连接，事务期间再切 `@DS` 也不换连接——**声明式事务默认只管开启事务那一刻的数据源**。所以：

- 单库事务：`@DS` 和 `@Transactional` 标在同一个方法上即可（先切库、再开事务，dynamic-datasource 的 starter 处理了这个顺序）。
- 跨库事务：本地事务管不了两个库，别想当然。要强一致上 Seata（AT 模式对业务侵入小，但要给每张表配 undo_log 并实测回滚）；能接受最终一致就走消息表/对账补偿，金融场景经验上后者更常见。
- 一个方法里先写主库再写 OB、中间抛异常，主库回滚、OB 若在另一事务里已提交则不回滚——这种「半成功」状态要在设计时就想清楚幂等与补偿。

## 4. 与项目栈的落点

- 神农 e 贷这种「MySQL + OceanBase」双跑的场景就靠它：同一套 MyBatis-Plus 代码，`@DS` 一标就切到 OB 跑兼容性验证。OceanBase 是 MySQL 模式时 JDBC 驱动与方言基本按 MySQL 处理，但自增主键、部分函数行为有差异，见 [MyBatis-Plus](开发语言/Java/MyBatis/MyBatis-Plus.md) 里 ASSIGN_ID 的说明。
- 每个数据源底层都是独立 Druid 连接池，池参数（max-active 等）要在各自数据源下分别配，别只配一份指望全局生效；监控页里也会按数据源分开统计，见 [Druid](开发语言/Java/Druid.md)。
- 数据源多了之后，健康检查和启动日志要能一眼看出每个库连没连上，建议启动时给每个数据源打一条探活日志。

## 5. 常见坑

- **密码等敏感配置别写死在 yml**：示例里的 `password: xxx` 只是占位，生产走环境变量或配置中心，且仓库是公开的，提交前先扫一遍。
- **`@DS` 标在 Controller 上没用**：Controller 里通常不直接操作 Mapper，且事务不在那一层；标 Service。
- **动态增减数据源**：starter 支持运行时 `addDataSource/removeDataSource`，做多租户按需建库时可用，但要注意移除前先确认没有在途事务。
- **PageHelper 与多数据源**：分页方言按连接自动识别，一般没问题；混用时留意方言配置别写死单一 DbType。

## 小技巧与冷知识

【小技巧】`@DS` 只对 public 方法生效：切换靠 Spring AOP 代理，private、final 方法上的 `@DS` 不会被代理拦截，注解写了也等于没写。切库方法一律写成 public，别把 `@DS` 标在 private 的工具方法上；排查“切库没生效”时，先看方法修饰符和是不是走代理调的，再去查配置。

【小技巧】`@DS` 和 `@Transactional` 写在同一个方法上时，两个注解在代码里的上下顺序不影响结果：dynamic-datasource 的切面排了优先级，保证先切库、再开事务，不是靠注解谁写在上面。别在调整注解顺序上浪费时间，顺序写反了也不会先开事务后切库；真正会坏事的是把两个注解拆到两个方法上（外层开事务、内层切库），那时连接已经取定了。

【小技巧】事务管理器要配成 dynamic-datasource 自带的 `DynamicDataSourceTransactionManager`：它知道事务开启时按当前 `@DS` 的 key 取连接；配成普通的 `DataSourceTransactionManager`，事务会直接绑死路由数据源之外的某一个库，`@DS` 在事务里就失灵了。Spring Boot 场景 starter 一般会自动配好，手动配事务管理器时先确认类型，别顺手 new 一个普通的。

【小技巧】`strict: true` 的校验发生在第一次取连接时，不是启动时：拼错名字的 `@DS` 方法只有被调用到才报错，冷门接口的拼写错误可能上线后才炸。 strict 只能保证“调用时立刻炸、不静默查错库”，保证不了“启动就发现”；上线前把所有标了 `@DS` 的方法跑一遍冒烟，别只测主链路。

【小技巧】本地只起一个库开发时，`strict: true` 会让 `@DS("oceanbase")` 的方法一调就报错：因为本地没有 oceanbase 这个数据源。解决办法是本地也配一个同名数据源、指向本地库（哪怕指向同一个 MySQL），让名字对得上；别为了本地方便把 strict 关了再上线，开关一忘就是生产静默查错库。

【小技巧】`@DS` 支持 SpEL 动态取 key：`@DS("#tenantId")` 或从请求头、方法参数里取租户标识，多租户按租户切库时不用为每个租户写一个方法。表达式里的变量要能在运行期取到（方法参数、ThreadLocal 里的租户上下文），取不到时按找不到数据源处理，strict 开着会直接报错而不是回退主库。

【小技巧】多数据源下别开 MyBatis 二级缓存：二级缓存按 Mapper 的 namespace + SQL 做 key，不认数据源，同一个 Mapper 查主库和查 OB 的结果会互相串——主库的缓存可能被 OB 的查询命中。dynamic-datasource 只路由连接，不管缓存；多数据源项目里二级缓存默认关掉，只留一级缓存（会话级、按连接走，不会串库）。

【小技巧】手动切库要用 `DynamicDataSourceContextHolder.push("oceanbase")` 时，必须在 finally 里 `poll()`：注解方式方法结束会自动弹栈，手动 push 不弹，线程池复用这个线程跑下一个任务时，还带着上一个任务的数据源 key。动态路由、框架代码里绕开注解切库的场景，一定要 push/finally/poll 成套写。

【小技巧】运行时动态增减数据源后，旧数据源的连接池不会自己消失：调 `addDataSource` 加了新库只是注册，要下线一个库得调 `removeDataSource`，它会关闭对应连接池并清理注册。多租户按需建库、租户退订删库时，只删注册不关池等于连接泄漏；移除前按原文说的先确认没有在途事务。

【冷知识】dynamic-datasource 和 MyBatis-Plus 是同一个组织 baomidou（苞米豆）出品，名字里的 dynamic 指路由是运行期动态决定的：数据源 key 在每次取连接时才从 ThreadLocal 栈顶读，而不是启动时写死绑定。所以同一个 Mapper、同一套代码能在不同调用间走不同库，路由发生在“取连接”那一刻，不是“启动配置”那一刻。

【冷知识】`@DS` 的栈式设计借鉴了“上下文栈”的思路：每次进入带 `@DS` 的方法就压栈、退出就弹栈，嵌套调用时内层方法用自己的 key、退出后自动恢复外层 key。理解这一点就明白为什么嵌套切换不用手动切回，也明白为什么“方法没走完就抛异常”也不用担心 key 残留——弹栈在 finally 里做，异常一样会弹。

## 6. 面试与自测

1. `@DS` 标在同类自调用的方法上为什么不生效？怎么修？
2. `@Transactional` 方法执行中途再切 `@DS`，新数据源会生效吗？为什么？
3. `@DS` 的数据源名字拼错、且 `strict` 没开，会发生什么？生产上怎么防？

### 参考答案

1. 不生效，因为切换靠 AOP + ThreadLocal 栈：同类内 `this.method()` 走的是对象本身、不经过代理，AOP 没机会入栈。修法：把带 `@DS` 的方法拆到另一个 Bean，或在类里注入自己（通过代理调自己）。
2. 不生效。Spring 事务管理器在事务开启时就从路由数据源取定了一个连接，事务期间再切 `@DS` 也不换连接。单库场景把 `@DS` 和 `@Transactional` 标在同一个方法上（先切库再开事务）；跨库事务本地事务管不了，要强一致上 Seata AT（每张表配 undo_log 并实测回滚），能接受最终一致就走消息表/对账补偿。
3. 会静默回退到默认数据源：查错库还不报错，是最难查的一类 bug。生产上开 `strict: true`，找不到指定数据源直接报错而不是悄悄走默认；数据源名拼写用常量集中管理，别手写字符串到处散。
