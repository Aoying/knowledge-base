# 限流熔断与降级

## 1. 核心概念

三个词管三件不同的事，别混用：

- **限流**：入口侧控速。请求量超过系统能处理的上限时，多余的直接拒绝或排队，保住系统不被打垮——是「我最多接这么多」。
- **熔断**：出口侧止损。依赖的下游已经变慢/报错时，快速失败不再调用，避免线程全卡在等下游上把自己拖死——是「它不行了，我先不等它」。
- **降级**：熔断或限流触发之后给调用方一个兜底结果（默认值、缓存旧值、友好提示），让业务以残缺但可用的形态继续——是「拿不到真数据时，给什么替代」。

## 2. 四种限流算法

| 算法 | 原理 | 特点 |
|---|---|---|
| 固定窗口计数器 | 按时间窗（如每秒）计数，超阈值拒绝，窗口切换清零 | 实现最简单；窗口临界点可突入 2 倍流量（窗口末尾和下个窗口开头各放满一波） |
| 滑动窗口 | 把窗口切成小格滚动统计 | 平滑掉临界突刺，精度与格数成正比，Sentinel 的统计即滑动窗口口径 |
| 漏桶 | 请求入桶，以恒定速率流出，桶满拒绝 | 输出绝对平稳，适合保护「处理速率恒定」的下游；不允许突发，积压即延迟 |
| 令牌桶 | 以恒定速率往桶里放令牌，请求拿到令牌才放行，桶可攒令牌 | 允许一定突发（攒的令牌一次用掉），平均速率仍受控；Guava RateLimiter、网关限流的主流选择 |

选型口径：控平均速率且容忍合理突发，用令牌桶；要整形到恒定速率喂给脆弱下游，用漏桶；计数器类适合做 QPS 上限这种粗粒度闸门。框架里算法多已封装，重点是每个接口该设多大的值（见第 7 节），不是手写算法。

## 3. Sentinel 的模型

Sentinel（Spring Cloud Alibaba 系，见 [Spring Cloud 概览](开发语言/Java/Spring/Spring-Cloud概览.md)）的三个基本概念：

- **资源**：被保护的对象，可以是一个接口、一个方法、一段代码块。用 `@SentinelResource` 注解或 `SphU.entry("资源名")` 定义。
- **规则**：流控规则（QPS/并发线程数阈值、调用关系限流）、熔断降级规则、热点参数规则、系统自适应规则、授权规则。规则可通过控制台或 Nacos 等数据源动态下发，不必改代码重启。
- **异常处理分工**（最容易写错的一点）：触发限流/熔断抛的是 `BlockException`，走 `blockHandler`；业务自身抛的异常走 `fallback`。两者分开写，混在一起会导致降级逻辑被限流误触发、或限流时返回了业务错误码。

```java
@SentinelResource(value = "submitApproval",
        blockHandler = "submitBlocked",      // 被限流/熔断时走这里
        fallback = "submitFallback")          // 业务异常时走这里
public Result submit(ApprovalCmd cmd) { ... }

public Result submitBlocked(ApprovalCmd cmd, BlockException e) {
    return Result.fail("系统繁忙，请稍后重试");      // 快速失败，不排队不重试
}
public Result submitFallback(ApprovalCmd cmd, Throwable e) {
    log.error("审批提交异常", e);
    return Result.fail("提交失败");
}
```

## 4. 熔断器三态

熔断器就是电路保险丝的状态机：

```text
闭合（正常放行，统计失败率/慢调用）
  └─ 指标越线 → 打开（直接快速失败，不调下游，计时中）
                  └─ 静默期到 → 半开（放少量试探请求）
                                  ├─ 试探成功 → 闭合（恢复）
                                  └─ 试探失败 → 重新打开
```

Sentinel 的熔断策略三种口径：**慢调用比例**（响应时间超阈值的占比越线）、**异常比例**、**异常数**。关键参数是统计窗口、最小请求数（样本太少不触发，避免低流量时误熔断）和熔断时长（对应「打开」状态的计时）。没有半开探测的「熔断」只是定时开关，下游没恢复就全量放行会造成二次雪崩——选组件和自研时先确认这一态在不在。

## 5. 降级与兜底策略

按数据时效容忍度从高到低选，别一刀切：

- **返回默认值/空结果**：适用于非关键展示位（推荐列表、附加信息），缺了不影响主流程。
- **读缓存旧值**：有缓存时降级读缓存，哪怕略过期也比报错强；缓存没兜住再退到默认值。
- **排队等待**：漏桶式削峰，把突发摊平（如批量任务入口）；同步接口慎用，等待即占用线程。
- **快速失败 + 明确文案**：写操作和强一致场景的正确选择。宁可明确说「稍后重试」，也不要返回假成功——降级写出脏数据比报错难收拾得多。

## 6. 两层分工：网关限流与应用限流

| 层 | 位置 | 粒度与职责 |
|---|---|---|
| 网关层 | Spring Cloud Gateway / Nginx | 粗粒度总闸：按路由、IP、租户控总量，挡掉明显过载与恶意流量，保护整个后端 |
| 应用层（Sentinel） | 每个服务进程内 | 细粒度：按资源、按热点参数（如单个客户号）限流，以及出方向的熔断——只有应用自己知道哪个下游在变慢 |

只有网关层，单实例的热点和下游故障它看不见；只有应用层，总入口没闸，洪峰先把连接数和网关打满。两层都要有，阈值口径对齐（网关总量 ≈ 各实例应用限流之和再留余量）。

## 7. 与现有系统的衔接

- **限流 ≠ 防重复提交**。审批流里「同一待办被连点两次」是幂等问题，靠状态机条件更新 + 幂等键解决（见 [REST 接口设计](工程实践/接口设计与文档.md) 的幂等设计）；限流解决的是「单位时间总量过载」。把防重当限流做（如按用户限 1 QPS）既挡不住慢速重复提交，又误伤正常操作。
- **接口保护的正确组合**：对外/跨系统接口 = 网关总量限流 + 应用层按调用方限流 + 写接口幂等，三件各管一段。
- **阈值从压测来，不拍脑袋**：先用 [JMeter 压测](工程实践/JMeter压测.md) 压出接口在可接受延迟下的拐点 QPS，限流值设在拐点的七八成留余量，上线后结合监控再回调。没压测数据写死的阈值，要么形同虚设，要么误杀正常流量。

## 8. 常见坑

- **熔断统计把业务异常算进去**：参数校验不过、业务规则拒绝属于正常返回，不应计入异常比例，否则正常业务高峰会把熔断打穿。Sentinel 里用 `exceptionsToIgnore` 排除业务异常。
- **被限流后调用方无脑重试**：限流是「明确拒绝」，重试只会放大流量形成重试风暴；重试策略必须配合退避，且非幂等接口不自动重试。
- **规则只配在控制台、重启即丢**：控制台规则默认在内存，生产要把规则持久化到 Nacos 等数据源下发，这一步漏配是经典事故。
- **只限入口不限出口**：本服务不限下游调用，慢下游照样拖死线程池；熔断要配在调用方一侧。
- **降级返回假成功**：见第 5 节，写路径禁止。

## 9. 限流与熔断阈值定量

阈值不能只凭感觉拍一个数。下面三组手算例的作用，是把「阈值是多少」翻译成「下游在最坏情况下会承受多少」，再决定这个数能不能上线。

### 9.1 固定窗口：临界点 2 倍突入

固定窗口的计数在窗口切换时清零，窗口末尾和下一个窗口开头可以各放满一波。取窗口 1 秒、阈值 100 QPS：

| 时段 | 放行数 |
|---|---|
| 第 1 个窗口的最后 0.1 秒 | 100 |
| 第 2 个窗口的开头 0.1 秒 | 100 |
| **合计（0.2 秒内）** | **200** |

0.2 秒内实际放行 200 个请求，折算瞬时速率是 200 ÷ 0.2 = **1000 QPS**，等于阈值（100 QPS）的 **10 倍**。更一般地，任意一个跨窗口边界的 1 秒滑动区间内最多放行 2 × 阈值，即 2 倍是固定窗口的理论上限。结论：下游的真实处理能力如果只有 100 QPS，固定窗口限流在临界点是挡不住的；对突发敏感的接口改用滑动窗口或令牌桶（见第 2 节）。

### 9.2 令牌桶：突发上限与排队等待

令牌桶的突发能力由桶容量决定，**桶容量 = 生成速率 × 允许突发时长**（Guava RateLimiter 的 `SmoothBursty` 里这个关系就是 `maxBurstSeconds × rate`，默认 `maxBurstSeconds = 1`）。

手算例：速率 100/s、桶容量 200（相当于允许 2 秒突发）：

- 桶满时可一次放行 200 个请求；若需求持续以 200/s 到达，桶里攒的 200 个令牌按净消耗 100/s（每秒进 100、出 200）计算，200 ÷ 100 = **2 秒**后耗尽，随后吞吐回落到 100/s。
- 令牌不足时请求要排队等令牌生成，第 N 个等待请求的等待时间 = 缺口令牌数 ÷ 速率。桶空时：第 1 个等 1 ÷ 100 = 0.01 秒，第 10 个等 10 ÷ 100 = 0.1 秒，第 100 个等 100 ÷ 100 = 1 秒；缺口 50 个令牌时等待 50 ÷ 100 = 0.5 秒。
- 推论：桶容量只决定「一次能冲多高」，不决定「能冲多久」；突发时长 = 桶容量 ÷ 速率。只调速率不管桶容量，突发还是挡不住（见「小技巧与冷知识」里令牌桶桶容量那条）。

### 9.3 Sentinel 慢调用比例：触发判定手算

Sentinel 1.8 的慢调用比例策略（`SLOW_REQUEST_RATIO`）触发条件是同时满足：统计窗口（`statIntervalMs`，默认 1000 ms）内请求数 ≥ 最小请求数（`minRequestAmount`，默认 5），且慢调用（RT 大于设定的慢调用 RT）占比 ≥ 慢调用比例阈值（`slowRatioThreshold`）。取慢调用 RT = 1000 ms、比例阈值 50%、最小请求数 5：

| 例 | 总请求数 | 慢调用数 | 慢调用比例 | 是否达到最小请求数 | 判定 |
|---|---|---|---|---|---|
| 例 1 | 10 | 6 | 60% | 是（10 ≥ 5） | **触发熔断** |
| 例 2 | 4 | 3 | 75% | 否（4 < 5） | **不触发** |

例 2 的比例更高（75%）却不触发：最小请求数就是干这个的——样本太少时比例没有统计意义，低流量接口一次抖动出现 3 次慢调用不该直接熔断。反过来也要注意：最小请求数设得太高，低流量接口就永远熔断不了。

慢调用 RT 阈值需结合接口的 P99 设定：如果接口正常 P99 是 800 ms，慢调用 RT 设 200 ms 会把大量正常尾部请求算成慢调用，熔断被正常流量打穿；一般取 P99 之上再留余量（或按业务 SLO 定的可接受上限），上线后看慢调用占比曲线再回调。

### 9.4 边界与注意点

- **阈值口径先定死再写数字**：同一个「100 QPS」写在网关上是集群总量，写在每个实例的 Sentinel 规则里是单机量，3 个实例就是 300 QPS 的集群总量。口径没对齐，网关和应用层两处阈值会互相打架（见第 6 节：网关总量 ≈ 各实例之和再留余量）。
- **熔断阈值过低误伤正常抖动，过高等于没熔断**：比例阈值太低时一次 GC 停顿就能触发；太高时下游基本不可用才触发，熔断形同虚设。比例阈值、慢调用 RT、最小请求数、统计窗口四个参数要一起调，只调一个等于没调。
- **阈值上线后必须配监控告警看触发次数**：给「单位时间被限流的请求数」和「熔断触发次数」配告警线，触发率突然从 0.1% 涨到 5%，要么是阈值设小了误杀正常流量，要么是真的有人在刷。没有触发率监控，阈值错了半年都没人知道。
- **固定窗口的 2 倍上限只在窗口边界处成立**：窗口内部的任意 1 秒都不会超过阈值，风险只在边界附近这种跨窗口时段；评估下游能不能扛，要按「最坏 0.2 秒 200 请求」算，不按「平均 100 QPS」算。

### 来源与核验（核验日期：2026-11-07）

- 已验证事实：Sentinel 慢调用比例触发条件——统计窗口内请求数达到最小请求数、且慢调用比例达到阈值时熔断，`minRequestAmount` 默认 5、`statIntervalMs` 默认 1000 ms，熔断后进入半开探测；来源：阿里云 MSE 熔断规则文档（Sentinel 熔断语义）<https://www.alibabacloud.com/help/en/mse/user-guide/configure-circuit-breaking-rules-1>、Sentinel 官方 Wiki 流控页（滑动窗口统计、Rate limiter 漏桶实现）<https://github.com/alibaba/Sentinel/wiki/Flow-Control>、慢调用比例定义与 DegradeRule 字段说明 <https://cloud.tencent.com/developer/article/2126274>。Guava RateLimiter 基于令牌桶、突发容量 = `maxBurstSeconds × rate`（默认 `maxBurstSeconds = 1`）；来源：<https://www.javathinking.com/blog/quick-guide-to-the-guava-ratelimiter/>。
- 个人推断 / 经验建议：慢调用 RT 取 P99 之上再留余量、熔断比例阈值过低过高的误伤与失效判断、「四个参数一起调」，为工程经验总结，未逐条对照官方文档。
- 注意：慢调用比例判定里「请求数 ≥ 最小请求数」还是「> 最小请求数」，不同版本资料表述有出入，按所用 Sentinel 版本以 `ResponseTimeCircuitBreaker` 实际行为为准；本节手算例避开了边界值（10 ≥ 5、4 < 5），两种口径下结论相同。

## 小技巧与冷知识

【小技巧】被限流时返回 HTTP 429 而不是 200 里的业务码：429（Too Many Requests）是 RFC 6585 专门给限流定义的状态码，调用方、网关、监控一眼就能认出这是“被限流”而不是“业务失败”。再配一个 Retry-After 响应头告诉调用方几秒后再试，客户端按这个时间退避，比固定文案“系统繁忙”更规范，也让重试风暴少一个源头。

【小技巧】降级读缓存旧值要设一个最大可接受陈旧度：缓存旧值“略过期比报错强”没错，但过期三天的价格、库存旧值直接返回就是脏数据。降级读缓存时先看旧值的写入时间，超过业务能容忍的上限（比如 10 分钟）就别读了，退到默认值或快速失败；“读旧值”这个兜底本身也需要一个过期边界。

【小技巧】热点参数限流的 key 要用“调用方 + 资源”组合：只按资源限流，一个调用方刷爆会把所有调用方一起挡住；只按调用方限流，又挡不住单个接口被刷。Sentinel 的热点规则支持按参数组合限流，key 拼成“调用方 ID + 资源名 + 参数值”，误伤面才收得住；key 拼得越粗，误伤越大。

【小技巧】blockHandler 和 fallback 的方法签名必须和原方法对得上：blockHandler 要在原方法参数后面再加一个 BlockException，fallback 再加一个 Throwable，少一个参数或顺序错了，编译能过、运行时 Sentinel 才报找不到方法。写完先跑一次被限流和业务异常两条路，确认两个方法真的被调到了，别等到线上第一次限流才发现签名写错。

【小技巧】降级发生时要把“这是降级结果”打进日志和指标：降级返回的默认值和正常返回长得一样，监控里看成功率全是绿的，实际上用户拿到的是残缺数据。给降级分支单独记一个计数器、日志里打一个 degraded=true 的标记，值班同学才能分清“接口真正常”和“接口在靠降级撑着”，阈值调得准不准也靠这个数说话。

【小技巧】网关限流的 key 优先用租户或调用方 ID，别只用 IP：公司内网、云厂商出口经常是多个调用方共用一个出口 IP，按 IP 限流等于把一群人绑在一起算账，一个人刷爆、全员被挡。能拿到调用方身份（API Key、租户 ID）就用它做 key，IP 只当没有身份信息时的退路。

【小技巧】令牌桶的桶容量就是允许的最大突发量：桶能攒多少令牌，一次就能放过去多少请求，容量设得太大等于给突发开了后门。容量一般按“业务能接受的瞬时峰值”定，比如平时 100 QPS、允许 1 秒内冲到 300，桶容量就设 300 左右；只调生成速率不管桶容量，限流值看着对、突发还是挡不住。

【小技巧】降级逻辑本身也要有个一键关闭的开关：降级读的缓存挂了、默认值分支写错了，降级就从“兜底”变成新的故障源。降级开关做成动态配置，开关一关就回到直接报错，至少故障是可见的；不能关的降级，出了问题连回退的路都没有，排查时先怀疑降级本身。

【小技巧】重试退避要用指数退避加随机抖动：固定间隔重试会让所有客户端在同一时刻一起重试，限流刚松开又被同一波打满。退避时间按 1 秒、2 秒、4 秒指数拉长，再加一段随机抖动把重试时刻打散，峰值才不会在同一个时间点重合；重试次数也要封顶，超过就直接失败，别无限重试。

【小技巧】限流阈值上线后要配触发率告警：阈值不是设完就完，触发率突然从 0.1% 涨到 5%，要么是阈值设小了误杀正常流量，要么是真的有人在刷。给“单位时间被限流的请求数”配一条告警线，触发率一变就有人看，否则阈值错了半年都没人知道，限流等于白配。

【冷知识】熔断器这个名字直接来自电路里的断路器：电流过大时断路器跳闸切断电路，电流恢复正常后合闸，熔断器的“打开—半开—闭合”就是照着这个抄的。Martin Fowler 在 2014 年专门写了 CircuitBreaker 一文，把这个模式从电力工程带进软件圈推广开，Resilience4j 这类库的名字也源于“让系统有韧性”这个思路。

【冷知识】Guava 的 RateLimiter 除了平滑突发，还有一种预热模式：SmoothWarmingUp 让令牌生成速率在启动后一段时间内从低逐渐爬升到目标值，避免服务刚启动、缓存还是冷的时候就被满速流量打进来。预热模式适合“冷启动时处理能力本身就弱”的服务，令牌桶只管速率不管冷热，预热是专门补冷启动这一课的。

【冷知识】Netflix 的 Hystrix 是熔断器最出名的早期实现，2018 年 11 月 Netflix 宣布不再给它加新功能、只做维护，社区随后转向 Resilience4j 和 Sentinel。Hystrix 的线程池隔离思路（每个依赖独占线程池）影响很大，但它按线程池隔离的代价是线程开销大，后来的实现多改成信号量或更轻的隔离方式。

## 10. 面试与自测

- 令牌桶和漏桶的本质区别是什么？各自适合保护什么样的下游？
- 熔断器的半开状态解决什么问题？没有它会怎样？
- Sentinel 里 blockHandler 和 fallback 为什么必须分开？
- 一个接口的限流阈值应该怎么定出来？
- 限流和幂等分别解决什么问题？为什么不能互相替代？
- 固定窗口限流阈值是 100 QPS，为什么下游仍可能在 0.2 秒内收到 200 个请求？令牌桶的突发上限又怎么算？

### 参考答案

1. 本质区别在输出是否允许突发：令牌桶以恒定速率放令牌、桶可攒令牌，请求拿到令牌才放行，平均速率受控但允许一定突发；漏桶以恒定速率流出，桶满拒绝，输出绝对平稳、不允许突发，积压即延迟。选型：控平均速率且容忍合理突发用令牌桶（如网关限流、Guava RateLimiter）；要把流量整形到恒定速率喂给脆弱下游用漏桶；计数器类只适合做 QPS 上限的粗粒度闸门。
2. 半开解决“下游恢复了如何安全探知”：打开状态静默期到后，只放少量试探请求，成功则恢复闭合，失败则重新打开。没有半开，要么永远不恢复，要么静默期一到就全量放行，下游未恢复会被瞬间打垮，造成二次雪崩；选组件或自研时要先确认半开这一态是否存在。
3. 因为两者是不同的触发源：限流/熔断触发抛 BlockException，走 blockHandler；业务自身抛异常走 fallback。分开写才能各给各的兜底：混在一起会导致限流时误走业务降级、返回业务错误码，或业务异常被当成限流处理，排查和前端处理都会错乱。
4. 不能拍脑袋：先用 JMeter 压测，压出接口在可接受延迟下的拐点 QPS，再把限流值设在拐点的七八成留余量，上线后结合监控回调调整。没有压测数据写死的阈值，要么形同虚设、要么误杀正常流量；同时网关总量与各实例应用限流的口径要对齐（网关总量约等于各实例之和再留余量）。
5. 限流解决单位时间总量过载，入口侧控速、保住系统不被打垮；幂等解决同一操作重复提交，如同一待办被连点两次，靠状态机条件更新 + 幂等键保证只生效一次。两者不能互相替代：按用户限 1 QPS 既挡不住慢速重复提交，又误伤正常操作；只做幂等也挡不住洪峰总量。正确组合是网关总量限流 + 应用层按调用方限流 + 写接口幂等，各管一段。
6. 固定窗口的计数在窗口切换时清零，窗口末尾和下一个窗口开头可以各放满一波：窗口 1 秒、阈值 100 时，第 1 个窗口最后 0.1 秒放 100、第 2 个窗口开头 0.1 秒再放 100，0.2 秒内共放行 200，折算 200 ÷ 0.2 = 1000 QPS，是阈值的 10 倍；任意跨窗口边界的 1 秒内最多放行 2 × 阈值。令牌桶的突发上限由桶容量决定，桶容量 = 生成速率 × 允许突发时长：速率 100/s、容量 200 时最长 2 秒突发 200/s（200 ÷ 100 = 2），随后回落到 100/s；令牌不足时第 N 个等待请求的等待时间 = 缺口令牌数 ÷ 速率，如缺口 50 个令牌等 0.5 秒。结论：评估下游能不能扛要按最坏突发算，不按平均 QPS 算；对突发敏感的接口改用滑动窗口或令牌桶。
