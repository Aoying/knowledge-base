# 限流熔断与降级

## 1. 核心概念

三个词管三件不同的事，别混用：

- **限流**：入口侧控速。请求量超过系统能处理的上限时，多余的直接拒绝或排队，保住系统不被打垮——是「我最多接这么多」。
- **熔断**：出口侧止损。依赖的下游已经变慢/报错时，快速失败不再调用，避免线程全卡在等下游上把自己拖死——是「它不行了，我先不等它」。
- **降级**：熔断或限流触发之后给调用方一个兜底结果（默认值、缓存旧值、友好提示），让业务以残缺但可用的形态继续——是「拿不到真数据时，给什么替代」。

## 2. 四种限流算法

| 算法 | 原理 | 特点 |
|---|---|---|
| 固定窗口计数器 | 按时间窗（如每秒）计数，超阈值拒绝，窗口切换清零 | 实现最简单；窗口临界点可突入 2 倍流量（窗口末尾和下个窗口开头各放满一波） |
| 滑动窗口 | 把窗口切成小格滚动统计 | 平滑掉临界突刺，精度与格数成正比，Sentinel 的统计即滑动窗口口径 |
| 漏桶 | 请求入桶，以恒定速率流出，桶满拒绝 | 输出绝对平稳，适合保护「处理速率恒定」的下游；不允许突发，积压即延迟 |
| 令牌桶 | 以恒定速率往桶里放令牌，请求拿到令牌才放行，桶可攒令牌 | 允许一定突发（攒的令牌一次用掉），平均速率仍受控；Guava RateLimiter、网关限流的主流选择 |

选型口径：控平均速率且容忍合理突发，用令牌桶；要整形到恒定速率喂给脆弱下游，用漏桶；计数器类适合做 QPS 上限这种粗粒度闸门。框架里算法多已封装，重点是每个接口该设多大的值（见第 7 节），不是手写算法。

## 3. Sentinel 的模型

Sentinel（Spring Cloud Alibaba 系，见 [Spring Cloud 概览](开发语言/Java/Spring-Cloud概览.md)）的三个基本概念：

- **资源**：被保护的对象，可以是一个接口、一个方法、一段代码块。用 `@SentinelResource` 注解或 `SphU.entry("资源名")` 定义。
- **规则**：流控规则（QPS/并发线程数阈值、调用关系限流）、熔断降级规则、热点参数规则、系统自适应规则、授权规则。规则可通过控制台或 Nacos 等数据源动态下发，不必改代码重启。
- **异常处理分工**（最容易写错的一点）：触发限流/熔断抛的是 `BlockException`，走 `blockHandler`；业务自身抛的异常走 `fallback`。两者分开写，混在一起会导致降级逻辑被限流误触发、或限流时返回了业务错误码。

```java
@SentinelResource(value = "submitApproval",
        blockHandler = "submitBlocked",      // 被限流/熔断时走这里
        fallback = "submitFallback")          // 业务异常时走这里
public Result submit(ApprovalCmd cmd) { ... }

public Result submitBlocked(ApprovalCmd cmd, BlockException e) {
    return Result.fail("系统繁忙，请稍后重试");      // 快速失败，不排队不重试
}
public Result submitFallback(ApprovalCmd cmd, Throwable e) {
    log.error("审批提交异常", e);
    return Result.fail("提交失败");
}
```

## 4. 熔断器三态

熔断器就是电路保险丝的状态机：

```text
闭合（正常放行，统计失败率/慢调用）
  └─ 指标越线 → 打开（直接快速失败，不调下游，计时中）
                  └─ 静默期到 → 半开（放少量试探请求）
                                  ├─ 试探成功 → 闭合（恢复）
                                  └─ 试探失败 → 重新打开
```

Sentinel 的熔断策略三种口径：**慢调用比例**（响应时间超阈值的占比越线）、**异常比例**、**异常数**。关键参数是统计窗口、最小请求数（样本太少不触发，避免低流量时误熔断）和熔断时长（对应「打开」状态的计时）。没有半开探测的「熔断」只是定时开关，下游没恢复就全量放行会造成二次雪崩——选组件和自研时先确认这一态在不在。

## 5. 降级与兜底策略

按数据时效容忍度从高到低选，别一刀切：

- **返回默认值/空结果**：适用于非关键展示位（推荐列表、附加信息），缺了不影响主流程。
- **读缓存旧值**：有缓存时降级读缓存，哪怕略过期也比报错强；缓存没兜住再退到默认值。
- **排队等待**：漏桶式削峰，把突发摊平（如批量任务入口）；同步接口慎用，等待即占用线程。
- **快速失败 + 明确文案**：写操作和强一致场景的正确选择。宁可明确说「稍后重试」，也不要返回假成功——降级写出脏数据比报错难收拾得多。

## 6. 两层分工：网关限流与应用限流

| 层 | 位置 | 粒度与职责 |
|---|---|---|
| 网关层 | Spring Cloud Gateway / Nginx | 粗粒度总闸：按路由、IP、租户控总量，挡掉明显过载与恶意流量，保护整个后端 |
| 应用层（Sentinel） | 每个服务进程内 | 细粒度：按资源、按热点参数（如单个客户号）限流，以及出方向的熔断——只有应用自己知道哪个下游在变慢 |

只有网关层，单实例的热点和下游故障它看不见；只有应用层，总入口没闸，洪峰先把连接数和网关打满。两层都要有，阈值口径对齐（网关总量 ≈ 各实例应用限流之和再留余量）。

## 7. 与现有系统的衔接

- **限流 ≠ 防重复提交**。审批流里「同一待办被连点两次」是幂等问题，靠状态机条件更新 + 幂等键解决（见 [REST 接口设计](工程实践/REST接口设计.md) 的幂等设计）；限流解决的是「单位时间总量过载」。把防重当限流做（如按用户限 1 QPS）既挡不住慢速重复提交，又误伤正常操作。
- **接口保护的正确组合**：对外/跨系统接口 = 网关总量限流 + 应用层按调用方限流 + 写接口幂等，三件各管一段。
- **阈值从压测来，不拍脑袋**：先用 [JMeter 压测](工程实践/JMeter压测.md) 压出接口在可接受延迟下的拐点 QPS，限流值设在拐点的七八成留余量，上线后结合监控再回调。没压测数据写死的阈值，要么形同虚设，要么误杀正常流量。

## 8. 常见坑

- **熔断统计把业务异常算进去**：参数校验不过、业务规则拒绝属于正常返回，不应计入异常比例，否则正常业务高峰会把熔断打穿。Sentinel 里用 `exceptionsToIgnore` 排除业务异常。
- **被限流后调用方无脑重试**：限流是「明确拒绝」，重试只会放大流量形成重试风暴；重试策略必须配合退避，且非幂等接口不自动重试。
- **规则只配在控制台、重启即丢**：控制台规则默认在内存，生产要把规则持久化到 Nacos 等数据源下发，这一步漏配是经典事故。
- **只限入口不限出口**：本服务不限下游调用，慢下游照样拖死线程池；熔断要配在调用方一侧。
- **降级返回假成功**：见第 5 节，写路径禁止。
