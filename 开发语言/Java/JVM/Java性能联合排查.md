# Java 性能联合排查

本篇不是第五遍讲单项工具用法。`top`、`jstack`、`jmap`、`jstat`、Arthas、GC 日志的单项用法见 [JVM 故障排查](开发语言/Java/JVM/JVM-故障排查.md)；GC 目标与收集器选型见 [JVM GC 调优](开发语言/Java/JVM/JVM-GC调优.md)；慢 SQL 的发现与诊断闭环见 [慢查询诊断](数据库/MySQL/慢查询诊断.md)；大盘与告警见 [监控告警](工程实践/运维/监控告警.md)。本篇只讲一件事：**CPU、内存、线程、GC、慢 SQL 五路证据怎么联合起来定根因**，而不是各查各的、最后凭感觉拍一个。

联合排查的核心判断：单路证据只能证明“这一路有异常”，只有两路以上证据在时间点与因果上对上号，结论才站得住。CPU 高可能是业务死循环，也可能是 GC 在拼命回收；慢 SQL 可能是缺索引，也可能是被别的事务挡住；线程池打满可能是下游慢，也可能是连接被慢 SQL 占着。先分流，再取证，最后用证据链收敛，顺序不能反。

## 1. 核心概念

### 五路证据

| 一路 | 回答的问题 | 核心指标 | 主力工具 |
|---|---|---|---|
| CPU | 谁在烧 CPU，是业务还是 GC | 进程 CPU、线程 CPU、方法热点 | top、jstack、Arthas、火焰图 |
| 内存 | 对象涨到哪里去了，是泄漏还是峰值 | 各代占用、对象排行、堆外 | jstat、jmap、MAT |
| 线程 | 线程在等什么，有没有死锁与池打满 | 线程状态、锁持有、池队列 | jstack、Actuator、监控大盘 |
| GC | 停顿与接口毛刺是否同源 | GC 频率、停顿、Full GC 原因 | GC 日志、jstat |
| 慢 SQL | 数据库是不是瓶颈，慢在计划还是锁 | 慢日志、Top SQL、执行计划、锁等待 | 慢日志、EXPLAIN、锁等待排查 |

### 证据链

证据链 = 同一故障窗口内，多路证据指向同一个根因的链条。合格的证据链有三个要素：**时间对齐**（GC 停顿、慢 SQL 时段、接口毛刺时点对得上）、**因果方向**（分清谁是因谁是果，如慢 SQL 是因、连接池排队是果）、**落点**（结论落到代码行或配置项，“机器不行”不是结论）。

## 2. 症状分流表

先定症状所属的主路，再决定先看什么、后看什么。分流错了，后面全是无用功。

| 症状 | 先看什么 | 后看什么 | 常见误判 |
|---|---|---|---|
| CPU 飙高 | `top -Hp` 找最忙线程，连续 3 次 jstack 定性 | 栈总在 GC 线程 → 转 GC 路；大量 BLOCKED 在同一把锁 → 转线程路查持锁线程 | 一见 CPU 高就认定业务死循环，漏掉 GC 拼命回收的情况 |
| 内存持续涨 | `jstat -gcutil` 看 Full GC 后老年代下限是否抬升 | 只涨不落 → 堆快照走 MAT 查引用链；能回落 → 堆不够或瞬时峰值 | 单次快照数值大就断言泄漏，趋势才是金标准 |
| 线程池打满 / 死锁 | jstack 看线程状态分布与死锁报告 | 大量 WAITING 在连接获取 → 转慢 SQL 路；大量 BLOCKED 在同一把锁 → 查持锁线程 | 只扩线程池或连接池，把下游慢放大成更大并发 |
| 接口毛刺 | 大盘 P99 毛刺时点 + GC 日志停顿时点是否对齐 | 对齐 → GC 路；不对齐 → 链路追踪看时间花在哪一跳 | 只看平均延迟，毛刺被平均数藏起来 |
| 慢 SQL 增多 | 慢日志 Top SQL：总耗时、平均耗时、执行次数三维度 | EXPLAIN 看计划，再看锁等待（计划正常但被挡住是锁问题） | 慢就等于缺索引，漏掉锁等待、统计信息过期、调用方 N+1 |

分流口诀：**单实例异常先看机器与 GC，全实例异常先看下游与变更**（见监控告警篇的排查路径）。单实例慢指向本机问题，全实例慢指向代码变更或公共依赖。

## 3. 五路证据对照

### 3.1 CPU：先分清是谁在烧

指标：进程 CPU 使用率、最忙线程 CPU、方法级热点。

```bash
top                              # 1. 找到吃 CPU 的 Java 进程 PID
top -Hp <pid>                    # 2. 找到最忙线程 TID（十进制）
printf '%x\n' <tid>              # 3. TID 转十六进制 = 线程栈里的 nid
jstack <pid> | grep -A 30 'nid=0x<hex>'   # 4. 看这条线程在跑什么代码
```

连续抓 3 次 jstack（间隔几秒）定性：栈总停在同一业务方法 = 死循环或热点计算；总在 GC 线程 = 问题在 GC 而不在业务，立即转 GC 路；大量线程 BLOCKED 在同一把锁 = 锁竞争，转查持锁线程。Arthas 快捷路径：`thread -n 3` 一步给出最忙线程及栈；`trace 包.类 方法 '#cost > 50'` 看方法内部耗时分布；火焰图（async-profiler）适合看“CPU 到底花在哪些方法上”的全景，定性后再用 jstack 精确到行。

印证关系：CPU 高 + GC 日志 Full GC 频繁 → 先查 GC 路，业务代码可能没问题；CPU 高 + jstack 全是业务栈 → 业务热点，火焰图定方法。

### 3.2 内存：看趋势，不看单点

指标：各代使用率、Full GC 后老年代下限、对象数量与占用排行、堆外直接内存。

```bash
jstat -gcutil <pid> 1000         # 每秒看各区使用率与 GC 次数/耗时
jmap -heap <pid>                 # 各代内存占用概览（JDK 11 已弱化，优先看 GC 日志/jstat）
jmap -dump:format=b,file=heap.hprof <pid>   # 导出堆快照给 MAT 分析
jmap -histo <pid>                # 对象数量/占用排行，定位哪类对象在涨
```

判断泄漏的金标准是**多次 Full GC 后老年代下限持续抬升**，不是单次快照数值大。MAT 打开 dump 后看三样：Histogram 第一名是谁、Dominator Tree 的 Retained Heap、Leak Suspects 报告，沿 GC Roots 引用链确认“谁在持有、本该何时释放”。常见真凶：静态集合只加不删、缓存无上限无过期、ThreadLocal 用完不 remove、监听器注册后不注销、大结果集一次全量查回内存（分页缺失）。堆外单独查：`Direct buffer memory` 报错指向 NIO/Netty 直接内存，看 `-XX:MaxDirectMemorySize` 与释放链路。大堆 dump 会长时间停顿，生产先报备、挑低峰做，dump 文件含业务数据，按敏感文件管理、分析完销毁。

印证关系：内存涨 + Full GC 后下限抬升 → 泄漏方向，走 MAT；内存涨 + GC 后能回落 → 堆不够或瞬时峰值，调堆或削峰，不按泄漏修。

### 3.3 线程：看状态分布，不看单个线程

指标：线程总数、RUNNABLE/BLOCKED/WAITING 分布、死锁报告、线程池活跃数与队列积压。

```bash
jstack -l <pid> > stack.txt      # -l 带锁信息，死锁与持锁关系一次看清
```

jstack 输出末尾的死锁报告（`Found one Java-level deadlock`）直接给死锁环；没有死锁报告时看状态分布：大量 BLOCKED 在同一把锁 → 锁竞争，找持锁线程的栈；大量 WAITING 在连接获取或下游调用 → 下游慢或连接池被占，转慢 SQL 路；线程数持续涨 + `unable to create new native thread` → 线程池无界或每请求建线程，看 `ulimit -u` 与线程数。线程池打满时先看队列与活跃数，再看池里线程的栈在等什么——栈在等数据库连接，根因在慢 SQL；栈在等同一把业务锁，根因在锁设计。单次 jstack 只能证明“那一刻”，热点与死锁判断靠多次采样一致性。

印证关系：线程池打满 + 慢日志 Top SQL 总耗时高 → 先修慢 SQL，池排队是果；线程池打满 + jstack 大量 BLOCKED → 锁竞争，与数据库无关。

### 3.4 GC：停顿归因先对时间

指标：Young GC / Full GC 频率、单次停顿、Full GC 触发原因、晋升失败。

GC 日志要预先开着，出事才有据可查。JDK 8：

```bash
-Xloggc:/data/logs/gc-%t.log -XX:+PrintGCDetails -XX:+PrintGCDateStamps
-XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=10 -XX:GCLogFileSize=20M
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/
```

JDK 9+ 统一日志：`-Xlog:gc*:file=/data/logs/gc-%t.log:time,uptime:filecount=10,filesize=20M`（其余参数同上）。

一条 Young GC 日志看四件事：频率（两次 GC 间隔越来越短 = 分配速率过高或堆太小）、回收效果（GC 后老年代占用是否回落，只涨不落 = 持续晋升且回收不掉，怀疑泄漏）、单次停顿（看 `real` 时间；停顿长但 GC 时间短，多是机器抢 CPU 或日志 IO）、Full GC 触发原因（`Metadata GC Threshold` 是元空间不足，`System.gc()` 是代码或框架显式调用，`Allocation Failure` 是老年代装不下晋升对象，三者解法完全不同）。

印证关系：**GC 频繁先看分配速率再看堆大小**——分配热点（大 JSON 拼装、日志狂打字符串、批量结果集）要修代码，调大堆只是续命；停顿与接口毛刺时间点对齐 → 毛刺根因在 GC；停顿不对齐 → 转链路追踪，别在 GC 上浪费时间。G1 日志里 Evacuation 之外的时间长，常见原因是引用处理（软/弱引用、Finalizer 积压）。

### 3.5 慢 SQL：先看执行计划再看锁

指标：慢日志 Top SQL（总耗时、平均耗时、执行次数）、执行计划（type、rows、Extra）、锁等待次数、连接池等待线程。

```sql
-- 示例：开启动态变量（重启后失效，持久化要写配置文件）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
-- log_queries_not_using_indexes 为 ON 时，连没走索引但跑得快的查询也记，量大，排查期开、平时关
```

`long_query_time` 设 1 秒是常见起点；设太小日志爆炸，设太大则漏掉“单条不慢、量大拖垮系统”的 SQL——这类 SQL 靠 Top SQL 的总耗时排序抓，不靠阈值。定位顺序固定：**慢 SQL 先看执行计划再看锁**——先 EXPLAIN 看是索引失效还是全表（type=ALL），计划正常但执行时被挡住才是锁等待，按锁等待篇流程找挡的人；再看统计信息（rows 估算是否失真，过期则 ANALYZE 方向）；最后看调用方（单条不慢、总量大 = 循环查库或 N+1，修调用方式比调 SQL 见效快）。Druid 监控页的 SQL 统计与慢日志双向印证：监控页看到的高频慢 SQL，到慢日志里找完整 SQL 文本和时间分布，两边对上号再动手。

印证关系：慢 SQL + 连接池排队同时出现 → 先看慢 SQL，池排队常是慢 SQL 占着连接不放的结果；慢 SQL + 线程池打满 → 同理，先修 SQL；慢 SQL + GC 毛刺同窗口 → 两件事可能同源（如大结果集既拖慢 SQL 又顶满老年代），也可能只是同时发生，靠时间对齐与 MAT 证据区分。

## 4. 联合根因流程

顺序固定：症状 → 分流 → 取证 → 证据链 → 根因，跳过任何一步都会把果当成因。

1. **定症状**：大盘看黄金信号（延迟、流量、错误、饱和度），是流量突增、错误伴随，还是纯延迟上升；再看分布，单实例还是全实例。
2. **分流**：按第 2 节症状分流表定主路，主路决定先取哪路证据。
3. **取证**：主路证据先取齐（命令、日志、快照），再取关联路证据做印证。取证时按时间窗口对齐：GC 停顿时点、慢 SQL 时段、接口毛刺时点必须落在同一窗口，否则不是同一故障。
4. **收敛**：用第 3 节的印证关系逐一排除——CPU 高排除 GC、慢 SQL 排除锁、池打满排除下游慢，每排除一路，根因范围缩一圈。排除不掉的，用下一路证据继续压。
5. **落点**：结论写成一句话，落到代码行或配置项：“导出接口一次查全表 + 静态缓存无上限，导致老年代泄漏式增长、Full GC 频繁、接口 P99 毛刺”。写不出来说明还没定位到，继续取证，不要先修。
6. **验证与上线**：改动先在测试环境复核（SQL 改写对照改写前后 EXPLAIN，索引先看计划变化）；索引上线走低峰窗口 + 回滚预案；上线后盯慢日志与 GC 日志确认回落再结案。

### 排查纪律

- **不要先重启，先保留现场**：jstack 三连、GC 日志、dump 路径记清，再允许重启恢复服务。重启前没留的东西事后无法复盘，同类故障必然复发且每次都从零查。
- 生产执行 `jmap -dump`、Arthas `redefine` 等高风险动作要走审批并避开业务高峰。
- 结论要能复现：同样的输入与流量下，根因链条能重走一遍；复现不了的结论先存疑。
- 告警与复盘：没有行动项的告警应删除或降级；复盘结论写回本篇或对应单项篇，不要只留在群聊里。

## 5. 案例串联（示例，非真实生产事故）

以下案例为**示例**，用于演示五路证据怎么一步步收敛到根因，并非真实生产事故。

**现象**：某导出接口 P99 从 800ms 涨到 6 秒，只在单个实例上出现，错误率没涨。

1. **大盘分流**：黄金信号里只有延迟上升，流量与错误正常；按实例看分布，单实例慢 → 先看机器与 GC，不看代码变更与下游。
2. **GC 路取证**：GC 日志里 Full GC 频率从每小时 1 次涨到每 5 分钟 1 次，停顿时点与 P99 毛刺时点对齐；`jstat -gcutil` 看 Full GC 后老年代下限一次比一次高 → 泄漏方向，不是堆不够。
3. **CPU 路排除**：`top -Hp` + 连续 3 次 jstack，线程没有死循环热点，栈多在等待 IO 与连接获取 → CPU 不是根因，GC 拼命回收才是 CPU 升高的伴生现象。
4. **线程路印证**：线程池队列积压，池里线程的栈多在等数据库连接 → 连接被占着，结合下一步看是谁占着。
5. **慢 SQL 路取证**：慢日志 Top SQL 里导出 SQL 总耗时第一；EXPLAIN 计划正常（走了索引），不是索引问题；锁等待篇流程走完，没有挡路事务 → 慢在数据量：导出一次查全表，单条跑 3 秒且并发一上来就占连接。
6. **内存路落点**：MAT 打开 heap dump，Histogram 第一名是导出结果集对象，Dominator Tree 里静态缓存持有了历史导出结果且无上限无过期 → 两处同源：导出未分页（瞬时大对象顶满老年代）+ 静态缓存无上限（老年代下限持续抬升）。
7. **根因一句话**：导出接口一次查全表 + 静态缓存无上限，导致老年代泄漏式增长、Full GC 频繁、接口 P99 毛刺，线程池与连接池排队是果不是因。
8. **解法与验证**：导出改流式/分页 + 缓存加过期与上限；测试环境复核 EXPLAIN 与 GC 日志，上线后盯慢日志与 P99 确认回落再结案。只调大堆或只扩连接池，都是给这个问题续命。

## 6. 常见误区

- 出事第一反应重启：服务活了，证据没了，同类故障必然复发且每次都从零查。
- 看到 Full GC 多就调大堆：泄漏型增长调多大都会满，只是把爆炸时间推后。
- 慢就等于缺索引：先 EXPLAIN，再看锁等待和统计信息；缺索引只是根因之一。
- 连接池排队就扩池：池排队常是慢 SQL 占着连接不放的结果，扩池是给慢 SQL 更多并发。
- 只看平均延迟：平均值会掩盖长尾，毛刺判断一律看 P95/P99 与 GC 停顿时点对齐。
- 单次快照下结论：一次 jstack、一次 heap 数值只能证明“那一刻”，趋势与多次采样才定性。
- 代码里 `System.gc()`“帮忙回收”：触发 Full GC 的停顿远比省下的内存贵，框架默认周期调用也要显式关掉或评估副作用。

## 小技巧与冷知识

【小技巧】抓 jstack 之前先把 `top -Hp` 里最忙线程的十进制 TID 抄下来，再用 `printf '%x\n' <tid>` 转成十六进制去 grep 线程栈里的 nid。直接拿十进制 TID 去 grep 是搜不到的，这是新手最常卡住的一步；连续抓 3 次、每次间隔几秒，栈总停在同一处才算定性，单次快照只能证明“那一刻”。

【小技巧】`jstat -gcutil <pid> 1000` 每秒采样一次，比单次看各代占用有用得多。判断泄漏的金标准是多次 Full GC 之后老年代下限是否持续抬升——只涨不落走 MAT 查引用链，能回落则是堆不够或瞬时峰值，两者解法完全不同，单次快照数值大就断言泄漏很容易误判。

【冷知识】`jmap -heap` 在 JDK 11 之后已经弱化，优先看 GC 日志和 `jstat`。很多老教程仍把 `jmap -heap` 当作查堆的主力，但新版本里它的信息不如 GC 日志完整；`jmap -histo` 看对象排行和 `jmap -dump` 导出快照给 MAT 仍然是常用组合。

【小技巧】GC 日志一定要预先开着，出事才有据可查。JDK 8 用 `-Xloggc` 加 `PrintGCDetails`、`PrintGCDateStamps` 并开日志轮转，JDK 9+ 用统一日志 `-Xlog:gc*`；等到线上出问题再去开日志，故障窗口的数据已经永远丢了，事后只能靠猜。

【小技巧】读一条 Young GC 日志时先看 Full GC 的触发原因再决定怎么修：`Metadata GC Threshold` 是元空间不足，`System.gc()` 是代码或框架显式调用，`Allocation Failure` 是老年代装不下晋升对象，三者解法完全不同。看到 Full GC 多就直接调大堆是最常见的误操作，泄漏型增长调多大都会满，只是把爆炸时间推后。

【冷知识】代码里写 `System.gc()`“帮忙回收”反而会触发 Full GC，停顿代价远比省下的内存贵。更隐蔽的是有些框架会周期性调用它，排查时如果在日志里反复看到 `System.gc()` 触发的 Full GC，要先找到调用方并显式关掉或评估副作用，而不是去调堆。

【小技巧】线程池打满时先别急着扩池，先看池里线程的栈在等什么。栈在等数据库连接，根因在慢 SQL；栈在等同一把业务锁，根因在锁设计；大量线程 BLOCKED 在同一把锁上，扩池只会让更多线程去抢同一把锁。扩池之前必须先确认慢 SQL 与锁竞争已排除，否则是给慢 SQL 更多并发。

【冷知识】jstack 输出末尾自带死锁报告，出现 `Found one Java-level deadlock` 会直接给出死锁环，不用自己一条条对锁关系。但没有死锁报告不等于没有线程问题，这时要看状态分布：大量 WAITING 在连接获取指向下游慢，大量 BLOCKED 在同一把锁指向锁竞争，线程数持续上涨加 `unable to create new native thread` 则要查 `ulimit -u` 与线程池是否无界。

【小技巧】慢日志的 `long_query_time` 设 1 秒是常见起点，但阈值本身抓不到“单条不慢、量大拖垮系统”的 SQL。设太小日志会爆炸，设太大又会漏掉这类 SQL，所以这类问题要靠慢日志 Top SQL 的总耗时排序来抓，而不是靠调阈值；`log_queries_not_using_indexes` 开着时连没走索引但跑得快的查询也记，排查期开、平时关。

【冷知识】G1 日志里 Evacuation 之外的时间如果很长，常见原因不是回收本身，而是引用处理——软引用、弱引用积压或 Finalizer 积压。这类停顿光看 GC 频率和堆大小是找不到原因的，要顺着引用处理这条线去查，否则很容易在错误的方向上反复调参。

【小技巧】接口毛刺判断一律看 P95/P99，并把毛刺时点和 GC 日志停顿时点对齐。平均延迟会把毛刺藏起来，对齐了说明毛刺根因在 GC，对不齐就转链路追踪看时间花在哪一跳，别在 GC 上浪费时间；时间对不上号的证据再多也不是同一故障的证据链。

【小技巧】生产上执行 `jmap -dump` 之前要先报备并挑低峰做，大堆 dump 会长时间停顿。dump 文件里含业务数据，要按敏感文件管理，分析完及时销毁；同样，Arthas `redefine` 这类高风险动作也要走审批、避开业务高峰，别在故障正当时顺手把现场改没了。

【冷知识】MAT 的 Leak Suspects 报告只是“嫌疑人名单”，不能直接当结论。正确做法是看 Histogram 第一名是谁、Dominator Tree 的 Retained Heap，再沿 GC Roots 引用链确认“谁在持有、本该何时释放”——静态集合只加不删、缓存无上限无过期、ThreadLocal 用完不 remove、监听器注册后不注销，都是原文点名的常见真凶。

## 7. 面试与自测

1. 接口出现毛刺时，GC、慢 SQL、线程池三路证据怎么互相印证？排除顺序是什么？
2. CPU 飙高时，怎么用多路证据分清是业务死循环还是 GC 问题？关键分叉点在哪？
3. 连接池排队、慢 SQL、线程池打满同时出现，应该先修哪个？为什么？

### 参考答案

1. 先对时间：GC 日志停顿时点、慢 SQL 时段、接口毛刺时点是否落在同一窗口，不对齐就不是同一故障。排除顺序：大盘先看分布（单实例还是全实例），再看 GC 停顿是否与毛刺对齐（对齐则 GC 是主因），再看慢日志 Top SQL 与锁等待（计划正常但被挡是锁问题，计划异常是索引问题），最后看线程池栈在等什么（等数据库连接指向慢 SQL，等同一把锁指向锁竞争）。三路证据在时间点与因果上对上号、结论落到代码行或配置项，才算收敛。
2. 分叉点在 jstack 连续采样的栈分布：`top -Hp` 找到最忙线程并转十六进制 nid，连续抓 3 次 jstack——栈总停在同一业务方法就是死循环或热点计算；总在 GC 线程说明问题在 GC 而不在业务，立即转 GC 路看堆与 GC 日志；大量线程 BLOCKED 在同一把锁则是锁竞争，转查持锁线程。再用 GC 日志印证：Full GC 频繁且停顿与 CPU 飙高时段对齐，支持 GC 成因；GC 平稳则支持业务热点成因。Arthas `thread -n 3` 可一步给出最忙线程及栈。
3. 先修慢 SQL。因为连接池排队常是慢 SQL 占着连接不放的结果，线程池打满常是线程在等数据库连接的结果，两者都是果不是因。把慢 SQL 修掉（先 EXPLAIN 看计划，再看锁等待，最后看调用方 N+1），池排队与线程池积压往往跟着缓解。反过来只扩连接池或线程池，是给慢 SQL 更多并发，治标不治本；扩池之前必须先确认慢 SQL 已排除。
