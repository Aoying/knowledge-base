# JVM GC 调优

## 1. 核心概念

GC 调优不是「背参数」，而是先定目标再选手段。对在线服务通常只有两个目标：**吞吐量**（单位时间处理多少请求）和**停顿时间**（单次 STW 多久），两者天然冲突：堆越大、回收越不频繁，吞吐越好但单次停顿越长。调优的顺序永远是「先观测、再定目标、最后动参数」，反过来调参数基本是在碰运气。

先记住分代假设：绝大多数对象朝生夕死，所以堆分年轻代（Eden + 两个 Survivor）和老年代。Minor GC 只扫年轻代，快；对象熬过多次 Minor GC（默认年龄阈值 15，可由 `-XX:MaxTenuringThreshold` 调整）才晋升老年代；老年代满了触发 Major/Full GC，要扫全堆，最伤停顿。

## 2. 常用收集器与选型

| 收集器 | 参数 | 特点 | 适用 |
|---|---|---|---|
| G1 | `-XX:+UseG1GC` | JDK 9+ 默认（JDK 8 需手动开），把堆切成 Region，按「垃圾最多优先」回收，可给停顿目标 | 通用在线服务，默认选它 |
| Parallel GC | `-XX:+UseParallelGC` | JDK 8 默认，吞吐优先，停顿不可控 | 批处理、离线任务 |
| ZGC | `-XX:+UseZGC` | 低延迟，并发回收，大堆下停顿也可控；JDK 15+ 可用，JDK 21 有分代 ZGC | 堆很大且延迟敏感（经验：一般业务系统用不上，别跟风） |
| Serial GC | `-XX:+UseSerialGC` | 单线程回收 | 小内存容器、工具进程 |

经验：JDK 8 时代的老参数（如 CMS 的一套）在 G1 上不要照搬，CMS 已在 JDK 14 移除。

## 3. 起步参数

```bash
java -Xms2g -Xmx2g -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -jar app.jar
```

- **Xms=Xmx**：别让堆动态伸缩，伸缩时的 Full GC 最伤；容器环境还要给堆外内存（元空间、线程栈、直接内存）留余量，`-Xmx` 不能等于容器内存上限。
- `MaxGCPauseMillis=200` 是给 G1 的**目标值不是保证值**：为了达标它会调整每次回收的 Region 数量；目标设得过小反而会让 GC 更频繁、吞吐下降。
- 年轻代大小一般不手动设（G1 会自适应在堆的 5%–60% 间调整），手动锁死 `-Xmn` 会废掉 G1 的停顿控制，先别动。
- 元空间：`-XX:MaxMetaspaceSize` 建议显式设上限，防止类加载泄漏把内存吃光且无声无息。

## 4. 观测：先看日志和 jstat，再谈调参

```bash
# JDK 9+ 统一日志；JDK 8 用 -XX:+PrintGCDetails -Xloggc:gc.log
-Xlog:gc*:file=gc.log:time,uptime:filecount=10,filesize=20m

# 每秒看一次各区占用与 GC 次数/耗时
jstat -gc <pid> 1000
```

看日志抓三个信号：

1. **Full GC 频繁**：老年代一直在涨、回收不下去，先怀疑内存泄漏或缓存无上限，而不是加大堆。
2. **单次停顿过长**：看停顿发生在哪个阶段；G1 日志里 Evacuation 之外的时间长，常见原因是引用处理（软/弱引用、Finalizer 积压）。
3. **晋升失败 / to-space exhausted**：Survivor 放不下、对象提前晋升把老年代顶满，多半是短时间内产生了大量「中年对象」，如批量查询结果集。

神农这种长跑服务：先保证堆够（`jstat -gc` 看 Old 区涨速），再调暂停目标，别反过来。

## 5. 常见坑

- **System.gc() 和显式触发**：代码里、或某些中间件默认会调 `System.gc()` 引发 Full GC；排查莫名 Full GC 时先加 `-XX:+DisableExplicitGC` 验证（注意 RMI 等依赖显式 GC 的场景要评估）。
- **大对象直进老年代**：G1 里超过 Region 一半的对象是 humongous 对象，直接放老年代专属 Region，频繁分配大 byte[]（如大文件、大报文一次性读入）会造成碎片和提前 Full GC；业务侧改流式处理比调参有效。
- **拿压测环境的参数上生产**：堆大小、对象存活率都随真实流量变化，参数必须用生产 GC 日志回放验证。
- **只看平均停顿**：平均值好看但 P99 长尾伤用户，GC 日志要按停顿分布看。

## 6. 排查工具速记

- `jmap -histo <pid>`：看对象数量/占用排行，定位哪类对象在涨（只看排行，别随便 dump 生产大堆）。
- `jmap -dump` / MAT 分析：确认泄漏时用，dump 大堆本身会引发停顿，挑低峰做。
- Arthas 的 `dashboard`、`jvm`、`memory` 命令适合线上快速摸底。

## 小技巧与冷知识

【小技巧】Minor GC 太频繁时，先算分配速率再谈加堆：G1 日志里每次 Young GC 的 Eden 占用量除以两次 Young GC 的时间间隔，就是这段时间的分配速率（MB/s）。分配速率高，Eden 再大也顶不住几秒就满——根子是业务在批量建临时对象，压分配（复用缓冲、流式处理）比加堆更治本；堆够但 Minor GC 密，十有八九是分配速率的问题。

【小技巧】查一次 Full GC 别从头翻日志，先 grep 两个关键词：`Pause Full` 定位 Full GC 那一行，`to-space exhausted` 看是不是 Survivor 放不下、对象提前晋升顶满了老年代。再往前翻它前面几次 Young GC 的晋升量，晋升量突然放大、随后就 Full GC，这条链就是根因方向；日志开了 `filecount`/`filesize` 轮转后还能按时间窗定位，没开轮转的日志先 grep 再谈分析。

【小技巧】`jmap -histo:live` 会触发一次 Full GC 才统计存活对象，高峰时段别用：线上只想看“哪类对象在涨”时，用不带 `:live` 的 `jmap -histo`，它只扫一遍堆做计数，不强制回收，代价小得多。原文第 6 节说“只看排行，别随便 dump 生产大堆”，histo:live 就是同一个道理——先确认你要的是排行还是存活数，再决定加不加 `:live`。

【小技巧】验证一次参数改动，要同一份流量跑前后对比：同一段压测脚本或同一段生产流量回放，改参数前后各跑一轮，同时看吞吐量和 P99 停顿两条曲线。只看“GC 次数少了”不够——次数少了、停顿却变长了，等于没调；两个指标一起变好才算有效，单指标变好、另一指标变差要打回重调。

【小技巧】停顿目标设得太小，G1 会反过来逼出 Full GC：`MaxGCPauseMillis` 压得越低，G1 每次回收的 Region 数就越少，Mixed GC 回收老年代的速度赶不上老年代的涨速，老年代越积越多，最后还是触发 Full GC。原文只说了目标过小会让 GC 更频繁、吞吐下降，更深一层是——过小的停顿目标会把 Full GC 提前，停顿目标要和老年代涨速一起看，不能只盯数字越小越好。

【小技巧】停顿长、但 GC 日志里 Evacuation 时间不长时，根子可能不在 GC 本身：加 `-Xlog:safepoint` 看 safepoint 停顿，偏向锁撤销、类卸载这类操作也会让应用线程停下，而且不计在 GC 的 Evacuation 时间里。原文第 4 节说“Evacuation 之外的时间长，先看引用处理”，safepoint 是同一类排查方向——停顿的账要分 GC 和非 GC 两本算，别全记在收集器头上。

【小技巧】改了堆大小，要重新核对大对象的行为：G1 的 Region 大小默认按堆大小自动选（1MB 起，最大 32MB），humongous 对象的阈值是 Region 大小的一半。堆从 2g 改到 8g，Region 跟着变大，原来算 humongous、直接进老年代的对象可能不再算了——大对象进老年代的路径变了，碎片和 Full GC 的节奏也会跟着变，改堆不是只改一个数字。

【冷知识】G1 的名字就是它的回收策略：G1 是 Garbage-First（垃圾优先）的缩写，回收时先挑垃圾最多的 Region 下手，“垃圾最多优先”不是比喻，是名字的直译。它在 2017 年随 JDK 9 成为默认收集器，之前 JDK 8 的默认是 Parallel GC——从“吞吐优先”换成“停顿可控”，默认值的变化本身就是调优思路的变化。

【冷知识】CMS 的全名是 Concurrent Mark Sweep（并发标记清除）：它在 JDK 8 时代是低延迟场景的首选，JDK 14 被正式移除。老项目升级 JDK 时，CMS 的整套参数要成批删掉，留着不删启动会直接报错；原文第 2 节只提了“不要照搬”，落到升级动作上就是“先 grep 出所有 CMS 参数再升级”。

【冷知识】STW 的全称是 Stop-The-World（停止全世界）：GC 停顿时应用线程全部停下，Minor GC 的停顿通常是毫秒级，Full GC 的停顿大致随堆大小增长——堆翻倍，Full GC 要扫的活对象也翻倍，停顿也跟着翻倍。这就是原文第 1 节“堆越大、单次停顿越长”的根子，调优时堆不是越大越好，停顿目标和堆大小要一起定。

## 面试与自测

1. GC 调优的两个目标是什么？为什么说两者天然冲突，调优顺序应该是怎样的？
2. 起步参数里的 `-XX:MaxGCPauseMillis=200` 是保证值吗？把这个目标设得过小会有什么反效果？
3. 线上发现 Full GC 频繁，第一反应应该是加大堆吗？按本篇应该先查什么？

### 参考答案

1. 两个目标是吞吐量（单位时间处理多少请求）和停顿时间（单次 STW 多久），两者天然冲突：堆越大、回收越不频繁，吞吐越好但单次停顿越长。调优顺序永远是“先观测、再定目标、最后动参数”，反过来调参数基本是在碰运气。
2. 不是保证值，只是给 G1 的目标值：为了达标它会调整每次回收的 Region 数量。目标设得过小反而会让 GC 更频繁、吞吐下降。年轻代大小一般也不手动设，G1 会自适应在堆的 5%–60% 间调整，手动锁死 `-Xmn` 会废掉 G1 的停顿控制。
3. 不是。老年代一直在涨、回收不下去时，先怀疑内存泄漏或缓存无上限，而不是加大堆；先看 GC 日志和 `jstat -gc` 的 Old 区涨速。神农这种长跑服务：先保证堆够，再调暂停目标，别反过来。
