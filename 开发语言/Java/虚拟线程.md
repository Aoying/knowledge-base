# 虚拟线程

## 1. 核心概念

虚拟线程（Virtual Thread，JDK 21 正式发布，JEP 444）是 JVM 管理的轻量线程：它不再 1:1 绑定操作系统线程，而是多个虚拟线程复用少量「载体线程」（平台线程）。虚拟线程阻塞在 IO 上时，JVM 把它从载体线程上卸载（unmount），载体线程去跑别的虚拟线程；阻塞结束再挂回来。这就是「写同步代码，跑异步性能」的实现原理——代码还是阻塞式写法，线程资源却不再被阻塞占住。

它解决的是**高并发 IO 密集场景下平台线程不够用**的问题，不解决 CPU 密集计算：计算该用几个核还是几个核，多开虚拟线程没有用。

```java
// 以前：平台线程 1:1 内核线程，开几千个就 OOM
// 现在：虚拟线程轻量到可以"一个请求一个线程"
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10000; i++)
        exec.submit(() -> callDownstream());
}
```

## 2. 创建方式

```java
// 1) 直接起一个
Thread.startVirtualThread(() -> doWork());

// 2) 工厂
ThreadFactory factory = Thread.ofVirtual().name("vt-", 0).factory();

// 3) 每任务一个虚拟线程的执行器（最常用，配合 try-with-resources 等任务跑完）
ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor();
```

注意没有「虚拟线程池」这个概念：不要用固定大小池子去限制虚拟线程数量，那等于退回平台线程的老路；要限并发用 `Semaphore` 控制下游保护，而不是限制线程数。

## 3. Pinning：最关键的坑

虚拟线程阻塞时若无法卸载，就会「钉住」（pin）载体线程，退化成平台线程的行为。两种钉住场景：

- 在 `synchronized` 块/方法内做阻塞操作（JDK 21 的实现限制；JDK 24 的 JEP 491 已解决此问题，JDK 21 上要避开）。
- 调用 native 方法或外来函数接口期间阻塞。

应对：把 `synchronized` 换成 `ReentrantLock`——`Lock` 的实现基于 AQS，阻塞时虚拟线程可以正常卸载。排查 pinning 用启动参数 `-Djdk.tracePinnedThreads=full`，它会打印钉住时的堆栈。

经验：老代码库里 `synchronized` 包着查库/调接口的写法不少，迁移虚拟线程前先全局搜一遍这个模式。

## 4. 与现有栈的落点

- 写同步代码，跑异步性能：`Thread.sleep`、`Lock` 在虚拟线程里不会 pin 住载体线程（`synchronized` 块里别调阻塞方法，仍会 pin）。
- 神农这种 IO 密集型（调 OceanBase/Redis/下游接口）最吃香：请求线程大量时间在等下游返回，换虚拟线程后同样的机器能挂住多得多的并发请求。
- Spring Boot 3.2+ 一键开启：`spring.threads.virtual.enabled=true`，Tomcat 请求处理、@Async 默认执行器都会切到虚拟线程。但神农在 Boot 2.7.3 + JDK 8 栈上，享受这个收益的前置条件是先完成 JDK 17/21 与 Boot 3 的升级，见 [Spring Boot](开发语言/Java/Spring/Spring-Boot.md) 的升级路线图。
- 数据库连接池不受虚拟线程影响：请求再多，能同时查库的还是连接池大小那几个连接。并发上去后要盯 Druid 的活跃连接和等待队列，别把瓶颈从线程挪到连接池还没发现，见 [Druid](开发语言/Java/Druid.md)。

## 5. ThreadLocal 与上下文

- 虚拟线程也是 Thread，`ThreadLocal` 能用，但「一个请求一个虚拟线程」意味着创建量巨大，重型 ThreadLocal 值（大对象、连接）会跟着放大内存占用；该用请求级上下文传递的别滥用 ThreadLocal 囤数据。
- JDK 21 提供了 ScopedValue（预览 API）作为 ThreadLocal 的轻量替代，适合「一次调用链内只读传递」的场景，了解即可，生产慎用预览特性。（2026-10-25 注：Java 25 中 ScopedValue 已转正为正式 API，见第 7 节。）

## 6. 升级路径

- 升级路径：JDK 17→21 主要是 `--release` 和依赖兼容性，先在测试环境跑一遍。
- 顺带检查：老版本 JDBC 驱动、字节码类库（ASM/旧 cglib）在 JDK 21 上的兼容性，是升级时最常见的翻车点（经验）。

## 7. 升级路径到 Java 25 LTS

> 时效注记（2026-10-25 核实）：Java 25 于 2025-09-16 发布，是 LTS 版本。下述 JEP 编号与状态以公开的 Java 25 特性资料为准。

- **ScopedValue 转正**：JEP 506，Java 25 起为正式 API，可生产使用。用法不变（`ScopedValue.where(...).run(...)`），绑定不可变、作用域结束自动失效；§5 里“预览、生产慎用”的表述到 Java 25 已过时。
- **结构化并发未转正**：Java 25 中仍是第五次预览，JEP 505，生产使用仍需 `--enable-preview`。神农这类业务代码先别拿它做核心流程控制，等转正再评估。
- **虚拟线程本身无变化**：JEP 444 自 JDK 21 已正式；synchronized 钉住问题 JDK 24 的 JEP 491 已解决（与 §3 一致）。

升级链建议：神农当前是 Boot 2.7.3 + JDK 8，不要从 8 直跳 25——先走 §6 的 JDK 21 + Boot 3 路线，再评估 25。到 25 之后，可把请求级上下文从 ThreadLocal 逐步迁到 ScopedValue（只读传递场景）；迁移前先全局搜一遍 ThreadLocal 用法，重型 ThreadLocal 值在虚拟线程下的放大问题（§5）迁过去自然消失。

## 小技巧与冷知识

【小技巧】虚拟线程默认是守护线程，JVM 不会等它跑完才退出：主流程结束时还在跑的虚拟线程会被进程退出直接截断，平台线程“线程活着进程就不退”的直觉在这里不成立。需要等任务完成时，用 try-with-resources 等执行器关闭、或用 CountDownLatch 显式等待，别把虚拟线程当成“后台慢慢跑”的保障。

【小技巧】载体线程数默认就等于 CPU 核数：虚拟线程的默认调度器是一个 ForkJoinPool，并行度是 `Runtime.getRuntime().availableProcessors()`。所以 CPU 密集的虚拟线程开再多也只能占满这几个载体线程，算一下核数就知道计算任务的天花板在哪；虚拟线程省的是阻塞等待占用的线程，不是算力。

【小技巧】自旋、死循环的虚拟线程不会卸载：卸载只发生在阻塞点（park、IO、sleep、拿锁），空转循环一直占着载体线程，别的虚拟线程排不上。换了虚拟线程却没提速时，先看热点路径里有没有忙等循环——它占住的载体线程数等于核数，几个死循环就能把调度器堵满。

【小技巧】synchronized 里不阻塞就不会钉住：钉住只发生在 synchronized 块内调用阻塞操作时，纯计算的短临界区不产生钉住，不用为此把全库的 synchronized 都换成锁。迁移时只改“锁里调 IO、调接口”的那几处，先全局搜这个模式，而不是无差别替换。

【小技巧】虚拟线程默认不继承 InheritableThreadLocal：`Thread.ofVirtual()` 默认 `inheritInheritableThreadLocals(false)`，父线程的 InheritableThreadLocal 值传不过去，平台线程“子线程自动继承”的老习惯在这里失效。需要跨线程传上下文时显式打开继承，或用 ScopedValue（§7）走作用域传递，别指望默认值帮你传。

【小技巧】虚拟线程的栈是动态伸缩的，`-Xss` 对它不起作用：平台线程的栈大小固定、由 `-Xss` 定，虚拟线程的栈按需增长、用完回收。虚拟线程开几十万个也不怕栈内存爆炸，根子就在这里；反过来，调 `-Xss` 省不出虚拟线程的内存，别在它身上浪费时间。

【小技巧】`newVirtualThreadPerTaskExecutor()` 造出来的执行器一定要 close：它返回的 ExecutorService 是 AutoCloseable，`close()` 会等已提交的任务跑完再返回，直接丢弃不关，任务可能在进程退出前被半路截断。§2 示例里的 try-with-resources 不是写法习惯，是“等任务跑完”的保证。

【小技巧】JFR 有虚拟线程专属事件，持续观测比事后排障直接：`jdk.VirtualThreadStart`、`jdk.VirtualThreadEnd`、`jdk.VirtualThreadPinned` 三个事件能看创建量、结束量和钉住次数。§3 的 `-Djdk.tracePinnedThreads` 是钉住发生时打堆栈，JFR 是长期监控——上线后盯着 VirtualThreadPinned 事件数，钉住一冒头就能发现。

【小技巧】线程名带序号才好排障：`Thread.ofVirtual().name("vt-", 0)` 会按顺序给虚拟线程编号，dump 里能直接定位是第几个任务；不带序号时几万个虚拟线程全叫一个名，线程转储里根本分不清谁是谁。§2 的工厂写法里 name 带计数器不是装饰，是排障的前提。

【冷知识】虚拟线程三度预览才转正：JEP 425（JDK 19 第一次预览）、JEP 436（JDK 20 第二次预览）、JEP 444（JDK 21 正式）。JDK 19/20 时期用 `--enable-preview` 写过的虚拟线程代码，升到 21 后记得把预览开关摘掉，API 本身没变，变的是它不再需要预览标志。

【冷知识】虚拟线程是 Project Loom 的成果，2018 年启动：Loom 的目标就是“轻量线程 + 阻塞式写法”，虚拟线程只是它的一半；另一半结构化并发（JEP 505）到 Java 25 仍在预览（§7）。理解这个出处就明白，虚拟线程和结构化并发是同一套“让并发代码写起来像同步”的思路，不是两个孤立特性。

【冷知识】Loom 早期原型里它不叫虚拟线程，叫 Fiber：早期设计用 `Fiber` 这个名字，后来改称 Virtual Thread，强调它是 Thread 的一种而不是新概念。老文章、老演讲里搜到 Fiber，说的往往就是同一回事，读的时候按虚拟线程理解就行。

## 面试与自测

1. 虚拟线程阻塞在 IO 上时，为什么不会像平台线程那样占住一个内核线程？
2. JDK 21 下，在 synchronized 块里做阻塞操作会有什么后果？怎么规避和排查？
3. 神农当前是 Boot 2.7.3 + JDK 8，能否直接开 `spring.threads.virtual.enabled=true` 用上虚拟线程？还要注意什么瓶颈？

### 参考答案

1. 虚拟线程阻塞时 JVM 会把它从载体线程上卸载（unmount），载体线程去跑别的虚拟线程，阻塞结束再挂回来；所以代码仍是阻塞式写法，线程资源却不再被阻塞占住。这正是“写同步代码，跑异步性能”的原理。
2. 会钉住（pin）载体线程，退化成平台线程行为——JDK 21 的实现限制，JDK 24 的 JEP 491 才解决。JDK 21 下的规避办法是把 synchronized 换成 ReentrantLock（基于 AQS，阻塞时可正常卸载）；排查用启动参数 `-Djdk.tracePinnedThreads=full` 打印钉住时的堆栈。迁移前先全局搜一遍“synchronized 包着查库/调接口”的老写法。
3. 不能。`spring.threads.virtual.enabled=true` 是 Spring Boot 3.2+ 的开关，前置条件是先完成 JDK 17/21 与 Boot 3 的升级（不要从 JDK 8 直跳 25，先走 JDK 21 + Boot 3 路线）。另外数据库连接池不受虚拟线程影响，能同时查库的还是连接池大小那几个连接，并发上去后要盯 Druid 的活跃连接和等待队列，别把瓶颈从线程挪到连接池还没发现。
