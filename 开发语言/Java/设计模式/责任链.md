# 责任链模式

## 模式介绍

**意图**：让请求沿处理者链条传递，每个处理者决定「自己处理还是传给下一个」，发送方不关心最终是谁处理的。

**结构与角色**：
- Handler（抽象处理者）：定义处理方法，持有一个后继处理者引用。
- ConcreteHandler（具体处理者）：满足条件就处理并终止或继续传递，不满足则直接后传。
- Client（客户端）：只向链头发起请求。
- 终止条件必须明确：链尾默认处理、返回 false 中断、抛异常，三选一并全链统一。

**效果**：
- 优点：新增、重排、删除处理环节不用改调用方；每个处理者单一职责；运行时可动态增减链。
- 代价：调试成本高（不知道被谁处理、为什么没人处理）；链太长排查必须配日志打点；环链会死循环。

**适用信号**：同一请求要依次经过多个「可插拔」的校验/处理步骤；审批要逐级上报，谁能拍板取决于金额/等级；请求的处理者不止一个、且事先不确定。

**落点**：
- Servlet Filter / Spring 拦截器（HandlerInterceptor）、网关过滤器链。
- 审批流：组长→经理→总监逐级审批，任一级驳回即终止（Flowable 的会签/顺序审批同理）。
- 日志框架的 Appender 链、参数校验链、风控规则链。

## 模式 Demo

```java
import java.util.*;

// 请求：请假申请，天数决定审批人
record LeaveRequest(String name, int days) {}

// 抽象处理者：返回 true 表示已处理(终止链)，false 表示继续向后传
abstract class Approver {
    protected Approver next;
    Approver setNext(Approver next) { this.next = next; return next; }
    abstract boolean approve(LeaveRequest req);
}

// 组长：只能批 1 天以内
class Leader extends Approver {
    boolean approve(LeaveRequest req) {
        if (req.days() <= 1) {
            System.out.println("组长批准: " + req.name() + " 请假 " + req.days() + " 天");
            return true;
        }
        System.out.println("组长批不了，转经理");
        return next != null && next.approve(req);
    }
}

// 经理：能批 3 天以内，且对 2 天以上的申请要驳回式终止(演示"中断")
class Manager extends Approver {
    boolean approve(LeaveRequest req) {
        if (req.days() <= 3) {
            System.out.println("经理批准: " + req.name() + " 请假 " + req.days() + " 天");
            return true;
        }
        System.out.println("经理处理不了，转总监");
        return next != null && next.approve(req);
    }
}

// 总监：链尾，必须给出最终结论
class Director extends Approver {
    boolean approve(LeaveRequest req) {
        if (req.days() <= 7) {
            System.out.println("总监批准: " + req.name() + " 请假 " + req.days() + " 天");
            return true;
        }
        System.out.println("总监驳回: " + req.name() + " 请假超 7 天，不批"); // 终止，不再后传
        return true;
    }
}

public class ChainDemo {
    public static void main(String[] args) {
        Approver leader = new Leader();
        leader.setNext(new Manager()).setNext(new Director()); // 组装链

        List<LeaveRequest> reqs = List.of(
            new LeaveRequest("小王", 1),
            new LeaveRequest("小李", 3),
            new LeaveRequest("小张", 10));
        for (LeaveRequest r : reqs) {
            leader.approve(r); // 客户端只认链头
            System.out.println("---");
        }
    }
}
```

- **谁决定终止**：本例用 boolean 返回值表达「已处理」，任何一环 return true 都不再后传，这就是审批「驳回即终止」的实现方式；过滤器链则是全员通过后才放行，两种终止语义要先定好。
- **链尾兜底**：链尾必须给出最终结论（批准/驳回/异常），否则请求会「石沉大海」，线上一律给链尾加默认处理和日志。
- **坑：链的组装顺序即业务规则**。顺序错了（比如总监放链头）行为全变；组装代码要集中一处，不要散落在各业务方法里临时拼链。

## 适用场景与选型

- 用它：同一请求要依次经过多个可插拔的校验/处理步骤；审批逐级上报、谁能拍板取决于金额或等级；请求的处理者不止一个、且事先不确定；步骤需要运行时动态增减或重排。
- 不用它：步骤固定且只有一两步，直接顺序调用更直观；每一步都必须执行、且后一步强依赖前一步的结果时，用组合或管道而非“可终止”的链；需要失败回溯或补偿时，链只向前走，回滚要另设计。
- 与装饰器的一句话区分：装饰器是层层包装、增强同一个请求（每个装饰器都参与）；责任链是多个处理者中某一个决定处理、其余只过手（处理者之间是“或”不是“叠加”）。

## 优缺点

- 优点：发送方与处理者解耦，客户端只认链头；新增、重排、删除环节不用改调用方；每个处理者单一职责；运行时可动态组装。
- 缺点：调试成本高——不知道被谁处理、为什么没人处理；请求无人处理时会静默消失；链太长时排查必须配日志打点；组装成环会死循环；链的顺序本身就是业务规则，顺序错行为全变。

## 常见误区

- 链尾不兜底：链上所有处理者都后传，请求石沉大海，调用方拿不到任何结论。正确：链尾必须给出最终结论（批准/驳回/异常），线上一律给链尾加默认处理和日志——Demo 的 Director 就是兜底。
- 终止语义不统一：有的处理者 return true 表示“已处理、终止”，有的表示“继续传”，同一条链两种语义必然出 bug。正确：全链统一约定并写进抽象处理者的注释，Demo 的约定是 true = 已处理终止。
- 组装顺序散落各处：每个业务方法里临时拼链，顺序错了（如总监放链头）行为全变且难发现。正确：组装代码集中一处，顺序即规则，测试要覆盖每种输入走到的处理者（Demo 的 1 天/3 天/10 天就是三种覆盖）。

## 小技巧与冷知识

【小技巧】链一旦组装好就别再改它：链头组装完成后，把后继引用收进构造器或工厂里一次性拼好，运行中别再 setNext 换环节。请求正在沿链走、另一线程中途改了 next，后续处理者看到的就是一条“半新半旧”的链；运行时动态增减是模式的优点，但改链要发生在请求之间，改完再放新请求进来，别在链跑着的时候动手。

【小技巧】处理者本身要无状态，状态全放进请求上下文对象：Handler 里别攒“本次请求处理到哪了”这类字段，一条链被多个请求共用时，字段会在请求之间互相串。请求走到哪、中间结果是什么，都装进一个随请求走的上下文对象（比如 LeaveContext），处理者只读它、改它，不留自己的字段——链可复用的前提就是处理者无状态。

【小技巧】“继续向后传”要写成显式的 return，别靠默认落到链尾：`return next != null && next.approve(req)` 这种写法把“没处理就后传”写在了 return 里，读代码的人一眼能看到这条路。反过来，只写 `if (能处理) {处理; return true;}` 然后让方法自然落到结尾，等于把“后传”藏进了隐式流程，后人加一环时很容易以为“不满足就直接结束”。

【小技巧】请求上要留一个“到底被谁处理了”的标记：上下文对象里加一个 `handledBy` 字段，处理者拍板时顺手写进自己的名字。线上排障时不用翻每环的日志拼路径，直接看最终结论是谁给的；审计、统计“哪一级批了多少单”也靠这个字段，而不是事后去日志里反推。

【小技巧】链只在“可能提前终止”时才有意义，每一步都必须跑就别用它：校验链里每一步都必须执行、后一步还强依赖前一步的结果时，责任链的“可终止”反而成了隐患——某环一不小心 return true，后面的步骤就悄悄跳过了。步骤固定、步步必跑的场景用顺序调用或管道，链是给“不知道谁拍板、随时可能停”准备的。

【小技巧】处理者改了请求再往后传时，要把“改了什么”写进注释或上下文：前一环给请求补了字段、改了金额，后一环看到的是改过的请求，顺序一换结果就变。链上允许改请求，但改动必须显性化——要么在上下文里记一笔“谁改了什么”，要么把“只读”和“可改”的请求拆成两个对象；悄悄改请求是链式代码最难查的一类 bug。

【小技巧】给链加一个最大跳数兜底，防组装失误造成的环链：上下文里记一个已走环节数，超过上限直接抛异常或记告警返回默认结论。原文说“环链会死循环”，光靠“组装时别成环”不够——配置化组装、运行时动态插环节时，环可能在运行中才出现；跳数上限是最后一道保险，和链尾兜底是一对。

【小技巧】高频命中的处理者放前面，链的顺序也是性能：审批链里 80% 的申请都在组长一级就批完，把组长放链头、总监放链尾，平均跳数只有一两步；反过来把最少命中的放前面，每个请求都要空跑大半条链。顺序是业务规则没错，但命中率也是排顺序的依据之一，线上可以统计各环的命中占比再调顺序。

【小技巧】处理者要分开测：单测只测“本环节”，用一个 stub 的 next 断言“满足条件时处理并终止、不满足时原样后传”；链整体再用原文 Demo 的 1 天/3 天/10 天三档输入做集成测试。两层测试分开写，链尾兜底漏了、顺序拼错了，集成测试能抓；某个环节的判断条件写反了，单测能抓；混在一起测，坏在哪一层说不清。

【小技巧】链的组装代码要能打印出来：工厂或 Builder 拼完链后，顺手记一条“链顺序：Leader → Manager → Director”的启动日志。线上发现“某类请求总被错误的人批了”，先看启动日志里链的实际顺序，再进处理者里查判断条件；顺序本身就是业务规则，组装结果值得一条日志留痕。

【冷知识】GoF 原书讲责任链用的例子是图形界面的帮助系统：用户在一个控件上点“帮助”，请求先交给这个控件，控件答不上来就传给对话框，对话框再传给整个应用，直到有人能回答。审批链、过滤器链都是这个例子的业务版——“沿着层级向上传，直到有人接住”是责任链的原始样板。

【冷知识】Servlet 的 Filter 链是责任链在 Java 里最经典的落地：`FilterChain.doFilter()` 就是“把请求传给下一个”，每个 Filter 决定放行、拦截还是改完再传。Filter 是 Servlet 2.3（2001 年，随 J2EE 1.3 发布）引入的，比 Spring 的拦截器链早得多，网关过滤器链也是同一套思路的后代。

【冷知识】`java.util.logging` 的日志记录也是沿链向上传的：一条日志记录先交给本 Logger 的 Handler，再沿父 Logger 一级级向上传，直到根 Logger，`useParentHandlers` 关掉就只在本级处理。日志“逐级上抛、直到有人处理”的传播方式，和责任链的传递语义是同一回事，只是这里的“处理者”是各级 Logger 的 Handler。

## 面试与自测

1. Demo 里 boolean 返回值表达什么？过滤器链的终止语义和审批链有什么不同？
2. 请求沿链走完却没人处理，线上怎么发现、怎么防范？
3. 责任链和装饰器有什么区别？什么场景该用装饰器而不是责任链？

### 参考答案

1. boolean 表达“是否已处理”：true 终止链，不再后传；false 继续向后传。审批链是“某一级拍板即终止”（驳回也终止）；过滤器链是“全员通过才放行”，任一环节拦截即终止放行——两种终止语义要先定好，不能混用。
2. 发现靠链尾兜底日志和“请求无结论”监控告警；防范靠三点：链尾必须给默认结论、每环打点日志（进了谁、出了什么结论）、组装后做测试覆盖（每种输入至少走到一个处理者）。
3. 装饰器是层层包装增强同一个请求，每个装饰器都参与处理（如加日志、加缓存、加权限校验后仍执行原逻辑）；责任链是多个处理者中某一个拍板，其余只过手。需要“叠加增强”用装饰器，需要“选一个处理者”用责任链。
