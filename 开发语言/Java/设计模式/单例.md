# 单例模式

## 模式介绍

**意图**：保证一个类全局只有一个实例，并提供一个全局访问点。解决的问题是「有些对象多建一个就出错」：配置管理器、连接池、缓存、计数器，多个实例之间状态不一致会互相打架。

**结构与角色**：
- 单例类本身：构造器私有化，自己持有自己唯一的静态实例，对外只暴露一个静态获取方法。

**效果**：
- 优点：全局状态集中、节省重复创建的资源、访问入口可控（可以加懒加载）。
- 代价：本质是可控的全局状态，滥用会让依赖关系隐藏化（谁都能拿，测试时难替换 mock）；实例活到进程结束，不当持有大对象会变相内存泄漏。

**适用信号**：
- 对象创建成本高且全程复用一份就够（连接池、线程池）。
- 需要跨多处协调的全局状态（配置、注册表）。
- 反信号：只是「图省事不想传参」就别做单例，那是在写全局变量。

**落点**：
- Spring Bean 默认作用域就是单例（每个容器一个实例），日常写业务代码通常不需要手写单例，交给容器。
- 取舍口诀：状态属于「整个应用一份」才配单例；
  状态属于「每个请求一份」「每个用户一份」的，坚决不能塞进单例字段，
  否则多线程下会串数据——这是手写单例在 Web 项目里最常见的事故来源。
- JDK：`Runtime.getRuntime()`、各种 `getInstance()` 工厂背后。
- 手写场景：脱离容器的工具进程、SDK 内部组件。

## 模式 Demo

```java
// 双重检查锁定（DCL）单例：懒加载 + 线程安全，生产里手写单例的标配
public class AppConfig {
    // volatile 不能少：禁止指令重排，防止其他线程拿到"还没构造完"的对象
    // new 对象分三步：分配内存 -> 初始化 -> 引用赋值；没有 volatile 时后两步可能重排
    private static volatile AppConfig instance;
    private final java.util.Properties props = new java.util.Properties();

    private AppConfig() { /* 构造私有，外部 new 不了 */ }

    public static AppConfig getInstance() {
        if (instance == null) {                 // 第一次检查：已有实例就直接返回，不进锁
            synchronized (AppConfig.class) {
                if (instance == null) {         // 第二次检查：防多个线程排队进来重复建
                    instance = new AppConfig();
                }
            }
        }
        return instance;
    }

    public String get(String key) { return props.getProperty(key); }
}

// 枚举单例：最简且绝对安全，Joshua Bloch 推荐写法
// 枚举天然防反射、防反序列化破坏唯一性，缺点是不能懒加载
enum ConfigEnum {
    INSTANCE;
    private final java.util.Properties props = new java.util.Properties();
    public String get(String key) { return props.getProperty(key); }
}

class Demo {
    public static void main(String[] args) {
        AppConfig a = AppConfig.getInstance();
        AppConfig b = AppConfig.getInstance();
        System.out.println(a == b);                       // true：同一实例
        System.out.println(ConfigEnum.INSTANCE == ConfigEnum.INSTANCE); // true
    }
}
```

Demo 要点与变体/坑：
- **饿汉式 vs 懒汉式**：饿汉式直接 `private static final AppConfig I = new AppConfig()`，类一加载就建好，简单且天然线程安全，缺点是可能用不上也先占资源；DCL 和静态内部类都属于懒汉式（第一次用才建）。实例小而必用就饿汉，重而未必用就懒汉。
- **DCL 为什么要 volatile**：`instance = new AppConfig()` 不是原子操作，重排后另一个线程可能在第一次检查时看到非 null 但未初始化完的对象，拿到半成品。漏掉 volatile 是最经典的单例 bug。
- **静态内部类写法**：`private static class Holder { static final AppConfig I = new AppConfig(); }`，靠类加载机制保证线程安全 + 懒加载，不想写 DCL 时用它，也很稳。
- **反射与序列化能破坏手写单例**：反射可强行调用私有构造；反序列化会生成新对象（需加 `readResolve()` 返回现有实例）。枚举单例对这两种攻击免疫，所以能用枚举就优先枚举。
- Spring 环境下先别手写：Bean 默认单例已经把生命周期和线程可见性都处理了，手写单例反而和容器打架；原型作用域的 Bean 也不是单例，别混淆概念。
