# 装饰器模式

## 模式介绍

**意图**：不改原类、不靠继承，在运行时给对象一层层「裹」上新功能。功能可以自由叠加和拆卸。

**结构与角色**：

- 抽象组件（Component）：被装饰的接口。
- 具体组件（ConcreteComponent）：最里层的真实对象。
- 装饰器（Decorator）：同样实现组件接口，内部持有另一个组件；自己的方法 = 先/后做点事，再转发给被裹对象。
- 具体装饰器：每个只加一种功能（加密、压缩、缓存、日志）。

**效果**：

- 优点：功能正交组合，避免「继承出 EncryptAndCompressAndCacheSource」的爆炸；增删功能只改组装顺序。
- 代价：层数多了调试时调用栈很长；顺序有语义（先压缩后加密和反过来结果不同），组装处要想清楚。

**适用信号**：

- 同一能力要按需拼装：这个数据源要压缩+加密，那个只要加密。
- 想加功能但动不了原类（第三方、已稳定），又不想为每种组合写子类。

**落点**：JDK IO 流是教科书例子——`new BufferedInputStream(new FileInputStream(f))`，每一层都是装饰器；Servlet 的 `HttpServletRequestWrapper`；MyBatis 的缓存插件链、Spring 的 `TransactionAwareCacheDecorator` 等各种 Wrapper。

## 模式 Demo

```java
// 抽象组件：数据源
interface DataSource {
    void write(String data);
    String read();
}

// 具体组件：最里层的内存数据源（示意，换成文件/网络同理）
class MemoryDataSource implements DataSource {
    private String stored = "";
    public void write(String data) { stored = data; }
    public String read() { return stored; }
}

// 装饰器基类：实现同一接口，持有被裹对象，默认只转发
abstract class DataSourceDecorator implements DataSource {
    protected final DataSource inner;
    protected DataSourceDecorator(DataSource inner) { this.inner = inner; }
    public void write(String data) { inner.write(data); }
    public String read() { return inner.read(); }
}

// 具体装饰器一：压缩（示意，用长度标记代替真实算法）
class CompressDecorator extends DataSourceDecorator {
    CompressDecorator(DataSource inner) { super(inner); }
    public void write(String data) { inner.write("ZIP(" + data + ")"); }
    public String read() { return inner.read().replace("ZIP(", "").replace(")", ""); }
}

// 具体装饰器二：加密（示意，用反转代替真实加密）
class EncryptDecorator extends DataSourceDecorator {
    EncryptDecorator(DataSource inner) { super(inner); }
    public void write(String data) { inner.write(new StringBuilder(data).reverse().toString()); }
    public String read() { return new StringBuilder(inner.read()).reverse().toString(); }
}

public class DecoratorDemo {
    public static void main(String[] args) {
        // 组装：先压缩再加密地写，读时按相反顺序自动解开——顺序写反就读不出原文
        DataSource ds = new EncryptDecorator(new CompressDecorator(new MemoryDataSource()));
        ds.write("hello-knowledge-base");
        System.out.println(ds.read()); // hello-knowledge-base
    }
}
```

- 装饰器与被装饰对象实现同一接口，客户端完全无感，这是它和「工具类静态方法」最大的区别。
- 顺序即语义：加密后压缩基本压不动（密文无冗余），所以永远先压缩后加密；组装顺序要写注释说明为什么。
- 与代理的区别：代理控制「能不能访问/何时访问」同一个功能，装饰器是「叠加新功能」；结构长得像，意图不同。

## 适用场景与选型

- 用它：同一能力要按需拼装（这个数据源要压缩 + 加密，那个只要加密），功能正交、可自由叠加拆卸；想加功能但动不了原类（第三方、已稳定），又不想为每种组合写子类。
- 不用它：功能组合固定只有一两种，直接写子类更直观，硬套装饰器只会多一层包装；顺序没有语义、层数又多，调试成本超过组合收益。
- 选型：装饰器基类（Demo 里的 DataSourceDecorator）要默认转发全部方法，具体装饰器只重写自己关心的那一两个方法；组装顺序要写注释说明为什么是这个顺序。
- 与代理的区别（一句话）：代理控制「能不能访问、何时访问」同一个功能，装饰器是「叠加新功能」——结构长得像，意图不同。

## 优缺点

- 优点：功能正交组合，避免「继承出 EncryptAndCompressAndCacheSource」的类爆炸；增删功能只改组装顺序，符合开闭原则；装饰器与被装饰对象实现同一接口，客户端完全无感。
- 缺点：层数多了调用栈很长，调试时要逐层剥；顺序即语义，组装错了结果就错，且错误往往在运行时才暴露；装饰后对象的身份变了，`instanceof` 具体类、== 比较都可能不再成立。

## 常见误区

- 组装顺序写反：先加密后压缩。错：密文基本没有冗余，压缩压不动，还可能让后续解密读不出原文。正确做法永远是先压缩后加密，读时按相反顺序自动解开，组装处写注释说明顺序原因。
- 装饰器漏转发：新写一个装饰器，只重写了 write 却忘了 read（或反过来），导致被裹对象的部分功能悄悄丢失。正确做法是基类默认转发全部方法，具体装饰器只重写自己要增强的方法。
- 装饰器里强转被裹对象：`((MemoryDataSource) inner)` 之类，假设 inner 一定是某个具体类。错：一旦组装顺序变了、或中间又裹了一层，强转就抛 ClassCastException。正确做法是装饰器只通过接口与 inner 打交道，永远不假设它的具体类型。

## 小技巧与冷知识

【小技巧】装饰器基类里留一个 `unwrap()` / `getWrapped()` 方法，否则链裹了几层就拆不开了：JDK 的 `FilterInputStream` 只把被裹的流存在 protected 的 `in` 字段里，没有公开的 getter，调试时想确认最里层到底是谁、想绕过某一层直接测内层，都无从下手。自己写装饰器基类时顺手加一个返回 inner 的方法，排障和单测时按层剥开，比对着几十层调用栈猜要快得多。

【小技巧】缓存装饰器要把“没查到”和“查到了 null”分开：缓存里没存键，下次再来还要穿透到底层查一遍；存了 null 但读时当成“没命中”又去查一遍，缓存等于没起作用。约定一个哨兵值代表“查过、确实是 null”，读到哨兵直接返回 null 不穿透；失效时删哨兵和删正常值走同一条路，别只清一半。

【小技巧】同步装饰器必须是最外层、且调用方只拿包装后的引用：`Collections.synchronizedList(list)` 返回的包装器才带锁，直接拿内层 list 读写就绕过了同步。组装处把内层引用收起来，只把包装后的引用交出去；链里一旦有人私藏了内层引用，多线程下的数据竞争就从装饰器眼皮底下漏过去了。

【小技巧】关流只关最外层，别在链中间关 inner：`FilterInputStream.close()` 会一路关到底层流，try-with-resources 里只关最外层就够了。中间某层先把 inner 关了，外层再读会直接抛“stream closed”，而且外层装饰器自己的收尾逻辑（比如刷缓冲）也没机会跑；关流的责任永远在最外层这一端。

【小技巧】装饰器不要继承被裹对象的 `equals` 语义：包装后的对象和原对象一般不该相等——`new EncryptDecorator(ds).equals(ds)` 语义上是两个东西，一个带加密、一个不带。装饰器若不重写 equals，默认按引用比较，包装器和原对象自然不等，这是对的；反过来把 equals 委托给 inner（`return inner.equals(other)`），会让“包装器 == 原对象”这种错觉进代码，比较和去重都会悄悄出错。

【小技巧】链里只要有一个装饰器没实现 `Serializable`，整条链都序列化不了：Java 序列化要求对象图里的每个节点都可序列化，内层对象可序列化、装饰器不可序列化，写出时照样抛 `NotSerializableException`。需要落盘或跨进程传的装饰链，装饰器和内层要一起实现 Serializable，缺一层就等于全缺。

【小技巧】日志、计时这类观测装饰器放最外层，才能看到完整调用：放在最外层时，进出链的每一次调用都会被它记下来；放在内层，它只能看到穿过它那一层以下的调用，外层装饰器自己的耗时和行为它一无所知。排障时想看“一次请求在链里到底走了多久、经过了谁”，观测层永远贴着调用方那一端。

【小技巧】状态型装饰器（如计数、限流）要自己管线程安全，别指望内层兜底：内层对象线程安全，只保证它自己的方法原子，不保证装饰器“先读数、再判断、再转发”这三步合起来原子。计数装饰器多个线程共用时，计数器本身要用 `AtomicLong` 或加锁；把线程安全完全推给内层，装饰器自己的状态先乱掉。

【小技巧】缓冲装饰器只加一层就够了，多裹一层等于白加：`new BufferedInputStream(new BufferedInputStream(in))` 里层和外层各建一个缓冲区，外层读时先填满自己的缓冲，内层再填满它的缓冲，内存多占一份、速度没有任何收益。链里出现两个同类缓冲装饰器，先查组装处是不是重复裹了，拆掉一层。

【小技巧】组装链的地方要集中，别把 `new XDecorator(new YDecorator(...))` 散在各处：顺序是装饰器的语义，十个调用点各写一遍组装，改一次顺序要改十处，漏一处就是一条行为不一致的链。把组装收进一个工厂方法或静态方法里，调用方只拿成品链，顺序只在一处定。

【冷知识】GoF 原书讲装饰器用的例子不是 IO 流，而是文本视图：`TextView` 是被装饰的组件，`ScrollDecorator` 给它加滚动条、`BorderDecorator` 给它加边框，同一个文本框可以只加滚动、只加边框，也可以两个都加。JDK 的 IO 流只是这个例子在 Java 里最著名的落地，模式的样板间本来是图形界面。

【冷知识】`java.io` 里 `FilterInputStream` / `FilterOutputStream` 就是装饰器基类：它们实现组件接口、持有被裹的流、默认把所有方法转发给内层，`BufferedInputStream`、`DataInputStream`、`GZIPInputStream` 都是它的具体装饰器。`Collections.unmodifiableList`、`Collections.checkedList` 也是装饰器——前者给集合加“不可改”，后者给集合加“运行时类型检查”，不改原集合、只在外面裹一层。

【冷知识】“Decorator”这个词来自室内装饰：decorate 本意是给房间加装饰——挂画、铺地毯，墙体结构一动不动，装饰随时可以换、可以叠。模式名直译就是“装饰者”，和原文“不改原类、运行时裹上新功能”是同一个意思——功能像装饰品一样往上挂，而不是把墙拆了重砌。

## 面试与自测

1. 装饰器模式和代理模式结构很像，区别是什么？各举一个例子。
2. Demo 里组装是 `new EncryptDecorator(new CompressDecorator(...))`，为什么读的时候能自动按相反顺序解开？
3. 装饰器基类 DataSourceDecorator 默认转发全部方法有什么用？不写基类会有什么问题？

### 参考答案

1. 代理控制「能不能访问、何时访问」同一个功能，如远程代理、懒加载、权限校验代理，功能本身不变；装饰器是「叠加新功能」，如给数据源加压缩、加密，功能在变多。结构像但意图不同：一个是控访问，一个是加功能。
2. 因为写的时候数据流是自外向内：EncryptDecorator.write 先反转，再调 CompressDecorator.write 加 ZIP 标记，最后落进内存；读的时候调用栈按相反顺序回弹——先读出带标记的数据，去标记，再反转回来，正好是写操作的逆操作，顺序天然相反。
3. 基类默认转发让具体装饰器只重写自己关心的那一两个方法，不用把接口的每个方法都抄一遍；不写基类时，每个具体装饰器都要手写全部转发方法，接口一加方法就得改所有装饰器，还容易漏转发导致功能悄悄丢失。
