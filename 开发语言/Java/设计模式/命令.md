# 命令模式

## 模式介绍

**意图**：把「一次请求」封装成对象，于是请求可以被排队、记录、延迟执行、撤销与重放，发送方与执行方彻底解耦。

**结构与角色**：
- Command（命令接口）：声明 `execute()`，支持撤销再加 `undo()`。
- ConcreteCommand（具体命令）：持有接收者，把 execute 委托给接收者的具体动作。
- Receiver（接收者）：真正干活的对象（账户、文档、设备）。
- Invoker（调用者）：持有命令队列/按钮，只认 Command 接口，负责触发与记录历史。

**效果**：
- 优点：请求可入队削峰、可持久化做审计与失败重放；撤销/重做有统一实现套路；新增命令不改调用者。
- 代价：命令类数量膨胀；撤销要保存执行前状态（常与备忘录配合）；异步执行后事务边界与失败补偿变复杂。

**适用信号**：操作要排队或延迟执行；需要 undo/redo；操作日志要落库审计、失败后按日志重放；同一动作有多个触发入口（按钮、定时任务、接口）。

**落点**：
- 任务队列与定时任务：Quartz 的 Job、线程池提交的 Runnable 本质都是命令对象。
- 消息队列：一条 MQ 消息就是命令的分布式版（生产者=Invoker，消费者=Receiver）。
- 编辑器 undo/redo、数据库操作日志回放、智能家居遥控器。

## 模式 Demo

```java
import java.util.*;

// 接收者：账户，真正执行存取
class Account {
    private int balance;
    void deposit(int amt) { balance += amt; System.out.println("存入 " + amt + "，余额 " + balance); }
    void withdraw(int amt) { balance -= amt; System.out.println("取出 " + amt + "，余额 " + balance); }
}

// 命令接口：支持执行与撤销
interface Command {
    void execute();
    void undo();
    String name();
}

class DepositCommand implements Command {
    private final Account acc; private final int amt;
    DepositCommand(Account acc, int amt) { this.acc = acc; this.amt = amt; }
    public void execute() { acc.deposit(amt); }
    public void undo() { acc.withdraw(amt); }
    public String name() { return "存入" + amt; }
}

class WithdrawCommand implements Command {
    private final Account acc; private final int amt;
    WithdrawCommand(Account acc, int amt) { this.acc = acc; this.amt = amt; }
    public void execute() { acc.withdraw(amt); }
    public void undo() { acc.deposit(amt); }
    public String name() { return "取出" + amt; }
}

// 调用者：命令队列 + 历史栈(支持撤销)
class Invoker {
    private final Deque<Command> queue = new ArrayDeque<>();
    private final Deque<Command> history = new ArrayDeque<>();
    void submit(Command cmd) { queue.add(cmd); }
    void runAll() {
        while (!queue.isEmpty()) {
            Command cmd = queue.poll();
            cmd.execute();
            history.push(cmd); // 执行完入历史栈，才能撤销
        }
    }
    void undoLast() {
        if (history.isEmpty()) { System.out.println("没有可撤销的命令"); return; }
        Command cmd = history.pop();
        cmd.undo();
        System.out.println("已撤销: " + cmd.name());
    }
}

public class CommandDemo {
    public static void main(String[] args) {
        Account acc = new Account();
        Invoker invoker = new Invoker();
        invoker.submit(new DepositCommand(acc, 500));
        invoker.submit(new WithdrawCommand(acc, 200));
        invoker.runAll();      // 队列依次执行
        invoker.undoLast();    // 撤销最近的"取出 200"
        invoker.undoLast();    // 再撤销"存入 500"
    }
}
```

- **撤销的前提是命令无副作用残留**：undo 要能精确逆运算（存↔取、加↔减、插入↔删除）；像「发送消息」这类不可逆操作，undo 只能做补偿动作（再发一条冲正消息），语义要在命令里写清。
- **队列与历史是两个结构**：队列管「待执行」，历史栈管「已执行可撤销」；只入队不记历史，就没有撤销能力。
- **坑：命令对象不要夹带可变共享状态**。命令可能延迟执行，创建时捕获的参数若被外部改掉，执行结果会莫名其妙；参数在构造时定死，或在 execute 时重新读取并校验。

## 适用场景与选型

- 用：操作要排队、延迟执行或削峰；操作日志要落库审计、失败后按日志重放；需要统一的 undo/redo；同一动作有多个触发入口（按钮、定时任务、接口）。
- 不用：调用关系就是简单的 A 直接调 B，没有排队、记录、撤销需求时硬套命令只会多一层类；操作不可逆且没有补偿语义时，不要假装它可撤销。
- 与责任链的区别（只记一句）：命令是把"一次请求"封装成对象以便存储、转发、重放；责任链是把请求沿链传递、让链上的某个处理者接手，关注点在"谁处理"而不在"请求本身可不可以被保存"。

## 优缺点

- 优点：发送方与执行方彻底解耦；请求可入队、可持久化、可审计、可重放；撤销/重做有统一套路；新增命令不改调用者。
- 代价：命令类数量随操作种类膨胀；撤销要保存执行前状态，成本常被低估；异步执行后事务边界与失败补偿变复杂；调用链多一层，出问题时定位要多跳一步。

## 常见误区

- 误区 1：命令对象夹带可变共享状态。错：创建命令时引用一个之后会被外部修改的集合，延迟执行时读到的是改过的值。正确：参数在构造时定死（拷贝一份），或在 execute 里重新读取并校验。
- 误区 2：只入队不记历史却想要撤销。错：Invoker 只有 queue 没有 history，执行完命令就丢了，undo 无从谈起。正确：队列管待执行，历史栈管已执行可撤销，两者缺一不可（Demo 正是这么分的）。
- 误区 3：给不可逆操作配假 undo。错：发送短信的命令 undo 里什么都不做或只打印日志。正确：不可逆操作要么不支持 undo（接口上就不提供），要么 undo 写成明确的补偿动作（再发一条冲正消息），并在命令里写清语义。

## 面试与自测

1. 命令模式里队列和历史栈各管什么？为什么需要两个结构？
2. undo 为什么常常要配合备忘录模式？
3. 一条 MQ 消息和命令模式里的命令对象有什么对应关系？

### 参考答案

1. 队列管待执行，历史栈管已执行、可撤销。只入队不记历史，执行完命令就丢了，撤销时找不到执行前状态；两个结构分工不同，缺一不可。
2. 有些 undo 不能靠逆运算还原（例如批量更新后的复杂状态），需要执行前先拍一张快照；备忘录正是"不暴露内部实现的快照"，两者配合才能回滚任意状态。
3. 生产者相当于 Invoker（发出请求但不执行），消息本身就是命令对象（封装了请求与参数），消费者相当于 Receiver（真正干活）；MQ 是命令模式的分布式版本。
