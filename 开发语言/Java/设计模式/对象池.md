# 对象池模式

> 对象池（Object Pool）不是 GoF 模式，是并发与资源管理的工程模式：昂贵对象不反复新建，用完归还、循环复用。Druid 连接池、线程池都是它。

## 模式介绍

**意图**：把创建成本高、数量要受控的对象（数据库连接、线程、网络连接）集中放在池里管理：借出、归还、复用，并限制总量，避免无节制新建压垮下游资源。

**结构与角色**：

- `Pool`（池）：持有空闲对象队列 + 已借出计数，提供 `borrow()` / `release()`，并负责总量上限与等待策略。
- 池中对象：有明确的「可用/不可用」状态，归还前要重置（连接要清会话状态、回滚未提交事务）。
- 策略参数：最小/最大池大小、借用超时、空闲回收、借出前校验（testOnBorrow）。

**效果**：

- 优点：摊薄创建成本（TCP 握手、连接认证、线程栈分配）；总量可控，给下游（数据库）设了硬上限；复用让吞吐更稳。
- 代价：实现复杂（并发安全、泄漏、死对象）；池太小成瓶颈、太大压垮下游；对象状态没重置干净会串数据，比新建更危险。

**适用信号**：

- 对象创建昂贵且可复用、无状态或状态可重置。
- 并发量需要对下游资源总量封顶。

**与享元的区别**：享元是**共享同一个对象**给所有人同时用（只读状态）；对象池是**同一时刻一个对象只借给一个使用者**，用完归还再借给下一个人（独占使用）。连接显然只能独占，所以是池不是享元。

**落点**：

- Druid/HikariCP 数据库连接池：`maxActive`、等待超时、连接有效性检测、泄漏监控（removeAbandoned）就是池参数的工业级版本。
- 线程池 `ThreadPoolExecutor`：线程即池中对象，任务队列相当于借用排队。
- Redis 连接池（Jedis Pool/Lettuce 虽默认单连接多路复用，思路相通）。

## 模式 Demo

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.TimeUnit;

// 池中对象：模拟昂贵的「连接」（真实场景是 java.sql.Connection）
class Conn {
    private final int id;
    private boolean dirty;                 // 借出期间被改动的状态标记

    Conn(int id) { this.id = id; }
    void exec(String sql) {
        dirty = true;
        System.out.println("连接" + id + " 执行：" + sql);
    }
    void reset() { dirty = false; }        // 归还前重置，清掉上一个人的状态
    boolean isDirty() { return dirty; }
}

// 极简对象池：固定大小 + 借用超时 + 归还重置
class SimplePool {
    private final BlockingQueue<Conn> idle;

    SimplePool(int size) {
        idle = new ArrayBlockingQueue<>(size);
        for (int i = 1; i <= size; i++) idle.offer(new Conn(i));   // 预创建
    }

    Conn borrow() throws InterruptedException {
        Conn c = idle.poll(2, TimeUnit.SECONDS);       // 等不到就超时，不无限排队
        if (c == null) throw new IllegalStateException("池已耗尽，借用超时");
        return c;
    }

    void release(Conn c) {
        if (c.isDirty()) c.reset();                    // 关键：重置后再放回
        idle.offer(c);
    }
}

public class PoolDemo {
    public static void main(String[] args) throws Exception {
        SimplePool pool = new SimplePool(2);
        Conn a = pool.borrow();
        Conn b = pool.borrow();
        a.exec("select 1");
        pool.release(a);                               // 归还后可再借
        Conn c = pool.borrow();                        // 拿到复用的连接
        c.exec("select 2");
        pool.release(b);
        pool.release(c);
        System.out.println("全部归还，池运转正常");
        // 注意：借了不还（异常路径漏 release）池会被掏空——生产代码必须 try-finally
    }
}
```

- 归还必须放在 `finally` 里（或用 try-with-resources 包装借出对象）：异常路径漏还一次，池就永久少一个对象，漏几次系统假死——这是连接池事故最常见的根因。
- 池大小不是越大越好：连接池上限应按数据库能承受的连接数反推，应用侧多开连接只会加剧下游排队；Druid 的监控页就是用来观察活跃/等待曲线再调参的。
- 本 Demo 省略了生产池的关键件：借出前校验连接存活、泄漏检测、空闲回收、等待公平性——真项目直接用 Druid/HikariCP，不要手写池上生产。

## 适用场景与选型

- 用它：对象创建昂贵（TCP 握手、连接认证、线程栈分配）且可复用、无状态或状态可重置；并发量需要对下游资源总量封顶；复用能让吞吐更稳。
- 不用它：对象创建便宜（如普通 POJO），池的管理成本（并发、泄漏检测、校验）超过复用收益；对象状态不可重置或线程不安全且无法隔离；数量波动极大且突发，池太小排队、太大压垮下游时，限流或弹性伸缩比固定池更合适。
- 与享元的一句话区分：享元是多人同时共享同一个只读对象；对象池是同一时刻一个对象只独占借给一个使用者，用完归还再借给下一个人——连接显然只能独占，所以是池不是享元。

## 优缺点

- 优点：摊薄创建成本；总量可控，给下游（数据库）设了硬上限；复用让吞吐更稳；借用超时和等待策略让过载行为可控（排队或快速失败，而不是无限新建）。
- 缺点：实现复杂（并发安全、泄漏检测、死对象校验、空闲回收）；归还遗漏会掏空池；状态重置不干净会串数据，比新建更危险；池参数调错本身成瓶颈；池的全局状态会让测试互相干扰。

## 常见误区

- 借了不还：异常路径漏了 finally，池永久少一个对象，漏几次系统假死——这是连接池事故最常见的根因。正确：归还必须放在 finally 里，或用 try-with-resources 包装借出对象（Demo 末尾的注释正是此意）。
- 归还前不重置：上一个人留下的会话状态、未提交事务被下一个人继承，数据串了还查不出来。正确：release 里统一重置，Demo 的 `isDirty()` 检查 + `reset()` 就是最小实现，生产连接池还要回滚未提交事务、清会话变量。
- 池开太大以为越快越好：连接数超过数据库能承受的上限，只会让下游排队更严重，全链路一起变慢。正确：按下游容量反推上限，用 Druid 监控页观察活跃/等待曲线再调参，而不是凭感觉加大。

## 面试与自测

1. 对象池和享元的根本区别是什么？为什么数据库连接只能用池不能用享元？
2. 连接池“借了不还”在线上是什么症状？怎么防？
3. 为什么生产不要手写连接池？生产池比 Demo 多了哪些关键件？

### 参考答案

1. 根本区别是使用方式：享元是多人同时共享同一个只读对象；对象池是同一时刻独占借用、用完归还。数据库连接有会话状态（事务、临时表、会话变量），两个人同时用一个连接会互相串状态，所以只能独占借用——是池不是享元。
2. 症状是池被慢慢掏空：可用连接越来越少，请求开始排队超时，最终系统假死，但数据库侧并不忙（连接根本没还回来）。防法：归还放 finally 或 try-with-resources；生产池开泄漏检测（如 Druid 的 removeAbandoned），超时未还的连接强制回收并打日志定位借出点。
3. 因为生产池的关键件 Demo 全省略了：借出前校验连接存活、泄漏检测、空闲回收、等待公平性、超时与重试策略、监控指标。手写容易在某一件上栽跟头，直接用 Druid/HikariCP 是更便宜的选择。
