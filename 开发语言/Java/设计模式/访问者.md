# 访问者模式

## 模式介绍

**意图**：把「作用在一组对象上的操作」从对象本身抽出来，封装成访问者类。对象结构保持稳定，新增一种操作只需新增一个访问者，不改任何被访问的类。

**结构与角色**：

- `Element`（元素接口）：声明 `accept(Visitor v)`，实现固定为一行 `v.visit(this)`——靠重载在编译期分发到对应方法，这就是「双分派」。
- `ConcreteElement`（具体元素）：不同类型各一个，如书籍、食品、电子产品。
- `Visitor`（访问者接口）：为每种元素声明一个 `visit(Xxx)` 方法。
- `ConcreteVisitor`（具体访问者）：一种完整操作，如计税、打印报表、稽核。
- `ObjectStructure`（对象结构）：一组元素的容器（常与组合模式的树搭配），负责遍历并逐个 accept。

**效果**：

- 优点：操作集中成类，新增操作成本低；同一批数据可以跑任意多种操作互不干扰。
- 代价：**新增元素类型成本极高**——访问者接口要加方法，所有已有访问者全得改。所以它只适合「元素类型稳定、操作经常变」的场景；另外元素要向访问者暴露内部数据，封装性被打破。

**适用信号**：

- 一组类型固定的对象（单据、节点、事实），要反复对它们做不同的事：打印、导出、校验、统计。
- 操作代码散落在各元素类里、越堆越杂，想按操作重新组织。

**落点**：

- 报表系统对同一批单据做「打印 / 导出 Excel / 稽核」三种操作。
- 编译器与静态分析对 AST 节点做类型检查、代码生成、格式化——AST 节点类型稳定、处理方式多样，是访问者的教科书场景。
- 规则引擎/矛盾检测对多种事实（人物、事件、关系）做不同维度的校验：元素是事实类型，访问者是每条校验规则。

## 模式 Demo

```java
import java.util.List;

// 元素：类型稳定的商品，各自 accept 一个访问者
interface Item {
    void accept(Visitor v);
}

class Book implements Item {
    final String title; final long priceCents;
    Book(String title, long priceCents) { this.title = title; this.priceCents = priceCents; }
    public void accept(Visitor v) { v.visit(this); }     // 双分派：按自身类型回调
}

class Food implements Item {
    final String name; final long priceCents;
    Food(String name, long priceCents) { this.name = name; this.priceCents = priceCents; }
    public void accept(Visitor v) { v.visit(this); }
}

// 访问者：每种元素一个 visit 方法
interface Visitor {
    void visit(Book b);
    void visit(Food f);
}

// 操作一：算税（书免税，食品 9%）
class TaxVisitor implements Visitor {
    long totalTax = 0;
    public void visit(Book b) { /* 书籍免税 */ }
    public void visit(Food f) { totalTax += f.priceCents * 9 / 100; }
}

// 操作二：打印小票明细
class PrintVisitor implements Visitor {
    public void visit(Book b) { System.out.println("书：《" + b.title + "》" + b.priceCents + " 分"); }
    public void visit(Food f) { System.out.println("食品：" + f.name + " " + f.priceCents + " 分"); }
}

public class VisitorDemo {
    public static void main(String[] args) {
        List<Item> cart = List.of(new Book("设计模式", 9900), new Food("牛奶", 1500));
        TaxVisitor tax = new TaxVisitor();
        PrintVisitor print = new PrintVisitor();
        for (Item it : cart) { it.accept(tax); it.accept(print); }  // 同一批数据跑两种操作
        System.out.println("总税额：" + tax.totalTax + " 分");      // 135
        // 新增「导出」操作 = 新增一个 ExportVisitor，Book/Food 一行不改
    }
}
```

- `accept` 里只有一行 `v.visit(this)`，靠方法重载在编译期选中正确 visit——这是访问者与普通遍历的根本区别（双分派）。
- 判断口诀：元素类型会变、操作稳定 → 别用访问者（直接把操作写回元素类）；元素稳定、操作多变 → 才是它的主场。
- 坑：访问者需要读取元素内部字段，元素类要么公开字段要么提供 getter，别为了模式把封装彻底放弃；Java 里也可用 `instanceof` 模式匹配替代，但那就丢了「新增操作不改元素」的编译期保障。

## 适用场景与选型

- 用它：元素类型稳定、操作经常变且种类多；操作代码散落在各元素类里、想按操作重新组织；同一批数据要跑多种操作且互不干扰。
- 不用它：元素类型还在变（每加一种元素，访问者接口加方法、所有已有访问者全得改）；只有一两种操作，直接在元素类里写方法更简单；元素内部数据不愿暴露（访问者要读内部字段，封装性会被打破）。
- 与策略的一句话区分：策略是给单个对象换一种算法；访问者是给一组异构元素批量施加同一种操作——前者换“怎么做”，后者把“对谁做”组织成类。

## 优缺点

- 优点：新增操作不改任何元素类；操作集中成类，同一批数据可跑任意多种操作；操作之间的代码互不干扰。
- 缺点：新增元素类型成本极高（接口加方法、所有访问者全改）；元素要向访问者暴露内部数据，封装性被打破；访问者接口随元素类型膨胀；双分派依赖方法重载，元素类型体系复杂时接口难维护。

## 常见误区

- accept 里写业务逻辑：accept 一旦超过一行 `v.visit(this)`，就丢了双分派，退化成普通遍历 + instanceof 判断。正确：accept 永远只有一行，把“做什么”全部交给访问者。
- 元素还在变就上访问者：商品类型三天两头加，访问者接口和全部访问者跟着全量改，模式收益变负。正确：先确认元素集合稳定（Demo 的 Book/Food 一旦定型才适用），元素多变时把操作写回元素类。
- 访问者带可变状态又复用：Demo 的 TaxVisitor 持有 `totalTax`，同一个实例跑第二批数据时会把上一批的税额带进来。正确：每批数据用新访问者，或跑完显式清零，别把访问者当无状态工具复用。

## 面试与自测

1. 为什么 accept 里必须只有一行 `v.visit(this)`？写多了会变成什么？
2. 新增一种元素类型和新增一种操作，哪个成本高？为什么？
3. 访问者破坏封装体现在哪里？怎么缓解？

### 参考答案

1. 这一行是双分派的关键：`this` 的静态类型是具体元素类，编译期靠方法重载选中对应的 `visit(Book)` 或 `visit(Food)`。accept 里一旦写业务逻辑或 instanceof 分支，分派就退化成手写判断，新增操作又要改元素类，模式的收益（新增操作不改元素）就没了。
2. 新增元素类型成本高得多：访问者接口要加一个 `visit(NewElement)`，所有已有访问者（计税、打印、导出……）全得补实现，漏一个就编译不过。新增操作则只需加一个访问者类，元素类一行不改——这正是访问者存在的理由，也是它只适合“元素稳定、操作多变”的原因。
3. 体现在访问者要读取元素内部字段：Demo 的 TaxVisitor 直接读 `f.priceCents`，元素不能再把字段藏起来。缓解：只暴露读所需的最小 getter，不暴露可写状态；或者把访问者限定在同包内，避免内部数据扩散到全系统。
