# 抽象工厂模式

## 模式介绍

**意图**：提供一个接口，用于创建一系列相互关联或相互依赖的对象（一个产品族），而无需指定它们的具体类。解决的问题是「一整套东西要整体切换」：换数据库不只是换连接，还要连命令、事务、方言一起换，混搭就会出错。

**结构与角色**：
- 抽象工厂（AbstractFactory）：声明一整族产品的创建方法，如 `createConnection()`、`createDialect()`。
- 具体工厂（ConcreteFactory）：实现某一族，如 MySQL 工厂、Oracle 工厂。
- 抽象产品（AbstractProduct）：族里每个成员的接口，如 `Connection`、`Dialect`。
- 具体产品（ConcreteProduct）：某族里的具体成员，族内成员彼此配套。

**效果**：
- 优点：切换一族 = 换一个工厂对象，全套组件自动配套，不会出现 MySQL 连接配 Oracle 方言的混搭事故。
- 代价：族里加一个新成员（比如多一个 `createCache()`），所有具体工厂都要改——对「新产品种类」扩展很差；工厂类与产品类数量乘积式增长。

**适用信号**：
- 一组对象总是成套出现，且有多套可选（多数据库、多平台、多主题皮肤）。
- 系统要独立于产品的创建细节，且产品族内部有约束（必须配套使用）。

**与工厂方法的区别**：工厂方法管「一个产品，由子类决定建哪个」；抽象工厂管「一族产品，由一个工厂一次性配齐」。抽象工厂内部每个 create 方法本质上就是一个工厂方法，它是工厂方法的组装层。

**落点**：
- JDK：`java.sql.DriverManager` 背后按驱动建连接族；JAXP 的 `DocumentBuilderFactory` 系列。
- 跨数据库场景：ao 在解抵押平台做过 MySQL → Oracle 的 SQL 迁移，这类「整套换供应商」正是抽象工厂的典型题面——连接、分页方言、函数转换打包成族一起换。
- GUI 跨平台组件族（Windows 风格按钮+菜单 vs Mac 风格）是教科书例子，实际业务里数据库族、支付渠道族（下单+退款+对账成套）更常见。

## 模式 Demo

```java
// 一族产品：连接 + 方言，必须配套
interface DbConnection { void open(); }
interface DbDialect { String pageSql(String sql, int offset, int size); }

class MysqlConnection implements DbConnection {
    public void open() { System.out.println("打开 MySQL 连接"); }
}
class MysqlDialect implements DbDialect {
    public String pageSql(String sql, int o, int s) { return sql + " LIMIT " + o + "," + s; }
}
class OracleConnection implements DbConnection {
    public void open() { System.out.println("打开 Oracle 连接"); }
}
class OracleDialect implements DbDialect {
    public String pageSql(String sql, int o, int s) {
        return "SELECT * FROM (SELECT t.*, ROWNUM rn FROM (" + sql + ") t) WHERE rn > " + o + " AND rn <= " + (o + s);
    }
}

// 抽象工厂：一族一起建
interface DbFactory {
    DbConnection createConnection();
    DbDialect createDialect();
}
class MysqlFactory implements DbFactory {
    public DbConnection createConnection() { return new MysqlConnection(); }
    public DbDialect createDialect() { return new MysqlDialect(); }
}
class OracleFactory implements DbFactory {
    public DbConnection createConnection() { return new OracleConnection(); }
    public DbDialect createDialect() { return new OracleDialect(); }
}

// 客户端：只依赖抽象，换库只换注入的工厂
class ReportService {
    private final DbFactory factory;
    ReportService(DbFactory factory) { this.factory = factory; }
    void run() {
        DbConnection conn = factory.createConnection();   // 连接与方言必定同族
        DbDialect dialect = factory.createDialect();
        conn.open();
        System.out.println(dialect.pageSql("SELECT * FROM loan", 0, 20));
    }
}

class Demo {
    public static void main(String[] args) {
        new ReportService(new MysqlFactory()).run();   // MySQL 一套
        new ReportService(new OracleFactory()).run();  // 整体切 Oracle，客户端代码不动
    }
}
```

Demo 要点与变体/坑：
- **整体切换是核心卖点**：客户端从头到尾不出现任何具体类名，换族只发生在组装处（main 或配置类）。验收标准：全局搜不到 `new Mysql...` 散落在业务代码里。
- **扩展性短板**：给族里加新成员（多一个 `createSequenceGenerator()`），两个具体工厂都要补实现，接口一变全族动——产品族要事先想清楚成员边界，别把会频繁增删的东西塞进同一族。
- **Spring 里的现实版**：多数项目不会手写抽象工厂类，而是用配置 + 条件装配（不同 profile 注入不同的一组 Bean）达成同样的「成套切换」效果；抽象工厂更多是理解这种组装思想的模型。
- 坑：族内成员若没有真实的配套约束（随便混搭也没问题），那就不需要抽象工厂，拆成普通工厂方法各自创建更简单。
