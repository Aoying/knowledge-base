# 抽象工厂模式

## 模式介绍

**意图**：提供一个接口，用于创建一系列相互关联或相互依赖的对象（一个产品族），而无需指定它们的具体类。解决的问题是「一整套东西要整体切换」：换数据库不只是换连接，还要连命令、事务、方言一起换，混搭就会出错。

**结构与角色**：
- 抽象工厂（AbstractFactory）：声明一整族产品的创建方法，如 `createConnection()`、`createDialect()`。
- 具体工厂（ConcreteFactory）：实现某一族，如 MySQL 工厂、Oracle 工厂。
- 抽象产品（AbstractProduct）：族里每个成员的接口，如 `Connection`、`Dialect`。
- 具体产品（ConcreteProduct）：某族里的具体成员，族内成员彼此配套。

**效果**：
- 优点：切换一族 = 换一个工厂对象，全套组件自动配套，不会出现 MySQL 连接配 Oracle 方言的混搭事故。
- 代价：族里加一个新成员（比如多一个 `createCache()`），所有具体工厂都要改——对「新产品种类」扩展很差；工厂类与产品类数量乘积式增长。

**适用信号**：
- 一组对象总是成套出现，且有多套可选（多数据库、多平台、多主题皮肤）。
- 系统要独立于产品的创建细节，且产品族内部有约束（必须配套使用）。

**与工厂方法的区别**：工厂方法管「一个产品，由子类决定建哪个」；抽象工厂管「一族产品，由一个工厂一次性配齐」。抽象工厂内部每个 create 方法本质上就是一个工厂方法，它是工厂方法的组装层。

**落点**：
- JDK：`java.sql.DriverManager` 背后按驱动建连接族；JAXP 的 `DocumentBuilderFactory` 系列。
- 跨数据库场景：ao 在解抵押平台做过 MySQL → Oracle 的 SQL 迁移，这类「整套换供应商」正是抽象工厂的典型题面——连接、分页方言、函数转换打包成族一起换。
- GUI 跨平台组件族（Windows 风格按钮+菜单 vs Mac 风格）是教科书例子，实际业务里数据库族、支付渠道族（下单+退款+对账成套）更常见。

## 模式 Demo

```java
// 一族产品：连接 + 方言，必须配套
interface DbConnection { void open(); }
interface DbDialect { String pageSql(String sql, int offset, int size); }

class MysqlConnection implements DbConnection {
    public void open() { System.out.println("打开 MySQL 连接"); }
}
class MysqlDialect implements DbDialect {
    public String pageSql(String sql, int o, int s) { return sql + " LIMIT " + o + "," + s; }
}
class OracleConnection implements DbConnection {
    public void open() { System.out.println("打开 Oracle 连接"); }
}
class OracleDialect implements DbDialect {
    public String pageSql(String sql, int o, int s) {
        return "SELECT * FROM (SELECT t.*, ROWNUM rn FROM (" + sql + ") t) WHERE rn > " + o + " AND rn <= " + (o + s);
    }
}

// 抽象工厂：一族一起建
interface DbFactory {
    DbConnection createConnection();
    DbDialect createDialect();
}
class MysqlFactory implements DbFactory {
    public DbConnection createConnection() { return new MysqlConnection(); }
    public DbDialect createDialect() { return new MysqlDialect(); }
}
class OracleFactory implements DbFactory {
    public DbConnection createConnection() { return new OracleConnection(); }
    public DbDialect createDialect() { return new OracleDialect(); }
}

// 客户端：只依赖抽象，换库只换注入的工厂
class ReportService {
    private final DbFactory factory;
    ReportService(DbFactory factory) { this.factory = factory; }
    void run() {
        DbConnection conn = factory.createConnection();   // 连接与方言必定同族
        DbDialect dialect = factory.createDialect();
        conn.open();
        System.out.println(dialect.pageSql("SELECT * FROM loan", 0, 20));
    }
}

class Demo {
    public static void main(String[] args) {
        new ReportService(new MysqlFactory()).run();   // MySQL 一套
        new ReportService(new OracleFactory()).run();  // 整体切 Oracle，客户端代码不动
    }
}
```

Demo 要点与变体/坑：
- **整体切换是核心卖点**：客户端从头到尾不出现任何具体类名，换族只发生在组装处（main 或配置类）。验收标准：全局搜不到 `new Mysql...` 散落在业务代码里。
- **扩展性短板**：给族里加新成员（多一个 `createSequenceGenerator()`），两个具体工厂都要补实现，接口一变全族动——产品族要事先想清楚成员边界，别把会频繁增删的东西塞进同一族。
- **Spring 里的现实版**：多数项目不会手写抽象工厂类，而是用配置 + 条件装配（不同 profile 注入不同的一组 Bean）达成同样的「成套切换」效果；抽象工厂更多是理解这种组装思想的模型。
- 坑：族内成员若没有真实的配套约束（随便混搭也没问题），那就不需要抽象工厂，拆成普通工厂方法各自创建更简单。

## 适用场景与选型

- 用：一组对象总是成套出现且有多套可选（多数据库、多支付渠道），族内成员有配套约束，混搭会出错。
- 不用：族内成员之间没有真实配套约束，随便混搭也没问题时，拆成各自独立的工厂方法更简单。
- 与工厂方法区分：工厂方法一次决定一个产品；抽象工厂一次配齐一族产品，抽象工厂里的每个 create 方法本质上就是一个工厂方法。
- 族边界事先想清楚：会频繁增删的成员不要塞进同一族，否则接口一变全族都要改。

## 优缺点

- 优点：换一族只换一个工厂对象，全套组件自动配套，杜绝混搭事故；客户端代码完全不出现具体类名。
- 缺点：给族里加新成员时所有具体工厂都要补实现，对"新产品种类"扩展很差；工厂类与产品类数量乘积式增长。

## 常见误区

- 业务代码里散落具体类名：客户端某处直接 `new MysqlDialect()`，换族时这处就漏网；验收标准是业务代码里搜不到具体产品类名，换族只发生在组装处。
- 族里塞不稳定的成员：把"下个月可能新增"的组件放进族接口，结果每加一个成员就全族改实现；不稳定的部分拆出去单独建。
- 只有一个产品族时也硬套：族只有一个具体实现时，抽象工厂只剩一层无意义的间接，普通工厂或配置注入就够了。

## 小技巧与冷知识

【小技巧】选哪个工厂别用 if-else 字符串散在业务里，用配置 key 映射到工厂：`Map<String, DbFactory>` 或 Spring 的条件装配按 profile 选工厂，换族只改配置一处。if-else 写在业务代码里，每加一族就多一处分支，抽象工厂"换族只换组装处"的验收标准就破了——选族逻辑本身也得集中。

【小技巧】建完一族后顺手做一次"同族断言"：单元测试里断言 `factory.createConnection()` 和 `factory.createDialect()` 来自同一族（比如方言名含 MySQL、连接驱动也是 MySQL），混搭在测试期就能抓出来。只靠"客户端不写具体类名"防混搭还不够，族内配套关系最好有一条自动化断言兜底。

【小技巧】抽象工厂的接口方法一多就按子族拆，别把无关产品硬塞进一个大工厂：连接族、缓存族、消息族各有自己的小工厂，客户端按需组合。接口方法超过四五个、且有的客户端只用其中一两个时，说明族边界画大了；拆成小工厂后，给某个子族加成员也只影响用到它的客户端。

【小技巧】具体工厂本身是无状态的建器，别每次建一族都 new 一个工厂：工厂对象做成单例、或交给容器管理，create 方法每次返回新产品即可。工厂无状态所以复用安全；反过来，往工厂里塞可变状态（比如缓存上一次建出的连接），换族时状态串族的风险就回来了。

【小技巧】测试业务逻辑时给抽象工厂造一个内存版工厂：返回假连接和假方言的 TestDouble 工厂，业务代码不连真实数据库也能跑通全流程。这是抽象工厂最实用的附带收益——客户端只依赖抽象接口，测试替身的成本几乎为零；写不出内存版工厂，说明客户端某处还是直接依赖了具体产品。

【小技巧】族内产品共享"族上下文"时，把上下文对象传给工厂构造器：数据库类型、字符集、时区这类全族共用的配置，由工厂在构造时一次性读进来，再分发给每个 create 方法。别让每个产品自己去查配置——配置读两次可能读出两份不一致的值，族内配套就从源头上裂了。

【小技巧】给族加新成员前先问一句"这个成员是不是所有族都必须有"：某个族根本没有该成员（比如 Oracle 族没有某种序列生成器），接口加方法会逼它造一个抛异常的假实现。出现"某族不需要这个成员"时，这个成员就不属于族，拆出去单独建，别为了凑齐一族硬塞。

【小技巧】抽象工厂和建造者别混用：工厂解决"选哪一族"，建造者解决"一族里的某个产品怎么组装参数"。族内某个产品的构造特别复杂（要依次装超时、重试、拦截器）时，让工厂方法内部调一个 Builder，create 只负责选族、返回 Builder 产出的产品；工厂方法自己变成组装车间，族切换就被构造细节拖住了。

【小技巧】Spring 里一个 @Configuration 类就是抽象工厂的"配置版"：类本身是具体工厂，里面的每个 @Bean 方法就是一个 create 方法，一组 @Bean 配套定义了一个产品族。换 profile 切换配置类，等价于换一个具体工厂；理解了这层对应关系，原文"配置 + 条件装配"就不只是口号，而是能直接落到代码上的结构。

【冷知识】抽象工厂在 GoF 书里还有一个别名 Kit（工具箱）：GoF 在"别名"一栏写着 Abstract Factory 也叫 Kit，意思是"一整套配套的工具"。名字本身就点出了模式的核心——工厂交付的不是单个工具，而是一整箱互相配套的工具，缺一件或混进别箱的工具都算坏事。

【冷知识】抽象工厂是 GoF 23 种模式里 5 种创建型模式之一：和工厂方法、建造者、原型、单例同属"怎么创建对象"的一组。它是其中唯一一个"一次创建一族"的模式——别的创建型模式一次只解决一个对象的创建，抽象工厂解决的是一组对象的配套创建，粒度天然比其他四种大一号。

【冷知识】GoF 原书讲抽象工厂用的例子是跨平台 GUI 工具箱：同一套界面要在 Motif 和 Presentation Manager 两种风格下跑，窗口、滚动条、按钮各自成族，换风格就是换一整族组件。原文 Demo 里的 MySQL/Oracle 数据库族是同一个结构的业务版——"换供应商"和"换界面风格"在模式层面是同一道题。

## 面试与自测

1. 抽象工厂对"新增一个产品族"和"给现有族加一个新成员"两种扩展，代价分别是什么？
2. 怎么验收一个抽象工厂的客户端真的做到了"整体切换"？
3. Spring 项目里不用手写抽象工厂类时，"成套切换"一般怎么实现？

### 参考答案

1. 新增产品族代价小：加一个具体工厂类，老代码不动；给族加新成员代价大：抽象工厂接口要加方法，所有具体工厂都要补实现。
2. 业务代码里搜不到任何具体产品类名，所有具体类只出现在组装处（配置类或 main）；换一个工厂对象，全套行为跟着变。
3. 用配置 + 条件装配：不同 profile 下注入不同的一组 Bean，成套切换由容器配置完成，抽象工厂是理解这种组装思想的模型。
