# 适配器模式

## 模式介绍

**意图**：把一个类的接口转换成客户端期望的另一种接口，让原本不兼容的类能一起工作。本质是「改不了源码、又对不上接口」时加一层转换。

**结构与角色**：

- 目标接口（Target）：客户端现在认的接口。
- 被适配者（Adaptee）：已有的老类/第三方类，接口对不上但功能可用。
- 适配器（Adapter）：实现目标接口，内部持有被适配者，把调用翻译过去。

两种实现：类适配器（继承被适配者，Java 单继承下受限，少用）；对象适配器（组合持有被适配者，主流）。

**效果**：

- 优点：复用存量代码，客户端零感知；换第三方库时只改适配器一处。
- 代价：多一层间接；适配器堆多了说明系统接口本身该统一，别用它掩盖设计混乱。

**适用信号**：

- 集成第三方 SDK，它的接口风格和系统内规范不一致。
- 老系统迁移，旧接口暂时下不了线，新代码又只想认新接口。
- 同一类能力有多个供应商（支付、短信、地图），需要抹平差异。

**类适配器 vs 对象适配器**：

- 类适配器：适配器继承被适配者、实现目标接口。省一层转发，但 Java 单继承下会占掉唯一的继承位，且被适配者若是 final 类就没法用。
- 对象适配器：适配器组合持有被适配者（Demo 用的就是这种）。灵活、可适配被适配者的子类，是实际项目的主流，优先选它。

**落点**：Spring MVC 的 `HandlerAdapter`（把各种 Controller 适配成统一调用）；SLF4J 对各日志框架的桥接/适配；MyBatis/各 ORM 对不同数据库方言的适配层；项目里对接外部系统（银行、政务接口）时几乎必用。

**与相邻模式区分**：适配器转换的是「单个接口的形态」，目的是让两个现存接口对接上；外观是「简化一组接口的调用」，不改接口形态；桥接是设计期就把两个维度拆开，不存在「接口对不上」的被迫感。

## 模式 Demo

```java
// 目标接口：系统内统一的支付接口（单位：分）
interface PayService {
    void pay(long cents);
}

// 被适配者：第三方老 SDK，接口是 payDollars(double)，改不了源码
class OldPaySdk {
    void payDollars(double dollars) {
        System.out.println("OldSDK 扣款 $" + dollars);
    }
}

// 对象适配器：实现目标接口，内部把「分」翻译成「美元」再调老 SDK
class OldPayAdapter implements PayService {
    private final OldPaySdk sdk = new OldPaySdk();

    @Override
    public void pay(long cents) {
        double dollars = cents / 100.0; // 单位换算就是最常见的适配内容
        sdk.payDollars(dollars);
    }
}

public class AdapterDemo {
    public static void main(String[] args) {
        // 客户端只认 PayService，底层是老 SDK 也完全无感
        PayService pay = new OldPayAdapter();
        pay.pay(12_500); // 输出：OldSDK 扣款 $125.0
    }
}
```

- 适配内容不只是方法名：参数单位、异常类型、回调方式、数据结构都要在适配器里抹平，别漏到客户端。
- 一个被适配者只写一个适配器；多个供应商各写一个，共同实现目标接口，上层就能无差别切换。
- 坑：适配器里做异常吞没（老 SDK 抛 checked 异常转成空返回）会把故障伪装成成功，转换异常时至少保留原始异常作为 cause。
- 适配器也是天然的防腐层：把第三方的模型、枚举、错误码挡在边界外，系统内部永远只见自己的领域对象；第三方换版时，爆炸半径只限适配器一个文件。
- 测试红利：目标接口是自己定的，单测时给客户端注入一个手写假适配器即可，不用真连第三方 SDK。
- 什么时候别用：差异大到适配器要重写大半业务逻辑时，那不是适配，是重新实现——老老实实写新实现类，别硬包。
