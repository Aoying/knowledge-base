# 备忘录模式

## 模式介绍

**意图**：在不暴露对象内部实现的前提下，捕获其某一时刻的内部状态保存为备忘录，之后可把对象恢复到该状态（快照 + 回滚）。

**结构与角色**：
- Originator（发起人）：被保存状态的对象，提供 `save()` 产出备忘录、`restore(memento)` 按备忘录回滚。
- Memento（备忘录）：状态的不可变快照，只存数据不含行为，通常对外只暴露给发起人读取。
- Caretaker（管理者）：持有备忘录（栈/列表/版本号），负责保管与调度，自己不看也不改快照内容。

**效果**：
- 优点：回滚实现对发起人是黑盒，封装不破；撤销/重做、存档读档、版本回退有统一套路。
- 代价：快照频繁或状态大时内存/存储成本高；深拷贝做不干净会出现「回滚后状态被后续修改污染」。

**适用信号**：需要 undo/回档；长流程要能在中间节点留检查点，失败从检查点重试而不是从头再来；要支持「分支试错」——保存当前状态，试一条路，不行就回档换另一条。

**落点**：
- 编辑器撤销栈、游戏存档/读档、IDE 的 Local History。
- 数据库事务 savepoint、Git 的 commit（本质是全量快照 + 指针）。
- 小说创作引擎的 Snapshot 机制：章节状态存快照，沙盒推演走一条剧情分支，不满意回档到快照点换分支继续——备忘录的工程化形态。

## 模式 Demo

```java
import java.util.*;

// 备忘录：不可变快照，只存状态
record Memento(int hp, int level, String position) {}

// 发起人：游戏角色
class GameRole {
    private int hp;
    private int level;
    private String position;

    GameRole(int hp, int level, String position) {
        this.hp = hp; this.level = level; this.position = position;
    }

    void fight() { // 打怪：升级但掉血并推进地图
        level++;
        hp -= 30;
        position = "第" + level + "层";
        System.out.println("打怪后: " + this);
    }

    Memento save() { // 存档：把当前状态打包成备忘录
        System.out.println("存档: " + this);
        return new Memento(hp, level, position);
    }

    void restore(Memento m) { // 读档：按备忘录回滚
        this.hp = m.hp();
        this.level = m.level();
        this.position = m.position();
        System.out.println("已回滚到: " + this);
    }

    @Override
    public String toString() {
        return "角色[HP=" + hp + ", 等级=" + level + ", 位置=" + position + "]";
    }
}

// 管理者：存档管理器，只保管不窥探
class SaveManager {
    private final Map<String, Memento> saves = new HashMap<>();
    void put(String slot, Memento m) { saves.put(slot, m); }
    Memento get(String slot) { return saves.get(slot); }
}

public class MementoDemo {
    public static void main(String[] args) {
        GameRole role = new GameRole(100, 1, "第1层");
        SaveManager saves = new SaveManager();

        saves.put("boss前", role.save()); // Boss 前存档
        role.fight();                     // 打了一关
        role.fight();                     // 又打一关，HP 只剩 40
        System.out.println("打不过了，读档重来...");
        role.restore(saves.get("boss前")); // 回滚到存档点，状态完好如初
    }
}
```

- **快照必须是深拷贝或不可变**：本例状态都是基本类型和 String，record 天然不可变；状态里一旦有 List/Map 等可变对象，save() 时必须拷贝一份，否则之后对原对象的修改会同步「污染」已保存的快照，回滚出错误状态。
- **管理者只保管不解释**：Caretaker 不读备忘录内容、不参与回滚逻辑，这样快照的内部格式可以随便演进；把「何时存、何时滚」的策略（自动存档点、保留几个版本）放在管理者或业务层。
- **坑：全量快照太贵时改增量**。状态很大（如整章小说的世界状态）时，每次全量拷贝成本高，工程上常用「基线快照 + 变更日志」：回滚 = 基线 + 重放变更到目标点，这也是数据库 PITR 的做法。

## 适用场景与选型

- 用：需要 undo/回档；长流程要在中间节点留检查点，失败从检查点重试而不是从头再来；要支持"分支试错"——保存当前状态，试一条路，不行回档换另一条。
- 不用：状态简单到用几个变量就能恢复，没必要建快照体系；状态巨大且快照非常频繁，全量快照成本扛不住时要先换增量方案，而不是硬套本模式。
- 与命令模式 undo 的区别（只记一句）：命令的 undo 靠逆运算还原（存↔取、加↔减）；备忘录的 undo 靠快照回滚，逆运算写不出来或不可靠时用备忘录。

## 优缺点

- 优点：回滚实现对发起人是黑盒，封装不破；撤销、重做、存档读档、版本回退有统一套路；分支试错不需要业务层自己管理状态副本。
- 代价：快照频繁或状态大时内存与存储成本高；深拷贝做不干净会出现"回滚后状态被后续修改污染"；快照粒度（存多细、存多 often）定不好，成本和恢复能力两头不讨好。

## 常见误区

- 误区 1：浅拷贝污染快照。错：状态里有 List，save() 时只把引用存进备忘录，之后对原 List 的修改会同步改掉已保存的快照，回滚出错误状态。正确：快照必须是深拷贝或不可变——像 Demo 那样只存基本类型和 String 的 record，或在 save() 里拷贝可变对象。
- 误区 2：管理者窥探或修改快照。错：Caretaker 读取备忘录内容做业务判断，甚至直接改快照字段。正确：管理者只保管、不解释、不修改，快照格式才能自由演进而不影响保管逻辑。
- 误区 3：状态很大仍坚持全量快照。错：整章小说的世界状态每次全量拷贝，存档一次卡一次。正确：改"基线快照 + 变更日志"，回滚等于基线加重放变更到目标点，这也是数据库 PITR 的做法。

## 小技巧与冷知识

【小技巧】存档之前先校验状态合不合法：save() 只是把当前状态原样打包，它不负责判断状态对不对。存了个"半初始化"或"已损坏"的状态，回滚回去也是错的，undo 反而成了把错误复活的工具。存档点前先做一次不变量检查（比如 HP 不能为负、关键字段非空），脏状态宁可不存，也别存下来等回滚时再炸。

【小技巧】restore() 之后要重新通知观察者和失效缓存：回滚只改了发起人自己的字段，监听状态变化的观察者、缓存了旧状态的下游并不会自动知道"状态被换回去了"。读档后如果不主动发一次变更通知或清掉相关缓存，UI 显示的还是回滚前的旧值，状态和视图就悄悄脱节了；把"恢复后通知"写进 restore 的收尾，别指望调用方记得补。

【小技巧】撤销栈要限长，别让它无限涨：每次操作都压一个快照，操作几千次后栈里就是几千份状态，内存先撑不住。常见做法是只保留最近 N 个版本（Deque 满了就丢最旧的），或者定期把旧快照落盘、内存里只留最近的。限长不是偷工减料——undo 能回到多远，本来就是产品要定的规格，不是技术默认无限。

【小技巧】快照里只存最小原始状态，派生值恢复后重新算：比如"总价"可以从单价和数量算出来，就别把它也存进备忘录。派生值和原始状态一起存，恢复时一旦两者对不上（存的时候就没对齐），回滚出来的状态自相矛盾。原始状态是快照的唯一真相，派生状态是恢复后算出来的结果，职责分开才不会存出"自己打架"的快照。

【小技巧】恢复时想清楚是"原地写回"还是"换引用"：restore() 直接改发起人的字段是原地写回，外部如果还持有发起人的旧引用（比如别的模块缓存了它的某个字段值），回滚后这些引用看到的是新值还是旧值要事先想明白。状态对象本身做成不可变、恢复时整体换引用，比原地改字段更容易推理，代价是调用方要重新拿一次引用。

【小技巧】多个对象要协同回滚时，检查点必须覆盖整组对象：只回滚玩家血量、不回滚怪物位置，读档后会留下一个"半新半旧"的组合状态——血回来了、怪还在原地打你。需要一致性的对象组要共用同一个检查点编号，存档和回滚都按组走；单对象的备忘录管不了跨对象的一致性，别把它当成分布式事务用。

【小技巧】快照要带版本号，格式演进后老存档才读得回来：备忘录序列化落盘（游戏存档、长流程检查点）后，下一版改了状态结构，旧存档按新结构解析直接报错。Memento 里放一个 version 字段，restore 时按版本分支解析、缺失的字段补默认值，老存档才能平滑升级；没版本号的快照，改一次结构就等于废掉所有历史存档。

【小技巧】存档点的名字要有业务语义，别只用时间戳：管理者按 slot 取快照时，"boss前""提交前""第3章开头"比"2026-10-31 03:00"好找得多，排障时也一眼知道这个检查点对应哪个业务节点。时间戳只适合自动存档的默认名，手动埋的检查点一定要写业务名，名字本身就是一份文档。

【小技巧】redo 不是 undo 的反方向，而是"撤销栈 + 重做栈"两套：undo 时把当前状态压入重做栈再回滚，redo 时从重做栈取出来恢复；一旦用户做了新操作，重做栈必须清空——新操作之后，旧的重做路径已经不存在了。只留一个栈、靠正反两次 restore 实现 redo，状态一多就乱，两个栈分开是标准做法。

【冷知识】数据库的 SAVEPOINT 就是 SQL 标准里的备忘录：`SAVEPOINT sp1` 在事务里打一个检查点，`ROLLBACK TO SAVEPOINT sp1` 只回滚到该点、事务本身不结束。SQL:1999 就把 SAVEPOINT 写进了标准，备忘录的思想比 GoF 写书早得多，只是名字不同——数据库厂商几十年前就在用快照回滚做事务的部分撤销。

【冷知识】GoF 原书讲备忘录用的例子是图形编辑器：移动、缩放图形对象时把状态存成备忘录，撤销就恢复上一个快照。编辑器撤销栈、游戏存档、IDE 的 Local History 都是同一个套路的不同皮肤——备忘录从一开始就是为"可视化编辑器的 undo"设计的，不是后来才套用到游戏和数据库上的。

【冷知识】"Memento" 这个词来自拉丁语 memento（"记住"），和短语 memento mori（"记住你必死"）同源：模式名直译就是"记住这个状态的东西"。GoF 起这个名字是有意的——备忘录的全部职责就是"记住"，它不计算、不判断、不协调，只负责在需要的时候把记住的状态原样还给你。

## 面试与自测

1. 为什么备忘录强调"快照必须是深拷贝或不可变"？浅拷贝会出什么问题？
2. 备忘录的 undo 和命令模式的 undo，分别适合什么场合？
3. 状态很大、全量快照太贵时，工程上常用的替代方案是什么？

### 参考答案

1. 因为快照保存的是"某一时刻的状态"；浅拷贝只存引用，之后对原可变对象的修改会同步污染已保存的快照，回滚时恢复的是被改过的状态，不是存档时的状态。
2. 能写出精确逆运算的（存↔取、插入↔删除）用命令 undo，轻量；逆运算写不出来、不可靠或状态复杂到逆运算容易错时，用备忘录快照回滚。
3. 基线快照 + 变更日志：定期存一次全量基线，平时只记变更；回滚时从基线重放变更到目标点，用少量存储换一次重放计算。
