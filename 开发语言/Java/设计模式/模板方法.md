# 模板方法模式

## 模式介绍

**意图**：在抽象类里定死算法的骨架（步骤顺序），把其中可变的步骤声明为抽象方法留给子类填。流程全局只写一份，差异被收进各个钩子方法。

**结构与角色**：

- `AbstractClass`（抽象类）：定义 `final` 的模板方法（骨架，不许子类改顺序）+ 若干步骤方法。
- 步骤分三种：抽象方法（子类必须实现）、具体方法（公共步骤，父类直接写）、钩子方法（有默认实现，子类可选覆盖，如 `boolean needAudit()` 默认 false）。
- `ConcreteClass`（子类）：只实现可变步骤，不关心整体流程。

**效果**：

- 优点：公共流程零重复（校验、日志、事务、异常处理写一次）；流程顺序被父类锁死，子类想写乱也乱不了。
- 代价：基于继承，子类与父类强耦合；骨架一旦要改，所有子类受影响；Java 单继承下，模板占掉唯一的继承位。

**适用信号**：

- 多个类的处理流程步骤完全一致，只有个别步骤实现不同（数据导入：读文件格式不同，校验/入库/记日志相同）。
- 想强制所有实现走同一套流程规范（发送前必校验、操作后必审计）。

**落点**：

- Spring 的 `JdbcTemplate`：连接获取、异常翻译、资源释放是骨架，SQL 和结果映射是留给调用方的可变步骤（用回调而非继承，是模板方法的变体）。
- `AbstractApplicationContext.refresh()`、各种导入/批处理基类、自研的消息发送骨架（校验 → 发送 → 审计，渠道填发送细节）。

**模板方法 vs 策略**：模板方法靠**继承**，骨架固定、步骤可变，编译期定型；策略靠**组合**，整个算法可替换，运行期可换。流程骨架稳定、只换局部步骤用模板；整段算法都要换用策略。现代 Java 里模板方法常用「抽象类 + 函数式参数」变体替代纯继承。

## 模式 Demo

```java
// 数据导入骨架：解析格式各不同，校验/入库/日志流程全局统一
abstract class DataImporter {

    // 模板方法：骨架定死，final 禁止子类改顺序
    public final void importData(String source) {
        Object data = parse(source);          // 可变步骤：子类实现
        validate(data);                       // 公共步骤：父类实现
        save(data);                           // 公共步骤：父类实现
        if (needAudit()) audit(source);       // 钩子：默认不审计，子类可开
        System.out.println("导入完成：" + source);
    }

    protected abstract Object parse(String source);   // 每个格式自己解析

    protected void validate(Object data) {
        if (data == null) throw new IllegalStateException("数据为空，终止导入");
        System.out.println("校验通过");
    }

    protected void save(Object data) { System.out.println("入库：" + data); }

    protected boolean needAudit() { return false; }   // 钩子方法

    protected void audit(String source) { System.out.println("审计记录：" + source); }
}

class CsvImporter extends DataImporter {
    protected Object parse(String source) {
        System.out.println("按 CSV 解析");
        return "csv-rows";
    }
}

class JsonImporter extends DataImporter {
    protected Object parse(String source) {
        System.out.println("按 JSON 解析");
        return "json-rows";
    }
    protected boolean needAudit() { return true; }    // 只开钩子，不碰骨架
}

public class TemplateDemo {
    public static void main(String[] args) {
        new CsvImporter().importData("a.csv");
        new JsonImporter().importData("b.json");      // 流程一致，多一步审计
    }
}
```

- 模板方法必须 `final`：不锁死骨架，子类随手改顺序，模式就形同虚设。
- 钩子方法是精髓：把「可选差异」做成带默认值的开关方法，避免为一点小不同就逼子类重写整条流程。
- 坑：骨架步骤别超过 7-8 步，否则子类作者要通读父类才能写对一个方法；步骤再多就该拆成策略或责任链。

## 适用场景与选型

- 用：多个类的处理流程步骤完全一致，只有个别步骤实现不同；想强制所有实现走同一套流程规范（发送前必校验、操作后必审计）。
- 不用：骨架本身经常变，改一次骨架就要通读所有子类；各实现的步骤差异大到骨架只剩空壳；需要在运行期整体换掉算法（那是策略模式的地盘）。
- 与策略模式的区别（只记一句）：模板方法靠继承，骨架固定、步骤可变，编译期定型；策略靠组合，整个算法可替换，运行期可换。

## 优缺点

- 优点：公共流程零重复，校验、日志、事务、异常处理只写一次；流程顺序被父类锁死，子类想写乱也乱不了。
- 代价：基于继承，子类与父类强耦合，骨架一改全部子类受影响；Java 单继承下模板占掉唯一的继承位；子类单测必须带着父类跑，隔离性差。

## 常见误区

- 误区 1：模板方法不加 final。错：骨架方法任由子类覆盖改顺序，子类随手调换校验和入库的次序，模式形同虚设。正确：骨架方法一律 final，只留步骤方法给子类（Demo 的 importData 就是 final）。
- 误区 2：骨架步骤贪多。错：一个模板方法塞十几步，子类作者要通读父类全文才能写对一个步骤。正确：步骤控制在 7-8 步以内，再多就拆成策略或责任链。
- 误区 3：拿模板方法做运行期切换。错：想根据配置切换整套算法，却去写多个模板子类再在运行期选。正确：整段算法要换时用策略组合，模板方法只适合"骨架稳定、局部步骤可变"的场合。

## 面试与自测

1. 模板方法里的抽象方法、具体方法、钩子方法各是什么？子类对三者分别要做什么？
2. 为什么说模板方法"占掉唯一的继承位"是一个代价？
3. Spring 的 JdbcTemplate 是模板方法的哪种变体？它和纯继承版有什么不同？

### 参考答案

1. 抽象方法子类必须实现，是可变步骤；具体方法是父类写好的公共步骤，子类直接复用；钩子方法有默认实现，子类可选覆盖，用来做"可选差异"的开关（如 needAudit 默认 false）。
2. Java 是单继承，子类继承了模板父类就不能再继承别的类；如果业务上更需要继承另一个基类，就会冲突。现代 Java 因此常用"抽象类 + 函数式参数"变体替代纯继承。
3. 回调变体：骨架（连接获取、异常翻译、资源释放）仍在 JdbcTemplate 里，可变步骤（SQL、结果映射）以回调参数传入而非子类继承，调用方不需要继承任何类。
