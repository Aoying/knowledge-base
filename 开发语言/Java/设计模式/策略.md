# 策略模式

## 模式介绍

**意图**：把一组可互换的算法（或业务规则）各自封装成实现同一个接口的类，调用方在运行时按条件选用其中一个。变化的是「怎么做」，不变的是「调用方式」。

**结构与角色**：

- `Strategy`（策略接口）：定义算法的统一入口，如 `pay(amount)`、`send(msg)`。
- `ConcreteStrategy`（具体策略）：每个实现类只负责一种算法，不互相知道。
- `Context`（上下文/调用方）：持有一个策略引用，业务流程写一次，算法靠注入或查表获得。

**效果**：

- 优点：新增算法只加新类，不改调用方（开闭原则）；消灭按类型分支的长 if-else；每个算法可独立单测。
- 代价：策略类变多；调用方必须先解决「怎么选策略」的问题——通常用工厂或 Map 注册表配套（策略 + 工厂是最常见组合）。

**适用信号**：

- 同一件事有 3 种以上做法，且做法还会继续增加（支付渠道、消息渠道、计价规则、导出格式）。
- if-else / switch 的分支里是「整段不同的业务逻辑」，而不是简单赋值。
- 算法之间需要 A/B 切换或按配置动态切换。

**落点**：

- 多渠道消息发送：邮件/短信/企业微信各一个策略，Spring 把所有实现按 bean 名注入 `Map<String, MsgChannel>`，按类型查表即完成选择。
- 支付与退款、运费与优惠计算、文件导出（Excel/PDF/CSV）。
- JDK 里 `Comparator` 就是策略：排序算法不变，比较规则由传入的策略决定。

**策略 vs 状态**：策略是调用方**外部选**的，选完相对稳定；状态是对象**内部流转**的，调用方不感知。**策略 vs 简单 if-else**：分支少于 3 个、且不会再涨，if-else 更直读，别硬套。

## 模式 Demo

```java
import java.util.Map;

// 策略接口：一组可互换的支付算法
interface PayStrategy {
    void pay(long cents);
}

class AliPay implements PayStrategy {
    public void pay(long cents) { System.out.println("支付宝支付：" + cents + " 分"); }
}

class WxPay implements PayStrategy {
    public void pay(long cents) { System.out.println("微信支付：" + cents + " 分"); }
}

class CardPay implements PayStrategy {
    public void pay(long cents) { System.out.println("银行卡支付：" + cents + " 分"); }
}

// 上下文：流程只写一次（校验 -> 扣款 -> 记账），算法靠查表注入
class CheckoutService {
    private final Map<String, PayStrategy> strategies;   // 注册表：key 是渠道名

    CheckoutService(Map<String, PayStrategy> strategies) {
        this.strategies = strategies;
    }

    void checkout(String channel, long cents) {
        PayStrategy s = strategies.get(channel);
        if (s == null) throw new IllegalArgumentException("不支持的渠道：" + channel);
        // 校验金额等公共流程写在这里，各渠道只管自己的 pay()
        if (cents <= 0) throw new IllegalArgumentException("金额必须为正");
        s.pay(cents);
        System.out.println("记账完成，渠道=" + channel);
    }
}

public class StrategyDemo {
    public static void main(String[] args) {
        // 组装注册表（Spring 里这一步就是 @Component + 按名注入 Map）
        Map<String, PayStrategy> map = Map.of(
                "ali", new AliPay(),
                "wx", new WxPay(),
                "card", new CardPay());
        CheckoutService svc = new CheckoutService(map);
        svc.checkout("ali", 1000);
        svc.checkout("wx", 2500);
        // 新增渠道 = 新增一个实现类 + 注册表加一行，CheckoutService 一行不改
    }
}
```

- 核心是「注册表 + 查表」：策略模式解决算法封装，选哪个交给 Map/工厂；Spring 项目直接把 Map 交给容器组装，是最省事的落地方式。
- 策略类应保持无状态（参数从方法入参进），这样单例共享才安全；需要上下文数据就随参数传，不要塞字段。
- 坑：把只差一两行参数的逻辑拆成一堆策略类是过度设计——先抽公共基类或用参数化配置，真正整段不同的才独立成策略。

## 适用场景与选型

- 用：同一件事有 3 种以上做法且还会增加；做法之间需要按配置、按渠道、按实验分组动态切换；分支里是整段不同的业务逻辑。
- 不用：分支少于 3 个且基本定型，直接写 if-else 更直读；各做法只差一两个参数值，用配置表或参数化就能解决；策略之间需要共享可变状态、互相协作完成一件事（那不是"可互换算法"，是流程分工）。
- 与状态模式的区别（只记一句）：策略是调用方在外部选定、选完相对稳定的算法；状态是对象内部随事件自动流转的行为，调用方不感知、不选。

## 优缺点

- 优点：新增算法只加新类，调用方零改动；每个算法可独立单测；运行时切换不需要改流程代码。
- 代价：策略类数量随算法膨胀；"怎么选策略"的逻辑会外溢，选型散落各处时比 if-else 更难追踪；调用方要理解每个策略的语义边界，否则选错策略的 bug 藏得很深。

## 常见误区

- 误区 1：把参数差异硬拆成策略。错：两个支付渠道只差费率和回调地址，却各写一个策略类。正确：差异只是参数时用配置表，差异是整段逻辑时才独立成策略。
- 误区 2：策略类带可变状态。错：策略里用字段缓存上一次的入参或中间结果，单例共享后并发请求互相污染。正确：策略保持无状态，所需数据全部走方法入参（Demo 的 PayStrategy 就是这么写的）。
- 误区 3：选型逻辑散落各处。错：每个调用点都写一遍 `if (channel.equals("ali")) ...`。正确：选型集中到一处——Map 注册表或工厂，调用方只传 key。

## 面试与自测

1. 策略模式与状态模式的根本区别是什么？
2. 为什么说"策略 + 工厂/Map 注册表"是最常见组合？策略模式本身缺了哪一块？
3. 只有两种支付方式、且未来基本不变时，该不该用策略模式？为什么？

### 参考答案

1. 选择权在谁手里不同：策略由调用方在外部选定，选完相对稳定；状态由对象内部根据事件自动流转，调用方不感知、不参与选择。
2. 策略模式只解决"算法怎么封装"，不解决"选哪个算法"；工厂或 Map 注册表补上选型这一块，调用方只传 key，新增策略时注册处加一行即可。
3. 不该。分支少且稳定时 if-else 更直读，硬套策略会多出接口、实现类、注册表三层间接，收益为负；等做法涨到 3 种以上或需要动态切换时再抽。
