# 依赖注入

> 依赖注入（Dependency Injection，DI）不是 GoF 模式，是与模式同源的设计思想：对象不自己创建依赖，而是由外部在组装时递进来。

## 模式介绍

**意图**：把「创建依赖对象」和「使用依赖对象」两件事拆开。类只声明自己需要什么（接口），由外部容器或组装代码负责 new 好并注入，于是实现可替换、类可单测、组装关系集中管理。

**三种注入方式**：

- **构造器注入**（首选）：依赖通过构造器传入，对象一出生就完整，依赖可声明 `final`，缺依赖编译/启动即失败。
- **Setter 注入**：适合可选依赖或需要运行期替换的场景，代价是对象可能处于「没注入完」的中间状态。
- **字段注入**：容器靠反射直接写字段（如 `@Autowired` 打在字段上），写起来最省事，但脱离容器无法手动组装、单测要靠反射，生产代码不推荐新增。

**结构与角色**：

- 依赖接口（如 `MsgChannel`）：使用者只认抽象。
- 实现类：被注入的具体对象。
- 组装方（容器/工厂/main）：知道全部具体类，负责创建和拼装——这是全系统唯一「知道细节」的地方。

**自己 new 的问题**：`new SmsChannel()` 写死在业务类里，换渠道要改源码、发版；想给业务类写单测，必须连真实短信通道一起跑，没法替换成假实现。

**效果**：优点是解耦、可测、可换；代价是多一层组装（容器或手工组装代码），对象关系不再「打开类就全看见」，需要靠命名和配置找实现。

**落点**：

- Spring DI 容器就是把 DI 工程化：Bean 定义（配置/注解）+ 容器负责创建、注入、生命周期（单例管理、初始化回调）。
- 手写项目同样适用：main 方法或工厂类集中组装，就是最小容器（见 Demo）。

## 模式 Demo

```java
// 依赖抽象：发送渠道接口
interface MsgChannel {
    void send(String to, String text);
}

class SmsChannel implements MsgChannel {
    public void send(String to, String text) {
        System.out.println("短信 -> " + to + "：" + text);
    }
}

// 测试用的假实现：DI 才能轻松换上它，自己 new 时做不到
class FakeChannel implements MsgChannel {
    public void send(String to, String text) {
        System.out.println("[fake] 已记录发送给 " + to);
    }
}

// 业务类：只声明需要什么，不 new、不关心实现是谁
class NotifyService {
    private final MsgChannel channel;               // final：构造后不可变

    NotifyService(MsgChannel channel) {             // 构造器注入
        this.channel = channel;
    }

    void notifyUser(String phone, String text) {
        // 业务流程：拼文案、做校验 …… 最后调用注入进来的渠道
        channel.send(phone, text);
    }
}

// 最小「容器」：全系统只有这里知道具体类，负责组装
class Container {
    static NotifyService notifyService() {
        return new NotifyService(new SmsChannel());
    }
}

public class DiDemo {
    public static void main(String[] args) {
        // 生产：从容器拿组装好的对象
        Container.notifyService().notifyUser("138...", "验证码 1234");
        // 测试/演示：直接手工注入假实现，NotifyService 一行不改
        new NotifyService(new FakeChannel()).notifyUser("138...", "验证码 1234");
    }
}
```

- 对比自己 new：若 `NotifyService` 内部写死 `new SmsChannel()`，换渠道要改业务类，单测也被真实发送绑架；DI 把「选实现」这一个决定收拢到组装方。
- 构造器注入优先的理由：依赖必填且不可变，对象没有半成品状态；Spring 新代码官方也推荐构造器注入（配合 Lombok `@RequiredArgsConstructor`）。
- 坑：别把 DI 用成「服务定位器」——到处从容器里按名 getBean，等于把耦合藏起来而不是消除；依赖只应出现在构造器签名上。

## 适用场景与选型

- 用它：依赖需要替换（多实现、测试替身、不同环境不同实现）；组装关系想集中管理；类需要可单测、不想被真实依赖绑架。
- 不用它：依赖是稳定值对象或纯工具、永不替换时，直接 new 更直观；只有一两个类的小脚本，容器是重武器；依赖关系本身就是业务逻辑的一部分、需要显式表达时，别把它藏进容器配置里。
- 与工厂方法的一句话区分：工厂回答“谁来创建”，DI 回答“创建与使用分离后、依赖由谁递进来”——工厂常被用作 DI 的组装方，二者互补而非替代；与服务定位器的区分见误区。

## 优缺点

- 优点：解耦——业务类只认接口；可测——测试可注入假实现，Demo 的 FakeChannel 就是例子；可换——换渠道只改组装方；组装关系集中，全系统只有一个“知道细节”的地方。
- 缺点：对象关系不再“打开类就全看见”，要查配置才知道实现是谁；容器启动与配置错误（如循环依赖、缺 Bean）的排查成本高于直接 new；构造器参数膨胀是类职责过多的信号，容易被容器掩盖。

## 常见误区

- 字段注入图省事：`@Autowired` 打在字段上，脱离容器无法手动组装，单测要靠反射写字段。正确：构造器注入优先，依赖必填且可声明 final，对象没有半成品状态——Demo 的 `NotifyService(MsgChannel channel)` 就是范本。
- 把 DI 用成服务定位器：业务代码到处从容器里按名 getBean，等于把耦合藏起来而不是消除，换实现时照样要改业务代码。正确：依赖只出现在构造器签名上，业务类永远不直接碰容器。
- 构造器参数越注越多还继续注：一个类注入七八个依赖还在加，说明它承担了太多职责。正确：这是拆类的信号，不是给容器加更多 Bean 的理由——先拆类，再谈注入。

## 面试与自测

1. 三种注入方式怎么选？为什么构造器注入优先？
2. 依赖注入和服务定位器有什么区别？为什么后者不推荐？
3. 一个类的构造器参数膨胀到七八个，说明什么？正确做法是什么？

### 参考答案

1. 构造器注入首选：依赖必填、可声明 final、对象一出生就完整，缺依赖编译或启动即失败。Setter 注入只适合可选依赖或运行期替换，代价是对象可能处于“没注入完”的中间状态。字段注入最省事但脱离容器无法组装、单测靠反射，生产代码不推荐新增。
2. 区别在依赖出现的位置：DI 是依赖出现在构造器签名上，调用方一眼看清类需要什么；服务定位器是业务代码主动向容器按名要依赖，依赖关系藏在方法体里。定位器没有消除耦合，只是把耦合藏起来——换实现、做单测时照样要改业务代码，所以不推荐。
3. 说明类承担了太多职责，违反单一职责原则的概率很高。正确做法是拆类：把一部分依赖连同使用它们的逻辑抽成新类，再分别注入，而不是继续往构造器里加参数。
