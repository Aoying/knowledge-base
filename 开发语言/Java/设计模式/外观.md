# 外观模式（Facade）

## 模式介绍

**意图**：给一组复杂的子系统开一扇简单的门。客户端只跟门面打一次交道，门面内部负责按正确顺序调用各子系统。

**结构与角色**：

- 外观（Facade）：知道每个子系统负责什么、调用顺序如何，对外只暴露粗粒度方法。
- 子系统（Subsystem）：库存、支付、物流等各自独立的类，对门面的存在无感知，也可以被直接调用。

**效果**：

- 优点：客户端与子系统解耦，子系统内部重构不波及调用方；把「流程编排」这种易错知识收敛到一处。
- 代价：门面容易膨胀成上帝类；门面不做权限与规则收口时，会退化成无意义的转发层。

**适用信号**：

- 一个业务动作要串联 3 个以上子系统，且这个串联顺序多处重复出现。
- 给外部（前端、第三方）提供接口，不想让对方理解内部系统拓扑。

**落点**：下单接口背后的 `OrderFacade` 串库存/支付/物流；Spring 里的 `JdbcTemplate` 本质是 JDBC 子系统的外观；微服务里的 BFF/聚合层、网关聚合接口；遗留系统重构时先立门面再逐步替换内部，是标准的绞杀者做法。

**粒度怎么定**：门面方法应该对应「一个完整的业务动作」（下单、退款、开通），不是把子系统的方法换个名再暴露一遍。判断标准：客户端调一次门面方法就能完成一件完整的事，不需要知道中间有几步、哪步失败了要怎么补偿。

**分层提醒**：门面不禁止客户端绕过它直连子系统（子系统保持独立可用），它提供的是「推荐路径」而不是「唯一通道」；只有涉及顺序与补偿的动作才强制走门面。

## 模式 Demo

```java
// 三个子系统：各自独立，接口和调用顺序只有门面知道
class InventoryService {
    boolean deduct(String sku, int num) {
        System.out.println("库存：扣减 " + sku + " x" + num);
        return true;
    }
}

class PaymentService {
    boolean charge(String userId, long cents) {
        System.out.println("支付：向 " + userId + " 扣款 " + cents + " 分");
        return true;
    }
}

class LogisticsService {
    String createOrder(String sku, String address) {
        System.out.println("物流：为 " + sku + " 建单，寄往 " + address);
        return "SF123456";
    }
}

// 外观：把"下单"这条流水线（验库存→扣款→建物流单）收成一个方法
class OrderFacade {
    private final InventoryService inventory = new InventoryService();
    private final PaymentService payment = new PaymentService();
    private final LogisticsService logistics = new LogisticsService();

    public String placeOrder(String userId, String sku, int num, long cents, String address) {
        if (!inventory.deduct(sku, num)) throw new IllegalStateException("库存不足");
        if (!payment.charge(userId, cents)) throw new IllegalStateException("支付失败");
        return logistics.createOrder(sku, address); // 返回运单号
    }
}

public class FacadeDemo {
    public static void main(String[] args) {
        // 客户端只知道"下单"，完全不用了解三个子系统的存在和调用顺序
        String waybill = new OrderFacade().placeOrder("u1001", "SKU-9", 2, 19900, "深圳市南山区");
        System.out.println("下单成功，运单号：" + waybill);
    }
}
```

- 门面的价值在「编排顺序」而不是转发：顺序、失败处理、补偿（如扣款成功但建单失败要退款）都收在门面里写一次。
- 与适配器的区别：外观是简化一组接口的调用，适配器是转换单个接口的形态；门面不改变子系统接口。
- 坑：门面一旦开始写业务规则就会膨胀。规则归领域服务，门面只做编排和参数组装。

## 适用场景与选型

- 用它：一个业务动作要串联 3 个以上子系统，且这个串联顺序多处重复出现；给外部（前端、第三方）提供接口，不想让对方理解内部系统拓扑；遗留系统重构时先立门面再逐步替换内部（绞杀者做法）。
- 不用它：背后只有一个子系统，门面只剩转发，多一层没有意义；门面方法与子系统方法一一对应、只是换个名再暴露，编排价值为零。
- 选型：门面方法应该对应「一个完整的业务动作」（下单、退款、开通），判断标准是客户端调一次门面方法就能完成一件完整的事，不需要知道中间有几步。粒度细到换名转发就是失败的门面。
- 与适配器的区别（一句话）：外观是简化一组接口的调用，不改任何子系统接口；适配器是转换单个接口的形态，让两个对不上的接口接上。

## 优缺点

- 优点：客户端与子系统解耦，子系统内部重构不波及调用方；「流程编排」这种易错知识收敛到一处，只写一次；对外暴露的接口面变小，外部调用方理解成本低。
- 缺点：门面容易膨胀成上帝类——什么编排都往里塞；过度封装会让客户端失去子系统级控制（比如只想扣库存、不要整单流程时，还得绕开门面）。
- 缺点：门面一旦开始写业务规则，规则和编排就缠在一起，领域服务和门面的边界会越来越糊。

## 常见误区

- 门面里写业务规则：比如在 OrderFacade 里顺手做「满减计算」「风控拦截」。错：规则归领域服务，门面只做编排和参数组装；规则一旦进门面，复用和测试都变难，门面也开始膨胀。
- 门面方法粒度过细：把 `deduct`、`charge`、`createOrder` 原样换个名再暴露一遍。错：这只是转发，没有收敛任何编排知识，客户端还是要自己拼顺序。正确做法是门面方法对应完整业务动作，一次调用完成一件事。
- 失败补偿缺失：Demo 的 placeOrder 在建单失败时只抛异常，没有回滚已经成功的扣款。生产实现里，门面要把补偿也收进来——扣款成功但建单失败要退款、库存扣减要回补，编排的每一步失败都得有对应的补偿动作，不能只抛异常了事。

## 面试与自测

1. 外观模式和适配器模式的区别是什么？各举一个落点。
2. 门面方法的粒度怎么定？什么样的门面算失败的门面？
3. 外观模式禁止客户端绕过门面直连子系统吗？为什么？

### 参考答案

1. 外观简化一组接口的调用，不改任何子系统接口，如 OrderFacade 把库存、支付、物流的下单流水线收成一个方法；适配器转换单个接口的形态，解决两个现存接口对不上的问题，如把老支付 SDK 适配成系统内的 PayService。
2. 门面方法对应「一个完整的业务动作」（下单、退款、开通），客户端调一次就能完成一件事，不需要知道中间有几步；如果门面方法与子系统方法一一对应、只是换名转发，就是失败的门面——它没有收敛任何编排知识。
3. 不禁止。门面提供的是「推荐路径」而不是「唯一通道」，子系统保持独立可用；只有涉及顺序与补偿的动作才强制走门面，客户端偶尔需要子系统级控制时可以直接调子系统。
