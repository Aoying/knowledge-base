# 外观模式（Facade）

## 模式介绍

**意图**：给一组复杂的子系统开一扇简单的门。客户端只跟门面打一次交道，门面内部负责按正确顺序调用各子系统。

**结构与角色**：

- 外观（Facade）：知道每个子系统负责什么、调用顺序如何，对外只暴露粗粒度方法。
- 子系统（Subsystem）：库存、支付、物流等各自独立的类，对门面的存在无感知，也可以被直接调用。

**效果**：

- 优点：客户端与子系统解耦，子系统内部重构不波及调用方；把「流程编排」这种易错知识收敛到一处。
- 代价：门面容易膨胀成上帝类；门面不做权限与规则收口时，会退化成无意义的转发层。

**适用信号**：

- 一个业务动作要串联 3 个以上子系统，且这个串联顺序多处重复出现。
- 给外部（前端、第三方）提供接口，不想让对方理解内部系统拓扑。

**落点**：下单接口背后的 `OrderFacade` 串库存/支付/物流；Spring 里的 `JdbcTemplate` 本质是 JDBC 子系统的外观；微服务里的 BFF/聚合层、网关聚合接口；遗留系统重构时先立门面再逐步替换内部，是标准的绞杀者做法。

**粒度怎么定**：门面方法应该对应「一个完整的业务动作」（下单、退款、开通），不是把子系统的方法换个名再暴露一遍。判断标准：客户端调一次门面方法就能完成一件完整的事，不需要知道中间有几步、哪步失败了要怎么补偿。

**分层提醒**：门面不禁止客户端绕过它直连子系统（子系统保持独立可用），它提供的是「推荐路径」而不是「唯一通道」；只有涉及顺序与补偿的动作才强制走门面。

## 模式 Demo

```java
// 三个子系统：各自独立，接口和调用顺序只有门面知道
class InventoryService {
    boolean deduct(String sku, int num) {
        System.out.println("库存：扣减 " + sku + " x" + num);
        return true;
    }
}

class PaymentService {
    boolean charge(String userId, long cents) {
        System.out.println("支付：向 " + userId + " 扣款 " + cents + " 分");
        return true;
    }
}

class LogisticsService {
    String createOrder(String sku, String address) {
        System.out.println("物流：为 " + sku + " 建单，寄往 " + address);
        return "SF123456";
    }
}

// 外观：把"下单"这条流水线（验库存→扣款→建物流单）收成一个方法
class OrderFacade {
    private final InventoryService inventory = new InventoryService();
    private final PaymentService payment = new PaymentService();
    private final LogisticsService logistics = new LogisticsService();

    public String placeOrder(String userId, String sku, int num, long cents, String address) {
        if (!inventory.deduct(sku, num)) throw new IllegalStateException("库存不足");
        if (!payment.charge(userId, cents)) throw new IllegalStateException("支付失败");
        return logistics.createOrder(sku, address); // 返回运单号
    }
}

public class FacadeDemo {
    public static void main(String[] args) {
        // 客户端只知道"下单"，完全不用了解三个子系统的存在和调用顺序
        String waybill = new OrderFacade().placeOrder("u1001", "SKU-9", 2, 19900, "深圳市南山区");
        System.out.println("下单成功，运单号：" + waybill);
    }
}
```

- 门面的价值在「编排顺序」而不是转发：顺序、失败处理、补偿（如扣款成功但建单失败要退款）都收在门面里写一次。
- 与适配器的区别：外观是简化一组接口的调用，适配器是转换单个接口的形态；门面不改变子系统接口。
- 坑：门面一旦开始写业务规则就会膨胀。规则归领域服务，门面只做编排和参数组装。

## 适用场景与选型

- 用它：一个业务动作要串联 3 个以上子系统，且这个串联顺序多处重复出现；给外部（前端、第三方）提供接口，不想让对方理解内部系统拓扑；遗留系统重构时先立门面再逐步替换内部（绞杀者做法）。
- 不用它：背后只有一个子系统，门面只剩转发，多一层没有意义；门面方法与子系统方法一一对应、只是换个名再暴露，编排价值为零。
- 选型：门面方法应该对应「一个完整的业务动作」（下单、退款、开通），判断标准是客户端调一次门面方法就能完成一件完整的事，不需要知道中间有几步。粒度细到换名转发就是失败的门面。
- 与适配器的区别（一句话）：外观是简化一组接口的调用，不改任何子系统接口；适配器是转换单个接口的形态，让两个对不上的接口接上。

## 优缺点

- 优点：客户端与子系统解耦，子系统内部重构不波及调用方；「流程编排」这种易错知识收敛到一处，只写一次；对外暴露的接口面变小，外部调用方理解成本低。
- 缺点：门面容易膨胀成上帝类——什么编排都往里塞；过度封装会让客户端失去子系统级控制（比如只想扣库存、不要整单流程时，还得绕开门面）。
- 缺点：门面一旦开始写业务规则，规则和编排就缠在一起，领域服务和门面的边界会越来越糊。

## 常见误区

- 门面里写业务规则：比如在 OrderFacade 里顺手做「满减计算」「风控拦截」。错：规则归领域服务，门面只做编排和参数组装；规则一旦进门面，复用和测试都变难，门面也开始膨胀。
- 门面方法粒度过细：把 `deduct`、`charge`、`createOrder` 原样换个名再暴露一遍。错：这只是转发，没有收敛任何编排知识，客户端还是要自己拼顺序。正确做法是门面方法对应完整业务动作，一次调用完成一件事。
- 失败补偿缺失：Demo 的 placeOrder 在建单失败时只抛异常，没有回滚已经成功的扣款。生产实现里，门面要把补偿也收进来——扣款成功但建单失败要退款、库存扣减要回补，编排的每一步失败都得有对应的补偿动作，不能只抛异常了事。

## 实战案例

### 案例一：门面方法与子系统方法一一对应，只是换名转发，编排价值为零

- **现象**：OrderFacade 里有 `deduct()`、`charge()`、`createOrder()` 三个方法，名字和子系统一模一样，调用方还是要自己拼“先扣库存、再扣款、最后建物流单”的顺序；门面多了一层，调用代码一行没少。
- **排查**：门面方法粒度过细：把 `deduct`、`charge`、`createOrder` 原样换个名再暴露一遍。错：这只是转发，没有收敛任何编排知识，客户端还是要自己拼顺序（原文“常见误区”第 2 条）。对照 Demo：`OrderFacade.placeOrder("u1001", "SKU-9", 2, 19900, "深圳市南山区")` 一次调用完成下单，返回运单号 `SF123456`，库存扣减、支付扣款、物流建单的顺序收在门面里，调用方完全不用了解三个子系统的存在和调用顺序。根子在门面方法的粒度定错了：门面方法应该对应「一个完整的业务动作」（下单、退款、开通），不是把子系统的方法换个名再暴露一遍（原文“粒度怎么定”一节）。
- **结论**：正确做法是门面方法对应完整业务动作，一次调用完成一件事（原文“常见误区”第 2 条）。判断标准：客户端调一次门面方法就能完成一件完整的事，不需要知道中间有几步、哪步失败了要怎么补偿（原文“粒度怎么定”一节）。门面方法的名字要用业务动作的动词加名词，别用子系统名拼接：`placeOrder()`、`refund()` 一看就知道是“一件完整的事”，`deductAndChargeAndCreate()` 只是把三个子系统名串起来，调用方还是得猜顺序（引自原文小技巧节）。

### 案例二：扣款成功但建单失败只抛异常，没退款也没回补库存

- **现象**：下单时物流建单失败，接口抛了异常；用户钱扣了、库存也扣了，运单却没有，客服查账才发现这笔订单“扣了款、没建单、没退款”。
- **排查**：失败补偿缺失：Demo 的 placeOrder 在建单失败时只抛异常，没有回滚已经成功的扣款（原文“常见误区”第 3 条）。对照 Demo 的流程：验库存→扣款→建物流单，`inventory.deduct` 与 `payment.charge` 成功后 `logistics.createOrder` 失败，异常直接抛给调用方，前面两步的成功结果没人管。原文“模式 Demo”后的要点点名了这一条：门面的价值在「编排顺序」而不是转发，顺序、失败处理、补偿（如扣款成功但建单失败要退款）都收在门面里写一次。根子在编排只写了正向流程、没写补偿路径：每一步成功都可能成为下一步失败时的待回滚项，只抛异常等于把补偿责任丢给了调用方，而调用方根本不知道前面哪几步已经成功了。
- **结论**：生产实现里，门面要把补偿也收进来——扣款成功但建单失败要退款、库存扣减要回补，编排的每一步失败都得有对应的补偿动作，不能只抛异常了事（原文“常见误区”第 3 条）。补偿要按逆序执行，补偿本身失败也不能静默吞掉：扣款成功、建单失败时，先退库存再退款，按“后做的先撤销”的顺序回滚；退款这一步如果也失败了，要记一条带业务单号的告警或进死信队列，别 catch 住什么都不做（引自原文小技巧节）。测门面只断言调用顺序和补偿路径，不测子系统内部逻辑：子系统全部 mock 掉，单测只验证“库存扣减失败时不调支付”“支付成功、建单失败时调了退款”这两类编排事实（引自原文小技巧节）。

## 小技巧与冷知识

【小技巧】门面方法的名字要用业务动作的动词加名词，别用子系统名拼接：`placeOrder()`、`refund()` 一看就知道是“一件完整的事”，`deductAndChargeAndCreate()` 只是把三个子系统名串起来，调用方还是得猜顺序。方法名本身就是门面的文档，名字起成业务动作，门面才算真正把编排知识藏起来了。

【小技巧】补偿要按逆序执行，补偿本身失败也不能静默吞掉：扣款成功、建单失败时，先退库存再退款，按“后做的先撤销”的顺序回滚；退款这一步如果也失败了，要记一条带业务单号的告警或进死信队列，别 catch 住什么都不做。补偿链上任何一步失败都得留痕，否则钱扣了、单没建、还没人知道。

【小技巧】门面本身不要持有可变状态：门面只做编排和参数组装，状态（进行中的订单、临时缓存）放在调用方或子系统里。门面一旦开始存状态，多个请求共用一个门面实例时状态就会串，并发下最先出问题；无状态的门面可以放心做成单例，有状态的门面每请求都要新建实例。

【小技巧】门面开始膨胀时，先看方法数和分支数：一个门面里方法数超过子系统数、方法里开始按业务类型 `if` 分流（普通下单、预售下单、跨境下单各一套分支），就是该拆的信号。拆法是按调用方或业务线拆成多个门面（OrderFacade、RefundFacade），或者把编排抽成独立的编排服务；继续往一个门面里塞，只会把它养成上帝类。

【小技巧】绞杀遗留系统时，门面接口先定死、内部先包旧实现：调用方只认门面方法签名，门面背后先调老系统，新实现写好一个就替换一个子系统，调用方全程无感。门面在这里的价值不只是简化调用，更是“新旧切换的隔离层”——接口不动，内部换血，迁移可以按子系统粒度分批走，不用一次全切。

【小技巧】超时和重试策略要在门面层统一，别让每个子系统各搞一套：库存超时 2 秒重试一次、支付超时 5 秒不重试、物流超时 3 秒重试两次，策略散在三个子系统里，改一次要改三处。门面收编排时顺手把“每步超时多久、失败重试几次、重试要不要幂等”收在一起，调用方只看到一次下单的整体超时。

【小技巧】对外暴露的门面返回值要按调用方裁剪，别把子系统内部 DTO 原样透出：前端要的运单号、预计到达时间和第三方要的对账字段不是同一套，门面按调用方各组装一份返回体。子系统内部字段（库存批次号、支付渠道内部码）一旦透出去，子系统重构就得同步改外部契约，门面的隔离作用就白费了。

【小技巧】测门面只断言调用顺序和补偿路径，不测子系统内部逻辑：子系统全部 mock 掉，单测只验证“库存扣减失败时不调支付”“支付成功、建单失败时调了退款”这两类编排事实。子系统自己的逻辑由它自己的单测管，门面的测试目标是顺序和补偿，别在门面测试里重测一遍子系统的边界条件。

【小技巧】一个门面只服务一类调用方，别把前端入口和第三方入口塞进同一个门面：前端要的是聚合展示字段，第三方要的是稳定契约和严格鉴权，两类入口的演进节奏完全不同。共用一个门面时，改前端展示会动到第三方契约；按调用方拆成两个门面，背后可以共用同一批子系统，入口各自演进互不干扰。

【冷知识】GoF 原书讲外观用的例子是编译器子系统：`Compiler` 类把词法分析器、语法分析器、代码生成器收成 `compile()` 一个入口，调用方只调 compile 就能完成一次编译。OrderFacade 的“下单流水线”和它是一个结构——门面模式的样板间本来就是编译器，不是电商下单。

【冷知识】“Facade”这个词来自法语 façade，意思是建筑物的正立面：整栋楼的内部结构（房间、楼梯、管道）全藏在立面后面，外人只看到一面墙。模式名本身就是一句提示——门面要像建筑立面一样，只露一个干净的入口，把内部的复杂结构全部挡在后面。

【冷知识】SLF4J 的全名就是 Simple Logging Facade for Java，名字里自带 Facade：它把 Logback、Log4j2 这些日志实现收成一套统一的 API，业务代码只跟 SLF4J 打交道，底层换日志框架不用改业务代码。日志门面和 OrderFacade 是同一回事，只是子系统换成了日志实现。

## 面试与自测

1. 外观模式和适配器模式的区别是什么？各举一个落点。
2. 门面方法的粒度怎么定？什么样的门面算失败的门面？
3. 外观模式禁止客户端绕过门面直连子系统吗？为什么？

### 参考答案

1. 外观简化一组接口的调用，不改任何子系统接口，如 OrderFacade 把库存、支付、物流的下单流水线收成一个方法；适配器转换单个接口的形态，解决两个现存接口对不上的问题，如把老支付 SDK 适配成系统内的 PayService。
2. 门面方法对应「一个完整的业务动作」（下单、退款、开通），客户端调一次就能完成一件事，不需要知道中间有几步；如果门面方法与子系统方法一一对应、只是换名转发，就是失败的门面——它没有收敛任何编排知识。
3. 不禁止。门面提供的是「推荐路径」而不是「唯一通道」，子系统保持独立可用；只有涉及顺序与补偿的动作才强制走门面，客户端偶尔需要子系统级控制时可以直接调子系统。
