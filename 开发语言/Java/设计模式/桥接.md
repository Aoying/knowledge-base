# 桥接模式

## 模式介绍

**意图**：当一个事物有两个（或多个）独立变化的维度时，把维度拆开，让它们各自独立变化、运行时自由组合，避免用继承做笛卡尔积导致类爆炸。

**结构与角色**：

- 抽象部分（Abstraction）：高层维度，如「消息类型」，内部持有一个实现维度的引用。
- 细化抽象（RefinedAbstraction）：普通消息、加急消息等具体子类。
- 实现部分（Implementor）：另一个维度的接口，如「发送渠道」。
- 具体实现（ConcreteImplementor）：短信、邮件、企业微信等具体渠道。

两个维度之间是组合关系（桥），不是继承。

**效果**：

- 优点：M 个抽象 × N 个实现只需 M+N 个类（继承做法要 M×N）；加新维度成员只加一个类。
- 代价：结构比直接继承绕，维度只有一维在变时用桥接是过度设计。

**适用信号**：

- 已经出现「A1B1、A1B2、A2B1、A2B2…」命名的类，或者预感马上要出现。
- 两个维度都明确还会继续扩展（消息类型还会加、渠道还会加）。

**落点**：JDBC 是经典桥接——`DriverManager`/连接 API 是抽象维，各厂商 Driver 是实现维；日志门面（API）与日志实现（Logback/Log4j）的分工同理；项目里的「报表类型 × 导出格式」「消息类型 × 渠道」都是天然桥接场景。

## 模式 Demo

```java
// 实现维：发送渠道（还会继续加：钉钉、飞书……）
interface SendChannel {
void send(String content);
}

class SmsChannel implements SendChannel {
public void send(String content) { System.out.println("[短信] " + content);}
}
class EmailChannel implements SendChannel {
public void send(String content) { System.out.println("[邮件] " + content);}
}
class WeComChannel implements SendChannel {
public void send(String content) { System.out.println("[企业微信] " + content);}
}

// 抽象维：消息类型，构造时注入一个渠道（这就是"桥"）
abstract class Message {
protected final SendChannel channel;

protected Message(SendChannel channel) { this.channel = channel;}

abstract void notify(String text);
}

class NormalMessage extends Message {
NormalMessage(SendChannel c) { super(c);}
void notify(String text) { channel.send(text);}
}

class UrgentMessage extends Message {
UrgentMessage(SendChannel c) { super(c);}
void notify(String text) { channel.send("" + text + "（请立即处理）");}
}

public class BridgeDemo {
public static void main(String[] args) {
// 2 种消息 × 3 种渠道 = 6 种组合，只写了 5 个类；继承做法要 6 个子类且继续膨胀
new NormalMessage(new SmsChannel()).notify("明天开会");
new UrgentMessage(new SmsChannel()).notify("服务器宕机");
new UrgentMessage(new EmailChannel()).notify("服务器宕机");
new NormalMessage(new WeComChannel()).notify("周报已提交");
}
}
```

- 识别关键：两个维度「都独立在变」。只有一个维度变化时，普通继承或策略模式就够了。
- 桥的连接点是构造注入的组合引用；运行时甚至可以切换实现（给消息换渠道），继承做不到。
- 与策略模式的区别：策略是「一个算法可替换」，桥接是「两个维度正交组合」，别混。

## 适用场景与选型

- 用它：已经出现「A1B1、A1B2、A2B1、A2B2……」命名的类，或者两个维度都明确还会继续扩展——Demo 里消息类型还会加、渠道还会加，就是典型信号。
- 不用它：只有一个维度在变，普通继承或策略模式就够了；维度组合固定、未来不会扩展，硬拆两维只会多一层抽象白绕。
- 选型：先确认两个维度真的正交（改 A 维不影响 B 维的语义），再立桥；维度划分不清时宁可先不拆，等变化方向明朗了再重构出桥。
- 与策略模式的区别（一句话）：策略是「一个算法可替换」，桥接是「两个维度正交组合」——策略只有一个变化点，桥接有两个。

## 优缺点

- 优点：M 个抽象 × N 个实现只需 M + N 个类，继承做法要 M × N；加新维度成员只加一个类，不动已有代码；实现维可以在运行时切换（给消息换渠道），继承做不到。
- 缺点：结构比直接继承绕一层，新人理解成本高；抽象层增多后调试要多跳几层；维度划分错了，桥反而把简单问题复杂化。

## 常见误区

- 把一维问题拆成两维：其实只有一个维度在变，却硬抽出一个实现维。结果是多了一层接口和一次转发，扩展收益为零。动手前先问：两个维度是不是都独立在变。
- 桥的引用被绕过：抽象类里留了 `channel` 引用，但子类图省事直接 `new SmsChannel()` 写死。错：桥一旦被绕过，组合就退化成硬编码，运行时切换和独立扩展全没了。正确做法是渠道只从构造注入，子类只用 `channel` 引用。
- 把桥接当事后适配用：接口已经对不上了才想起桥接。错：桥接是设计期拆分维度的模式，事后对接是适配器的活；两者解决问题的时点不同，别混。

## 面试与自测

1. 桥接模式和策略模式的区别是什么？各举一个例子。
2. Demo 里 2 种消息 × 3 种渠道，为什么只写了 5 个类？继承做法要写几个？
3. 桥接的「桥」在 Demo 代码里具体是什么？它为什么能让实现维运行时切换？

### 参考答案

1. 策略是「一个算法可替换」，如支付方式选微信还是支付宝，只有一个变化点；桥接是「两个维度正交组合」，如消息类型 × 发送渠道，两个维度各自独立扩展。只有一个变化点时用策略，两个正交变化点时用桥接。
2. 抽象维 2 个类（NormalMessage、UrgentMessage）加实现维 3 个类（Sms/Email/WeComChannel）共 5 个，组合在运行时完成；继承做法要为每种组合写一个子类，2 × 3 = 6 个，且维度一扩展就继续膨胀。
3. 桥就是 Message 持有的 `SendChannel channel` 组合引用，由构造注入。因为抽象维只依赖渠道接口不依赖具体渠道，运行时传入不同的 Channel 实现就能切换，继承关系在编译期就定死了，做不到这一点。
