# 迭代器模式

## 模式介绍

**意图**：提供统一的遍历方式访问聚合对象的元素，不暴露其内部结构（数组、链表、树、分页数据源对客户端长一个样）。

**结构与角色**：
- Iterator（迭代器接口）：`hasNext()` / `next()`，可选 `remove()`。
- ConcreteIterator（具体迭代器）：持有聚合引用与游标位置，负责推进规则（顺序、逆序、按条件过滤、按页拉取）。
- Aggregate（聚合接口）：声明 `iterator()` 工厂方法。
- ConcreteAggregate（具体聚合）：内部结构私有，只通过迭代器对外供数。

**效果**：
- 优点：同一聚合可同时存在多个不同规则的迭代器；遍历算法与存储结构解耦，换存储（内存→数据库分页）调用方代码不动。
- 代价：简单数组遍历用迭代器是过度设计；懒加载迭代器在并发修改、资源释放上有坑（见 Demo 要点）。

**适用信号**：遍历规则不止一种（正序/倒序/过滤/跳过）；数据量大到要分页/流式拉取，不能一次全量加载；底层存储未来会换。

**落点**：
- JDK 的 `Iterator` / `Iterable` / Stream：Java 里现成可用，增强 for 本质就是迭代器语法糖。
- 数据库游标分页：按 id 游标翻页读大表（`WHERE id > ? ORDER BY id LIMIT ?`）就是迭代器的工程化，避免深分页 `LIMIT 1000000, 20` 的性能坑。
- 组合模式的树结构遍历：把树拍平成迭代器逐个输出。

## 模式 Demo

```java
import java.util.*;

// 聚合：订单仓库，内部用 List 存储(对外不暴露)
class OrderRepo implements Iterable<String> {
    private final List<String> orders = new ArrayList<>();
    void add(String order) { orders.add(order); }

    @Override
    public Iterator<String> iterator() {
        return new Itr();
    }

    // 具体迭代器：只返回已支付订单(过滤规则写在迭代器里)
    private class Itr implements Iterator<String> {
        private int cursor = 0;
        private int nextIdx = -1; // 预探到的下一个命中下标，-1 表示还没探

        private int probe(int from) {
            while (from < orders.size()) {
                if (orders.get(from).startsWith("PAID")) return from;
                from++;
            }
            return -1;
        }

        @Override
        public boolean hasNext() {
            if (nextIdx < 0) nextIdx = probe(cursor);
            return nextIdx >= 0;
        }

        @Override
        public String next() {
            if (!hasNext()) throw new NoSuchElementException();
            String val = orders.get(nextIdx);
            cursor = nextIdx + 1;
            nextIdx = -1;
            return val;
        }
    }

    // 逆序迭代器：同一聚合的第二种遍历规则
    Iterator<String> reverseIterator() {
        return new Iterator<>() {
            private int idx = orders.size() - 1;
            public boolean hasNext() { return idx >= 0; }
            public String next() {
                if (!hasNext()) throw new NoSuchElementException();
                return orders.get(idx--);
            }
        };
    }
}

public class IteratorDemo {
    public static void main(String[] args) {
        OrderRepo repo = new OrderRepo();
        repo.add("PAID-001");
        repo.add("UNPAID-002");
        repo.add("PAID-003");
        repo.add("CANCELLED-004");

        System.out.println("只遍历已支付:");
        for (String o : repo) System.out.println("  " + o); // 增强 for 走过滤迭代器

        System.out.println("逆序遍历全部:");
        Iterator<String> rev = repo.reverseIterator();
        while (rev.hasNext()) System.out.println("  " + rev.next());
    }
}
```

- **过滤迭代器的关键是「预探」**：`hasNext()` 要先探到下一个命中元素再回答，否则会出现 hasNext 为 true 但 next 拿不到值的错位；多次调用 hasNext 必须幂等，不能推进游标。
- **快速失败（fail-fast）**：JDK 的迭代器在遍历中检测到集合被并发修改会抛 `ConcurrentModificationException`，这是防呆不是并发保证；真要并发安全遍历，用快照（拷贝一份）或并发集合的弱一致性迭代器。
- **坑：分页迭代器别忘释放资源**。包着 ResultSet/文件流的迭代器遍历中断（break/异常）时游标不会自动关，必须 try-with-resources 或提供 close() 并在使用方兜底。

## 适用场景与选型

- 用：遍历规则不止一种（正序、倒序、过滤、跳过）；数据量大到要分页、流式拉取，不能一次全量加载；底层存储未来可能换（内存换数据库分页）。
- 不用：就是一次遍历简单数组，遍历逻辑固定且不会变；调用方本来就要直接操作集合本身（如随机访问、排序），迭代器包一层反而碍事。
- 与直接暴露内部集合的区别（只记一句）：直接暴露让调用方依赖内部结构（List 还是数组、什么顺序），换存储就得改调用方；迭代器把"怎么遍历"收进迭代器，调用方只认 hasNext/next，存储换了调用方不动。

## 优缺点

- 优点：遍历算法与存储结构解耦；同一聚合可同时存在多个不同规则的迭代器；支持延迟加载，数据不必一次全量进内存。
- 代价：简单场景是过度设计；懒加载迭代器在并发修改、资源释放上有坑；多一层抽象，调试时要多看一层游标状态。

## 常见误区

- 误区 1：hasNext 推进游标。错：hasNext 里直接移动 cursor 找下一个命中元素，调用方连调两次 hasNext 会跳过一个元素。正确：像 Demo 那样"预探"——先探到下一个命中下标存起来，hasNext 只回答、不推进，幂等。
- 误区 2：把 fail-fast 当并发保证。错：遍历中别的线程改了集合，以为 fail-fast 会保护数据正确性。正确：fail-fast 只是快速抛 ConcurrentModificationException 防呆，不是并发安全；真要并发遍历用快照拷贝或并发集合的弱一致性迭代器。
- 误区 3：包着资源的迭代器不释放。错：包着 ResultSet 或文件流的分页迭代器，遍历中 break 或抛异常后游标没关，连接泄漏。正确：提供 close() 并要求 try-with-resources，或在使用方兜底关闭。

## 面试与自测

1. 为什么过滤迭代器的 hasNext 必须"预探"？多次调用 hasNext 应该有什么性质？
2. fail-fast 抛 ConcurrentModificationException 意味着什么？它保证并发安全吗？
3. 大表翻页时，为什么游标分页（WHERE id > ?）比深分页（LIMIT 1000000, 20）好？

### 参考答案

1. 因为 hasNext 要回答"还有没有下一个命中元素"，不先探到它就无法回答；而且多次调用 hasNext 必须幂等——只回答、不推进游标，否则会跳过元素。
2. 意味着遍历过程中检测到集合被修改，快速失败提醒调用方"数据已变，结果不可信"；它不保证并发安全，只防呆，真并发场景要用快照或弱一致性迭代器。
3. 深分页的 offset 越大，数据库要扫描并丢弃的行越多，越往后越慢；游标分页按主键范围定位，每次只读一页，走索引，页数再深成本也基本稳定。
