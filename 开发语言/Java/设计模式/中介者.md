# 中介者模式

## 模式介绍

**意图**：用一个中介对象封装一组对象的交互，同事对象之间不直接互相引用，网状的多对多通信收拢为星型的「都跟中介说话」。

**结构与角色**：
- Mediator（中介接口）：声明同事之间的通信入口，如 `relay(from, event)`。
- ConcreteMediator（具体中介）：持有全部同事引用，集中实现协调规则（谁触发什么、通知谁、按什么顺序）。
- Colleague（同事类）：只持有中介引用，状态变化时上报中介，不直接调其他同事的方法。

**效果**：
- 优点：交互规则集中一处，改联动逻辑只改中介；同事类互相零感知，可独立复用、独立测试。
- 代价：中介容易膨胀成「上帝类」——所有规则都往里塞，最后比原来的网还难维护；多一层转发，调用链变长。

**适用信号**：一组对象之间互相调用成网状，改一个动一片；联动规则本身复杂且经常变（如表单字段联动：选了 A 显示 B、禁用 C、重算 D）。

**落点**：
- 聊天室服务器（成员只跟服务器说话）、航班塔台调度（飞机之间不直接协调）。
- MVC 里的 Controller、Spring 的 `DispatcherServlet`：请求协调的中介。
- 复杂表单/工作台 UI 的状态联动、微服务里的编排式 Saga 协调者。

## 模式 Demo

```java
import java.util.*;

// 中介接口：同事只通过它通信
interface ChatMediator {
    void register(User user);
    void relay(User from, String msg);
}

// 具体中介：聊天室，持有全部成员，负责转发规则
class ChatRoom implements ChatMediator {
    private final List<User> users = new ArrayList<>();

    @Override
    public void register(User user) {
        users.add(user);
        user.bind(this);
    }

    @Override
    public void relay(User from, String msg) {
        System.out.println("[聊天室] " + from.name() + " 说: " + msg);
        for (User u : users) {
            if (u != from) u.receive(from.name(), msg); // 广播给除发送者外的所有人
        }
    }
}

// 同事类：只认中介，不知道其他成员的存在
class User {
    private final String name;
    private ChatMediator mediator;
    User(String name) { this.name = name; }
    String name() { return name; }
    void bind(ChatMediator m) { this.mediator = m; }

    void send(String msg) { mediator.relay(this, msg); } // 不直接调别人的 receive
    void receive(String from, String msg) {
        System.out.println("  " + name + " 收到 " + from + " 的消息: " + msg);
    }
}

public class MediatorDemo {
    public static void main(String[] args) {
        ChatRoom room = new ChatRoom();
        User alice = new User("Alice");
        User bob = new User("Bob");
        User carol = new User("Carol");
        room.register(alice);
        room.register(bob);
        room.register(carol); // 新成员加入，不用改任何已有成员的代码

        alice.send("大家好，明天上线评审改到十点");
        bob.send("收到");
    }
}
```

- **中介和观察者的分界**：观察者是一对多的单向通知，订阅者之间互不感知；中介是多对多的双向协调，转发时带规则（过滤、改写、决定通知谁）。只是「状态变了通知大家」用观察者就够了。
- **防膨胀是第一要务**：中介只放「协调规则」，不放业务计算；规则多到分不清时，按事件类型拆多个中介或退回事件总线，别让中介长成第二个单体。
- **坑：同事类里偷藏直连**。只要有一处同事绕过中介直接调另一个同事，星型结构就破了，后续改规则必然漏改；code review 时把「同事之间的 import」当红线。

## 适用场景与选型

- 用：一组对象互相调用成网状，改一个动一片；联动规则本身复杂且经常变（表单字段联动、航班调度、多服务编排）。
- 不用：对象之间交互简单直接，一对一调用就能说清；只是"状态变了通知大家"，没有协调规则——那是观察者模式的地盘。
- 与观察者的区别（只记一句）：观察者是一对多的单向通知，订阅者之间互不感知；中介者是多对多的双向协调，转发时带规则（过滤、改写、决定通知谁）。

## 优缺点

- 优点：交互规则集中一处，改联动逻辑只改中介；同事类互相零感知，可独立复用、独立测试；网状通信收拢为星型，依赖关系一眼看清。
- 代价：中介容易膨胀成"上帝类"，所有规则都往里塞后比原来的网还难维护；多一层转发，调用链变长，定位问题要先进中介再分发。

## 常见误区

- 误区 1：同事偷藏直连。错：某个同事图省事绕过中介直接调另一个同事的方法，星型结构破了一个口子，后续改规则必然漏改。正确：把"同事之间的 import/引用"当作 code review 红线，一律走中介。
- 误区 2：把业务计算塞进中介。错：中介里既做协调又算折扣、做校验，规则和业务搅在一起。正确：中介只放协调规则（谁触发、通知谁、按什么顺序），业务计算留在同事或服务层。
- 误区 3：只有单向通知却上中介。错：A 状态变了要通知 B、C，没有任何协调规则，却建一个中介转发。正确：纯一对多通知用观察者，中介留给真正需要多对多协调的场合。

## 面试与自测

1. 中介者模式与观察者模式的分界线在哪里？
2. 中介者膨胀成"上帝类"时，有哪两种拆法？
3. MVC 里的 Controller 为什么可以看作中介者？

### 参考答案

1. 有没有协调规则：只是"状态变了通知大家"用观察者；需要多对多双向协调、转发时带过滤、改写、决定通知谁等规则时用中介者。
2. 按事件类型拆多个中介，各管一类协调；或者退回事件总线，让同事通过事件解耦，中介不再集中所有规则。
3. View 和 Model 不直接互相调用，都通过 Controller 协调：View 的输入交给 Controller，Controller 调 Model、再把结果推回 View，交互规则集中在 Controller 一处，符合星型结构。
