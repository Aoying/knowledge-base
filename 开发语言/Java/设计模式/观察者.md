# 观察者模式

## 模式介绍

**意图**：定义对象间一对多的依赖：被观察者状态变化时，自动通知所有订阅它的观察者，发布方不需要知道订阅者是谁、拿到通知做什么。

**结构与角色**：
- Subject（主题/被观察者）：维护订阅列表，提供 attach/detach/notify。
- Observer（观察者接口）：只声明一个更新方法，如 `update(event)`。
- ConcreteObserver（具体观察者）：短信、邮件、积分、日志等各自独立的实现，互不知情。

**效果**：
- 优点：发布与订阅彻底解耦，新增一种通知动作只加一个观察者类，不改发布方；订阅关系运行时可动态增减。
- 代价：通知顺序与失败隔离要自己管（一个观察者抛异常不能拖垮其他人）；链式触发容易失控（A 通知里改 B、B 又通知回 A）；异步化后排查顺序问题更难。

**适用信号**：一个事件要触发多个互相独立的后续动作（下单成功→发短信+加积分+记日志+推消息）；后续动作还会持续增加；发布方不应感知订阅方细节。

**落点**：
- Spring 的 `ApplicationEvent` + `@EventListener`：框架内置的观察者实现，业务里优先用它别手写。
- MQ 的发布-订阅：观察者的分布式版，一条事件扇出到多个消费组。
- GUI 事件监听、配置中心变更通知、缓存失效广播。

## 模式 Demo

```java
import java.util.*;

// 观察者接口：只关心"订单已支付"这个事件
interface OrderObserver {
    void onPaid(String orderId, int amount);
}

// 主题：订单服务，状态变化时通知全部订阅者
class OrderService {
    private final List<OrderObserver> observers = new ArrayList<>();

    void attach(OrderObserver o) { observers.add(o); }
    void detach(OrderObserver o) { observers.remove(o); }

    void pay(String orderId, int amount) {
        System.out.println("订单 " + orderId + " 支付成功: " + amount + " 元");
        for (OrderObserver o : observers) { // 只认接口，不认具体是谁
            try {
                o.onPaid(orderId, amount);
            } catch (Exception e) { // 单个订阅者失败不影响其他订阅者
                System.out.println("  某订阅者处理失败(已隔离): " + e.getMessage());
            }
        }
    }
}

// 具体观察者们：彼此独立，互不知情
class SmsObserver implements OrderObserver {
    public void onPaid(String orderId, int amount) {
        System.out.println("  [短信] 已发送支付成功通知: " + orderId);
    }
}

class PointObserver implements OrderObserver {
    public void onPaid(String orderId, int amount) {
        System.out.println("  [积分] 增加积分: " + amount / 10);
    }
}

class LogObserver implements OrderObserver {
    public void onPaid(String orderId, int amount) {
        System.out.println("  [日志] 落库: order=" + orderId + ", amount=" + amount);
    }
}

public class ObserverDemo {
    public static void main(String[] args) {
        OrderService orders = new OrderService();
        orders.attach(new SmsObserver());
        orders.attach(new PointObserver());
        orders.attach(new LogObserver()); // 加新动作只加一行 attach，支付代码零改动

        orders.pay("ORD-1001", 299);
    }
}
```

- **发布方零感知是核心收益**：pay() 里没有一行 if 判断「要不要发短信」，新增/下线通知动作全在 attach/detach 层完成，这就是与「在业务方法里顺手都调一遍」拉开差距的地方。
- **失败隔离与通知顺序要显式设计**：同步通知时单个观察者抛异常会中断整条链（Demo 里逐个 try-catch 隔离）；顺序有依赖的观察者别用观察者，改责任链或显式编排。
- **坑：内存泄漏来自忘了 detach**。长生命周期 Subject 持有短生命周期 Observer 引用，订阅者用完不取消订阅就永远被通知、也无法被 GC；框架实现（如 Spring 事件）无此问题，手写时必须成对提供取消订阅入口。

## 适用场景与选型

- 用它：一个事件要触发多个互相独立的后续动作（下单成功→发短信 + 加积分 + 记日志 + 推消息），后续动作还会持续增加，发布方不应感知订阅方细节；订阅关系运行时可动态增减。
- 不用它：观察者之间有顺序依赖（必须先 A 再 B），观察者不保证顺序，硬用只会埋下时序 bug；需要可靠投递、跨进程扇出，那是 MQ 发布-订阅的活，不是进程内观察者的活。
- 选型：同步通知简单但发布方要等所有观察者跑完，适合轻量动作；观察者里有耗时或易失败的动作时，改异步事件或 MQ，别让一次下单被一条短信拖垮。能用框架内置实现（Spring ApplicationEvent）就别手写。
- 与中介者的区别（一句话）：观察者是「一对多单向广播」，发布方只管通知；中介者是「多对多对等协调」，多个对象互相调用都要经过中心协调，方向和对等性都不同。

## 优缺点

- 优点：发布与订阅彻底解耦，新增一种通知动作只加一个观察者类，不改发布方；订阅关系运行时可动态增减，下线一个动作就是一行 detach。
- 缺点：通知顺序不确定，有顺序依赖的观察者不能用它；单个观察者失败会拖垮整条链，失败隔离要自己做；链式触发容易失控（A 的通知里改 B、B 又通知回 A）；异步化后排查顺序问题更难。

## 常见误区

- 忘了 detach 导致内存泄漏：长生命周期 Subject 持有短生命周期 Observer 引用，订阅者用完不取消订阅，就永远被通知、也无法被 GC。正确做法是 attach/detach 成对提供，订阅者的生命周期结束处必须有对应的 detach。
- 观察者抛异常拖垮整条链：同步通知时第一个观察者一抛异常，后面的观察者全收不到通知。正确做法是像 Demo 这样逐个 try-catch 隔离，单个订阅者失败只记日志，不中断其他订阅者。
- 在通知里改主题状态引发重入：观察者的 onPaid 里又调了会触发新一轮 notify 的方法，通知套通知，轻则重复通知、重则循环触发。正确做法是观察者只做自己的后续动作，不反向改主题状态；需要联动的走显式编排，别藏在通知链里。

## 小技巧与冷知识

【小技巧】通知时先把订阅列表快照一份再遍历，别直接遍历原列表：观察者在回调里又调了 attach/detach，正在遍历的列表会被改，轻则漏通知、重则抛 ConcurrentModificationException。正确做法是通知前 `new ArrayList<>(observers)` 拷一份快照再循环，快照里多一个少一个都是上一轮注册的结果，这一轮通知的集合是确定的；原文 Demo 用 ArrayList 直接遍历，生产里要先快照。

【小技巧】推模型和拉模型二选一，别混着用：推模型是 notify 时把事件对象整个塞给观察者，观察者拿到就能用；拉模型是只发一个“变了”的信号，观察者自己回主题查最新状态。推模型省一次回查、事件对象就是契约，拉模型少传数据、但主题要多暴露读状态的接口；一个主题里有的观察者靠推、有的靠拉，契约很快就乱了，选一种写进接口注释。

【小技巧】订阅列表用 CopyOnWriteArrayList，遍历时不用加锁：订阅关系不常变、通知很频繁的场景，写时复制、读时无锁正好对上——attach/detach 偶尔拷一次数组，notify 每次都是无锁快照遍历。反过来订阅关系频繁变动时别用它，每次 attach 都复制整个数组，写得多反而比 ArrayList 加锁更贵；选集合先看读写比。

【小技巧】观察者里别做耗时 IO，耗时动作要转异步：短信、推送、调第三方接口这些动作放在同步通知里，发布方要等它们全部跑完，一次下单被一条短信拖垮就是这么来的。正确分工是同步通知只做“轻量动作”（记日志、改内存状态），耗时动作交给异步事件或消息队列；原文选型里“有耗时动作改异步”这条，落点就是把耗时观察者从同步链里摘出去。

【小技巧】多个观察者共享的事件对象要做成不可变：notify 时同一个事件对象被依次传给短信、积分、日志三个观察者，某一个观察者改了事件里的字段，后面的观察者读到的就是改过的值。事件类字段全 final、构造时一次定死，谁也改不了谁的输入；事件对象可变，观察者之间就多了一条看不见的数据通道。

【小技巧】同一个观察者重复 attach 会收到两次通知：attach 时不查重，同一个对象注册两次，notify 循环里它会出现两遍，短信发两条、积分加两次。attach 里先判 `contains`，或者订阅列表直接用 Set 存；下线时 detach 一次也要清干净，重复注册的坑和忘了 detach 的坑是一对——一个多通知、一个漏下线。

【小技巧】先改状态、再发通知，顺序别反：主题的状态还没改完就 notify，观察者回调里回头查主题状态，读到的还是旧值。`pay()` 里“先记账、再通知”就是这条的落地——状态变化和通知是成对的，通知是“状态已变”的宣告，不是“状态要变”的预告；顺序反了，观察者拿到的事件和主题的真实状态就对不上了。

【小技巧】异步通知的测试别用 sleep 固定等几秒：观察者在别的线程跑，测试里 `Thread.sleep(1000)` 再断言，机器一慢就 flaky、一快又浪费时间。用 `CountDownLatch` 让观察者回调里 countDown，测试主线程 await 带超时等它，通知到了立刻继续、超时了才算失败；异步测试的等待要靠同步原语，不靠猜时间。

【小技巧】给观察者配独立的线程池，别和发布方的业务线程池共用：异步通知的观察者跑在业务线程池里，观察者一慢，业务线程也被占满，下单接口跟着变慢。通知线程池单独建、单独配队列和拒绝策略，观察者再慢也只堵自己的池；原文“异步化后排查更难”之外，线程池隔离是异步通知先要补的一课。

【冷知识】GoF 原书讲观察者用的例子是电子表格：一个单元格的值变了，依赖它的公式单元格要自动重算，单元格之间就是一对多的订阅关系。MVC 里的 Model-View 也是同一结构——Model 变了，所有 View 自动刷新；下单通知短信只是这个例子的业务版，样板间本来是表格和界面。

【冷知识】JDK 自带的 `java.util.Observable` 和 `Observer` 在 Java 9 就被废弃了：官方认为它设计有问题（Observable 是类不是接口、setChanged 必须手动调），废弃后推荐用 `java.beans.PropertyChangeListener` 或自己写接口。它是少数被 JDK 正式废弃的基础类之一——手写观察者时别再继承它，看到老代码里它出现就知道那是 Java 9 之前的写法。

【冷知识】RxJava、Reactor 这类响应式库的订阅，本质是观察者的异步拉取版：订阅者订阅一个数据流，发布者有数据就推过来，和观察者是一套骨架；多出来的东西是背压——订阅者可以告诉发布者“我处理不过来、慢点推”，而经典观察者只能被动接。理解了这层关系，看响应式代码就不再陌生：它只是在观察者上加了流量控制。

## 面试与自测

1. 观察者模式和 MQ 的发布-订阅是什么关系？什么时候该从观察者升级到 MQ？
2. 同步通知时，单个观察者抛异常会有什么后果？Demo 里是怎么处理的？
3. 观察者之间有顺序依赖时为什么不能用观察者模式？应该改成什么？

### 参考答案

1. MQ 发布-订阅是观察者的分布式版：一条事件扇出到多个消费组，跨进程、带持久化和重试。进程内、动作轻量、丢通知可接受时用观察者；需要跨进程、可靠投递、削峰填谷时升级到 MQ。
2. 同步通知是顺序循环调用，第一个观察者抛异常会中断整条链，后面的观察者全收不到通知。Demo 里在循环内逐个 try-catch，单个订阅者失败只打印日志隔离，不中断其他订阅者。
3. 因为观察者模式不保证通知顺序，依赖顺序的观察者会在时序上埋下不确定的 bug。应该改成责任链（顺序显式）或显式编排（在业务方法里按顺序调），把顺序写进代码而不是依赖通知的到达次序。
