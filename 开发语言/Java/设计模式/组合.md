# 组合模式

## 模式介绍

**意图**：把对象组织成树形结构，客户端对「单个对象」和「对象组合」用同一套 API 处理，不用每次判断节点是叶子还是容器。

**结构与角色**：

- 抽象组件（Component）：统一接口，声明叶子和容器共有操作（如统计、打印）。
- 叶子（Leaf）：没有子节点的节点，实现接口，递归到此为止。
- 容器（Composite）：持有子组件列表，自己的操作 = 对子节点逐个调用再汇总。

**效果**：

- 优点：遍历、统计、渲染一棵树只需一份递归代码；新增节点类型不影响客户端。
- 代价：接口里被迫塞进「加子节点」这类只对容器有意义的方法，叶子实现只能空转或抛异常（透明式组合的固有代价）。

**适用信号**：

- 数据天然是树：组织架构、部门、菜单权限、文件目录、商品分类。
- 业务表里出现 `parentId` 字段，需求是「查整棵子树/汇总整棵树」——本质就是组合结构。

**落点**：组织树/父子事项（督办事项的父子任务汇总进度）；前端菜单与权限树；报表里的多级分组汇总；XML/DOM 文档树、AST 语法树；Swing/JavaFX 的组件树。

## 模式 Demo

```java
import java.util.ArrayList;
import java.util.List;

// 抽象组件：叶子（员工）和容器（部门）实现同一接口
abstract class OrgNode {
    protected final String name;

    protected OrgNode(String name) { this.name = name; }

    abstract int headCount();          // 统计人数：叶子返回 1，部门返回子树合计
    abstract void print(String indent); // 打印整棵树
}

class Employee extends OrgNode {
    Employee(String name) { super(name); }
    int headCount() { return 1; }
    void print(String indent) { System.out.println(indent + "- " + name); }
}

class Department extends OrgNode {
    private final List<OrgNode> children = new ArrayList<>();

    Department(String name) { super(name); }

    void add(OrgNode node) { children.add(node); } // 只有容器有 add，这就是 parentId 的内存版

    int headCount() {
        int sum = 0;
        for (OrgNode c : children) sum += c.headCount(); // 不关心子节点是人还是部门
        return sum;
    }

    void print(String indent) {
        System.out.println(indent + "+ " + name + "（" + headCount() + "人）");
        for (OrgNode c : children) c.print(indent + "  ");
    }
}

public class CompositeDemo {
    public static void main(String[] args) {
        Department company = new Department("总公司");
        Department rd = new Department("研发部");
        rd.add(new Employee("张三"));
        rd.add(new Employee("李四"));
        Department sub = new Department("后端组");
        sub.add(new Employee("王五"));
        rd.add(sub); // 部门里再套部门，客户端代码不用变
        company.add(rd);
        company.add(new Employee("前台小赵"));

        company.print("");
        System.out.println("总人数：" + company.headCount()); // 4
    }
}
```

- 数据库里用 parentId 存树、内存里用组合模式处理树，是同一结构的两种形态：查出来组装成 Composite，统计/渲染/校验都走递归。
- 坑：建树时不校验成环（A 的父是 B、B 的父又是 A），递归直接爆栈；入库和组装时都要防环。
- 汇总类需求（人数、金额、进度）最适合组合：一行递归聚合。父事项进度 = 子事项加权平均，就是这个套路。

## 适用场景与选型

- 用它：数据天然是树（组织架构、菜单权限、文件目录、商品分类、父子事项），且客户端要对整棵树做统一操作——统计、渲染、校验、汇总，典型如 Demo 里 `headCount()` 的递归聚合。
- 不用它：结构基本扁平、很少嵌套，硬套组合只会多一层抽象；叶子和容器的操作差异极大，统一接口会逼叶子实现一堆无意义的方法，接口失真比收益大。
- 选型：透明式（add 等方法放进统一接口）让客户端代码最简单，但叶子要为无意义的方法空转或抛异常；安全式（add 只放容器类）接口干净，但客户端又要区分叶子和容器。按客户端统一处理的收益是否大于叶子接口失真的代价来选。
- 与装饰器的区别（一句话）：组合处理的是「整体与部分用同一接口」，目的是统一对待一棵树；装饰器是给单个对象叠加功能，目的是功能组合，两者结构都像树但意图不同。

## 优缺点

- 优点：遍历、统计、渲染一棵树只需一份递归代码，客户端不用判断节点是叶子还是容器；新增节点类型不影响客户端，符合开闭原则。
- 优点：汇总类需求天然契合——父事项进度、部门人数、分类金额都是一行递归聚合。
- 缺点：透明式下叶子接口失真（Employee 也得有个 add 方法）；安全式下客户端又要做类型判断，统一性打折。
- 缺点：递归深度和成环是固有风险，树很深时递归可能爆栈，建树不防环时递归直接死循环。

## 常见误区

- 建树不防环：A 的父是 B、B 的父又是 A，`headCount()` 递归永不终止直接爆栈。正确做法是入库和组装时都校验（组装时沿父链向上检查，或用访问集合判重），不能只依赖「数据应该没问题」。
- 叶子对 add 的处理前后不一致：有的叶子 add 空转、有的抛异常，客户端行为变得不可预测。正确做法是全组统一约定一种（推荐抛 UnsupportedOperationException 并写进接口注释），不要两种混用。
- 在容器里缓存汇总值却不失效：Department 缓存了 headCount，子节点增减后缓存没更新，统计结果悄悄变旧。正确做法要么像 Demo 这样每次现算，要么在 add/remove 时显式使缓存失效并写单测覆盖。

## 小技巧与冷知识

【小技巧】扁平记录组装成树要用“先建 map、再挂子节点”的两遍写法：第一遍把所有节点按 id 放进 Map，第二遍遍历记录、按 parentId 把子节点挂到父节点上，整体是 O(n)。别在循环里逐条按 parentId 查父节点再挂，数据量一上来就是 O(n²)；组装代码的复杂度不在递归，在这一遍挂接上。

【小技巧】树很深时把递归改成显式栈的迭代遍历：递归的深度受线程栈大小限制，默认栈只有几百 KB 到 1MB，树深到几千上万层就容易爆栈。用一个显式栈（Deque）自己模拟“进节点、处理子节点、出节点”的过程，深度只受堆内存限制；递归写起来短，迭代兜得住深度，生产里的深树优先用迭代。

【小技巧】聚合类操作要按后序遍历写——先算子节点、再汇总父节点：headCount、金额合计、进度加权平均，都是“子节点的值先出来，父节点再汇总”。在进入节点时就汇总、或在子节点还没算完就读父节点的值，拿到的是半成品；递归函数里先循环子节点、再用子节点结果算自己，这条顺序写死了就不会错。

【小技巧】叶子对无意义方法的处理要全组统一成抛 `UnsupportedOperationException`：这就是 JDK 自己的惯例，不可变集合（`Collections.unmodifiableList`）对 add 就是这么做的——接口上有方法、调用时直接抛异常。空转和抛异常混用时客户端行为不可预测，统一抛异常并把约定写进接口注释，调用方一调就知道“这个节点不支持这个操作”。

【小技巧】容器 remove 子节点时，顺手把子节点的父引用断开：只从 children 列表里删掉子节点，子节点自己的 parent 指针还指着旧父节点，后续沿父链向上走会走到一个已经不存在的父节点上。remove 时把子节点的 parent 置 null，双向引用要双向维护，单向删是树结构里最常见的残留引用来源。

【小技巧】查整棵子树别在数据库里递归查，一次查出所有节点再内存组装：按 parentId 逐层查数据库是 N+1 查询，树越深查询次数越多。做法是按根节点一次查出子树全部扁平记录（按 parentId 过滤或整表拉取后过滤），再用“先建 map、再挂子节点”在内存里拼成 Composite；数据库只负责一次批量取数，遍历和汇总是内存里的事。

【小技巧】遍历、统计、校验别全塞进组件类，配一个访问者：组合模式常和访问者模式结伴——组件只负责接受访问（accept），统计人数、打印、校验规则各写一个 Visitor。新增一种遍历逻辑时只加一个访问者，不用改叶子和容器的类；组件类每加一个操作就改一次，类很快就被各种操作撑大。

【小技巧】查祖先链要沿 parentId 向上走、并用集合判重防环：从某个节点找它所有的上级（部门的上级部门、事项的父事项），循环里每走一步把节点 id 记进 Set，遇到已见过的 id 立刻停下——环数据下不判重就是死循环。数据库层也可以用递归 CTE（MySQL 8.0+ 的 `WITH RECURSIVE`）一次查出整条祖先链，不用在代码里逐层向上查。

【小技巧】打印或排障时给树加缩进和节点类型标记：叶子前面打 `-`、容器前面打 `+`，再按深度缩进（原文 Demo 的 print 就是这个写法），一眼就能看出哪层是部门、哪层是人。线上排障要看一棵几百个节点的树时，先把它按这个格式打出来，结构问题（挂错父节点、层级少一层）比对着 parentId 表查直观得多。

【冷知识】GoF 原书讲组合模式用的例子是图形编辑器：一个图形可以包含其他图形（图形组里套图形、图形里再套图形组），叶子是矩形、圆形这些基本图形，容器是图形组。Swing/JavaFX 的组件树、DOM 树都是这个例子的后代——“界面组件嵌套”这个场景，从 GoF 写书时就是组合模式的样板间。

【冷知识】组合模式在 GoF 的 23 种模式里属于结构型模式：它和适配器、装饰器、外观同组，解决的都是“类和对象怎么组合成更大结构”的问题。组合的特别之处在于它是结构型里唯一讲“整体与部分用同一接口”的一个——别的结构型模式多在包一层，组合是在把“一棵树”压平成一个接口。

【冷知识】DOM 树就是组合模式的现实版：DOM 里的 Node 是抽象组件，Element 是容器（能挂子节点），Text 是叶子（没有子节点），`getChildNodes()`、`appendChild()` 这些方法对单个节点和整棵子树用的是同一套接口。前端操作 DOM 时“对一个节点调用的方法、对一棵子树同样能调”，用的就是组合模式的统一接口思想。

## 面试与自测

1. 透明式组合和安全式组合的区别是什么，各自的代价是什么？
2. 数据库里 parentId 存树、内存里组合模式处理树，两者是什么关系？查出数据后通常要做什么？
3. Demo 里 Department 的 headCount() 为什么每次现算，而不是缓存起来？

### 参考答案

1. 透明式把 add 等容器方法放进统一接口，客户端最简单，但叶子要为无意义的方法空转或抛异常，接口失真；安全式把 add 只放容器类，接口干净，但客户端需要区分叶子和容器，统一性打折。
2. 是同一结构的两种形态：parentId 是树的存储形态，组合模式是树的内存处理形态；查出扁平记录后要按 parentId 组装成 Composite（先建节点 map，再把子节点挂到父节点上），统计、渲染、校验都走递归。
3. 因为子节点随时可能增减，缓存的汇总值会在变化后失效，统计结果悄悄变旧；每次现算虽然多花遍历成本，但结果永远正确。数据量大到现算成为瓶颈时，才改为缓存加显式失效，并用单测覆盖 add/remove 后的统计。
