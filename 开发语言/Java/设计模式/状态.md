# 状态模式

## 模式介绍

**意图**：让对象在内部状态改变时自动改变行为。把「每个状态下能做什么、做完去哪个状态」封装进独立的状态类，消灭主类里按状态分支的大 if-else / switch。

**结构与角色**：

- `Context`（上下文）：持有当前状态对象，把请求委托给它；状态切换时替换引用。
- `State`（状态接口）：声明每个状态下允许的操作。
- `ConcreteState`（具体状态）：实现本状态的操作逻辑，并在操作完成后决定下一个状态（回写给 Context）。

**效果**：

- 优点：新增状态只加一个类，不改已有状态；每个状态的行为内聚在一处；非法操作在状态类里直接拒绝，规则显性化。
- 代价：状态多时类数量膨胀；状态流转关系分散在各状态类里，全局流转图不如集中式状态表直观，需要靠注释或文档补一张流转图。

**适用信号**：

- 对象行为明显依赖状态，且状态超过 3 个、转换关系复杂。
- 同一个操作在不同状态下语义完全不同（如订单的 `pay()`：待支付可付、已支付应拒绝、已取消应报错）。
- 代码里反复出现 `if (status == X)` 判断同一字段。

**落点**：

- 订单状态机：待支付 → 已支付 → 已发货 → 已完成 / 已取消，每个状态定义 pay/ship/cancel 的合法性。
- Flowable 流程节点状态：任务待办、已办、驳回、挂起，本质都是状态约束下的操作集合。
- 连接与会话生命周期：未连接、已连接、已关闭各自能调用的方法不同。

**状态 vs 策略（最易混淆）**：策略由**调用方从外部选**算法，选完通常不再变；状态由**对象内部流转**决定下一步，调用方甚至不关心当前是什么状态，只管发操作。判断口诀：谁决定切换——外部选是策略，内部流转是状态。

## 模式 Demo

```java
// 订单状态机：状态决定 pay/cancel 的合法性，操作完成后状态自动流转
interface OrderState {
    void pay(Order ctx);
    void cancel(Order ctx);
    String name();
}

class Order {
    private OrderState state = new Unpaid();        // 初始状态：待支付
    void setState(OrderState s) { this.state = s; }
    void pay()    { state.pay(this); }              // 委托给当前状态
    void cancel() { state.cancel(this); }
    String status() { return state.name(); }
}

class Unpaid implements OrderState {
    public void pay(Order ctx) {
        System.out.println("支付成功");
        ctx.setState(new Paid());                   // 流转：待支付 -> 已支付
    }
    public void cancel(Order ctx) {
        System.out.println("订单已取消");
        ctx.setState(new Cancelled());
    }
    public String name() { return "待支付"; }
}

class Paid implements OrderState {
    public void pay(Order ctx) {
        throw new IllegalStateException("已支付，不能重复支付");  // 本状态下非法
    }
    public void cancel(Order ctx) {
        System.out.println("已支付订单取消，走退款流程");
        ctx.setState(new Cancelled());
    }
    public String name() { return "已支付"; }
}

class Cancelled implements OrderState {
    public void pay(Order ctx)    { throw new IllegalStateException("已取消订单不能支付"); }
    public void cancel(Order ctx) { throw new IllegalStateException("已取消，不能重复取消"); }
    public String name() { return "已取消"; }
}

public class StateDemo {
    public static void main(String[] args) {
        Order o = new Order();
        o.pay();                                    // 支付成功
        System.out.println("当前状态：" + o.status()); // 已支付
        o.cancel();                                 // 退款取消
        System.out.println("当前状态：" + o.status()); // 已取消
    }
}
```

- 状态类只管「本状态的规则 + 下一个状态」，Order 主类没有任何状态判断分支，新增「已发货」状态只需加一个类并在 Paid 里多一个流转入口。
- 非法操作在状态类里直接抛异常，比在主类里层层校验更靠近规则本身；生产代码建议把状态持久化为枚举字段，状态对象用无状态单例共享，别每单 new 一套。
- 坑：状态流转关系分散后排查困难，复杂状态机建议先画流转图（或用表格列清 状态×操作→结果），再照图写类。
