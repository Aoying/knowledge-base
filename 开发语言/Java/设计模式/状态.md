# 状态模式

## 模式介绍

**意图**：让对象在内部状态改变时自动改变行为。把「每个状态下能做什么、做完去哪个状态」封装进独立的状态类，消灭主类里按状态分支的大 if-else / switch。

**结构与角色**：

- `Context`（上下文）：持有当前状态对象，把请求委托给它；状态切换时替换引用。
- `State`（状态接口）：声明每个状态下允许的操作。
- `ConcreteState`（具体状态）：实现本状态的操作逻辑，并在操作完成后决定下一个状态（回写给 Context）。

**效果**：

- 优点：新增状态只加一个类，不改已有状态；每个状态的行为内聚在一处；非法操作在状态类里直接拒绝，规则显性化。
- 代价：状态多时类数量膨胀；状态流转关系分散在各状态类里，全局流转图不如集中式状态表直观，需要靠注释或文档补一张流转图。

**适用信号**：

- 对象行为明显依赖状态，且状态超过 3 个、转换关系复杂。
- 同一个操作在不同状态下语义完全不同（如订单的 `pay()`：待支付可付、已支付应拒绝、已取消应报错）。
- 代码里反复出现 `if (status == X)` 判断同一字段。

**落点**：

- 订单状态机：待支付 → 已支付 → 已发货 → 已完成 / 已取消，每个状态定义 pay/ship/cancel 的合法性。
- Flowable 流程节点状态：任务待办、已办、驳回、挂起，本质都是状态约束下的操作集合。
- 连接与会话生命周期：未连接、已连接、已关闭各自能调用的方法不同。

**状态 vs 策略（最易混淆）**：策略由**调用方从外部选**算法，选完通常不再变；状态由**对象内部流转**决定下一步，调用方甚至不关心当前是什么状态，只管发操作。判断口诀：谁决定切换——外部选是策略，内部流转是状态。

## 模式 Demo

```java
// 订单状态机：状态决定 pay/cancel 的合法性，操作完成后状态自动流转
interface OrderState {
    void pay(Order ctx);
    void cancel(Order ctx);
    String name();
}

class Order {
    private OrderState state = new Unpaid();        // 初始状态：待支付
    void setState(OrderState s) { this.state = s; }
    void pay()    { state.pay(this); }              // 委托给当前状态
    void cancel() { state.cancel(this); }
    String status() { return state.name(); }
}

class Unpaid implements OrderState {
    public void pay(Order ctx) {
        System.out.println("支付成功");
        ctx.setState(new Paid());                   // 流转：待支付 -> 已支付
    }
    public void cancel(Order ctx) {
        System.out.println("订单已取消");
        ctx.setState(new Cancelled());
    }
    public String name() { return "待支付"; }
}

class Paid implements OrderState {
    public void pay(Order ctx) {
        throw new IllegalStateException("已支付，不能重复支付");  // 本状态下非法
    }
    public void cancel(Order ctx) {
        System.out.println("已支付订单取消，走退款流程");
        ctx.setState(new Cancelled());
    }
    public String name() { return "已支付"; }
}

class Cancelled implements OrderState {
    public void pay(Order ctx)    { throw new IllegalStateException("已取消订单不能支付"); }
    public void cancel(Order ctx) { throw new IllegalStateException("已取消，不能重复取消"); }
    public String name() { return "已取消"; }
}

public class StateDemo {
    public static void main(String[] args) {
        Order o = new Order();
        o.pay();                                    // 支付成功
        System.out.println("当前状态：" + o.status()); // 已支付
        o.cancel();                                 // 退款取消
        System.out.println("当前状态：" + o.status()); // 已取消
    }
}
```

- 状态类只管「本状态的规则 + 下一个状态」，Order 主类没有任何状态判断分支，新增「已发货」状态只需加一个类并在 Paid 里多一个流转入口。
- 非法操作在状态类里直接抛异常，比在主类里层层校验更靠近规则本身；生产代码建议把状态持久化为枚举字段，状态对象用无状态单例共享，别每单 new 一套。
- 坑：状态流转关系分散后排查困难，复杂状态机建议先画流转图（或用表格列清 状态×操作→结果），再照图写类。

## 适用场景与选型

- 用它：状态在 3 个以上、转换关系复杂；同一个操作在不同状态下语义完全不同；代码里反复出现 `if (status == X)` 判断同一字段。
- 不用它：只有 2 个状态且转换简单，if 或枚举 + switch 更轻；流转关系需要集中审计、可视化或持久化审批（如审批流），状态表或工作流引擎比散落在各状态类的流转更合适；状态只是数据标签、不影响任何行为时，别用模式，用枚举字段存着就行。
- 与策略的一句话区分：策略由调用方从外部选算法，状态由对象内部流转决定下一步——谁决定切换，是区分两者的唯一标准。

## 优缺点

- 优点：消灭主类里的状态分支；新增状态只加一个类，不改已有状态；每个状态的行为内聚在一处；非法操作在状态类里就近拒绝，规则显性化。
- 缺点：状态多时类数量膨胀；流转关系分散在各状态类里，全局流转图不如集中式状态表直观；状态间共享逻辑要抽公共父类或组合，否则重复；状态对象如果带可变状态又被共享，会串数据（Demo 建议无状态单例正是为此）。

## 常见误区

- Context 里又写状态判断：`Order.pay()` 里先 `if (state instanceof Paid)` 再分支，等于没用模式。正确：调用方只发操作，分支只存在于状态类内部，或者根本不存在——Demo 的 `Order.pay()` 只有一行委托。
- 流转逻辑写在 Context 的业务方法里：状态切换由主类决定，状态类退化成行为袋。正确：状态类在操作完成后自己 `ctx.setState(下一个)`，流转权归状态。
- 终态漏拦截：已取消是终态，新增一个操作（如 `ship()`）时忘了在 Cancelled 里拒绝，已取消订单就继续流转了。正确：终态的每个方法都显式拒绝，新增操作时先补终态——Demo 的 Cancelled 三个方法全是拒绝，就是范本。

## 小技巧与冷知识

【小技巧】状态切换时给 Context 的 `setState` 留一个钩子：切换前后记一条带旧状态、新状态、触发操作的日志，或发一个状态变更事件。流转关系分散在各状态类里，线上排障时靠日志才能把“订单怎么从待支付走到已取消”还原出来；只在状态类里 setState、不留痕，事后连哪一步跳错了都查不到。

【小技巧】状态对象里别直接 `new` 下一个状态：`ctx.setState(new Paid())` 把流转目标写死在状态类里，测试想换一个假状态、想统计流转次数都插不进去。下一个状态从工厂或注册表里取，状态类只说“要去 Paid”，由谁来建 Paid 交给 Context 或工厂——流转方向归状态，对象创建归工厂。

【小技巧】状态类要不要共享，看它有没有自己的可变字段：无状态的状态对象可以做成单例共享（原文 Demo 就是这个做法），一旦状态类里多了计数器、缓存、累计值，共享后多订单会互相串数据。判断标准就一条——状态对象只读 `ctx` 参数、不写自己的字段，才能共享；写了自己的字段，必须每单独立建。

【小技巧】终态别只靠“每个方法都拒绝”，给终态一个默认拒绝的基类：终态（已取消、已完成）的每个操作都要拒绝，新增一个操作时最容易漏补终态。写一个 `TerminalState` 抽象类，里面每个方法默认抛 `IllegalStateException`，终态只继承它、什么都不用写，新增操作时终态自动拒绝——漏拦截的口子从“靠记性”变成“靠继承”。

【小技巧】非法操作抛异常还是返回拒绝结果，看调用方是谁：内部代码调错了状态（比如已支付订单又调 pay），抛 `IllegalStateException` 是对的，这是程序 bug；前端用户点的按钮本就不该出现，接口层要返回“当前状态不可操作”的业务拒绝，而不是把异常堆栈抛给前端。同一个“不允许”，对内是异常、对外是可读的拒绝结果。

【小技巧】进入新状态和离开旧状态要各留一个钩子：`onExit()` 做清理（比如待支付离开时取消倒计时）、`onEntry()` 做初始化（比如进入已发货时发通知）。没有这两个钩子，状态切换的副作用只能散在各个操作的尾巴里，改一个状态的进入动作要翻所有能流转到它的地方；钩子把“切换时顺带做的事”收进状态类自己手里。

【小技巧】持久化只存状态枚举字段，别序列化状态对象：数据库里存 `status = 'PAID'`，恢复时按字段查表取对应的状态单例。状态对象本身可能带方法、带引用，序列化后版本一变就读不回来；枚举字段是稳定的契约，状态对象是运行时的解释器，两者分开，存档才不怕重构。

【小技巧】操作加流转不是原子的，并发下要加锁或乐观锁：两个线程同时对同一订单调 `pay()`，都看到待支付、都执行成功，订单会被支付两次。状态模式本身不管并发，`pay()` 到 `setState()` 这段要包进同一把锁，或者按“当前状态 + 版本号”做条件更新——模式解决了分支问题，没解决竞态问题。

【小技巧】枚举常量各自实现 State 接口，是最轻的状态模式：状态不到 5 个、每个状态行为简单时，不用写一堆状态类，`enum OrderStatus implements OrderState`，每个常量重写自己的 `pay/cancel`。枚举自带单例、天然可序列化、还能直接存库，类数量不膨胀；状态一多、行为一复杂，再拆回独立状态类。

【小技巧】测试状态机按“状态 × 操作”的表全量跑一遍：每个状态 × 每个操作一行，断言“合法流转到哪、非法抛什么错”，表有多少格、测试就有多少例。终态漏拦截、新增操作忘补旧状态，这类 bug 靠随机抽查抓不到，靠全量表才能兜底——这张表和原文说的流转图是同一张，写代码前先列出来。

【冷知识】GoF 原书讲状态模式用的例子是 TCP 连接：`TCPConnection` 的状态有 `Established`、`Listening`、`Closed`，`open()`、`close()`、`acknowledge()` 在不同状态下行为完全不同，收到报文后状态自己决定下一步。订单状态机和 TCP 连接是同一个结构——状态模式的样板间本来就是网络协议，不是电商订单。

【冷知识】状态模式和策略模式的类图几乎一模一样，GoF 自己在书里也承认这一点：两者都是 Context 持有一个接口引用、把请求委托出去，区别只在意图——策略是“调用方选算法”，状态是“对象内部流转”。结构相同、意图不同，这也是为什么只看类图分不清两者，必须问“谁决定切换”才能区分。

【冷知识】JDK 的 `Thread.State` 不是状态模式：线程的 NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED 是枚举值，JVM 内部用枚举加条件判断做流转，没有给每个状态配一个状态类。它走的是原文说的“集中式状态表”路线——状态少、流转要由 JVM 集中控制时，枚举加 switch 比状态模式更合适，JDK 自己就是这么选的。

## 面试与自测

1. 状态模式和策略模式的本质区别是什么？各举一个 Demo 之外的例子。
2. 为什么 Demo 建议状态对象用无状态单例共享？什么情况下不能共享？
3. 状态很多、流转很复杂时，状态模式的短板是什么？用什么办法补？

### 参考答案

1. 切换的决定权：策略由调用方从外部选，选完通常不再变（如支付方式选微信还是支付宝）；状态由对象内部流转决定，调用方不关心当前状态、只管发操作（如订单从待支付流转到已支付）。决定权在外是策略，在内是状态。
2. 状态对象本身不存数据、只存规则，共享无副作用且省内存；Demo 的 Unpaid/Paid/Cancelled 都只靠 `ctx` 参数办事。不能共享的情况：状态类自己持有可变字段（如某状态下的计数器、缓存），共享后多订单会互相串数据，这时必须每单独立建状态对象。
3. 短板是流转关系分散在各状态类里，没法一眼看清全局，排障和评审都困难。补法：先画流转图（或列一张 状态×操作→结果 的表）再照图写类，让图成为评审依据；状态多到一定规模时，改用集中式状态表或状态机框架。
