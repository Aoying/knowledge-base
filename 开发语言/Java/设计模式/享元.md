# 享元模式

## 模式介绍

**意图**：用共享换内存。当同类对象数量巨大、且大部分状态相同时，把不变的部分抽出来只存一份，所有实例共用。

**结构与角色**：

- 享元（Flyweight）：只持有内部状态（可共享、不随使用场景变的部分，如树的种类、颜色、贴图）。
- 享元工厂（FlyweightFactory）：按 key 缓存享元，保证同一 key 只建一个对象。
- 客户端：自己保存外部状态（随场景变的部分，如每棵树的坐标），调用时传给享元。

内/外状态的划分是享元成败的关键：划错了，要么共享不了，要么数据串味。

**效果**：

- 优点：对象数从「实例总数」降到「种类数」，百万级对象场景内存可差几个数量级。
- 代价：外部状态要到处传递，代码变啰嗦；享元必须不可变（或线程安全），否则一个调用方改状态全体遭殃。

**适用信号**：

- 对象数量以万/百万计，且逐个看状态高度重复（棋盘棋子、森林里的树、文档里的字符样式）。
- 内存或 GC 已经因为这类对象报警，而不是「感觉可能会多」。

**落点**：`Integer.valueOf` 的 -128~127 缓存、`String` 常量池（同一字面量只存一份）；数据库连接池/线程池是思想近亲（复用而非共享状态，严格说是对象池）；游戏中同种怪物/子弹的模型数据共享。

## 模式 Demo

```java
import java.util.HashMap;
import java.util.Map;

// 享元：树的"种类"——名称和颜色是内部状态，全森林同种树共用一份，不可变
class TreeType {
    private final String species;
    private final String color;

    TreeType(String species, String color) {
        this.species = species;
        this.color = color;
    }

    // 坐标是外部状态：不存享元里，由客户端在调用时传入
    void draw(int x, int y) {
        System.out.println("在 (" + x + "," + y + ") 画一棵 " + color + " 的 " + species);
    }
}

// 享元工厂：按 key 缓存，保证同种树全局只有一个 TreeType 对象
class TreeFactory {
    private static final Map<String, TreeType> CACHE = new HashMap<>();

    static TreeType get(String species, String color) {
        String key = species + "|" + color;
        return CACHE.computeIfAbsent(key, k -> new TreeType(species, color));
    }

    static int typeCount() { return CACHE.size(); }
}

public class FlyweightDemo {
    public static void main(String[] args) {
        // 种 10 万棵树：每棵树只在客户端侧记两个 int 坐标，种类对象全程只有 2 份
        int trees = 100_000;
        for (int i = 0; i < trees; i++) {
            TreeType type = TreeFactory.get(i % 2 == 0 ? "松树" : "枫树",
                                            i % 2 == 0 ? "深绿" : "红色");
            if (i < 3) type.draw(i * 10, i * 5); // 只演示前 3 棵的绘制
        }
        System.out.println("共 " + trees + " 棵树，享元对象只有 " + TreeFactory.typeCount() + " 个");
    }
}
```

- 先分清内/外状态再动手：问一句「这份数据换个使用场景还成立吗」，成立的是内部状态（共享），不成立的是外部状态（外传）。
- 享元对象必须不可变：字段全 final、不给 setter，否则共享即串数据；`Integer` 缓存就是靠不可变才敢全局共享。
- 与单例的区别：单例是「全程一个」，享元是「每个 key 一个」，工厂缓存 map 就是享元的标配。

## 适用场景与选型

- 用它：对象数量以万/百万计，且逐个看状态高度重复（棋盘棋子、森林里的树、文档里的字符样式），内存或 GC 已经因为这类对象报警——注意是「已经报警」，不是「感觉可能会多」。
- 不用它：对象数量不大，工厂加外传状态的啰嗦不值；内/外状态分不开，硬拆只会让调用方到处传参，代码可读性反而下降。
- 选型：先分清内/外状态再动手，判断句式是「这份数据换个使用场景还成立吗」——成立的是内部状态（共享），不成立的是外部状态（外传）。分不清时宁可先不共享。
- 与单例的区别（一句话）：单例是「全程一个」，享元是「每个 key 一个」，工厂缓存 map 就是享元的标配；与对象池的区别是对象池复用的是对象本身，享元共享的是对象里的不变状态。

## 优缺点

- 优点：对象数从「实例总数」降到「种类数」，同类对象量巨大时内存可差几个数量级，GC 压力也随之下降。
- 缺点：外部状态要到处传递，调用代码变啰嗦；享元必须不可变（或线程安全），否则一个调用方改状态全体遭殃；工厂缓存本身要设计（key 空间、容量），否则缓存反而成了新的内存问题。

## 常见误区

- 享元可变：给 TreeType 加了 setter，某个调用方一改颜色，全森林同种树全变色。错：共享的前提是不可变。正确做法是字段全 final、不给 setter，像 Demo 里这样，想换颜色就换一个 key 拿新的享元。
- 内/外状态划错：把每棵树的坐标存进 TreeType。错：坐标随场景变，存进享元后 10 万棵树就共享了同一坐标，画出来全挤在一个点。正确做法是坐标由客户端保存、调用时作为参数传入，享元里只留种类信息。
- 工厂缓存无限增长：key 空间无限（比如 key 里带了用户输入的任意字符串），CACHE 只进不出，最终缓存本身成了内存泄漏。正确做法是评估 key 空间是否有限；无限时要给缓存设上限或淘汰策略，不能无条件 computeIfAbsent 到底。

## 面试与自测

1. 享元的内/外状态怎么划分？用 Demo 里的树举例说明。
2. 享元模式和单例模式的区别是什么？工厂缓存 map 在享元里起什么作用？
3. 为什么享元对象必须不可变？如果给 TreeType 加了 setter 会发生什么？

### 参考答案

1. 判断句式是「这份数据换个使用场景还成立吗」：树的种类、颜色换棵树还成立，是内部状态，放进享元共享；坐标换棵树就不成立，是外部状态，由客户端保存、调用 draw(x, y) 时传入。
2. 单例是「全程一个」对象；享元是「每个 key 一个」对象，工厂缓存 map 保证同一 key 只建一个对象，不同 key 各有一个——Demo 里松树和枫树就是两个 key、两个享元。
3. 因为享元是被所有使用者共享的，一个调用方改了状态，全体使用者看到的数据全变了，等同于数据串味；给 TreeType 加 setter 后，某处一改颜色，全森林同种树都会变色，所以字段必须全 final、不给 setter。
