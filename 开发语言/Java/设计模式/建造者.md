# 建造者模式

## 模式介绍

**意图**：把一个复杂对象的构造过程拆成链式步骤，一步步设置，最后统一构建。解决的问题是「参数一多，构造器就爆炸」：十几个参数（还有一半是可选的）用构造器重载会出现一长串同类型参数，调用处根本分不清哪个是哪个，传错顺序还不报错。

**结构与角色**：
- 产品（Product）：被构建的复杂对象，通常做成不可变（字段 final）。
- 建造者（Builder）：持有与产品同名的待定参数，提供链式 setter，`build()` 时做完整性校验并产出产品。
- 客户端：`new X.Builder().必填().可选().build()`，不用再面对构造器参数表。
- （经典 GoF 还有 Director 角色负责固定组装顺序，Java 里日常写法基本省略，Builder 自己兼任。）

**效果**：
- 优点：调用处自带参数名（`.timeout(30)` 一看就懂），可选参数缺省清晰；校验集中在 `build()`，建出来的对象可以是不可变对象，天然线程安全。
- 代价：样板代码翻倍（Builder 字段要和产品字段写两遍），参数少的类用它是杀鸡用牛刀。Lombok `@Builder` 能把样板抹掉大半。

**适用信号**：
- 参数 ≥ 4 个且多个可选，或多个参数同类型容易传错位置。
- 对象创建前需要跨参数的一致性校验（如 start 不能晚于 end）。
- 反信号：只有两三个必填参数的简单对象，老老实实构造器。

**落点**：
- JDK 与生态：`StringBuilder`（思路同源）、`OkHttpClient.Builder`、`Elasticsearch` 的查询 DSL、`Stream` 收集器构建。
- Lombok `@Builder` 是 Java 项目里的事实标准，ao 的日常开发里参数多的请求 DTO、查询条件对象都适合用它。
- 与工厂的区别：工厂管「建哪个类」，建造者管「一个类的复杂对象怎么一步步攒出来」。

## 模式 Demo

```java
// 产品：HTTP 请求对象，参数多、可选项多、还有跨参数校验
public class HttpRequest {
    private final String url;        // 必填
    private final String method;     // 必填
    private final int timeoutMs;     // 可选，默认 3000
    private final int retry;         // 可选，默认 0
    private final String token;      // 可选

    private HttpRequest(Builder b) {
        this.url = b.url; this.method = b.method;
        this.timeoutMs = b.timeoutMs; this.retry = b.retry; this.token = b.token;
    }

    public static class Builder {
        private final String url;
        private final String method;
        private int timeoutMs = 3000;
        private int retry = 0;
        private String token;

        public Builder(String url, String method) { this.url = url; this.method = method; }
        public Builder timeoutMs(int v) { this.timeoutMs = v; return this; }  // 返回 this 才能链下去
        public Builder retry(int v) { this.retry = v; return this; }
        public Builder token(String v) { this.token = v; return this; }

        public HttpRequest build() {
            // 校验集中在出口：跨参数规则只写一份，所有调用方都受保护
            if (url == null || !url.startsWith("http"))
                throw new IllegalArgumentException("url 非法: " + url);
            if (timeoutMs <= 0) throw new IllegalArgumentException("timeoutMs 必须 > 0");
            if (retry > 0 && token == null)
                throw new IllegalStateException("开启重试必须带 token，否则重试会重复扣费");
            return new HttpRequest(this);
        }
    }
    public String toString() {
        return method + " " + url + " timeout=" + timeoutMs + " retry=" + retry;
    }
}

class Demo {
    public static void main(String[] args) {
        // 链式调用：每个参数自带名字，可选的想设才设
        HttpRequest r = new HttpRequest.Builder("https://api.example.com/loan", "POST")
                .timeoutMs(5000)
                .retry(2)
                .token("abc123")
                .build();
        System.out.println(r);
        // 只给必填也能建，其余走默认值
        System.out.println(new HttpRequest.Builder("https://api.example.com/ping", "GET").build());
    }
}
```

Demo 要点与变体/坑：
- **必填进 Builder 构造器、可选走链式 setter**：必填参数这样设计后，漏传在编译期就暴露；如果全做成 setter，漏设必填只能靠 `build()` 运行时报错，能编译期解决的别拖到运行期。
- **校验放 build() 出口**：单个 setter 只管赋值，跨字段规则（retry 与 token 的关系）集中在一处校验，这是建造者比 Bean 式 setter 注入更可靠的关键。
- **Lombok `@Builder`**：一行注解生成全部样板，项目里优先用它；手写 Builder 留给需要自定义校验、默认值逻辑不平凡的类。注意 Lombok 的 build() 默认不做校验，需要校验时手写 build 逻辑或配合校验注解。
- 坑：Builder 不是线程安全的，一个 Builder 实例别在多线程间共享攒参数；产品类字段加了 final 才是真不可变，只靠「没有 setter」挡不住反射和内部可变集合外泄（集合字段要在构造时做防御性拷贝）。

## 适用场景与选型

- 用：参数 ≥ 4 个且多个可选，或多个参数同类型容易传错位置；对象创建前需要跨参数一致性校验（如 Demo 里 retry 与 token 的关系）。
- 不用：只有两三个必填参数的简单对象，老老实实构造器；参数全必填且无校验时建造者纯添样板。
- 与伸缩构造器区分：构造器重载一多，调用处一串同类型参数分不清谁是谁，传错顺序编译器也不报错；建造者每个参数自带名字，`.timeoutMs(5000)` 一看就懂。
- 与工厂方法区分：工厂管"建哪个类"，建造者管"一个类的复杂对象怎么一步步攒出来"，两者解决的问题不在一层。

## 优缺点

- 优点：调用处可读性高，可选参数缺省清晰；校验集中在 `build()` 出口，建出的对象可做成不可变，天然线程安全。
- 缺点：样板代码翻倍（Builder 字段与产品字段写两遍），Lombok `@Builder` 能抹掉大半但默认不做校验；Builder 本身不是线程安全的。

## 常见误区

- 必填参数也全做成 setter：漏设必填只能靠 `build()` 运行时报错；像 Demo 这样必填进 Builder 构造器，漏传在编译期就暴露。
- 一个 Builder 实例多线程共享着攒参数：Builder 内部是可变字段，并发攒参数会互相覆盖；Builder 一次只用一个线程，建完即弃。
- 以为"没有 setter"就是不可变：产品字段若是集合等可变对象，外部拿到引用照样能改；集合字段要在构造时做防御性拷贝，字段加 final 才是真不可变。

## 面试与自测

1. 为什么 Demo 把 url、method 放进 Builder 构造器，而 timeoutMs、retry、token 走链式 setter？
2. 跨参数校验（retry 与 token 的关系）为什么要集中放在 `build()` 里，而不是每个 setter 里各管各的？
3. 建造者模式和工厂方法模式分别解决什么问题？能互相替代吗？

### 参考答案

1. 必填参数进构造器，漏传在编译期就暴露；可选参数走 setter，想设才设、其余走默认值，两类参数的约束强度不同。
2. 跨参数规则在单个 setter 里看不到其他字段的值，只有 `build()` 出口能看到完整参数集；集中一处也避免规则散落在各处、改一处漏一处。
3. 建造者解决"一个复杂对象怎么一步步攒出来"，工厂方法解决"建哪个类由谁决定"；不能互相替代，一个管组装过程，一个管类型选择。
