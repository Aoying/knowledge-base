# 原型模式

## 模式介绍

**意图**：用一个现成的对象作原型，通过克隆来创建新对象，而不是从头构造。解决的问题是「对象的初始构建很贵或很繁琐，但之后只需要改几个字段就能得到变体」——模板已经配好了，复制一份再微调，比每次重新组装便宜得多。

**结构与角色**：
- 原型（Prototype）：声明克隆自己的方法，如实现 `Cloneable` 并重写 `clone()`，或自定义 `copy()`。
- 具体原型：实现克隆逻辑，难点在于引用字段要拷到什么深度。
- 客户端：拿到原型后 `clone()`，再改差异字段，不关心原型的构造细节。

**效果**：
- 优点：绕过复杂构造（查库组装、远程拉取配置）；运行时可以动态增删原型（注册表里放一批模板，随取随克隆）。
- 代价：克隆语义全靠自己把控——浅拷贝共享引用、深拷贝成本递增，含循环引用的对象图手动深拷贝极易写错。这是所有创建型模式里坑最集中的一个。

**适用信号**：
- 对象构造涉及大量查询/计算，但实例间差异很小（报表模板、关卡配置、角色初始属性）。
- 需要在运行时按已有实例「照着再来一个」。
- 反信号：对象构造本来就便宜（几个字段赋值）时，克隆纯属自找麻烦。

**落点**：
- JDK：`Object.clone()` 与 `Cloneable` 标记接口就是原型模式的语言级支持（设计上有争议，见下方坑）。
- Spring：Bean 作用域 `prototype` 是「每次取都新建」的语义借用，靠的仍是构造而非克隆，别和本模式混淆。
- ao 的小说引擎：章节/实体模板、沙盒推演的分支起点都是原型思想——复制一份世界状态快照，在副本上推演，不动原件；引擎里的 Snapshot 机制正是把「克隆一份再改」工程化。

## 模式 Demo

```java
import java.util.*;

// 原型：实体模板（小说引擎风格）——构造要查一堆默认配置，克隆后只改差异
class EntityTemplate implements Cloneable {
    String name;
    int hp;
    List<String> skills;        // 引用类型字段：深浅拷贝的分水岭
    Map<String, Integer> attrs; // 同上

    EntityTemplate(String name, int hp, List<String> skills, Map<String, Integer> attrs) {
        this.name = name; this.hp = hp; this.skills = skills; this.attrs = attrs;
    }

    // 浅拷贝：Object.clone() 默认行为——引用字段与原件共享同一份集合
    EntityTemplate shallowCopy() throws CloneNotSupportedException {
        return (EntityTemplate) super.clone();
    }

    // 深拷贝：引用字段逐个新建，克隆体与原件互不影响
    EntityTemplate deepCopy() {
        return new EntityTemplate(name, hp,
                new ArrayList<>(skills),
                new HashMap<>(attrs));
    }
}

class Demo {
    public static void main(String[] args) throws Exception {
        EntityTemplate proto = new EntityTemplate("剑客模板", 100,
                new ArrayList<>(List.of("劈砍")),
                new HashMap<>(Map.of("力量", 10)));

        // 浅拷贝的坑：改克隆体的技能列表，原件被一起改了
        EntityTemplate shallow = proto.shallowCopy();
        shallow.skills.add("突刺");
        System.out.println("浅拷贝后原件技能: " + proto.skills);   // [劈砍, 突刺] 被污染

        // 深拷贝：各改各的，互不影响
        EntityTemplate deep = proto.deepCopy();
        deep.skills.add("御剑");
        deep.attrs.put("敏捷", 8);
        System.out.println("深拷贝后原件技能: " + proto.skills);   // 仍是 [劈砍, 突刺]
        System.out.println("深拷贝后原件属性: " + proto.attrs);    // 只有 力量=10
        System.out.println("克隆体: " + deep.skills + " " + deep.attrs);
    }
}
```

Demo 要点与变体/坑：
- **深浅拷贝是原型的核心考点**：基本类型字段克隆即独立；引用字段浅拷贝只复制引用，集合/Map/自定义对象全部共享。判断标准：克隆后改任意一方的集合，另一方会不会变——会变就是浅拷贝。要独立必须逐层新建（Demo 的 `deepCopy` 只处理了一层，嵌套对象还要继续往下拷）。
- **`clone()` 的名声不好**：`Cloneable` 是空标记接口、`clone()` 在 `Object` 上是 protected、浅拷贝语义不写在签名里，Joshua Bloch 在《Effective Java》里明确不推荐用它。实务替代：写拷贝构造器或静态工厂 `copyOf(other)`，语义自控、类型安全；对象图复杂时也可走序列化深拷贝（对象先写出再读回），但要求全图可序列化且慢，只适合小图和低频场景。
- **循环引用直接爆**：A 里有 B、B 里回指 A 时，手写深拷贝会无限递归，要先用 `IdentityHashMap` 记录「已拷贝过的对象」再逐个复制。框架级方案可以看 Kryo、MapStruct 这类工具，或在领域设计上避免双向引用。
- 与单例正相反：原型是「一个变多个」，别把原型实例当单例到处传着改——模板一旦被污染，后面克隆出来的全是错的，原型本身应尽量当只读模板使用。

## 适用场景与选型

- 用：对象构造涉及大量查询、计算或远程拉取，但实例间差异很小（报表模板、关卡配置、角色初始属性）；需要在运行时按已有实例"照着再来一个"。
- 不用：对象构造本来就便宜（几个字段赋值）时，克隆纯属自找麻烦；对象图含循环引用且必须深拷贝时，手写深拷贝成本可能超过重建。
- 与建造者区分：建造者从零一步步攒出一个新对象；原型从现成模板复制一份再改差异字段，前提是已经有一个配好的模板。
- 与 Spring prototype 作用域区分：prototype 是"每次取都重新构造"，靠的仍是构造而非克隆，别和本模式混淆。

## 优缺点

- 优点：绕过复杂构造，复制模板再微调；运行时可动态增删原型（注册表里放一批模板，随取随克隆）。
- 缺点：克隆语义全靠自己把控，浅拷贝共享引用、深拷贝成本递增，含循环引用的对象图手写深拷贝极易写错；原型本身一旦被污染，后面克隆出来的全是错的。

## 常见误区

- 浅拷贝当深拷贝用：Demo 里 `shallowCopy()` 后改克隆体的 skills，原件跟着变；要独立必须像 `deepCopy()` 那样把引用字段逐个新建，嵌套对象还要继续往下拷。
- 把原型实例当可变对象到处传着改：模板被污染后，后续所有克隆体都带错；原型本身应尽量当只读模板使用，改只改克隆体。
- 滥用 `Cloneable`：`clone()` 在 `Object` 上是 protected、`Cloneable` 是空标记接口、浅拷贝语义不写在签名里；实务替代是拷贝构造器或静态工厂，语义自控、类型安全：

```java
// 替代 clone() 的写法：语义写在方法名里，调用方一看就知道是复制
static EntityTemplate copyOf(EntityTemplate other) {
    return new EntityTemplate(other.name, other.hp,
            new ArrayList<>(other.skills),
            new HashMap<>(other.attrs));
}
```

## 小技巧与冷知识

【小技巧】`clone()` 的返回值是 Object，每次调用都要强转，改写时用协变返回类型去掉强转：把重写的 `clone()` 声明成 `public EntityTemplate clone()`，返回类型收窄到子类，调用方直接拿到具体类型。协变返回类型是 Java 5 就支持的语言特性，`clone()` 的重写天生适合用它，签名一改，调用点就再也不用写 `(EntityTemplate) super.clone()`。

【小技巧】`clone()` 不走构造器，构造器里的校验和初始化全被绕过：`Object.clone()` 是在内存里直接复制字段值，不调任何构造器，构造器里做的参数校验、不变式建立、默认值填充都不会执行。克隆出来的对象可能带着构造器本不允许的状态，字段校验不能只放在构造器里，克隆路径也要单独保证——这也是 `copyOf` 静态工厂更稳的原因之一，它走的是正常构造流程。

【小技巧】数组的 `clone()` 也是浅拷贝，别把它当深拷贝用：`int[]` 克隆后互不影响是因为元素是基本类型，`String[]`、`Entity[]` 克隆后两个数组共享同一批元素对象，改克隆数组里的某个对象，原数组里的也跟着变。数组要深拷贝得先 `Arrays.copyOf` 复制数组本身，再逐个复制元素，`clone()` 只解决第一层。

【小技巧】不可变字段不用深拷贝，深拷贝只拷可变部分：String、Integer、LocalDate 这类不可变对象，浅拷贝共享引用完全安全，两个对象谁也改不了它。判断一个字段要不要深拷贝，先问“它能不能被改”，不能被改的共享无妨，能被改的才逐层新建；全图无差别深拷贝既浪费又容易把循环引用拷进来。

【小技巧】子类的 `clone()` 必须调 `super.clone()` 而不是 `new` 一个本类对象：`super.clone()` 会按实际运行时类型分配对象，再由每一层重写逐层复制自己的字段，跳过 `super.clone()`、直接 `new`，父类新增的字段就漏拷了。克隆的正确链条是每层都调 `super.clone()`、各拷各的字段，链条断在任何一层都会丢字段。

【小技巧】`clone()` 抛的是受检异常，调用方必须处理 `CloneNotSupportedException`：方法签名上不写 `throws`，编译器就过不去，异常会从每一层调用点往上冒。`copyOf` 静态工厂没有这个包袱——它不依赖 `Cloneable`，也就不用在签名里带受检异常，调用代码干净一截。

【小技巧】序列化深拷贝会丢 `transient` 字段：走“先写出再读回”的深拷贝时，被标成 `transient` 的字段不会被写进字节流，读回来的克隆体里这些字段是默认值（null 或 0），缓存、派生值、临时状态全丢了。序列化深拷贝之前先盘点对象图里的 transient 字段，丢不起的要手动补，或者干脆换拷贝构造器。

【小技巧】原型注册表返回的必须是克隆体，绝不能把注册表里的模板本身交出去：注册表里放的是只读模板，调用方拿到的是 `registry.get("剑客").clone()`，而不是模板引用。原文“原型本身应尽量当只读模板”落到注册表上就是这条——取模板和取克隆体是两步，注册表的方法内部就要把克隆做掉，调用方连碰到模板的机会都没有。

【小技巧】record 天生适合当原型：record 的字段全是 final、不可变，复制一份只需要 `new Record(旧字段…, 改掉的那一个)`，不用写 `clone()`、不用处理深浅拷贝。给 record 加一个 `withHp(int hp)` 这样的方法，返回改掉一个字段的新 record，就是最干净的原型写法——不可变由语言特性兜底，克隆语义写在方法名里。

【小技巧】深拷贝写完要拿变异测试验一下：克隆体建好后，改克隆体里最深的那层集合或嵌套对象，再断言原件纹丝不动，单测里写一遍这个断言，比肉眼检查每一层靠谱。深拷贝漏拷的层级往往藏在两三层之下，只测第一层集合通过、第二层共享，是最常见的漏网之鱼。

【冷知识】`Object.clone()` 是 native 方法：它的实现在 JVM 内部（C++ 代码），做的是按字段逐个复制的内存级拷贝，不经过 Java 构造器、也不调任何 Java 方法。理解这一点就明白为什么克隆绕过了构造器校验、为什么 `clone()` 的行为不写在 Java 签名里——它本质上是 JVM 的底层操作，`Cloneable` 只是个放行标志。

【冷知识】枚举不能被克隆：`Enum.clone()` 被重写成直接抛 `CloneNotSupportedException`，枚举实例全局唯一，克隆一个枚举在语义上就不成立。原型模式的模板千万别选枚举类型，编译能过、运行时一调 `clone()` 就炸，枚举和原型是两条互不相交的路。

【冷知识】原型是 GoF 23 种模式里 5 种创建型模式之一：和抽象工厂、建造者、工厂方法、单例同属“怎么创建对象”那一组，区别是它不从零构造、而是从现成对象复制。GoF 原书里原型模式的例子是图形编辑器里的图形对象——复制一个画好的图形再微调，比重新画一个便宜得多，和 Demo 里“角色模板复制一份再改”是一个思路。

## 面试与自测

1. 怎么判断一次拷贝是深拷贝还是浅拷贝？给一个可操作的判断标准。
2. Joshua Bloch 为什么不推荐用 `Object.clone()`？实务替代是什么？
3. 对象图含循环引用（A 有 B、B 回指 A）时，手写深拷贝会遇到什么问题，怎么解决？

### 参考答案

1. 克隆后改任意一方引用字段指向的集合，另一方会不会跟着变：会变就是浅拷贝，不变才是深拷贝；基本类型字段克隆即独立，不用测。
2. `Cloneable` 是空标记接口、`clone()` 是 protected、浅拷贝语义不体现在签名里，调用方无法从接口看出拷贝深度；替代是拷贝构造器或 `copyOf(other)` 静态工厂，语义自控、类型安全。
3. 会无限递归：拷 A 要拷 B，拷 B 又要拷 A；解决办法是用 `IdentityHashMap` 记录已拷贝过的对象，遇到已拷贝的直接复用，不再往下拷。
