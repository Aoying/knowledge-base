# 工厂方法模式

## 模式介绍

**意图**：定义一个创建对象的接口，但让子类决定实例化哪一个产品类。解决的问题是「调用方只知道要用某个抽象产品，不知道也不应该关心具体是哪个实现」——把「建哪个」这个决定从调用处挪到工厂子类里。

**结构与角色**：
- 产品接口（Product）：产品的抽象，如 `MsgChannel`。
- 具体产品（ConcreteProduct）：每种实现，如 `EmailChannel`、`SmsChannel`。
- 工厂（Creator）：声明工厂方法 `create()`，可以带一个默认实现骨架。
- 具体工厂（ConcreteCreator）：每个产品配一个，决定真正 new 哪个产品。

**效果**：
- 优点：新增产品 = 新增一对（产品类 + 工厂类），不改老代码，符合开闭原则；调用方只依赖抽象。
- 代价：类数量翻倍——一个产品一个工厂，产品多了文件满天飞；对「只有一种实现」的场景属于过度设计。

**适用信号**：
- 调用方不确定将来会有几种实现，且每种实现的创建逻辑各有讲究。
- 框架设计：框架定骨架，留工厂方法给使用者扩展（模板方法常和它成对出现）。

**与简单工厂的区别（关键）**：
- 简单工厂：一个工厂类，内部按参数 `if/switch` 分支返回不同产品。加产品必须改这个类的分支——改老代码。
- 工厂方法：把那个分支变成了多态——每个产品一个工厂子类，加产品只加新类，不动老类。
- 代价对换：简单工厂集中、简单，但违反开闭；工厂方法分散、类多，但扩展干净。产品少且稳定时简单工厂完全够用，别为模式而模式。

**落点**：
- JDK：`Collection.iterator()` 就是工厂方法（每个集合返回自己的迭代器）；`Calendar.getInstance()` 内部也是这套。
- Spring：`FactoryBean` 接口就是工厂方法的框架化——实现它，容器就用它产出的对象注册 Bean。
- ao 的多渠道消息系统：渠道少而稳时用简单工厂（Map 注册）即可；当每个渠道的构建过程开始复杂（要组装重试器、限流器）再升级成工厂方法。

## 模式 Demo

```java
// 产品：消息渠道
interface MsgChannel { void send(String msg); }

class EmailChannel implements MsgChannel {
    public void send(String msg) { System.out.println("邮件发送: " + msg); }
}
class SmsChannel implements MsgChannel {
    public void send(String msg) { System.out.println("短信发送: " + msg); }
}

// 工厂：只声明"建渠道"这件事，具体建哪个交给子类
abstract class ChannelFactory {
    abstract MsgChannel create();
    // 工厂之上还能放共用骨架：创建 + 统一的发送前处理
    public final void deliver(String msg) {
        MsgChannel ch = create();
        ch.send(msg);
    }
}

// 具体工厂：一个产品一个工厂，新增渠道时不改任何老类
class EmailFactory extends ChannelFactory {
    MsgChannel create() { return new EmailChannel(); }
}
class SmsFactory extends ChannelFactory {
    MsgChannel create() { return new SmsChannel(); }
}

class Demo {
    public static void main(String[] args) {
        // 调用方只认识抽象工厂，具体用哪家由组装时决定
        ChannelFactory factory = new SmsFactory();
        factory.deliver("验证码 1234");
        factory = new EmailFactory();   // 换渠道只换工厂，deliver 代码不动
        factory.deliver("月度账单");
    }
}
```

Demo 要点与变体/坑：
- **对照简单工厂**：简单工厂是 `ChannelFactory.create("sms")` 一个类里 switch 分支，新增渠道改分支；这里的版本新增渠道 = 新写 `XxxChannel + XxxFactory` 两个类，老代码零修改，这就是工厂方法付的类数量代价换来的开闭。
- **工厂方法 + 模板方法**：Demo 里 `deliver()` 就是模板方法——流程骨架在抽象工厂里，变化点（create）下放子类。这两个模式在框架代码里几乎总是结伴出现。
- **现代替代**：有了 Spring，`@Component` + 按名注入 `Map<String, MsgChannel>` 一行搞定注册与查找，手写工厂类大多可以退休；手写工厂方法主要留给脱离容器的 SDK 和框架层代码。
- 坑：产品层级和工厂层级要一一对应平行维护，产品改名/增减时两边都要动；只有一两个产品时这层间接纯属负担。

## 适用场景与选型

- 用：调用方只依赖产品抽象、具体产品种类未来会增加，且每种产品的创建过程各有讲究（要组装不同的重试器、限流器）。
- 不用：产品种类固定且只有一两种、创建只是一句 new 时，一个简单工厂或直接 new 更省事；为模式而模式只会多出一堆类。
- 与简单工厂区分：简单工厂把"建哪个"写成一个类里的 if/switch 分支，加产品要改分支；工厂方法把分支变成多态，每个产品配一个工厂子类，加产品只加新类。
- 与抽象工厂区分：工厂方法一次只决定一个产品；一整族产品要成套切换时用抽象工厂。

## 优缺点

- 优点：新增产品不改老代码，符合开闭原则；调用方只依赖抽象，产品实现可整体替换。
- 缺点：类数量翻倍（产品与工厂平行两套层级），改名、增减产品时两边都要动；产品少时这层间接纯属负担。

## 常见误区

- 只有一个产品也硬上工厂方法：产品层级和工厂层级各一层，纯添间接层；产品稳定且单一时简单工厂或直接 new 就够了。
- 工厂里塞业务逻辑：工厂只负责"建出来"，Demo 里 `deliver()` 这种共用骨架可以放，但渠道计费、重试策略这类业务不要塞进工厂，否则工厂变成大杂烩。
- 有了 Spring 还手写全套工厂类：`@Component` + 按名注入 `Map<String, MsgChannel>` 就能完成注册与查找，手写工厂方法主要留给脱离容器的 SDK 和框架层。

## 小技巧与冷知识

【小技巧】工厂方法的返回类型可以用协变返回类型收窄：抽象工厂声明 `MsgChannel create()`，子类工厂可以写成 `EmailChannel create()`，返回更具体的产品类型，调用方拿到手就不用再强转。协变返回类型是 Java 5 就支持的语言特性，工厂方法的重写天生适合用它——返回类型越具体，调用点越干净。

【小技巧】抽象工厂里的工厂方法可以带默认实现，子类只重写需要变的那部分：Creator 不必把 `create()` 写成纯抽象方法，可以先给一个默认产品，80% 的场景直接用默认实现，只有特殊的产品才由子类覆盖。原文说 Creator“可以带一个默认实现骨架”，这就是它的落点——默认实现不是摆设，是“多数情况不用写子类”的省力点。

【小技巧】工厂方法决定“建哪个”，对象“怎么组装”交给建造者：产品创建过程一旦复杂（要依次装重试器、限流器、超时配置），别把十几行组装代码全塞进 `create()`，让工厂方法内部调一个 Builder，create 只负责“选哪个 Builder、返回它 build 出来的产品”。两个模式各管一头，工厂方法不变成组装车间。

【小技巧】工厂子类太多时，可以用注册表收敛类数量：产品到十几种、每个产品配一个工厂类时，文件数会先失控。可以把“产品名 → Supplier<Product>”写进一张 Map 注册表，由一个工厂按 key 查表创建——这其实是简单工厂与工厂方法的折中：扩展时只加一行注册、不改分发逻辑，类数量不再翻倍，代价是又回到“集中式”的老路上，取舍要看产品数。

【小技巧】测工厂方法时断言“返回了什么”，别 mock 工厂本身：工厂的职责就是产出正确产品，单测里调 `create()`、断言返回对象的具体类型和行为（比如 `instanceof SmsChannel`、send 走短信网关），一测就覆盖了“建对了没有”。把工厂 mock 掉再断言调用方，等于把最该测的创建逻辑绕过去了。

【小技巧】工厂方法返回的是新实例还是共享实例，要在方法名或文档里写明：`create()` 按惯例每次返回新对象，如果某个工厂返回的是缓存的单例产品，调用方按“每次拿到新的”去改它的状态，就会互相污染。返回共享实例时方法名别叫 create，改叫 `getSharedChannel()` 之类，或者在注释里写清“返回共享实例、调用方不得修改状态”。

【小技巧】调用方不要自己 new 具体工厂，把工厂当依赖注入进来：Demo 里 `new SmsFactory()` 写在 main 里只是演示，业务代码里调用方直接 new 工厂，换产品又要改调用方——开闭原则在工厂层守住了、在调用层又丢了。工厂本身也是依赖，同样走构造器注入或配置传入，换产品只改装配，不改调用代码。

【小技巧】产品接口的方法一旦定下来，所有产品都要跟着实现：工厂方法模式下新增一个产品方法要改产品接口、再改每一个具体产品，扩展成本不在工厂层、在产品层。设计产品接口时尽量小而稳，需要扩展行为时优先给接口加默认方法（default method），而不是直接加抽象方法逼所有产品重写。

【小技巧】枚举的每个常量重写抽象方法，就是一种现成的工厂方法：`enum ChannelType { EMAIL { MsgChannel create() { return new EmailChannel(); } }, SMS { ... } }`，每个常量就是一个具体工厂，不用再写一堆工厂类。产品种类固定、数量有限时，枚举版工厂方法比“产品 + 工厂”两套层级省事得多，种类会动态增加时再换回类的方式。

【冷知识】“静态工厂方法”和“工厂方法模式”是两个东西，别被名字骗了：《Effective Java》第 1 条说的静态工厂方法（static factory method，如 `Integer.valueOf()`、`List.of()`）是类的静态方法，返回实例、可以换名、可以返回子类型；而 GoF 的工厂方法模式是“用子类多态决定建哪个产品”的对象结构。一个是静态方法技巧，一个是类层级设计，名字撞了、内容完全不同。

【冷知识】GoF 原书讲工厂方法用的例子是应用程序框架：框架里 `Application` 类有个工厂方法 `CreateDocument()`，创建哪种文档由具体的应用子类决定——画图应用返回 `DrawingDocument`，文字应用返回 `TextDocument`。框架定骨架、子类定产品，这个例子就是原文“框架设计：框架定骨架，留工厂方法给使用者扩展”那条的出处。

【冷知识】`Collection.iterator()` 是工厂方法，但它返回的迭代器大多是“一次性”的：每个集合的 `iterator()` 每次调用都新建一个迭代器实例，且迭代器本身有状态（游标位置），同一个迭代器不能 reset 后重用。调用方拿迭代器当“可复用的遍历器”反复用，是对工厂方法返回值的常见误读——工厂方法保证“每次给你一个能用的新产品”，不保证“这个产品能反复用”。

## 面试与自测

1. 工厂方法相对简单工厂，到底换来了什么、付出了什么？
2. 新增一种消息渠道时，工厂方法版本要改哪些类、新增哪些类？
3. `Collection.iterator()` 为什么是工厂方法？它解决了什么问题？

### 参考答案

1. 换来开闭：新增产品只加新类，不改老代码；付出类数量翻倍，产品与工厂两套层级要平行维护。
2. 不改任何老类；新增一个产品类（如 `PushChannel`）和一个工厂类（如 `PushFactory`），调用方换注入的工厂即可。
3. 每个集合类返回自己的迭代器实现，调用方只依赖 `Iterator` 抽象；新增集合类型不用改遍历代码，创建迭代器的决定下放到了各个集合子类。
