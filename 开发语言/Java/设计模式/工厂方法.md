# 工厂方法模式

## 模式介绍

**意图**：定义一个创建对象的接口，但让子类决定实例化哪一个产品类。解决的问题是「调用方只知道要用某个抽象产品，不知道也不应该关心具体是哪个实现」——把「建哪个」这个决定从调用处挪到工厂子类里。

**结构与角色**：
- 产品接口（Product）：产品的抽象，如 `MsgChannel`。
- 具体产品（ConcreteProduct）：每种实现，如 `EmailChannel`、`SmsChannel`。
- 工厂（Creator）：声明工厂方法 `create()`，可以带一个默认实现骨架。
- 具体工厂（ConcreteCreator）：每个产品配一个，决定真正 new 哪个产品。

**效果**：
- 优点：新增产品 = 新增一对（产品类 + 工厂类），不改老代码，符合开闭原则；调用方只依赖抽象。
- 代价：类数量翻倍——一个产品一个工厂，产品多了文件满天飞；对「只有一种实现」的场景属于过度设计。

**适用信号**：
- 调用方不确定将来会有几种实现，且每种实现的创建逻辑各有讲究。
- 框架设计：框架定骨架，留工厂方法给使用者扩展（模板方法常和它成对出现）。

**与简单工厂的区别（关键）**：
- 简单工厂：一个工厂类，内部按参数 `if/switch` 分支返回不同产品。加产品必须改这个类的分支——改老代码。
- 工厂方法：把那个分支变成了多态——每个产品一个工厂子类，加产品只加新类，不动老类。
- 代价对换：简单工厂集中、简单，但违反开闭；工厂方法分散、类多，但扩展干净。产品少且稳定时简单工厂完全够用，别为模式而模式。

**落点**：
- JDK：`Collection.iterator()` 就是工厂方法（每个集合返回自己的迭代器）；`Calendar.getInstance()` 内部也是这套。
- Spring：`FactoryBean` 接口就是工厂方法的框架化——实现它，容器就用它产出的对象注册 Bean。
- ao 的多渠道消息系统：渠道少而稳时用简单工厂（Map 注册）即可；当每个渠道的构建过程开始复杂（要组装重试器、限流器）再升级成工厂方法。

## 模式 Demo

```java
// 产品：消息渠道
interface MsgChannel { void send(String msg); }

class EmailChannel implements MsgChannel {
    public void send(String msg) { System.out.println("邮件发送: " + msg); }
}
class SmsChannel implements MsgChannel {
    public void send(String msg) { System.out.println("短信发送: " + msg); }
}

// 工厂：只声明"建渠道"这件事，具体建哪个交给子类
abstract class ChannelFactory {
    abstract MsgChannel create();
    // 工厂之上还能放共用骨架：创建 + 统一的发送前处理
    public final void deliver(String msg) {
        MsgChannel ch = create();
        ch.send(msg);
    }
}

// 具体工厂：一个产品一个工厂，新增渠道时不改任何老类
class EmailFactory extends ChannelFactory {
    MsgChannel create() { return new EmailChannel(); }
}
class SmsFactory extends ChannelFactory {
    MsgChannel create() { return new SmsChannel(); }
}

class Demo {
    public static void main(String[] args) {
        // 调用方只认识抽象工厂，具体用哪家由组装时决定
        ChannelFactory factory = new SmsFactory();
        factory.deliver("验证码 1234");
        factory = new EmailFactory();   // 换渠道只换工厂，deliver 代码不动
        factory.deliver("月度账单");
    }
}
```

Demo 要点与变体/坑：
- **对照简单工厂**：简单工厂是 `ChannelFactory.create("sms")` 一个类里 switch 分支，新增渠道改分支；这里的版本新增渠道 = 新写 `XxxChannel + XxxFactory` 两个类，老代码零修改，这就是工厂方法付的类数量代价换来的开闭。
- **工厂方法 + 模板方法**：Demo 里 `deliver()` 就是模板方法——流程骨架在抽象工厂里，变化点（create）下放子类。这两个模式在框架代码里几乎总是结伴出现。
- **现代替代**：有了 Spring，`@Component` + 按名注入 `Map<String, MsgChannel>` 一行搞定注册与查找，手写工厂类大多可以退休；手写工厂方法主要留给脱离容器的 SDK 和框架层代码。
- 坑：产品层级和工厂层级要一一对应平行维护，产品改名/增减时两边都要动；只有一两个产品时这层间接纯属负担。
