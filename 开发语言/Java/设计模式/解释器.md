# 解释器模式

## 模式介绍

**意图**：给一门小语言定义文法，用类表示语法规则，把句子解析成一棵表达式树，再递归求值。每条语法规则一个类，加规则就是加类。

**结构与角色**：

- `AbstractExpression`（抽象表达式）：声明 `interpret(context)` 求值入口。
- `TerminalExpression`（终结符表达式）：最小单元，如变量、常量，直接从上下文取值。
- `NonterminalExpression`（非终结符表达式）：组合规则，如 And、Or、GreaterThan，内部持有子表达式并递归求值——结构上就是组合模式的一棵树。
- `Context`（上下文）：求值时需要的变量环境（字段名 → 值）。
- 客户端：把句子（如配置里的规则字符串）解析（parse）成表达式树，再对每个上下文求值。

**效果**：

- 优点：文法显性化，规则可组合、可单测；业务人员写的规则字符串能在运行期生效，不用改代码发版。
- 代价：文法稍复杂类就爆炸；解析、优先级、错误提示都要自己维护；性能远不如直接写代码。文法超过十来条规则，手写解释器基本必然失控。

**适用信号**：

- 有固定文法的小句子反复出现：风控规则、筛选条件、告警条件（「金额 > 1000 且 状态 = 已审」）。
- 规则需要配置化、由非开发人员维护，且形态简单（比较 + 与或非）。

**落点**：

- 实际项目里**优先用现成表达式引擎**：Spring 的 SpEL、MVEL、 Aviator、QLExpress，文法、性能、报错都比手写强。手写解释器只适合极简规则或理解原理。
- 框架内部实例：Spring Security 的表达式授权、`@PreAuthorize("hasRole('ADMIN')")` 背后就是 SpEL 解释求值。
- 小说引擎的剧情规则检测（「源石可修改记忆」「林溯不知道父母已死亡」这类事实断言）本质就是在事实上下文上求值一组规则表达式。

## 模式 Demo

```java
import java.util.Map;

// 极简规则解释器：支持 字段 > 数值 / 字段 < 数值 / 字段 = 值，用 && 连接
interface Expr {
    boolean eval(Map<String, Object> ctx);
}

// 终结符：单条比较，如 amount > 1000
class Compare implements Expr {
    private final String field, op;
    private final long value;

    Compare(String field, String op, long value) {
        this.field = field; this.op = op; this.value = value;
    }

    public boolean eval(Map<String, Object> ctx) {
        long actual = ((Number) ctx.get(field)).longValue();
        return switch (op) {
            case ">" -> actual > value;
            case "<" -> actual < value;
            default  -> actual == value;   // "="
        };
    }
}

// 非终结符：逻辑与，组合两个子表达式（组合模式的树）
class And implements Expr {
    private final Expr left, right;
    And(Expr left, Expr right) { this.left = left; this.right = right; }
    public boolean eval(Map<String, Object> ctx) {
        return left.eval(ctx) && right.eval(ctx);
    }
}

// 极简解析器：按 && 切分，每段解析成一个 Compare，再左结合成 And 树
class RuleParser {
    static Expr parse(String rule) {
        Expr result = null;
        for (String part : rule.split("&&")) {
            String[] tok = part.trim().split("\\s+");        // 字段 运算符 值
            Expr e = new Compare(tok[0], tok[1], Long.parseLong(tok[2]));
            result = (result == null) ? e : new And(result, e);
        }
        return result;
    }
}

public class InterpreterDemo {
    public static void main(String[] args) {
        Expr rule = RuleParser.parse("amount > 1000 && level >= 0 && count < 5"
                .replace(">= 0", "> -1"));                   // 本极简版只支持 > < =，借道演示
        Map<String, Object> ctx = Map.of("amount", 1500, "level", 2, "count", 3);
        System.out.println("规则命中：" + rule.eval(ctx));    // true
        Map<String, Object> ctx2 = Map.of("amount", 500, "level", 2, "count", 3);
        System.out.println("规则命中：" + rule.eval(ctx2));   // false
    }
}
```

- 核心结构是「表达式树 + 递归求值」：解析（parse）和求值（eval）严格分离，同一棵树可对任意上下文反复求值，规则对象天然可缓存复用。
- 本 Demo 为讲清结构故意极简：不支持括号、或、非和字符串比较。真要加这些，就该换 SpEL/Aviator，而不是继续给手写版打补丁。
- 坑：规则字符串来自配置或用户输入时，先校验字段名白名单再求值，别让规则直接触达任意对象属性——表达式注入是真实风险。

## 适用场景与选型

- 用：有固定文法的小句子反复出现（风控规则、筛选条件、告警条件）；规则需要配置化、由非开发人员维护，且形态简单（比较 + 与或非）。
- 不用：文法超过十来条规则，类爆炸、优先级、报错全要自己维护；性能敏感的求值路径；规则形态会不断长出括号、函数、字符串运算等新花样。
- 与直接写 if 代码的区别（只记一句）：规则字符串在运行期解析求值，改规则不用改代码发版；if 代码写死逻辑，规则一变就要改代码、走发布流程。

## 优缺点

- 优点：文法显性化，规则可组合、可单测；同一棵表达式树可对任意上下文反复求值，规则对象天然可缓存复用；业务人员维护的规则能运行期生效。
- 代价：文法稍复杂类就爆炸；解析、优先级、错误提示都要自己维护；性能远不如直接写代码；规则来自外部输入时有表达式注入风险。

## 常见误区

- 误区 1：文法变复杂仍给手写版打补丁。错：规则长出括号、或、非、字符串比较后，继续往 RuleParser 里加分支，解析器越改越乱。正确：到这个规模就换 SpEL、Aviator、QLExpress 等现成引擎，手写版只留给极简规则或理解原理。
- 误区 2：规则直通任意属性。错：规则字符串来自配置或用户输入，求值时不校验字段名，规则可以直接触达任意对象属性。正确：先校验字段名白名单再求值，表达式注入是真实风险（Demo 要点里已提）。
- 误区 3：解析与求值搅在一起。错：每次求值都重新解析规则字符串，或把解析逻辑写进 eval 里。正确：解析（parse）和求值（eval）严格分离，解析一次产出表达式树，同一棵树对不同上下文反复求值。

## 小技巧与冷知识

【小技巧】And/Or 节点求值要用短路语义：`left.eval(ctx) && right.eval(ctx)` 里右子树只在左子树为 true 时才跑，Or 同理。短路不只是性能——右子树可能查一个不存在的字段或做昂贵计算，左子树已定胜负时再跑它，要么白花钱、要么无端抛错；手写 eval 时把 `&` 写成 `&&`、把 `|` 写成 `||`，是解释器里最便宜的一层保护。

【小技巧】终结符节点是唯一该报“字段问题”的地方：`ctx.get(field)` 返回 null 或类型不对时，别让它在深层递归里变成 NullPointerException——在 Compare 这一层就抛带字段名和规则名的异常（如“规则 amount > 1000：字段 amount 不存在”）。求值栈越深，现场信息丢得越干净，错误在叶子节点就定性，比在顶层猜要省一半排障时间。

【小技巧】求值用的 Context 只读不写：eval 期间不要让任何节点往 ctx 里写临时变量，否则同一棵树对两个上下文求值会互相污染，并发求值更会直接串数据。上下文用不可变 Map（`Map.copyOf`）或只读包装传进来，节点只能读、不能改；需要在求值中途存中间结果时，挂在表达式树自己的节点上，别借 ctx 当草稿纸。

【小技巧】解析一次、按规则字符串缓存表达式树：parse 是字符串处理加建树，比 eval 贵得多，同一条规则对一万条数据求值时，解析一次、缓存起来反复用才是正确姿势。缓存 key 直接用规则字符串本身（`ConcurrentHashMap<String, Expr>`），规则一变 key 就变，不用另写失效逻辑；缓存的不是求值结果，是解析好的树——结果随上下文变，树不随上下文变。

【小技巧】取反单独做一个 Not 节点，别给 Compare 加“取反标志位”：Not 只包一个子表达式、返回 `!child.eval(ctx)`，一个节点只干一件事；Compare 一旦带上 negate 标志，And/Or/Not 的组合语义都要跟着改，等于把“非”散进每个节点里。新增语法元素时先问“能不能用一个新节点表达”，能就加节点、别改老节点，文法扩展的代价才收得住。

【小技巧】给每个表达式节点加一个能打印中缀形式的 toString：规则字符串进配置中心后，线上出问题时只看原始字符串猜不出解析器到底建了哪棵树——And 套 Or 还是 Or 套 And，优先级错一点结果全变。`And(Compare(amount > 1000), Compare(count < 5))` 这样的树形打印一打出来，解析错没错一眼见分晓；调试解释器先打树，再猜逻辑。

【小技巧】解析器别再用 split 切字符串，写个最小词法器：Demo 里按 `&&` 切分、按空白切分只适合演示，规则值里一旦出现带空格的字符串或 `&&` 本身（比如 `name = "a && b"`），split 直接切错位置。词法器一次只吐一个 token（字段名、运算符、数值、字符串字面量、括号），解析器只跟 token 打交道；字符串解析的坑，九成出在分词这层，不在建树那层。

【小技巧】加 Or/括号时优先级必须显式定，别靠“左结合”蒙：Demo 只有 And，左结合够用；一旦 Or 进来，`A || B && C` 按“&& 优先”还是“从左到右”结果完全不同，业务方写规则时默认的是前者。加新运算符前先写死一张优先级表（Not > And > Or），解析时按优先级递归下降或用调度场算法，别指望“按出现顺序建树”碰巧是对的。

【小技巧】数值比较别用 longValue() 粗暴转：Demo 的 Compare 把字段值转 long 再比，金额带小数时直接截断，`amount > 1000.5` 和 `amount > 1000` 会算成同一个结果。字段值统一按 BigDecimal 或 double 比较，比较前先按字段类型定好数值语义；金融、风控类规则里，小数截断不是精度问题，是判错问题。

【冷知识】GoF 原书讲解释器用的例子是布尔表达式和正则表达式：VariableExp、AndExp、OrExp、NotExp、Constant 这几个类拼出一棵布尔表达式树，对上下文求值；正则表达式则是“把模式串编译成一棵匹配树再跑”。Java 自带的 `java.util.regex.Pattern` 就是这个思路——compile 时把正则串编成内部节点树，matcher 时在树上跑，解释器模式在 JDK 里最常见的落地不是规则引擎，是正则。

【冷知识】SQL 的 WHERE 子句就是解释器模式的现实版：数据库收到一条 SQL，先解析 WHERE 部分建成一棵表达式树（比较节点、And/Or 节点），再对每一行数据求值决定要不要这行。风控规则、筛选条件、告警条件和 SQL WHERE 是同一套结构——“文法 + 树 + 按行求值”，差别只在文法长什么样、上下文是什么。

【冷知识】SpEL 不只解释执行，还能编译成字节码：Spring 的 `SpelCompiler`（Spring 4.1 起）会把反复求值的表达式编译成 JVM 字节码再跑，热点规则的性能接近手写代码。这也是“优先用现成引擎”的另一层理由——手写解释器只能解释执行，现成引擎在热点路径上会自己升级成编译执行，性能差距不是常数倍，是量级差。

## 面试与自测

1. 解释器模式为什么要把解析（parse）和求值（eval）严格分离？
2. 文法超过十来条规则时，手写解释器会遇到哪些失控点？正确做法是什么？
3. 规则字符串来自用户输入时，求值前必须先做什么？为什么？

### 参考答案

1. 解析一次产出表达式树，同一棵树可对任意上下文反复求值，规则对象天然可缓存复用；混在一起则每次求值都要重新解析，性能差且无法复用规则对象。
2. 类爆炸（每条规则一个类）、运算符优先级、括号处理、错误提示都要自己维护，规模一上来必然失控；正确做法是换 SpEL、MVEL、Aviator、QLExpress 等现成表达式引擎。
3. 先校验字段名白名单。否则规则可以直接触达任意对象属性，造成表达式注入，攻击者可能读到或改动不该碰的数据。
