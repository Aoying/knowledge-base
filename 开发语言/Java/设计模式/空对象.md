# 空对象模式

> 空对象（Null Object）不是 GoF 模式，是社区沉淀的常用手法：用一个「什么都不做」的实现代替 null 返回。

## 模式介绍

**意图**：当「没有对象」是一种正常情况时，不返回 null，而是返回一个行为为空（或返回安全默认值）的同接口实现。调用方从此不用判空，照常调用。

**结构与角色**：

- 抽象接口：正常实现与空实现共同实现的接口。
- 正常实现：真实业务行为。
- 空实现（Null Object）：方法空转或返回默认值（空字符串、0、空集合），通常做成无状态单例。
- 提供方（工厂/查询层）：查不到时返回空对象而不是 null，这是模式的约定所在。

**效果**：

- 优点：消灭散落各处的 `if (x != null)`，尤其是链式调用；「无此用户」「未配置日志」等缺省语义集中在一个类里。
- 代价：可能掩盖本应报错的错误——查不到用户究竟是正常（游客）还是异常（数据丢了）？把异常悄悄变空转，排查时更难。只对「缺省是合法业务语义」的场景用。

**适用信号**：

- 同一个对象在多处被判空，且判空后做的都是同一件「跳过/用默认值」的事。
- 接口的消费者很多，逐个加判空不如源头给空对象。
- 典型对象：日志器（未配置时静默）、权限（游客用户）、缓存未命中时的空结果集、审计/埋点（未启用时空转）。

**落点**：

- 日志框架的 `NOPLogger`（slf4j 未绑定实现时用的就是空对象，什么都不打但绝不 NPE）。
- 集合接口的 `Collections.emptyList()` 思想：返回空集合而非 null，调用方直接遍历。
- Spring 里可选依赖未注入时给一个默认空实现 Bean，避免每个使用处判空。

**与 Optional 的分工**：Optional 是在方法签名上**显式声明可能没有**，逼调用方处理；空对象是让「没有」**隐形**，调用方无感。可能没有且必须处理 → Optional；没有也要流程顺滑走完 → 空对象。

## 模式 Demo

```java
// 用户查询：查不到返回「游客」空对象，而不是 null
interface User {
    String name();
    boolean canPost();
}

class RealUser implements User {
    private final String name;
    RealUser(String name) { this.name = name; }
    public String name() { return name; }
    public boolean canPost() { return true; }
}

// 空对象：行为是「安全的什么都不做」
class GuestUser implements User {
    static final GuestUser INSTANCE = new GuestUser();   // 无状态，做成单例
    public String name() { return "游客"; }
    public boolean canPost() { return false; }
}

class UserRepository {
    User findById(long id) {
        if (id == 1L) return new RealUser("林溯");
        return GuestUser.INSTANCE;          // 约定：查不到给空对象，不给 null
    }
}

// 调用方：全程不判空
class PageService {
    private final UserRepository repo = new UserRepository();

    void renderHome(long userId) {
        User u = repo.findById(userId);
        System.out.println("欢迎，" + u.name());            // 游客也正常渲染
        System.out.println(u.canPost() ? "显示发帖框" : "发帖框置灰（游客）");
    }
}

public class NullObjectDemo {
    public static void main(String[] args) {
        PageService page = new PageService();
        page.renderHome(1L);    // 真实用户
        page.renderHome(999L);  // 查不到 -> 游客空对象，无任何判空代码
    }
}
```

- 关键在「约定」：提供方必须保证永不返回 null，空对象模式才成立；只要有一处漏给 null，调用方的信任就崩了。
- 空实现的方法要返回与类型匹配的安全默认值：对象返回空对象、集合返回空集合、数值返回 0，别随手 return null 把问题又带回来。
- 坑：写操作场景慎用——「查不到账户就空转跳过扣款」会把数据异常吞成静默失败；空对象适合读多、展示、日志类场景，涉及钱与状态变更的路径宁可显式报错。

## 适用场景与选型

- 用它：查不到、未配置、未启用是合法业务语义（游客、未配置日志、未启用埋点）；同一个对象在多处被判空、且判空后做的都是同一件“跳过/用默认值”的事；接口消费者很多，逐个加判空不如源头给空对象。
- 不用它：查不到本应是异常（数据丢了、越权访问）——该抛异常或用 Optional 显式处理；写操作和涉钱路径（空转会把失败吞成静默成功）；空对象的“安全默认值”本身有歧义、说不清该返回什么时。
- 与 Optional 的一句话区分：Optional 在签名上显式声明“可能没有”，逼调用方处理；空对象让“没有”隐形，调用方无感——必须处理时用 Optional，流程要顺滑走完时用空对象。

## 优缺点

- 优点：消灭散落各处的 `if (x != null)`，尤其是链式调用；“无此用户”“未配置日志”等缺省语义集中在一个类里，改缺省行为只改一处；调用方代码更干净。
- 缺点：可能掩盖本应报错的错误（游客和数据丢失看起来一样）；空对象泛滥后“到底有没有”难追踪；模式成立依赖全链路约定“永不返回 null”，一处漏 null 信任就崩；调试时看到的是 GuestUser 而非缺失原因。

## 常见误区

- 提供方某条分支漏返回 null：调用方基于“永不 null”的信任不判空，结果 NPE 又回来了，模式等于白做。正确：工厂/查询层统一出口，查不到分支必须返回空对象，必要时加断言或测试覆盖查不到分支。
- 空对象的方法返回 null：`GuestUser.name()` 随手 return null，等于把问题又带回来。正确：每个方法返回与类型匹配的安全默认值——对象返回空对象、集合返回空集合、数值返回 0、布尔返回 false（如 Demo 的 `canPost()` 返回 false）。
- 写路径用空对象：查不到账户就空转跳过扣款，数据异常被吞成静默失败，账对不上才发现。正确：空对象只用于读、展示、日志类场景，涉钱与状态变更的路径宁可显式报错。

## 面试与自测

1. 空对象和 Optional 怎么选？各给一个适用场景。
2. 为什么说“提供方永不返回 null”是空对象模式成立的前提？
3. 哪类场景禁用空对象？为什么？

### 参考答案

1. 可能没有且调用方必须处理 → Optional：如按订单号查订单，查不到要提示“订单不存在”，签名上的 Optional 逼调用方写分支。没有也要流程顺滑走完 → 空对象：如未配置日志器时打日志应当静默，游客浏览页面应当正常渲染，判空只会污染所有调用处。
2. 因为调用方是基于“拿到的绝不是 null”才敢全程不判空的。只要有一处漏给 null，调用方的信任就崩了——NPE 会在任意调用处出现，比处处判空更难排查。所以约定必须由提供方（工厂/查询层）统一保证，而不是靠调用方自觉。
3. 写操作和涉钱路径禁用：查不到账户就空转跳过扣款、查不到库存就空转跳过扣减，都会把数据异常吞成静默成功，事后对账才发现。读、展示、日志类场景可以用，凡是“没做就等于错”的路径都必须显式报错。
