# 设计模式

> 本篇是模式汇总与索引：每种模式已拆为独立文件（模式介绍 + 模式 Demo），存放在 `开发语言/Java/设计模式/` 子目录。先掌握标 ★ 的 9 个核心，其余查表。

## 创建型（独立文件）

- [单例](开发语言/Java/设计模式/单例.md) ★：全场只有一个实例，并控制它的创建入口。
- [工厂方法](开发语言/Java/设计模式/工厂方法.md) ★：每个产品配一个工厂子类，用多态代替分支。
- [抽象工厂](开发语言/Java/设计模式/抽象工厂.md)：建一族互相配套的对象，整体切换供应商。
- [建造者](开发语言/Java/设计模式/建造者.md) ★：分步构建复杂对象，告别一长串构造参数。
- [原型](开发语言/Java/设计模式/原型.md)：克隆现成对象再改差异，不重新构造。

## 结构型（独立文件）

- [适配器](开发语言/Java/设计模式/适配器.md) ★：把不兼容的接口包一层，让它们能协作。
- [桥接](开发语言/Java/设计模式/桥接.md)：抽象与实现两维拆开，各自独立变化。
- [组合](开发语言/Java/设计模式/组合.md)：树形结构统一处理整体与部分。
- [装饰器模式](开发语言/Java/设计模式/装饰器模式.md) ★：功能叠加不改原类，一层层往外包。
- [外观](开发语言/Java/设计模式/外观.md)：给复杂子系统开一扇简单门。
- [享元](开发语言/Java/设计模式/享元.md)：共享细粒度对象的内部状态，省内存。
- [代理](开发语言/Java/设计模式/代理.md) ★：替目标对象站一层，控制访问或加横切逻辑。

## 行为型（独立文件）

- [责任链](开发语言/Java/设计模式/责任链.md)：请求沿链传递，能处理的人接手。
- [命令](开发语言/Java/设计模式/命令.md)：把请求封装成对象，可排队/记录/撤销。
- [迭代器](开发语言/Java/设计模式/迭代器.md)：统一遍历，不暴露集合内部结构。
- [中介者](开发语言/Java/设计模式/中介者.md)：多对多通信收拢到一个中间人。
- [备忘录](开发语言/Java/设计模式/备忘录.md)：存状态快照，随时回滚。
- [观察者](开发语言/Java/设计模式/观察者.md) ★：一处变化，多处订阅者自动收到通知。
- [状态](开发语言/Java/设计模式/状态.md)：行为随内部状态自动切换，消灭状态 if-else。
- [策略](开发语言/Java/设计模式/策略.md) ★：算法做成可替换的策略，调用方选。
- [模板方法](开发语言/Java/设计模式/模板方法.md) ★：父类定流程骨架，子类填细节。
- [访问者](开发语言/Java/设计模式/访问者.md)：操作抽成访问者，新增操作不改被访问的类。
- [解释器](开发语言/Java/设计模式/解释器.md)：给小语言定文法，逐句解释执行。

## 非 GoF 但常用（独立文件）

- [依赖注入](开发语言/Java/设计模式/依赖注入.md)：对象不自己 new 依赖，外部容器组装（Spring 核心）。
- [空对象](开发语言/Java/设计模式/空对象.md)：用「什么都不做」的实现代替 null，消灭判空。
- [对象池](开发语言/Java/设计模式/对象池.md)：复用昂贵对象：连接池、线程池。

## Spring 里的模式（面试常问）

工厂（BeanFactory）、单例（Bean 作用域）、代理（AOP）、观察者（事件）、模板方法（JdbcTemplate）。

## 实战：策略 + 工厂 + 模板方法组合

三种模式最常见的组合拳——以"多渠道消息发送"为例：

```java
// 1. 策略：每种渠道一个实现
interface MsgChannel { void send(Msg m); }
@Component("email") class EmailChannel implements MsgChannel { /*...*/ }
@Component("sms")   class SmsChannel   implements MsgChannel { /*...*/ }

// 2. 工厂：按类型取策略（Spring 直接按 name 注入 Map）
@Service
class ChannelFactory {
    @Resource Map<String, MsgChannel> channels;  // key 就是 @Component 的名字
    MsgChannel get(String type) { return channels.get(type); }
}

// 3. 模板方法：发送流程定骨架，渠道填细节
abstract class AbstractSender {
    final void execute(Msg m) {  // 模板：校验→发送→记日志
        validate(m);
        doSend(m);
        audit(m);
    }
    abstract void doSend(Msg m);
}
```

- 为什么组合：策略解决"选哪个"，工厂解决"怎么拿到"，模板方法解决"流程复用"。
- 你的多渠道消息系统就是这套：策略模式 + 工厂 + 统一发送接口。

## 反模式提醒

- 别为了用模式而用：3 个分支的 if-else 比策略模式好读。
- 过度抽象是技术债：YAGNI，能简单就简单。

## 基础知识补强

### 核心概念与术语

- **设计模式是什么**：在特定场景下反复出现的问题的一套被验证过的解法结构，是经验的命名，不是框架也不是库。
- **模式四要素**：名称（沟通黑话）、问题（什么场景）、方案（类与对象的结构）、效果（收益与代价）。
- **GoF 三大分类**：创建型管"对象怎么建"，结构型管"类与对象怎么组合"，行为型管"对象之间怎么协作与分配职责"。
- **耦合与内聚**：耦合是模块间依赖程度（越低越好改）；内聚是模块内部相关程度（越高越专注）。模式的本质多在降耦合。
- **依赖**：一个类用了另一个类就会形成依赖；依赖越具体（写死实现类），替换成本越高。
- **接口隔离思想**：依赖抽象（接口）而不是实现，上层不关心下层具体是谁，这叫依赖倒置。
- **组合与继承**：继承是"is-a"（复用父类行为但绑死层级）；组合是"has-a"（把对象拼起来，运行时可替换），多数模式优先组合。
- **里氏替换**：子类对象能替换父类出现的任何地方而不破坏行为，违反它时多态就是陷阱。
- **开闭原则**：对扩展开放、对修改关闭；加新功能应该加新类，而不是改已经稳定的老代码。
- **单一职责**：一个类只有一个变化理由；类越胖，它被各种需求拉扯着改坏的概率越高。
- **迪米特法则**：只跟直接朋友说话，不顺着对象链一路调到底（`a.getB().getC().doX()` 就是信号）。
- **UML 关系速记**：继承（空心三角实线）、实现（空心三角虚线）、组合（实心菱形）、聚合（空心菱形）、依赖（虚线箭头）。

### 基础语法与用法

```java
// 用最朴素的代码看"没有模式"与"有了结构"的差别
// 没有结构：加一种支付方式就要改这个方法内部
class PayBad {
    void pay(String type) {
        if ("ali".equals(type)) { /* 支付宝流程 */ }
        else if ("wx".equals(type)) { /* 微信流程 */ }
        else if ("card".equals(type)) { /* 银行卡流程 */ }
        // 每加一种，改一次这里，还要回归测试全部旧分支
    }
}
```

```java
// 结构化的心智模型：先定义抽象，再让变化在实现类里长
interface Pay {
    void pay(long cents);
}
class AliPay implements Pay {
    public void pay(long cents) { /* 支付宝细节只写在这里 */ }
}
class WxPay implements Pay {
    public void pay(long cents) { /* 微信细节只写在这里 */ }
}
// 调用方只认 Pay 接口，新增渠道 = 新增一个实现类，老代码不动
Pay p = new AliPay();
p.pay(1000);
```

```java
// 识别模式的最小词汇：看清三个角色再套名字
// 抽象（接口/抽象类）——定义"能做什么"
// 实现（具体类）     ——定义"具体怎么做"
// 客户端（调用方）   ——只依赖抽象，按需组装实现
class ReportService {
    private final Pay pay;              // 组合：把实现拼进来
    ReportService(Pay pay) { this.pay = pay; }   // 构造器注入
    void checkout(long cents) { pay.pay(cents); }
}
```

```text
类图关系一分钟自测（画不出就说明结构没想清）：
ReportService ──依赖──▶ Pay（接口）
AliPay ──────实现──▶ Pay
WxPay  ──────实现──▶ Pay
读法：箭头从使用方/实现方，指向抽象方；抽象方不反向依赖任何具体类。
```

```java
// 观察一个现成例子：JDK 里的迭代器就是行为型模式的基本形态
List<String> list = Arrays.asList("a", "b");
Iterator<String> it = list.iterator();   // 抽象：统一的遍历方式
while (it.hasNext()) {                   // 客户端不关心底层是数组还是链表

}
```

### 关键机制速览

- **其余模式一句话地图（创建型）**：抽象工厂建一族对象；原型是克隆现成对象；简单工厂不是 GoF 正式成员但最常见。
- **其余模式一句话地图（结构型）**：外观给复杂子系统开一扇简单门；桥接把抽象与实现两维拆开；组合用树形结构统一处理整体与部分；享元共享细粒度对象省内存。
- **其余模式一句话地图（行为型）**：责任链让请求沿链传递到能处理的人；命令把请求封装成对象；迭代器统一遍历；状态让对象在状态变化时改行为；中介者用中间人收拢多对多通信。
- **模式与框架的区别**：模式是思路，你自己写代码落地；框架是可运行的半成品，你填空。框架内部大量使用模式。
- **模式与重构的关系**：先让代码跑起来、重复出现三次以上再抽模式，过早抽象比重复更贵。
- **识别信号 1**：`new` 具体类散落各处、换实现要改一片，多半缺工厂或依赖注入。
- **识别信号 2**：一个方法里按类型分支越长越多，多半缺策略或状态。
- **识别信号 3**：对象创建步骤多且易写错（参数一长串），多半缺建造者。
- **识别信号 4**：两个接口对不上又改不了源码，多半缺适配器。
- **代价账**：每个模式至少多一层间接（接口 + 实现类），换来的是变化被隔离在局部，没有变化就别付这笔账。

### 新手易错点

- **先背名字后找场景**：面试式学习顺序反了。正确顺序是先遇问题，再对照模式名。
- **把简单工厂说成工厂方法**：简单工厂是一个类按参数返回产品；工厂方法是每个产品配一个工厂子类，两者不是一回事。
- **单例写成全局变量思维**：单例管的是"只建一个实例并控制入口"，不是把所有东西都塞成静态。
- **继承用错关系**：只为复用几行代码就继承，会把父类改动风险全继承过来；先问是不是真的 is-a。
- **接口定得太胖**：一个接口塞十几个方法，实现类被迫写空实现，违反接口隔离，拆小更健康。
- **策略和状态混淆**：策略是调用方主动选算法；状态是对象内部随状态自动切换行为，看"谁决定切换"区分。
- **模板方法与策略混淆**：模板方法是继承 + 固定流程骨架；策略是组合 + 整体算法可替换。
- **为了模式改坏可读性**：三行能说清的逻辑套上四层抽象，新人接手先骂半小时，这就是过度设计。
- **忽略默认实现与演进**：接口一旦被多处实现，再加方法会逼所有实现类改；加方法前先考虑给默认实现。
- **只抄结构不抄意图**：类图画得像，但变化点选错，等于白套。先写清"将来哪部分最可能变"再定结构。

## 小技巧与冷知识

【小技巧】模式名本身就是沟通黑话，直接写进评审和注释里：看到一段“按类型选实现”的代码，评审意见写“这里抽成策略模式”比写三行描述省事，类名里带 `Strategy`、`Factory`、`Decorator` 也一样——团队成员一听名字就知道结构、知道该去哪里改。模式的四要素里“名称”就是干这个用的，名字起对了，沟通成本先降一半。

【小技巧】适配器、外观、代理都是“包一层”，按意图区分别按结构区分：接口对不上、改不了源码，用适配器把旧接口翻译成新接口；子系统太复杂、调用方只想调一个简单入口，用外观；想控制访问（权限、懒加载、远程调用），用代理。三者的类图几乎一样，拿不准该叫哪个名字时，先问“这一层到底在干什么”。

【小技巧】代理和装饰器最容易认错，看它在“控制谁进”还是在“加功能”：代理决定目标对象能不能被访问、什么时候被创建（权限校验、懒加载、远程代理），装饰器是在不改原类的前提下往上叠功能（加缓冲、加校验、加日志）。一段包了一层的代码，先问它在管访问还是在加功能，名字就定下来了，评审时也不会把两者混着叫。

【小技巧】观察者用完要记得取消订阅，不然就是内存泄漏：发布者持有订阅者的强引用，订阅者就算业务上已经不用了，只要没 `removeObserver`，GC 就收不走它。生命周期比发布者短的订阅者（比如一次性的界面、临时任务），退出时一定先取消订阅；实在管不住生命周期，订阅关系就用弱引用持有。

【小技巧】模板方法的骨架标 `final`，钩子方法给默认实现：骨架是流程的契约，被子类重写了流程就乱了，所以模板方法本身要 `final`；钩子（hook）是“可改可不改的步骤”，给一个空的或默认的实现，子类按需重写，没重写的就走默认行为。骨架不 final、钩子没默认值，模板方法等于没锁住流程也没给子类留口子。

【小技巧】策略数固定时，用枚举实现策略接口比工厂加 Map 更省事：一个枚举常量就是一个策略实现，天然单例，不用建工厂类、不用维护注册表，调用方直接按枚举值取策略。策略要动态扩展（插件式加载、配置驱动）时再上工厂加 Map；策略就三五种还固定不变，枚举一步到位。

【小技巧】JDK 动态代理只能代理接口，想代理没有接口的类要走 CGLIB：`java.lang.reflect.Proxy` 生成的代理类只实现接口，目标类没有接口就建不出来；Spring AOP 就是按这个规则选的——有接口用 JDK 代理，没接口用 CGLIB 生成子类。给一个类加切面却发现没生效时，先看它有没有接口、走的是哪条代理路。

【小技巧】责任链的链尾一定要兜底：链上没人处理时，要么抛异常、要么记日志、要么给一个默认处理器把请求收下来。请求悄悄丢了是最难查的 bug——调用方以为发出去了，链上没人接也没人报错，排查时只能把整条链打日志重走一遍。

【小技巧】备忘录的快照要深拷贝可变状态，只存引用等于没快照：快照里存的是对象的引用，回滚时引用的对象早被后续操作改了，恢复出来的是改完之后的状态。快照只存需要恢复的那几个字段，且可变对象要拷贝一份；全量深拷贝整个对象图既贵又没必要，存“恢复所需的最小状态”就够了。

【冷知识】GoF 的《设计模式》1994 年出版，23 种模式；模式思想源自建筑师 Christopher Alexander 1977 年的《A Pattern Language》：他先在建筑领域提出“模式语言”，用一套命名的解法描述反复出现的生活与空间问题，四人帮把它搬进了软件领域。设计模式本质上是“给反复出现的问题起名字”，名字本身就是模式的一半价值。

【冷知识】JDK 里到处都是现成的模式：`java.io` 的流就是装饰器模式，`BufferedInputStream` 包着 `FileInputStream`，一层层往上叠缓冲、校验；`Integer` 的 -128 到 127 缓存是享元模式，同一个值返回同一个对象，不重复创建。学模式时先看 JDK 源码里的现成例子，比从零搭 Demo 更容易建立“这东西真有人在用”的体感。

【冷知识】过度用模式有个名字叫“黄金锤子”：手里拿着锤子，看什么都像钉子——刚学会一个模式，就想把它套到所有问题上。反模式（AntiPattern）也是正式概念，1998 年成书，专门收录“看起来像解法、实际是坑”的做法；原文“别为了用模式而用”那条，在反模式的语境里就是最常见的坑之一。

## 面试与自测

1. 策略 + 工厂 + 模板方法这套组合拳里，三种模式各自解决什么问题？
2. 简单工厂和工厂方法有什么区别？
3. 策略和状态怎么区分？模板方法和策略又怎么区分？

### 参考答案

1. 策略解决“选哪个”，工厂解决“怎么拿到”，模板方法解决“流程复用”。以多渠道消息发送为例：每种渠道一个策略实现，工厂按类型取策略，模板方法定校验→发送→记日志的骨架、渠道填细节。
2. 简单工厂是一个类按参数返回产品；工厂方法是每个产品配一个工厂子类，用多态代替分支。两者不是一回事。
3. 策略和状态看“谁决定切换”：策略是调用方主动选算法，状态是对象内部随状态自动切换行为。模板方法和策略看实现手段：模板方法是继承 + 固定流程骨架，策略是组合 + 整体算法可替换。
