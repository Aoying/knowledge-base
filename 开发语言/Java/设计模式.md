# 设计模式

> 模式是"前人踩坑的命名"。别背 23 种，先掌握下面 9 个核心，其余 14 种在「其余模式补全」里速查，GoF 23 种全覆盖。

## 创建型

- **单例**：DruidDataSource、Spring Bean 默认；双重检查 + volatile。
- **工厂**：`ChannelFactory.create("email")`，多渠道消息就靠它。
- **建造者**：`Lombok @Builder`，参数多的对象告别 telescoping 构造器。

## 结构型

- **代理**：Spring AOP、MyBatis Mapper 接口（JDK 动态代理）；静态代理写起来累，动态代理是正道。
- **装饰器**：`BufferedInputStream` 包 `FileInputStream`，功能叠加不改原类。
- **适配器**：把不兼容的接口包一层；老系统对接新规范时用。

## 行为型

- **策略**：`if-else` 超过 3 个分支就换策略模式 + Map 注册；支付/渠道选择是典型。
- **观察者**：Spring Event、MQ 解耦，本质都是"发布-订阅"。
- **模板方法**：定骨架，子类填细节；和策略模式常一起用。

## Spring 里的模式（面试常问）

工厂（BeanFactory）、单例（Bean 作用域）、代理（AOP）、观察者（事件）、模板方法（JdbcTemplate）。

## 其余模式补全（GoF 全集速查）

上面 9 个是高频核心，下面 14 种补齐 GoF 全集。每条给：意图、结构要点、Java 里的典型落点。先认得出、查得到，真要用时再展开成完整实现。

### 创建型补

- **抽象工厂**：建「一族」互相配套的对象（不是单个）。结构：抽象工厂接口 + 多个产品族实现。落点：跨库切换（MySQL 族 vs Oracle 族的连接/命令/事务对象）、跨平台 UI 组件族。信号：一组对象总是成套出现、要整体换供应商。
- **原型**：不重新构造，克隆现成对象再改差异。结构：`Cloneable`/`clone()` 或拷贝构造、序列化深拷贝。落点：配置对象模板复制、游戏怪/装备批量生成、报表模板。坑：深拷贝与浅拷贝——引用字段默认共享，改克隆体连原体一起变。
- **工厂方法**（与简单工厂区分）：每个产品配一个工厂子类，调哪个工厂决定建哪个产品。落点：`Calendar.getInstance()`、日志框架的 LoggerFactory。简单工厂是一个类按参数分支返回，工厂方法是把「分支」变成「多态」。

### 结构型补

- **外观（Facade）**：给复杂子系统开一扇简单门，客户端只跟门面打交道。落点：下单接口内部串库存/支付/物流三个系统，对外只露一个 `placeOrder()`。与适配器区别：外观是简化调用，适配器是转换接口。
- **桥接**：把「抽象维度」与「实现维度」拆开各自独立变化，用组合连起来。落点：消息发送（抽象）× 渠道实现（短信/邮件/推送）两维自由组合，避免类爆炸（3 种消息 × 3 种渠道不用写 9 个类）。
- **组合（Composite）**：树形结构统一对待整体与部分，客户端对单节点和整棵树用同一套 API。落点：组织架构/部门树、文件目录、菜单权限树、审批事项的父子事项（你的 parentId 场景本质就是组合结构）。
- **享元（Flyweight）**：共享细粒度对象的内部状态，外部状态调用时传入，用「共享」换内存。落点：`Integer.valueOf` 的 -128~127 缓存、字符串常量池、棋盘上成千上万个同色棋子。信号：对象数量巨大且大部分状态相同。

### 行为型补

- **责任链**：请求沿链传递，每个处理者决定「自己处理还是传给下一个」。落点：Servlet Filter、Spring 拦截器、审批流逐级审批、日志级别过滤。变体：链可以中途停（审批驳回）、也可以全过（过滤器链）。坑：链太长排查难，必须有日志打点。
- **命令**：把「请求」封装成对象，于是可以排队、记录、撤销、重做。落点：任务队列与延迟执行、操作日志回放、编辑器 undo/redo、MQ 消息本身就是命令的分布式版。结构：Command 接口 + 具体命令 + 调用者 + 接收者四件套。
- **迭代器**：统一遍历，不暴露集合内部结构。落点：`Iterator`/`Iterable`、分页游标读取大表（按 id 游标翻页就是迭代器思想）。Java 里现成可用，自己实现主要出现在自研集合或流式数据源。
- **状态**：对象行为随内部状态自动切换，消灭「按状态大 if-else」。落点：订单状态机（待付→已付→已发货→完成，每个状态能做的操作不同）、Flowable 节点状态、连接/会话生命周期。与策略区别：策略由调用方外部选，状态由对象内部流转。
- **中介者**：多对多通信收拢到一个中间人，同事之间不直接互相引用。落点：聊天室、航班塔台式调度、复杂表单字段联动。Spring 里的 `DispatcherServlet` 就是前端控制器式的中介。信号：类之间网状互相调用，改一个动一片。
- **备忘录**：保存对象内部状态快照，之后可回滚，不暴露实现细节。落点：编辑器撤销、游戏存档、流程驳回后恢复到上一节点的数据。你的小说引擎 Snapshot 机制就是备忘录的工程化：存状态、随时回档、沙盒分支。
- **访问者**：把「对一组对象做的操作」抽成访问者类，新增操作不用改被访问的类。落点：报表系统对同一批单据做「打印/导出/稽核」三种操作、AST 节点处理、规则引擎对多种事实做校验。代价：被访问的元素类型一变，所有访问者都得改——元素稳定、操作多变时才用。
- **解释器**：给一门小语言定文法，用类表示语法规则并逐句解释执行。落点：规则表达式（金额 > 1000 且 状态 = 已审）、EL/SpEL 这类表达式求值、自研 DSL。信号：有固定文法的小句子反复出现。真正项目里很少手写，多是直接用现成表达式引擎，手写只适合极简规则。

### 非 GoF 但常用

- **依赖注入（DI）**：不算 GoF 模式，但思想同源——对象不自己 `new` 依赖，由外部容器组装。Spring 的核心，本质是把工厂 + 单例 + 组合的组装工作外包给容器。
- **空对象（Null Object）**：用一个「什么都不做」的实现代替 null，消灭满屏判空。如无日志时注入 `NoOpLogger`，查无用户时返回 `GuestUser` 而非 null。
- **对象池**：复用昂贵对象（连接、线程）。Druid 连接池、线程池都是它；与享元区别：池管生命周期与借还，享元管状态共享。

## 实战：策略 + 工厂 + 模板方法组合

三种模式最常见的组合拳——以"多渠道消息发送"为例：

```java
// 1. 策略：每种渠道一个实现
interface MsgChannel { void send(Msg m); }
@Component("email") class EmailChannel implements MsgChannel { /*...*/ }
@Component("sms")   class SmsChannel   implements MsgChannel { /*...*/ }

// 2. 工厂：按类型取策略（Spring 直接按 name 注入 Map）
@Service
class ChannelFactory {
    @Resource Map<String, MsgChannel> channels;  // key 就是 @Component 的名字
    MsgChannel get(String type) { return channels.get(type); }
}

// 3. 模板方法：发送流程定骨架，渠道填细节
abstract class AbstractSender {
    final void execute(Msg m) {  // 模板：校验→发送→记日志
        validate(m);
        doSend(m);
        audit(m);
    }
    abstract void doSend(Msg m);
}
```

- 为什么组合：策略解决"选哪个"，工厂解决"怎么拿到"，模板方法解决"流程复用"。
- 你的多渠道消息系统就是这套：策略模式 + 工厂 + 统一发送接口。

## 反模式提醒

- 别为了用模式而用：3 个分支的 if-else 比策略模式好读。
- 过度抽象是技术债：YAGNI，能简单就简单。

## 基础知识补强

### 核心概念与术语

- **设计模式是什么**：在特定场景下反复出现的问题的一套被验证过的解法结构，是经验的命名，不是框架也不是库。
- **模式四要素**：名称（沟通黑话）、问题（什么场景）、方案（类与对象的结构）、效果（收益与代价）。
- **GoF 三大分类**：创建型管"对象怎么建"，结构型管"类与对象怎么组合"，行为型管"对象之间怎么协作与分配职责"。
- **耦合与内聚**：耦合是模块间依赖程度（越低越好改）；内聚是模块内部相关程度（越高越专注）。模式的本质多在降耦合。
- **依赖**：一个类用了另一个类就会形成依赖；依赖越具体（写死实现类），替换成本越高。
- **接口隔离思想**：依赖抽象（接口）而不是实现，上层不关心下层具体是谁，这叫依赖倒置。
- **组合与继承**：继承是"is-a"（复用父类行为但绑死层级）；组合是"has-a"（把对象拼起来，运行时可替换），多数模式优先组合。
- **里氏替换**：子类对象能替换父类出现的任何地方而不破坏行为，违反它时多态就是陷阱。
- **开闭原则**：对扩展开放、对修改关闭；加新功能应该加新类，而不是改已经稳定的老代码。
- **单一职责**：一个类只有一个变化理由；类越胖，它被各种需求拉扯着改坏的概率越高。
- **迪米特法则**：只跟直接朋友说话，不顺着对象链一路调到底（`a.getB().getC().doX()` 就是信号）。
- **UML 关系速记**：继承（空心三角实线）、实现（空心三角虚线）、组合（实心菱形）、聚合（空心菱形）、依赖（虚线箭头）。

### 基础语法与用法

```java
// 用最朴素的代码看"没有模式"与"有了结构"的差别
// 没有结构：加一种支付方式就要改这个方法内部
class PayBad {
    void pay(String type) {
        if ("ali".equals(type)) { /* 支付宝流程 */ }
        else if ("wx".equals(type)) { /* 微信流程 */ }
        else if ("card".equals(type)) { /* 银行卡流程 */ }
        // 每加一种，改一次这里，还要回归测试全部旧分支
    }
}
```

```java
// 结构化的心智模型：先定义抽象，再让变化在实现类里长
interface Pay {
    void pay(long cents);
}
class AliPay implements Pay {
    public void pay(long cents) { /* 支付宝细节只写在这里 */ }
}
class WxPay implements Pay {
    public void pay(long cents) { /* 微信细节只写在这里 */ }
}
// 调用方只认 Pay 接口，新增渠道 = 新增一个实现类，老代码不动
Pay p = new AliPay();
p.pay(1000);
```

```java
// 识别模式的最小词汇：看清三个角色再套名字
// 抽象（接口/抽象类）——定义"能做什么"
// 实现（具体类）     ——定义"具体怎么做"
// 客户端（调用方）   ——只依赖抽象，按需组装实现
class ReportService {
    private final Pay pay;              // 组合：把实现拼进来
    ReportService(Pay pay) { this.pay = pay; }   // 构造器注入
    void checkout(long cents) { pay.pay(cents); }
}
```

类图关系一分钟自测（画不出就说明结构没想清）：
ReportService ──依赖──▶ Pay（接口）
AliPay ──────实现──▶ Pay

读法：箭头从使用方/实现方，指向抽象方；抽象方不反向依赖任何具体类。

// 观察一个现成例子：JDK 里的迭代器就是行为型模式的基本形态

### 关键机制速览

- **其余模式一句话地图（创建型）**：抽象工厂建一族对象；原型是克隆现成对象；简单工厂不是 GoF 正式成员但最常见。
- **其余模式一句话地图（结构型）**：外观给复杂子系统开一扇简单门；桥接把抽象与实现两维拆开；组合用树形结构统一处理整体与部分；享元共享细粒度对象省内存。
- **其余模式一句话地图（行为型）**：责任链让请求沿链传递到能处理的人；命令把请求封装成对象；迭代器统一遍历；状态让对象在状态变化时改行为；中介者用中间人收拢多对多通信。
- **模式与框架的区别**：模式是思路，你自己写代码落地；框架是可运行的半成品，你填空。框架内部大量使用模式。
- **模式与重构的关系**：先让代码跑起来、重复出现三次以上再抽模式，过早抽象比重复更贵。
- **识别信号 1**：`new` 具体类散落各处、换实现要改一片，多半缺工厂或依赖注入。
- **识别信号 2**：一个方法里按类型分支越长越多，多半缺策略或状态。
- **识别信号 3**：对象创建步骤多且易写错（参数一长串），多半缺建造者。
- **识别信号 4**：两个接口对不上又改不了源码，多半缺适配器。
- **代价账**：每个模式至少多一层间接（接口 + 实现类），换来的是变化被隔离在局部，没有变化就别付这笔账。

### 新手易错点

- **先背名字后找场景**：面试式学习顺序反了。正确顺序是先遇问题，再对照模式名。
- **把简单工厂说成工厂方法**：简单工厂是一个类按参数返回产品；工厂方法是每个产品配一个工厂子类，两者不是一回事。
- **单例写成全局变量思维**：单例管的是"只建一个实例并控制入口"，不是把所有东西都塞成静态。
- **继承用错关系**：只为复用几行代码就继承，会把父类改动风险全继承过来；先问是不是真的 is-a。
- **接口定得太胖**：一个接口塞十几个方法，实现类被迫写空实现，违反接口隔离，拆小更健康。
- **策略和状态混淆**：策略是调用方主动选算法；状态是对象内部随状态自动切换行为，看"谁决定切换"区分。
- **模板方法与策略混淆**：模板方法是继承 + 固定流程骨架；策略是组合 + 整体算法可替换。
- **为了模式改坏可读性**：三行能说清的逻辑套上四层抽象，新人接手先骂半小时，这就是过度设计。
- **忽略默认实现与演进**：接口一旦被多处实现，再加方法会逼所有实现类改；加方法前先考虑给默认实现。
- **只抄结构不抄意图**：类图画得像，但变化点选错，等于白套。先写清"将来哪部分最可能变"再定结构。
