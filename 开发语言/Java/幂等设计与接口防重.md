# 幂等设计与接口防重

幂等不是某一个技巧，而是一组分层手段的组合：同一请求被重复递送时，系统只产生一次业务效果。本篇是深篇增量——幂等键与状态机校验的基础见《接口设计与文档》第 5 节，那一节讲“是什么”，本篇讲“全景怎么选、每种手段的边界在哪”。

## 1. 防重全景：分层看

重复递送的来源各不相同，手段要按层配：

| 层 | 重复来源 | 主要手段 |
|---|---|---|
| 前端层 | 用户连点、表单重复提交 | 防抖、按钮置灰、提交后禁用 |
| 网关层 | 客户端重试、超时重发 | 请求去重（按幂等键） |
| 接口层 | 同一业务请求被调两次 | 幂等键、Token 机制 |
| 服务层 | 审批、状态流转被并发触发 | 状态机前置校验 |
| 数据层 | 最后一道防线，前面全漏 | 唯一索引、业务唯一键 |
| 消费层 | 消息重投、消费失败重试 | 消息幂等、消费记录表 |

关键结论：前端手段只能防“手误”，不能防“重发”——网络超时后客户端重试、消息中间件重投，前端根本看不到。服务端手段才是防重本体，前端只是体验优化。

## 2. 前端手段：防抖与按钮置灰

- 防抖（debounce）：连续点击只认最后一次，适合搜索框输入；提交按钮不要用防抖，用“提交后禁用”。
- 按钮置灰：点击后立即禁用按钮，请求结束（成功或失败）再恢复；失败后必须恢复，否则用户以为系统卡死。
- 边界：只防同页面、同会话的连点。防不住刷新后重提、换设备重提、程序化重试。写进检查表里的一条就是：前端防重永远不计入防重方案，只算体验。

## 3. Token 机制：一次性提交令牌

流程：进入表单页时服务端发一个一次性 Token（存 Redis，带过期）；提交时带上 Token，服务端校验通过后立即删除 Token，校验不通过直接拒绝。

- 适用：表单提交、创建类接口，且调用方是浏览器页面（能先取 Token 再提交）。
- 局限：Token 要多一次往返；纯 API 调用方（第三方系统、定时任务）配合成本高，这时改用幂等键；Token 被删除后“合法重试”也会被拒，所以只适合“提交一次即生效”的场景，不适合需要重试的调用。

## 4. 幂等键设计

幂等键（Idempotency-Key）是调用方给一次业务操作起的唯一名字，服务端按它去重。

- 键怎么来：客户端生成的 UUID 最省事；有业务单号的直接用业务单号（订单号、申请单号），天然唯一且可查。
- 键存哪：Redis（带 TTL，适合高频）或数据库防重表（适合要留痕审计的场景）。键的存活期要覆盖“调用方可能重试的时间窗”，太短等于没防，太长占存储。
- 结果回放：首次执行成功后把结果（或结果摘要）随键一起存下来；重复请求命中键时直接返回首次结果，而不是重新执行业务——否则“查单成功但建单重复”的半吊子幂等毫无意义。
- 进行中状态：键要区分“处理中”和“已完成”。处理中的重复请求应返回“处理中”（或等待），而不是并行再跑一次；否则两个并发请求同时发现“键不存在”，双双执行。

```python
# 防重表状态机演示（内存 dict 模拟，逻辑与 DB 版一致）
store = {}

def submit(key, action):
    st = store.get(key)
    if st == "done":
        return "duplicate, return first result"
    if st == "processing":
        return "duplicate, still processing"
    store[key] = "processing"
    try:
        action()
    except Exception:
        del store[key]  # 失败放行，允许重试
        raise
    store[key] = "done"
    return "processed"

print(submit("order-001", lambda: None))
print(submit("order-001", lambda: None))
```

## 5. 唯一索引兜底：最后一道防线

数据库唯一索引（唯一键、联合唯一键）是成本最低、可靠性最高的防重手段：前面所有手段漏网，唯一约束都会在写入时拦住。

- 用法：业务唯一字段（订单号、申请单号、幂等键）建唯一索引；写入冲突时捕获唯一键异常，转为“查询已有记录并返回”，不要把异常直接抛给调用方。
- 边界：唯一索引只防“重复建”，不防“重复改”——状态流转类问题靠状态机校验；它也不负责“返回首次结果”，结果回放要幂等键或防重表配合。

## 6. 防重表：独立记录的设计

高频或强审计场景适合一张独立防重表，字段：幂等键、业务类型、状态（处理中/成功/失败）、首次结果摘要、创建时间、过期时间。

- 状态流转：处理中 → 成功（终态，不可再变）；处理中 → 失败（可重试，失败原因记下来）；成功是终态，任何重复请求都走“返回首次结果”分支。
- 过期清理：按业务保留期定时清理过期键；清理前确认没有“处理中”卡住的记录，卡住的要人工介入而不是自动删。
- 与业务表的关系：防重表只记“这次操作做过没有”，业务数据仍在业务表里；不要把防重表当业务表查，也不要在业务表里塞防重字段把职责搅在一起。

## 7. 消息幂等：消费端的防重

消息重投是常态（消费失败重试、Broker 重发、消费者重启后位点回退），消费端必须自带幂等。

- 做法：消费逻辑先按业务唯一键（订单号、事件 ID）查消费记录表或业务表，已处理则跳过；处理与“记消费记录”要在同一个本地事务里，否则“处理了但没记下来”下次还会重跑。
- 与生产端的关系：生产端去重（幂等生产者）只能减少重复，不能保证零重复；消费端幂等是必选项，生产端去重是可选项。
- 相关篇：消息侧的顺序、延迟、死信等语义见《消息队列进阶语义》，本篇只讲消费端防重这一环。

## 8. 状态机幂等：流转类的正解

审批、确认、发货这类“状态只能往前走”的操作，防重靠状态机前置校验：更新时带条件 `WHERE status = 'PENDING'`，影响行数为 0 说明已被处理过，返回 409 或当前状态。基础形态见《接口设计与文档》第 5 节，本篇补三条深层规则：

- 终态不可逆：已到终态（通过/驳回/作废）的单据，任何流转请求都直接拒绝，不要出现“驳回后再通过”的回流。
- 并发两人同时点：靠条件更新的行锁语义决胜负，先到者成功、后到者看到影响行数 0 后返回当前状态；不要靠“先查状态再更新”的两步，先查后改中间有竞态窗口。
- 状态图先行：新业务上线前先画状态图（哪些状态、哪些迁移动作合法），状态机校验的代码按图生成条件，图和代码不一致是流转类 bug 的头号来源。

## 9. 组合清单：按场景选手段

| 场景 | 必选 | 可选 | 不适用 |
|---|---|---|---|
| 浏览器表单提交 | 服务端幂等键或 Token | 按钮置灰 | 只靠前端 |
| 支付/创建类 API | 幂等键 + 唯一索引兜底 | 防重表（强审计时） | Token（第三方难配合） |
| 审批/状态流转 | 状态机前置校验 | 幂等键（防同一人连点） | 只靠唯一索引 |
| 消息消费 | 消费记录表 + 业务唯一键 | 幂等生产者 | Token |
| 定时任务重跑 | 业务唯一键或防重表 | 分布式锁（防多实例并发跑） | 前端手段 |

## 10. 落地检查表

- [ ] 每个写接口都标出“重复递送会怎样”，没标的默认按“会重复”处理。
- [ ] 幂等键的生成方、存储位置、TTL、结果回放、进行中状态五项都有明确答案。
- [ ] 唯一索引已建，且唯一键冲突时返回已有结果而不是 500。
- [ ] 状态流转类接口全部是条件更新，没有“先查后改”。
- [ ] 消息消费端有消费记录表，且处理与记账同事务。
- [ ] 前端防重只算体验，不计入防重方案。

## 11. 常见误区

- “前端置灰了所以不会重复”：防不住超时重试、消息重投、换设备重提。
- “幂等键存了但不存结果”：重复请求命中键后重新执行业务，等于没做。
- “唯一索引能防一切重复”：它只防重复建，不防重复改、不负责结果回放。
- “处理中状态不区分”：两个并发请求同时发现键不存在，双双执行，是最常见的幂等失效。

## 面试与自测

1. 前端按钮置灰为什么不能算防重方案？服务端防重必须覆盖哪几种重复来源？
2. 幂等键的“进行中”状态为什么不能省略？省略后会出现什么竞态？
3. 审批流转类接口为什么必须用条件更新，而不能“先查状态再更新”？

### 参考答案

1. 因为前端置灰只防同页面连点，防不住网络超时后的客户端重试、消息中间件重投、刷新或换设备重提。服务端防重必须覆盖：用户连点、超时重试、消息重投、定时任务重跑、多实例并发触发。
2. 因为不区分进行中，两个并发请求可能同时发现键不存在而双双执行，幂等失效。正确做法是键分处理中与已完成两态：处理中的重复请求返回“处理中”或等待，已完成的返回首次结果。
3. 因为“先查后改”中间有竞态窗口：两人同时查到 PENDING、同时更新，都会成功。条件更新（WHERE status='PENDING'）把判断与写入合成一个原子操作，先到者成功、后到者影响行数为 0，靠行锁语义决胜负。
