# 分布式锁实现与选型

单机锁（synchronized、ReentrantLock）只在同一个 JVM 内有效；服务多实例部署后，两个实例各拿各的锁，互斥就不存在了。分布式锁就是把“互斥”这件事放到多个实例都能看到的共享存储上做。本篇讲四种实现的原理与选型——Redis 锁的正确形态、看门狗续期、RedLock 争议与 fencing token 已在《Redis-缓存问题与分布式锁》讲透，本篇不再重复，只在相关处一句话指回。

## 1. Redis 实现：SET NX + 唯一持有者

原理：`SET key owner-id NX EX ttl`——NX 保证只有一个实例能建键成功，owner-id（UUID）标识持有者，EX 给锁一个过期时间防死锁。

- 释放：必须用 Lua 脚本“校验 owner-id 再删”合成原子操作；先 GET 再 DEL 中间有窗口，锁可能已被续期或易主，删错别人的锁。
- 续期：业务耗时可能超过 TTL，靠看门狗后台线程在 TTL 过半时续期；看门狗本身挂了锁会过期，业务要能接受“锁过期后被别人接管”的语义。
- 适用：高频、短临界区、对锁丢失有一定容忍度的场景；强正确性场景要叠加 fencing token（见 Redis 篇第 6 节）。

```java
// Redis 分布式锁骨架：加锁、Lua 安全释放、续期只列入口
// 加锁：SET key uuid NX EX 30
// 释放：EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 key uuid
// 续期：后台线程在 TTL 过半时对持有中的锁执行 PEXPIRE，业务结束或异常时取消续期
```

## 2. ZooKeeper 实现：临时顺序节点

原理：所有竞争者在同一个父节点下创建临时顺序节点，编号最小的持有锁；其他节点监听自己前一个节点的删除事件，前驱消失时按序接管。

- 释放：会话断开时临时节点自动删除，锁随之释放——这是 ZooKeeper 锁最大的优点，不依赖 TTL 猜业务时长。
- 正确性：ZooKeeper 的顺序一致性（ZAB 协议）保证同一时刻只有一个最小节点，锁的正确性不依赖时钟，时钟漂移影响不到它。
- 代价：要维护一个 ZooKeeper 集群；监听是“羊群效应”的反面教材——每个节点只监听前驱，不是所有节点监听同一个节点，所以唤醒是链式的，不会惊群。
- 适用：对正确性要求高、已有 ZooKeeper 基础设施（注册中心、配置中心同源）的系统。

## 3. etcd 实现：租约 + 事务 CAS

原理：客户端先拿一个带 TTL 的租约（lease），再用事务“比较并创建”抢锁键；抢到锁的键绑定租约，租约靠心跳续期，租约过期键自动删除。

- 释放：主动删除锁键，或租约过期自动失效；官方 v3 lock API 把这套流程封装好，业务代码只调 lock/unlock。
- 正确性：etcd 的 Raft 强一致，锁语义同样不依赖时钟；但要注意租约续期失败时的语义——租约一过期锁就没了，业务要处理“锁丢了但业务还在跑”的情况。
- 适用：Kubernetes 生态内（etcd 现成）、Go 服务为主的系统；Java 体系用 etcd 要额外接客户端，运维成本高于 Redis。

## 4. 数据库实现：唯一索引与行锁

两种路子：

- 悲观路子：`SELECT ... FOR UPDATE` 锁住一行（锁记录表），事务提交即释放；实现最简单，但锁持有期间占数据库连接，长临界区会拖垮连接池。
- 乐观路子：锁记录表 + 版本号，抢锁时 `UPDATE ... SET owner=?, version=version+1 WHERE id=? AND version=?`，影响行数 1 为抢到；续期靠心跳线程定时 UPDATE 延长过期时间。
- 边界：数据库锁的性能天花板最低，不适合高频抢锁；适合低频、已有数据库且不想引入新组件的场景（如定时任务单实例抢跑、配置下发互斥）。

## 5. 对比选型表

| 维度 | Redis | ZooKeeper | etcd | 数据库 |
|---|---|---|---|---|
| 正确性基础 | 最终一致 + TTL（需 fencing 补强） | 强一致（ZAB） | 强一致（Raft） | 依赖事务隔离级别 |
| 抢锁延迟 | 最低（内存操作） | 中（写 quorum） | 中（写 quorum） | 最高（磁盘 + 连接） |
| 锁丢失风险 | TTL 过期、GC 停顿续期失败 | 会话失效才丢 | 租约过期才丢 | 连接断开事务回滚 |
| 运维成本 | 已有 Redis 则最低 | 需独立集群 | K8s 内现成 | 零新增组件 |
| 适用场景 | 高频短锁、缓存式互斥 | 强正确性、已有 ZK | K8s 生态、强正确性 | 低频、已有 DB、抢跑互斥 |

选型口诀：已有组件优先——有 Redis 且容忍 fencing 补强就用 Redis；正确性压倒一切且已有 ZK/etcd 就用它们；什么都没有、频率又低，数据库锁最省事。

## 6. 故障场景：锁丢了怎么办

- 时钟漂移：依赖 TTL 的锁（Redis、etcd 租约）受时钟影响，节点时钟跳变会让锁“提前过期”或“过期了还被认为有效”；强一致锁（ZK）不受时钟影响，这是选型时最容易被低估的一点。
- GC 停顿：持有锁的进程 Full GC 几十秒，看门狗线程也被冻住，续期失败、锁过期、另一个实例接管，旧实例恢复后继续写共享资源——这是分布式锁最经典的失效模式，解法是 fencing token（见 Redis 篇第 6 节），不是把 TTL 调大。
- 网络分区：分区后旧持有者以为自己还有锁、新持有者也拿到锁，双写已成事实；事后靠 fencing token 的单调递增序号让旧写被拒绝，而不是靠“分区不会发生”安慰自己。
- 锁超时与业务时长：TTL 要大于“业务正常耗时 + 一次 GC 停顿”的量级，但 TTL 越大锁丢失后的空窗越长；没有万能值，按业务 P99 耗时定，超时的业务要能安全中断。

## 7. 主从异步复制丢锁：完整时序与选型结论

本篇 §6 讲了锁丢的几种故障场景；本节把其中最容易被低估的一种展开讲透：Redis 主从异步复制下的丢锁。它和 §6 的 GC 停顿、时钟漂移不是一回事——那两种是“持有者自己掉链子”，这一种是“锁根本没来得及告诉所有人”。

### 完整时序

1. **T0**：客户端 A 在旧主上 `SET lock:order:1001 uuid-A NX EX 30` 成功，A 认为自己持锁，进入临界区。
2. **T1**：旧主把这条写操作放进复制积压区，准备异步发往从节点；但在发出之前，存在一个复制窗口——窗口大小取决于复制延迟，可用 `INFO replication` 的偏移量差量出，不是理论值。
3. **T2**：旧主宕机，窗口内的写操作（包括这把锁）永久丢失，从节点从没见过它。
4. **T3**：哨兵判定旧主下线，提拔从节点为新主；新主的锁表里没有 `lock:order:1001`。
5. **T4**：客户端 B 在新主上 `SET lock:order:1001 uuid-B NX EX 30` 成功——NX 检查通过，因为新主眼里这把锁根本不存在。
6. **T5**：A 仍认为自己持锁（它的 TTL 还没到，也没收到任何通知），A、B 同时进入临界区，双执行已成事实。

关键点：**丢的不是某一次运气差，而是窗口内的一切写**。锁只是其中一种写；同一窗口内丢的还可能有缓存更新、计数器，全都一样。所以“锁丢了”从来不是孤立事件，而是异步复制语义的必然代价。

### RedLock 为什么只能缓解，不能根除

RedLock 的机制与争议已在 Redis-缓存问题与分布式锁 §6 讲透，这里只补它和异步复制的关系：

- **缓解的原理**：RedLock 向 5 个独立主节点加锁、拿到多数派才算成功。单节点 failover 丢一把锁不影响多数派判定——3／5 还在，锁整体仍有效。异步复制丢锁从“单点故障即丢”降级为“多数派同时出问题才丢”，概率确实小了一个量级。
- **不能根除的四条理由**：
  1. **时间假设还在**：RedLock 成立要求有界网络延迟、有界执行时间、时钟大体同步（Kleppmann 质疑第 1 条）。时钟跳变、GC 长暂停照样能让锁在持有者不知情时过期，多数派挡不住时间假设的崩塌。
  2. **节点崩溃重启丢状态**：节点重启后锁表为空，会把已授出的锁再授给别人——除非重启后延迟一段时间（大于锁的最大 TTL）再对外授锁。运维上漏了这条延迟，RedLock 的多数派一样被击穿。
  3. **节点自身配主从等于把问题搬进来**：如果为了高可用给每个 RedLock 节点再配一个从节点，failover 时的异步复制丢锁会在每个节点内部重演，多数派的意义被掏空。RedLock 的 5 个节点必须是独立主节点，不能再套一层主从。
  4. **没有 fencing，旧写照样进**：即使锁机制本身完美，旧持有者醒来后仍可能误写（Kleppmann 质疑第 2 条）。锁丢失只是把“误写”从可能变成必然；真正兜底的是 fencing token 的单调代次校验，不是锁本身。

### 三档选型结论

| 方案 | 可接受的场景 | 不可接受的场景 | 备注 |
|---|---|---|---|
| 单 Redis（SET NX＋uuid＋Lua＋看门狗） | 削峰、去重、防重复提交、缓存回源互斥等效率场景；能容忍 failover 窗口内丢锁 | 资金、库存扣减等正确性场景 | 成本最低；丢锁窗口可用复制偏移量量出并写进业务风险评估 |
| RedLock（5 独立节点＋多数派） | 效率场景但要求比单点更高的可用性，且能接受 5 节点成本 | 正确性场景——没有 fencing 就不算正确性锁 | 节点必须是独立主节点，不能再套主从；重启必须延迟授锁 |
| ZooKeeper／etcd（ZAB／Raft 强一致） | 正确性场景；已有对应基础设施 | 高频抢锁（延迟与运维成本扛不住） | 锁语义不依赖时钟；租约／会话过期才丢锁，见本篇 §2、§3 |

统一口径（与两篇已有结论一致，不重复论证）：**无论选哪档，正确性场景都要 fencing token 或 DB 唯一约束、幂等键兜底**。锁只回答“谁持有”，不回答“这次持有比上次新多少”；没有代次校验，任何锁方案都不能单独做正确性裁决。

## 8. 锁粒度与分段锁

- 按业务键分段：锁 key 带业务维度（订单号、用户 ID、库存 SKU），不同键互不阻塞；不要用一把全局锁串行化所有业务。
- 热点 key 打散：同一 SKU 被高频抢时，把锁拆成 N 段（如 SKU + hash % 16），抢锁先抢段，段内再串行；代价是跨段操作要按固定顺序拿锁，防死锁。
- 拿锁顺序：一次拿多把锁时全局固定顺序（按 key 排序后依次拿），否则两个业务以相反顺序拿锁必然死锁。
- 锁内只放临界区：锁里不要调外部接口、不要等用户输入；临界区越长，锁丢失与超时的概率越高。

## 9. 常见误区

- “Redis 锁 SETNX 就够了”：缺唯一持有者校验的释放会删别人的锁，缺 TTL 会死锁，缺续期会中途丢锁，三者缺一不可。
- “TTL 调大就安全”：TTL 大只推迟丢锁，不解决 GC 停顿与分区下的双写；正确性靠 fencing，不靠 TTL。
- “锁能替代幂等”：锁只保证同一时刻一个在跑，不保证重复请求只生效一次；锁 + 幂等键才是完整方案。
- “一把锁管所有”：全局锁是性能瓶颈的头号来源，先按业务键分段再谈优化。

## 小技巧与冷知识

【小技巧】抢锁别用无限阻塞的 `lock()`，用带等待超时的 `tryLock(waitTime, leaseTime)`：拿不到锁时在 waitTime 后直接返回失败走降级，而不是在原地一直等到天荒地老。Redisson 的 tryLock 就是这个语义——等锁的上限和锁的租期是两个独立参数，排障时先分清这次卡住的是“等不到锁”还是“锁被别人一直占着”。

【小技巧】锁 key 一定要带环境前缀：`lock:prod:order:1001` 和 `lock:dev:order:1001` 必须是两个 key。测试环境和生产共用一个 Redis 时，没有环境前缀的 key 会让测试代码抢走生产的锁，反过来也一样；key 命名里带上业务维度（原文 §8 的分段思路）再加环境维度，两层前缀都不能省。

【小技巧】锁和缓存别混用同一个 Redis 实例的同一个库：锁的 key 过期、逐出策略和缓存 key 不一样，缓存库开了 allkeys-lru 逐出时，锁 key 可能在 TTL 没到之前就被当成缓存逐掉。锁单独放一个库或单独的实例，逐出策略设成 noeviction，锁的生命周期只由 TTL 和显式释放决定，不受缓存逐出干扰。

【小技巧】释放锁之前先确认“这把锁现在还是我的”：Lua 脚本校验 owner-id 再删（原文 §1）是原子操作，但业务代码里还有一层要查——当前线程是否仍是持有者（Redisson 的 `isHeldByCurrentThread()`）。进程 GC 停顿后锁已过期易主，醒来的旧持有者在 finally 里直接解锁会把新持有者的锁删掉；先校验、再释放，finally 里的解锁也要走同一条校验路径。

【小技巧】ZooKeeper 锁不要自己手写临时顺序节点，用 Curator 的 `InterProcessMutex`：它把“建顺序节点、只监听前驱、会话断开自动释放”整套流程封装好了，而且是可重入的——同一线程重复加锁只加计数器，不会把自己堵死。自己手写容易在“前驱节点已删但监听还没挂上”的竞态窗口里漏掉唤醒，Curator 内部用 `getChildren` + 监听的组合规避了这个窗口。

【小技巧】数据库锁不要对没有索引的列做 `SELECT ... FOR UPDATE`：MySQL 里它走全表扫描，会把整张表符合条件的行都锁住，等于一把表锁。锁记录表的抢锁字段（比如业务键）必须有唯一索引，`FOR UPDATE` 只锁住索引命中的那一行；没索引的悲观锁在并发一上来就变成全表串行，性能比不用锁还差。

【小技巧】etcd 锁的租约心跳和业务线程要解耦：租约续期靠客户端后台的心跳协程，一旦业务线程被长 GC 冻住，心跳停了租约就过期，锁丢了业务还在跑。处理办法和 Redis 看门狗一样——业务开始前先评估“最长一次停顿会不会超过租约 TTL”，续期失败时业务必须能安全中断，而不是假装锁还在；etcd 的 v3 lock API 只封装了抢锁流程，续期失败的语义还是要业务自己兜底。

【小技巧】拿多把分布式锁时，除了按 key 排序（原文 §8），还要给整组加锁设一个总超时：逐个拿锁时如果中间某把拿不到，前面已拿到的锁要按逆序释放，不能留着等。常见 bug 是“拿了 A、等 B 等到超时，A 一直占着不放”，别的业务等 A 等到超时，链式死锁就这么来的；总超时一到，立刻逆序释放已持有的锁再整体重试。

【小技巧】锁超时告警要看“锁等待时长”，不是只看“抢锁失败次数”：抢锁失败可能是业务正常争用，但等待时长持续爬升说明临界区在变长或某把锁被异常持有。监控里同时记 tryLock 的等待耗时和持有时长两条曲线，持有时长逼近 TTL 时先查业务是不是变慢了，别等到锁过期双写了才发现。

【冷知识】RedLock 是 Redis 作者 Salvatore Sanfilippo 在 2014 年提出的，名字里的 Red 就是 Redis 的缩写；Martin Kleppmann 在 2016 年发文质疑它的时间假设与 fencing 缺失，原文 §7 的四条理由就是这场争论的延续。知道这段来龙去脉，就明白为什么 RedLock 的讨论永远绕不开“时间假设”这个点——它从一开始就是一个带假设的算法，不是一个无条件的正确性保证。

【冷知识】ZooKeeper 的顺序节点编号是 10 位零填充的数字：`lock-0000000007` 这种后缀不是随便生成的，是父节点维护的单调计数器，每次建节点加一、格式化成 10 位。锁的公平性就靠这个编号排序——先到先得是节点创建顺序决定的，不是靠抢；这也是 ZooKeeper 锁天生公平、而 Redis 锁抢到靠运气的区别之一。

【冷知识】etcd 的名字来自 Unix 的 `/etc` 目录加一个 `d`：etcd 的定位就是“分布式的 /etc”，即全集群共享的配置目录，`d` 代表 distributed。它一开始是 CoreOS 为容器集群做的配置存储，锁只是后来长出来的能力——理解这个出处就明白，为什么 etcd 的锁 API 是租约 + 事务拼出来的，而不是像 ZooKeeper 那样原生按锁设计的。

## 面试与自测

1. Redis、ZooKeeper、etcd 三种锁的正确性基础各是什么？时钟漂移分别影响谁？
2. GC 停顿导致锁过期、旧持有者恢复后继续写共享资源，这个问题靠调大 TTL 能解决吗？正解是什么？
3. 热点 SKU 被高频抢锁时，分段锁怎么拆？一次拿多把锁时怎么防死锁？

### 参考答案

1. Redis 锁的正确性基础是最终一致加 TTL，需要 fencing token 补强；ZooKeeper 靠 ZAB 顺序一致性，etcd 靠 Raft 强一致，后两者不依赖时钟。时钟漂移影响依赖 TTL 的 Redis 与 etcd 租约，不影响 ZooKeeper。
2. 不能。调大 TTL 只推迟丢锁，不解决停顿恢复后的双写。正解是 fencing token：每次拿锁带单调递增序号，写共享资源时带上序号，资源方拒绝旧序号的写。
3. 按业务键哈希拆成 N 段（如 SKU + hash % 16），抢锁先抢段；一次拿多把锁时全局固定顺序（按 key 排序后依次拿），避免相反顺序死锁。
