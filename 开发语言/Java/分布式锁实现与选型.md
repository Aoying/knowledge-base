# 分布式锁实现与选型

单机锁（synchronized、ReentrantLock）只在同一个 JVM 内有效；服务多实例部署后，两个实例各拿各的锁，互斥就不存在了。分布式锁就是把“互斥”这件事放到多个实例都能看到的共享存储上做。本篇讲四种实现的原理与选型——Redis 锁的正确形态、看门狗续期、RedLock 争议与 fencing token 已在《Redis-缓存问题与分布式锁》讲透，本篇不再重复，只在相关处一句话指回。

## 1. Redis 实现：SET NX + 唯一持有者

原理：`SET key owner-id NX EX ttl`——NX 保证只有一个实例能建键成功，owner-id（UUID）标识持有者，EX 给锁一个过期时间防死锁。

- 释放：必须用 Lua 脚本“校验 owner-id 再删”合成原子操作；先 GET 再 DEL 中间有窗口，锁可能已被续期或易主，删错别人的锁。
- 续期：业务耗时可能超过 TTL，靠看门狗后台线程在 TTL 过半时续期；看门狗本身挂了锁会过期，业务要能接受“锁过期后被别人接管”的语义。
- 适用：高频、短临界区、对锁丢失有一定容忍度的场景；强正确性场景要叠加 fencing token（见 Redis 篇第 6 节）。

```java
// Redis 分布式锁骨架：加锁、Lua 安全释放、续期只列入口
// 加锁：SET key uuid NX EX 30
// 释放：EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 key uuid
// 续期：后台线程在 TTL 过半时对持有中的锁执行 PEXPIRE，业务结束或异常时取消续期
```

## 2. ZooKeeper 实现：临时顺序节点

原理：所有竞争者在同一个父节点下创建临时顺序节点，编号最小的持有锁；其他节点监听自己前一个节点的删除事件，前驱消失时按序接管。

- 释放：会话断开时临时节点自动删除，锁随之释放——这是 ZooKeeper 锁最大的优点，不依赖 TTL 猜业务时长。
- 正确性：ZooKeeper 的顺序一致性（ZAB 协议）保证同一时刻只有一个最小节点，锁的正确性不依赖时钟，时钟漂移影响不到它。
- 代价：要维护一个 ZooKeeper 集群；监听是“羊群效应”的反面教材——每个节点只监听前驱，不是所有节点监听同一个节点，所以唤醒是链式的，不会惊群。
- 适用：对正确性要求高、已有 ZooKeeper 基础设施（注册中心、配置中心同源）的系统。

## 3. etcd 实现：租约 + 事务 CAS

原理：客户端先拿一个带 TTL 的租约（lease），再用事务“比较并创建”抢锁键；抢到锁的键绑定租约，租约靠心跳续期，租约过期键自动删除。

- 释放：主动删除锁键，或租约过期自动失效；官方 v3 lock API 把这套流程封装好，业务代码只调 lock/unlock。
- 正确性：etcd 的 Raft 强一致，锁语义同样不依赖时钟；但要注意租约续期失败时的语义——租约一过期锁就没了，业务要处理“锁丢了但业务还在跑”的情况。
- 适用：Kubernetes 生态内（etcd 现成）、Go 服务为主的系统；Java 体系用 etcd 要额外接客户端，运维成本高于 Redis。

## 4. 数据库实现：唯一索引与行锁

两种路子：

- 悲观路子：`SELECT ... FOR UPDATE` 锁住一行（锁记录表），事务提交即释放；实现最简单，但锁持有期间占数据库连接，长临界区会拖垮连接池。
- 乐观路子：锁记录表 + 版本号，抢锁时 `UPDATE ... SET owner=?, version=version+1 WHERE id=? AND version=?`，影响行数 1 为抢到；续期靠心跳线程定时 UPDATE 延长过期时间。
- 边界：数据库锁的性能天花板最低，不适合高频抢锁；适合低频、已有数据库且不想引入新组件的场景（如定时任务单实例抢跑、配置下发互斥）。

## 5. 对比选型表

| 维度 | Redis | ZooKeeper | etcd | 数据库 |
|---|---|---|---|---|
| 正确性基础 | 最终一致 + TTL（需 fencing 补强） | 强一致（ZAB） | 强一致（Raft） | 依赖事务隔离级别 |
| 抢锁延迟 | 最低（内存操作） | 中（写 quorum） | 中（写 quorum） | 最高（磁盘 + 连接） |
| 锁丢失风险 | TTL 过期、GC 停顿续期失败 | 会话失效才丢 | 租约过期才丢 | 连接断开事务回滚 |
| 运维成本 | 已有 Redis 则最低 | 需独立集群 | K8s 内现成 | 零新增组件 |
| 适用场景 | 高频短锁、缓存式互斥 | 强正确性、已有 ZK | K8s 生态、强正确性 | 低频、已有 DB、抢跑互斥 |

选型口诀：已有组件优先——有 Redis 且容忍 fencing 补强就用 Redis；正确性压倒一切且已有 ZK/etcd 就用它们；什么都没有、频率又低，数据库锁最省事。

## 6. 故障场景：锁丢了怎么办

- 时钟漂移：依赖 TTL 的锁（Redis、etcd 租约）受时钟影响，节点时钟跳变会让锁“提前过期”或“过期了还被认为有效”；强一致锁（ZK）不受时钟影响，这是选型时最容易被低估的一点。
- GC 停顿：持有锁的进程 Full GC 几十秒，看门狗线程也被冻住，续期失败、锁过期、另一个实例接管，旧实例恢复后继续写共享资源——这是分布式锁最经典的失效模式，解法是 fencing token（见 Redis 篇第 6 节），不是把 TTL 调大。
- 网络分区：分区后旧持有者以为自己还有锁、新持有者也拿到锁，双写已成事实；事后靠 fencing token 的单调递增序号让旧写被拒绝，而不是靠“分区不会发生”安慰自己。
- 锁超时与业务时长：TTL 要大于“业务正常耗时 + 一次 GC 停顿”的量级，但 TTL 越大锁丢失后的空窗越长；没有万能值，按业务 P99 耗时定，超时的业务要能安全中断。

## 7. 锁粒度与分段锁

- 按业务键分段：锁 key 带业务维度（订单号、用户 ID、库存 SKU），不同键互不阻塞；不要用一把全局锁串行化所有业务。
- 热点 key 打散：同一 SKU 被高频抢时，把锁拆成 N 段（如 SKU + hash % 16），抢锁先抢段，段内再串行；代价是跨段操作要按固定顺序拿锁，防死锁。
- 拿锁顺序：一次拿多把锁时全局固定顺序（按 key 排序后依次拿），否则两个业务以相反顺序拿锁必然死锁。
- 锁内只放临界区：锁里不要调外部接口、不要等用户输入；临界区越长，锁丢失与超时的概率越高。

## 8. 常见误区

- “Redis 锁 SETNX 就够了”：缺唯一持有者校验的释放会删别人的锁，缺 TTL 会死锁，缺续期会中途丢锁，三者缺一不可。
- “TTL 调大就安全”：TTL 大只推迟丢锁，不解决 GC 停顿与分区下的双写；正确性靠 fencing，不靠 TTL。
- “锁能替代幂等”：锁只保证同一时刻一个在跑，不保证重复请求只生效一次；锁 + 幂等键才是完整方案。
- “一把锁管所有”：全局锁是性能瓶颈的头号来源，先按业务键分段再谈优化。

## 面试与自测

1. Redis、ZooKeeper、etcd 三种锁的正确性基础各是什么？时钟漂移分别影响谁？
2. GC 停顿导致锁过期、旧持有者恢复后继续写共享资源，这个问题靠调大 TTL 能解决吗？正解是什么？
3. 热点 SKU 被高频抢锁时，分段锁怎么拆？一次拿多把锁时怎么防死锁？

### 参考答案

1. Redis 锁的正确性基础是最终一致加 TTL，需要 fencing token 补强；ZooKeeper 靠 ZAB 顺序一致性，etcd 靠 Raft 强一致，后两者不依赖时钟。时钟漂移影响依赖 TTL 的 Redis 与 etcd 租约，不影响 ZooKeeper。
2. 不能。调大 TTL 只推迟丢锁，不解决停顿恢复后的双写。正解是 fencing token：每次拿锁带单调递增序号，写共享资源时带上序号，资源方拒绝旧序号的写。
3. 按业务键哈希拆成 N 段（如 SKU + hash % 16），抢锁先抢段；一次拿多把锁时全局固定顺序（按 key 排序后依次拿），避免相反顺序死锁。
