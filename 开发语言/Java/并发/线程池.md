# 线程池

## 1. 核心概念

- 定位：复用一组工作线程执行异步任务，解决「频繁建/销毁线程的开销」和「线程数量失控打爆 CPU 与内存」两个问题。
- 业务代码不要直接 `new Thread()`：线程数不可控、异常无人收、无背压。线程池是生产环境提交任务的唯一正道。
- 两个常用入口：`ThreadPoolExecutor`（通用池，自己配参数）与 `CompletableFuture`（异步编排，底层也要落到某个池上执行，见第 5 节）。

## 2. 基础知识：七参数与执行流程

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4,                              // corePoolSize 核心线程数：常驻线程
    8,                              // maximumPoolSize 最大线程数：忙不过来时最多扩到多少
    60L, TimeUnit.SECONDS,          // keepAlive：非核心线程空闲多久回收
    new LinkedBlockingQueue<>(1000),   // 任务队列：核心线程忙时先排队
    new ThreadFactoryBuilder().setNameFormat("biz-%d").build(),  // 线程工厂：必须给业务名
    new ThreadPoolExecutor.CallerRunsPolicy());                 // 拒绝策略：队列满+线程满时怎么办
```

任务提交后的决策顺序（背下来，排查问题全靠它）：

1. 运行线程数 < 核心数 → 直接新建核心线程执行。
2. 核心线程都在忙 → 任务进队列排队。**注意：队列不满时永远不会扩到最大线程数**，`maximumPoolSize` 形同虚设，这是最常见的参数误解。
3. 队列也满了 → 才新建非核心线程，直到最大线程数。
4. 线程数到顶且队列已满 → 触发拒绝策略。

四种拒绝策略：

| 策略 | 行为 | 适用 |
|---|---|---|
| AbortPolicy（默认） | 抛 `RejectedExecutionException` | 能感知失败的同步调用 |
| CallerRunsPolicy | 提交任务的线程自己执行 | 天然削峰：提交方被拖慢形成背压 |
| DiscardPolicy | 默默丢弃 | 可丢弃的日志、埋点类任务 |
| DiscardOldestPolicy | 丢掉队列里最老的任务 | 只要最新数据的场景，如行情推送 |

线程数经验值（只是起点，上线后按监控调）：计算密集 ≈ CPU 核数 + 1；IO 密集 ≈ CPU 核数 × (1 + 平均等待时间/计算时间)，粗算常用 2 倍核数再压测修正。

## 3. 进阶知识

- **为什么不用 `Executors` 快捷工厂**：`newFixedThreadPool` / `newSingleThreadExecutor` 用无界 `LinkedBlockingQueue`，任务堆积只涨内存不拒绝，最终 OOM；`newCachedThreadPool` 最大线程数是 `Integer.MAX_VALUE`，突发流量直接建线程到爆。阿里手册明确禁用，生产一律手写 `ThreadPoolExecutor`。
- **队列选型**：有界 `LinkedBlockingQueue` 是默认选择（容量就是背压阀门）；`ArrayBlockingQueue` 结构固定、内存更可控；`SynchronousQueue` 不存任务、直接交接，配大最大线程数就是 Cached 的玩法，只适合任务短平快的场景。
- **优雅关闭**：`shutdown()` 不再收新任务、等存量跑完；`shutdownNow()` 中断正在跑的线程并返回未执行任务清单。服务停机时先 `shutdown()`，再 `awaitTermination` 限时等待、超时才 `shutdownNow()`。
- **异常去向**：`execute` 提交的任务抛异常会打到线程的 UncaughtExceptionHandler 并让该工作线程结束（池子会补新线程）；`submit` 提交的异常被吞进 `Future`，不 `get()` 就永远不知道任务失败了——批量 `submit` 后必须逐个 `get` 或统一收集结果。
- **监控指标**：活跃线程数 `getActiveCount()`、队列长度 `getQueue().size()`、已完成数 `getCompletedTaskCount()`，接到监控告警上；队列持续增长 = 下游变慢或线程数不够，是最早的事故信号。

## 4. 实战应用

```java
// 审批流场景：并行校验多个下游（额度、黑名单、影像件），任一失败整体失败
ExecutorService pool = new ThreadPoolExecutor(
    8, 16, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(200),
    r -> { Thread t = new Thread(r, "approve-check"); t.setDaemon(true); return t; },
    new ThreadPoolExecutor.CallerRunsPolicy());

CompletableFuture<Boolean> quota  = CompletableFuture.supplyAsync(() -> checkQuota(), pool);
CompletableFuture<Boolean> black  = CompletableFuture.supplyAsync(() -> checkBlacklist(), pool);
CompletableFuture<Boolean> image  = CompletableFuture.supplyAsync(() -> checkImage(), pool);
boolean pass = quota.join() && black.join() && image.join();
```

- 与 [Async-异步](开发语言/Java/Async-异步.md) 的呼应：Spring `@Async` 默认用 `SimpleAsyncTaskExecutor`（每次新建线程）或共享池，务必显式配置自己的 `ThreadPoolTaskExecutor` 并给业务名，否则出问题时堆栈里全是无名线程，无从定位哪个业务的池打满了。
- `CompletableFuture` 不传执行器时默认用 `ForkJoinPool.commonPool`（全 JVM 共享、线程数 ≈ 核数 - 1），IO 任务塞进去会把全应用的并行流一起堵死；凡是阻塞型任务，一律 `supplyAsync(fn, 业务池)`。
- 池要按业务隔离：核心链路（审批、支付）与非核心（通知、报表）共用一个池，非核心任务一波堆积就能把核心链路拖死；隔离后各自队列、各自拒绝，互不传染。

## 5. 常见误区与坑

- **在池里再套池又互相等待**：父任务提交子任务后 `get()` 阻塞等结果，而子任务排在同一队列后面没线程可跑，形成线程饥饿死锁。对策：父子用不同池，或改全异步编排不阻塞。
- **ThreadLocal 不清理**：池线程长期复用，上一个任务塞进 [ThreadLocal](开发语言/Java/并发/ThreadLocal.md) 的用户信息会被下一个任务读到，串号又泄漏，用完必须 `remove()`。
- **捕获了中断却不停**：`shutdownNow` 靠中断协作，任务里 catch `InterruptedException` 后吞掉继续跑，停机就会卡死；正确做法是恢复中断标志或直接退出循环。
- **队列容量拍脑袋给几万**：等于没有背压，故障时任务全堆在内存里，表现为「接口超时但进程还活着」，比直接拒绝更难排查。宁可队列小一点 + CallerRuns 削峰。

## 6. 线程池参数定量：排队、拒绝与 Little's Law

本节所有数字均为手算，Python 3 本地复算（见节末“### 复算口径”）。口径说明：凡标【官方】的是 JDK 官方文档等可信来源的事实；凡标【估算】的是简化假设下的手算或经验估计，不是官方数字、不是实测值。原文第 2 节的决策顺序（核心满先入队、队列满才扩线程、再满才拒绝）是本节所有计算的前提【官方】。

### 6.1 Little's Law 套到线程池队列

Little's Law：L = λW，其中 L 是系统内平均任务数，λ 是平均到达率，W 是任务在系统内的平均停留时间；只看队列时 Lq = λWq。本节取一组与原文不同的参数（原文面试第 3 问用的是 5 核 + 100 队列 + 5 非核 = 110、第 111 个拒绝，那组数字这里不再用）：

- corePoolSize = 8，maximumPoolSize = 16，队列容量 200，keepAliveTime = 60s
- 平均到达率 λ = 240 任务/秒，单任务平均耗时 S = 50ms（0.05s），任务同质、相互独立

先算服务能力与利用率【估算】：

- 平均同时被服务的任务数（爱尔朗数）= λ × S = 240 × 0.05 = 12
- 仅 8 个核心线程时服务能力 μ_core = 8 / 0.05 = 160 任务/秒；利用率 ρ_core = 12 / 8 = 1.5，超过 1，说明只靠核心线程队列会无限增长
- 扩到 16 个线程时服务能力 μ_max = 16 / 0.05 = 320 任务/秒；利用率 ρ_max = 12 / 16 = 0.75，系统稳定

再算队列的涨落（流体近似：到达与服务都按平均速率计）【估算】：

- 核心线程满后，队列以 λ − μ_core = 240 − 160 = 80 个/秒的速度积压，200 容量的队列约 2.5 秒被填满（200 / 80 = 2.5）
- 队列一满，非核心线程才开始创建【官方】，扩到 16 线程后服务能力超过到达率，队列以 μ_max − λ = 320 − 240 = 80 个/秒的速度排空，约 2.5 秒排空（200 / 80 = 2.5）
- 队列长度在 0→200→0 之间走三角波，平均积压 Lq = 200 / 2 = 100 个任务
- 平均排队等待 Wq = Lq / λ = 100 / 240 ≈ 0.417 秒 ≈ 417ms；平均总停留 W = Wq + S ≈ 467ms；系统内平均任务数 L = λ × W = 240 × 0.467 ≈ 112，与 Lq + λS = 100 + 12 = 112 自洽

轻载对照【估算】：到达率降到 λ = 150 任务/秒时，λS = 7.5 < 8，核心线程就够用，利用率 ρ_core = 7.5 / 8 = 93.75%，队列基本为空，W ≈ S = 50ms，L ≈ 7.5。轻载利用率离 100% 的稳定边界只差约 6 个百分点（100 − 93.75 = 6.25），可一旦越过 100%（本节主场景相对核心线程是 150%），等待就从约 0ms 跳到约 417ms——利用率过 100% 是质变点，不是渐变。

拒绝阈值【官方规则 + 手算】：同一时刻最多容纳 8 个核心线程在跑 + 200 个排队 + 8 个非核心线程在跑 = 216 个任务；第 217 个任务到来时线程已到顶、队列已满，触发拒绝策略，默认 AbortPolicy 抛 RejectedExecutionException。

### 6.2 核心满先入队 vs 先扩线程：成本换算

“核心满先入队而不是先扩线程”常被解释为“建线程贵”，但按本节数字算，这笔账并不成立【估算】：

- 建一条线程的成本量级约 0.1–1ms（分配栈内存、创建操作系统线程、调度器入队），一次上下文切换约 1–10μs；这两个数是经验估计，不是官方数字、不是实测值，不同平台、不同 JVM 参数下会变
- 本节场景里排队等待约 417ms，是建线程成本（取 1ms 计）的约 417 倍；即使按最悲观的 10ms 建线程算，排队等待仍是它的约 42 倍
- 换算成任务耗时：417ms 的等待相当于白白多跑了约 8 个 50ms 的任务（417 / 50 ≈ 8.3）

所以“先入队”真正的理由不是建线程贵，而是另外三条【估算】：一是给突发一个缓冲，短暂峰值靠队列扛过去就不用扩线程；二是给线程数设上限，线程一多，切换开销、锁竞争和内存（每条线程默认栈约 1MB 虚拟内存，HotSpot 64 位 Linux 默认 -Xss 1M，平台相关）都会跟着涨；三是队列容量就是背压阀门，队列满了才扩线程、扩满才拒绝，拒绝本身就是一种明确的、可监控的失败信号，比无声堆积好排查。面试答“建线程贵”只能得一半分，要补上“限流与背压”这一半。

### 6.3 keepAliveTime 对非核心线程回收的量化影响

keepAliveTime 只对超过核心数的线程生效：池中线程数超过 corePoolSize 时，空闲超过 keepAliveTime 的多余线程会被回收；默认不对核心线程生效，要回收核心线程需再开 allowCoreThreadTimeOut(true)【官方】。取 keepAliveTime = 60s、非核心线程 8 条：

- 突发间隔 30 秒（< 60s）：上一波扩出来的 8 条非核心线程还没到回收线就等来了下一波，全程存活，突发之间零重建
- 突发间隔 90 秒（> 60s）：上一波的 8 条非核心线程在空闲 60 秒后被回收，下一波到来时要重新创建，最多重建 8 条；按每小时 40 波（3600 / 90 = 40）算，一小时约 320 次线程创建（40 × 8），每次约 0.1–1ms【估算】，合计约 0.03–0.32 秒的创建开销，分摊到每小时可忽略，但每波首批任务要吃建线程的延迟
- 把 keepAliveTime 从 60s 放到 120s：90 秒间隔的突发下非核心线程也不再回收，代价是低峰期常驻 8 条多余线程（约 8MB 栈虚拟内存【估算】），换来的是突发零建线程延迟；keepAliveTime 的本质就是“省资源”与“少延迟”之间的一根刻度尺，调它之前先量突发间隔

### 6.4 边界条件与打折验算

本节结论只在以下假设下成立，假设一变，结论要打折重算：

1. **到达率与耗时恒定，且 λ < 最大服务能力**。打折验算：单任务耗时从 50ms 翻倍到 100ms，下游变慢的常见情形——λS = 24，ρ_max = 24 / 16 = 1.5，μ_max = 16 / 0.1 = 160 任务/秒 < λ = 240，队列永远排空不了，2.5 秒排空、417ms 等待的结论全部失效，只剩“队列 2.5 秒填满、第 217 个拒绝”还成立。利用率公式本身没错，但它只在稳定区（ρ_max < 1）才有“平均等待”可言。
2. **任务同质、独立、无共享锁竞争**。打折验算：如果任务都要抢同一把锁，有效服务时间 S 会被锁等待放大，ρ_max 被低估，实际等待比 417ms 更长；反过来任务全是纯 CPU 计算、无任何等待时，S 才接近实测耗时。先有 S 的实测分布，再谈排队数字。
3. **流体近似：到达与服务都按平均速率计，忽略随机波动**。真实到达是随机的，同样 λ = 240、S = 50ms，突发扎堆时瞬时等待会超过 417ms 的均值；Little's Law（L = λW）对长期平均值恒成立，但 Wq = 417ms 只是流体近似下的均值，不是 P99。P99 等待要按到达分布重算，本节不展开。
4. **队列是 FIFO 且容量 200 全程有效**。如果换成 SynchronousQueue（容量 0、不存任务），“先入队”这一步直接消失，核心一满就扩线程，全部数字推倒重来；队列选型变了，定量模型就要跟着变，见原文第 3 节。

### 复算口径

```python
# Python 3 本地复算：core=8, max=16, 队列=200, lam=240/s, S=50ms
core, max_, qcap = 8, 16, 200
lam = 240.0      # 任务/秒
S = 0.05         # 秒
erlangs = lam * S            # 12.0, 平均同时被服务的任务数
rho_core = erlangs / core    # 1.5
rho_max = erlangs / max_     # 0.75
mu_core = core / S           # 160.0/s
mu_max = max_ / S            # 320.0/s
t_fill = qcap / (lam - mu_core)   # 2.5s, 队列填满时间
t_drain = qcap / (mu_max - lam)   # 2.5s, 队列排空时间
Lq = qcap / 2                # 100.0, 三角波平均积压
Wq = Lq / lam                # 0.4167s = 416.7ms, 平均排队等待
W = Wq + S                   # 0.4667s = 466.7ms, 平均总停留
L = lam * W                  # 112.0, 校验: Lq + erlangs = 112.0
# 轻载对照 lam=150/s: erlangs=7.5, rho_core=0.9375, W≈50ms, L=7.5
# 拒绝阈值: 8 + 200 + 8 = 216, 第 217 个任务拒绝
# 成本换算: 416.7ms / 1ms ≈ 417 倍; / 10ms ≈ 41.7 倍
# keepAlive=60s: 突发间隔 30s 存活零重建; 间隔 90s 每波重建 ≤8 条, 每小时 40 波 ≈ 320 次创建
# 打折验算 S=100ms: erlangs=24.0, rho_max=1.50, mu_max=160/s < lam=240/s, 队列永不排空
# 打折验算 lam=300/s: erlangs=15.0, rho_max=0.9375, mu_max=320/s, 余量 20/s
```

## 原理剖析

本节只把原文已有章节给出的结论拆开讲清机制：不引入新概念，不补新数字，数字一律复用 §6 已核验的定量算例；凡原文没展开的点，文中明确标注，不作定论。

### 七参数与执行流程：核心满先入队

七参数是 corePoolSize、maximumPoolSize、keepAliveTime + 时间单位、workQueue、ThreadFactory、RejectedExecutionHandler（§2）。任务提交后的决策顺序是固定的四步（§2）：运行线程数小于核心数时直接新建核心线程执行；核心线程都在忙时任务进队列排队；队列也满了才新建非核心线程，直到最大线程数；线程数到顶且队列已满才触发拒绝策略。关键机制在于第二步：队列不满时永远不会扩到最大线程数，maximumPoolSize 形同虚设（§2）——扩线程不是核心一满就发生，而是队列先被填满才轮到它。

按 §6 的算例（§6.1）把这条顺序换算成容量：corePoolSize = 8、maximumPoolSize = 16、队列容量 200，同一时刻最多容纳 8 个核心线程在跑 + 200 个排队 + 8 个非核心线程在跑 = 216 个任务，第 217 个任务到来时线程已到顶、队列已满，触发拒绝策略。也就是说，拒绝阈值不是“线程数”，而是“核心线程 + 队列 + 非核心线程”三段容量之和。

“核心满先入队而不是先扩线程”常被解释为“建线程贵”，但按 §6 的数字算，这笔账并不成立（§6.2）：建一条线程的成本量级约 0.1–1ms，一次上下文切换约 1–10μs，这两个数是经验估计，不是官方数字、不是实测值；本节场景里排队等待约 417ms，是建线程成本（取 1ms 计）的约 417 倍，即使按最悲观的 10ms 建线程算，排队等待仍是它的约 42 倍，换算成任务耗时相当于白白多跑了约 8 个 50ms 的任务（417 / 50 ≈ 8.3）。所以“先入队”真正的理由是另外三条（§6.2）：一是给突发一个缓冲，短暂峰值靠队列扛过去就不用扩线程；二是给线程数设上限，线程一多，切换开销、锁竞争和内存（每条线程默认栈约 1MB 虚拟内存）都会跟着涨；三是队列容量就是背压阀门，队列满了才扩线程、扩满才拒绝，拒绝本身就是一种明确的、可监控的失败信号，比无声堆积好排查。只答“建线程贵”只能得一半分，要补上“限流与背压”这一半（§6.2）。

### 拒绝策略：四种策略如何分流

拒绝是决策顺序的最后一步，只有在核心线程、队列、非核心线程三段全部到顶之后才会发生（§2）。四种策略的分流机制各不相同（§2）：AbortPolicy（默认）抛 RejectedExecutionException，把失败显式抛给提交方，适用能感知失败的同步调用；CallerRunsPolicy 让提交任务的线程自己执行，提交方被拖慢就形成背压，天然削峰；DiscardPolicy 默默丢弃，适用可丢弃的日志、埋点类任务；DiscardOldestPolicy 丢掉队列里最老的任务，适用只要最新数据的场景，如行情推送。

按 §6 的算例（§6.1），容量上限是 216 个任务，第 217 个任务触发拒绝，默认 AbortPolicy 抛 RejectedExecutionException。四种策略的区别不在触发条件——触发条件都是“三段到顶”——而在触发之后任务的去向：抛给提交方、由提交方自己执行、无声丢弃、还是丢最老的腾位置给最新的。选策略就是在选“满了之后谁来承担代价”：Abort 让提交方感知失败，CallerRuns 让提交方变慢，Discard 与 DiscardOldest 让任务本身消失。

### 排队与 Little's Law：417ms 等待是怎么来的

Little's Law 是 L = λW，其中 L 是系统内平均任务数，λ 是平均到达率，W 是任务在系统内的平均停留时间；只看队列时 Lq = λWq（§6.1）。§6 的主算例取 corePoolSize = 8、maximumPoolSize = 16、队列容量 200、平均到达率 λ = 240 任务/秒、单任务平均耗时 S = 50ms（0.05s），任务同质、相互独立（§6.1）。

先算服务能力与利用率（§6.1）：平均同时被服务的任务数 λ × S = 240 × 0.05 = 12；仅 8 个核心线程时服务能力 μ_core = 8 / 0.05 = 160 任务/秒，利用率 ρ_core = 12 / 8 = 1.5，超过 1，说明只靠核心线程队列会无限增长；扩到 16 个线程时服务能力 μ_max = 16 / 0.05 = 320 任务/秒，利用率 ρ_max = 12 / 16 = 0.75，系统稳定。利用率超过 1 的含义是到达比核心服务更快，队列必然积压；而扩到最大线程数后利用率回到 0.75，系统才有排空队列的能力。

再算队列的涨落（流体近似：到达与服务都按平均速率计）（§6.1）：核心线程满后，队列以 λ − μ_core = 240 − 160 = 80 个/秒的速度积压，200 容量的队列约 2.5 秒被填满（200 / 80 = 2.5）；队列一满，非核心线程才开始创建，扩到 16 线程后服务能力超过到达率，队列以 μ_max − λ = 320 − 240 = 80 个/秒的速度排空，约 2.5 秒排空（200 / 80 = 2.5）。队列长度在 0→200→0 之间走三角波，平均积压 Lq = 200 / 2 = 100 个任务；平均排队等待 Wq = Lq / λ = 100 / 240 ≈ 0.417 秒 ≈ 417ms；平均总停留 W = Wq + S ≈ 467ms；系统内平均任务数 L = λ × W = 240 × 0.467 ≈ 112，与 Lq + λS = 100 + 12 = 112 自洽。

轻载对照（§6.1）：到达率降到 λ = 150 任务/秒时，λS = 7.5 < 8，核心线程就够用，利用率 ρ_core = 7.5 / 8 = 93.75%，队列基本为空，W ≈ S = 50ms，L ≈ 7.5。轻载利用率离 100% 的稳定边界只差约 6 个百分点（100 − 93.75 = 6.25），可一旦越过 100%（本节主场景相对核心线程是 150%），等待就从约 0ms 跳到约 417ms——利用率过 100% 是质变点，不是渐变。

原文未展开：P99 等待，§6.4 已说明 Wq ≈ 417ms 只是流体近似下的均值，不是 P99，真实到达是随机的，突发扎堆时瞬时等待会超过 417ms 的均值，P99 要按到达分布重算，原文未展开，不作定论。

### keepAliveTime：非核心线程的回收刻度

keepAliveTime 只对超过核心数的线程生效：池中线程数超过 corePoolSize 时，空闲超过 keepAliveTime 的多余线程会被回收；默认不对核心线程生效，要回收核心线程需再开 allowCoreThreadTimeOut(true)（§6.3）。取 keepAliveTime = 60s、非核心线程 8 条（§6.3）：突发间隔 30 秒（< 60s）时，上一波扩出来的 8 条非核心线程还没到回收线就等来了下一波，全程存活，突发之间零重建；突发间隔 90 秒（> 60s）时，上一波的 8 条非核心线程在空闲 60 秒后被回收，下一波到来时要重新创建，最多重建 8 条，按每小时 40 波（3600 / 90 = 40）算，一小时约 320 次线程创建（40 × 8），每次约 0.1–1ms，合计约 0.03–0.32 秒的创建开销，分摊到每小时可忽略，但每波首批任务要吃建线程的延迟。

把 keepAliveTime 从 60s 放到 120s（§6.3）：90 秒间隔的突发下非核心线程也不再回收，代价是低峰期常驻 8 条多余线程（约 8MB 栈虚拟内存），换来的是突发零建线程延迟。keepAliveTime 的本质就是“省资源”与“少延迟”之间的一根刻度尺，调它之前先量突发间隔：间隔短于 keepAliveTime，线程留得住；间隔长于 keepAliveTime，线程会被回收，下一波要重建。

## 实战案例

以下两则均按 §6 已核验的算例推演，不引入原文之外的数字与事实；现象、排查、结论三段均只用原文 §2、§3、§6 已给出的结论与数字。

### 案例一：突发流量下队列 2.5 秒填满，第 217 个任务被拒绝

现象：按 §6 主算例（§6.1），池子 corePoolSize = 8、maximumPoolSize = 16、队列容量 200，平均到达率 λ = 240 任务/秒、单任务平均耗时 S = 50ms。核心线程满后队列以 80 个/秒的速度积压，200 容量的队列约 2.5 秒被填满；同一时刻最多容纳 216 个任务，第 217 个任务到来时线程已到顶、队列已满，触发拒绝策略，默认 AbortPolicy 抛 RejectedExecutionException。

排查：先按 §2 的决策顺序定位卡在哪一段：运行线程数小于核心数时应直接新建核心线程，核心满后任务进队列，队列满后才新建非核心线程。再看 §3 的监控指标：活跃线程数 getActiveCount()、队列长度 getQueue().size()、已完成数 getCompletedTaskCount()。若活跃线程数已到 16 且队列长度已到 200，说明三段容量同时到顶，拒绝是决策顺序走到最后一步的结果，不是线程建不出来；若活跃线程数远小于 16 但队列已满，说明仍在“核心满先入队”的阶段，最大线程数尚未启用（§2）。§3 也指出，队列持续增长 = 下游变慢或线程数不够，是最早的事故信号。

结论：拒绝不是建线程慢造成的——按 §6.2 的换算，约 417ms 的排队等待是建线程成本（取 1ms 计）的约 417 倍，建线程的延迟在排队等待面前可以忽略。拒绝是队列这个背压阀门顶满后发出的明确信号（§6.2）：队列满了才扩线程、扩满才拒绝，拒绝本身就是一种明确的、可监控的失败信号，比无声堆积好排查。

原文未展开：到达率随机波动下瞬时等待超过 417ms 均值的幅度，§6.4 已说明真实到达是随机的，突发扎堆时瞬时等待会超过均值，未给出具体数值，不作定论。

### 案例二：下游变慢，单任务耗时翻倍后队列再也排空不了

现象：复用原文 §4 的审批流池子（8 核、16 最大、200 队列、CallerRunsPolicy），按 §6.4 的打折验算推演下游变慢的情形：单任务耗时从 50ms 翻倍到 100ms，λS = 24，ρ_max = 24 / 16 = 1.5，μ_max = 16 / 0.1 = 160 任务/秒 < λ = 240 任务/秒，队列永远排空不了，2.5 秒排空、417ms 等待的结论全部失效，只剩“队列 2.5 秒填满、第 217 个拒绝”还成立。

```java
// 审批流场景：并行校验多个下游（额度、黑名单、影像件），任一失败整体失败
ExecutorService pool = new ThreadPoolExecutor(
    8, 16, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(200),
    r -> { Thread t = new Thread(r, "approve-check"); t.setDaemon(true); return t; },
    new ThreadPoolExecutor.CallerRunsPolicy());

CompletableFuture<Boolean> quota  = CompletableFuture.supplyAsync(() -> checkQuota(), pool);
CompletableFuture<Boolean> black  = CompletableFuture.supplyAsync(() -> checkBlacklist(), pool);
CompletableFuture<Boolean> image  = CompletableFuture.supplyAsync(() -> checkImage(), pool);
boolean pass = quota.join() && black.join() && image.join();
```

排查：先看 §3 的监控指标，队列持续增长 = 下游变慢或线程数不够，是最早的事故信号；再按 §6.4 的打折验算核对假设：利用率公式本身没错，但它只在稳定区（ρ_max < 1）才有“平均等待”可言，ρ_max = 1.5 已在稳定区之外，417ms 的等待数字不再适用。§6.4 也指出，任务同质、独立、无共享锁竞争是本节结论的前提，如果任务都要抢同一把锁，有效服务时间 S 会被锁等待放大，ρ_max 被低估，实际等待比 417ms 更长；先有 S 的实测分布，再谈排队数字。

结论：这时扩线程已经到顶也无济于事——扩到 16 线程后服务能力 μ_max = 160 任务/秒仍小于到达率 λ = 240 任务/秒（§6.4），问题不在池子容量，而在单任务耗时 S 翻倍。按本则复用的 §4 池子，拒绝策略是 CallerRunsPolicy，第 217 个任务触发拒绝时由提交任务的线程自己执行（§2），提交方被拖慢形成背压，而不是抛异常；但背压只能拖慢提交方，不能让队列排空，根因仍是下游耗时。

## 小技巧与冷知识

【小技巧】核心线程是懒创建的，首批任务要吃建线程的延迟：池子刚建好时一个线程都没有，第一个任务进来才建第一个线程，突发流量一到，前几个任务都在等线程启动。服务启动后调一次 `prestartAllCoreThreads()` 把核心线程提前建好，首批请求就不用在建线程上排队；定时任务池、网关入口池这类“启动即有流量”的池尤其值得预热。

【小技巧】`keepAliveTime` 默认只对非核心线程生效，核心线程空闲多久都不会回收：低峰期想把池子缩回去省资源，光调小 keepAlive 没用，要再调 `allowCoreThreadTimeOut(true)`，核心线程空闲超时后才会被回收。调了这个开关再遇到突发，核心线程又要重新建，低峰省资源和高峰少延迟之间要自己取舍，两个开关是成对出现的。

【小技巧】`CallerRunsPolicy` 削峰之前先确认“调用线程是谁”：提交任务的线程如果是 Tomcat 的工作线程或 Netty 的 IO 线程，它被拖去执行任务期间就接不了新请求，入口吞吐会跟着掉。调用方是后台线程或定时任务线程时 CallerRuns 很合适，调用方是请求处理线程时要换成自定义拒绝策略——削峰不能削到入口线程头上。

【小技巧】拒绝策略别直接用默认的 `AbortPolicy` 裸奔，包一层自定义的 `RejectedExecutionHandler`：先记一条带任务信息（任务类型、队列长度、活跃线程数）的日志或埋点，再决定抛异常还是入死信队列重试。线上池子一打满，裸抛的 `RejectedExecutionException` 只告诉你“被拒了”，包一层才能在事后复盘出“哪个业务、什么时候、因为什么满的”。

【小技巧】想统计每个任务跑了多久、哪个任务抛了异常，用 `beforeExecute` / `afterExecute` 钩子：继承 `ThreadPoolExecutor` 重写这两个方法，`beforeExecute` 里记开始时间，`afterExecute` 里算耗时、打慢任务日志。`afterExecute` 的第二个参数只有 `execute` 提交的任务抛异常时才非空，`submit` 提交的异常被吞进 Future，钩子里拿不到，要从 `Future.get()` 里取——两个入口的异常去向在这里也分叉。

【小技巧】线程数不用重启也能调：`setCorePoolSize()` / `setMaximumPoolSize()` 可以在运行时改，配上配置中心就能热调。但调小核心数不会立刻杀掉正在跑的线程，只影响空闲线程的回收速度；调大最大线程数在队列是无界时依然没用——先确认队列类型，再决定调哪个参数。

【小技巧】取消任务要分清 `cancel(true)` 和 `cancel(false)`：`cancel(false)` 只取消还没开始跑的任务，正在跑的照跑不误；`cancel(true)` 会尝试中断正在跑的任务，但任务里不响应中断就停不下来。想让取消真正生效，任务代码里要像原文第 5 节说的那样配合中断标志，取消 API 只是发信号，不是强制杀线程。

【小技巧】`shutdownNow()` 返回的未执行任务清单别直接丢掉：它返回的是还没开始跑的任务列表，停机时这些任务要么落盘、要么重投到别的节点、要么明确记一条“已丢弃”的日志。直接忽略返回值，停机那一刻排队的任务就无声无息没了，事后连丢了多少、丢了哪些都查不到。

【小技巧】池子里的线程默认是非守护线程，主线程跑完进程也不会退出：原文第 4 节示例里特意写了 `t.setDaemon(true)`，就是为了让示例进程能正常结束。生产里的业务池一般不要设守护线程——守护线程会在 JVM 退出时被直接抛弃，正在跑的任务没机会收尾；正确做法是服务停机时走 `shutdown()` + `awaitTermination` 的优雅关闭，而不是靠守护线程兜底。

【冷知识】线程池的工作线程 `Worker` 继承了 `AbstractQueuedSynchronizer`（AQS）：它的 state 初始值是 -1，作用是在线程启动前屏蔽中断，等 `runWorker` 开始跑任务才把 state 置 0；`shutdown()` 只中断空闲线程的原理也在这里——空闲的 Worker 能拿到这把内部锁，正在跑任务的 Worker 拿不到，也就不会被中断。池子的中断控制不是靠标志位，而是靠每个 Worker 身上的一把 AQS 锁。

【冷知识】`CallerRunsPolicy` 在池子已经 `shutdown()` 之后会直接丢弃任务：它的源码里先判 `if (!e.isShutdown())` 才让调用线程执行任务，池子关了就什么都不做、也不抛异常。停机窗口里提交的任务用 CallerRuns 不会报错、也不会执行，是静默丢弃——优雅关闭期间要先停入口再关池，别指望拒绝策略帮你兜底。

【冷知识】`ThreadPoolExecutor` 是 JDK 5 随 JSR 166 的 `java.util.concurrent` 一起引入的：Doug Lea 主导的这套并发包把线程池、锁、原子类、并发集合一次性带进标准库，在此之前 Java 开发者只能自己写线程池或用第三方库。`Executors` 工厂方法和 `ThreadPoolExecutor` 是同一批货，工厂方法只是把参数写死后的快捷写法，理解这一点就明白为什么“禁用 Executors、 hand 写 ThreadPoolExecutor”只是换了种调用方式，而不是换了实现。

### 参考答案

1. 七参数：corePoolSize、maximumPoolSize、keepAliveTime + 时间单位、workQueue、ThreadFactory、RejectedExecutionHandler。决策顺序：运行线程数 < 核心数 → 新建核心线程；核心忙 → 进队列；队列满 → 新建非核心线程至最大数；仍满 → 拒绝策略。核心满先入队而不是先扩线程：队列是缓冲，扛瞬时突发；线程创建与切换有成本，先排队能避免为短暂峰值反复建线程，maximumPoolSize 只在队列也满时才起作用，队列不满时它形同虚设。
2. execute 提交的任务抛异常：打到线程的 UncaughtExceptionHandler，该工作线程结束、池子会补新线程。submit 提交的异常：被吞进 Future，不 get() 就永远不知道任务失败了；批量 submit 后必须逐个 get 或统一收集结果。
3. 第 106 个任务不会触发拒绝：前 5 个占满核心线程，第 6–105 个填满 100 容量的队列，第 106 个到来时队列已满、线程未到上限，于是新建第 6 个线程（第一个非核心线程）执行。拒绝要到第 111 个任务才触发（5 核 + 100 队列 + 5 非核 = 110 满），默认 AbortPolicy 抛 RejectedExecutionException。

4. keepAliveTime 只回收超过核心数的空闲线程，默认不回收核心线程【官方】。突发间隔 90 秒 > keepAliveTime 60 秒，上一波的 8 条非核心线程空闲满 60 秒后被回收，下一波要重建，最多重建 8 条；突发间隔缩到 30 秒 < 60 秒，非核心线程还没到回收线就等来了下一波，全程存活、零重建。把 keepAliveTime 改成 120 秒后，90 秒间隔下非核心线程也不再回收，代价是低峰期常驻 8 条多余线程（约 8MB 栈虚拟内存【估算】），换来突发零建线程延迟；keepAliveTime 的本质是“省资源”与“少延迟”之间的刻度尺，调它之前先量突发间隔。
