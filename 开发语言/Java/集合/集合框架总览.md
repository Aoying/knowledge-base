# 集合框架总览

## 1. 核心概念

- 集合框架是 JDK 装数据的标准容器体系：接口定语义、实现类给性能取舍，算法（`Collections`、`Arrays`）是通用操作。
- 两大体系，互不继承：`Collection` 装单个元素，`Map` 装键值对。`Map` 不是 `Collection` 的子接口，别用“集合”一词同时指代两者。
- 与数组相比：集合长度可变、带泛型、有一套现成算法；代价是装箱、扩容与遍历开销。定长且类型固定时数组更直接。
- 泛型是编译期检查：`List<String>` 只能装 `String`，取出来不用强转；运行时泛型擦除，`List<String>` 与 `List<Integer>` 是同一个类。

## 2. 基础知识

### 2.1 Collection 三子体系

| 子接口 | 语义 | 代表实现 | 备注 |
|---|---|---|---|
| `List` | 有序（按插入/索引）、可重复、有索引 | `ArrayList`、`LinkedList`、`CopyOnWriteArrayList` | 按位置取元素是 List 专属能力 |
| `Set` | 去重、无索引 | `HashSet`、`LinkedHashSet`、`TreeSet`、`EnumSet` | 去重靠 `equals/hashCode` 或比较器，详见 `Set集合基础` |
| `Queue` | 排队语义：队尾进、队头出 | `ArrayDeque`、`LinkedList`、`PriorityQueue` | `Deque` 是双端队列，可当栈用 |

### 2.2 Map 体系

- `Map` 按 key 找 value：`HashMap`（无序）、`LinkedHashMap`（保插入/访问顺序）、`TreeMap`（按 key 排序）、`ConcurrentHashMap`（并发）。
- `Map` 的 key 集合是 `Set`，value 集合是 `Collection`，键值对集合是 `Set<Map.Entry>`：三者都是视图，改视图会反映到底层 Map。
- Java 21 起 `List`、`Set`、`Map` 各自有了有序子接口：`SequencedCollection`、`SequencedSet`、`SequencedMap`，提供 `reversed()`、`getFirst/getLast` 等统一操作（Java 21）。

### 2.3 选型速查

| 需求 | 首选 | 备选 |
|---|---|---|
| 随机访问多、增删少 | `ArrayList` | — |
| 队头队尾操作多 | `ArrayDeque` | `LinkedList` |
| 去重 | `HashSet` | `LinkedHashSet`（要顺序）、`TreeSet`（要排序） |
| key 找 value，无序 | `HashMap` | — |
| key 找 value，要排序 | `TreeMap` | — |
| 多线程读写 | `ConcurrentHashMap` / `CopyOnWriteArrayList` | 加锁的普通集合（见第 3.4 节） |

## 3. 原理剖析

### 3.1 哈希约定：所有哈希容器的地基

- 约定只有一条：`equals` 相等的对象，`hashCode` 必须相等；反过来不要求（哈希冲突允许）。
- 违反约定的后果是静默错误：`HashSet` 去重失效、`HashMap.get` 找不到已 `put` 的 key，编译器不报错。
- `String`、`Integer` 等 JDK 类已正确实现；自定义 key 必须同时重写两个方法，缺一个就是 bug。

### 3.2 排序约定：比较器说了算

- `TreeMap`/`TreeSet` 不用 `hashCode`，用 `Comparable` 或构造时传入的 `Comparator` 定序。
- 比较器返回 0 即视为“相等”：`TreeSet` 会据此去重，哪怕两个对象的 `equals` 并不相等，这是最常见的排序容器坑。
- 比较器必须满足自反、反对称、传递三性，否则排序结果不可预测。

### 3.3 迭代与 fail-fast

- 迭代器是“遍历时的快照游标”，不是集合本身：`Iterator.remove()` 是迭代中唯一安全的删除方式。
- fail-fast 机制：大多数集合内部维护 `modCount`，迭代中检测到结构性修改（增删）就抛 `ConcurrentModificationException`。它是“尽早暴露 bug”的检测，不是并发安全保证。
- 增强 for 循环本质就是迭代器：循环体内直接 `list.remove()` 同样触发 fail-fast，改法是用迭代器删、或先收集待删项再批量删。

### 3.4 不可变集合与并发衔接

- 不可变集合（Java 9：`List.of`、`Set.of`、`Map.of`）：创建后不能增删改，元素不允许为 `null`，读多写少、作常量或安全发布时用；试图修改抛 `UnsupportedOperationException`。
- `Collections.unmodifiableXXX` 只是只读视图，底层集合变了视图跟着变；`List.of` 是真正的数据拷贝，与原集合脱钩。
- 并发衔接三条路：读多写极少用 `CopyOnWriteArrayList/CopyOnWriteArraySet`（写时全量复制）；高并发键值用 `ConcurrentHashMap`（分段思想的现代实现：CAS + 锁桶头）；低并发或复合操作直接给普通集合加锁，复合操作（判存再写）必须整个包进同一把锁，只换并发容器不够。

## 4. 选型指南

- 先定语义再定实现：要不要重复、要不要顺序、要不要排序、要不要并发——四个问题答完，实现类基本唯一。
- 不要为“可能用到”的特性买单：无序场景用 `TreeMap` 是白付 O(log n)；单线程场景用并发容器是白付同步开销。
- 容量与扩容只在数据量可预估时调：`HashMap`/`ArrayList` 构造时给初始容量，避免反复扩容；元素量未知时别瞎猜，默认容量即可。
- 返回值类型优先声明接口：方法返回 `List` 而不是 `ArrayList`，调用方只依赖语义，日后换实现不改签名。

## 5. 实战应用与常见坑

- 遍历删除坑：增强 for 里删元素抛 `ConcurrentModificationException`；正确姿势是 `Iterator.remove()` 或 `removeIf`。
- `null` 政策各不相同：`HashMap`/`ArrayList` 允许 `null`，`TreeMap`/`TreeSet` 的 key（无比较器时）与 `ConcurrentHashMap` 的 key/value、`List.of` 的元素一律不允许，混用前先查表。
- `Arrays.asList` 返回的是定长列表：能改元素、不能增删；要可增删就 `new ArrayList<>(Arrays.asList(...))`。
- `subList` 是原列表的视图：改子列表影响原列表，原列表结构性修改后子列表再用就抛异常；需要独立列表时拷贝一份。
- 复合操作不是原子操作：`if (!map.containsKey(k)) map.put(k, v)` 在并发下会丢更新，要用 `putIfAbsent`/`computeIfAbsent` 这类原子方法。

## 小技巧与冷知识

【小技巧】遍历 Map 时用 `entrySet()`，别用 `keySet()` 加 `get()`：`for (String k : map.keySet()) map.get(k)` 每轮都要重新哈希查一次桶，等于把遍历又做了一遍查找；`entrySet()` 一次遍历直接拿到键值对。Map 越大差距越明显，读值、过滤、转换三类操作都该从 entrySet 入手，keySet 只适合“只关心 key”的场景。

【小技巧】判空用 `isEmpty()`，别用 `size() == 0`：有些集合的 `size()` 并不便宜——`ConcurrentLinkedQueue` 的 `size()` 是 O(n) 全遍历，`ConcurrentHashMap` 的 `size()` 也要汇总各分段的计数。`isEmpty()` 在这些实现里通常有更快的短路判断，语义也更直白——“有没有元素”问 isEmpty，“有多少个”才问 size。

【小技巧】`Set.add()` 的返回值就是“第一次出现”的判断：`add` 成功返回 true、已存在返回 false，不用先 `contains` 再 `add` 查两遍。去重、统计首次出现、过滤重复数据时，`if (seen.add(x))` 一行就是“第一次见到才处理”，比 `contains + add` 少一次查找，语义也更干净。

【小技巧】`HashMap` 构造传的初始容量是桶数，不是元素数：默认负载因子 0.75，`new HashMap<>(1000)` 的桶数是 1024（向上取到 2 的幂），大约装 768 个元素就扩容。期望装 n 个元素不扩容，容量要按 `(int)(n / 0.75) + 1` 换算着传；直接传元素个数，等于把扩容点算小了四分之一。

【小技巧】只读的集合参数别防御性拷贝，要拷贝就用 `List.copyOf`：方法收到一个集合只读不写，直接用就行，拷一份是白花钱；确实需要“调用方改了原集合也不影响我”时，用 Java 10 的 `List.copyOf(list)` 一行得到不可变快照，`Set.copyOf`、`Map.copyOf` 同理。防御性拷贝只在“调用方可能改、我又要长期持有”时才做，别逢参数就拷。

【小技巧】Stream 去重会丢顺序，保序要换收集器：`stream().collect(Collectors.toSet())` 返回的 Set 不保证顺序，想去重又保插入顺序，用 `Collectors.toCollection(LinkedHashSet::new)`。去重本身不分顺序，顺序是收集器决定的；写收集器之前先问一句“下游在不在意顺序”，在意的场景默认就该选 LinkedHashSet。

【小技巧】取 Map 里的值用 `getOrDefault`，别写“get 后判 null 再给默认值”：`map.getOrDefault(k, 0)` 一行拿到“有就用、没有就用默认值”，默认值只是临时返回，不会写进 map。注意它和 `computeIfAbsent` 的分工：只想读就用 getOrDefault，想“没有就顺手存一个”才用 computeIfAbsent；读操作别顺手改了 map。

【小技巧】同步包装器的复合操作仍要手动加锁，迭代时也一样：`Collections.synchronizedList` 只让单个方法原子，`contains + add`、遍历整个列表都不是原子操作，官方文档明确要求迭代时用 `synchronized(list)` 把循环包起来。换了同步包装器就以为“整个集合线程安全了”，是最常见的误判——同步的是方法，不是操作序列。

【小技巧】静态常量集合直接用 `List.of` / `Map.of`，别再 `new ArrayList` 装完又包一层：常量集合天生只读，`List.of("a", "b")` 一行就是不可变快照，创建后谁也改不了，也不用再为“怕别人改”多做防御性拷贝。元素少（10 个以内）时 `of` 重载最顺手，元素多时用 `List.copyOf` 从现成集合转一道。

【冷知识】集合框架是 Java 1.2（1998 年）才随 JDK 1.2 一起引入的：Java 1.0/1.1 时代只有 `Vector`、`Hashtable`、`Enumeration` 这套老容器，接口与实现混在一起。集合框架由 Joshua Bloch 主导设计，第一次把“接口定语义、实现类给性能取舍”这套分层带进 JDK——`Vector`、`Hashtable` 至今还留在 JDK 里，只是新代码基本不再用。

【冷知识】`Collections.sort` 与对象数组排序用的是 TimSort：Java 7 起，`Arrays.sort(Object[])` 和 `Collections.sort` 底层都是 TimSort（Tim Peters 为 Python 写的归并排序变体），对“局部已有序”的数据特别快；基本类型数组用的则是双枢轴快速排序。同一句 `sort`，对象走归并、基本类型走快排，选型依据是“对象排序要稳定、基本类型不用稳定”。

【冷知识】`EnumSet` 内部就是一个 long 的位向量：枚举类型元素个数不超过 64 时，一个 `EnumSet` 只用一个 long 表示，增删查全是位运算，速度接近数组下标访问。`EnumMap` 同理，内部直接按枚举序数当数组下标。枚举集合快不是因为算法巧，是因为数据结构本身就是位图——用枚举当 key 或做标志位集合时，`EnumSet` 是最省的那一个。

【冷知识】`Set.of` / `Map.of` 的迭代顺序是不固定的：不可变集合为了防御哈希攻击，迭代顺序经过随机化，同一份数据每次运行的遍历顺序都可能不同。代码里依赖 `Set.of` 的输出顺序、或拿它当“有序”的集合用，等于在靠运气跑——要顺序用 `LinkedHashSet` 或 `List.of`，`Set.of` 只保证去重、不保证任何顺序。

## 6. 面试与自测

- `Collection` 与 `Map` 是什么关系？为什么 `Map` 不继承 `Collection`？
- `List`、`Set`、`Queue` 各自的语义是什么？各举一个代表实现并说清适用场景。
- fail-fast 是什么机制？它能保证线程安全吗？增强 for 里删元素为什么会抛异常？
- `Collections.unmodifiableList` 与 `List.of` 有什么本质区别？各适合什么场景？
- 自测：写一段代码，分别用 `HashSet`（无序）、`LinkedHashSet`（插入顺序）、`TreeSet`（自然排序）装同一组字符串并打印，验证三者的遍历顺序差异。

### 参考答案

1. 两者是平行的两大体系，`Map` 不继承 `Collection`。`Collection` 装单个元素，语义是“元素的集合”；`Map` 装键值对，语义是“key 到 value 的映射”，没有“元素”的概念，`size`、`add` 这些接口语义都对不上，硬继承只会让接口失真。
2. `List` 有序可重复、有索引，如 `ArrayList`，适合随机访问；`Set` 去重无索引，如 `HashSet`，适合判重与去重；`Queue` 是排队语义，如 `ArrayDeque`，适合队头队尾操作与生产消费。选型先看语义：要索引选 List、要去重选 Set、要排队选 Queue。
3. fail-fast 靠内部 `modCount` 检测迭代中的结构性修改，发现就抛 `ConcurrentModificationException`。它只是尽早暴露 bug 的检测机制，不能保证线程安全，多线程仍需并发容器或加锁。增强 for 本质是迭代器，循环体内直接删元素会改 `modCount`，下次 `next()` 检测到不一致就抛异常，正确做法是用 `Iterator.remove()` 或 `removeIf`。
4. 本质区别是视图还是拷贝：`unmodifiableList` 是只读视图，底层集合变了视图跟着变；`List.of` 是数据拷贝，与原集合脱钩，且元素不允许为 `null`。要“快照式常量”用 `List.of`，要“别人只能读、自己还能改”用 unmodifiable 视图。
5. 验证要点：`HashSet` 输出顺序不固定（与哈希分布有关，多次运行也可能变化）；`LinkedHashSet` 输出顺序等于插入顺序；`TreeSet` 输出按字符串自然排序（字典序）。三者装同一组元素、去重结果相同，只有遍历顺序不同，这正是“语义定顺序”的直观证据。
