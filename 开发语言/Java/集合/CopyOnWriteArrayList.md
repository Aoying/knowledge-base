# CopyOnWriteArrayList

## 1. 核心概念

- `CopyOnWriteArrayList` 是 [ArrayList与扩容](开发语言/Java/集合/ArrayList与扩容.md) 的线程安全对应物，位于 `java.util.concurrent` 包。
- 核心机制写时复制：任何修改（add/set/remove）都先把底层数组整表拷贝一份，在副本上改，改完再把引用切到新数组。读操作完全无锁，直接读当前数组。
- 适用画像非常窄：**读极多、写极少、数据量小**。偏离这个画像就是性能灾难，选它之前先对照第 5 节。
- 允许 null 元素；迭代器是快照迭代器（见第 3 节），弱一致，不抛 `ConcurrentModificationException`。

## 2. 基础知识

```java
List<String> list = new CopyOnWriteArrayList<>();
list.add("a");
list.addIfAbsent("a");     // 独有方法：不存在才添加，检查+添加是原子的
list.addAllAbsent(List.of("a", "b")); // 批量版，只加不存在的
list.get(0);               // 无锁读
```

- 复合操作注意：单个方法是线程安全的，但 `if (!list.contains(x)) list.add(x);` 这种检查再添加仍非原子，要用 `addIfAbsent`，和 [ConcurrentHashMap](开发语言/Java/集合/ConcurrentHashMap.md) 里「单个方法原子 ≠ 复合操作原子」是同一条纪律。
- 配套类 `CopyOnWriteArraySet` 底层就是它（元素去重靠线性扫描的 contains 判断），同样只适合小数据量。

## 3. 进阶知识

### 快照迭代器

- 迭代器创建时记住当时的数组引用，之后集合怎么改，迭代看到的都是那一份快照：不反映新增，也看不到删除。
- 因此迭代器不支持 `remove`（调了抛 `UnsupportedOperationException`）——它操作的是过期快照，删谁都没有意义。
- 好处：迭代期间零锁、零干扰，长遍历不会拖住写线程。代价：读到的可能是旧数据，业务必须能容忍。

## 4. 原理剖析

```java
// add 简化流程
lock.lock();                        // 写锁：同一时刻只有一个写者（锁实现随版本有变化，语义不变）
try {
    Object[] old = getArray();
    Object[] copy = Arrays.copyOf(old, old.length + 1);
    copy[old.length] = e;
    setArray(copy);                 // volatile 引用一次性切换
} finally { lock.unlock(); }
```

- 数组引用字段是 `volatile` 的：切换后其他线程的读立刻看到新数组；单个元素在数组内的位置不变，读不需要任何同步。
- 每次写都是 O(n) 整表拷贝 + 新数组分配：写 n 次就是 O(n²) 的拷贝量，还持续制造垃圾数组给 GC。
- 与 [ConcurrentHashMap](开发语言/Java/集合/ConcurrentHashMap.md) 对照：CHM 是分桶细化锁、读写并行；COW 是写全量复制换读零成本，两个极端，不要混用场景。

## 5. 实战应用

适合的典型场景：

- 事件监听器列表：注册/注销偶尔发生，事件触发时高频遍历调用。
- 读多写少的配置/白名单：启动加载、偶尔热更新，请求路径上反复查。
- 路由表、策略表这类小规模、变更低频的数据。

不适合：

- 写频繁（日志收集、任务列表）：拷贝成本直接爆炸，用 [Queue与Deque](开发语言/Java/集合/Queue与Deque.md) 的阻塞队列或 CHM。
- 数据量大：哪怕写得少，单次拷贝大数组也会造成毛刺；考虑不可变快照 + volatile 引用手动实现，或读写锁保护普通 ArrayList。

## 6. 疑难杂症

### 场景 1：换上 COW 后吞吐反而暴跌

- 原因：写比例被低估。先统计真实读写比，写超过个位数百分比就该回滚到 `Collections.synchronizedList`、读写锁方案或 CHM 家族。
- 排查：看 GC 日志里 `Object[]` 分配是否异常增多，这是 COW 写拷贝的典型指纹。

### 场景 2：遍历时拿不到刚 add 的元素

- 不是 bug：迭代器是创建时的快照。要求读到最新数据的遍历，每次都新建迭代器或用下标 get 循环（get 读的永远是当前数组）。

## 7. 常见误区

- 误区：线程安全就等于万能。它只解决并发正确性，写成本和数据新鲜度是另付的价钱。
- 误区：迭代器弱一致 = 随便改不用管。遍历期间写线程照常全量拷贝，频繁写+长遍历叠加时拷贝开销翻倍。
- 误区：用它装大集合再偶尔改一次就行。单次拷贝的延迟毛刺也可能打到 P99，先算数据量。

## 8. 性能优化

- 批量写合并：能一次 `addAll` 就不要逐个 add，每次 add 都是一次全量拷贝，这是最大的优化点。
- 容量无法预分配（无 initialCapacity 的数组复用机制，构造传容量只影响初始数组），数据量大从一开始就别选它。

## 9. 版本差异

- 机制自 JDK 5 引入后不变；内部写锁的实现细节在后续版本有调整（锁字段形式不同），不影响语义与选型结论。

## 小技巧与冷知识

【小技巧】注册监听器时要把实例引用留下来，注销时才能删掉：`remove(Object)` 是按 `equals` 匹配的，监听器类没重写 `equals` 时就是按引用比较——注册时用匿名内部类 `add(new Listener(){...})`，注销时再 `new` 一个长得一样的根本删不掉。注册返回的实例要存进字段或 Map，注销传同一个引用；“注册一时爽、注销找不到人”是监听器列表最常见的泄漏。

【小技巧】`addIfAbsent` 内部已经先线性扫描了一遍，调用前别再自己 `contains` 一次：先 `contains` 再 `addIfAbsent`，同一个元素被扫了两遍，列表越长浪费越大。`addIfAbsent` 的返回值就是答案——返回 true 说明加进去了，false 说明已存在；外部那层 `contains` 是纯多余的检查，删掉它。

【小技巧】批量删元素先收集待删集合、再调一次 `removeAll`：逐个 `remove` 时每次删除都是一次整表拷贝，删 k 个就是 k 次拷贝；`removeAll` 内部一次锁内把待删元素过滤掉、只拷一次新数组。删除量越大差距越明显；“先收集、再一次删”和原文“批量写合并成 addAll”是同一条纪律在删除方向的落地。

【小技巧】逐个 `set` 改元素和逐个 `add` 一样贵：`set` 不是原地改数组元素，同样要整表拷贝一份再切换引用，循环里逐个 `set` 改 100 个元素就是 100 次全表拷贝。批量改先在普通 `ArrayList` 上改完，再把改好的内容一次性交给新列表；“改一个元素”的代价和“加一个元素”一样，只和表大小有关，和改动大小无关。

【小技巧】热更新配置时先在新列表上改好、再整体替换引用，别逐条改线上列表：配置热更新是“读多写少”里唯一的写操作，逐条 add/remove 会连续触发多次全表拷贝，还让读线程在更新中途看到半新半旧的中间态。做法是另建一个普通列表改好、再用它构造新的 `CopyOnWriteArrayList`，把持有它的字段（volatile 引用）一次性换掉——读线程要么看到旧配置、要么看到新配置，永远看不到改一半的配置。

【小技巧】监听器回调要逐个 try-catch，别让一个监听器掀翻整条遍历：遍历是按顺序调每个监听器的回调，中间某一个抛了运行时异常，遍历直接中断，后面的监听器收不到这次事件，发布方还以为通知发出去了。回调外包一层 try-catch、异常只记日志不中断，是事件分发里和快照迭代器同等重要的纪律。

【小技巧】别拿它当计数器或累加器：计数器是“写频繁”的典型——每次自增都是一次整表拷贝，几千次自增就能把 GC 打爆。计数用 `AtomicLong` 或 `LongAdder`，列表只装真正需要遍历的条目；“每次写都拷全表”这条代价，写操作越小、越频繁，反噬越严重。

【小技巧】想“拍一张快照再慢慢处理”时直接调 `toArray`：`toArray` 返回的是当前数组的一份拷贝，和创建时刻的快照迭代器看到的是同一份数据，但用起来更顺手——不用守着迭代器的 hasNext/next 慢慢走，拿到的数组可以传给别的线程、反复遍历、排序过滤都不影响原集合。快照语义不只迭代器有，`toArray` 是同一机制的另一种出口。

【小技巧】它的 `equals` 是按内容比较的，可以直接拿来断言两次快照是否相同：两个 `CopyOnWriteArrayList` 只要元素序列相同，`equals` 就返回 true，不管底层是不是同一份数组。热更新后想验证“新配置确实生效了”，直接比较新旧两个列表的 `equals`；想判断“这次更新到底改了什么”，比较前后快照比翻日志快。

【冷知识】它随 JDK 5 的 `java.util.concurrent` 包一起引入，是 JSR 166（Doug Lea 主导）的一部分：写时复制的思路在并发包诞生之初就定型了，之后二十年机制没变过，变的只是写锁的内部实现细节。一个机制二十年不用改，说明它解决的是一个很窄但很稳定的问题——读极多、写极少。

【冷知识】写时复制不只是集合的技巧，是操作系统和数据库都在用的通用思想：Linux 的 `fork` 子进程共享父进程内存、写时才复制页面；ZFS、Btrfs 的快照是“写时复制文件系统”；数据库的 MVCC 也是“读旧版本、写新版本”。`CopyOnWriteArrayList` 只是把这套思想搬进了一个集合类——理解了 fork 和快照，就理解了它为什么读不用锁。

【冷知识】写操作的代价和“改了多少”无关，只和“表有多大”有关：改一个元素和加一个元素拷的数组一样大，删一个元素和清空重建拷的数组也一样大。评估它合不合适时，唯一要算的数就是表的大小——表越大，任何一次写都越贵，这也是原文说“数据量大从一开始就别选它”的底层原因。

## 10. 面试与自测

- 写时复制的完整流程是什么？读为什么不用加锁？
- 它的迭代器和 ArrayList 的 fail-fast 迭代器有什么本质区别？
- 什么场景适合 COW？什么场景用它必翻车？
- `addIfAbsent` 解决了什么复合操作问题？
- 它与 ConcurrentHashMap 的并发思路有什么不同？分别适合什么读写画像？
- 自测：一个线程循环 add，另一个线程用迭代器遍历，验证遍历内容恒为某时刻快照且永不抛异常。

### 参考答案

1. 写流程：加写锁 → 整表拷贝一份新数组 → 在副本上改 → volatile 数组引用一次性切换到新数组 → 解锁。读不用加锁：读直接读当前 volatile 数组引用，数组内元素位置不变、从不原地修改，读到的要么是旧数组要么是新数组，不会读到改一半的状态。
2. 本质区别：ArrayList 的 fail-fast 迭代器靠 modCount/expectedModCount 校验，迭代中结构性修改就抛 ConcurrentModificationException；COW 的迭代器是快照迭代器，创建时记住当时数组引用，之后集合怎么改都只看到那份快照，不抛异常，但也不支持 remove（调了抛 UnsupportedOperationException），且读到的可能是旧数据。
3. 适合：读极多、写极少、数据量小——事件监听器列表、读多写少的配置/白名单、路由表/策略表。必翻车：写频繁（每次写都是 O(n) 整表拷贝，写 n 次就是 O(n²) 拷贝量 + 大量垃圾数组）、数据量大（单次拷贝也会造成 P99 毛刺）。写超过个位数百分比就该回滚到 synchronizedList、读写锁方案或 CHM 家族。
4. addIfAbsent 把“检查 + 添加”做成一个原子操作：单个方法线程安全不等于复合操作原子，if (!contains(x)) add(x) 两步之间仍有竞态，addIfAbsent 在写锁内一次完成判断与添加；批量版是 addAllAbsent。
5. 思路不同：CHM 是分桶细化锁、读写并行，适合通用高并发读写；COW 是写全量复制换读零成本，适合读极多写极少的小数据。读写画像：CHM 写多读多都能打；COW 只有读多写极少才划算，写一多就反噬。
6. 自测思路：一个线程循环 add，另一个线程用迭代器遍历。验证要点：遍历过程永不抛 ConcurrentModificationException；遍历内容恒为迭代器创建那一刻的快照（看不到遍历开始后新 add 的元素）；多次运行结果稳定；注意这验证的是快照语义，不是“读到最新数据”。
