# 生成器

## 1. 核心概念

生成器（Generator）是惰性求值的迭代器：函数体里只要出现 `yield`，这个函数就不再是普通函数，调用它不执行函数体，只返回一个生成器对象；每次 `next()` 时函数体才向前推进到下一个 `yield`，产出一个值并暂停，局部变量和执行位置被完整保存。

价值：以 O(1) 内存处理任意长的数据流，把"生产一串值"从一次性建表变成按需管道——读大文件、分页拉取、无限序列、流水线过滤都靠它。

```python
def count_up(n):
    i = 0
    while i < n:
        yield i
        i += 1

g = count_up(3)   # 不执行任何代码
next(g)           # 0
list(g)           # [1, 2]
```

## 2. 基础知识

### 生成器表达式

```python
squares = (x * x for x in range(10))     # 圆括号，惰性
total = sum(x * x for x in range(10))    # 作为唯一参数时可省括号
```

与列表推导式的区别只有一字：`[]` 立即求值建表，`()` 返回生成器。数据只遍历一次且量大时一律用生成器式。

### 迭代器协议

- 可迭代对象实现 `__iter__()` 返回迭代器；迭代器实现 `__next__()`，耗尽时抛 `StopIteration`。
- 生成器自动实现两者，`for` 循环就是协议的消费者：循环结束靠的正是捕获 `StopIteration`。
- 生成器只能遍历一次，耗尽后再次迭代得到空序列，不会报错。

### yield from

委托子生成器并透传其返回值（PEP 380）：

```python
def flatten(nested):
    for item in nested:
        if isinstance(item, list):
            yield from flatten(item)
        else:
            yield item
```

## 3. 进阶知识

### send / throw / close：双向通信

生成器不只是"生产者"，暂停在 `yield` 处时还能接收外部送入的值，`yield` 表达式的返回值就是送入值——这是协程的原型。

```python
def accumulator():
    total = 0
    while True:
        x = yield total      # 产出当前总和，并等待接收新值
        if x is None:
            break
        total += x
    return total

acc = accumulator()
next(acc)          # 启动，产出 0（必须先 next 或 send(None) 激活）
acc.send(10)       # 产出 10
acc.send(5)        # 产出 15
```

- `gen.throw(exc)`：在暂停点往生成器内部抛异常，可用于取消、超时控制。
- `gen.close()`：在暂停点抛 `GeneratorExit`，触发 finally 清理；关闭后再产出值会抛 RuntimeError。
- 生成器函数的 `return value` 不能直接拿到——它藏在 `StopIteration.value` 里，用 `yield from` 时则成为表达式的值。

### 生成器作管道

```python
def read_lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")

pipeline = (l for l in read_lines("big.log") if "ERROR" in l)
for line in pipeline:
    handle(line)
```

每一级都是惰性的：内存里同时只存在一行。

## 4. 原理剖析

- 生成器对象内部持有一个帧对象（frame），保存指令指针、局部变量、操作数栈状态；`yield` 时帧被挂起而非销毁，`next` 时恢复。代价是每个生成器约几百字节到几 KB 的固定开销，海量小生成器并存时要注意。
- 函数里有 `yield` 时，CPython 在编译期就把该函数的 code object 标记为 generator function，调用时直接构造生成器对象而不建普通帧执行。
- `for`、解包、`*` 展开、`list()` 都通过迭代器协议消费生成器；展开无限生成器（如 `*count_up(∞)`）会挂死。

## 5. 实战应用

**大文件流式处理**（小说引擎读章节文本、日志分析同理）：

```python
def iter_chapters(path, encoding="utf-8"):
    """按空行分段惰性产出段落，GB 级文件也不爆内存。"""
    buf = []
    with open(path, encoding=encoding) as f:
        for line in f:
            if line.strip():
                buf.append(line.rstrip("\n"))
            elif buf:
                yield "\n".join(buf)
                buf = []
    if buf:
        yield "\n".join(buf)
```

**分页拉取 API**：把"翻页直到空"封装成生成器，调用方只写一个 for。

```python
def iter_pages(fetch_page, page_size=100):
    page = 1
    while True:
        rows = fetch_page(page, page_size)
        yield from rows
        if len(rows) < page_size:
            break
        page += 1
```

**无限序列**：斐波那契、心跳、重试间隔（指数退避生成器）都适合写成生成器配合 `itertools.islice` 截断。

## 6. 疑难杂症

- **`return` 与 `yield` 混用的困惑**：生成器里 `return` 表示结束迭代，不是给调用方返回值（除 `StopIteration.value` 的特殊通道）。
- **生成器在布尔判断里恒为真**：`if gen:` 永远 True，判断是否有数据要 try `next()` 或先转 list。
- **异常位置难定位**：惰性求值让异常在"消费点"而非"定义点"爆出，堆栈里要顺着 yield 链往回看；调试时可临时 `list(gen)` 提前触发。

## 7. 常见误区

- 以为生成器能反复用：耗尽即空，重复遍历需重新调用生成器函数。
- 小数据也滥用生成器：几百个元素的场景列表更快更直观，生成器有帧开销。
- 在生成器里做重 CPU 计算又期望并发：生成器只是惰性，不是异步；阻塞计算仍阻塞，异步场景看 [[asyncio]] 的异步生成器（`async def` + `yield`，用 `async for` 消费）。

## 8. 性能优化

- 经验法则：数据量未知/超大、只需一遍、中间结果可丢弃 → 生成器；需要 len、索引、反复遍历 → 列表。
- 省内存不等于省时间：逐个 yield 的函数调用开销略高于列表批量构建；纯 CPU 小数据列表推导式通常更快，先测量再选。
- 管道层数别太多：每多一层生成器就多一层帧切换，长链用 itertools 组合子（C 实现）替代手写嵌套。

## 9. 版本差异

- Python 3.7：生成器内的 `StopIteration` 自动转为 RuntimeError（PEP 479 全面生效），避免静默吞迭代。
- Python 3.8：`yield` 可用在推导式等更多位置的限制放宽（赋值表达式配合）。
- Python 3.12：生成器性能有小幅优化；`asyncio` 异步生成器在事件循环关闭时的清理更严格，必须 `aclose()` 或用 `async with` 管理。

## 小技巧与冷知识

- 【小技巧】取生成器的第一个元素时用 `next(gen, 默认值)` 而不是裸 `next(gen)`：空生成器会抛 `StopIteration`，带默认值的形式在耗尽时直接返回默认值，写"peek 一下有没有数据"或"取首行做表头"时不用再包 try/except，代码干净得多。注意它只消耗一个元素，不会把生成器重置。
- 【小技巧】无限生成器一定要配 `itertools.islice` 截断，千万别直接 `list()`：`list(count_up(10**9))` 这类写法会一直产出直到内存耗尽，而 `list(islice(gen, 10))` 只取前 10 个就停，`islice` 本身也是惰性的。调试无限序列时先用 `islice` 取一小段看输出，是最安全的习惯。
- 【小技巧】想把一个生成器"分给"两个消费者时用 `itertools.tee(gen, 2)`，而不是把生成器转成 list 再复用：`tee` 返回两个独立的迭代器，各自可以按自己的速度消费，适合"一边计数一边取样"这类场景。但要记住代价：`tee` 会在内部缓存已被一个分支消费、另一个分支还没消费的值，两个分支消费速度差得越大，缓存占用的内存就越大，极端情况下和转 list 没区别。
- 【小技巧】生成器当作"资源守门人"时，用 `contextlib.closing(gen)` 或 `try/finally` 包住消费循环：`close()` 会在暂停点抛 `GeneratorExit`，触发生成器内部的 `finally` 做清理（关文件、释放连接）。只写 `break` 跳出 for 循环不会立即清理——清理要等到生成器对象被垃圾回收时才发生，文件句柄可能因此多占一段时间。
- 【小技巧】`yield from` 不只能委托产出，还能"接住"子生成器的 return 值：`result = yield from 子生成器()` 里的 `result` 就是子生成器 `return` 的值，这是 PEP 380 规定的透传机制。写递归遍历、分页拉取"顺便汇总总数"时，用这一行就能把子生成器的汇总结果带回上层，不用再靠可变参数或全局变量传值。
- 【小技巧】`@contextlib.contextmanager` 本质上就是一个生成器：`yield` 之前是 `__enter__` 的准备代码，`yield` 之后是 `__exit__` 的清理代码。理解了这一点，写自定义上下文管理器时就不用再手写 `__enter__`/`__exit__` 两个方法；反过来，调试 contextmanager 出问题时，也可以把它当成普通生成器单步跟踪 `yield` 前后的执行。
- 【小技巧】生成器表达式作为函数唯一参数时可以省略外层括号，如 `sum(x * x for x in range(10))`，但一旦函数有第二个参数就必须补回括号，否则是语法错误。这个细节在写 `max/min/sorted` 的 key 式调用时最容易踩到：`max((x, y) for x, y in pairs)` 没问题，`sorted(x for x in data, reverse=True)` 就必须写成 `sorted((x for x in data), reverse=True)`。
- 【小技巧】调试惰性管道时，先把链路"截短"再逐步加长：先 `list(islice(第一级, 5))` 确认源头产出正确，再逐级接上过滤、映射，最后才全量跑。惰性求值让异常在消费点才爆出，链路越长越难定位是哪一级出的问题，分段验证是最省时间的排错方法。
- 【冷知识】生成器对象没有 `__len__`，也无法用 `len()` 或下标访问：因为它根本不知道后面还有多少个值，不产出就永远算不出来。想知道"还剩几个"只能把它消费完，或者一开始就用列表。同样，`in` 运算符对生成器是"消费式"的——`x in gen` 会一路 next 直到找到或耗尽，找到之后前面的元素就丢了。
- 【冷知识】生成器被垃圾回收时，CPython 会自动对它调用 `close()`，在暂停点抛 `GeneratorExit` 触发 `finally` 清理。所以原文里"关闭后再产出值会抛 RuntimeError"之外，还有一个隐含行为：如果生成器函数里捕获了 `GeneratorExit` 却又 `yield` 了一个值，CPython 会直接抛 `RuntimeError`，因为已经处于关闭流程的生成器不允许再恢复执行。
- 【冷知识】生成器函数体里出现 `yield` 的那一刻，整个函数就变成了"生成器工厂"：哪怕函数第一行就是 `return`，调用它也不会执行任何代码，只返回生成器对象；只有第一次 `next()` 才会真正进入函数体。这个"调用不执行"的特性常被新手忽略，也是"为什么生成器里的参数校验错误要到消费时才爆出"的原因——想提前校验参数，要在外层包一个普通函数，先校验再返回内部生成器。
- 【冷知识】`yield` 不能出现在推导式里：在本地 Python 3.12 上实测，`[(yield i) for i in range(3)]` 直接报 `SyntaxError: 'yield' inside list comprehension`，连海象运算符配合也不行。带状态的逻辑就该写成显式的生成器函数，推导式里只做简单产出——可读性和可维护性都更好。
- 【冷知识】生成器对象的帧可以通过 `gen.gi_frame` 直接访问，调试时能看到当前挂起位置的局部变量和行号。这在排查"生成器停在哪一步"时很有用，不过它只是调试手段——生产代码不应该依赖帧对象内部结构，不同 Python 实现的帧细节并不保证一致。
- 【冷知识】`for` 循环消费生成器时，循环体里 `break` 不会调用 `close()`，生成器只是被丢弃、等待垃圾回收才清理。如果生成器内部持有文件句柄或网络连接，`break` 后资源释放的时机是不确定的；需要确定性清理时，显式调用 `gen.close()` 或用 `contextlib.closing` 包起来才是可靠做法。

## 10. 面试与自测

1. 列表推导式与生成器表达式的求值时机、内存、速度差异？
2. 生成器为什么只能遍历一次？想遍历两次怎么办？
3. `send()` 前为什么必须先 `next()` 或 `send(None)`？
4. 生成器函数的 return 值去哪了？如何取到？
5. 一次写出"惰性读取大文件并过滤 ERROR 行计数"的管道。

### 参考答案

1. 求值时机：列表推导式立即求值建表，生成器表达式返回生成器、惰性按需产出。内存：列表随数据量线性增长，生成器是 O(1) 内存处理任意长的数据流。速度：纯 CPU 小数据场景列表推导式通常更快（生成器有帧开销），数据量未知或超大、只需遍历一遍、中间结果可丢弃时一律用生成器。
2. 生成器只能遍历一次，是因为它内部持有一个帧对象保存执行位置，耗尽后再次迭代得到空序列，不会报错。想遍历两次时，重新调用生成器函数生成一个新的生成器对象；或者一开始就转成 list（代价是失去 O(1) 内存优势），也可以用 itertools.tee 分流，但 tee 会在内部缓存已产出未消费的值。
3. 因为刚创建的生成器还没有启动，执行位置停在函数开头，yield 表达式无法接收值；此时 send 一个非 None 的值会抛 TypeError。必须先用 next() 或 send(None) 把执行推进到第一个 yield 处激活，之后 send 的值才会成为该 yield 表达式的返回值。
4. 生成器函数的 return 值藏在 StopIteration.value 里，for 循环会自动捕获 StopIteration 所以直接拿不到。取到它的办法有两种：手动用 next() 驱动并捕获 StopIteration 读 .value；或用 yield from 委托子生成器，此时委托表达式的值就是子生成器的 return 值（PEP 380 的透传机制）。
5. 关键思路是三段惰性管道：第一段逐行 yield（一次内存里只存在一行），第二段用生成器表达式过滤含 ERROR 的行，第三段用 sum 或计数器聚合，全程不建表。验证要点：ERROR 行数与 grep -c ERROR 对照一致；拿 GB 级文件跑一遍确认内存不随文件变大；注意文件编码统一用 utf-8 打开，避免中途编解码报错打断管道。
