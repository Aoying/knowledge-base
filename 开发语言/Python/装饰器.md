# 装饰器

## 1. 核心概念

装饰器（Decorator）是把一个函数（或类）作为参数、返回一个新函数的可调用对象。语法糖 `@decorator` 等价于 `func = decorator(func)`，在不修改原函数代码的前提下织入横切逻辑：日志、计时、重试、缓存、权限校验、事务。

本质前提：Python 里函数是一等对象——可以赋值、作参数、作返回值、嵌套定义；再配合闭包，内层函数就能"记住"外层传入的原函数。

```python
def deco(fn):
    def wrapper(*args, **kwargs):
        print("before")
        result = fn(*args, **kwargs)
        print("after")
        return result
    return wrapper

@deco            # 等价于 greet = deco(greet)
def greet(name):
    return f"hello {name}"
```

## 2. 基础知识

### 三层结构：带参装饰器

装饰器本身要接收参数时，需要三层嵌套：最外层收参数，中层收函数，内层收调用参数。

```python
import functools, time

def retry(times=3, delay=0.5):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            last_exc = None
            for i in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    last_exc = e
                    time.sleep(delay)
            raise last_exc
        return wrapper
    return decorator

@retry(times=5)
def fetch(url):
    ...
```

### functools.wraps 必须写

不用 `@functools.wraps(fn)`，被装饰函数的 `__name__`、`__doc__`、`__module__` 会变成 wrapper 的，导致日志、调试、框架反射（如 Flask 路由、pytest 收集）出错。wraps 本身也是一个装饰器，它把原函数的元数据拷贝到 wrapper 上，并设置 `__wrapped__`。

## 3. 进阶知识

### 类装饰器两种形态

1. **用类实现装饰器**：类定义 `__call__` 即可当装饰器用，适合需要保存状态的场景（计数、限流）。

```python
class CountCalls:
    def __init__(self, fn):
        functools.update_wrapper(self, fn)
        self.fn = fn
        self.count = 0
    def __call__(self, *args, **kwargs):
        self.count += 1
        return self.fn(*args, **kwargs)

@CountCalls
def work(): ...
work.count  # 调用次数
```

2. **装饰类本身**：`@dataclass`、`@singleton` 就是装饰类——接收类、加工后返回类（可返回原类或子类）。

### 装饰器叠加顺序

```python
@a
@b
def f(): ...
# 等价于 f = a(b(f))：定义时自下而上包裹，调用时自上而下进入
```

### functools 工具箱

- `functools.lru_cache(maxsize=128)`：函数结果缓存，参数必须可哈希；Python 3.9+ 可直接用 `functools.cache`（无限缓存）。
- `functools.singledispatch`：按第一个参数类型分发，实现泛型函数。
- `functools.partial`：偏函数，冻结部分参数。

## 4. 原理剖析

装饰发生在**定义期**（模块导入时），不是调用期：`@deco` 在 `def` 语句执行完的瞬间就调用 deco 并替换名字绑定。所以装饰器里不要放重 IO，否则 import 就变慢。

闭包的实现：内层函数引用的外层变量保存在 `wrapper.__closure__` 的 cell 中；`fn.__name__` 等元数据存储在 `__dict__` 与 dunder 属性上，wraps 做的就是 `WRAPPER_ASSIGNMENTS` 的拷贝。

带参装饰器比普通装饰器多执行一层调用：`@retry(3)` 先执行 `retry(3)` 得到真正的 decorator，再用它装饰函数。

## 5. 实战应用

- **重试**：调本地 Ollama / 外部 HTTP 接口时的重试装饰器（见第 2 节），生产版要加指数退避和只重试可恢复异常。
- **缓存**：`@lru_cache` 给纯计算函数（如小说引擎里章节上下文的指纹计算）加速；注意缓存无界增长风险。
- **日志与计时**：统一记录函数耗时，定位慢逻辑。

```python
def timed(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} cost {time.perf_counter() - t0:.3f}s")
    return wrapper
```

- **权限/校验**：Web 框架的 `@login_required`；参数校验装饰器统一做入参检查，避免每个函数重复写。
- Java 对照：等价物是 Spring AOP 的 `@Aspect` + 注解，思想一致（横切关注点抽离），只是 Python 装饰器是语言级语法、无需容器。

## 6. 疑难杂症

- **装饰后函数签名丢失**：inspect.signature 显示 wrapper 的 `(*args, **kwargs)`——wraps 已处理大部分，但 IDE 提示仍可能不准；严格场景用 `decorator` 第三方库或类型存根。
- **方法装饰顺序问题**：`@staticmethod`/`@classmethod` 与自定义装饰器叠加时，自定义装饰器要放在它们**上方**（更靠近 def 的先执行）；顺序反了拿到的是 descriptor 对象而非函数。
- **lru_cache 用在方法上**：`self` 参与缓存键，实例无法被 GC 回收，造成内存泄漏；改为缓存独立函数或用 `functools.cached_property` 的思路处理。

## 7. 常见误区

- 认为装饰器在每次调用时才"装饰"——错，装饰只发生一次，在定义期；每次调用执行的是 wrapper。
- 无参和带参装饰器写法混淆：`@retry` 与 `@retry()` 不是一回事，漏括号会把函数当参数传给 retry。
- 在 wrapper 里忘记 `return fn(...)`，函数静默返回 None，是最常见的装饰器 bug。

## 8. 与 asyncio 的关系

协程函数也是函数，装饰器同样适用，但 wrapper 必须是 `async def` 并 `await` 原函数：

```python
def async_timed(fn):
    @functools.wraps(fn)
    async def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        result = await fn(*args, **kwargs)
        print(f"{fn.__name__} cost {time.perf_counter() - t0:.3f}s")
        return result
    return wrapper
```

用普通同步 wrapper 装饰协程函数，会得到一个"返回协程对象但从不 await"的假函数，运行时报 `coroutine was never awaited`。判断依据：`asyncio.iscoroutinefunction(fn)`，需要同时支持同步/异步时写两个版本或运行时分流。

## 9. 版本差异

- Python 3.9：新增 `functools.cache`、`functools.singledispatchmethod` 完善。
- Python 3.10：`@decorator` 语法放宽，允许任意表达式（如 `@buttons[0].click`）。
- Python 3.12：`functools.wraps` 等行为无变化；类型标注可用 `ParamSpec` 精确标注装饰器签名（PEP 612，自 3.10 起可用）。

## 10. 面试与自测

1. 手写一个带参数的重试装饰器，并说明为什么要三层嵌套。
2. 不用 wraps 会出什么问题？wraps 具体拷贝了什么？
3. `@a @b def f` 的包裹与执行顺序分别是什么？
4. lru_cache 的失效策略和适用边界是什么？用在实例方法上有什么风险？

### 参考答案

1. 三层嵌套的分工是：最外层收装饰器参数（如 times、delay），中层收被装饰的函数，内层 wrapper 收调用参数（*args、**kwargs）并在循环里 try 调用原函数、捕获异常后 sleep 再试，次数耗尽后抛出最后一次异常。之所以必须三层，是因为 @retry(times=5) 要先执行 retry(5) 得到真正的装饰器，再用它装饰函数；少一层就分不清参数和函数，@retry 与 @retry() 也会变成两回事。验证要点：失败 N 次内成功则返回结果；超过次数抛原异常而非静默 None；只重试可恢复异常并加指数退避；装饰后函数名与文档未变（配合 wraps）。
2. 不用 wraps 时，被装饰函数的 __name__、__doc__、__module__ 会变成 wrapper 的，导致日志、调试、框架反射（如 Flask 路由、pytest 收集）出错。wraps 具体拷贝的是 WRAPPER_ASSIGNMENTS 里列出的元数据，并设置 __wrapped__ 指向原函数。注意 wraps 已处理大部分元数据，但 inspect.signature 仍可能显示 wrapper 的 (*args, **kwargs)，严格场景用 decorator 第三方库或类型存根。
3. 包裹顺序是定义时自下而上：@a @b def f 等价于 f = a(b(f))，先 b 包 f，再 a 包 b(f)。执行顺序是调用时自上而下进入：先进入 a 的 wrapper，再进入 b 的 wrapper，最后执行原函数，返回时再逐层 unwind。
4. lru_cache 的失效策略是 LRU：maxsize 满时淘汰最久未使用项，maxsize 默认 128，Python 3.9 以上可用 functools.cache 表示无限缓存。适用边界是纯函数且参数必须可哈希；用在实例方法上有风险：self 参与缓存键，实例无法被 GC 回收，造成内存泄漏，应改为缓存独立函数，或用 cached_property 的思路处理。
