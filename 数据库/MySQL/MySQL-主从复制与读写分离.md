# MySQL-主从复制与读写分离

## 1. 核心概念

主从复制解决两个问题：**读扩展**（一主多从分摊查询压力）和**高可用底座**（主库挂了有副本可顶上，备份、统计类查询也卸载到从库）。它不解决写扩展和单库容量——那是 [分库分表](数据库/分库分表.md) 的活，分工见第 8 节。

代价先摆明：复制是异步搬运 binlog，从库数据天然**落后于主库一个延迟窗口**。读写分离的设计本质都是在和这个窗口打交道。

## 2. 复制链路：一条 binlog 的旅程

binlog 的格式与参数见 [MySQL binlog](数据库/MySQL/MySQL-binlog.md)，本篇只讲它怎么在主从之间流动：

1. 主库事务提交时写 binlog（`sync_binlog=1` 才保证落盘不丢）。
2. 主库的 **dump 线程**把 binlog 发给从库（从库 IO 线程先注册，再由主库推送）。
3. 从库 **IO 线程**接收，写入本地 **relay log**（中继日志），记录已接收位点。
4. 从库 **SQL 线程**（回放线程）读 relay log 在从库重放，记录已执行位点。

两个位点之差就是延迟来源：网络通常不是瓶颈，**回放跟不上主库写入**才是常态。

工程要点：**GTID**（全局事务标识）给每个事务编号，位点不再依赖 binlog 文件名 + 偏移量，切换与新增从库按 GTID 自动找位点，新部署默认开启；从库设 `read_only` 防误写——被独立写入后，主库同主键数据同步过来就是冲突中断。

## 3. 三种复制模式对比

| 模式 | 机制 | 一致性 | 代价 |
|---|---|---|---|
| 异步复制（默认） | 主库写完 binlog 就返回，不等从库 | 从库可能丢最后几个事务（主库宕机时） | 性能最好；切换必丢数据窗口 |
| 半同步复制 | 主库至少等一个从库确认收到 relay log 才返回 | 宕机切换时已确认事务不丢 | 每次提交多一个网络往返；从库全挂超时后退化为异步 |
| 组复制（MGR） | 多节点组内多数派认证后才提交，Paxos 类协议 | 强一致（实际多用单主模式） | 部署运维复杂、冲突检测开销；细节口径以官方文档为准 |

选型口径：普通业务异步复制、切换容忍丢秒级数据即可；金额、订单状态这类丢了要对账的，至少半同步；MGR 是重方案，没有专职 DBA 时慎上。

## 4. 主从延迟：成因与对策

**成因**（按出现频率）：

- **大事务**：一个事务改 10 万行，从库要一口气回放完才推进位点，延迟陡增。批处理更新必须在主库就拆小。
- **回放并行度不足**：老版本 SQL 线程单线程，主库并发写、从库串行放，必然越落越远。
- **无主键/无索引表更新**：ROW 格式按行匹配回放，无索引时每行全表扫描，回放被拖死。
- **从库自身负载**：报表、备份压在从库上抢 CPU/IO，回放排队。
- **DDL 与锁**：大表 DDL 在从库回放期间阻塞后续事务。

**对策**：开**并行复制**（5.7 按逻辑时钟/组提交并行，8.0 默认基于 WriteSet——行不冲突即可并行回放）；监控延迟别只看 `Seconds_Behind_Master`（粗略口径），准确延迟看 GTID 差或心跳表打点；治理先治源头（拆大事务、补主键），加机器最后一步。

## 5. 「读己之写」：读写分离的硬骨头

用户刚下单，跳到订单页却查不到——写主读从 + 延迟窗口的经典事故。处理策略按严格程度排：

1. **关键链路读主**：下单后跳转页、支付结果页、审批待办这类「写完马上看」的路径直接读主库，简单可靠，代价是这部分读压力回主库。默认首选。
2. **会话级粘性**：用户写后 N 秒内读全走主库，平衡一致性与分流。
3. **位点等待**：写时拿到事务 GTID，读从库前等从库回放位点追上它（`WAIT_FOR_EXECUTED_GTID_SET`），一致性最强，但延迟大时读被拖住，要配超时降级回主库。
4. **延迟阈值路由**：从库延迟超阈值自动摘除或回退主库，防故障级延迟，不解决秒级读己之写。

原则：**别追求全站强一致**。列表、搜索、历史详情放心走从，强一致只给少数关键路径，逐条列清单而不是全局开关。

## 6. 读写分离落地三路线

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 应用层多数据源 | 代码里显式区分主/从 DataSource，注解切库 | 零中间件、行为可控、排障直接 | 每应用都要接；从库增减要改配置发版 |
| ShardingSphere | JDBC 层透明路由（或 Proxy 模式独立部署） | 对代码近乎透明，自带负载均衡，常与分片一起用 | 框架复杂度；SQL 兼容性要逐条验证 |
| 独立中间件（ProxySQL 等） | 应用连中间件，按 SQL 类型与规则转发 | 语言无关、集中运维、切换只改中间件 | 多一跳延迟；多一个要保高可用的组件 |

Java 侧应用层路线就是 [多数据源](开发语言/Java/多数据源.md) 的 dynamic-datasource：写 `@DS("master")`、读 `@DS("slave")`，把读主清单落到注解上。ao 的神农 e 贷用 OceanBase，OB 内部多副本强一致、读写不分家，这三条路线针对自建 MySQL 场景。

## 7. 主从切换与数据回补

主库故障切换的动作清单（MHA、Orchestrator 等工具做的也是这几步）：

1. 确认主库真死（防网络分区误判），冻结旧主写入。
2. 选数据最新的从库（已执行 GTID 最大）提升为新主。
3. 其余从库改指向新主，按 GTID 补齐差异。
4. 流量切换：改 VIP / 中间件配置 / 应用数据源，写流量只进新主。
5. 旧主恢复后**不能直接当主用**：它可能有未同步的事务，只能降为从库，对账回补后再上线。

**脑裂**是最坏情况：分区两侧都在写，同一业务在两个库各生成一份。防护靠 fencing——切换前先确保旧主不可写（封端口、置只读），宁可切换慢，不可双主并存。**数据回补**没有银弹：按 GTID 比对差异行、逐表对账（校验和 + 按主键补差，思路同 pt-table-checksum/sync），金额类走业务对账单兜底——冲突数据哪份对，是业务问题不是技术问题。

## 8. 与分库分表的分工

- **复制**解决读压力、可用性、备份卸载，数据每份都是全量。
- **分片**解决写压力、单库容量，数据按规则切开，每片只有一部分。

组合顺序：先一主多从 + 读写分离（成本低、无侵入），扛不住写再分片；分片后**每个分片内部仍是一主多从**，复制的知识不作废。

## 9. 常见误区

- 上了读写分离读性能就翻倍：从库回放也占资源、热点读前面还有缓存层，先定位真瓶颈再扩。
- 延迟显示为零就等于没延迟：无流量时恒为 0，大事务一来立刻跳秒。
- 切换演练没必要：没演练过的流程，故障当晚必然卡在某一步（权限、位点、连接串）。

## 10. 复制延迟定量：半同步等待与并行回放

复制延迟不是凭感觉估的：半同步每次提交多等的往返、并行回放的追赶速度、relay log 的积压量，都能手算。本节给三组可复算的算例，每例的前提写在开头，换了前提就重算；数字是估算口径，不是生产实测值。

### 10.1 半同步等待：每次提交多一个往返

半同步的等待点在提交返回之前：主库写完 binlog 并落盘后，等至少一个从库确认“已收到并写入 relay log”才返回。注意确认只到 relay log，不等从库回放执行——这是“半”的定量含义，确认的事务仍可能还没在从库上可见。

单连接串行提交时，每次提交至少多等一个 RTT，提交上限就是：

```
单连接提交上限（TPS）≈ 1000 ÷ RTT（毫秒）
```

| 主从 RTT | 单连接提交上限 | 备注 |
|---|---|---|
| 0.5ms（同机房） | 约 2000 TPS | 接近异步，半同步代价可忽略 |
| 2ms（同城跨机房） | 约 500 TPS | 单连接写密集业务开始感知 |
| 10ms（跨地域） | 约 100 TPS | 串行提交基本不可用 |

**算例 1**：某订单库单连接串行提交，本地提交耗时约 1ms。异步时每次提交约 1ms，单连接约 1000 TPS；开半同步后，RTT 0.5ms 时每次提交约 1.5ms，约 667 TPS；RTT 2ms 时每次提交约 3ms，约 333 TPS；RTT 10ms 时每次提交约 11ms，只剩约 91 TPS。RTT 每翻几倍，单连接吞吐就按同一比例往下掉。

这张表的上限只约束单连接串行提交，是悲观下界，不是实测值。多连接并发时，一次往返可以由组提交（group commit）摊到一批事务上，整体 TPS 高于表里数字；但单连接的延迟下限摆在那里，串行写密集的业务跨地域开半同步前先算这笔账。

超时兜底也要算进去：`rpl_semi_sync_master_timeout` 默认 10000 毫秒（10 秒），等不到确认就退化为异步复制，之后从库恢复再悄悄切回半同步。超时设得比正常 RTT 还小，等于变相关闭了半同步；生产常把它调到 1000 毫秒左右，宁可早降级也别让每次提交都卡满 10 秒。

### 10.2 并行回放：worker 数与追赶时间

回放速度决定延迟是收敛还是发散。先比大小：从库回放速度低于主库产生速度，延迟只会越拖越大，加监控也追不上；高于产生速度，多出的部分才是追赶积压的速度。

**算例 2**：主库每秒产生 1200 个事务，从库单线程回放速度 800 txn/s。

- 单线程时每秒净落 400 个事务，10 分钟新增积压 24 万事务，延迟单调增长。
- 开 4 个并行 worker，并行效率按 0.7 计：回放速度 = 800 × 4 × 0.7 = 2240 txn/s，净追赶速度 = 2240 − 1200 = 1040 txn/s。
- 已有积压 36 万事务时，追赶时间 = 360000 ÷ 1040 ≈ 346 秒，约 5.8 分钟追平。

换算公式就两条：

```
并行回放速度 ≈ 单线程回放速度 × worker 数 × 并行效率
追赶时间 = 积压事务数 ÷（并行回放速度 − 主库产生速度）
```

分母小于等于 0 意味着永远追不上，这时加 worker 只是减速带，治本是拆大事务、补主键、把从库上的报表负载挪走。worker 数的口径：MySQL 8.0.27 起 `replica_parallel_workers` 默认 4，从库默认就是多线程回放；8.0.27 之前默认 0（单线程），老版本升级后要显式调，设为 0 在 8.0.30 起已废弃。

并行效率不是线性：worker 数翻倍不等于回放速度翻倍。热点行更新、大事务、单库单表写集都会让多个 worker 互相等锁，效率打折；8.0 默认的 WRITESET 依赖跟踪比 COMMIT_ORDER 更容易并行，但治不了热点行——同一行被反复改，再多 worker 也只能串行。

### 10.3 relay log 积压量估算

延迟秒数乘以主库写入速率，就是从库 relay log 里攒下的量：

```
relay log 积压量 ≈ 延迟（秒）× 主库 binlog 写入速率
```

**算例 3**：主库 binlog 写入速率 2MB/s。延迟 60 秒时积压约 120MB；延迟 300 秒时积压约 600MB；写入速率 5MB/s、延迟 300 秒时积压约 1500MB。按事务数算也一样：300 秒 × 每秒 1200 事务 = 36 万事务积压，正好是算例 2 里那笔积压的来源。

磁盘口径：relay log 积压占的是从库磁盘，估容量时按“可容忍最大延迟 × 峰值写入速率”留空间，别按平均速率算——延迟最大那一刻往往正好是写入峰值。`relay_log_space_limit` 可以限制 relay log 总量，8.0 默认 0 表示不限，设了上限后 IO 线程会被限速，等于把磁盘压力转成接收延迟。

### 10.4 Seconds_Behind_Master 读数的口径与误读边界

`SHOW REPLICA STATUS` 里的 `Seconds_Behind_Master`（8.0.22 起改名 `Seconds_Behind_Source`）不是直接量出来的延迟，而是算出来的：从库当前时钟，减去 SQL 线程正在执行那个事件在主库上的时间戳。追平后显示 0，SQL 线程停了显示 NULL。

这个口径有四条误读边界：

1. **无流量时恒为 0**：没有新事件可执行，读数就是 0，不代表从库和主库数据一致，只代表没活干。
2. **时钟不同步直接虚报**：读数里减的是从库自己的时钟，主从时钟差几秒，延迟就虚高或虚低几秒；看延迟之前先确认两台机器都对了 NTP。
3. **长事务按开始时间戳计**：事件的时间戳是语句在主库上开始执行的时间，一个跑了 20 秒的大事务，从库刚开始回放它就显示 20 秒延迟，执行期间读数还继续涨；它后面排队的事务也被连带算进去。
4. **读数 0 不等于追平位点**：复制线程跑着不等于数据追上了，位点差要看 `Executed_Gtid_Set` 和主库的 `Executed_Gtid_Set` 对不对得上。准确延迟看 GTID 差或心跳表打点，`Seconds_Behind_Master` 只适合做粗略告警阈值。

边界条件汇总：半同步的表只适用于单连接串行提交，多连接加组提交会摊薄等待；并行回放的追赶公式要求回放速度大于产生速度，否则无解；relay log 估算要用峰值写入速率而不是平均值；`Seconds_Behind_Master` 的四条误读边界决定了它只能做粗略监控，不能当一致性判据。

## 原理剖析

本节只把原文已有章节给出的结论拆开讲清机制：不引入新概念，不补新数字，数字一律复用 §10 已核验的定量算例；凡原文没展开的点，文中明确标注，不作定论。

### 复制链路：两个位点之间差了什么

原文第 2 节给出的链路是四步：主库事务提交时写 binlog（`sync_binlog=1` 才保证落盘不丢）；主库的 dump 线程把 binlog 发给从库；从库 IO 线程接收，写入本地 relay log（中继日志），记录已接收位点；从库 SQL 线程（回放线程）读 relay log 在从库重放，记录已执行位点。机制的关键不在四步本身，而在两个位点之间：已接收位点追上主库，说明 binlog 已经搬到了从库；已执行位点追上已接收位点，数据才真正在从库上可见。延迟就是这两个位点之差在时间上的表现，原文第 2 节明确说网络通常不是瓶颈，回放跟不上主库写入才是常态——也就是说，多数时候 IO 线程已经把 binlog 搬到了 relay log 里，拖后腿的是 SQL 线程重放的速度。

GTID 在这条链路里的作用，是给每个事务编号，让位点不再依赖 binlog 文件名加偏移量，切换与新增从库按 GTID 自动找位点。原文第 2 节还给了从库设 `read_only` 防误写的要点：被独立写入后，主库同主键数据同步过来就是冲突中断。relay log 里攒下多少，可以用 §10 的口径换算：relay log 积压量约等于延迟（秒）乘以主库 binlog 写入速率（出处：§10.3）；算例 3 里主库 binlog 写入速率 2MB/s 时，延迟 60 秒积压约 120MB，延迟 300 秒积压约 600MB，写入速率 5MB/s、延迟 300 秒时积压约 1500MB（出处：§10.3 算例 3）。积压占的是从库磁盘，原文第 10.3 节明确说估容量时按可容忍最大延迟乘以峰值写入速率留空间，别按平均速率算。relay log 积压到什么程度会反过来限速 IO 线程、以及 `relay_log_space_limit` 之外的磁盘告警阈值取何值，原文未展开，不作定论。

### 半同步与异步：“半”到底卡在哪一步

原文第 3 节的对比表把三种模式的差别落在一个点上：主库返回之前等不等从库。异步复制是主库写完 binlog 就返回，不等从库，性能最好，但主库宕机时从库可能丢最后几个事务，切换必丢数据窗口。半同步是主库至少等一个从库确认收到 relay log 才返回，宕机切换时已确认事务不丢，代价是每次提交多一个网络往返；从库全挂超时后退化为异步。组复制（MGR）是多节点组内多数派认证后才提交，强一致，部署运维复杂，细节口径以官方文档为准。

“半”的定量含义在 §10.1 讲清了：确认只到 relay log，不等从库回放执行——已确认的事务仍可能还没在从库上可见。单连接串行提交时，每次提交至少多等一个 RTT，提交上限就是单连接提交上限（TPS）约等于 1000 除以 RTT（毫秒）（出处：§10.1）。原文给出的表是：RTT 0.5ms（同机房）约 2000 TPS，RTT 2ms（同城跨机房）约 500 TPS，RTT 10ms（跨地域）约 100 TPS（出处：§10.1）。算例 1 把这张表落到一次提交上：某订单库单连接串行提交，本地提交耗时约 1ms，异步时每次提交约 1ms、单连接约 1000 TPS；开半同步后，RTT 0.5ms 时每次提交约 1.5ms、约 667 TPS，RTT 2ms 时每次提交约 3ms、约 333 TPS，RTT 10ms 时每次提交约 11ms、只剩约 91 TPS（出处：§10.1 算例 1）。RTT 每翻几倍，单连接吞吐就按同一比例往下掉。

这张表的适用边界原文第 10.1 节也写明了：上限只约束单连接串行提交，是悲观下界，不是实测值；多连接并发时，一次往返可以由组提交摊到一批事务上，整体 TPS 高于表里数字，但单连接的延迟下限摆在那里。超时兜底也要算进去：`rpl_semi_sync_master_timeout` 默认 10000 毫秒（10 秒），等不到确认就退化为异步复制，之后从库恢复再悄悄切回半同步；生产常把它调到 1000 毫秒左右，宁可早降级也别让每次提交都卡满 10 秒（出处：§10.1）。超时设得比正常 RTT 还小，等于变相关闭了半同步。从库恢复后切回半同步的具体触发条件、以及组提交一次往返能摊到多少个事务，原文未展开，不作定论。

### 主从延迟：为什么回放跟不上是常态

原文第 4 节把延迟成因按出现频率排了五条：大事务、回放并行度不足、无主键或无索引表更新、从库自身负载、DDL 与锁。机制上它们都指向同一个结论：主库是并发写，从库回放如果跟不上这个并发度，位点差只会越拉越大。老版本 SQL 线程单线程时，主库并发写、从库串行放，必然越落越远；无主键或无索引表更新时，ROW 格式按行匹配回放，无索引时每行全表扫描，回放被拖死；从库自身负载（报表、备份）抢 CPU 与 IO，回放排队；大表 DDL 在从库回放期间阻塞后续事务。对策原文第 4 节也给了方向：开并行复制，5.7 按逻辑时钟与组提交并行，8.0 默认基于 WriteSet——行不冲突即可并行回放；治理先治源头，拆大事务、补主键，加机器最后一步。

§10.2 把“跟不上”算成了追不追得上的判断：先比大小，从库回放速度低于主库产生速度，延迟只会越拖越大；高于产生速度，多出的部分才是追赶积压的速度。算例 2 的数字是：主库每秒产生 1200 个事务，从库单线程回放速度 800 txn/s，单线程时每秒净落 400 个事务，10 分钟新增积压 24 万事务，延迟单调增长；开 4 个并行 worker，并行效率按 0.7 计，回放速度等于 800 × 4 × 0.7 = 2240 txn/s，净追赶速度等于 2240 − 1200 = 1040 txn/s；已有积压 36 万事务时，追赶时间等于 360000 ÷ 1040 ≈ 346 秒，约 5.8 分钟追平（出处：§10.2 算例 2）。换算公式就两条：并行回放速度约等于单线程回放速度乘以 worker 数乘以并行效率；追赶时间等于积压事务数除以并行回放速度减主库产生速度（出处：§10.2）。分母小于等于 0 意味着永远追不上，这时加 worker 只是减速带，治本是拆大事务、补主键、把从库上的报表负载挪走。

并行效率不是线性，原文第 10.2 节写明了：worker 数翻倍不等于回放速度翻倍，热点行更新、大事务、单库单表写集都会让多个 worker 互相等锁，效率打折；8.0 默认的 WRITESET 依赖跟踪比 COMMIT_ORDER 更容易并行，但治不了热点行——同一行被反复改，再多 worker 也只能串行。worker 数的口径是：MySQL 8.0.27 起 `replica_parallel_workers` 默认 4，从库默认就是多线程回放；8.0.27 之前默认 0（单线程），老版本升级后要显式调，设为 0 在 8.0.30 起已废弃（出处：§10.2）。算例 2 里 36 万事务积压的来源，§10.3 也给了同一笔账：300 秒乘以每秒 1200 事务等于 36 万事务积压（出处：§10.3 算例 3）。并行效率 0.7 这个取值在不同 workload 下是多少、以及热点行场景下效率具体打几折，原文未展开，不作定论。

### 「读己之写」与延迟监控：为什么读数 0 不能当一致性判据

原文第 5 节把读己之写说成写主读从加延迟窗口的经典事故：用户刚下单，跳到订单页却查不到。机制上，写进了主库，还没回放到从库，这段时间从库上根本没有这行数据，读从库必然读不到。原文给的四种策略按严格程度排，差别在于绕开延迟窗口的方式不同：关键链路读主是写完马上看的路径直接读主库，简单可靠，代价是这部分读压力回主库，默认首选；会话级粘性是用户写后 N 秒内读全走主库，平衡一致性与分流；位点等待是写时拿到事务 GTID，读从库前等从库回放位点追上它（`WAIT_FOR_EXECUTED_GTID_SET`），一致性最强，但延迟大时读被拖住，要配超时降级回主库；延迟阈值路由是从库延迟超阈值自动摘除或回退主库，防故障级延迟，不解决秒级读己之写。原则是别追求全站强一致，列表、搜索、历史详情放心走从，强一致只给少数关键路径，逐条列清单而不是全局开关。

监控侧的坑在 §10.4：`SHOW REPLICA STATUS` 里的 `Seconds_Behind_Master`（8.0.22 起改名 `Seconds_Behind_Source`）不是直接量出来的延迟，而是算出来的——从库当前时钟，减去 SQL 线程正在执行那个事件在主库上的时间戳；追平后显示 0，SQL 线程停了显示 NULL（出处：§10.4）。这个口径有四条误读边界：无流量时恒为 0，没有新事件可执行，读数就是 0，不代表从库和主库数据一致，只代表没活干；时钟不同步直接虚报，读数里减的是从库自己的时钟，主从时钟差几秒，延迟就虚高或虚低几秒，看延迟之前先确认两台机器都对了 NTP；长事务按开始时间戳计，事件的时间戳是语句在主库上开始执行的时间，一个跑了 20 秒的大事务，从库刚开始回放它就显示 20 秒延迟，执行期间读数还继续涨，它后面排队的事务也被连带算进去；读数 0 不等于追平位点，复制线程跑着不等于数据追上了，位点差要看 `Executed_Gtid_Set` 和主库的 `Executed_Gtid_Set` 对不对得上（出处：§10.4）。所以原文第 4 节才说监控延迟别只看 `Seconds_Behind_Master`（粗略口径），准确延迟看 GTID 差或心跳表打点。会话粘性里写后 N 秒的 N 取何值、位点等待的超时取何值、心跳表打点的具体表结构与打点间隔，原文未展开，不作定论。

## 实战案例

### 案例一：跨地域开半同步，单连接串行提交吞吐掉下来了

**现象：** 按原文 §10.1 算例 1 的口径，某订单库单连接串行提交，本地提交耗时约 1ms。异步时每次提交约 1ms，单连接约 1000 TPS；开半同步后，RTT 0.5ms 时每次提交约 1.5ms，约 667 TPS；RTT 2ms 时每次提交约 3ms，约 333 TPS；RTT 10ms 时每次提交约 11ms，只剩约 91 TPS（出处：§10.1 算例 1）。RTT 每翻几倍，单连接吞吐就按同一比例往下掉，跨地域那档掉得最狠。

**排查：** 先按原文 §10.1 的公式算上限：单连接提交上限（TPS）约等于 1000 除以 RTT（毫秒）（出处：§10.1）。对照原文的表：RTT 0.5ms（同机房）约 2000 TPS，RTT 2ms（同城跨机房）约 500 TPS，RTT 10ms（跨地域）约 100 TPS（出处：§10.1）。这张表的上限只约束单连接串行提交，是悲观下界，不是实测值；多连接并发时，一次往返可以由组提交摊到一批事务上，整体 TPS 高于表里数字，但单连接的延迟下限摆在那里，串行写密集的业务跨地域开半同步前先算这笔账（出处：§10.1）。再核对超时兜底：`rpl_semi_sync_master_timeout` 默认 10000 毫秒（10 秒），等不到确认就退化为异步复制，之后从库恢复再悄悄切回半同步；生产常把它调到 1000 毫秒左右，宁可早降级也别让每次提交都卡满 10 秒；超时设得比正常 RTT 还小，等于变相关闭了半同步（出处：§10.1）。该业务实际的并发连接数与组提交摊薄后的实测 TPS，原文未展开，不能把算例 1 的单连接数字直接当作整库 TPS，不作定论。

**结论：** 半同步的代价不在从库回放，而在提交返回前多等的那一个 RTT，确认只到 relay log，不等回放执行（出处：§10.1）。同机房 RTT 0.5ms 时半同步代价可忽略，跨地域 RTT 10ms 时单连接串行提交基本不可用，选型时先按 1000 除以 RTT 算单连接上限，再决定这条写链路能不能开半同步；超时值要按正常 RTT 取，设得比 RTT 还小等于变相关闭了半同步（出处：§10.1）。

### 案例二：从库延迟越拖越大，监控读数却一度显示 0

**现象：** 按原文 §10.2 算例 2 的口径，主库每秒产生 1200 个事务，从库单线程回放速度 800 txn/s，单线程时每秒净落 400 个事务，10 分钟新增积压 24 万事务，延迟单调增长（出处：§10.2 算例 2）。同一笔积压按 §10.3 的口径也能算出来：300 秒乘以每秒 1200 事务等于 36 万事务积压（出处：§10.3 算例 3）。与此同时监控上的 `Seconds_Behind_Master` 却一度显示 0——原文 §10.4 写明了，无流量时恒为 0，没有新事件可执行，读数就是 0，不代表从库和主库数据一致，只代表没活干（出处：§10.4）。

**排查：** 先别信读数 0，按原文 §10.4 的口径核对位点：`Seconds_Behind_Master` 是从库当前时钟减去 SQL 线程正在执行那个事件在主库上的时间戳算出来的，追平后显示 0，SQL 线程停了显示 NULL；读数 0 不等于追平位点，位点差要看 `Executed_Gtid_Set` 和主库的 `Executed_Gtid_Set` 对不对得上，准确延迟看 GTID 差或心跳表打点（出处：§10.4）。再核对时钟与长事务两条边界：主从时钟差几秒，延迟就虚高或虚低几秒，看延迟之前先确认两台机器都对了 NTP；一个跑了 20 秒的大事务，从库刚开始回放它就显示 20 秒延迟，执行期间读数还继续涨（出处：§10.4）。然后按 §10.2 算追赶账：开 4 个并行 worker，并行效率按 0.7 计，回放速度等于 800 × 4 × 0.7 = 2240 txn/s，净追赶速度等于 2240 − 1200 = 1040 txn/s，已有积压 36 万事务时，追赶时间等于 360000 ÷ 1040 ≈ 346 秒，约 5.8 分钟追平（出处：§10.2 算例 2）。worker 数的口径是 MySQL 8.0.27 起 `replica_parallel_workers` 默认 4，8.0.27 之前默认 0（单线程），设为 0 在 8.0.30 起已废弃（出处：§10.2）。relay log 侧再按 §10.3 核对磁盘：主库 binlog 写入速率 2MB/s 时，延迟 60 秒积压约 120MB，延迟 300 秒积压约 600MB，写入速率 5MB/s、延迟 300 秒时积压约 1500MB（出处：§10.3 算例 3）。该从库真实的并行效率取值与真实积压事务数，原文未展开，需按原文口径用 GTID 差与心跳表实测，不作定论。

**结论：** 延迟收敛还是发散，先比回放速度与产生速度的大小：分母小于等于 0 意味着永远追不上，这时加 worker 只是减速带，治本是拆大事务、补主键、把从库上的报表负载挪走（出处：§10.2）。`Seconds_Behind_Master` 只适合做粗略告警阈值，不能当一致性判据，读数 0 时先对 GTID 再下结论（出处：§10.4）。relay log 积压按可容忍最大延迟乘以峰值写入速率留磁盘，别按平均速率算（出处：§10.3）。

## 小技巧与冷知识

【小技巧】从库只开 `read_only` 还不够，改用 `super_read_only` 才算锁死：`read_only=1` 只拦普通账号，有 SUPER 权限的账号照样能写；`super_read_only=1` 连 SUPER 账号也写不了。从库上一次手滑写入就会产生 GTID 里的“野事务”（errant transaction），之后主从切换时 GTID 对不上、复制直接中断，所以从库建议两个开关一起开。

【小技巧】复制断了先看 `SHOW REPLICA STATUS` 里的 `Last_IO_Error` 和 `Last_SQL_Error`：这两列直接写着断复制的报错原文，比翻 error log 快；再看 `Replica_IO_Running` 和 `Replica_SQL_Running` 是不是两个 Yes。IO 线程停了是网络或账号问题，SQL 线程停了多半是回放冲突（主键重复、表不存在），两者定位方向完全不同。

【小技巧】想临时冻结从库回放、又不想断接收，用 `STOP REPLICA SQL_THREAD`：它只停 SQL 回放线程，IO 线程继续收主库 binlog 写 relay log。适合“在从库做一致性快照、等主库某批写入过去再放行”的场景；恢复时 `START REPLICA SQL_THREAD`，攒下的 relay log 会快速追赶，比整条复制停掉重建快得多。

【小技巧】建新从库不用停主库：`mysqldump --single-transaction --master-data=2`，`--single-transaction` 让 InnoDB 在一致快照下导出，`--master-data=2` 会把当时的 binlog 位点以注释形式写进备份文件头。导入后按文件头里的 `CHANGE MASTER TO` 位点起复制，整个过程主库不用锁表停写。

【小技巧】8.0 想让并行回放更充分，把主库的 `binlog_transaction_dependency_tracking` 从默认 `COMMIT_ORDER` 改成 `WRITESET`：COMMIT_ORDER 只允许按组提交顺序并行，WRITESET 按行写集判断冲突，行不冲突的事务更容易并行回放。改的是主库参数（写集信息要随 binlog 发过去），从库配合把并行工作线程数调上来才见效；大事务、热点行更新多时别指望它，治本还是拆事务。

【小技巧】新从库上线前按清单验三项再接流量：`super_read_only` 已开、`SHOW REPLICA STATUS` 的两个 Running 都是 Yes、从库的 `Executed_Gtid_Set` 已经追上主库的 `Executed_Gtid_Set`。三项缺一项都别把读流量切过来，尤其第三项——复制线程跑着不等于数据追上了，位点没追平就接读流量，读到的还是旧数据。

【小技巧】从库误写之后别直接 `SET GLOBAL SQL_SLAVE_SKIP_COUNTER=1` 跳过去：跳事务只会把冲突藏起来，GTID 集合里多出的野事务还在，之后切换主库时照样对不上。正确做法是先 `SHOW REPLICA STATUS` 看清是哪个事务冲突，确认是误写后在从库上把那行数据手工改回与主库一致，再重启复制；金额类表宁可停复制对账，也别跳。

【冷知识】`Seconds_Behind_Master` 是拿时间戳相减算出来的：从库用 SQL 线程最近执行事件的时间戳，和主库上同一事件的时间戳相减，差值就是显示的秒数。所以主从两台机器的时钟不同步会直接虚报延迟，时钟快几秒、延迟就虚高几秒；看延迟之前先确认两台机器都对了 NTP，这是原文“粗略口径”背后的具体原因。

【冷知识】MySQL 8.0.22 起把复制术语里的 `SLAVE` 换成了 `REPLICA`：`SHOW SLAVE STATUS` 变成 `SHOW REPLICA STATUS`，`CHANGE MASTER TO` 变成 `CHANGE REPLICATION SOURCE TO`，状态里的 `Slave_IO_Running` 也改名 `Replica_IO_Running`。旧语法目前还能用，但已被标记废弃，新版官方文档、监控脚本和工具输出一律用 replica，写新脚本时直接用新名字。

【冷知识】半同步“等一个从库确认”的等待是有上限的：`rpl_semi_sync_master_timeout` 默认 10000 毫秒（10 秒），等不到确认就自动降级为异步复制，之后有从库恢复会再悄悄切回半同步。生产上常把这个值调小（比如 1000 毫秒），宁可早降级也别让每次提交都卡满 10 秒；调多小合适看从库的网络往返，设得比正常往返还小等于变相关闭了半同步。

【冷知识】GTID 长相就是“服务器 UUID + 事务序号区间”，比如 `3E11FA47-71CA-11E1-9E33-C80AA9429562:1-100`。看从库 `Executed_Gtid_Set` 的区间缺口，就能直接读出它缺了哪几段事务；主从切换时“选数据最新的从库”，本质就是比谁的 `Executed_Gtid_Set` 区间最全，不用再对 binlog 文件名和偏移量。

【冷知识】`RESET MASTER` 是复制运维里最危险的一条命令：它会清空主库全部 binlog 并重置 GTID 执行集，在主库上误敲一次，等于把复制的“账本”撕了，所有从库的位点立刻作废，只能重建。相对安全的是从库侧的 `RESET REPLICA ALL`，它只清掉从库自己的复制配置；两条命令名字像、后果天差地别，敲之前先确认自己连的是哪台。

【冷知识】主从复制是 MySQL 3.23 时代（2000 年前后）就有的老功能，比 InnoDB 成为默认存储引擎（5.5 版本）还早一代。它最初只是为备份和读扩展设计的，“主库挂了自动切换”这类高可用用法是后来 MHA、Orchestrator、MGR 这些工具一层层长出来的；理解这段历史，就明白为什么复制的默认行为偏保守——它生来就不是为强一致准备的。

## 11. 面试与自测

- 复制链路里 IO 线程和 SQL 线程各管什么？延迟主要卡在哪一段？
- 半同步复制「半」在哪？从库全挂时它会怎样？
- 读己之写的四种策略各自的代价是什么？你会默认选哪种？
- 旧主恢复后为什么不能直接切回去当主？未同步事务怎么处理？

- 主库到从库 RTT 是 10ms，业务单连接串行提交，半同步复制下每秒最多能提交多少次？从库单线程回放 800 txn/s、主库每秒产生 1200 个事务，积压 36 万事务时开 4 个并行 worker（效率 0.7）多久能追上？`Seconds_Behind_Master` 显示 0 时能不能断定从库没有延迟？

### 参考答案

1. 从库 IO 线程负责接收主库 dump 线程发来的 binlog，写入本地 relay log（中继日志），记录已接收位点；从库 SQL 线程（回放线程）读 relay log 在从库重放，记录已执行位点。延迟主要卡在回放段：网络通常不是瓶颈，回放跟不上主库写入才是常态，成因按频率是大事务、回放并行度不足、无主键或无索引表更新、从库自身负载、DDL 与锁。
2. 半同步的半在于：主库至少等一个从库确认收到 relay log 才返回，而不是等全部从库、也不是等从库回放执行完。代价是每次提交多一个网络往返；从库全挂时，等待超时后退化为异步复制，性能保住但已确认事务不丢的保证就没了。
3. 四种策略按严格程度排：关键链路读主（下单后跳转页、支付结果页这类写完马上看的路径直接读主，简单可靠，代价是这部分读压力回主库，默认首选）；会话级粘性（用户写后 N 秒内读全走主库，平衡一致性与分流）；位点等待（写时拿到事务 GTID，读从库前等回放位点追上它，一致性最强，但延迟大时读被拖住，要配超时降级回主库）；延迟阈值路由（从库延迟超阈值自动摘除或回退主库，防故障级延迟，不解决秒级读己之写）。原则是别追求全站强一致，强一致只给少数关键路径逐条列清单。
4. 因为旧主可能有未同步的事务：它宕机前已提交但没传到从库的事务，在新主上并不存在，直接切回去当主会造成数据分叉。正确做法是旧主恢复后只能降为从库，按 GTID 比对差异行、逐表对账（校验和加按主键补差，思路同 pt-table-checksum/sync），金额类走业务对账单兜底；冲突数据哪份对是业务问题不是技术问题。脑裂防护靠 fencing：切换前先确保旧主不可写（封端口、置只读），宁可切换慢，不可双主并存。

5. RTT 10ms 时串行提交上限 100 TPS；4 worker 回放 2240 txn/s，净追赶 1040 txn/s，36 万积压 346 秒追平。读数 0 不等于无延迟，需看 GTID 差或心跳表。
