# MySQL 索引与执行计划

> 《MySQL-数据库》里已有最左前缀、失效场景和 EXPLAIN 速查；本篇讲结构原理和执行计划的完整读法，两篇配合看。

## 1. 核心概念

索引的本质是**用额外的存储和写入代价，换查询时少扫行**。InnoDB 用 B+ 树组织索引：查询慢不慢，先看这条 SQL 在树上走了多远、回表了几次。

## 2. B+ 树为什么适合做索引

- **只有叶子节点存数据**，非叶子节点只存键和指针：一页（默认 16KB）能放更多键，树更矮。千万级数据通常 3～4 层，一次点查只需 3～4 次页访问。
- **叶子节点按顺序链表相连**：范围查询、排序沿链表走即可，不用回树上反复跳。
- 对比：B 树每个节点都存数据，扇出小、树更高；哈希索引只支持等值、不支持范围和排序；跳表是 Redis ZSet 的选择，磁盘场景页利用率不如 B+ 树。

### 聚簇索引与二级索引

- InnoDB 的表数据本身就是按主键排的 B+ 树（聚簇索引），叶子存整行。
- 二级索引（普通/唯一/联合）的叶子只存索引列 + 主键值，所以查非索引列要拿主键再查一次聚簇索引，这就是**回表**。
- 推论：主键用自增/有序 ID 时插入是顺序追加；用 UUID 做主键会随机插页、频繁页分裂，写入和缓存都吃亏。

## 3. 联合索引与最左前缀（深化）

联合索引 `(a, b, c)` 的排序是先 a、再 b、再 c，所以：

```sql
-- 索引 idx_abc (a, b, c)
WHERE a = 1 AND b = 2 AND c > 3   -- a、b 等值定位，c 做范围
WHERE a = 1 AND c = 3             -- 只用到 a；c 在 b 不确定时无序
WHERE a > 1 AND b = 2             -- a 是范围，b 用不上（范围列后面的列失效）
ORDER BY a, b                     -- 顺序与索引一致，免排序
```

设计口诀：**等值列在前、范围列在后；区分度高的列优先考虑，但要服务最常用的查询组合**。别给每个查询都建一个索引——索引越多写入越慢，联合索引能覆盖的单个查询就不要再建单列索引（`(a,b)` 已能服务只查 a 的场景）。

### 覆盖索引与索引下推

- **覆盖索引**：查询列全在索引里，不回表。`EXPLAIN` 的 Extra 出现 `Using index`。
- **索引下推（ICP，5.6+）**：二级索引里能先判断的条件（如联合索引后列的部分条件），在存储引擎层先过滤，减少回表次数，Extra 出现 `Using index condition`。

```sql
-- 例：idx_name_age (name, age)，name 前缀匹配 + age 过滤可下推
SELECT * FROM t_user WHERE name LIKE '张%' AND age = 20;
```

## 4. EXPLAIN 完整读法

```sql
EXPLAIN SELECT * FROM t_order WHERE user_id = 1001 AND status = 0;
-- 8.0 可用 EXPLAIN FORMAT=TREE 看树形计划；EXPLAIN ANALYZE 直接给实际耗时（谨慎在生产大查询上用）
```

| 字段 | 怎么看 |
|---|---|
| type | `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`；`index` 是全索引扫描，也不好 |
| key / key_len | 实际选用的索引；key_len 可反推联合索引用到了几列 |
| ref | 索引列与什么比较（常量、列、函数） |
| rows | 预估扫描行数，只是估算，和实际差很大时先 `ANALYZE TABLE` 更新统计信息 |
| filtered | 存储引擎返回后还要过滤掉的比例，越接近 100 越好 |
| Extra | `Using index` 覆盖索引（好）；`Using index condition` 下推；`Using where` 回表后过滤；`Using filesort` 额外排序；`Using temporary` 临时表（group by/distinct 常见） |

排查顺序：先看 type 是不是 `ALL` → 再看 key 是否选错 → 再看 rows 估算是否离谱 → 最后看 Extra 的 filesort/temporary 能否用调整索引顺序消掉。

### 优化器可能选错索引

统计信息过期、数据分布倾斜时优化器会选错。先 `ANALYZE TABLE t;` 刷新统计；仍不对再考虑 `FORCE INDEX(idx_x)` 临时兜底，并记录下来——强制索引是补丁不是常态，数据分布变了它会变成新的坑。

## 5. 慢 SQL 定位流程

```sql
-- 1. 打开慢日志（会话级先验证，再落全局配置）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;          -- 阈值 1 秒起步，按业务收紧
SHOW VARIABLES LIKE 'slow_query_log_file';

-- 2. 聚合慢日志找 Top SQL（mysqldumpslow 按总耗时排序）
-- mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log

-- 3. 对单条 SQL 看计划和实际开销
EXPLAIN FORMAT=TREE SELECT ...;
SHOW WARNINGS;                            -- 看优化器改写后的 SQL
```

定位闭环：慢日志聚合出 Top 指纹 → EXPLAIN 看计划 → 缺索引就补、选错就刷统计 → 改完用同一条 SQL 复测 rows 和耗时 → 上线后观察慢日志里该指纹是否消失。没有复测的优化不算完成。

深分页和 `SELECT *` 等写法问题《MySQL-数据库》的慢查询排查一节已有，不重复；本篇只补一句：`rows` 估算正常但就是慢，优先怀疑回表太多（把查询列收进联合索引做覆盖）和排序临时表落盘。

## 6. 常见坑

- **索引列上做运算/函数**：`WHERE YEAR(create_time) = 2026` 全表扫；改写成范围 `create_time >= '2026-01-01' AND create_time < '2027-01-01'`，或建函数索引（8.0 支持）。
- **联合索引顺序凭感觉**：把范围列放第一位，后面等值列全废。按「等值在前、范围在后」排。
- **低区分度列单独建索引**：如 status 只有 0/1，单独建了优化器也多半不走；它适合做联合索引的后列。
- **索引建了但统计没更新**：大批量导入/删除后 `ANALYZE TABLE` 一次，再看执行计划。
- **长字符串前缀索引**：`KEY idx (name(10))` 能省空间但无法覆盖索引、不能用于排序，权衡后再用。

## 7. B+ 树高度与回表次数定量

> 本节所有数字均为手算，Python 3 本地复算（见节末“复算口径”）；凡标【官方】的是 MySQL 8.0 官方手册事实，凡标【估算】的是按简化假设手算或经验估计，不是官方数字。不要把估算值当成实测值。

### 7.1 扇出：一个非叶子页能放多少个键

前提：【官方】InnoDB 索引页默认 16KB（`innodb_page_size` 默认 16384，实例初始化时定，之后不可改）；【官方】除空间索引外 InnoDB 索引都是 B-tree 结构，索引记录存在叶子页，非叶子页只存键和子页指针。

扇出公式（手算）：`扇出 ≈ 16384 ÷ (键字节数 + 指针字节数)`，向下取整。

| 主键类型 | 每项字节 | 扇出（复算） |
|---|---|---|
| BIGINT | 8 + 6 = 14 | 16384 ÷ 14 = 1170.29 → **约 1170** |
| INT | 4 + 6 = 10 | 16384 ÷ 10 = 1638.4 → **约 1638** |
| VARCHAR(36)（按 latin1/单字节计，见下） | 36 + 6 = 42 | 16384 ÷ 42 = 390.10 → **约 390** |

【估算·需注意】“指针 6 字节”是**常见教材估算口径，不是官方手册给出的数字**：官方手册只说非叶子页存键和指针，未规定指针字节数；可信的 InnoDB 结构资料指出二级索引非叶子记录的子页指针是 4 字节页号，而 6 字节是 InnoDB 隐藏列 `DB_TRX_ID` / 无主键时 `DB_ROW_ID` 的长度，两者常被混用。本节沿用 6 字节口径是为了与常见估算对齐、便于复核；若按 4 字节页号算，BIGINT 扇出会更大（16384 ÷ 12 ≈ 1365），树只会更矮，下面的树高结论不变。另：VARCHAR(36) 按 36 字节是单字节字符集下的简化，utf8mb4 下最坏 36 × 4 = 144 字节，扇出会更小（见 7.5 边界条件）。

结论：主键越窄扇出越大；这就是第 2 节“主键越宽，所有二级索引都会跟着变胖”的定量版——宽主键先压低聚簇索引扇出，再被复制进每个二级索引。

### 7.2 树高换算：多少行才需要再长一层

容量公式（手算）：`h 层树最多容纳行数 ≈ 扇出^(h-1) × 每叶子页行数`；粗略估算时常用 `扇出^h` 看量级（把叶子页也按一层扇出计，误差在可接受范围，只用于定量级）。

以 BIGINT 主键、扇出 1170 计：

- 1170² = 1,368,900 ≈ **137 万**；1170³ = 1,601,613,000 ≈ **16 亿**。
- **1000 万行 → 3 层**（2 层只够 137 万行，3 层够 16 亿行）。
- **1 亿行 → 仍 3 层**（1 亿 < 16 亿）。
- **约 16 亿行才到 4 层**。
- 点查页访问次数 = 树高：**3 层树点查约 3 次页访问，4 层约 4 次**（每次沿树下一层读一页；命中缓冲池时是逻辑读，不一定是磁盘读）。与第 2 节“千万级数据通常 3～4 层，一次点查只需 3～4 次页访问”一致，本节给出的是算出来的 3 层。

二级索引扇出一例：索引列 VARCHAR(20)（单字节计 20 字节）+ BIGINT 主键 8 字节 + 指针 6 字节 = 34 字节/项，扇出 16384 ÷ 34 = 481.88 → **约 481**；481² = 231,361，481³ = 111,284,641 ≈ 1.1 亿，所以 **1000 万行二级索引也是 3 层**。

### 7.3 叶子页容量与范围扫描

假设行约 100 字节（【估算】含行头与隐藏列的约数，不同表差异很大，只用于量级估算）：

- 每叶子页行数：16384 ÷ 100 = 163.84 → **约 163 行/页**（取整说法“约 160 行/页”亦可，但复算精确值是 163）。
- 1000 万行叶子页数：10,000,000 ÷ 163 ≈ **61,350 页**（按约 160 行/页取整则是 62,500 页，两者都是同一量级，精确复算值以 61,350 为准）。
- 范围扫 1 万行：10,000 ÷ 163 ≈ **61 页顺序读**（按 160 行/页取整约 63 页）。叶子页按链表相连（第 2 节），范围扫是沿链表顺序走页，不用回树上反复跳——这是范围扫便宜的定量原因。

### 7.4 回表次数换算

- 二级索引命中 **1000 行、无覆盖索引时，最多 1000 次回表**：每行拿主键再查一次聚簇索引，最坏每行落在不同叶子页，就是 1000 次随机页读（每次还要走聚簇索引的 3 层定位，但回表次数通常按“回表行数”计，不按页访问数计）。
- **覆盖索引时回表 0 次**：查询列全在二级索引里，`EXPLAIN` 的 Extra 出现 `Using index`（第 3 节）。
- 所以“回表多少次”先看命中行数，再看是否覆盖：命中行数 × 是否覆盖，决定了回表成本的数量级。`rows` 估算正常但查询慢时优先怀疑回表太多（第 5 节），本节给出的是换算方法。

### 7.5 用 key_len 反推用到了几列

【官方/可信】utf8mb4 每个字符最多 4 字节；`VARCHAR(n)` 的 key_len 按最大长度计，另加 2 字节长度前缀，可空列再加 1 字节 NULL 标记。

- `VARCHAR(20)` utf8mb4、NOT NULL：20 × 4 + 2 = **82 字节**。
- `EXPLAIN` 显示 `key_len = 82`，说明**只用了该列**（若联合索引还用上第二列，key_len 会更大；若该列可空则应为 83）。反推时先确认列是否可空、字符集是不是 utf8mb4，再对数，否则会错一位。

### 7.6 边界条件（至少 3 条，结论不变才敢用）

1. **扇出按满页算，实际页没那么满**：【官方】InnoDB 插入时尽量每页留 1/16 空闲，顺序插入的页约 15/16 满（约 94%），随机插入的页填充率在 1/2～15/16 之间。【估算】本节取页利用率约 70% 打折验算：1170 × 0.7 = 819，819² = 670,761，819³ = 549,353,259 ≈ 5.5 亿——1000 万行、1 亿行仍是 3 层，只是 4 层的门槛从约 16 亿行降到约 5.5 亿行。**树高结论不变**。
2. **大字段行溢出会让叶子页存更少行**：行含 TEXT/BLOB 或超长 VARCHAR 时，行数据部分存到溢出页，叶子页每页行数远低于 163 行/页，7.3 的叶子页数与范围扫页数都要按实际行长重算；但非叶子页的扇出不受行长影响，树高结论不受影响。
3. **回表次数是上限，不是实测值**：多行可能落在同一叶子页（一次页读带回多行），命中行也可能已在缓冲池里（逻辑读不产生磁盘读）。1000 行命中 → 最多 1000 次回表，实际往往更少；拿它做上限估算，不要当成实测 IO 数。
4. **VARCHAR 主键按字符集重算**：7.1 的 VARCHAR(36) 按单字节计；utf8mb4 下最坏 144 + 6 = 150 字节/项，扇出只有约 109，109³ ≈ 130 万——1000 万行就要 4 层。宽字符串主键的代价比单字节估算更大，优先用自增/有序 ID 做主键（第 2 节）。

### 复算口径

```python
# Python 3 本地复算（2026-11-08）
16384 // 14   # 1170  BIGINT 扇出
16384 // 10   # 1638  INT 扇出
16384 // 42   # 390   VARCHAR(36) 扇出
16384 // 34   # 481   二级索引扇出
1170 ** 2      # 1368900   ≈ 137 万
1170 ** 3      # 1601613000 ≈ 16 亿
481 ** 2       # 231361
481 ** 3       # 111284641 ≈ 1.1 亿
16384 // 100   # 163  每叶子页行数（行约 100 字节）
10_000_000 // 163  # 61349  ≈ 61,350 叶子页
10000 // 163   # 61    范围扫 1 万行约 61 页
20 * 4 + 2     # 82    VARCHAR(20) utf8mb4 key_len（NOT NULL）
819 ** 3       # 549353259  70% 利用率下 3 层容量
```

来源（2026-11-08 核验）：MySQL 官方手册《The Physical Structure of an InnoDB Index》——InnoDB 索引为 B-tree 结构、索引页默认 16KB、插入时每页留 1/16 空闲、顺序插入页约 15/16 满：https://dev.mysql.com/doc/refman/9.7/en/innodb-physical-structure.html ；MySQL 8.0 手册行大小限制（默认 16KB 页）：https://dev.mysql.com/doc/refman/8.0/en/column-count-limit.html?ref=cloudnatively.com ；二级索引记录格式（非叶子记录存 4 字节子页号、无主键列，叶子记录存索引列 + 主键；聚簇记录含 6 字节 TRX_ID、7 字节回滚指针）：https://deepwiki.com/jeremycole/innodb_diagrams/3.3.4-secondary-index-record-formats ；key_len 计算规则（utf8mb4 每字符 4 字节，VARCHAR(20) NOT NULL 为 20×4+2=82，可空 +1 为 83）：https://copyprogramming.com/howto/understanding-mysql-key-len-in-explain-statement （非官方，仅作计算规则佐证）。

## 原理剖析

本节只把原文已有章节给出的结论拆开讲清机制：不引入新概念，不补新数字，数字一律复用 §7 已核验的定量算例；凡原文没展开的点，文中明确标注，不作定论。

### B+ 树矮的机制：扇出决定树高

原文 §2 的结论是“只有叶子节点存数据，非叶子节点只存键和指针，一页能放更多键，树更矮”。机制是：非叶子页不存整行，只存键和子页指针，所以一页能放的键数（扇出）很大。§7.1 给出的算例是：页默认 16KB，主键 BIGINT 每项 8 + 6 = 14 字节，扇出约 1170；主键 INT 每项 4 + 6 = 10 字节，扇出约 1638；主键 VARCHAR(36) 按单字节计每项 36 + 6 = 42 字节，扇出约 390。扇出越大，同样行数需要的层数越少。§7.2 的换算是：1170² ≈ 137 万，1170³ ≈ 16 亿，所以 1000 万行是 3 层，1 亿行仍是 3 层，约 16 亿行才到 4 层；点查页访问次数等于树高，3 层树点查约 3 次页访问。§7.6 第 1 条还打了折验算：页利用率按约 70% 计，扇出 1170 × 0.7 = 819，819³ ≈ 5.5 亿，1000 万行、1 亿行仍是 3 层，树高结论不变。需要注意的是，§7.1 已明确标注“指针 6 字节”是常见教材估算口径，不是官方手册给出的数字；若按 4 字节页号算，BIGINT 扇出约 1365，树只会更矮，树高结论不变。原文未展开：具体某张表的实际扇出与树高，原文未展开，不作定论。

### 叶子链表与范围扫描的机制

原文 §2 的结论是“叶子节点按顺序链表相连，范围查询、排序沿链表走即可”。机制是：范围扫描定位到起点后，沿叶子链表顺序走页，不用回到树上反复跳。§7.3 给出的算例是：行约 100 字节时，每叶子页约 163 行，1000 万行约 61,350 页，范围扫 1 万行约 61 页顺序读。§7.6 第 2 条补充了边界：行含 TEXT/BLOB 或超长 VARCHAR 时，行数据部分存到溢出页，叶子页每页行数远低于 163 行，§7.3 的叶子页数与范围扫页数要按实际行长重算，但非叶子页的扇出不受行长影响，树高结论不受影响。原文未展开：具体某次范围扫描实际走了多少页，原文未展开，不作定论。

### 最左前缀与覆盖索引的机制

原文 §3 的结论是联合索引 `(a, b, c)` 的排序是先 a、再 b、再 c。机制是：索引内的数据按这个顺序排好，查询只能沿着已确定的前缀往下定位。§3 给出的写法是：`WHERE a = 1 AND b = 2 AND c > 3` 时 a、b 等值定位，c 做范围；`WHERE a = 1 AND c = 3` 时只用到 a，c 在 b 不确定时无序；`WHERE a > 1 AND b = 2` 时 a 是范围，b 用不上。覆盖索引的机制在 §3 与 §7.4 是一致的：查询列全在索引里就不回表，`EXPLAIN` 的 Extra 出现 `Using index`；索引下推（ICP）是二级索引里能先判断的条件在存储引擎层先过滤，减少回表次数，Extra 出现 `Using index condition`。§3 给出的写法是：`SELECT * FROM t_user WHERE name LIKE '张%' AND age = 20;`，在索引 `idx_name_age (name, age)` 上 name 前缀匹配加 age 过滤可下推。原文未展开：优化器在什么情况下会放弃本可用的最左前缀列而改走全表扫描，原文未展开，不作定论。

### EXPLAIN 读法与回表的机制

原文 §4 的排查顺序是：先看 type 是不是 `ALL`，再看 key 是否选错，再看 rows 估算是否离谱，最后看 Extra 的 filesort/temporary 能否用调整索引顺序消掉；type 的好坏顺序是 `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。key_len 的机制在 §7.5：`VARCHAR(20)` utf8mb4、NOT NULL 时 key_len 为 20 × 4 + 2 = 82 字节，`EXPLAIN` 显示 `key_len = 82` 说明只用了该列，若联合索引还用上第二列，key_len 会更大；反推时先确认列是否可空、字符集是不是 utf8mb4，否则会错一位。rows 只是预估扫描行数，和实际差很大时先 `ANALYZE TABLE` 更新统计信息（§4）。回表的机制在 §2 与 §7.4：二级索引的叶子只存索引列加主键值，查非索引列要拿主键再查一次聚簇索引；二级索引命中 1000 行、无覆盖索引时，最多 1000 次回表，覆盖索引时回表 0 次。宽主键的代价在 §7.1 的结论里：主键越窄扇出越大，宽主键先压低聚簇索引扇出，再被复制进每个二级索引。§7.6 第 3 条提醒：回表次数是上限，不是实测值，多行可能落在同一叶子页，命中行也可能已在缓冲池里，实际往往更少。原文未展开：具体某条 SQL 的实际回表次数与实际耗时，原文未展开，不作定论。

## 实战案例

### 案例一

**现象：** `rows` 估算正常但查询就是慢。原文 §5 只给了这一句判断：优先怀疑回表太多（把查询列收进联合索引做覆盖）和排序临时表落盘。

**排查：** 按原文 §4 的排查顺序看计划：先看 type 是不是 `ALL`，再看 key 是否选错，再看 rows 估算是否离谱，最后看 Extra。复用原文 §4 的写法：

```sql
EXPLAIN SELECT * FROM t_order WHERE user_id = 1001 AND status = 0;
```

若 Extra 是 `Using where` 而不是 `Using index`，说明查询列不在索引里，需要回表后过滤；若是 `Using index`，则已是覆盖索引，回表 0 次（§3、§7.4）。换算只用 §7.4 已核验的数字：二级索引命中 1000 行、无覆盖索引时，最多 1000 次回表；覆盖索引时回表 0 次。所以先看命中行数，再看是否覆盖，决定了回表成本的数量级（§7.4）。

**结论：** 按原文 §5 的做法，把查询列收进联合索引做覆盖；改完用同一条 SQL 复测 rows 和耗时，上线后观察慢日志里该指纹是否消失，没有复测的优化不算完成。原文未展开：本案例所指查询的实际命中行数、Extra 实际值与复测耗时，原文未展开，不作定论。

### 案例二

**现象：** 联合索引建了，但 `EXPLAIN` 的 key_len 只显示 82，疑似只用了一列。原文 §7.5 只给了 key_len 的换算规则，没有给出现象案例。

**排查：** 复用原文 §7.5 已核验的算例：`VARCHAR(20)` utf8mb4、NOT NULL 时 key_len 为 20 × 4 + 2 = 82 字节；`EXPLAIN` 显示 `key_len = 82`，说明只用了该列，若联合索引还用上第二列，key_len 会更大；若该列可空则应为 83。反推前先确认列是否可空、字符集是不是 utf8mb4，再对数，否则会错一位。再对照原文 §3 的最左前缀规则判断：复用原文 §3 的写法，`WHERE a = 1 AND c = 3` 只用到 a，`WHERE a > 1 AND b = 2` 时 a 是范围、b 用不上；跳列或范围列截断都会让后面的列用不上。

**结论：** key_len 只对上了一列，说明联合索引后面的列没有被用上；按原文 §3 的口诀“等值列在前、范围列在后”检查列顺序与 WHERE 写法，而不是再补一个单列索引。原文未展开：本案例所指联合索引的实际列组成、WHERE 实际写法与 key_len 实际值，原文未展开，不作定论。

## 小技巧与冷知识

【小技巧】查联合索引的列顺序别凭记忆，直接问 `INFORMATION_SCHEMA.STATISTICS`：`SELECT INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME FROM INFORMATION_SCHEMA.STATISTICS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 't_order' ORDER BY INDEX_NAME, SEQ_IN_INDEX;`。它能直接看到每个索引由哪些列组成、顺序是怎样的。排错时先对一下顺序，再判断最左前缀到底用到了哪几列，比凭印象猜要准，也能发现把 `(a, b)` 记成 `(b, a)` 这类低级错误。

【小技巧】想删一个疑似无用的索引又不敢直接删，可以先把它设为不可见：MySQL 8.0 支持 `ALTER TABLE t_order ALTER INDEX idx_x SET INVISIBLE;`，设为不可见后优化器会忽略它，效果上等同于删掉，但随时能用 `SET VISIBLE` 恢复。观察一段时间，确认慢日志里没有因为缺它而变慢的查询，再真正执行 `DROP INDEX`，这样试错成本比直接删低得多。

【冷知识】主键越宽，所有二级索引都会跟着变胖：InnoDB 二级索引的叶子节点存的是索引列加主键值，主键并不是只影响聚簇索引本身。原文只提了 UUID 主键会导致随机插页，但宽主键还有另一层代价，就是每个二级索引里都要重复存一份很长的主键值，索引变大、写入放大、缓存占用都会跟着涨。很多人只算主键列本身的长度，忽略了它会被复制到每一个二级索引里。

【冷知识】一条查询不一定只用一个索引：优化器在合适的时候会对同一张表做索引合并，EXPLAIN 的 type 会显示 `index_merge`，Extra 里会出现 `Using union` 或 `Using intersect`。这说明 MySQL 会分别用两个索引各查出一批主键，再合并或取交集后回表，而不是像多数人以为的那样一次查询只能选一个索引。看到 `index_merge` 不用慌，它本身不是坏信号，真正要看的是合并后回表的行数是否仍然很大。

## 面试与自测

1. 联合索引 `(a, b, c)` 下，`WHERE a = 1 AND c = 3` 能用到几列？为什么？
2. EXPLAIN 的 Extra 出现 `Using index`、`Using index condition`、`Using filesort` 各代表什么？
3. `rows` 估算正常但查询就是慢，按本篇应优先怀疑什么？怎么处理？

4. 主键 BIGINT 的表有 1000 万行，点查要读几页？为什么 1 亿行还是 3 层？二级索引命中 1000 行、无覆盖索引时最多回表几次？

### 参考答案

1. 只用到 a。联合索引的排序是先 a、再 b、再 c，c 在 b 不确定时无序，所以跳过 b 直接用 c 是用不上的；同理 a 是范围时，后面的 b 也用不上——口诀是等值列在前、范围列在后。
2. `Using index` 是覆盖索引，查询列全在索引里，不回表，是好事；`Using index condition` 是索引下推（ICP），二级索引里能先判断的条件在存储引擎层先过滤，减少回表次数；`Using filesort` 是额外排序，需要看能否用调整索引顺序消掉。
3. 优先怀疑回表太多：把查询列收进联合索引做覆盖；以及排序临时表落盘。排查顺序仍是先看 type 是不是 `ALL`、key 是否选错、rows 估算是否离谱，最后看 Extra 的 filesort/temporary。

4. 点查约 3 次页访问：页 16KB，主键 BIGINT 8 字节 + 指针 6 字节 = 14 字节/项，扇出约 1170；1170² ≈ 137 万 < 1000 万 < 1170³ ≈ 16 亿，所以 1000 万行是 3 层树，点查每层读一页共 3 次。1 亿行仍小于 16 亿，所以还是 3 层，约 16 亿行才到 4 层。二级索引命中 1000 行、无覆盖索引时最多回表 1000 次（每行拿主键再查一次聚簇索引，最坏每行落在不同页）；覆盖索引时 0 回表。注意 6 字节指针是常见估算口径、页利用率按 70% 打折后树高结论不变，回表次数是上限（多行可能同页、命中缓冲池也不产生磁盘读）。
