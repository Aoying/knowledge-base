# 慢查询诊断

本篇讲“从发现一条慢 SQL 到它上线不慢”的完整闭环。单点内容不重复：Druid 监控页上怎么定位慢 SQL 见 [Druid](开发语言/Java/Druid.md)第 3 节，慢查询速记见 [MySQL-数据库](数据库/MySQL/MySQL-数据库.md)，EXPLAIN 读法见 [MySQL-索引与执行计划](数据库/MySQL/MySQL-索引与执行计划.md)第 4 节，锁等待排查见 [锁等待与死锁分析](数据库/MySQL/锁等待与死锁分析.md)。

## 1. 发现：慢日志与 Top SQL

**慢日志开启。** 示例（以官方文档为准，不同版本变量名与默认值可能有差异）：

```sql
-- 示例：开启动态变量（重启后失效，持久化要写配置文件）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
-- log_queries_not_using_indexes 为 ON 时，连没走索引但跑得快的查询也记，量大，排查期开、平时关
```

- `long_query_time` 设多少：1 秒是常见起点；设太小（如 0.01 秒）日志会爆炸，排查价值被噪声淹没；设太大则漏掉“单条不慢、量大拖垮系统”的 SQL——这类 SQL 靠 Top SQL 的总耗时排序抓，不靠阈值。
- **Top SQL 定位思路**：对慢日志做聚合排序，看三个维度——总耗时（谁拖垮系统）、平均耗时（谁单条最慢）、执行次数（谁被调用最频繁）。单条慢和总量大是两类问题：前者调 SQL 本身，后者看调用方是不是在循环里查库。
- **应用侧印证**：Druid 监控页的 SQL 统计（执行次数、慢 SQL 列表）与慢日志双向印证——监控页看到的高频慢 SQL，到慢日志里找它的完整 SQL 文本和时间分布，两边对上号再动手。

## 2. 诊断闭环：发现→定位→验证→上线

- **发现**：慢日志或监控页报出 Top SQL，记下完整 SQL 文本、出现时段、并发量。
- **定位**：按根因清单（第 4 节）逐项排除。先 EXPLAIN 看计划（索引失效还是全表），再看锁等待（是不是被别的事务挡住），再看统计信息（rows 估算是否失真）。定位结论要写成一句话：“这条 SQL 慢是因为 X”，写不出来说明还没定位到。
- **验证**：测试环境用同量级数据复核 EXPLAIN；改动是索引时，先在测试环境建索引看计划变化；改动是 SQL 改写时，对照改写前后的 EXPLAIN（type、rows、Extra 三处）。不要在生产直接试。
- **上线**：索引上线走低峰窗口（大表建索引要评估锁表与耗时，以官方文档为准）；SQL 改写走正常发布流程；上线后盯慢日志里该 SQL 的耗时变化，确认回落再结案。回滚预案：索引可删，SQL 改写可回滚到上一版——预案先想好再上线。

## 3. 与监控的衔接

慢查询诊断不是一次性排查，要接进日常监控：

- **Druid 监控页**：SQL 墙看执行次数与慢 SQL 列表，连接池看等待线程——连接池排队 + 慢 SQL 同时出现时，先看慢 SQL（池排队常是慢 SQL 占着连接不放的结果，不是原因）。
- **应用链路**：一次请求的 traceId 把应用日志、Druid 监控、慢日志串起来（traceId 约定见接口设计相关篇）。客诉“某个操作慢”时，先拿 traceId 找到那次请求的 SQL，再进闭环，不要凭感觉猜。
- **告警阈值**：慢 SQL 数量突增、平均耗时爬升、锁等待次数上升，三类信号分开告警；混成一个“数据库慢”告警，定位时还得重拆一遍。

## 4. 常见慢查询根因清单

| 根因 | 特征 | 排查与解法方向 |
|---|---|---|
| 索引缺失 | EXPLAIN type=ALL | 补索引；先看 WHERE/join 列，见 SQL调优实战第 2、3 节 |
| 索引失效 | 索引建了但没走 | 按失效清单逐项对（函数、隐式转换、OR、LIKE 前导 %） |
| 统计信息过期 | rows 估算与实际差很远 | ANALYZE TABLE 方向；统计信息更新后复核 EXPLAIN |
| 锁等待 | SQL 本身计划正常，但执行时被挡 | 按锁等待排查流程找挡的人，见锁等待篇 |
| 回表 + 大分页 | 计划正常，数据量大时变慢 | 覆盖索引、游标分页、延迟关联，见 SQL调优实战第 4 节 |
| 配置方向 | 缓冲池、join_buffer、临时表相关 | 只讲方向不给具体数值：缓冲池决定热数据命中率，join_buffer 影响 BNL 代价，临时表参数影响排序落盘；数值按实例规格与官方文档定 |
| 大事务 / 大批量写入 | 写操作拖慢读 | 拆小批量、缩短事务，见锁等待篇第 5 节 |
| 调用方问题 | 单条不慢，总量大 | 查调用方是不是循环查库、N+1；修调用方式比调 SQL 见效快 |

## 5. 常见误区

- 慢就等于缺索引：先 EXPLAIN，再看锁等待和统计信息；缺索引只是根因之一。
- long_query_time 越小越好：阈值太小日志爆炸，真正的问题会被噪声淹没；总量大的 SQL 靠 Top SQL 排序抓。
- 只看单条 SQL 不看并发：单条跑 100ms，100 并发就是 10 秒的排队；慢查询诊断要同时看执行次数和并发量。
- 上线索引不验证：大表建索引本身可能锁表；低峰窗口 + 事先评估 + 回滚预案，缺一不可。

## 面试与自测

1. 慢日志的 long_query_time 设太小会有什么问题？“单条不慢、总量大”的 SQL 靠什么抓？
2. 诊断闭环四步分别做什么？为什么验证不能在生产直接试？
3. 连接池排队和慢 SQL 同时出现时，应该先看哪个？为什么？

### 参考答案

1. 阈值太小（如 0.01 秒）会让日志爆炸，真正的问题会被噪声淹没；而且单条不慢、量大拖垮系统的 SQL 本来就不会被阈值抓到——这类 SQL 靠 Top SQL 按总耗时排序抓，不靠阈值。
2. 四步：发现（慢日志或监控页报出 Top SQL，记下完整 SQL、时段、并发量）；定位（按根因清单逐项排除，结论写成一句话）；验证（测试环境同量级数据复核 EXPLAIN，索引与改写都先在测试环境看计划变化）；上线（低峰窗口、回滚预案、上线后盯慢日志确认回落）。不能在生产直接试，因为索引上线可能锁表、改写可能改错语义，生产试错成本不可接受。
3. 先看慢 SQL。因为连接池排队常是慢 SQL 占着连接不放的结果，不是原因；把慢 SQL 修掉，池排队往往跟着缓解。反过来只扩连接池，是给慢 SQL 更多并发，治标不治本。
