# 慢查询诊断

本篇讲“从发现一条慢 SQL 到它上线不慢”的完整闭环。单点内容不重复：Druid 监控页上怎么定位慢 SQL 见 [Druid](开发语言/Java/Druid.md)第 3 节，慢查询速记见 [MySQL-数据库](数据库/MySQL/MySQL-数据库.md)，EXPLAIN 读法见 [MySQL-索引与执行计划](数据库/MySQL/MySQL-索引与执行计划.md)第 4 节，锁等待排查见 [锁等待与死锁分析](数据库/MySQL/锁等待与死锁分析.md)。

## 1. 发现：慢日志与 Top SQL

**慢日志开启。** 示例（以官方文档为准，不同版本变量名与默认值可能有差异）：

```sql
-- 示例：开启动态变量（重启后失效，持久化要写配置文件）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
-- log_queries_not_using_indexes 为 ON 时，连没走索引但跑得快的查询也记，量大，排查期开、平时关
```

- `long_query_time` 设多少：1 秒是常见起点；设太小（如 0.01 秒）日志会爆炸，排查价值被噪声淹没；设太大则漏掉“单条不慢、量大拖垮系统”的 SQL——这类 SQL 靠 Top SQL 的总耗时排序抓，不靠阈值。
- **Top SQL 定位思路**：对慢日志做聚合排序，看三个维度——总耗时（谁拖垮系统）、平均耗时（谁单条最慢）、执行次数（谁被调用最频繁）。单条慢和总量大是两类问题：前者调 SQL 本身，后者看调用方是不是在循环里查库。
- **应用侧印证**：Druid 监控页的 SQL 统计（执行次数、慢 SQL 列表）与慢日志双向印证——监控页看到的高频慢 SQL，到慢日志里找它的完整 SQL 文本和时间分布，两边对上号再动手。

## 2. 诊断闭环：发现→定位→验证→上线

- **发现**：慢日志或监控页报出 Top SQL，记下完整 SQL 文本、出现时段、并发量。
- **定位**：按根因清单（第 4 节）逐项排除。先 EXPLAIN 看计划（索引失效还是全表），再看锁等待（是不是被别的事务挡住），再看统计信息（rows 估算是否失真）。定位结论要写成一句话：“这条 SQL 慢是因为 X”，写不出来说明还没定位到。
- **验证**：测试环境用同量级数据复核 EXPLAIN；改动是索引时，先在测试环境建索引看计划变化；改动是 SQL 改写时，对照改写前后的 EXPLAIN（type、rows、Extra 三处）。不要在生产直接试。
- **上线**：索引上线走低峰窗口（大表建索引要评估锁表与耗时，以官方文档为准）；SQL 改写走正常发布流程；上线后盯慢日志里该 SQL 的耗时变化，确认回落再结案。回滚预案：索引可删，SQL 改写可回滚到上一版——预案先想好再上线。

## 3. 与监控的衔接

慢查询诊断不是一次性排查，要接进日常监控：

- **Druid 监控页**：SQL 墙看执行次数与慢 SQL 列表，连接池看等待线程——连接池排队 + 慢 SQL 同时出现时，先看慢 SQL（池排队常是慢 SQL 占着连接不放的结果，不是原因）。
- **应用链路**：一次请求的 traceId 把应用日志、Druid 监控、慢日志串起来（traceId 约定见接口设计相关篇）。客诉“某个操作慢”时，先拿 traceId 找到那次请求的 SQL，再进闭环，不要凭感觉猜。
- **告警阈值**：慢 SQL 数量突增、平均耗时爬升、锁等待次数上升，三类信号分开告警；混成一个“数据库慢”告警，定位时还得重拆一遍。

## 4. 常见慢查询根因清单

| 根因 | 特征 | 排查与解法方向 |
|---|---|---|
| 索引缺失 | EXPLAIN type=ALL | 补索引；先看 WHERE/join 列，见 SQL调优实战第 2、3 节 |
| 索引失效 | 索引建了但没走 | 按失效清单逐项对（函数、隐式转换、OR、LIKE 前导 %） |
| 统计信息过期 | rows 估算与实际差很远 | ANALYZE TABLE 方向；统计信息更新后复核 EXPLAIN |
| 锁等待 | SQL 本身计划正常，但执行时被挡 | 按锁等待排查流程找挡的人，见锁等待篇 |
| 回表 + 大分页 | 计划正常，数据量大时变慢 | 覆盖索引、游标分页、延迟关联，见 SQL调优实战第 4 节 |
| 配置方向 | 缓冲池、join_buffer、临时表相关 | 只讲方向不给具体数值：缓冲池决定热数据命中率，join_buffer 影响 BNL 代价，临时表参数影响排序落盘；数值按实例规格与官方文档定 |
| 大事务 / 大批量写入 | 写操作拖慢读 | 拆小批量、缩短事务，见锁等待篇第 5 节 |
| 调用方问题 | 单条不慢，总量大 | 查调用方是不是循环查库、N+1；修调用方式比调 SQL 见效快 |

## 5. 常见误区

- 慢就等于缺索引：先 EXPLAIN，再看锁等待和统计信息；缺索引只是根因之一。
- long_query_time 越小越好：阈值太小日志爆炸，真正的问题会被噪声淹没；总量大的 SQL 靠 Top SQL 排序抓。
- 只看单条 SQL 不看并发：单条跑 100ms，100 并发就是 10 秒的排队；慢查询诊断要同时看执行次数和并发量。
- 上线索引不验证：大表建索引本身可能锁表；低峰窗口 + 事先评估 + 回滚预案，缺一不可。

## 6. 慢查询的量：扫描行数与分位耗时

本节所有数字均为手算，Python 3 本地复算；【官方】指 MySQL 8.0 官方手册事实（来源见节末），【估算】指本节明确给出的简化假设下手算的结果，不是官方数字、不是实测值，换一组假设数字会变，结论的判断方向不变。

### 6.1 rows_examined / rows_sent：扫了多少、只返回多少

【官方】慢日志每条记录含 `Rows_sent`（发给客户端的行数）与 `Rows_examined`（服务端层检查的行数，不计存储引擎内部处理），见 MySQL 8.0 手册 7.4.5 节。只看 `Query_time` 不看这两个数，分不清“查得慢”还是“扫得多、返回得少”。

比值 = rows_examined ÷ rows_sent，三组【估算】例子：

| 情形 | rows_examined | rows_sent | 比值 | 判断 |
|---|---|---|---|---|
| 健康：主键/唯一索引点查 | 12 | 10 | 12 ÷ 10 = 1.2 | 基本只扫返回的行，正常 |
| 亚健康：索引范围扫后过滤大半 | 5,000 | 50 | 5,000 ÷ 50 = 100 | 扫 100 倍才返回 1 行，值得看索引与 WHERE 条件 |
| 病态：全表扫后只取几行 | 2,000,000 | 5 | 2,000,000 ÷ 5 = 400,000 | 扫 40 万倍才返回 1 行，先按第 4 节根因清单查索引缺失/失效 |

判断阈值【估算，非官方】：比值 ≤ 10 视为健康；10 < 比值 ≤ 1,000 视为亚健康，先看能不能加/改索引收窄扫描；比值 > 1,000 视为病态，优先处理。阈值是经验分界，不是手册规定：分页查 `LIMIT 10` 本来就会让比值偏大，要结合绝对扫描行数一起看。

全表扫描成本换算【估算】：扫描页数 ≈ 总行数 × 平均行长 ÷ 页大小。取页大小 16 KiB（16,384 字节）为简化假设：

- 1,000,000 行 × 200 字节 ÷ 16,384 字节/页 = 200,000,000 ÷ 16,384 ≈ 12,207.03 页，约 12,207 页；
- 100,000 行 × 100 字节 ÷ 16,384 字节/页 = 10,000,000 ÷ 16,384 ≈ 610.35 页，约 610 页。

行数翻 10 倍、行长翻 2 倍，扫描页数翻 20 倍（12,207 ÷ 610 ≈ 20.01）。这就是“表长大后原来不慢的 SQL 突然变慢”的量级来源：成本随行数与行长线性涨，索引把扫描从“整表页数”降到“命中行附近的页数”。

### 6.2 long_query_time：阈值动一位，日志量动几个数量级

【官方】`long_query_time` 最小值 0、默认值 10 秒，可精确到微秒；慢日志记录的是执行超过该阈值且检查行数不少于 `min_examined_row_limit` 的语句。原文第 1 节只说“设太小日志会爆炸”，这里把“爆炸”换算成数。

假设【估算】：QPS = 1,000，全天总查询数 = 1,000 × 86,400 = 86,400,000 条；三档阈值下的慢查询占比取 10 秒档 0.001%、1 秒档 0.05%、0.1 秒档 2%（占比本身是假设，不同业务差几个数量级都正常，关键看阈值收紧时占比的放大倍数）：

| long_query_time | 慢查询占比（假设） | 每天日志条数 | 每秒约 |
|---|---|---|---|
| 10 秒（默认值） | 0.001% | 86,400,000 × 0.00001 = 864 条 | 0.01 条/秒 |
| 1 秒 | 0.05% | 86,400,000 × 0.0005 = 43,200 条 | 0.5 条/秒 |
| 0.1 秒 | 2% | 86,400,000 × 0.02 = 1,728,000 条 | 20 条/秒 |

倍数关系：1 秒档是 10 秒档的 43,200 ÷ 864 = 50 倍；0.1 秒档是 1 秒档的 1,728,000 ÷ 43,200 = 40 倍；0.1 秒档是 10 秒档的 1,728,000 ÷ 864 = 2,000 倍。阈值从 10 秒收到 0.1 秒（100 倍），日志量涨了 2,000 倍——因为耗时分布是长尾，越靠近中位数，落进来的查询越多。所以排查期可以临时收到 0.1 秒，平时留在 1 秒左右；收到 0.1 秒还不设轮转与聚合（`mysqldumpslow`/`pt-query-digest`），日志盘先被写满。

### 6.3 P50/P95/P99：平均耗时会把长尾藏起来

取一组 20 次耗时采样（毫秒，已排序）【估算】：8、12、15、20、22、25、30、35、40、45、50、55、60、70、80、90、120、200、500、3,000。

分位数用最近秩法：P_k 的位置 = ceil(k% × n)，n = 20：

- P50：位置 ceil(0.50 × 20) = 第 10 个 = 45 ms；
- P95：位置 ceil(0.95 × 20) = 第 19 个 = 500 ms；
- P99：位置 ceil(0.99 × 20) = 第 20 个 = 3,000 ms。

平均耗时 = (8 + 12 + … + 3,000) ÷ 20 = 4,477 ÷ 20 = 223.85 ms。平均数 223.85 ms 比 P50（45 ms）大近 5 倍，却只有 P99（3,000 ms）的约 1/13：它既不代表典型请求（典型是 45 ms），也不代表最差体验（最差是 3,000 ms）。更关键的是长尾占比：最慢 1 次占总耗时 3,000 ÷ 4,477 ≈ 67.0%，最慢 2 次合计占 (500 + 3,000) ÷ 4,477 ≈ 78.2%。一半以上的总耗时集中在 2 次调用上——只看平均数，会以为“整体慢了 5 倍”，实际是“19 次正常、1 次极慢”；修法也不同，前者要整体优化，后者要先抓那 1 次的根因（锁等待、大扫描、冷数据）。

Top SQL 要按总耗时排序，总耗时 = 单次耗时 × 执行次数【估算】：

| SQL | 单次耗时 | 执行次数/天 | 总耗时/天 |
|---|---|---|---|
| A | 0.8 秒 | 10,000 | 0.8 × 10,000 = 8,000 秒 |
| B | 5 秒 | 100 | 5 × 100 = 500 秒 |
| C | 0.05 秒 | 200,000 | 0.05 × 200,000 = 10,000 秒 |

按单次耗时排是 B > A > C，按总耗时排是 C > A > B。C 单次最快、总量最大，是最先拖垮系统的那条——这正是原文第 1 节说的“单条慢和总量大是两类问题”，也是 `sys.statement_analysis` 按总耗时排序的原因。

### 6.4 索引选择性：不同值越多，索引越值得建

选择性 = 不同值数 ÷ 总行数，越接近 1 越好（每个值对应越少的行）。两组【估算】，总行数均为 1,000,000：

- 低选择性列（如只有 2 个取值的状态列）：2 ÷ 1,000,000 = 0.000002，即 0.0002%。单建这列的索引基本筛不掉行，优化器大概率仍选全表扫，单独建不值得。
- 高选择性列（如 950,000 个不同值的用户 ID 列）：950,000 ÷ 1,000,000 = 0.95，即 95%。索引一次能定位到约 1 行，值得建。

判断阈值【估算，非官方】：选择性 > 0.1 可考虑建；选择性 < 0.01 单独建一般不值（可作联合索引的后置列）；0.01–0.1 之间看查询模式——等值点查且返回行少时仍可能有用，范围扫加回表多时要实测 EXPLAIN 再定。

### 6.5 边界条件

- `rows_sent = 0` 时比值无定义：空结果查询、UPDATE/DELETE 不返回行，不要算比值，直接看 `rows_examined` 的绝对值——扫 200 万行改 0 行，同样是全表扫。
- 小表全扫不贵：表只有 50 行时，比值再大，扫描页数也不到 1 页（50 × 200 ÷ 16,384 < 1），全表扫比走索引还快；比值阈值只对“扫描行数本身已上千”的表有意义。
- `long_query_time = 0` 时日志量 = 全部查询量：QPS 1,000 则每天 86,400,000 条，只可作短时抓包，绝不能长期开。
- 样本太少时 P99 就是最大值：n = 20 时 P99 落在第 20 个（最大值 3,000 ms），一次抖动就改写 P99；要让 P99 稳定，样本量至少上百，P99.9 则要上千。
- 选择性会被数据倾斜骗过：不同值数很高，但 90% 的行集中在同一个热点值上——对热点值的查询仍是全表扫的量，平均选择性好看不等于每个值都好查，热点值要单独看。

### 复算口径

```python
import math

# 6.1 比值与扫描页数（页大小取 16 KiB = 16384 字节，为简化假设）
for name, examined, sent in [("健康", 12, 10), ("亚健康", 5000, 50), ("病态", 2000000, 5)]:
    print(name, examined / sent)  # 1.2 / 100.0 / 400000.0
for rows, avg_len in [(1000000, 200), (100000, 100)]:
    print(rows * avg_len / 16384)  # 12207.03125 / 610.3515625

# 6.2 阈值与日志量（QPS=1000，占比为假设）
total = 1000 * 86400  # 86400000
for thr, pct in [(10, 0.00001), (1, 0.0005), (0.1, 0.02)]:
    print(thr, total * pct, total * pct / 86400)  # 864.0/0.01, 43200.0/0.5, 1728000.0/20.0
print(43200 / 864, 1728000 / 43200, 1728000 / 864)  # 50.0 / 40.0 / 2000.0

# 6.3 分位数（最近秩法）与 Top SQL 总耗时
s = [8, 12, 15, 20, 22, 25, 30, 35, 40, 45, 50, 55, 60, 70, 80, 90, 120, 200, 500, 3000]
print(sum(s), sum(s) / len(s))  # 4477 / 223.85
for p in (50, 95, 99):
    print(f"P{p}", s[math.ceil(p / 100 * len(s)) - 1])  # 45 / 500 / 3000
print(3000 / sum(s), 3500 / sum(s))  # 0.67009... / 0.78177...
for name, single, cnt in [("A", 0.8, 10000), ("B", 5, 100), ("C", 0.05, 200000)]:
    print(name, single * cnt)  # 8000.0 / 500.0 / 10000.0

# 6.4 选择性
print(2 / 1000000, 950000 / 1000000)  # 2e-06 / 0.95
```

## 小技巧与冷知识

【小技巧】慢日志别只开、还要定期做聚合：原生慢日志是一行行流水账，靠肉眼翻找不出 Top SQL，用 `mysqldumpslow -s t` 按总耗时排序、或 pt-query-digest 做指纹聚合（把常量换成问号再分组），才能看到“哪类 SQL 总耗时最高”。日志开了不聚合，等于只存了证据没做分析。

【小技巧】`log_output` 可以写表也可以写文件，各有利弊：默认写文件适合离线分析；设成 `TABLE` 后慢日志进 `mysql.slow_log`，能用 SQL 直接查“过去一小时最慢的十条”，排查时不用先导文件。但写表本身也有开销，排查期临时切表、平时切回文件，别长期开着表模式跑。

【小技巧】8.0 可以用 `log_slow_extra=ON` 让慢日志多记一行信息：它会在每条慢日志里补上执行计划概要、锁等待时间、扫描行数等字段，排障时不用再去翻 EXPLAIN 补数据。默认是 OFF，排查期打开再关，日志量会涨一些，但省掉“慢日志和 EXPLAIN 两边对不上”的反复核对。

【小技巧】只想抓“没走索引”的慢查询，用 `log_queries_not_using_indexes` 配合 `log_throttle_queries_not_using_indexes`：前者把没走索引的查询也记下来，后者限制每分钟最多记多少条，防止一波全表扫描把日志写爆。原文说过排查期开、平时关，补充一点：节流值设为 0 就是不限流，排查时别忘了它默认有限流，别以为“没记就是没发生”。

【小技巧】`min_examined_row_limit` 可以过滤掉“扫描行很少”的慢查询：设成 1000 后，扫描行不到 1000 的查询即使超过阈值也不记日志，慢日志里就只剩真正扫了大量数据的 SQL。排查“大表全扫”时打开它，噪声一下子少很多；但别长期开着，否则“小表反复查”的总量问题会被漏掉。

【小技巧】怀疑“慢的是管理语句”时，检查 `log_slow_admin_statements`：默认情况下 `ALTER TABLE`、`OPTIMIZE TABLE` 这类管理语句即使跑很久也不进慢日志，因为它默认是 OFF。一次 DDL 把库拖慢、慢日志里却找不到记录时，先看这个开关——管理语句的慢，往往比业务 SQL 的慢更致命。

【小技巧】主从延迟排查时别只看主库慢日志，从库也有自己的慢日志开关：`log_slow_slave_statements` 默认 OFF，从库回放的慢 SQL 不会记下来。从库延迟高、主库慢日志干净时，把从库的这个开关打开，才能看到回放侧到底哪条 SQL 在拖；只看主库会误以为“SQL 没问题，是复制本身慢”。

【小技巧】慢日志里的 `Query_time` 和 `Lock_time` 是两个数，别混着读：`Query_time` 是总耗时，`Lock_time` 是其中等锁的时间。`Query_time` 大、`Lock_time` 小，是 SQL 本身慢；`Lock_time` 占了大头，是被别的事务挡住了。原文第 4 节把“锁等待”列为单独根因，读日志时先拆这两个数，定位方向立刻就分出来了。

【小技巧】Performance Schema 的摘要表是慢日志之外的第二条路：`performance_schema.events_statements_summary_by_digest` 按 SQL 指纹聚合了每类语句的总耗时、平均耗时、执行次数和锁等待时间，不用开慢日志就能拿到 Top SQL。慢日志没开、或历史日志已被轮转掉时，先查这张摘要表——它一直在内存里累计，重启才清零。

【小技巧】sys 库里有现成的 Top SQL 视图，不用自己写聚合：`sys.statements_with_runtimes_in_95th_percentile` 直接给出 95 分位耗时最高的语句，`sys.statement_analysis` 按总耗时排序。排查时先跑这两个视图，十分钟就能锁定嫌疑 SQL，再进原文的诊断闭环，比从零写聚合 SQL 快得多。

【小技巧】`EXPLAIN` 看计划、`EXPLAIN ANALYZE` 看实测，两者别只用一个：EXPLAIN 只给优化器的估算行数，统计信息过期时估算和实测能差几个数量级；`EXPLAIN ANALYZE`（8.0.18+）真的执行一遍并输出每一步的实际行数和耗时。定位“rows 估算失真”这类根因时，两个结果一对照就知道是统计信息的问题还是索引的问题。

【冷知识】慢查询日志的阈值 `long_query_time` 精度到微秒：可以设 `0.5`、`0.1` 这种小数，但它统计的是语句执行时间，不含连接建立和网络传输。客户端感知的“慢”比日志里的 `Query_time` 大，是因为后者只量数据库内的执行；客诉“慢了 3 秒”、日志只记 0.5 秒时，差值往往在网络和连接池，不在 SQL 本身。

【冷知识】`SHOW STATUS LIKE 'Slow_queries'` 是累计计数器，不是当前速率：它从服务启动开始累计，数值一直在涨。想判断“现在是不是在变慢”，要隔一分钟取两次做差值，或者直接看慢日志的写入速度；只看一次绝对值，无法区分“历史累计多”和“现在正变慢”。

【冷知识】`EXPLAIN` 也能对 UPDATE 和 DELETE 用，不只是 SELECT：`EXPLAIN UPDATE t SET ... WHERE ...` 会显示这条写操作走什么索引、扫多少行。慢的 UPDATE、DELETE 常常因为 WHERE 没走索引而全表扫，排障时别只对 SELECT 做 EXPLAIN，写操作同样值得先看一眼计划再动手。

【冷知识】`SHOW PROFILE` 已废弃，定位“慢在哪一步”改用 Performance Schema：`SHOW PROFILE` 在 8.0 里是 deprecated 状态，替代品是 `events_stages_history_long`，能按阶段（解析、加锁、排序、发送结果）拆耗时。老教程里用 `SET profiling=1` 的排障脚本，在新版本上迟早跑不动，排查脚本直接写 Performance Schema 的查询更稳妥。

## 面试与自测

1. 慢日志的 long_query_time 设太小会有什么问题？“单条不慢、总量大”的 SQL 靠什么抓？
2. 诊断闭环四步分别做什么？为什么验证不能在生产直接试？
3. 连接池排队和慢 SQL 同时出现时，应该先看哪个？为什么？

4. 一条 SQL 的 `rows_examined` 是 2,000,000、`rows_sent` 是 5，比值是多少、说明什么？另有一组 20 次耗时采样，平均 223.85 ms、P50 45 ms、P99 3,000 ms，为什么只看平均耗时会漏掉长尾？

### 参考答案

1. 阈值太小（如 0.01 秒）会让日志爆炸，真正的问题会被噪声淹没；而且单条不慢、量大拖垮系统的 SQL 本来就不会被阈值抓到——这类 SQL 靠 Top SQL 按总耗时排序抓，不靠阈值。
2. 四步：发现（慢日志或监控页报出 Top SQL，记下完整 SQL、时段、并发量）；定位（按根因清单逐项排除，结论写成一句话）；验证（测试环境同量级数据复核 EXPLAIN，索引与改写都先在测试环境看计划变化）；上线（低峰窗口、回滚预案、上线后盯慢日志确认回落）。不能在生产直接试，因为索引上线可能锁表、改写可能改错语义，生产试错成本不可接受。
3. 先看慢 SQL。因为连接池排队常是慢 SQL 占着连接不放的结果，不是原因；把慢 SQL 修掉，池排队往往跟着缓解。反过来只扩连接池，是给慢 SQL 更多并发，治标不治本。
