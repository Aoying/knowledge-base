# 锁等待与死锁分析

本篇讲“锁住了之后怎么查、怎么解”。锁的基础概念（行锁、间隙锁与死锁的定义）见 [MySQL-事务与MVCC](数据库/MySQL/MySQL-事务与MVCC.md)第 5 节，死锁速记见 [MySQL-数据库](数据库/MySQL/MySQL-数据库.md)疑难杂症一节；本篇往深处写类型全表、排查流程、死锁日志读法和典型场景。

## 1. 锁类型全表

InnoDB 默认隔离级别是 REPEATABLE READ（RR），下表按这个前提讲；隔离级别改成 RC 后间隙锁行为会变，以官方文档为准。

| 锁 | 锁什么 | 关键点 |
|---|---|---|
| 行锁 S（共享） | 单行读 | S 与 S 兼容，S 与 X 互斥；`SELECT ... LOCK IN SHARE MODE` 加 S |
| 行锁 X（排他） | 单行写 | X 与任何行锁互斥；`SELECT ... FOR UPDATE`、UPDATE、DELETE 加 X |
| 间隙锁（Gap） | 索引记录之间的空隙 | 只在 RR 下阻止区间内插入，不锁已存在的行；解决幻读 |
| Next-Key 锁 | 行 + 行前间隙 | RR 下默认的行锁形态，是行锁与间隙锁的组合 |
| 意向锁 IS / IX | 表级意向 | 表示事务想在表里加 S/X 行锁；表锁检查意向锁就够了，不用逐行扫 |
| 表锁 | 整表 | 显式 LOCK TABLES、DDL 期间的元数据锁（MDL）都属此类；MDL 会阻塞 DML，见第 4 节 |

兼容关系记一条就够：S 与 S 兼容，其余行锁组合基本互斥；意向锁之间 IS/IX 互相兼容（它们只表意向，不阻塞行操作）。

## 2. 锁等待排查流程

按顺序查，不要跳步；每一步的输出决定下一步：

**第一步：看谁在等。** 示例：

```sql
-- 示例：看当前会话状态，Locked、Waiting for table metadata lock 都是锁等待信号
SHOW PROCESSLIST;
-- 或 information_schema.PROCESSLIST，字段与上面对应
```

**第二步：看运行中的事务。** 示例：

```sql
-- 示例：trx_started 看事务跑了多久，trx_rows_locked 看锁了多少行，trx_query 看它在跑什么 SQL
SELECT trx_id, trx_started, trx_rows_locked, trx_query
FROM information_schema.INNODB_TRX;
```

事务跑了很久、锁了很多行、query 是 UPDATE/DELETE 全表——这就是重点怀疑对象。

**第三步：看谁等谁。** 示例：

```sql
-- 示例：MySQL 8.0 后推荐用 performance_schema 的两张表；老版本对应 INNODB_LOCK_WAITS
SELECT * FROM performance_schema.data_lock_waits;
-- 关键字段：REQUESTING_ENGINE_TRANSACTION_ID（等的人）、BLOCKING_ENGINE_TRANSACTION_ID（挡的人）
```

等的人和挡的人都拿到后，去第二步的事务表里找它们的 SQL，阻塞链就出来了。

**第四步：看死锁现场（如果已发生死锁）。** 示例：

```sql
-- 示例：输出里 LATEST DETECTED DEADLOCK 一节就是最近一次死锁的完整现场
SHOW ENGINE INNODB STATUS;
```

注意：INNODB STATUS 只保留最近一次死锁；要长期留存，靠慢日志或监控采集，不要指望事后还能翻出来。

## 3. 死锁日志读法

LATEST DETECTED DEADLOCK 一节的结构是固定的，读三要素：

```
*** (1) TRANSACTION:
TRANSACTION 12345, ACTIVE 3 sec
...（事务 1 在跑的 SQL）
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ...（事务 1 在等哪把锁）
*** (2) TRANSACTION:
TRANSACTION 12346, ACTIVE 5 sec
...（事务 2 在跑的 SQL）
*** (2) HOLDS THE LOCK(S):
RECORD LOCKS ...（事务 2 持有事务 1 等的那把锁）
*** WE ROLL BACK TRANSACTION (2)
```

- **谁被回滚**：最后一行写明，事务 2 被回滚（通常是改动较小的那个）；被回滚的事务业务层要能重试，重试必须幂等。
- **争哪把锁**：WAITING FOR 和 HOLDS 里锁的表、索引、行范围对上号，就是争夺点。
- **哪两条 SQL**：两个 TRANSACTION 下的 SQL 就是死锁的直接参与者；再结合业务代码看它们的上游调用链，才能定位到真正的顺序问题。

## 4. 典型死锁场景与解法

- **无索引更新，全表加锁**：UPDATE 的 WHERE 列没有索引，InnoDB 会逐行加锁，锁范围远超预期，极易与别的事务撞上。解法：给 WHERE 列建索引，让锁只落在命中的行上。
- **两个事务以相反顺序访问两行**：A 先改行 1 再改行 2，B 先改行 2 再改行 1，撞上就是死锁。解法：业务层固定访问顺序（比如一律按 id 升序改），顺序一致就撞不上。
- **间隙锁插入冲突**：RR 下范围条件或唯一键检查会加间隙锁，两个事务往同一间隙插数据时会互相挡。解法：缩小范围条件；业务上避免并发往同一区间插（如用唯一键 + 业务层去重，或把热点区间拆开）。
- **长事务持有锁**：一个事务里先查后改、中间还调外部接口，锁从头拿到尾。解法：缩短事务（接口调用移出事务）、大批量更新拆成小批量分批提交。
- **外键无索引**：子表外键列没有索引时，父表操作会锁子表全表。解法：给外键列建索引。
- **DDL 被 MDL 挡住**：执行 ALTER 时发现一直等，原因是长事务持有 MDL。解法：先查长事务（第二步），而不是反复重试 DDL；DDL 走低峰窗口。

## 5. 预防清单

- 索引先行：UPDATE/DELETE 的 WHERE 列先有索引，再谈别的优化。
- 固定顺序：同一批行的访问顺序全库统一。
- 短事务：事务里只放数据库操作，不放 RPC、文件 IO、 sleep。
- 小批量：大批量更新按主键分批，每批独立提交。
- 可重试：被回滚是正常现象，业务层对死锁回滚做有限次重试，重试操作本身要幂等（见接口防重相关篇）。

## 6. 常见误区

- 死锁等于 Bug 必现：死锁是并发时序问题，单测跑不出来很正常；靠固定顺序和短事务预防，靠日志定位，不要指望复现。
- 加锁越多越安全：锁范围越大，撞上的概率越高；精确加锁（索引定位到行）比大范围加锁更安全。
- KILL 掉一个事务就根治：KILL 只是解开当前这次等待，不改访问顺序和索引缺失，下次还会撞。
- 锁等待就是死锁：锁等待是“等着”，死锁是“互相等”；前者靠排查流程找挡的人，后者靠日志找回滚的事务。

## 小技巧与冷知识

【小技巧】`data_lock_waits` 只告诉你“谁等谁”，想看“到底等的是哪把锁”要去 `performance_schema.data_locks`：这张表里有每把锁的模式（LOCK_MODE，如 X、S、X,GAP）、锁的表和索引、以及 LOCK_DATA 里的行值。等的人和挡的人都查到后，再用这两张表的事务 ID 对照，就能把“等哪行、哪种锁”拼完整，排查流程的第三步到这里才算闭环。

【小技巧】`SHOW ENGINE INNODB STATUS` 不只有死锁现场，TRANSACTIONS 一节里正在等的事务会直接标 `---TRANSACTION ... LOCK WAIT`：等哪把锁、已经等了几秒、等的是哪条 SQL 都会写在同一段里。死锁还没发生、只是“等得久”时，先看这一节比等死锁日志出现更快；锁等待的现场也是从这里看，不是只看 LATEST DETECTED DEADLOCK。

【小技巧】锁等了 50 秒报错 1205 和死锁报错 1213 是两回事，别混着重试：`innodb_lock_wait_timeout` 默认 50 秒，超时报 `ERROR 1205 (HY000): Lock wait timeout exceeded`，是“等太久放弃”；死锁报 `ERROR 1213 (40001): Deadlock found when trying to get lock`，是“互相等被检测到”。重试逻辑要按错误码区分：1213 值得有限次重试，1205 先要查挡住你的是谁，重试大概率还是超时。

【小技巧】想杀掉挡住别人的事务，KILL 的是连接 ID，不是事务 ID：`INNODB_TRX` 里的 `trx_mysql_thread_id` 才是连接号，`KILL <trx_mysql_thread_id>` 才能杀掉它；直接拿 `trx_id` 去 KILL 会报“找不到这个线程”。杀之前先确认它锁了多少行（`trx_rows_locked`），别把一个正在提交的大事务当成僵尸杀了。

【小技巧】DDL 卡在 `Waiting for table metadata lock` 时，去 `performance_schema.metadata_locks` 里找谁拿着 MDL：这张表按对象列出每个连接持有的元数据锁，看到某个长事务对这张表持有 SHARED_WRITE 之类的锁，DDL 的 EXCLUSIVE 锁就排不上队。原文第 4 节说“先查长事务”，这张表就是查 MDL 持有者的直接入口，比在 PROCESSLIST 里猜快得多。

【小技巧】`sys` 库里有个现成的视图 `sys.innodb_lock_waits`，把三张表拼成一行：它把等的人、挡的人、各自的 SQL、等了多久都拼在一行里显示，现场排障时一条 `SELECT * FROM sys.innodb_lock_waits;` 就够了，不用自己 JOIN `data_lock_waits`、`data_locks` 和 `INNODB_TRX`。需要写进监控脚本时再用裸表，日常人工排障直接用这个视图。

【小技巧】死锁日志只保留最近一次，想长期留存要开 `innodb_print_all_deadlocks`：默认是 OFF，打开后每次死锁都会完整写进 error log，和慢日志一样可以长期归档。原文第 2 节说“不要指望事后还能翻出来”，这个开关就是对应的解法——开之前确认 error log 的轮转和磁盘空间，死锁频繁的库别让日志把磁盘写满。

【小技巧】RR 下 `SELECT ... FOR UPDATE` 查一个不存在的行也会加锁，锁的是间隙：`WHERE id = 5 FOR UPDATE` 且 id=5 不存在时，InnoDB 会在 5 所在的间隙上加间隙锁，防止别的事务插进这一行。`data_locks` 里 LOCK_DATA 显示 `supremum pseudo-record` 就是“最后一个记录之后的间隙”被锁住了，看到它别以为是锁错了行，它是幻读防护在起作用。

【小技巧】自动提交下锁的持有时间只有一条语句：autocommit 开启时，每条 UPDATE/DELETE 自成一个事务，语句跑完锁就放了；“事务里先查后改、中间调接口”这种长事务才会在整个事务期间持锁。排障时看到某个事务持锁很久，先看它是多语句事务还是单条语句跑得慢——前者缩短事务，后者优化 SQL，解法完全不同。

【小技巧】死锁检测可以关，但关掉后死锁会变成超时：`innodb_deadlock_detect` 默认开启，死锁一出现立刻被发现并回滚代价小的事务；高并发下检测本身有开销，有人会把它关掉省开销。关掉之后死锁不再被主动发现，两个事务会互相等到 `innodb_lock_wait_timeout`（默认 50 秒）才报错 1205——等于把“立刻回滚一个”换成了“两个一起等 50 秒”，关之前先算清这笔账。

【冷知识】死锁的“受害者”不是随机挑的，是按改动行数选的：InnoDB 检测到等待环后，会回滚 undo 日志更小、也就是改动行数更少的那个事务，因为回滚它代价最小。日志最后一行 `WE ROLL BACK TRANSACTION (2)` 里的事务 2，通常就是改得更少的那个；所以“被回滚的是小事务”不是巧合，是检测算法有意为之。

【冷知识】`data_locks` 和 `data_lock_waits` 是 8.0 才有的，替代了老版本的 `INFORMATION_SCHEMA.INNODB_LOCKS` / `INNODB_LOCK_WAITS`：老版本的两张表在 8.0 里已被移除，旧排查脚本直接抄过来会报“表不存在”。8.0 之前用的是 information_schema 的锁表，8.0 之后统一走 performance_schema，升级后先确认排障脚本里引的是新表名。

【冷知识】元数据锁（MDL）是 5.5 才引入的：5.5 之前 DDL 和 DML 之间没有这层保护，一个事务在读表时另一个连接可以直接 ALTER 改表结构；5.5 引入 MDL 后，DDL 要拿到表的排他 MDL 才能执行，正在用表的事务会挡住它。这也是“ALTER 被长事务挡住”这个现象的历史起点，锁等待排查里 MDL 是一类独立的问题。

【冷知识】`supremum pseudo-record` 是 InnoDB 里的“虚拟最大值”：每张索引最后都有一条伪记录代表“正无穷”，间隙锁锁到索引末尾时，LOCK_DATA 就会显示这个名字。它不是真实存在的一行，只是用来表示“最后一个真实记录之后的间隙”；看到它就知道这把间隙锁锁的是尾部区间，而不是某一行。

【冷知识】行锁的等待关系在内部是一张“等待图”：InnoDB 维护每个事务在等谁的锁，死锁检测就是在这张图上找环，找到环就回滚其中一个事务破环。这张图只在内存里，不对外暴露，排障时看到的 `data_lock_waits` 其实就是这张图的边——每行记录就是一条“事务 A 等事务 B”的边，阻塞链就是沿着这些边走出来的。

## 面试与自测

1. 锁等待排查四步分别看什么？第二步里哪两个字段最能定位长事务？
2. 死锁日志里三要素是什么？被回滚的事务业务层应该怎么处理？
3. 两个事务以相反顺序改两行为什么会死锁？根治办法是什么？

### 参考答案

1. 四步：SHOW PROCESSLIST 看谁在等；INNODB_TRX 看运行中的事务；data_lock_waits（老版本 INNODB_LOCK_WAITS）看谁等谁；ENGINE INNODB STATUS 看死锁现场。第二步里 trx_started（事务跑了多久）和 trx_rows_locked（锁了多少行）最能定位长事务，再结合 trx_query 看它在跑什么 SQL。
2. 三要素：谁被回滚（最后一行 WE ROLL BACK TRANSACTION）、争哪把锁（WAITING FOR 与 HOLDS 对上号的锁）、哪两条 SQL（两个 TRANSACTION 下的 SQL）。被回滚的事务业务层要做有限次重试，且重试操作本身必须幂等。
3. 因为 A 持有行 1 的锁等行 2，B 持有行 2 的锁等行 1，互相等、谁也不放，就是死锁。根治办法是业务层固定访问顺序（一律按 id 升序改），顺序一致就撞不上；只 KILL 事务是治标。
