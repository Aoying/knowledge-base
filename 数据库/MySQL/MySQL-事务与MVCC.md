# MySQL 事务与 MVCC

## 1. 核心概念

事务解决的是并发下的数据正确性：ACID 里原子性靠 undo log、持久性靠 redo log、隔离性靠锁 + MVCC 一起实现。理解事务，不要只背定义，要落到「这条数据现在有几个版本、谁能看见哪个」。

## 2. 隔离级别与可见性

| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|---|---|---|---|
| 读未提交 RU | 有 | 有 | 有 | 几乎不用 |
| 读已提交 RC | 无 | 有 | 有 | 每条语句生成新快照；Oracle 默认 |
| 可重复读 RR | 无 | 无 | 基本无 | InnoDB 默认；快照读靠 MVCC、当前读靠间隙锁防幻读 |
| 串行化 | 无 | 无 | 无 | 读也加锁，并发最差，只在极端场景用 |

```sql
SELECT @@transaction_isolation;                 -- 看当前隔离级别（5.7 变量名 tx_isolation）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

关键区别只记一条：**RC 是每执行一条 SELECT 就刷新快照，RR 是事务第一次快照读时定格快照**。长事务在 RR 下会一直拿着旧快照，undo 版本链越攒越长，这就是「长事务拖垮数据库」的原理。

### 快照读 vs 当前读

- 快照读：普通 `SELECT`，读 MVCC 版本，不加锁。
- 当前读：`SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE`、`UPDATE`、`DELETE`，读最新版本并加锁。
- 同一事务里先快照读、后当前读，会读到不同版本的数据，写代码时要有意识。

## 3. undo 与 redo

| 日志 | 作用 | 内容 |
|---|---|---|
| undo log | 回滚 + MVCC 版本链 | 修改前的数据，事务回滚时反向执行；旧版本靠它串成链 |
| redo log | 崩溃恢复、保证已提交不丢 | 页的物理修改，循环写；提交时先刷 redo（WAL），再异步刷数据页 |
| binlog | 主从复制、归档恢复 | 逻辑变更，server 层产生，见《MySQL-binlog》 |

两阶段提交（redo prepare → 写 binlog → redo commit）保证两个日志不打架，细节知道结论即可：**redo 决定事务算不算提交成功，binlog 必须与之对齐**。

## 4. WAL 深入原理

第 3 节只给了结论：提交时先刷 redo，再异步刷数据页。本节把这句话展开——WAL（Write-Ahead Logging，预写日志）不是一句口号，是一整套“崩溃后不丢已提交事务”的机制。

### 为什么必须先写日志，后写数据页

数据页刷盘是随机 IO：一个事务可能改散落在各处的几页，每页刷盘都要寻道、写盘，又贵又慢。redo log 是顺序追加写：不管事务改了多少页，提交时只要把这批修改顺序写进日志文件，就可以向客户端返回成功，数据页慢慢刷、后台刷、攒一批刷。

WAL 规则只有一条，刻在所有实现里：**数据页落盘之前，对应这次修改的日志必须先落盘**。反过来不成立：日志落盘了，数据页可以迟迟不落盘。崩溃后内存里的数据页全丢，但只要日志在，重启时按日志把修改重放一遍，数据就回来了。这就是持久性（D）的落地方式：持久性不靠“数据页立刻写盘”，靠“日志立刻写盘 + 崩溃后重放”。

### redo log 的形态：物理日志、循环写、LSN

- **物理日志**：redo 记的是“哪个页的哪个位置改成了什么”，不是 SQL，也不是行变更。恢复时按页重放，不需要重新执行 SQL、不需要解析语义，所以快。
- **循环写**：redo 是一组固定大小的日志文件，写满后从头覆盖。旧日志能被覆盖的前提是它对应的数据页已经刷盘——这个“能覆盖到哪里”的边界，就是检查点（见下）。
- **LSN（Log Sequence Number）**：日志流里的字节偏移，单调递增。每个数据页页眉也记着最后一次修改它的 LSN。恢复时拿日志记录的 LSN 和页 LSN 对比：页 LSN 更大，说明这条修改已经在页里了，跳过；否则重放。这保证重放是幂等的，重复跑一遍也不会错。

容量配置：8.0.30 起用 `innodb_redo_log_capacity` 统管 redo 总容量，取代过去“文件数 × 单文件大小”的配法。redo 配太小，检查点会被迫频繁推进、脏页被迫提前刷盘，写负载一高就出现性能毛刺；配太大，崩溃恢复要重放的日志变长，恢复时间变长。

### 提交时的刷盘策略：性能与持久性的档位

事务提交时，redo 先写进内存里的 log buffer，再按 `innodb_flush_log_at_trx_commit` 的档位决定何时落盘：

| 档位 | 行为 | 崩溃后果 |
|---|---|---|
| 1 | 每次提交都 fsync 到磁盘 | 最安全；MySQL 崩溃、机器断电都不丢已提交事务 |
| 0 | 每秒由后台线程刷一次（`innodb_flush_log_at_timeout` 控制间隔，默认 1 秒） | MySQL 崩溃最多丢 1 秒已提交事务 |
| 2 | 每次提交写到操作系统缓存，不 fsync | MySQL 崩溃不丢（操作系统还在）；机器断电/宕机可能丢操作系统没刷下去的部分 |

生产默认用 1。和 binlog 的 `sync_binlog=1` 合称“双 1”：redo 侧和 binlog 侧都每次提交落盘，才是真不丢。只放宽 redo 侧，丢的是已提交事务本身；只放宽 binlog 侧，丢的是复制关系（见 MySQL-binlog 篇“组提交与刷盘策略全谱”一节的风险说明）。

### 组提交：多次提交摊一次 fsync

fsync 是提交路径上最贵的系统调用。并发高时，多个事务几乎同时提交，InnoDB 会把它们的 redo 合并成一次 fsync：先到的事务稍等一会儿，等一小批凑齐再一起刷盘。单个事务的提交延迟略增，但每秒能提交的事务数大幅上升。binlog 侧也有对应的组提交参数（`binlog_group_commit_sync_delay`），两边是同一思想：**用一点延迟换吞吐**。延迟敏感的业务别把等待窗口开大，否则一次 fsync 的等待会直接体现在接口 RT 上。

### 检查点：让旧日志空间可复用

检查点（checkpoint）是一个 LSN 水位：小于这个 LSN 的日志所对应的修改，都已经刷进数据页了，这段日志空间可以安全覆盖。检查点推进 = 脏页刷盘进度 + 日志可覆盖边界前移。

触发时机（原理层，不列具体阈值参数）：

- redo 日志空间快写满时——不推进就无处可写，写事务会被迫停下来等刷盘，这是最危险的一种，表现为毫无征兆的写停顿。
- 脏页比例达到水位时——后台刷脏页线程按水位工作，把检查点往前推。
- 后台空闲时、定时推进时——平时慢慢刷，别攒到日志满了再集中刷。
- 实例正常关闭时——关机前把脏页刷干净、检查点推到最新，下次启动恢复最快。

InnoDB 用的是模糊检查点（fuzzy checkpoint）：不停机、不锁表，后台线程按 LSN 渐进刷脏页，检查点一点点往前挪。排障时看检查点离最新 LSN 有多远，就知道崩溃后要重放多少日志：

```sql
SHOW ENGINE INNODB STATUS;   -- 看 LOG 段
```

```text
Log sequence number  1234567890   -- 最新 LSN：日志写到了哪里
Log flushed up to    1234567800   -- 已落盘 LSN：日志刷到了哪里
Last checkpoint at   1234500000   -- 检查点 LSN：小于它的修改都已进数据页
```

三个数的差值就是“崩溃后要重放的量”和“还没落盘的量”。`Last checkpoint at` 长期远远落后于 `Log sequence number`，说明脏页刷盘跟不上写速度，先查写负载和刷盘能力，别只盯着慢查询。

### 崩溃恢复流程：前滚 + 回滚

实例崩溃重启时，InnoDB 按固定顺序恢复，不需要人工干预：

1. **从检查点开始前滚**：从 `Last checkpoint at` 对应的 LSN 起，按 LSN 顺序重放 redo，把已提交事务的修改重新写回数据页。页 LSN 已大于日志 LSN 的跳过（幂等保证）。
2. **对未提交事务回滚**：重放完成后，靠 undo log 把崩溃时没提交的事务反向滚掉，数据页回到事务开始前的状态。
3. **恢复完成才对外服务**：恢复结束的点，就是“所有已提交事务都在、所有未提交事务都不在”的状态，和崩溃前客户端看到的已提交结果一致。

关键推论：崩溃恢复能恢复的上限是“日志里有的已提交事务”。`innodb_flush_log_at_trx_commit=0` 下丢的那 1 秒，是因为日志本身就没落盘，重放无从谈起——不是恢复流程的 bug，是档位选型的代价。

### WAL 与 binlog 的关系及两阶段提交

redo 和 binlog 是两套日志，分属两层，缺一不可：

| 日志 | 层级 | 内容 | 覆盖范围 | 用途 |
|---|---|---|---|---|
| redo log | InnoDB 引擎层 | 页的物理修改 | 循环写，会被覆盖 | 崩溃恢复 |
| binlog | MySQL Server 层 | 逻辑行变更 | 归档保留（按保留期 purge） | 主从复制、PITR、CDC |

redo 不能做主从复制（它是物理的、循环覆盖的）；binlog 不能做崩溃恢复（事务提交前不写 binlog，崩溃后未提交数据的回滚靠 undo、已提交数据的重放靠 redo）。两阶段提交（2PC）就是让这两套日志在崩溃面前保持一致：

```text
1) InnoDB 写 redo，事务进入 prepare 状态
2) 写 binlog（落盘与否看 sync_binlog）
3) InnoDB 写 redo commit 标记，事务正式提交
```

崩溃可能发生在任意一步，恢复时的判定规则是固定的：

| 崩溃点 | 恢复结果 | 原因 |
|---|---|---|
| 第 1 步之后（只有 redo prepare） | 回滚 | binlog 里没有这条事务，主库回滚才和从库一致 |
| 第 2 步之后（binlog 已写，redo 未 commit） | 提交 | binlog 已有这条事务，主库必须提交，否则从库多出主库没有的数据 |
| 第 3 步之后 | 已提交 | 正常提交状态 |

所以第 3 节那句话的完整含义是：**redo 决定事务在主库算不算提交成功，binlog 决定这条事务会不会出现在从库，两阶段提交 + 恢复时查 binlog 的判定规则，保证两者永远对齐**。反例就是 binlog 篇里写过的风险：`sync_binlog=0` 时崩溃，redo 已提交、binlog 未落盘——主库有这条事务、从库没有，主从静默不一致，而且没有任何报错告诉你。

### 常见坑

- **把 redo 当成备份**：redo 是循环覆盖的，不能替代 binlog + 全量备份做 PITR。误删恢复靠 binlog 重放（见 MySQL-binlog 篇），不是靠 redo。
- **档位 0/2 一刀切说“不安全”**：档位是取舍，不是道德判断。日志型、埋点型、可重放的业务用 0/2 换吞吐是合理选择；钱、订单、库存类业务用 1，别省这一次 fsync。
- **检查点落后只盯慢查询**：写停顿、毛刺先看 `Last checkpoint at` 和脏页水位，再看 SQL。日志空间和刷盘能力是另一类瓶颈，不在执行计划里。
- **大事务放大 WAL 代价**：一个事务改的页越多，redo 越大、组提交收益越低、崩溃恢复重放越长。拆小事务既是锁治理，也是 WAL 治理。

## 5. MVCC 可见性判断

每行隐藏两个字段：`DB_TRX_ID`（最后修改的事务 ID）、`DB_ROLL_PTR`（指向 undo 里的旧版本）。快照读时拿当前事务的 ReadView 判断：

1. 版本的 trx_id 就是自己 → 可见。
2. trx_id 小于 ReadView 的最小活跃事务 ID（min_trx_id）→ 在快照生成前已提交，可见。
3. trx_id 大于等于最大事务 ID（max_trx_id）→ 快照之后才开启，不可见，沿版本链回溯。
4. 落在活跃列表里（还没提交）→ 不可见，回溯；不在列表里（已提交）→ 可见。

回溯就是沿 `DB_ROLL_PTR` 一版一版往旧了找，直到找到第一个可见版本。版本链太长时一次快照读要跳很多版——再次说明长事务是性能毒药。

```sql
-- 查正在跑的长事务（排障第一条）
SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx ORDER BY trx_started;

-- 查锁等待关系（8.0）
SELECT * FROM performance_schema.data_lock_waits;
```

## 6. 锁：行锁、间隙锁与死锁

- 记录锁（Record Lock）：锁索引记录本身。**InnoDB 的行锁锁的是索引**，没索引的更新会锁全表扫描过的所有行，效果近似表锁——更新语句必须走索引。
- 间隙锁（Gap Lock）：锁索引记录之间的空隙，只在 RR 下、当前读时生效，用来防幻读（插入新行）。
- 临键锁（Next-Key Lock）= 记录锁 + 间隙锁，RR 下当前读的默认形态。

```sql
-- 例：idx_status 上不存在 status=5 的行
BEGIN;
SELECT * FROM t_order WHERE status = 5 FOR UPDATE;  -- 锁住 status 所在的间隙
-- 此时其他事务 INSERT status=5 会被挡住（防幻读），但也更容易死锁
COMMIT;
```

### 死锁排查

```sql
SHOW ENGINE INNODB STATUS;   -- 看 LATEST DETECTED DEADLOCK 段：两个事务各持有什么锁、在等什么
```

死锁的成因永远是**加锁顺序不一致**或**锁范围过大**。治理顺序：

1. 业务层统一加锁顺序（如永远按 id 从小到大更新）。
2. 缩短事务：事务里不调远程接口、不做无关查询。
3. 保证更新走索引，避免单条 UPDATE 锁一片。
4. 应用层对死锁异常（1213）做有限重试——死锁是可恢复错误，重试是正规手段，不是掩盖问题。

## 7. 常见坑

- **隐式提交**：事务中执行 DDL（CREATE/ALTER 等）会自动提交前面的操作，迁移脚本里混 DDL 和 DML 要特别小心。
- **自增不回滚**：事务回滚后自增值不回收，ID 有空洞是正常现象，别拿自增当连续序号。
- **长事务不自知**：开了事务忘提交（连接池里连接被复用时更隐蔽）。监控 `innodb_trx` 里超过阈值的事务并告警。
- **`SELECT ... FOR UPDATE` 不带索引条件**：RR 下可能把整表范围都临键锁住，并发直接雪崩。
- **在 RC 下还假设不幻读**：项目改过隔离级别（或迁到 OceanBase）后，防幻读逻辑要重新评估，别按 RR 的直觉写代码。

## 8. undo 版本链与长事务定量

本节所有数字均为手算，Python 3 本地复算（见节末“### 复算口径”）。凡标【官方】的是 MySQL 8.0 官方手册事实；凡标【估算】的是简化假设下的手算，不是官方数字、不是实测值。行宽、写分布、purge 能力一变，字节数按比例变，版本数结论不变。

### 8.1 Read View 可见性手算

取一个 RR 事务的快照（第一次快照读时生成），设其 `creator_trx_id = 99`，快照生成瞬间系统里还有 3 个活跃事务：

```text
m_ids = [100, 101, 102]，min_trx_id = 100，max_trx_id = 103（下一个待分配的事务 ID）
```

判定规则（与正文第 5 节一致，先判自己、再比两端、最后查活跃列表）：

| 版本 trx_id | 判定步骤 | 结论 |
|---|---|---|
| 95 | 95 < min_trx_id（100），快照前已提交 | 可见 |
| 99 | 等于 creator_trx_id，是自己改的 | 可见 |
| 100 | 落在 [100, 103)，且在 m_ids 里，未提交 | 不可见，沿链回溯 |
| 101 | 落在 [100, 103)，且在 m_ids 里，未提交 | 不可见，沿链回溯 |
| 102 | 落在 [100, 103)，且在 m_ids 里，未提交 | 不可见，沿链回溯 |
| 103 | 103 ≥ max_trx_id（103），快照之后才开启 | 不可见，沿链回溯 |
| 110 | 110 ≥ max_trx_id（103），快照之后才开启 | 不可见，沿链回溯 |

【官方】每行隐藏 `DB_TRX_ID`（6 字节，最后修改该行的事务 ID）与 `DB_ROLL_PTR`（7 字节，指向 undo 里的旧版本）；更新 undo 日志只有在“没有任何快照在一致读时可能需要它来重建更早版本”之后才能丢弃。

链式回溯的例子：某行当前版本 `trx_id = 102`，沿 `DB_ROLL_PTR` 的版本链是 `102 → 101 → 100 → 95`。上面这个快照读它时：102 不可见、101 不可见、100 不可见、95 可见——一次快照读遍历 4 个版本、回溯 3 跳，才读到第一个可见版本。链越长，这趟回溯越长。

### 8.2 undo 版本链长度增长：同一行被反复更新

【估算】设同一行被以固定速率反复更新，每次更新产生一个新版本，旧版本全部留在 undo 版本链里（因为长事务的旧快照还可能需要它们）。版本链长度 = 写速率 × 持续时间：

| 写速率 | 长事务持有快照时长 | 版本链长度 |
|---|---|---|
| 50 次/秒 | 600 秒（10 分钟） | 50 × 600 = 30,000 个版本 |
| 10 次/秒 | 3,600 秒（1 小时） | 10 × 3,600 = 36,000 个版本 |
| 50 次/秒 | 3,600 秒（1 小时） | 50 × 3,600 = 180,000 个版本 |

含义：10 分钟的长事务 + 每秒 50 次同行更新，一次快照读最坏要沿链遍历 30,000 个版本才找到可见版；1 小时则是最坏 180,000 个版本。注意这是“最坏遍历版本数”，不是耗时毫秒数——每跳一次是沿指针找上一版，本节不把版本数换算成毫秒，因为那取决于缓存命中与行宽，没有实测值就不要编一个。

### 8.3 长事务持有旧快照时，undo 积压的量级估算

【估算】上面是“同一行”的链；全局看，设全库更新速率 500 次/秒，一个 RR 长事务持有旧快照 1 小时不提交，则这 1 小时内产生、且 purge 不能丢弃的 undo 记录数：

```text
500 次/秒 × 3,600 秒 = 1,800,000 条 undo 记录
```

字节量级要借一个“每条 undo 记录多大”的假设。【官方】purge 文档在举例时假设“事务很小，只有 100 字节”，并算出 `innodb_max_purge_lag = 1,000,000` 对应约 100MB 未 purge 的表行。本节沿用这个 100 字节/条的示例假设：

```text
1,800,000 条 × 100 字节/条 = 180,000,000 字节 = 180 MB（约 171.7 MiB）
```

对照官方基线：【官方】History list length“通常是一个很小的值，一般不到几千”，而写负载大或长事务会让它上涨。1,800,000 对 3,000 是 600 倍——也就是说，500 次/秒写压 + 1 小时长事务，History list length 的量级会从“几千”涨到“百万级”。

单行链的字节数同理（100 字节/条假设下）：30,000 个版本的链约 2.9 MiB，180,000 个版本的链约 17.2 MiB。行越宽数字越大：若每条 undo 记录 1KB，1,800,000 条就是约 1.72 GiB；这正是“版本数是硬结论、字节数随行宽缩放”的意思。

### 8.4 purge 滞后与 undo 表空间膨胀的关系

【官方】purge 按固定周期解析并处理 history list 里的 undo 日志页，处理完才释放；`innodb_purge_batch_size` 默认每批处理 300 页；`innodb_max_purge_lag` 默认 0（即不设上限、不延迟 DML），超过阈值时会对 INSERT / UPDATE / DELETE 施加延迟、让 purge 追上来；History list length 就是 `SHOW ENGINE INNODB STATUS` 的 TRANSACTIONS 段里那个数。【官方】在 RR 等一致读隔离级别下，事务必须返回与创建 ReadView 时相同的结果，所以 InnoDB 必须把 undo 里的数据副本一直保留到所有依赖它的事务完成；mysqldump `--single-transaction` 期间有大量并发 DML、以及长查询，都是会让 History list length 上涨的典型场景。【官方】官方手册还明确建议定期提交事务（包括只做一致读的事务），否则 InnoDB 无法丢弃 update undo 日志，rollback segment 可能涨得过大、撑满所在的 undo 表空间。

【估算】定量关系是这样串起来的：长事务不提交 → 它的 ReadView 是 purge 的下限水位，比该快照新的 update undo 记录一条都不能丢 → purge 只能处理比水位更老的记录，处理量跟不上新增量 → History list length 以约等于全库更新速率的速度线性增长（上节的 500 次/秒 → 每小时 +1,800,000 条、约 +180 MB）。长事务不结束，这个增长就不停；它一提交（或回滚、被 kill），水位瞬间前移，purge 才能把积压批量清掉。undo 表空间的物理文件未必立刻缩小（截断是异步的），但逻辑积压（History list length）会先掉下来。

一个可直接用的判断标尺（把官方基线和估算拼在一起）：History list length 长期在几千以内算正常；到 100,000 量级说明 purge 已明显滞后；到 1,000,000 量级（按官方示例约 100MB 未 purge 行）就该先找最老的活跃事务，而不是先调 purge 参数——正文“小技巧”里那条“先找最老的事务”就是这个道理。

### 8.5 边界条件：结论在何种假设下成立

1. **写分布假设**：8.2 节“30,000 个版本”假设每秒 50 次更新全落在同一行上。若更新分散到很多行，单行链不会这么长，一次快照读的回溯代价就打折；但 8.3 节的全局积压（每小时 1,800,000 条）只取决于全库总更新速率，与分布无关，结论不变。
2. **快照已生成假设**：结论要求长事务在 RR 下、且已经做过快照读（ReadView 已生成）。若事务只是 `BEGIN` 后一直没读，或隔离级别是 RC（每条语句刷新快照），它并不持有旧快照，purge 不被它卡住，本节的积压估算不成立。排障时要先确认 `trx_started` 久的事务是不是真的持有了旧 ReadView。
3. **purge 能力假设**：8.3–8.4 节假设 purge 线程本身能跟上、唯一的瓶颈是最老 ReadView 卡住水位。若写压本身已超过 purge 的处理能力（例如持续大批量删改、每批只处理 300 页），即使没有长事务，History list length 也会涨。这时要区分“被长事务卡住”（杀掉最老事务即缓解）与“purge 跟不上写压”（需降写压或调 purge），两种成因的解法不同。
4. **undo 记录大小假设**：所有字节数（180 MB、2.9 MiB、17.2 MiB、1.72 GiB）都建立在“每条 undo 记录 100 字节 / 1KB”的假设上，100 字节是借用官方 purge 文档的示例假设。真实 undo 记录大小随行宽、变长字段、有无大列变化：打折验算——若实际是 200 字节/条，1,800,000 条就是 360 MB（翻倍）；若实际是 50 字节/条，就是 90 MB（减半）。字节结论按比例缩放，版本数结论（30,000 / 36,000 / 180,000 / 1,800,000）不受行宽影响。
5. **均匀速率假设**：手算假设写速率均匀。若写负载是突发式的（例如整点批量任务几分钟内打满），版本链会在短时间内冲得比“平均速率 × 时间”更高，峰值时刻的回溯代价要按峰值速率算，不能拿全天平均速率去估峰值。

### 复算口径

```python
# Python 3 本地复算（2026-11-08）：ReadView 可见性 + 版本链 + undo 积压
m_ids = {100, 101, 102}; min_trx = 100; max_trx = 103; creator = 99

def visible(t):
    if t == creator: return True
    if t < min_trx: return True
    if t >= max_trx: return False
    if t in m_ids: return False
    return True

for t in [95, 99, 100, 101, 102, 103, 110]:
    print(t, visible(t))
# 95 True / 99 True / 100 False / 101 False / 102 False / 103 False / 110 False
chain = [102, 101, 100, 95]
print("chain versions traversed:", len(chain), "hops:", len(chain) - 1)  # 4 版, 3 跳

for rate, T in [(50, 600), (10, 3600), (50, 3600)]:
    print(f"rate={rate}/s T={T}s chain={rate * T}")  # 30000 / 36000 / 180000

rate, T = 500, 3600
recs = rate * T
print("global undo records:", recs)                       # 1800000
print("bytes @100B:", recs * 100, "MiB:", recs * 100 / 1024 / 1024)  # 180000000, 约 171.7 MiB
print("bytes @1KB GiB:", recs * 1024 / 1024**3)          # 约 1.72 GiB
print("single-row 30k @100B MiB:", 30000 * 100 / 1024 / 1024)   # 约 2.9 MiB
print("single-row 180k @100B MiB:", 180000 * 100 / 1024 / 1024) # 约 17.2 MiB
print("HLL vs baseline 3000x:", recs / 3000)             # 600.0
print("purge example 1M x 100B MB:", 1000000 * 100 / 1e6) # 100.0
print("half rate 250/s 1h recs:", 250 * 3600, "MB @100B:", 250 * 3600 * 100 / 1e6)  # 900000, 90.0
print("200B per rec, 1.8M MB:", 1800000 * 200 / 1e6)     # 360.0
```

## 实战案例

### 案例一：RR 长事务持有旧快照，同行被反复更新，单次快照读要沿版本链回溯

**现象：** 一个 RR 事务第一次快照读后迟迟不提交，期间同一行被持续更新。按原文 §8.1 的 ReadView 算例，该事务 `creator_trx_id = 99`，快照瞬间活跃事务 `m_ids = [100, 101, 102]`，`min_trx_id = 100`，`max_trx_id = 103`；某行版本链为 `102 → 101 → 100 → 95`，这次快照读依次判定 102、101、100 均不可见，直到 95 才可见，一次快照读遍历 4 个版本、回溯 3 跳（出处：§8.1）。这还只是 4 个版本的小链。按 §8.2 的手算，若同一行以 50 次/秒被更新、长事务持有快照 600 秒（10 分钟），版本链长到 50 × 600 = 30,000 个版本；若持有 3,600 秒（1 小时），则为 50 × 3,600 = 180,000 个版本；10 次/秒 × 3,600 秒则为 36,000 个版本（出处：§8.2）。也就是说，现象不是“读到了错数据”，而是“每次快照读都要沿链多跳很多版才找到可见版”。

**排查：** 先确认这个长事务是不是真的持有了旧 ReadView。原文 §8.5 第 2 条明确要求先确认这一点：若事务只是 `BEGIN` 后一直没读，或隔离级别是 RC（每条语句刷新快照），它并不持有旧快照，purge 不被它卡住，本节的积压估算不成立。确认用原文已出现的写法：

```sql
SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx ORDER BY trx_started;
```

查到 `trx_started` 最久的事务后，再按原文 §5 的判断复核：版本 `trx_id` 小于 `min_trx_id`（100）如 95、等于自己的 99 才可见；落在活跃列表里的 100、101、102 与大于等于 `max_trx_id`（103）的 103、110 均不可见、沿链回溯（出处：§8.1；§5）。同时注意 §8.5 第 1 条的写分布假设：30,000 个版本的前提是每秒 50 次更新全落在同一行上；若更新分散到很多行，单行链不会这么长，一次快照读的回溯代价就打折。单行链的字节数原文未对本案例实测：按 100 字节/条 undo 记录的示例假设，30,000 个版本的链约 2.9 MiB，180,000 个版本的链约 17.2 MiB（出处：§8.3）；真实行宽下的字节数原文未展开，不作定论。本节不把版本数换算成毫秒耗时，原文 §8.2 已说明每跳一次是沿指针找上一版，耗时取决于缓存命中与行宽，没有实测值就不要编一个。

**结论：** 长事务在 RR 下持有旧快照越久、同行更新越密，单次快照读的回溯版本数就按“写速率 × 持续时间”线性增长（50 次/秒 × 600 秒 = 30,000 个版本），这是原文 §2“长事务拖垮数据库”的定量落点：快照读要沿 `DB_ROLL_PTR` 一版一版往旧了找，直到第一个可见版本（出处：§8.2；§5）。治理方向按原文正文：缩短事务、定期提交——原文 §8.4 引官方建议，定期提交事务（包括只做一致读的事务），否则 InnoDB 无法丢弃 update undo 日志。至于本案例中某次具体查询实际跳了多少版、耗时多少毫秒，原文未展开，需按原文口径实测，不作定论。

### 案例二：长事务不提交，History list length 从几千量级涨到百万量级

**现象：** 全库更新速率 500 次/秒，一个 RR 长事务持有旧快照 1 小时不提交。按 §8.3 的手算，这 1 小时内产生、且 purge 不能丢弃的 undo 记录数为 500 × 3,600 = 1,800,000 条；沿用官方 purge 文档示例的 100 字节/条假设，约 180,000,000 字节 = 180 MB（约 171.7 MiB）（出处：§8.3）。对照官方基线：History list length“通常是一个很小的值，一般不到几千”，1,800,000 对 3,000 是 600 倍——量级从“几千”涨到“百万级”（出处：§8.3）。原文 §8.4 给出的判断标尺是：长期在几千以内算正常；到 100,000 量级说明 purge 已明显滞后；到 1,000,000 量级（按官方示例约 100 MB 未 purge 行）就该先找最老的活跃事务，而不是先调 purge 参数（出处：§8.4）。

**排查：** 先看 History list length，再找最老的事务，不要先调 purge 参数。History list length 就是 `SHOW ENGINE INNODB STATUS` 的 TRANSACTIONS 段里那个数（出处：§8.4），写法复用原文：

```sql
SHOW ENGINE INNODB STATUS;
```

再用原文 §5 的语句定位最老的活跃事务：

```sql
SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx ORDER BY trx_started;
```

定量关系按 §8.4 串起来核对：长事务不提交 → 它的 ReadView 是 purge 的下限水位，比该快照新的 update undo 记录一条都不能丢 → purge 只能处理比水位更老的记录，处理量跟不上新增量 → History list length 以约等于全库更新速率的速度线性增长（500 次/秒 → 每小时 +1,800,000 条、约 +180 MB）（出处：§8.4）。同时排除另一种成因，原文 §8.5 第 3 条：若写压本身已超过 purge 的处理能力（例如持续大批量删改、每批只处理 300 页——`innodb_purge_batch_size` 默认每批处理 300 页），即使没有长事务，History list length 也会涨；要区分“被长事务卡住”（杀掉最老事务即缓解）与“purge 跟不上写压”（需降写压或调 purge），两种成因的解法不同（出处：§8.5 第 3 条；§8.4）。另外注意 `innodb_max_purge_lag` 默认 0（即不设上限、不延迟 DML），超过阈值时才对 INSERT / UPDATE / DELETE 施加延迟（出处：§8.4）；官方 purge 文档示例中 `innodb_max_purge_lag = 1,000,000` 对应约 100 MB 未 purge 的表行（出处：§8.3）。本案例的真实 undo 记录大小、真实 History list length 峰值、purge 的实际处理速度，原文未展开：字节数都建立在 100 字节/条的假设上，若实际是 200 字节/条，1,800,000 条就是 360 MB（翻倍），若是 50 字节/条就是 90 MB（减半），若每条 1 KB 则约 1.72 GiB——字节结论按比例缩放，版本数结论（1,800,000 条）不受行宽影响（出处：§8.5 第 4 条；§8.3）。undo 表空间的物理文件未必立刻缩小（截断是异步的），但逻辑积压（History list length）会先掉下来（出处：§8.4）。

**结论：** 长事务不结束，History list length 的增长就不停；它一提交（或回滚、被 kill），水位瞬间前移，purge 才能把积压批量清掉（出处：§8.4）。排障顺序按原文 §8.4 的标尺：先找最老的活跃事务并让它结束，而不是先调 purge 参数；`mysqldump --single-transaction` 期间有大量并发 DML、以及长查询，都是会让 History list length 上涨的典型场景，导出窗口内出现百万量级积压时先按同一顺序排查（出处：§8.4）。至于本案例的实际 purge 速度、实际 History list length 峰值，原文未展开，不作定论。

## 小技巧与冷知识

【小技巧】查“长事务拖了多久”别只看 `innodb_trx` 的开始时间，顺手看 `SHOW ENGINE INNODB STATUS` 里的 History list length：这个数是还没被 purge 掉的 undo 版本数，长事务一直不提交，它就一直涨。History list length 长期在高位，说明 purge 线程被最老的活跃事务卡住了，先找那个最老的事务、而不是去调 purge 参数。

【小技巧】排障时 `trx_query` 为空不代表事务在空闲睡觉：`information_schema.innodb_trx` 的 `trx_query` 只显示事务当前正在执行的语句，事务在等应用下一次发 SQL 时它就是空的。判断“这个事务是不是僵尸”，要看 `trx_started` 距今多久、结合 `trx_mysql_thread_id` 去 `SHOW PROCESSLIST` 里看对应连接的状态，两个表拼起来才准。

【小技巧】事务里想回滚一半，别整个回滚，用 SAVEPOINT：`SAVEPOINT sp1;` 之后出问题只 `ROLLBACK TO sp1;`，之前已执行的部分还留着，继续提交也没问题。适合“多步写入、某一步可降级”的流程，比如先插主表、再插从表，从表失败只回滚从表那一步；注意 `RELEASE SAVEPOINT` 只是删掉存档点，不提交任何东西。

【小技巧】抢任务、发券这类“取一条、锁一条”的队列写法，用 `SELECT ... FOR UPDATE SKIP LOCKED`：它会直接跳过已被别的事务锁住的行，拿下一条没锁的，不用等锁超时。MySQL 8.0 才支持 `SKIP LOCKED` 和 `NOWAIT`；`NOWAIT` 是不等、立刻报错，适合“锁不到就换一条路”的逻辑，`SKIP LOCKED` 适合“多 worker 并行消费同一张队列表”的场景。

【小技巧】同一事务里“快照读看不见、UPDATE 后突然冒出来”的行不是 bug，是 RR 下的幻读残口：快照读按 ReadView 读旧版本，新插入的行对它不可见；但同一事务随后 `UPDATE` 是当前读，读最新版本，就会把那行“新”行也改了，改完再 `SELECT` 就能看见它。防的办法是涉及范围更新时先 `SELECT ... FOR UPDATE` 锁住范围，让并发插入先被挡住，而不是指望快照读永远看不到新行。

【小技巧】RC 下默认没有间隙锁，唯一键冲突检查和外键检查是例外：切到 RC 之后，普通范围更新不再锁间隙，幻读防护基本靠业务自己扛；但插入时判唯一键重复、以及外键级联检查时，InnoDB 仍会短暂加间隙锁。所以 RC 下“间隙锁彻底消失”是错的，准确说法是“只有这两类检查还会用到它”，死锁排查时别因为隔离级别是 RC 就排除间隙锁。

【小技巧】等值查唯一索引时，临键锁会退化成记录锁：`WHERE id = 5 FOR UPDATE` 且 id 是唯一索引时，InnoDB 只锁这一行，不锁间隙；同样条件走非唯一索引时，锁的是“记录 + 它前面的间隙”。所以“等值更新也锁了一片”时，先看条件字段是不是唯一索引，再看执行计划是不是真的走了那个索引，两步确认比猜锁范围快。

【小技巧】二级索引查可见性要回表，不是因为它没存版本信息：二级索引条目里没有 `DB_TRX_ID`，InnoDB 无法仅凭二级索引判断这行对当前快照是否可见，必须按主键回聚簇索引取行、再比对 ReadView。覆盖索引能省回表的前提是“查询只用索引列”；一旦要判断可见性、或者要返回非索引列，回表省不掉，执行计划里看到回表别先怀疑它多余。

【小技巧】死锁排查时先确认 `innodb_deadlock_detect` 是不是被人关了：默认是开启的，死锁一出现立刻被发现、牺牲掉代价小的事务；如果有人为了省检测开销把它关掉，死锁就只能靠 `innodb_lock_wait_timeout`（默认 50 秒）超时来解，报错会从 1213 变成 1205。看到 1205 先问“检测关了没”，再看锁等待链，别按死锁的套路去查。

【小技巧】大事务回滚别急着 kill 连接：回滚本身也是要按 undo log 一条条反向执行的活，事务改了多少行，回滚就要还多少行，kill 掉连接不会让回滚变快，只会让连接断掉、回滚继续在后台跑。真正省时间的是事前拆事务；事后只能等，盯着 `SHOW ENGINE INNODB STATUS` 的事务段看回滚进度。

【小技巧】`START TRANSACTION WITH CONSISTENT SNAPSHOT` 是给“导出一致快照”准备的：它在事务一开始就定格快照，而不是等第一条 SELECT 才定格，mysqldump 的 `--single-transaction` 用的就是这套机制。普通业务代码不用它，写备份、导出、跨表对账脚本时用它，才能保证“多张表在同一个时间点上”。

【小技巧】改隔离级别要趁事务还没开始：`SET SESSION TRANSACTION ISOLATION LEVEL ...` 只对下一个新事务生效，已经开始的事务里改了也不生效；`SET GLOBAL` 更只影响之后新建的连接。切隔离级别后验证是否生效，要新开连接、开新事务再查 `@@transaction_isolation`，在旧连接里查到旧值别以为没改成功。

【冷知识】InnoDB 的删除不是真删，是先打“删除标记”：`DELETE` 只把行标记为删除（delete-marked），旧版本留在原地供 MVCC 和 purge 用，物理空间要等 purge 线程确认没有快照再需要它之后才回收。所以大批量删除后表空间不缩小是正常的，想回收要靠 `OPTIMIZE TABLE` 重建；反过来，MVCC 的可见性判断也因此能读到“已删但对我仍可见”的行。

【冷知识】没有主键、也没有唯一键的表，InnoDB 会悄悄加一个隐藏主键：每行自动带一个 6 字节的 `DB_ROW_ID`，按插入顺序递增，行定位靠它。这个隐藏列的存在意味着“没主键的表”只是你看不见主键，不是没有主键；建表时显式给主键，既是给 MVCC 和行锁一个稳定的行标识，也是给从库回放和删改一个可定位的依据。

【冷知识】`innodb_flush_log_at_trx_commit=1` 的 fsync 不是每次都写整段 redo：提交时只把本次事务产生的 redo 从 log buffer 刷下去，配合组提交把多个事务的 redo 合并成一次 fsync。所以高并发下档位 1 的成本没有想象中高，性能差主要来自“每次提交都必须等磁盘确认”这个等待本身，而不是写入量；机械盘和 SSD 上这个等待的差距，就是档位 1 在不同机器上表现差异的来源。

【冷知识】`SELECT ... FOR UPDATE` 锁住的行，别的事务 `SELECT` 照常能读：行锁只挡当前读和写，不挡快照读。这正是 MVCC 存在的意义——读不阻塞写、写不阻塞读。排障时看到“某行被锁了但查询还能出结果”，不是锁失效了，是快照读根本不走锁；想验证锁是不是真加上了，要用另一个事务的 `FOR UPDATE` 或 `UPDATE` 去试，而不是用普通 `SELECT`。

## 面试与自测

1. RC 和 RR 在快照生成时机上有何区别？为什么长事务在 RR 下会拖垮数据库？
2. 同一事务里先快照读、后当前读，为什么会读到不同版本的数据？
3. `innodb_flush_log_at_trx_commit=0` 和 `=2` 在 MySQL 崩溃与机器断电时的丢数后果有何不同？

4. 某 RR 事务的 ReadView 为 m_ids=[100,101,102]、min_trx_id=100、max_trx_id=103，另有一行版本链为 102 → 101 → 100 → 95：这次快照读会读到哪个版本、遍历了几个版本？若同一行以每秒 50 次被更新、该长事务持有快照 10 分钟，版本链会长到多少？

### 参考答案

1. RC 是每执行一条 SELECT 就刷新快照，RR 是事务第一次快照读时定格快照。长事务在 RR 下会一直拿着旧快照，undo 版本链越攒越长，一次快照读要沿版本链回溯很多版，这就是“长事务拖垮数据库”的原理。
2. 快照读是普通 SELECT，读 MVCC 版本、不加锁；当前读是 `SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE`、`UPDATE`、`DELETE`，读最新版本并加锁。两种读法读的版本来源不同，所以同一事务里先快照读、后当前读会读到不同版本的数据。
3. 档位 0 是每秒由后台线程刷一次，MySQL 崩溃最多丢 1 秒已提交事务；档位 2 是每次提交写到操作系统缓存、不 fsync，MySQL 崩溃不丢（操作系统还在），机器断电/宕机可能丢操作系统没刷下去的部分。生产默认用 1，和 `sync_binlog=1` 合称“双 1”才是真不丢。

4. 逐条判定：95 < 100，快照前已提交，可见；102、101、100 都在 m_ids 里，未提交，不可见；所以沿链回溯 102 → 101 → 100 都不可见，读到 95 这一版，一次快照读遍历 4 个版本、回溯 3 跳。版本链长度 = 50 次/秒 × 600 秒 = 30,000 个版本；这 30,000 个版本在长事务提交前都不能被 purge 丢弃。按 100 字节/条 undo 记录估算，单这条链约 2.9 MiB；若全库写压 500 次/秒、长事务持快照 1 小时，全局积压约 1,800,000 条 undo 记录、约 180 MB，History list length 会从通常的几千量级涨到百万量级。
