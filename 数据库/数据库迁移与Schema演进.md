# 数据库迁移与 Schema 演进

表结构不是一次定型的：业务迭代就要改表。迁移工具解决的是同一个问题：让表结构变更可版本化、可重复、可回滚、可审计——改表的脚本跟代码一起进版本库，而不是靠人手动在各环境敲 SQL。

## 1. 三个工具的机制

### 1.1 Flyway

最直观，适合 SQL 为主的团队：

- 版本化迁移：脚本按 `V<版本>__<描述>.sql` 命名，如 `V3__add_user_nickname.sql`，按版本号顺序执行，跳号、乱序都会被发现。
- 历史表：Flyway 在库里建一张历史表（默认 `flyway_schema_history`），记录每个已执行脚本的版本、校验和（checksum）、执行时间。
- 校验：启动时重算脚本 checksum，跟历史表比对。已执行的脚本被改过就报错停住，防止“本地改了已上线脚本，环境之间悄悄不一致”。
- 基线（Baseline）：已有库第一次接 Flyway 时，用基线把现状定为某个版本，之后的迁移从该版本往后走，老库不用重放全部历史脚本。
- 回滚：开源版不提供自动回滚，靠手写反向迁移脚本（比如 `V4__drop_user_nickname.sql`）；undo 属于付费版本能力，以官方文档为准。

```sql
-- V3__add_user_nickname.sql：只加可空列，不碰已有数据
ALTER TABLE user ADD COLUMN nickname VARCHAR(64) NULL COMMENT '昵称';
```

### 1.2 Liquibase

Changelog 驱动，适合多库、需要结构化管理的团队：

- Changelog：用 XML / YAML / JSON / SQL 写变更集（changeset），每个 changeset 有唯一 id + author，执行记录存在 `DATABASECHANGELOG` 表里，同样带 checksum 校验。
- 回滚：changeset 里写 `rollback` 段，声明怎么撤销；没写 rollback 段的变更，回滚时会直接失败，别指望它自动猜。
- 标签与上下文：changeset 可以打标签（tag）和上下文（context，比如 `dev`、`prod`），执行时按标签/上下文过滤，同一份 changelog 可以在不同环境跑不同子集。
- 跨库抽象：change 类型（addColumn、createTable）是抽象的，Liquibase 再翻译成各库方言。但方言差异并没有消失，写了 MySQL 特有的东西，换库还是要改，以官方文档为准。

```xml
<!-- changelog 片段骨架：只做演示，不直接上生产 -->
<changeSet id="20261026-01" author="ao">
    <addColumn tableName="user">
        <column name="nickname" type="VARCHAR(64)"/>
    </addColumn>
    <rollback>
        <dropColumn tableName="user" columnName="nickname"/>
    </rollback>
</changeSet>
```

### 1.3 Alembic

Python / SQLAlchemy 生态的标配：

- Revision 链：每个迁移是一个 revision 文件，有 `revision`（本版本 ID）和 `down_revision`（父版本 ID），串成一条链；`upgrade()` 往前走，`downgrade()` 往回走。
- 自动生成：`autogenerate` 能对比模型和当前库结构，生成候选迁移脚本。但它只是候选：默认不会处理数据迁移、不会判断字段语义变化，必须人工审一遍再上生产。
- 离线与在线：可以只生成 SQL 不执行（离线模式，给 DBA 评审），也可以直接连库执行（在线模式）。
- 多分支：多人同时建 revision 会分叉出多个 head，需要 `merge` 成一个，合并后同样要审。

```
# Alembic revision 骨架（配置骨架，不直接执行）：upgrade / downgrade 必须成对写
# （revision 说明：add user nickname）

revision = "a1b2c3d4e5f6"
down_revision = "0987654321ab"

from alembic import op
import sqlalchemy as sa


def upgrade():
    op.add_column("user", sa.Column("nickname", sa.String(64), nullable=True))


def downgrade():
    op.drop_column("user", "nickname")
```

### 1.4 三个工具怎么选

- 团队以 SQL 为主、库相对单一：Flyway，简单直接。
- 要跨库、要结构化 changelog、要标签上下文：Liquibase。
- Python + SQLAlchemy 项目：Alembic，基本是默认选项。
- 选型只看团队现状，别看功能列表：三个工具的核心能力（版本化、校验、历史记录）是一样的，差异在生态和写法。

## 2. Schema 演进原则：向后兼容

核心约束：新旧两版代码会在一段时间内共存（灰度、滚动发布），表结构必须同时兼容新旧代码。

### 2.1 只加不改

- 加列：加可空列，或者带默认值的列。别加非空无默认值列——旧数据填什么，库说了不算。
- 不删列、不改列类型、不改列含义：删列会让旧代码读到不存在的列；改类型可能让旧代码写入的值被截断或报错。
- 改名等于删 + 加：旧代码认旧名，新代码认新名，中间必须有一段双写期。

### 2.2 扩展-迁移-收缩三步

这是演进的标准套路，分三个发布做，别合成一步：

1. 扩展（Expand）：加新结构（新列、新表），新代码双写新旧两处，读仍走旧处。
2. 迁移（Migrate）：把旧数据回填到新结构，切读到新处，验证一致。
3. 收缩（Contract）：确认没有代码再用旧结构，删旧列、旧表。

每一步都是独立发布、可独立回滚。把三步合成一次发布，等于放弃了回滚点。

## 3. 多环境与 CI 集成

- 迁移脚本跟代码一起进版本库、一起评审：改表不是运维操作，是代码变更。
- 部署顺序：先跑迁移，再起新版服务。反过来（先起服务后迁移），新代码会在旧表上报错。
- 迁移失败即停：迁移脚本报错，部署就停住，别带病上线。失败的迁移要先定位（是脚本错、锁冲突、还是数据问题），修好再重跑，别手动在库里改历史表绕过去。
- 各环境独立历史表：开发、测试、生产各有自己的迁移记录，别共用一张表。
- 生产迁移先演练：拿生产的备份在 staging 恢复出来跑一遍，测耗时、测锁、测回填量，演练通过再上生产。

## 4. 常见坑

### 4.1 并发迁移锁

多实例同时启动（比如 K8s 滚动发布拉起多个 Pod），每个实例都想跑迁移。Flyway 和 Liquibase 都有锁表机制：第一个拿到锁的执行，其他的等。别自己写“先判断再执行”的逻辑，判断和执行之间有竞态，锁表才是正解。

### 4.2 大表 DDL

大表上加列、建索引、改类型都可能锁表或跑很久：

- 先在 staging 用同量级数据测耗时，别在生产上现测。
- 能用库原生 online DDL 的用 online DDL；MySQL 场景下业界常用 pt-osc、gh-ost 这类影子表工具，具体选哪个按库和版本定，以官方文档为准。
- 实在要在大表上改，选低峰期，备好回滚方案和监控（锁等待、慢查询、复制延迟）。

### 4.3 数据回填

- 分批：一次 UPDATE 几百万行会锁很久、拖垮复制。按主键分批（比如每次 1000 行），批间 sleep，给复制留喘息时间。
- 可断点续跑：回填脚本记进度（跑到哪个主键了），中断后能接着跑，别从头来。
- 幂等：回填逻辑跑两遍结果要一样，否则重跑一次就把数据算坏了。
- 回填和双写别混：双写期新写入的数据已经进新结构了，回填只补双写开始之前的数据，范围要划清楚。

### 4.4 其他坑

- 迁移脚本里写业务逻辑：迁移只做结构和数据搬运，别调业务接口、别发消息，业务逻辑一变，历史迁移就跑不通了。
- 已执行脚本被改：Flyway / Liquibase 的 checksum 就是防这个的。发现校验失败，先查是谁改了已上线脚本，恢复原脚本再说，别直接清历史表。
- 忘记给新列加索引：加了查询条件用的列却没加索引，上线后慢查询先炸出来，迁移评审时把索引列进检查项。

## 小技巧与冷知识

【小技巧】Flyway 脚本命名里的双下划线不能省：`V3__add_user_nickname.sql` 里版本号和描述之间是两个下划线，写成一个下划线时 Flyway 认不出版本号，启动直接报错。描述部分可以用下划线连词，但版本号后的分隔必须是 `__`；新脚本版本号别和已执行过的重复，跳号会被校验拦住。

【小技巧】已上线的 Flyway 脚本要改结构，别直接改原脚本，用新版本脚本叠加：已执行脚本的 checksum 已经被历史表记死，改原脚本会在所有环境触发校验失败。正确做法是写一个新版本迁移做这处调整，比如 `V5__fix_nickname_length.sql`；原脚本只在“还没执行过的环境”才能改，执行过的环境一律只追加。

【小技巧】给已有的老库第一次接 Flyway，先跑 `baseline` 而不是重放全部历史：老库表结构已经是现状，从 V1 开始重放会在已存在的表上报错。基线把现状定为某个版本，之后只跑基线之后的迁移；基线版本号要和代码库里第一个新脚本的版本号衔接上，否则会出现“基线定了 V5，第一个新脚本却是 V3”的断档。

【小技巧】Liquibase 的 changeset id 要全局唯一且别用“流水号”当 id：id 一旦写入 `DATABASECHANGELOG` 就成了历史记录的一部分，改 id 等于改身份，Liquibase 会把它当成一个没执行过的新 changeset 再跑一遍。id 里带上日期加序号，比如 `20261031-01`，比 `001`、`002` 更不容易撞；同一个 changeset 也别在不同分支里被复制粘贴出两份。

【小技巧】Alembic 的 `autogenerate` 生成的脚本先看 `downgrade()` 再看 `upgrade()`：自动生成经常只写好 `upgrade()`，`downgrade()` 留空或直接 `pass`，这样的脚本一上线就没法回滚。审脚本时先确认 downgrade 是不是真的能把 upgrade 的每一步反向做回去，重命名列、改类型这类操作最容易在 downgrade 里被漏掉。

【小技巧】多人同时建 Alembic revision 出现多 head 时，别直接删其中一个 revision 文件：删文件会让依赖链断掉，历史表里的记录对不上。正确做法是用 `alembic merge` 生成一个合并 revision，把两个 head 收成一个，再审一遍合并后的顺序；合并前先让两个人各自把自己的 revision 在本地跑通，确认都没有互相冲突的改动。

【小技巧】迁移脚本里给新列加默认值要分两步走，别一步到位：`ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'active'` 在大表上会触发全表重写，MySQL 8.0 之前尤其慢。先加可空列、再分批回填默认值、最后才把列改成 NOT NULL 并补默认值，三步分开发布，每一步都不锁全表；小表可以直接一步走，但别把小表的习惯带到大表上。

【小技巧】回填进度别记在脑子里，记在回填脚本自己的进度表里：回填脚本每跑完一批就把“当前最大主键”写进一张独立的进度表，中断后重启脚本先读进度表、从断点继续。进度表和回填目标表分开，别把进度记在目标表的某个字段里——回填失败回滚时进度字段也会被一起回滚，断点就丢了。

【小技巧】迁移评审时把“这条 DDL 会不会锁表”当成必查项：MySQL 里 `ADD COLUMN`、`ADD INDEX`、`ALTER COLUMN` 的锁行为各不相同，有的只锁元数据、有的要重建表。评审前先在 staging 用同量级数据跑一遍，看 `SHOW PROCESSLIST` 里有没有 `Waiting for table metadata lock` 和锁等待时长，别只看脚本语法对不对。

【小技巧】CI 里跑迁移别只跑“能不能成功”，跑完再跑一遍“从零重建”：测试环境定期删库重建、从 V1 开始全量跑迁移，能发现“某步迁移依赖了另一环境手工建的东西”这类隐性问题。只跑增量迁移的环境永远发现不了断档，全量重建是迁移链完整性的定期体检。

【小技巧】生产迁移前先在 staging 测“回滚脚本能不能跑”，而不是只测迁移本身：回滚脚本平时没人跑，出问题时才发现写错了等于没回滚。演练时迁移跑完马上跑一遍回滚，再跑一遍迁移，确认正反两个方向都能走通；回滚脚本里涉及删数据的操作要先确认数据已回填到别处，删了就回不来了。

【冷知识】Flyway 的名字来自“飞行路线”（flyway）这个词：候鸟迁徙的路线叫 flyway，作者用它比喻“数据库版本的迁徙路线”——每个版本化脚本就是路线上的一个站点，历史表记录走到了哪一站。Liquibase 的名字则是“液态的数据库”（liquid base），强调 schema 像液体一样流动演进，两个工具的名字都藏着各自的隐喻。

【冷知识】Alembic 的名字来自蒸馏器（alembic）：中世纪炼金术里的蒸馏装置，作者用它比喻“把数据库结构的变化蒸馏成一段段可执行的迁移”。SQLAlchemy 生态里这类隐喻不少，Alembic 的 revision 链就像蒸馏的每一步，提纯的是“从旧结构到新结构的路径”。

【冷知识】扩展-迁移-收缩（Expand-Migrate-Contract）这个模式最早来自 Martin Fowler 的演进式数据库设计：他把“先扩展、再迁移、最后收缩”写进《演进式数据库设计》一文，核心是把一次不兼容变更拆成三次兼容变更。这个模式比 Flyway、Liquibase 这些工具更老，工具只是把它落地的手段，模式本身不依赖任何工具。

【冷知识】MySQL 的 `ALTER TABLE` 在 5.6 之前几乎都会锁全表：5.6 引入 online DDL 后部分操作可以在线做，但“加列”这类操作在不同版本、不同引擎下的行为差别很大，pt-osc、gh-ost 这类影子表工具正是在这个背景下出现的——它们绕开原生 DDL，用“建影子表、同步增量、原子切换”来做在线改表。选工具前先确认当前 MySQL 版本的 online DDL 覆盖了哪些操作，别默认“新版本什么都能在线改”。

【冷知识】Flyway 的历史表默认名 `flyway_schema_history` 是可以改的：配置 `flyway.table` 就能指定别的表名，多租户或多应用共用一个库时，各自用不同的历史表可以避免互相干扰。但改表名之后，旧历史表里的记录不会自动迁移，新表名下 Flyway 会认为“什么都没执行过”，改名前要先把旧表重命名成新表名，别直接改配置就启动。

## 面试与自测

1. Flyway 的 checksum 校验是在防什么？发现校验失败应该怎么处理？
2. 为什么表结构演进要“只加不改”，灰度发布时旧代码会遇到什么问题？
3. 扩展-迁移-收缩三步为什么不能合成一次发布？

### 参考答案

1. 防已执行的迁移脚本被事后修改。历史表里存了每个脚本执行时的 checksum，启动时重算比对，不一致就报错停住，防止各环境表结构悄悄不一致。处理办法：先查是谁改了脚本，恢复原脚本；不要直接清历史表或改 checksum 绕过去。
2. 灰度期新旧两版代码共存，旧代码只认旧结构。删列会让旧代码读到不存在的列而报错，改类型可能让旧代码写入的值被截断或转换失败。只加可空列，旧代码不受影响，新代码用新列，两边都能跑。
3. 三步合成一次发布等于放弃了回滚点：扩展、迁移、收缩任何一步出问题，都只能整体回滚，代价大；分开后每一步都可独立发布、独立验证、独立回滚，收缩那步还能等确认无代码用旧结构后再做。
