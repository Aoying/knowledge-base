# OceanBase

> ao 在神农 e 贷法人版项目中实际使用的数据库。本篇只写公开可核实的通用知识，版本相关细节以官方文档为准；项目侧经验在《MySQL-数据库》的 OceanBase 小节里，本篇做体系化展开，不重复项目排障记录。

## 1. 核心概念

OceanBase 是原生分布式数据库：一份数据多副本分布在多台机器上，对应用呈现为**一个逻辑数据库**。与「MySQL + 分片中间件」路线的根本区别是分布能力长在数据库内部：应用不需要感知分片，扩容靠加节点和副本调度，而不是改代码、迁数据。

概念链条：**集群（Cluster）→ Zone（机房/可用区）→ OBServer（节点）→ 租户（Tenant）→ 数据库**。

- 每个 Zone 一份完整副本，副本间用 Paxos 协议同步，多数派提交才算成功，单 Zone 故障不丢数据。
- 存储引擎是 LSM-Tree（增量数据在内存、基线数据在磁盘，定期合并），与 InnoDB 的 B+ 树原地更新不同：写入友好，空间放大和合并开销是它的代价。

## 2. 租户与资源单元

租户是 OceanBase 最重要的管理概念，相当于「一台虚拟的数据库服务器」：

- 每个租户有独立的 CPU、内存、IO 配额，互不干扰；一个集群可以同时跑 MySQL 模式租户和 Oracle 模式租户（模式在建租户时定，之后不能改）。
- 资源以**资源单元（Unit）**分配：Unit 是打包的资源规格（若干 CPU + 若干内存），租户在每个 Zone 的节点上各放一个或多个 Unit。
- 日常影响：连接数、内存上限、慢 SQL 阈值都是**租户级**配置；排查「资源不够」先看自己租户的配额，不要拿整机指标下结论。

```sql
-- 在 MySQL 模式租户内常用的查看命令（具体系统视图以官方文档为准）
SHOW TENANT;                 -- 当前连接所属租户
SHOW DATABASES;
SHOW VARIABLES LIKE 'ob_trx_timeout';   -- OB 特有变量示例：事务超时
```

## 3. 分区（Partition）

单表数据量大时在 OB 内部分区解决，这与应用层分库分表是两个层次（详见《分库分表》与 OceanBase 的关系一节）：

- 常用分区类型：RANGE（按时间/范围，多用于流水、历史）、HASH（按键均匀分布）、KEY 分区。
- 分区键查询能命中**分区裁剪**时只扫相关分区；不带分区键的查询会扫全部分区并行执行，能跑但成本随分区数涨。
- 设计要点与分片键选择同理：选高频查询条件做分区键；时间类流水用 RANGE 按月/按年分区便于归档下线。

```sql
-- RANGE 分区示例（语法以官方文档为准）
CREATE TABLE t_flow (
  id BIGINT NOT NULL,
  create_time DATETIME NOT NULL,
  PRIMARY KEY (id, create_time)
) PARTITION BY RANGE (TO_DAYS(create_time)) (
  PARTITION p202609 VALUES LESS THAN (TO_DAYS('2026-10-01')),
  PARTITION p202610 VALUES LESS THAN (TO_DAYS('2026-11-01'))
);
```

## 4. MySQL 模式与原生 MySQL 的差异

兼容是「协议和常用语法兼容」，不是「行为完全一致」。开发时要留意的点（具体清单以官方文档的兼容性矩阵为准）：

- **对标版本**：MySQL 模式大致对标 MySQL 5.7 / 8.0 的语法子集；8.x 独有新语法、新函数在 OB 上不要默认可用。
- **JDBC**：可用 MySQL 驱动连接（官方也提供 obclient / OceanBase 驱动），连接串、字符集按 MySQL 习惯配置一般可通。
- **自增列**：分布式下自增值保证唯一和大体有序，**不保证连续、无空洞**，行为与单机 MySQL 不同，业务不能依赖自增连续性。
- **事务**：单分区事务与跨分区事务的实现路径不同，跨分区大事务的成本和超时行为与单机不同；事务超时有 `ob_trx_timeout` 等 OB 特有变量控制（以官方文档为准）。
- **DDL**：在线 DDL 的实现机制不同，大表改结构的时间和锁影响要在测试环境实测，不要套用 MySQL 的经验值。
- **系统视图与变量**：`SHOW` 命令大体兼容，但性能视图、参数体系是 OB 自己的；MySQL 的 `performance_schema` / `information_schema` 内容在 OB 上是映射实现，字段可用性以官方文档为准。
- **执行计划**：`EXPLAIN` 照常使用，但分布式计划会出现数据分发、并行等算子，读计划时先看有没有全分区扫描，思路与单机一致（见《MySQL 索引与执行计划》）。

## 5. 日常开发注意事项

1. **SQL 先在 OB 测试环境跑**：同一套 SQL 在开发用的 MySQL 上通过，不等于在 OB 上通过，特别是窗口函数、复杂子查询、DDL 和系统函数。
2. **主键设计**：优先用雪花 ID 等有序全局 ID；依赖数据库自增生成业务单号的做法不要带进 OB。
3. **大事务拆小**：批量更新分批提交（如每 500～1000 行一批），避免跨分区长事务触发超时和回滚成本放大。
4. **更新要带分区键/主键**：不带条件的全表更新在分布式下代价远高于单机，评审 SQL 时把这条当红线。
5. **别在 OB 上再叠一层分片中间件**：分区表能解决的不要用 ShardingSphere 再拆，理由见《分库分表》。
6. **参数与限制查租户级文档**：如单次结果集、事务超时、连接上限等，先确认是租户参数还是集群参数再改。

## 6. 常见坑

- 拿单机 MySQL 的锁行为写并发代码：OB 的锁与事务实现不同，`SELECT ... FOR UPDATE` 的实际范围要实测验证。
- 用 `information_schema` 的 MySQL 字段做自动化脚本，上线 OB 后取不到值——改用 OB 的系统视图（以官方文档为准）。
- 忽略租户配额：压测时先顶满的是租户 Unit 的 CPU/内存，不是整机，监控要看租户维度。

## 7. 生产深度：连接层、同步与租户运维

- **OBProxy 连接层**：生产应用连 OBProxy（ODP，默认端口 2883）而不是直连单个 OBServer（直连默认 2881）。OBProxy 按分区位置把 SQL 路由到持有数据的节点，减少跨节点转发；同时屏蔽节点增减、宕机、Unit 分布与合并等后端变化，连接层不用跟着改。连接串账号格式为 `用户名@租户名#集群名`（直连时为 `用户名@租户名`）。生产只走 OBProxy，不直连单节点。
- **OMS / CDC**：OMS（OceanBase 迁移服务）做全量迁移 + 增量同步；CDC 增量订阅走日志代理订阅增量日志，下游接 Kafka、数仓或搜索。落地盯三点：位点管理（断点续拉、位点失效后的重建口径）、DDL 同步（表结构变更要同步演进，否则下游先坏）、延迟监控（订阅延迟先于业务感知告警）。
- **全局索引与分区键约束**：本地索引与分区同分布，查询带分区键时就近；全局索引自带分区规则，索引数据与主表数据可能不在同一节点，读写要多一次 RPC，严重时走分布式事务，维护成本高于本地索引，能少用就少用。硬约束：分区表的主键与唯一键中至少要含一个分区键字段，本地唯一索引必须含分区键；不带分区键的查询走全分区，建表与建索引时先对齐分区键。
- **租户运维查看清单**：租户配额（Unit 的 CPU/内存数、各 Zone 分布）；节点与副本状态（`oceanbase.DBA_OB_SERVERS` 看节点清单）；连接数与慢 SQL（看租户维度，不要拿整机指标下结论）；合并进度与空间水位（LSM 合并跟不上时空间放大、写入抖动）；租户级参数变更前先确认是租户参数还是集群参数再改。

## 8. 副本、选举与租户资源定量

> 本节数字分两类：官方文档默认值（注明来源与核验日期）与演示算例（明确标注“假设”）。版本口径为 OceanBase 4.x，未注明版本的默认值以 V4.2.1 文档为准；V4.3.5 有不同表述处另行注明。

### 8.1 副本与多数派：容几个故障是算出来的

一个分区（Partition）的多个副本组成一个 Paxos 组，写操作要得到多数派（quorum）确认才算提交成功。多数派的算术是：

```text
quorum = floor(n / 2) + 1，可容忍故障数 = n - quorum
```

| 副本数 n | 多数派 quorum | 可容忍故障数 |
| --- | --- | --- |
| 3 | 2 | 1 |
| 5 | 3 | 2 |

- **单 Zone 故障不丢数据的条件**：副本必须跨 Zone 分布，且故障后剩余副本数仍 ≥ quorum。3 副本部署在 3 个 Zone 时，一个 Zone 故障后剩 2 个副本，正好等于 quorum，可以继续读写、已提交数据不丢；如果 3 个副本全放在同一个 Zone 里，一个 Zone 故障就丢全部副本，多数派算术救不了分布错误。
- **按副本数计，不按 Zone 数计**：5 副本容 2 个副本故障，不等于容 2 个 Zone 故障——5 个副本分布在 3 个 Zone 时，一个 Zone 里可能放 2 个副本，一个 Zone 故障就可能同时丢 2 个副本。评估 Zone 级容灾要先看副本在各 Zone 的实际分布，再套多数派算术。

**可用性换算例（全部为假设，演示量级用）**：假设每节点故障相互独立、年故障率均为 1%，则一年内丢多数派的概率为：单节点 1%；3 副本约 0.0298%（约单节点的 1/33.6）；5 副本约 0.000985%（约 3 副本的 1/30.3）。计算式为二项分布求和：P(丢多数派) = Σ C(n,k)·p^k·(1-p)^(n-k)，k 从 quorum 取到 n。真实故障往往相关（同机房断电、批量升级、同一批次硬件），实际概率高于这个独立模型，独立假设只用于比较 3 副本与 5 副本的量级差异，不可当作 SLA 承诺。

### 8.2 选举与租期：机制讲清，默认值官方未公开

- **选举**：每个 Paxos 组有一个主副本（Leader），只接受主副本的写。主副本宕机或失联后，剩余副本通过 Paxos 选举产生新主副本；选举期间该分区的写会阻塞，直到新主副本选出。选举要多数派参与，丢多数派的分区选不出新主副本，写一直不可用——这就是 8.1 的多数派算术直接决定可用性的地方。
- **租期（Lease）**：主副本持有租期，在租期内其他副本不会发起选举，避免“主副本只是网络抖动、还没死”时出现两个主副本（脑裂）。租期与选举超时是两个不同的量：选举超时决定“多久没收到主副本心跳就发起选举”，租期决定“主副本的写权限在多长时间内有效”；调大选举超时可以减少网络抖动引发的误选举，但会拉长真实故障后的恢复时间，两者是 trade-off，不是越大越好。
- **默认值：官方文档未公开默认值。**本次核对的 OceanBase 官方文档（V4.2.1《Reference — System management》，全文检索“election”）只提到选举线程、选举模块日志，未给出选举超时或租期的参数名与默认值；V4.3.5 同类文档同样未给出。因此本节不写任何选举超时/租期的具体毫秒数，生产调优以 `SHOW PARAMETERS` 实测当前集群取值为准，不要引用网传数字。
- **时钟偏差（待验证）**：OceanBase 社区问答引用官方部署要求，称各节点间时钟偏差需控制在 2 秒以内，否则可能影响选举、导致无主副本或脑裂。该数值未在本次核对的官方文档正文中找到原文，标记为待验证；部署时仍按“配 NTP/chrony、避免时钟跳变”的官方要求做，不要等数值核实了再配时间同步。

### 8.3 租户 Unit 内存定量：总量、MemStore 与合并水位

**Unit 内存换算**：租户在每个 Zone 的内存 = 该 Zone 的 Unit 数 × 每 Unit 内存；三 Zone 部署时集群为该租户分配的总内存 = 3 × 每 Zone 内存。算例：每 Unit 8 GB，每 Zone 2 个 Unit，则每 Zone 租户内存 16 GB，三 Zone 共分配 48 GB。注意口径：三个 Zone 各存一份完整副本，48 GB 是“三个 Zone 的分配总量”，不是“租户能用的 48 GB 容量”；单 Zone 视角的可用内存仍是 16 GB，扩容先算每 Zone 够不够，不要被总量迷惑。

**MemStore 占比与冻结水位**：写入先进入内存中的 MemTable（MemStore），达到水位后触发冻结（freeze），再转储为 SSTable（小合并）；多次小合并攒够次数后触发大合并。官方公式与默认值（V4.2.1 文档）：

```text
memstore_limit = 租户内存 × memstore_limit_percentage（默认值 50）
冻结水位 = memstore_limit × freeze_trigger_percentage（默认值 20）
```

算例（租户每 Zone 内存 16 GB）：memstore_limit = 16 × 50% = 8 GB，冻结水位 = 8 × 20% = 1.6 GB，即活动 MemTable 用到 1.6 GB 就触发冻结。版本差异注意：V4.3.5 文档称，未显式配置时 MemStore 占比按租户内存自适应——租户内存 ≤ 8 GB 时取 40%，> 8 GB 时取 50%。按此规则，8 GB 租户的 memstore_limit = 8 × 40% = 3.2 GB，冻结水位 = 3.2 × 20% = 0.64 GB。两个版本的默认值表述不同，排障时以所用版本的 `SHOW PARAMETERS LIKE 'memstore_limit_percentage'` 实测值为准。

**大合并触发**：`enable_major_freeze` 默认值为 True（开启全局大合并）；`major_compact_trigger`（触发一次大合并所需的小合并次数）V4.2.1 文档默认值为 0，文档示例建议值 50。默认值 0 的确切语义（是否表示“按其他条件触发”）待验证，本节不展开；调大合并相关参数前先确认当前集群的实际取值与合并进度，不要凭默认值推断行为。

### 8.4 分区数定量：分区越多，不带分区键的查询越贵

承接 §3 的分区裁剪：带分区键的查询只扫相关分区，不带分区键的查询扫全部分区。演示算例（全部为假设）：一张 1200 万行的流水表，按月 RANGE 分区。

| 分区方案 | 分区数 | 每分区行数 | 带分区键查 1 个月扫多少行 | 不带分区键全扫行数 |
| --- | --- | --- | --- | --- |
| 按月分 1 年 | 12 | 100 万 | 100 万 | 1200 万 |
| 按天分 120 天 | 120 | 10 万 | 10 万 | 1200 万 |

- **带分区键时分区越细越好**：查 1 个月的数据，120 分区方案只扫 10 万行，是 12 分区方案的 1/10。
- **不带分区键时行数不变，固定开销随分区数线性涨**：两种方案全扫都是 1200 万行，但每个分区都有打开、调度、合并结果的固定开销。假设每分区固定开销 5 ms（假设值，仅用于演示线性关系），12 分区全扫固定开销 60 ms，120 分区全扫 600 ms，是前者的 10 倍。分区数翻 10 倍，不带分区键查询的固定开销也翻 10 倍。
- **结论**：分区数不是越多越好。分区粒度的选择要看查询模式：高频查询都带分区键时可以分细一点；常有不带分区键的全表查询时，分区过细会把每次查询的固定开销放大，分区数要与查询模式一起定，不要只按归档方便定。

### 8.5 边界条件

1. **多数派只保“提交不丢”，不保“读不堵”**：多数派保证的是已提交的写不丢失，不保证故障期间读一定能走。强一致读（`ob_read_consistency = STRONG`，默认值）只读主副本，主副本所在的 Zone 故障、选举完成前，强一致读同样阻塞；放宽为 WEAK 读从副本才能继续读，但读到的数据可能落后主副本几个事务。
2. **选举超时与网络分区的关系**：网络分区把多数派隔在两边时，少数派一侧选不出新主副本、写不可用，这是 Paxos 保证不脑裂的代价，不是故障；把选举超时调得过小，网络抖动就会频繁触发误选举、主副本来回切换，写入抖动比故障本身更伤业务。
3. **Unit 内存是上限，不是预留**：租户 Unit 的内存是“最多能用到这么多”，不是“一创建就占满这么多”；租户实际内存占用看 `GV$OB_MEMORY` 等视图。反过来，Unit 内存也是硬上限——租户内存打满时先被限流、再报错，不会自动借用其他租户或整机的空闲内存。
4. **MemStore 水位是触发点，不是容量**：冻结水位（memstore_limit × 20%）一到就触发冻结，不等于 MemStore 只能用到这么多；冻结后转储需要磁盘与 IO 资源，转储跟不上时 MemStore 会继续涨，直到触发写入限流。写入抖动先分清是冻结频繁、转储跟不上还是大合并在抢 IO，再决定调内存还是错峰。
5. **分区数不是越多越好**：分区数涨了，带分区键的查询受益、不带分区键的查询固定开销线性涨（8.4 算例：12 分区 60 ms → 120 分区 600 ms，假设值）；分区数还影响建表、DDL 与合并的元数据规模，超大分区数本身就是运维负担。
6. **本节所有换算都依赖“假设”成立**：可用性算例假设节点故障相互独立、年故障率 1%，真实故障相关，算出的 0.0298%/0.000985% 只是量级比较；分区算例假设每分区固定开销 5 ms，真实开销随硬件、并发与数据分布变化。拿本节数字做容量规划前，先用自己集群的实测值替换假设值。

> 来源（核验日期 2026-11-08）：`memstore_limit_percentage` 默认值 50、`freeze_trigger_percentage` 默认值 20、`major_compact_trigger` 默认值 0、`enable_major_freeze` 默认值 True，均见 OceanBase 官方文档 V4.2.1《Reference — System management》：<https://obportal.s3.ap-southeast-1.amazonaws.com/doc/product_pdf/oceanbase-database/144/OceanBase-Database-V4.2.1-Reference--System-management.pdf>；MemStore 自适应占比（租户内存 ≤ 8 GB 取 40%、> 8 GB 取 50%）与冻结公式见 V4.3.5《Reference — System management》：<https://obportal.s3.ap-southeast-1.amazonaws.com/doc/product_pdf/oceanbase-database/213/OceanBase-Database-V4.3.5-Reference--System-management.pdf>；选举超时/租期默认值未在上述官方文档中找到，写作“官方文档未公开默认值”；时钟偏差 2 秒引自 OceanBase 社区问答（ask.oceanbase.com），待以官方部署文档复核。

## 小技巧与冷知识

【小技巧】读一致性可以按需放宽：默认 `ob_read_consistency` 是 STRONG（强一致读，只读主副本），对延迟不敏感的统计、报表类查询可以在会话级改成 WEAK，走从副本读，减轻主副本压力。但 WEAK 读到的是副本上已提交的数据，可能落后主副本几个事务，刚写完马上读的场景别用；只在“读旧一点没关系”的查询上放宽。

【小技巧】查慢 SQL 别只看业务日志，用 OB 自带的 SQL 审计视图：`GV$OB_SQL_AUDIT` 里按租户、按 SQL 文本能看到执行次数、平均耗时和返回行数，定位“哪条 SQL 在拖慢租户”比翻应用日志快。注意它按租户隔离，一个租户只能看到自己的 SQL，排查时先确认连的是哪个租户，别拿 sys 租户的视角查业务租户的慢 SQL。

【小技巧】大批量导入别一条一条 INSERT，优先用旁路导入：OceanBase 的旁路导入（direct load）绕过 SQL 层和事务，直接把数据写成 SSTable 落盘，适合初始化、历史数据回填这类“一次导几百万行”的场景。普通 INSERT 走完整事务路径，批量导入时又慢又容易触发事务超时；导入前先确认目标表没有触发器和外键这类旁路导入不支持的约束。

【小技巧】想确认一条 SQL 有没有命中分区裁剪，看执行计划里的分区信息而不是只看耗时：EXPLAIN 输出里如果只列出少量分区，说明裁剪生效；列出全部的分区间隔，说明没带分区键在全分区扫。排查“这条 SQL 怎么突然变慢”时，先看分区数有没有变多——分区数涨了、查询又没带分区键，成本是跟着分区数一起涨的。

【小技巧】租户资源不够用时先查 Unit 分布再提扩容：`DBA_OB_UNITS` 能看到租户在每个 Zone 各放了几个 Unit、每个 Unit 的 CPU 和内存数。扩容不只是“加内存”，还要看新 Unit 落在哪个 Zone、副本分布是否均匀；单 Zone 的 Unit 加满了、别的 Zone 还有空闲，瓶颈在分布不在总量。

【小技巧】集群里有个特殊的 sys 租户，日常业务别连它：sys 租户是 OceanBase 自己的管理租户，建租户、调参数、看集群状态都在它里面做，业务数据都放在业务租户里。排查问题时先确认当前连接是哪个租户——连错租户，查到的表、参数、慢 SQL 全是另一个租户的，排障方向一开始就歪了。

【小技巧】参数分三级，先认清再改：OceanBase 的参数有集群级、租户级和会话级，`SHOW PARAMETERS` 看到的是当前租户视角的值，改租户级参数用 `ALTER SYSTEM SET ... TENANT = '租户名'`，改会话级只影响当前连接。改之前先确认这个参数是哪一级——在会话里改集群级参数不会生效，在租户里改集群级参数会改到所有租户。

【小技巧】出问题先跑官方诊断工具 obdiag 再手动翻日志：obdiag 是 OceanBase 官方的诊断工具，能一键收集节点日志、配置和性能快照，还能按场景做巡检。自己翻日志容易只看到报错的最后一行，obdiag 收集的是“报错前后一段时间”的完整上下文，提工单、找 DBA 协助时先把 obdiag 的采集包准备好。

【小技巧】备份恢复走 OB 自己的物理备份，别只靠 mysqldump 逻辑导出：OceanBase 支持把数据备份到对象存储或 NFS，恢复时按备份集 + 归档日志做时间点恢复，适合“整库丢了、要回到某天某时”的场景。mysqldump 适合小表、跨库迁移，大库全量导出又慢又容易超时，两种备份的用途不一样，恢复演练时按真实场景各练一次。

【小技巧】DDL 之前先看租户的合并状态：LSM 结构下大表改结构要和后台合并抢资源，合并正忙时跑大 DDL 容易互相拖慢。生产改表前先确认合并进度正常、磁盘水位有余量，避开业务高峰；改完再看一眼合并有没有被 DDL 顶住，合并长期跟不上时写入会先抖动、再被限流。

【冷知识】OceanBase 出身支付宝，2010 年立项：当时淘宝收藏夹的业务量冲破单机 MySQL 上限，阳振坤团队从零写了这套分布式数据库，最早只服务支付宝内部。它的设计起点就是“金融级强一致 + 分布式扩展”，不是先做通用数据库再补一致性，这也解释了为什么它默认走 Paxos 多数派提交、而不是最终一致。

【冷知识】OceanBase 在 2019 年登顶 TPC-C：TPC-C 是衡量联机事务处理能力的行业基准，OceanBase 当年刷新了这项纪录，此后又多次刷新。榜单成绩本身不等于你的业务也能跑出这个数——TPC-C 的模型是标准化的仓储订单，真实业务的分区设计、事务大小、热点分布才是决定性能的关键，跑分只能证明引擎上限。

【冷知识】OceanBase 2021 年开源了社区版：核心代码在 GitHub 上公开，社区版和企业版同源，MySQL 模式和 Oracle 模式都在开源范围内。看源码、提 Issue、自己编译部署都可以走社区版；但生产用的 OCP 运维平台、OMS 迁移服务这些配套工具是另外的商业组件，开源代码库里没有。

【冷知识】OceanBase 4.0 提出了“单机分布式一体化”：同一个安装包既能单机部署、也能多节点分布式部署，单机模式下就是一个节点跑全部功能，扩容时再加节点变成分布式。不用像早期版本那样“要么单机、要么集群”二选一，小项目可以先单机跑起来，等数据量上来了再扩成分布式，中间不用换数据库。

【冷知识】LSM-Tree 的“合并”在 OB 里分两级：内存里的增量数据先转储成小的 SSTable（小合并/转储），多个小 SSTable 再定期合并成大的基线 SSTable（大合并）。转储是轻量操作、频率高，大合并是重操作、频率低；写入抖动多半是转储或大合并在抢 IO，排查时先分清是哪一级合并在忙，再决定是调内存配额还是错峰。

【冷知识】OB 的租户名和集群名都写进连接串，拼错一个字就连到别的租户：账号格式 `用户名@租户名#集群名` 里，租户名和集群名都是连接身份的一部分。开发、测试、生产各有一套集群和租户时，连接串只差一个字的后果不是“连不上”，而是“连上了错误的租户”，上线前对连接串做一次逐字核对，比事后查“数据怎么跑到测试库去了”便宜得多。

## 面试与自测

1. 租户在 OceanBase 里是什么？为什么排查“资源不够”要先看租户配额而不是整机指标？
2. 分区查询带分区键和不带分区键有什么区别？分区表的主键、唯一键与本地唯一索引对分区键有什么硬约束？
3. 生产应用为什么要连 OBProxy 而不是直连 OBServer？连接串的账号格式各是什么？
4. 3 副本的 OceanBase 集群容几个节点故障？为什么说“5 副本容 2 个故障”不等于“容 2 个 Zone 故障”？租户每 Zone 内存 16 GB 时，MemStore 的冻结水位是多少（按 V4.2.1 默认值）？

### 参考答案

1. 租户相当于“一台虚拟的数据库服务器”，每个租户有独立的 CPU、内存、IO 配额，互不干扰；一个集群可同时跑 MySQL 模式租户和 Oracle 模式租户，模式在建租户时定、之后不能改。连接数、内存上限、慢 SQL 阈值都是租户级配置，所以排查“资源不够”先看自己租户的配额，不要拿整机指标下结论；压测时先顶满的也是租户 Unit 的 CPU/内存，不是整机。
2. 分区键查询能命中分区裁剪时只扫相关分区；不带分区键的查询会扫全部分区并行执行，能跑但成本随分区数涨。硬约束：分区表的主键与唯一键中至少要含一个分区键字段，本地唯一索引必须含分区键；不带分区键的查询走全分区，建表与建索引时先对齐分区键。另外全局索引自带分区规则，索引数据与主表数据可能不在同一节点，读写要多一次 RPC，严重时走分布式事务，维护成本高于本地索引，能少用就少用。
3. 生产应用连 OBProxy（ODP，默认端口 2883）而不是直连单个 OBServer（直连默认 2881）。OBProxy 按分区位置把 SQL 路由到持有数据的节点，减少跨节点转发；同时屏蔽节点增减、宕机、Unit 分布与合并等后端变化，连接层不用跟着改。连接串账号格式为 `用户名@租户名#集群名`（直连时为 `用户名@租户名`）；生产只走 OBProxy，不直连单节点。
4. 3 副本时多数派 quorum = floor(3/2)+1 = 2，可容忍 3-2 = 1 个副本故障；5 副本时 quorum = 3，可容忍 2 个副本故障。5 副本容的是 2 个“副本”故障，不是 2 个 Zone 故障——5 个副本分布在 3 个 Zone 时，一个 Zone 里可能放 2 个副本，一个 Zone 故障就可能同时丢 2 个副本。租户每 Zone 16 GB 时，memstore_limit = 16 × 50% = 8 GB，冻结水位 = 8 × 20% = 1.6 GB。
