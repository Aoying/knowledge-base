# OceanBase

> ao 在神农 e 贷法人版项目中实际使用的数据库。本篇只写公开可核实的通用知识，版本相关细节以官方文档为准；项目侧经验在《MySQL-数据库》的 OceanBase 小节里，本篇做体系化展开，不重复项目排障记录。

## 1. 核心概念

OceanBase 是原生分布式数据库：一份数据多副本分布在多台机器上，对应用呈现为**一个逻辑数据库**。与「MySQL + 分片中间件」路线的根本区别是分布能力长在数据库内部：应用不需要感知分片，扩容靠加节点和副本调度，而不是改代码、迁数据。

概念链条：**集群（Cluster）→ Zone（机房/可用区）→ OBServer（节点）→ 租户（Tenant）→ 数据库**。

- 每个 Zone 一份完整副本，副本间用 Paxos 协议同步，多数派提交才算成功，单 Zone 故障不丢数据。
- 存储引擎是 LSM-Tree（增量数据在内存、基线数据在磁盘，定期合并），与 InnoDB 的 B+ 树原地更新不同：写入友好，空间放大和合并开销是它的代价。

## 2. 租户与资源单元

租户是 OceanBase 最重要的管理概念，相当于「一台虚拟的数据库服务器」：

- 每个租户有独立的 CPU、内存、IO 配额，互不干扰；一个集群可以同时跑 MySQL 模式租户和 Oracle 模式租户（模式在建租户时定，之后不能改）。
- 资源以**资源单元（Unit）**分配：Unit 是打包的资源规格（若干 CPU + 若干内存），租户在每个 Zone 的节点上各放一个或多个 Unit。
- 日常影响：连接数、内存上限、慢 SQL 阈值都是**租户级**配置；排查「资源不够」先看自己租户的配额，不要拿整机指标下结论。

```sql
-- 在 MySQL 模式租户内常用的查看命令（具体系统视图以官方文档为准）
SHOW TENANT;                 -- 当前连接所属租户
SHOW DATABASES;
SHOW VARIABLES LIKE 'ob_trx_timeout';   -- OB 特有变量示例：事务超时
```

## 3. 分区（Partition）

单表数据量大时在 OB 内部分区解决，这与应用层分库分表是两个层次（详见《分库分表》与 OceanBase 的关系一节）：

- 常用分区类型：RANGE（按时间/范围，多用于流水、历史）、HASH（按键均匀分布）、KEY 分区。
- 分区键查询能命中**分区裁剪**时只扫相关分区；不带分区键的查询会扫全部分区并行执行，能跑但成本随分区数涨。
- 设计要点与分片键选择同理：选高频查询条件做分区键；时间类流水用 RANGE 按月/按年分区便于归档下线。

```sql
-- RANGE 分区示例（语法以官方文档为准）
CREATE TABLE t_flow (
  id BIGINT NOT NULL,
  create_time DATETIME NOT NULL,
  PRIMARY KEY (id, create_time)
) PARTITION BY RANGE (TO_DAYS(create_time)) (
  PARTITION p202609 VALUES LESS THAN (TO_DAYS('2026-10-01')),
  PARTITION p202610 VALUES LESS THAN (TO_DAYS('2026-11-01'))
);
```

## 4. MySQL 模式与原生 MySQL 的差异

兼容是「协议和常用语法兼容」，不是「行为完全一致」。开发时要留意的点（具体清单以官方文档的兼容性矩阵为准）：

- **对标版本**：MySQL 模式大致对标 MySQL 5.7 / 8.0 的语法子集；8.x 独有新语法、新函数在 OB 上不要默认可用。
- **JDBC**：可用 MySQL 驱动连接（官方也提供 obclient / OceanBase 驱动），连接串、字符集按 MySQL 习惯配置一般可通。
- **自增列**：分布式下自增值保证唯一和大体有序，**不保证连续、无空洞**，行为与单机 MySQL 不同，业务不能依赖自增连续性。
- **事务**：单分区事务与跨分区事务的实现路径不同，跨分区大事务的成本和超时行为与单机不同；事务超时有 `ob_trx_timeout` 等 OB 特有变量控制（以官方文档为准）。
- **DDL**：在线 DDL 的实现机制不同，大表改结构的时间和锁影响要在测试环境实测，不要套用 MySQL 的经验值。
- **系统视图与变量**：`SHOW` 命令大体兼容，但性能视图、参数体系是 OB 自己的；MySQL 的 `performance_schema` / `information_schema` 内容在 OB 上是映射实现，字段可用性以官方文档为准。
- **执行计划**：`EXPLAIN` 照常使用，但分布式计划会出现数据分发、并行等算子，读计划时先看有没有全分区扫描，思路与单机一致（见《MySQL 索引与执行计划》）。

## 5. 日常开发注意事项

1. **SQL 先在 OB 测试环境跑**：同一套 SQL 在开发用的 MySQL 上通过，不等于在 OB 上通过，特别是窗口函数、复杂子查询、DDL 和系统函数。
2. **主键设计**：优先用雪花 ID 等有序全局 ID；依赖数据库自增生成业务单号的做法不要带进 OB。
3. **大事务拆小**：批量更新分批提交（如每 500～1000 行一批），避免跨分区长事务触发超时和回滚成本放大。
4. **更新要带分区键/主键**：不带条件的全表更新在分布式下代价远高于单机，评审 SQL 时把这条当红线。
5. **别在 OB 上再叠一层分片中间件**：分区表能解决的不要用 ShardingSphere 再拆，理由见《分库分表》。
6. **参数与限制查租户级文档**：如单次结果集、事务超时、连接上限等，先确认是租户参数还是集群参数再改。

## 6. 常见坑

- 拿单机 MySQL 的锁行为写并发代码：OB 的锁与事务实现不同，`SELECT ... FOR UPDATE` 的实际范围要实测验证。
- 用 `information_schema` 的 MySQL 字段做自动化脚本，上线 OB 后取不到值——改用 OB 的系统视图（以官方文档为准）。
- 忽略租户配额：压测时先顶满的是租户 Unit 的 CPU/内存，不是整机，监控要看租户维度。

## 7. 生产深度：连接层、同步与租户运维

- **OBProxy 连接层**：生产应用连 OBProxy（ODP，默认端口 2883）而不是直连单个 OBServer（直连默认 2881）。OBProxy 按分区位置把 SQL 路由到持有数据的节点，减少跨节点转发；同时屏蔽节点增减、宕机、Unit 分布与合并等后端变化，连接层不用跟着改。连接串账号格式为 `用户名@租户名#集群名`（直连时为 `用户名@租户名`）。生产只走 OBProxy，不直连单节点。
- **OMS / CDC**：OMS（OceanBase 迁移服务）做全量迁移 + 增量同步；CDC 增量订阅走日志代理订阅增量日志，下游接 Kafka、数仓或搜索。落地盯三点：位点管理（断点续拉、位点失效后的重建口径）、DDL 同步（表结构变更要同步演进，否则下游先坏）、延迟监控（订阅延迟先于业务感知告警）。
- **全局索引与分区键约束**：本地索引与分区同分布，查询带分区键时就近；全局索引自带分区规则，索引数据与主表数据可能不在同一节点，读写要多一次 RPC，严重时走分布式事务，维护成本高于本地索引，能少用就少用。硬约束：分区表的主键与唯一键中至少要含一个分区键字段，本地唯一索引必须含分区键；不带分区键的查询走全分区，建表与建索引时先对齐分区键。
- **租户运维查看清单**：租户配额（Unit 的 CPU/内存数、各 Zone 分布）；节点与副本状态（`oceanbase.DBA_OB_SERVERS` 看节点清单）；连接数与慢 SQL（看租户维度，不要拿整机指标下结论）；合并进度与空间水位（LSM 合并跟不上时空间放大、写入抖动）；租户级参数变更前先确认是租户参数还是集群参数再改。

## 面试与自测

1. 租户在 OceanBase 里是什么？为什么排查“资源不够”要先看租户配额而不是整机指标？
2. 分区查询带分区键和不带分区键有什么区别？分区表的主键、唯一键与本地唯一索引对分区键有什么硬约束？
3. 生产应用为什么要连 OBProxy 而不是直连 OBServer？连接串的账号格式各是什么？

1. 租户相当于“一台虚拟的数据库服务器”，每个租户有独立的 CPU、内存、IO 配额，互不干扰；一个集群可同时跑 MySQL 模式租户和 Oracle 模式租户，模式在建租户时定、之后不能改。连接数、内存上限、慢 SQL 阈值都是租户级配置，所以排查“资源不够”先看自己租户的配额，不要拿整机指标下结论；压测时先顶满的也是租户 Unit 的 CPU/内存，不是整机。
2. 分区键查询能命中分区裁剪时只扫相关分区；不带分区键的查询会扫全部分区并行执行，能跑但成本随分区数涨。硬约束：分区表的主键与唯一键中至少要含一个分区键字段，本地唯一索引必须含分区键；不带分区键的查询走全分区，建表与建索引时先对齐分区键。另外全局索引自带分区规则，索引数据与主表数据可能不在同一节点，读写要多一次 RPC，严重时走分布式事务，维护成本高于本地索引，能少用就少用。
