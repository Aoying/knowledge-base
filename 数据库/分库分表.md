# 分库分表

## 1. 核心概念

单机数据库有三道硬天花板：**容量**（单表数据量过大后 B+ 树层数增加、索引效率下降，经验值单表 2000 万行左右开始劣化）、**连接与 CPU**（单实例连接数、并发处理能力有限）、**IO 吞吐**（单机磁盘写入上限）。分库分表就是把数据按规则拆到多个库/表中，把压力分摊到多台机器。

四个概念先分清：

| 拆法 | 做法 | 解决什么 |
|---|---|---|
| 分表（垂直） | 一张宽表按列拆成多张表 | 冷热字段分离、大字段拖慢查询 |
| 分表（水平） | 同结构多张表，按行分散 | 单表数据量过大 |
| 分库（垂直） | 按业务拆库（订单库、用户库） | 业务隔离、微服务拆分的前置 |
| 分库（水平） | 同结构多个库 + 库内分表 | 容量 + 并发一起解决 |

**什么时候才该拆**：单表行数逼近千万级且增长可预期、单机存储/连接/CPU 已成瓶颈、归档冷数据和加索引加缓存都解决不了。数据量不大就拆，只会把简单问题复杂化——分布式事务、跨片查询、扩容迁移的成本都是真金白银。

## 2. 基础知识

### 分片策略

| 策略 | 规则 | 优点 | 缺点 | 典型场景 |
|---|---|---|---|---|
| 范围分片 | 按 ID/时间区间，如每 500 万行一表、按月分表 | 范围查询友好、扩容只需加新片 | 易热点（新数据全打到最新片） | 日志、流水、按时间归档 |
| 哈希取模 | `hash(分片键) % N` | 数据均匀、无热点 | 扩容要全量重新分布 | 用户、订单等均匀访问 |
| 一致性哈希 | 哈希环 + 虚拟节点 | 扩容只迁移环上一段数据 | 实现复杂、均匀性依赖虚拟节点数 | 缓存分片、自研中间件 |
| 列表/枚举 | 按枚举值，如地区、租户 | 隔离性好、便于按维度下线 | 枚举值分布不均会倾斜 | 多租户、按地区建站 |

生产里最常见的是**哈希取模 + 预留扩容空间**：一次规划到位，比如直接建 1024 张逻辑分表映射到 16 个物理表，扩容时只调整映射、不动数据。

### 分片键选择

分片键是分库分表最重要的一次决策，选错了后面全是补丁。原则：

1. **高频查询条件**：绝大多数查询都带这个字段，否则每次查都要广播全部分片。
2. **分布均匀**：避免倾斜，如按状态分片会导致「进行中」那片爆掉。
3. **稳定不变**：分片键一旦变更等于数据搬家，如手机号会换绑，不如用用户 ID。
4. **基数足够大**：性别这种只有两个值的字段没有分片意义。

经典案例：电商订单表按 `user_id` 分片，用户查自己的订单是单片直达；但商家按 `order_id` 查就跨片了。解法是**冗余一份按商家维度分片的表**（空间换路由），或用异构索引表/基因法。没有万能分片键，只有对主要查询路径最友好的分片键。

## 3. 进阶知识

### 跨分片查询与聚合

跨片是分片后最痛的部分，常见手段按代价从低到高：

- **绑定表（广播小表）**：字典、配置类小表在每个分片都存一份，join 时本地完成。ShardingSphere 里叫绑定表/广播表。
- **异构索引表**：为第二查询维度再建一份按该维度分片的索引表（只存主键+索引列或整行冗余），写入时双写。
- **ES 宽表**：把多维度查询、全文检索、聚合统计卸载到 Elasticsearch，库里只保留按主键/分片键的点查。这是银行、政务项目最常见的组合——ao 的数据分析平台项目就是 MySQL/OceanBase 存数据 + ES 承接检索统计。
- **应用层归并**：中间件把 SQL 下发各分片，结果在内存里排序、聚合。`ORDER BY + LIMIT`、分组聚合都能做，但深分页和大结果集归并会吃内存，只能兜底，不能当主力方案。
- **离线数仓**：报表类跨片聚合走 binlog 同步到数仓/OLAP 实时算，在线库不背这个包袱。

跨片 join、跨片事务能避则避：设计阶段用冗余和维度表把它们消灭掉，比运行时硬算划算一个数量级。

### 全局唯一 ID

分片后自增主键必然冲突，全局 ID 方案：

| 方案 | 原理 | 特点 |
|---|---|---|
| UUID | 随机/时间戳拼接 | 无序、太长、索引插入随机 IO，不推荐做主键 |
| 号段模式 | 一次从中心库领一批 ID 在本地发 | 简单、依赖中心库可用性，美团 Leaf-segment 即此 |
| 雪花算法 | 时间戳 + 机器号 + 序列号 | 有序、无中心依赖；命门是时钟回拨，必须处理 |
| Redis INCR | 原子自增 | 多一个外部依赖，高并发下要做号段缓存 |
| 数据库多步长 | 各分片 auto_increment 步长错开 | 扩容改步长很痛苦，只适合分片数固定的场景 |

结论：默认选**雪花算法（含时钟回拨防护）或号段模式**；ID 里要不要嵌入分片信息（分片基因）看路由需求——按订单号反查用户分片时，基因法能省一张映射表。

## 4. 原理剖析

### 中间件的执行链路

以 ShardingSphere 为例，一条 SQL 的生命周期：**解析**（生成 AST，识别分片键）→ **路由**（按分片算法算出目标库表，单片直达或多片广播）→ **改写**（把逻辑表名换成真实表名，补齐聚合所需的列）→ **执行**（多分片并行执行）→ **归并**（流式归并排序、分组聚合、分页修正）。

两个细节最容易踩：

- **分页改写**：`LIMIT 10000, 10` 在 N 个分片上要改写成每个分片 `LIMIT 0, 10010` 再归并取舍，分片越多深分页越贵。这就是跨片深分页在生产上不可行的原理。
- **聚合改写**：`AVG` 会被改写成 `SUM + COUNT` 分别下发再合并；`COUNT(DISTINCT)` 无法这样拆，中间件只能全量拉回内存去重——这类 SQL 要单独拎出来改走 ES 或预聚合。

### 一致性哈希为什么能少搬数据

取模分片从 N 扩到 N+1，`hash % N` 的结果几乎全变，理论上要迁移约 N/(N+1) 的数据。一致性哈希把节点和 key 都映射到环上，key 归顺时针最近的节点；新增节点只接管环上相邻一段的 key，迁移量约 1/(N+1)。代价是均匀性靠虚拟节点（每个物理节点映射上百个虚拟点）来抹平，节点少的场景仍可能倾斜。

## 5. 实战应用

### 扩容迁移的标准流程

1. **双写**：新代码同时写老集群和新集群（按新分片规则），老集群仍提供读。
2. **存量迁移**：用全量 + binlog 增量同步工具（如 ShardingSphere 的数据管道、Canal、DataX）把存量搬到新集群并持续追增量。
3. **对账校验**：按分片键抽样 + 分组计数/校验和全量比对，不一致的以老集群为准修复。
4. **灰度切读**：按比例把读流量切到新集群，观察延迟和错误率。
5. **切写回滚预案**：写切到新集群，老集群保留只读一段时间，确认无误再下线双写和老集群。

全程的关键是**可回滚**：任何一步出问题都能退回上一步状态，双写期是保险丝，不要急着拆。

### ShardingSphere 简介

Apache ShardingSphere 是国内用得最广的分片方案，两个形态：

- **ShardingSphere-JDBC**：增强版 JDBC 驱动，以 jar 包形式嵌在应用里。无额外进程、性能损耗小；缺点是只支持 Java、每台应用都要部署配置。银行内网、TongWeb 这类国产化环境里经常选它，因为少一个独立组件就少一层运维和采购审查。
- **ShardingSphere-Proxy**：独立进程，对应用伪装成一个 MySQL 实例。语言无关、集中运维；多一跳网络和一个高可用组件要维护。

配套能力：分片、读写分离、分布式事务（XA/Seata 柔性事务）、数据加密、影子库压测、数据迁移管道。选型建议：Java 单体/少量服务用 JDBC 形态，多语言或已有 DBA 集中运维体系用 Proxy。

### 与 OceanBase 的关系

ao 现在的项目（神农 e 贷）用的是 OceanBase MySQL 模式。OceanBase 本身就是**原生分布式数据库**：内部用分区表（Partition）实现数据分布，LSM-Tree 存储、多副本 Paxos 同步，对应用呈现为一个逻辑库。用了 OceanBase 之后，要分清两层：

- **OB 内部的分区 ≠ 应用层分库分表**：OB 分区是数据库自己管的数据分布和并行，应用无感知，不需要 ShardingSphere 再拆一层。
- **单表过大时先想 OB 分区表**：按 RANGE/HASH/KEY 分区 + 分区裁剪，多数「分表」诉求在 OB 里就是建分区表，不用改应用代码。
- **什么时候还要应用层分片**：跨多个独立 OB 集群部署（多地多中心且集群间不做统一）、单租户数据需物理隔离下线、历史系统从 MySQL 迁 OB 前已有分片逻辑暂时保留。新项目直接上 OB 的，一般不要再叠 ShardingSphere，两层分片只会互相打架（路由、事务、运维全都双份复杂度）。

一句话：**MySQL 系靠中间件补分布式能力，OceanBase 自带；在 OB 上做「分库分表设计」≈ 做分区表设计。**

## 6. 疑难杂症

- **分片后 count、翻页越来越慢**：不是索引问题，是跨片归并。先确认 SQL 是否命中分片键；命不中就是全片广播，解法是加维度索引表或转 ES，不要指望调中间件参数。
- **数据倾斜，某个分片先爆**：查分片键分布。常见元凶是按时间范围分片导致当前片承接全部写入，或哈希键里混了低基数字段。热分片可二次拆分（把该片单独再按二级键拆），或改分片算法重迁。
- **雪花 ID 出现重复**：先查时钟回拨（NTP 同步、虚拟机快照恢复都会让时间倒流）和机器号冲突（容器扩容时 workerId 分配重叠）。发号服务必须对回拨做等待或拒绝发号并告警。
- **分布式事务偶发不一致**：跨片更新别用本地事务硬扛。要么把跨片写改成同片（调整分片键让关联数据同片），要么上柔性事务（可靠消息/Seata TCC），并配对账兜底——金融场景没有对账的分布式事务等于裸奔。

## 7. 常见误区

- **一上来就分 1024 张表**：分片数要匹配数据量级和机器数。小表分片后每片几千行，中间件广播开销比收益大。
- **以为分片能救慢 SQL**：分片解决的是容量和并发，不解决单条 SQL 写得烂；全表扫描分到 16 个片还是 16 次全表扫描。
- **分片键跟着业务随便定**：分片键变更 ≈ 全量数据迁移，上线前必须拿真实查询清单逐条验证路由命中率。
- **跨片 join 靠中间件兜底**：能跑不等于能用，归并 join 的内存和延迟随数据量线性恶化，设计期就该用冗余消灭它。
- **在 OceanBase 上再套一层 ShardingSphere**：重复建设，两层路由和事务叠加，出问题时排查路径翻倍。

## 8. 性能优化

- **路由命中率是第一指标**：监控 SQL 的分片命中情况，广播 SQL 占比应压到 5% 以下，每一条广播 SQL 都要有明确归属和优化计划。
- **绑定表本地化 join**：高频联查的维表做广播表，join 不出本机。
- **预聚合代替实时跨片聚合**：报表类统计用定时任务/binlog 同步生成汇总表，查询打汇总表。
- **连接池按分片核算**：分片数 × 每片连接数别超过实例上限，ShardingSphere-JDBC 下每个应用实例都持有全部分片连接，扩容应用时同步评估 DB 连接总量。
- **冷热分离**：历史分片（如按年分片的往年数据）迁到低成本存储或只读实例，在线分片只保留热数据。

## 9. 版本差异

- **ShardingSphere 4.x → 5.x**：配置模型大改（5.x 用 YAML 规则配置 + DistSQL 动态管理），5.x 补齐了数据迁移管道、影子库等企业级能力；老项目从 4.x 升级要按配置迁移处理，不能只换版本号。
- **MySQL 8.0**：原生分区、函数索引等能力增强，但仍不提供跨实例分片，中间件层该做的工作不变。
- **OceanBase 3.x → 4.x**：4.x 单机分布式一体化、MySQL 兼容性继续增强，分区表和并行执行能力更成熟；从 3.x 的「伪分布式」部署习惯迁过来时，注意 4.x 推荐的部署拓扑和资源规格口径不同。

## 10. 面试与自测

1. 分片键选 user_id 时，商家按 order_id 查订单怎么办？（基因法、异构索引表、ES 三条路线各自的代价）
2. 取模分片从 16 扩到 32，为什么几乎要全量迁移？一致性哈希好在哪、差在哪？
3. 跨分片 `LIMIT 100000, 10` 为什么慢？中间件是怎么改写的？
4. 雪花算法在时钟回拨时会发生什么？生产环境怎么防？
5. 已经用了 OceanBase，还需要 ShardingSphere 吗？什么场景下两者会共存？
6. 双写迁移期间，新老集群数据不一致怎么发现、怎么修复、怎么回滚？

### 参考答案

1. 三条路线各自的代价：基因法是把分片信息嵌进 ID（如按订单号反查用户分片时省一张映射表），代价是 ID 格式与分片规则耦合，规则一变 ID 体系跟着动；异构索引表是为第二查询维度再建一份按该维度分片的索引表，代价是写入时双写，以及双写不一致时的对账成本；ES 宽表是把多维度查询卸载到 Elasticsearch，库里只保留按主键与分片键的点查，代价是多一套系统、同步延迟与运维成本。没有万能分片键，只有对主要查询路径最友好的分片键。
2. 取模分片从 16 扩到 32 时，hash % N 的结果几乎全变，理论上要迁移约 N/(N+1) 的数据，所以几乎要全量迁移。一致性哈希好在新增节点只接管环上相邻一段的 key，迁移量约 1/(N+1)；差在实现复杂，均匀性依赖虚拟节点数（每个物理节点映射上百个虚拟点），节点少的场景仍可能倾斜。生产里最常见的是哈希取模加预留扩容空间，如一次建 1024 张逻辑分表映射到 16 个物理表，扩容时只调整映射、不动数据。
3. 跨分片 LIMIT 100000, 10 慢，是因为中间件要把 SQL 下发各分片、结果在内存里排序归并：它会把语句改写成每个分片 LIMIT 0, 100010 再归并取舍，分片越多深分页越贵。解法是命中分片键避免广播，或把深翻页需求改走 ES、预聚合汇总表；应用层归并只能兜底，不能当主力方案。
4. 时钟回拨时雪花算法可能发重复 ID：时间戳倒流后，同一毫秒加同一机器号加同一序列号会撞号。生产防护：先查时钟回拨来源（NTP 同步、虚拟机快照恢复都会让时间倒流）和机器号冲突（容器扩容时 workerId 分配重叠）；发号服务必须对回拨做等待（等时钟追上）或拒绝发号并告警，不能静默发号。
5. 已经用了 OceanBase，一般不需要 ShardingSphere：OB 内部用分区表实现数据分布，应用无感知，单表过大时先想 OB 分区表（RANGE/HASH/KEY 分区加分区裁剪），两层分片只会互相打架（路由、事务、运维全都双份复杂度）。两者共存的场景是：跨多个独立 OB 集群部署（多地多中心且集群间不做统一）、单租户数据需物理隔离下线、历史系统从 MySQL 迁 OB 前已有分片逻辑暂时保留。
6. 发现靠对账校验：按分片键抽样加分组计数与校验和全量比对，不一致的以老集群为准修复。修复与回滚靠双写迁移流程本身的可回滚设计：双写期老集群仍提供读，灰度切读观察延迟和错误率，切写后老集群保留只读一段时间，任何一步出问题都能退回上一步状态，确认无误再下线双写和老集群。双写期就是保险丝，不要急着拆。
