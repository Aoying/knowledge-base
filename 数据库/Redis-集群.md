# Redis 集群与哨兵

## 1. 核心概念

单机 Redis 的上限很明确：内存装不下、单核 CPU 处理命令串行、机器挂了就全停。从单机走向高可用/可扩展有三级台阶：

| 形态 | 解决什么 | 不解决什么 |
|---|---|---|
| 主从复制 | 读扩展、数据冗余备份 | 自动故障转移、写扩展、容量 |
| 哨兵（Sentinel） | 在主从之上加自动故障转移 | 容量扩展（数据还是全量一份逻辑上） |
| Cluster 模式 | 数据分片，容量和写吞吐水平扩展 + 自带故障转移 | 多键操作、运维简单度 |

选哪级看瓶颈：**只是怕挂 → 主从 + 哨兵；内存不够/写 QPS 顶不住 → Cluster**。哨兵不是 Cluster 的低配版，两者解决的问题维度不同，不要混为一谈。

## 2. 基础知识

### 主从复制

- 从节点通过 `replicaof` 向主节点发起同步：先全量同步（主节点 fork 出子进程生成 RDB，快照期间的新写命令进复制缓冲区），再持续增量同步命令流。
- 复制是**异步**的：主节点写成功不等从节点确认。主节点宕机时未同步的数据会丢——这是后面脑裂丢数据的根源。
- 读扩展：一主多从分摊读流量，但从节点数据有延迟，**读己之写**场景（刚下单就查订单）必须强制读主或做延迟等待。
- 关键参数：`repl-backlog-size`（增量同步环形缓冲区，太小会导致断线重连时频繁全量同步）、`min-replicas-to-write`（见脑裂一节）。

### 哨兵机制

哨兵是独立进程，专门干三件事：**监控**（定时 PING 所有节点）、**通知**（故障转移后告知客户端新主地址）、**自动故障转移**。

- 主观下线（SDOWN）：单个哨兵认为主节点不可达。
- 客观下线（ODOWN）：超过 `quorum`（法定人数）个哨兵都报告主观下线，判定主节点确实挂了，才触发选举和故障转移。
- 哨兵之间先用 Raft 式选举选出一个领头哨兵，由它执行转移：从从节点中挑一个（按优先级、复制偏移量、runID 综合排序）提升为新主，其余从节点改指向新主，旧主恢复后自动降为从节点。
- 客户端通过哨兵获取当前主地址（Spring Data Redis、Jedis、Lettuce 都支持 Sentinel 模式），应用不要把主节点地址写死。

哨兵数量必须是**奇数且 ≥ 3**，且要部署在不同机器上——哨兵和 Redis 节点全挤在一台机器上，机器一挂全军覆没，高可用形同虚设。

## 3. 进阶知识

### 脑裂与数据丢失

脑裂场景：主节点所在机房网络分区，主节点其实活着但哨兵联系不上，哨兵在另一分区选出新主；老主继续接收客户端写入（客户端还没感知切换）。分区恢复后老主降为从节点，它上面那批「分区期间的写入」被全量同步直接覆盖清掉。

两个层面的解法：

1. **减少发生**：`min-replicas-to-write 1` + `min-replicas-max-lag 10`——主节点发现自己连不上足够从节点时拒绝写入，宁可不可用也不写孤岛数据。这是拿可用性换一致性，金融场景应该开。
2. **接受并补偿**：缓存定位是可丢数据（重要数据落 DB、Redis 只做加速），脑裂丢的是缓存，靠回源重建。Redis 里存的是不可重建的权威数据时，先反问架构：它不该只存在 Redis 里。

### Cluster 模式与哈希槽

Cluster 把键空间切成 **16384 个哈希槽（slot）**：`slot = CRC16(key) % 16384`，每个主节点负责一段槽，槽可以在节点间迁移（扩缩容就是搬槽）。

- **为什么是 16384**：节点间心跳包要携带槽位图，16384 个槽用位图表示是 2KB，节点数上限约 1000 时心跳开销可接受；槽太多心跳包就爆了。
- **哈希标签（hash tag）**：key 写成 `user:{1001}:profile` 时只对 `{}` 内的部分算槽，可以把一组相关 key 钉在同一槽——这是 Cluster 里做多键操作的唯一正道。
- **重定向**：客户端连错节点时，节点返回重定向而不是代为转发：
  - `MOVED`：槽已永久迁到另一节点，客户端应刷新本地槽位缓存，后续直连新节点；
  - `ASK`：槽正在迁移中，这次请求临时去目标节点（先发 `ASKING`），客户端不要更新缓存。
  智能客户端（Lettuce、JedisCluster）会缓存槽位映射，所以 Cluster 扩容后偶发 MOVED 是正常现象，频繁出现才需要查槽位状态。
- **多键限制**：`MGET`、多键事务、`KEYS` 类命令要求所有 key 在同一槽，否则报 `CROSSSLOT`。Lua 脚本同理，脚本里用到的 key 必须同槽。设计 key 时就要用 hash tag 把「需要一起操作」的 key 归组，这是 Cluster 上线前评审的重点。

## 4. 原理剖析

### 全量同步为什么贵

主节点 fork 子进程写 RDB 时用写时复制（COW）：同步期间主节点每修改一个内存页就复制一份，写流量越大、同步越久，额外内存占用越高，极端情况内存翻倍直接 OOM。所以大内存实例（几十 GB）的从节点重建要避开业务高峰，`repl-backlog-size` 要给足（经验值按复制延迟和写速率估算，常见 256MB–1GB），让短暂断线走增量同步（PSYNC）而不是全量。

### Cluster 的故障转移

Cluster 没有哨兵，节点间用 Gossip 协议互探：节点标记某主节点 `PFAIL`（疑似下线），集群多数主节点都报告后标记 `FAIL`，触发该主节点的从节点发起选举（同样是 Raft 式投票，多数派授权），胜出的从节点接管槽位并广播新拓扑。参数 `cluster-node-timeout` 决定判定速度，太小误判、太大切换慢，一般 5–15 秒量级按业务容忍度调。

### 一致性定位

无论哨兵还是 Cluster，Redis 的复制都是异步的，故障转移**必然有丢数据窗口**，官方定位就是 AP（可用性优先）。需要强一致的场景（余额、库存扣减的权威判断）不要拿 Redis 当唯一真相源，用 DB 事务/分布式锁校验兜底，或把关键计数放 DB、Redis 只做前置削峰。

## 5. 实战应用

### 选型对比

| 维度 | 主从 + 哨兵 | Cluster |
|---|---|---|
| 数据容量 | 受单机内存限制（全量数据一份） | 多主分片，总容量 = 各主之和 |
| 写吞吐 | 单主上限 | 多主并行扩展 |
| 故障转移 | 哨兵自动切换，秒级到几十秒 | 内置选举，秒级 |
| 多键/事务/Lua | 完整支持 | 必须同槽（hash tag） |
| 客户端 | 连哨兵取主地址，简单 | 需智能客户端维护槽位缓存 |
| 运维复杂度 | 低，3 哨兵 + 一主多从即可 | 高，最少 3 主 3 从起步，槽迁移要演练 |
| 典型规模 | 数据量 < 单机内存，读多写少 | 数据量大、写并发高、大促型业务 |

结论口径：**数据能装进一台机器、只是要高可用，哨兵足够，别为了「先进」上 Cluster**；数据量奔着几百 GB 去或写 QPS 单主扛不住，再上 Cluster。银行内网项目（ao 的环境）以哨兵居多——数据量可控、运维人力有限、还要过稳定性审查，Cluster 的槽运维成本不划算；互联网大流量缓存层则相反，Cluster 是默认选项。

### 部署要点

- 哨兵、Redis 实例分机部署；哨兵配置里的 `quorum` 一般设为哨兵数过半（如 3 个哨兵设 2）。
- 内存上限 `maxmemory` 必设，配合淘汰策略；Redis 当缓存用 `allkeys-lru/lfu`，当队列/存储用禁止淘汰并靠告警扩容。
- 持久化：缓存场景可关 RDB/AOF 换性能，但要接受重启冷启动冲击；混用部署保持一主一从开 AOF。
- 大 key 和热 key 治理在集群下更重要：一个大 key 只会压垮它所在的那个分片，扩容解决不了。

## 6. 疑难杂症

- **故障转移后客户端还往老主写**：客户端没走哨兵/没有重连刷新拓扑，或连接池里存着旧连接。检查客户端是否用的 Sentinel 模式、故障转移通知（+switch-master）是否被消费，转移演练时抓包验证。
- **从节点频繁全量同步**：先看 `repl-backlog-size` 是否太小和网络抖动，再看主节点内存是否大到快照生成时间过长。`master_repl_offset` 与从节点 offset 差距持续拉大，就是增量追不上的信号。
- **Cluster 偶发 CROSSSLOT 报错**：新上线的多键操作没做 hash tag 归组。逐条排查报错命令的 key 集合，统一加 `{}` 标签，注意加标签会改变槽位，存量数据要迁移或双读过渡。
- **MOVED 报错刷屏**：多半是扩缩容后客户端槽位缓存没刷新，或用了不支持重定向的客户端/代理。重启客户端可临时恢复，根治是升级智能客户端并检查 `cluster_state`。
- **哨兵迟迟不切换**：`down-after-milliseconds` 设得太大、quorum 设得比存活哨兵数还高、或哨兵之间网络不通。逐项核对哨兵日志的 SDOWN/ODOWN 记录定位卡点。
- **切换瞬间批量请求失败**：切换窗口内连接被重置属正常现象，客户端必须配置重试（Lettuce 的拓扑刷新 + 命令重试），业务层对非幂等写要做幂等校验，别把切换窗口的失败当数据错误处理。

## 7. 常见误区

- **哨兵只有 1 个或 2 个**：1 个哨兵自己就是单点；2 个哨兵 quorum 设 2 时挂一个就永远达不成客观下线。至少 3 个、奇数部署。
- **把从节点延迟当不存在**：秒杀、发券这类强一致读打从节点，必然出现「刚写查不到」的客诉。用哨兵不等于读写分离可以不分场景。
- **Cluster 里随手用多 key 命令**：单机时代写惯的 `MSET`、跨 key 事务搬到 Cluster 直接 CROSSSLOT，上线前必须全量扫描多键操作。
- **觉得上了集群就不用管大 key**：分片均衡的是 key 数量不是 key 大小，一个 500MB 的大 key 在哪个分片哪个分片倒霉。
- **用 KEYS 做生产查询**：单机阻塞、Cluster 还要逐节点扫，生产一律用 SCAN 或提前建索引结构。

## 8. 性能优化

- **复制链路优化**：无盘复制（`repl-diskless-sync`）避免大实例落盘 RDB 的 IO 峰值；从节点多时考虑级联复制（从连从）给主节点减压。
- **槽位均衡**：Cluster 扩容后用 `cluster rebalance` 均摊槽位，迁移安排在低峰并限速，迁移中的 ASK 重定向会增加一跳延迟。
- **热 key 打散**：读热点 key 做多副本（如 key 后缀随机分片 + 客户端随机选）或本地缓存兜一层，别让单个分片承接全部热点流量。
- **连接与管道**：客户端用连接池 + pipeline 批量命令；Cluster 下 pipeline 的 key 要按槽分组发送，客户端一般已封装，注意版本支持。
- **监控四件套**：复制延迟（offset 差）、内存碎片率（`mem_fragmentation_ratio` > 1.5 关注）、慢日志、逐分片内存/ops 分布——只监控集群总量会掩盖单分片倾斜。

## 9. 版本差异

- **Redis 5.0**：Cluster 总线与复制优化，Stream 结构落地，哨兵/Cluster 仍是 6.x 之前的主力形态。
- **Redis 6.0**：多线程 IO（命令执行仍单线程）、ACL、客户端缓存；对集群的影响主要在单节点吞吐上限抬高，哨兵切换逻辑无本质变化。
- **Redis 7.x**：多 AOF、函数（Functions）、分片发布订阅（SSUBSCRIBE 按槽分发，解决老版本广播全集群的问题）；从 7.0 起 ACL 选择器、命令元数据等运维能力补齐。新建集群直接上 7.x，不要再部署 5.x。
- **RESP3 与客户端**：新客户端默认协议升级对 Cluster 槽位缓存和重定向处理更完善，老客户端（早期 Jedis）在 MOVED 处理上有过兼容坑，升级时一并核对客户端版本矩阵。

## 10. 面试与自测

1. 哨兵判定主节点客观下线的流程是什么？quorum 和哨兵选举领头是两回事吗？
2. 脑裂时为什么会丢数据？`min-replicas-to-write` 怎么缓解、代价是什么？
3. Cluster 为什么是 16384 个槽而不是 65536？
4. MOVED 和 ASK 的区别？客户端分别应该怎么处理？
5. Cluster 下要保证 `user` 的 profile、setting、score 三个 key 能做事务，怎么设计 key？
6. 数据量只有 20GB、读 QPS 很高，应该上 Cluster 还是哨兵 + 多从？说明理由。

### 参考答案

1. 流程是：单个哨兵认为主节点不可达叫主观下线（SDOWN）；超过 quorum（法定人数）个哨兵都报告主观下线，才判定客观下线（ODOWN），触发选举和故障转移。quorum 和哨兵选举领头是两回事：quorum 是判定客观下线的门槛，领头哨兵是哨兵之间再用 Raft 式选举选出一个，由它执行转移（从从节点中按优先级、复制偏移量、runID 综合排序挑新主）。
2. 脑裂丢数据的原因是复制异步：主节点所在机房网络分区后，哨兵在另一分区选出新主，老主其实活着还继续接收客户端写入；分区恢复后老主降为从节点，分区期间的那批写入被全量同步直接覆盖清掉。min-replicas-to-write 1 加 min-replicas-max-lag 10 的缓解方式是：主节点发现自己连不上足够从节点时拒绝写入，宁可不可用也不写孤岛数据；代价就是拿可用性换一致性，金融场景应该开。
3. 因为节点间心跳包要携带槽位图：16384 个槽用位图表示是 2KB，在节点数上限约 1000 时心跳开销可接受；槽太多心跳包就爆了。槽数是心跳开销与分片粒度之间的折中，不是越大越好。
4. MOVED 表示槽已永久迁到另一节点，客户端应刷新本地槽位缓存，后续直连新节点；ASK 表示槽正在迁移中，这次请求临时去目标节点（先发 ASKING），客户端不要更新缓存。智能客户端（Lettuce、JedisCluster）会缓存槽位映射，扩容后偶发 MOVED 是正常现象，频繁出现才需要查槽位状态。
5. 用哈希标签把三个 key 钉在同一槽：user:{1001}:profile、user:{1001}:setting、user:{1001}:score。Cluster 只对花括号内的部分算槽，这样三个 key 落在同一槽，多键事务就不会报 CROSSSLOT；注意加标签会改变槽位，存量数据要迁移或双读过渡。
6. 选哨兵加多从。理由：20GB 装得进单机内存，瓶颈只是高可用和读扩展，哨兵正好解决这两点，运维也简单；Cluster 解决的是容量扩展和写吞吐水平扩展，数据量奔着几百 GB 去或写 QPS 单主扛不住时才上。数据能装进一台机器、只是要高可用时，哨兵足够，别为了先进上 Cluster。
