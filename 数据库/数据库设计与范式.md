# 数据库设计与范式

> 定位：本篇讲“表怎么拆、键怎么定”——设计流程、范式、反范式、主键外键、命名类型。类型速选表、建表语法、DML 速记在总纲篇，[MySQL 数据库](数据库/MySQL/MySQL-数据库.md)；事务与一致性模型见[事务一致性模型与选型](数据库/事务一致性模型与选型.md)，分库分表后的键策略见[分库分表](数据库/分库分表.md)。

示例贯穿全篇（虚构电商库 shop，无任何真实业务表）：用户（t_user）、订单（t_order）、订单明细（t_order_item）、商品（t_product）。

## 1. 核心概念

- 数据库设计的目标有三个，按优先级排：**数据不错**（约束保证业务规则不被写坏）→ **查询不难**（常用查询不用七八张表连）→ **演进不疼**（加字段、加表不重构全库）。
- 设计的输入是业务规则，不是字段清单。先把规则写成句子（“一个订单属于一个用户”“一个订单可含多个商品”），再落成表——规则没说清就建表，后面一定返工。
- 范式是“拆表的标尺”，不是“拆表的目的”：先懂范式，再谈什么时候可以不遵守（第 4 节）。

## 2. ER 设计步骤

### 第 1 步：识别实体与属性

- 实体是业务里独立存在的东西：用户、订单、商品。属性是实体的描述：用户有姓名、城市；订单有订单号、金额、状态。
- 判断实体还是属性的土办法：它有没有自己的生命周期、会不会被多处引用？订单明细里的“商品名”会被多处引用 → 商品是实体，不是订单明细的一个字段。

### 第 2 步：定关系与基数

| 关系 | 例子 | 落表方式 |
|---|---|---|
| 1 : 1 | 一个用户对应一个实名认证档案 | 外键放任意一边，或共用主键 |
| 1 : N | 一个用户多个订单 | 外键放 N 的一边（订单表存 user_id） |
| N : M | 一个订单多个商品，一个商品出现在多个订单 | 必须建中间表（订单明细表存 order_id + product_id） |

### 第 3 步：画 ER 图再转表

- ER 图只画实体、属性、关系、基数，不写 SQL；评审时业务方能看懂 ER 图，看不懂建表语句——先对图，再对表。
- 转表规则：实体 → 表；1:N 的外键放 N 侧；N:M 建中间表，中间表的主键通常是两边外键的联合主键；1:1 的外键放查询更频繁的一侧。

### 第 4 步：加约束收口

- 每个实体一张表都要有主键；每个外键都要说明“被删了怎么办”（见第 5 节）；每个业务唯一（如订单号）都要有唯一约束，别只靠应用层保证。

## 3. 范式：每一级解决什么问题

范式是逐级收紧的：满足后一级必然满足前一级。实务中 3NF 是常态目标，BCNF 是“发现异常时再拆”的标尺，4NF/5NF 知道即可。

### 1NF：列不可再分

- 规则：每个字段都是原子值，不能一个字段塞多个值。
- 反例：订单表里 `product_names` 字段存“手机,耳机,充电器”——查“买过耳机的人”只能 LIKE，改、删单个商品都要字符串手术。
- 正解：拆成订单明细表，一行一个商品。

### 2NF：消除部分依赖（只针对联合主键的表）

- 规则：非主键列必须完全依赖整个主键，不能只依赖主键的一部分。单列主键的表天然满足 2NF。
- 反例：订单明细表主键是（order_id, product_id），却冗余存了 `product_name`——商品名只依赖 product_id，不依赖 order_id。商品一改名，所有历史明细都要跟着改，漏改就是脏数据。
- 正解：`product_name` 只留在商品表，明细表只存 product_id；查时 JOIN。

```sql
-- 反例：明细表冗余商品名（部分依赖）
CREATE TABLE t_order_item_bad (
  order_id     BIGINT NOT NULL,
  product_id   BIGINT NOT NULL,
  product_name VARCHAR(64) NOT NULL,   -- 只依赖 product_id，违反 2NF
  qty          INT NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
```

### 3NF：消除传递依赖

- 规则：非主键列不能依赖另一个非主键列。
- 反例：订单表冗余存 `user_name`、`user_city`——它们依赖 user_id，而 user_id 不是订单表的主键（订单表主键是 id）。用户一改城市，所有历史订单都要跟着改。
- 正解：用户名、城市只留在用户表，订单表只存 user_id；查时 JOIN。
- 一句话区分 2NF 与 3NF：2NF 管“依赖主键的一部分”，3NF 管“依赖非主键列”。

### BCNF：每个决定因素都必须是候选键

- 规则：所有函数依赖的左部都必须是超键。BCNF 比 3NF 严格，专门处理“主键本身有重叠”的情况。
- 经典例子：选课表（学生，课程，教师），规则是“一门课只有一个教师，一个教师只教一门课”。
  - 候选键有两个：（学生，课程）和（学生，教师）。
  - 依赖 `教师 → 课程` 的左部“教师”不是超键 → 违反 BCNF（虽然满足 3NF：教师、课程都是主键的一部分，不算“非主键列依赖非主键列”）。
  - 后果：教师换课时要改多行，漏改就出现“同一教师在两门课”的矛盾数据。
- 正解：拆成（教师，课程）与（学生，教师）两张表，依赖关系各归其位。

### 4NF 与 5NF：知道即可

- 4NF 消除多值依赖：一个员工有多个技能、多个语言，写在一张表会产生“技能 × 语言”的笛卡尔积冗余 → 拆成技能表、语言表两张。
- 5NF 消除连接依赖：极少见，日常业务基本碰不到，知道名字即可。
- 实务线：OLTP 业务设计到 3NF，出现 BCNF 型异常再拆到 BCNF；4NF/5NF 不必主动追求。

## 4. 反范式：什么时候可以不遵守

范式是默认值，不是铁律。以下场景可以主动反范式，但每处反范式都要有“维护方案”，否则就是埋雷。

| 场景 | 反范式做法 | 代价与维护方案 |
|---|---|---|
| 读多写少的高频查询 | 订单表冗余 `user_name`，省掉 JOIN | 用户改名时要同步更新历史订单；应用层事务内双写，或定时对账任务兜底 |
| 报表与统计 | 日汇总表（按天预聚合订单数、金额） | 汇总逻辑要可重算（按日期重跑）；源数据修正后汇总表要同步修正 |
| 计数器 | 商品表冗余 `sale_count`，不用每次 COUNT 明细 | 并发更新要防丢（原子递增或单线程聚合）；定期与明细表对账 |
| 排行榜与宽表 | 宽表预拼多表字段，查询一次出结果 | 宽表只能由固定任务生成（ETL/定时任务），不接受业务直接写 |

- 判断题只有一个：**这个冗余字段不一致时，业务能不能接受、能不能发现、能不能修复？** 三个答案有一个是“不能”，就别反范式，老实 JOIN。
- 反范式不等于不要约束：冗余字段照样给类型、给默认值、给注释；唯一键、非空这些底线约束不因为反范式而放松。

## 5. 主键与外键策略

### 主键选择

| 方案 | 优点 | 缺点与适用边界 |
|---|---|---|
| 自增 BIGINT | 简单、有序、对 B+ 树友好 | 不保证连续（回滚、删除留空洞）；分库分表下各分片自增会冲突；不能当业务序号用 |
| 雪花算法 ID | 全局唯一、趋势递增、分库可用 | 需要 ID 生成服务或算法实现；时钟回拨要处理 |
| UUID | 无需中心协调、全局唯一 | 无序、随机写导致页分裂、占空间大；主键用 UUID 的表慎做大批量写入 |
| 业务自然键（如订单号、手机号） | 业务可读 | 业务键会变（手机号可换、订单号规则可改），主键一变所有外键跟着变——主键只用代理键 |

- 默认策略：**单库用自增 BIGINT，分库分表用雪花 ID；业务号（订单号）只做唯一键，不做主键**。总纲篇的自增坑与分库主键结论与本条一致。
- 中间表（N:M）的主键：两边外键的联合主键即可，多数场景不需要再加自增 id；联合主键本身就是唯一性约束。

### 外键：用还是不用

- 外键的收益：数据库层兜底——删用户时有未完成订单会直接报错，不用靠应用层人人记得判。
- 外键的代价：写操作要查父表（性能损耗）、分库分表下跨库外键无法建立、删改父表被阻塞时排障链路变长。
- 实务取舍：
  - 单库核心业务表：建外键，约束优先于那点性能损耗。
  - 分库分表 / 跨服务：不建物理外键，改“逻辑外键”——应用层校验 + 定时对账任务兜底；外键列、索引照样建，只是不声明 FOREIGN KEY。
- 外键动作（ON DELETE / ON UPDATE）：默认 NO ACTION（拒绝删）；CASCADE（级联删）只用于“子表无独立意义”的场景（如订单明细随订单删），核心实体之间一律不用 CASCADE，删错一行会连锁删一片。

## 6. 命名与类型选择建议

### 命名

- 表名：小写下划线，统一前缀（如 `t_`）或统一不加前缀，全库一致比选哪个前缀重要；名词语义化，`t_order` 不叫 `t_o`，`t_order_item` 不叫 `t_detail`。
- 列名：主键一律 `id`；外键用“被引表 + _id”（`user_id`、`order_id`），一眼看出引用关系；状态字段后缀 `_status`，布尔标志后缀 `_flag`；时间字段后缀 `_time`（`create_time`、`update_time`），不用 `date`/`time` 这类保留词裸奔。
- 避免保留词与中文：`order`、`group`、`key` 是保留词，作表名列名要加反引号，干脆避开；中文字段名在跨工具迁移时总有坑，一律英文。
- 注释：每张表、每个含义不自明的字段都要有 COMMENT（状态码的取值含义必须写进注释，如 `0待支付 1已支付`），注释是给半年后的自己看的。

### 类型选择原则

- 钱用 DECIMAL，不用 FLOAT/DOUBLE（精度误差）；ID 用 BIGINT；状态用 TINYINT + 字典表或注释；时间用 DATETIME（绝对时间），跨时区业务慎用 TIMESTAMP；短文本 VARCHAR（长度按实际设计，别无脑 255）；长文本 TEXT（不设默认值、少建索引）。
- 完整类型速选表见总纲篇 [MySQL 数据库](数据库/MySQL/MySQL-数据库.md)，本篇只定原则：类型选错的代价（溢出、精度丢、时区错）远大于选保守的代价，拿不准时选更宽、更精确的那个。

## 7. 常见误区

1. **范式越高越好**：3NF 是常态，BCNF 按需，4NF/5NF 不必主动追求；过度拆分会让常用查询连七八张表，性能与可读性双输。
2. **反范式不留维护方案**：冗余字段写进去却没人同步更新，三个月后就是脏数据；每处冗余都要配双写或对账。
3. **主键用业务键**：手机号、订单号都会变，主键一变所有外键跟着变；主键只用代理键，业务键做唯一键。
4. **分库分表还建物理外键**：跨库外键建不起来，硬建会让分片方案直接卡住；分库场景用逻辑外键 + 对账。
5. **CASCADE 随手开**：核心实体间开级联删除，删一行用户可能连锁删掉订单、明细、对账记录；CASCADE 只给无独立意义的子表。
6. **钱用 FLOAT、时间用字符串、枚举用中文字符串**：三类经典建模错误，分别改 DECIMAL、DATETIME、TINYINT + 字典表。
7. **无主键表**：没有主键就没有行级定位，更新、删除、同步、排障全靠全行匹配；每张表都要有主键。
8. **字段名含义靠猜**：状态码、标志位不写注释，半年后没人敢改；注释是设计的一部分，不是附赠品。

## 面试与自测

1. 订单明细表主键是（order_id, product_id），里面冗余存了 product_name，违反第几范式？为什么？怎么改？
2. 订单表冗余 user_name 是违反 3NF 还是合理的反范式？判断标准是什么？
3. 分库分表场景下主键和外键分别该怎么选？为什么不能用自增 ID 和物理外键？

### 参考答案

1. 违反 2NF。product_name 只依赖主键的一部分（product_id），不依赖整个主键（order_id, product_id），属于部分依赖。改法：product_name 只留在商品表，明细表只存 product_id，查询时 JOIN 商品表。
2. 两种可能，取决于有没有维护方案。按范式它是传递依赖（user_name 依赖非主键列 user_id），违反 3NF；但如果该字段是高频查询的冗余、且配了双写或对账的同步方案，就是合理的反范式。判断标准是：不一致时业务能不能接受、能不能发现、能不能修复，三者缺一就别反范式。
3. 主键用雪花算法 ID（全局唯一、趋势递增），不用自增 ID（各分片自增会冲突）；外键不用物理外键（跨库无法建立），改逻辑外键——外键列和索引照样建，引用完整性由应用层校验加定时对账兜底。
