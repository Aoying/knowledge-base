# 分布式事务

## 1. 核心概念

单库事务靠数据库自己的 ACID 就够了。一旦一次业务要写**两个库、或两个服务**（下单扣库存、放款同时记账和通知），本地事务管不到对面，分布式事务解决的是这种跨边界的一致性。

先把预期摆正：

- **CAP**：分区出现时，一致性（C）和可用性（A）只能选一个。金融核心选 CP，互联网高并发多选 AP + 最终一致。
- **BASE**：基本可用、软状态、最终一致——柔性事务的理论底座，与 ACID 的刚性事务相对。
- 刚性方案（XA）强一致但吞吐差；柔性方案（TCC、本地消息表、Saga）都是最终一致，差别在侵入程度和补偿怎么写。**选型的第一问题永远是：这笔业务能不能接受最终一致**（秒级到账 vs 分钟级对账兜底）。

## 2. 2PC 与 XA

两阶段提交：协调者先问所有参与者「能提交吗」（Prepare，各自写日志、锁资源但不提交），全票通过再统一 Commit，有一票否决就全 Rollback。XA 是它在数据库层的标准接口，MySQL、OceanBase（MySQL 模式）都支持 XA 语句。

缺点是结构性的：

- **同步阻塞**：Prepare 后资源一直锁着等协调者发话，协调者慢或宕机，参与者全员干等，长事务把连接和行锁占满。
- **协调者单点 + 脑裂窗口**：Commit 指令下发一半协调者挂了，一部分提交一部分回滚，数据直接不一致，只能靠人工介入。
- 所以 XA 只适合参与者少、事务短、内部可控的场景（如同一中间件管的两个库），跨公司、跨系统的长链路不要用。

## 3. Seata AT 模式

Seata 是国内最常用的框架，三种角色：TC（事务协调者，独立部署的 Server）、TM（发起方，定义全局事务边界）、RM（参与方，管本地分支）。

AT 模式的主意是**把补偿自动化**：

1. 一阶段：RM 拦截业务 SQL，执行前先查出前镜像、执行后查出后镜像，拼成 `undo_log` 与业务数据**在同一个本地事务里**提交，同时向 TC 注册分支并申请全局锁。
2. 二阶段提交：TC 通知各分支删除 undo_log，异步清理，快。
3. 二阶段回滚：RM 用 undo_log 的前镜像反向生成补偿 SQL 恢复数据；恢复前校验当前数据与后镜像一致，不一致说明被全局事务之外改过（脏写），直接告警人工处理。

要点与代价：

- 对业务无侵入（不用写补偿代码），但隔离性是**读未提交**级别：全局锁只挡写不挡读，两个全局事务并发改同一行靠锁串行，热点行上吞吐明显掉。
- 每张参与的表都要有主键、要建 `undo_log` 表；批量 SQL、无主键更新会让镜像生成失败或变慢。
- 全局事务别包太长：AT 的锁持有到二阶段结束，链路里掺远程调用、人工审批等于把锁放大，先想清楚边界。

## 4. TCC 模式

Try（预留资源：冻结金额、置中间状态）→ Confirm（真扣减）→ Cancel（释放预留），三个方法全部由业务自己实现，框架只负责编排和重试。性能好、锁定粒度自己控制，代价是每个服务都要写三套逻辑。

三个必踩的坑，面试和生产都高频：

| 坑 | 现象 | 解法 |
|---|---|---|
| 空回滚 | Try 还没执行，Cancel 先到了 | Cancel 里查不到预留记录时也要落一条「已回滚」标记，不能直接报错 |
| 悬挂 | Cancel 比 Try 先执行完，迟到的 Try 又预留成功，资源永远冻结 | Try 执行前先查回滚标记，有标记直接拒绝 |
| 幂等 | Confirm/Cancel 被重试多次 | 按事务 ID + 分支做状态机，重复调用直接返回成功 |

Seata TCC、以及手动实现的「冻结表」模式，本质都绕不开这三件事。

## 5. 本地消息表与最大努力通知

思路是降级成可靠消息问题，不再追求强一致：

1. 业务数据与一条消息记录**写在同一个本地事务**里（消息表在业务库）。
2. 定时任务或事务提交后异步把消息投到 MQ；下游消费成功回执（或提供查询接口供核对），失败按退避间隔重试。
3. 超过重试上限的进死信/异常表，人工或对账任务兜底。

这与 [消息可靠性](消息队列/消息可靠性.md) 是同一套组合拳：本地消息表解决「消息发不出去」，消费幂等解决「消息重复投」。**最大努力通知**是它的对外版：给外部系统（如支付结果通知商户）按固定间隔重试 N 次，再提供主动查询接口让对方兜底，不承诺必达。

优点：无框架锁定、无额外锁、吞吐高。缺点：一致性窗口最长（秒到分钟级），且每个接入点都要写消息表 + 补偿扫描 + 对账，工程量分散在各个业务里。

## 6. Saga：长事务拆成带补偿的本地事务链

Saga 的思路是放弃「一个全局原子事务」，改成一串各自提交的本地事务：下单（订单库提交）→ 扣款（支付库提交）→ 扣库存（库存库提交），每步成功就真正落库；某一步失败，已完成的前序步骤靠**补偿事务**（compensating transaction）逆向抵消——退款抵扣款、释放库存抵扣库存、取消订单抵创建订单。补偿不是数据库回滚，是另一笔正向业务操作：已扣的钱只能再退一笔，不存在「撤销扣款」这个 SQL。这个名字与思路来自 Garcia-Molina 与 Salem 1987 年的论文《Sagas》（出处见本篇冷知识）。

- **补偿三条硬要求**：幂等（重试不会重复退款）、可重入（中途崩溃续跑能接着补）、逆序执行（正向下单→扣库存→扣款，补偿就退款→恢复库存→取消订单，逆序才能保证每步补偿时它依赖的状态还在——小技巧节已有此条）。
- **补偿不了的操作要先想好**：发出去的短信、邮件无法「撤回」，只能再发一条「订单已取消」的通知；这类步骤要排在链路末尾，或接受「发了就发了」的语义。
- **两种协调方式**：
  - **编排式（Orchestration）**：一个中心协调器（Saga 执行器/工作流引擎）按状态机依次调各服务，失败时按逆序发补偿。流程在协调器里一目了然，步骤多、分支多时首选；代价是协调器本身要持久化状态（崩溃续跑靠它），成了新的单点——工作流引擎（Temporal、Cadence 这类）本质上就是把它做成了基础设施。Seata 的 Saga 模式（JSON 状态机描述流程与补偿）是编排式的一种落地。
  - **协同式（Choreography）**：没有中心节点，各服务做完本地事务就发领域事件，下一个服务监听事件接着做；失败事件触发各服务自行补偿。耦合最松（服务只认事件不认彼此），但流程散在各服务的监听器里，步骤超过 4–5 步后排障与推理成本陡增；且强依赖事件总线的至少一次投递（见 [事件驱动架构与 CQRS 事件溯源](工程实践/事件驱动架构与CQRS事件溯源.md)与 [消息可靠性](消息队列/消息可靠性.md)）。
  - 选型口径：步骤少、反应简单用协同式；步骤多、要显式控制流与可视化时用编排式；生产里超过 4–5 步的 Saga 多数会收敛到编排式。
- **与 TCC 的关系**：TCC 可以看作 Saga 在「预留资源」语义上的特化——Try 就是带预留语义的 Saga 正向步骤，Confirm/Cancel 就是它的「完成/补偿」分支。已经有冻结语义的点（金额、库存）用 TCC，没有预留概念的长链路（下单→风控→放款→通知）用 Saga 更自然。
- **Saga 的一致性窗口与对账**：Saga 全程是最终一致，中间状态对外可见（订单已建、钱已扣、库存还没扣），读侧要能展示「处理中」而不是假装已完成；补偿失败不能静默跳过，进死信/人工队列——与本地消息表一样，配对账任务才算闭环。

（来源：Garcia-Molina & Salem《Sagas》1987；Seata 官方文档 Saga 模式；核验日期 2026-11-03）

## 7. 项目落点与选型（OceanBase 场景）

先说 OceanBase 的特殊性:OB 本身是分布式数据库,**单个租户内的事务由 OB 内部保证强一致**(Paxos 多副本 + 两阶段提交在引擎内部完成)。很多在 MySQL 分库分表架构下被迫上分布式事务的场景,搬到 OB 后可以靠**不拆库**直接消解——业务表放同一租户同一库,本地事务就够了。这也是 ao 在神农 e 贷项目里的默认取舍顺序:

1. **能收敛到同库就收敛**:审批、额度、台账在同一 OB 库内,普通本地事务,别为了"架构先进"引入 Seata。
2. **跨系统写**(调信贷核心、征信、短信平台):对方不可能参与你的事务协调,老老实实用本地消息表 + 状态机 + 每日对账文件兜底,这是银行系统的常规打法。
3. **真的需要近实时强一致且参与方都在自己手里**:再考虑 Seata AT;TCC 只用在金额冻结这类已经有明确预留语义的点上,不要全链路铺开。

决策一句话:**先降级问题(收敛边界),再选框架**;分布式事务框架是最后一招,不是默认项。

## 8. 常见误区

- 误区：上了 Seata 就是强一致。AT 是最终一致 + 写锁，全局读到的是可能被回滚的数据，账务展示口径要想清楚。
- 误区：XA 和 2PC 是两个方案。XA 是 2PC 的接口标准，Seata 的 XA 模式也是它。
- 误区:本地消息表只管发不管查。没有消费回执查询和对账,消息发出去了对方没处理,你永远不知道。
- 误区:补偿逻辑随便写写。补偿必须幂等、可重入、且要处理"补偿时数据已被正常流程改过"的情况,这正是 TCC 三坑的来源。

## 小技巧与冷知识

【小技巧】Seata AT 模式要生效，数据源必须换成 Seata 的代理数据源：AT 靠拦截业务 SQL 生成前后镜像，如果某个库还直连原生数据源、没走 DataSourceProxy，那个分支就不会被拦截、不会注册到 TC，全局回滚时它的数据原样不动。接入后先跑一次“故意回滚”的端到端验证，确认每个参与库都在分支列表里，再上线。

【小技巧】AT 模式的 undo_log 别手删、也别设 TTL 硬清：二阶段提交成功后 RM 会异步删 undo_log，二阶段回滚靠它恢复；清理任务只清“已提交且超过保留期”的行。undo_log 表突然暴涨，先查是不是有全局事务卡住了、分支迟迟没走完二阶段，而不是先清表——清掉正在等待回滚的 undo_log，等于把回滚的唯一依据删了。

【小技巧】TCC 的 Try 本身也要幂等，不只 Confirm/Cancel：网络超时重试时 Try 可能被调两次，两次都冻结同一笔金额，账户就多冻了一份。Try 里按事务 ID + 分支查一次“已冻结”标记，有标记直接返回成功，别重复冻结；幂等要覆盖三个方法，不是只覆盖后两个。

【小技巧】Saga 的补偿要按与正向操作相反的顺序执行：正向是“下单 → 扣库存 → 扣款”，补偿就得是“退款 → 恢复库存 → 取消订单”，逆序才能保证每一步补偿时它依赖的状态还存在。补偿动作也要幂等、可重入，补偿失败时别静默跳过，进死信或人工队列，否则链路断在中间、数据停在半一致状态。

【小技巧】本地消息表的轮询投递要防重复投递：定时任务扫到一批未投递消息，先按主键把状态从“待投递”改成“投递中”（带上本次任务的标识），再逐条投；投完按回执改“已投递”。不加这一步，两个轮询实例同时扫到同一批消息会重复投递，下游即使幂等也会多一倍处理量；用状态机 + 唯一标识抢占，比分布式锁更轻。

【小技巧】给全局事务设一个比锁等待超时更短的超时：Seata 全局事务默认超时偏长，链路里一旦某个分支卡住，锁会一直占到超时才释放。按业务给全局事务设超时（比如核心下单链路几秒），超时后 TC 直接发起回滚，比“等锁超时再等全局超时”两层叠加要快得多；超时值要写进配置，别依赖框架默认值。

【小技巧】Seata 的 TC 本身也是单点，生产要部署集群：TC 挂了，未完成的全局事务既不能提交也不能回滚，分支锁一直占着。2.x 起 TC 支持 Raft 模式做高可用，多个 TC 节点选主；1.x 则靠多节点 + 注册中心做主备。TC 的可用性直接决定全局事务的可用性，TC 的部署规格别比业务服务低。

【小技巧】XA 别和非 XA 资源混在同一个全局事务里：XA 事务里掺一个不参与 XA 的 Redis 写或本地文件写，回滚时那部分不会跟着回滚，数据就裂开了。必须混用时，把非 XA 的操作挪到全局事务之外、改成“事务提交后异步做 + 补偿”，别指望 XA 帮它兜底。

【小技巧】最终一致的方案一定要配对账任务，别只靠重试：本地消息表、Saga、最大努力通知的重试都有上限，重试耗尽后唯一能发现“漏了哪笔”的就是定期对账。银行场景的每日对账文件就是这个角色——按业务主键逐笔核对两边状态，差出来的进异常表人工处理；没有对账，最终一致就只是“希望一致”。

【小技巧】消费者幂等别只靠消息 ID 去重表：消息 ID 去重能防“同一条消息投两次”，但防不住“业务方重复下单产生两条不同消息”。幂等键要用业务主键（订单号、放款流水号），消费前按业务主键查一次“已处理”标记，两层都拦才算严；只做消息级去重，业务重复照样会穿过去。

【小技巧】OceanBase 里“跨库”不等于“跨事务边界”：同一租户同一 OB 集群内的多个库，事务仍由 OB 内部 Paxos + 两阶段提交保证强一致，不用上 Seata；只有跨租户、跨集群、跨 OB 与外部系统时，才需要分布式事务框架。先问“这几个库在不在同一个租户”，再决定要不要上框架，很多“分布式事务需求”到这一步就消失了。

【冷知识】两阶段提交的思想来自 Jim Gray 1978 年的论文《Notes on Data Base Operating Systems》：他最早系统地描述了 2PC 的 Prepare/Commit 两步，以及协调者宕机时的阻塞问题。XA 则是 X/Open 在 1991 年发布的标准接口，把 2PC 落到“事务管理器与资源管理器之间怎么对话”，所以 XA 是 2PC 的接口标准，不是另一个协议。

【冷知识】Seata 最早叫 Fescar：2019 年初阿里巴巴开源时叫 Fescar（Fast & Easy Commit And Rollback），同年 3 月改名 Seata。AT 模式的名字里，A 是 Automatic Transaction——“自动”指的是补偿 SQL 由框架按前后镜像自动生成，业务不用手写，这也是它和 TCC 最大的分工差别。

【冷知识】Saga 这个名字来自 1987 年 Hector Garcia-Molina 与 Kenneth Salem 的论文《Sagas》：他们提出把长事务拆成一串带补偿的子事务，每步失败就按逆序执行已完成步骤的补偿。它比 TCC 更早，是“长事务 + 补偿”这条路线的源头，TCC 可以看作 Saga 在“预留资源”语义上的一个特化。

【冷知识】BASE 这个说法是 2008 年由 eBay 架构师 Dan Pritchett 在《BASE: An Acid Alternative》里推广开来的：基本可用（Basically Available）、软状态（Soft state）、最终一致（Eventually consistent），对应的是 eBay 这类高并发场景“宁可暂时不一致、也不能不可用”的取舍。它不是某个产品的特性，而是一套与 ACID 对照的取舍框架。

【冷知识】OceanBase 的 Paxos 不是经典 Paxos 的照搬：OB 内部用的是 Paxos 的工程化变体（多副本多数派提交 + 日志同步），单租户内跨分区的事务由它保证强一致。这就是原文说“OB 内部完成两阶段提交”的底气——分布式事务的协调成本被收进数据库引擎里了，业务层看不到，但成本并没有消失，只是从应用框架挪到了存储层。

## 9. 面试与自测

- 2PC 的阻塞点在哪？协调者 Commit 阶段宕机会发生什么？
- Seata AT 的 undo_log 为什么必须和业务 SQL 同一个本地事务？
- AT 的全局锁锁的是什么粒度？为什么说它隔离性弱？
- TCC 的空回滚、悬挂分别怎么防？
- 本地消息表方案里，一致性窗口由哪几段耗时构成？怎么缩短？

- Saga 的补偿事务和数据库回滚有什么本质区别？编排式与协同式 Saga 怎么选？

### 参考答案

1. 阻塞点在 Prepare 之后：参与者各自写日志、锁资源但不提交，一直等协调者发话，协调者慢或宕机，参与者全员干等，长事务把连接和行锁占满。协调者 Commit 阶段宕机时，Commit 指令可能只下发了一半，一部分参与者提交、一部分回滚，数据直接不一致，只能靠人工介入。
2. 因为 undo_log 是回滚的唯一依据：RM 拦截业务 SQL，执行前查前镜像、执行后查后镜像，拼成 undo_log 与业务数据在同一个本地事务里提交。如果 undo_log 不在同一事务，业务提交了但 undo_log 没落盘（或反过来），崩溃后要么无法回滚、要么镜像对不上，二阶段回滚就无从谈起。
3. 全局锁锁的是行粒度：两个全局事务并发改同一行时靠锁串行，热点行上吞吐明显掉。隔离性弱是因为全局锁只挡写不挡读：AT 的隔离性是读未提交级别，其他事务能读到可能被回滚的数据，所以上了 Seata 不等于强一致，账务展示口径要想清楚。
4. 空回滚的防法：Try 还没执行、Cancel 先到了，Cancel 里查不到预留记录时也要落一条已回滚标记，不能直接报错。悬挂的防法：Cancel 比 Try 先执行完，迟到的 Try 又预留成功、资源永远冻结，解法是 Try 执行前先查回滚标记，有标记直接拒绝。另外 Confirm 与 Cancel 被重试多次时要幂等：按事务 ID 加分支做状态机，重复调用直接返回成功。
5. 一致性窗口由四段耗时构成：业务数据与消息记录写在同一个本地事务里的时间、定时任务或提交后异步投递的延迟、重试间隔与下游消费处理的时间、消费回执查询与对账核对的周期。缩短办法：事务提交后立即投递而不是等长间隔轮询、失败按短退避间隔重试、提供消费回执查询接口供核对、超过重试上限进死信或异常表由人工或对账任务兜底。窗口最长在秒到分钟级，且每个接入点都要写消息表加补偿扫描加对账，工程量分散在各个业务里。
6. 本质区别是补偿是另一笔正向业务操作、不是回滚：本地事务一旦提交就无法用 SQL 撤销，已扣的钱只能再退一笔、已发的短信只能再发一条取消通知；补偿必须幂等、可重入、逆序执行，且补偿不了的操作要排在链路末尾或接受其语义。选型上：步骤少、反应简单用协同式（各服务监听领域事件、无中心节点、耦合最松，但流程散在监听器里、超 4–5 步后排障成本陡增，且依赖事件总线至少一次投递）；步骤多、要显式控制流与可视化时用编排式（中心协调器按状态机驱动、失败按逆序发补偿，代价是协调器要持久化状态、成了新单点，Seata Saga 模式与 Temporal/Cadence 都是这种落地）。
