# 分布式事务

## 1. 核心概念

单库事务靠数据库自己的 ACID 就够了。一旦一次业务要写**两个库、或两个服务**（下单扣库存、放款同时记账和通知），本地事务管不到对面，分布式事务解决的是这种跨边界的一致性。

先把预期摆正：

- **CAP**：分区出现时，一致性（C）和可用性（A）只能选一个。金融核心选 CP，互联网高并发多选 AP + 最终一致。
- **BASE**：基本可用、软状态、最终一致——柔性事务的理论底座，与 ACID 的刚性事务相对。
- 刚性方案（XA）强一致但吞吐差；柔性方案（TCC、本地消息表、Saga）都是最终一致，差别在侵入程度和补偿怎么写。**选型的第一问题永远是：这笔业务能不能接受最终一致**（秒级到账 vs 分钟级对账兜底）。

## 2. 2PC 与 XA

两阶段提交：协调者先问所有参与者「能提交吗」（Prepare，各自写日志、锁资源但不提交），全票通过再统一 Commit，有一票否决就全 Rollback。XA 是它在数据库层的标准接口，MySQL、OceanBase（MySQL 模式）都支持 XA 语句。

缺点是结构性的：

- **同步阻塞**：Prepare 后资源一直锁着等协调者发话，协调者慢或宕机，参与者全员干等，长事务把连接和行锁占满。
- **协调者单点 + 脑裂窗口**：Commit 指令下发一半协调者挂了，一部分提交一部分回滚，数据直接不一致，只能靠人工介入。
- 所以 XA 只适合参与者少、事务短、内部可控的场景（如同一中间件管的两个库），跨公司、跨系统的长链路不要用。

## 3. Seata AT 模式

Seata 是国内最常用的框架，三种角色：TC（事务协调者，独立部署的 Server）、TM（发起方，定义全局事务边界）、RM（参与方，管本地分支）。

AT 模式的主意是**把补偿自动化**：

1. 一阶段：RM 拦截业务 SQL，执行前先查出前镜像、执行后查出后镜像，拼成 `undo_log` 与业务数据**在同一个本地事务里**提交，同时向 TC 注册分支并申请全局锁。
2. 二阶段提交：TC 通知各分支删除 undo_log，异步清理，快。
3. 二阶段回滚：RM 用 undo_log 的前镜像反向生成补偿 SQL 恢复数据；恢复前校验当前数据与后镜像一致，不一致说明被全局事务之外改过（脏写），直接告警人工处理。

要点与代价：

- 对业务无侵入（不用写补偿代码），但隔离性是**读未提交**级别：全局锁只挡写不挡读，两个全局事务并发改同一行靠锁串行，热点行上吞吐明显掉。
- 每张参与的表都要有主键、要建 `undo_log` 表；批量 SQL、无主键更新会让镜像生成失败或变慢。
- 全局事务别包太长：AT 的锁持有到二阶段结束，链路里掺远程调用、人工审批等于把锁放大，先想清楚边界。

## 4. TCC 模式

Try（预留资源：冻结金额、置中间状态）→ Confirm（真扣减）→ Cancel（释放预留），三个方法全部由业务自己实现，框架只负责编排和重试。性能好、锁定粒度自己控制，代价是每个服务都要写三套逻辑。

三个必踩的坑，面试和生产都高频：

| 坑 | 现象 | 解法 |
|---|---|---|
| 空回滚 | Try 还没执行，Cancel 先到了 | Cancel 里查不到预留记录时也要落一条「已回滚」标记，不能直接报错 |
| 悬挂 | Cancel 比 Try 先执行完，迟到的 Try 又预留成功，资源永远冻结 | Try 执行前先查回滚标记，有标记直接拒绝 |
| 幂等 | Confirm/Cancel 被重试多次 | 按事务 ID + 分支做状态机，重复调用直接返回成功 |

Seata TCC、以及手动实现的「冻结表」模式，本质都绕不开这三件事。

## 5. 本地消息表与最大努力通知

思路是降级成可靠消息问题，不再追求强一致：

1. 业务数据与一条消息记录**写在同一个本地事务**里（消息表在业务库）。
2. 定时任务或事务提交后异步把消息投到 MQ；下游消费成功回执（或提供查询接口供核对），失败按退避间隔重试。
3. 超过重试上限的进死信/异常表，人工或对账任务兜底。

这与 [消息可靠性](消息队列/消息可靠性.md) 是同一套组合拳：本地消息表解决「消息发不出去」，消费幂等解决「消息重复投」。**最大努力通知**是它的对外版：给外部系统（如支付结果通知商户）按固定间隔重试 N 次，再提供主动查询接口让对方兜底，不承诺必达。

优点：无框架锁定、无额外锁、吞吐高。缺点：一致性窗口最长（秒到分钟级），且每个接入点都要写消息表 + 补偿扫描 + 对账，工程量分散在各个业务里。

## 6. 项目落点与选型（OceanBase 场景）

先说 OceanBase 的特殊性:OB 本身是分布式数据库,**单个租户内的事务由 OB 内部保证强一致**(Paxos 多副本 + 两阶段提交在引擎内部完成)。很多在 MySQL 分库分表架构下被迫上分布式事务的场景,搬到 OB 后可以靠**不拆库**直接消解——业务表放同一租户同一库,本地事务就够了。这也是 ao 在神农 e 贷项目里的默认取舍顺序:

1. **能收敛到同库就收敛**:审批、额度、台账在同一 OB 库内,普通本地事务,别为了"架构先进"引入 Seata。
2. **跨系统写**(调信贷核心、征信、短信平台):对方不可能参与你的事务协调,老老实实用本地消息表 + 状态机 + 每日对账文件兜底,这是银行系统的常规打法。
3. **真的需要近实时强一致且参与方都在自己手里**:再考虑 Seata AT;TCC 只用在金额冻结这类已经有明确预留语义的点上,不要全链路铺开。

决策一句话:**先降级问题(收敛边界),再选框架**;分布式事务框架是最后一招,不是默认项。

## 7. 常见误区

- 误区：上了 Seata 就是强一致。AT 是最终一致 + 写锁，全局读到的是可能被回滚的数据，账务展示口径要想清楚。
- 误区：XA 和 2PC 是两个方案。XA 是 2PC 的接口标准，Seata 的 XA 模式也是它。
- 误区:本地消息表只管发不管查。没有消费回执查询和对账,消息发出去了对方没处理,你永远不知道。
- 误区:补偿逻辑随便写写。补偿必须幂等、可重入、且要处理"补偿时数据已被正常流程改过"的情况,这正是 TCC 三坑的来源。

## 8. 面试与自测

- 2PC 的阻塞点在哪？协调者 Commit 阶段宕机会发生什么？
- Seata AT 的 undo_log 为什么必须和业务 SQL 同一个本地事务？
- AT 的全局锁锁的是什么粒度？为什么说它隔离性弱？
- TCC 的空回滚、悬挂分别怎么防？
- 本地消息表方案里，一致性窗口由哪几段耗时构成？怎么缩短？

### 参考答案

1. 阻塞点在 Prepare 之后：参与者各自写日志、锁资源但不提交，一直等协调者发话，协调者慢或宕机，参与者全员干等，长事务把连接和行锁占满。协调者 Commit 阶段宕机时，Commit 指令可能只下发了一半，一部分参与者提交、一部分回滚，数据直接不一致，只能靠人工介入。
2. 因为 undo_log 是回滚的唯一依据：RM 拦截业务 SQL，执行前查前镜像、执行后查后镜像，拼成 undo_log 与业务数据在同一个本地事务里提交。如果 undo_log 不在同一事务，业务提交了但 undo_log 没落盘（或反过来），崩溃后要么无法回滚、要么镜像对不上，二阶段回滚就无从谈起。
3. 全局锁锁的是行粒度：两个全局事务并发改同一行时靠锁串行，热点行上吞吐明显掉。隔离性弱是因为全局锁只挡写不挡读：AT 的隔离性是读未提交级别，其他事务能读到可能被回滚的数据，所以上了 Seata 不等于强一致，账务展示口径要想清楚。
4. 空回滚的防法：Try 还没执行、Cancel 先到了，Cancel 里查不到预留记录时也要落一条已回滚标记，不能直接报错。悬挂的防法：Cancel 比 Try 先执行完，迟到的 Try 又预留成功、资源永远冻结，解法是 Try 执行前先查回滚标记，有标记直接拒绝。另外 Confirm 与 Cancel 被重试多次时要幂等：按事务 ID 加分支做状态机，重复调用直接返回成功。
5. 一致性窗口由四段耗时构成：业务数据与消息记录写在同一个本地事务里的时间、定时任务或提交后异步投递的延迟、重试间隔与下游消费处理的时间、消费回执查询与对账核对的周期。缩短办法：事务提交后立即投递而不是等长间隔轮询、失败按短退避间隔重试、提供消费回执查询接口供核对、超过重试上限进死信或异常表由人工或对账任务兜底。窗口最长在秒到分钟级，且每个接入点都要写消息表加补偿扫描加对账，工程量分散在各个业务里。
