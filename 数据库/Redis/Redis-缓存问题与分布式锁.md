# Redis 缓存问题与分布式锁

> 《Redis》总篇里有三大问题的简版和锁的四件套；本篇展开对策细节、一致性方案和 Redisson 的正确用法。

## 1. 穿透 / 击穿 / 雪崩：先分清再对症

| 问题 | 本质 | 典型触发 | 核心对策 |
|---|---|---|---|
| 穿透 | 查**根本不存在**的数据，缓存永远不命中 | 恶意构造不存在的 id、参数错误 | 空值缓存、布隆过滤器、入口参数校验 |
| 击穿 | **单个热点 key** 过期瞬间并发回源 | 大促商品详情、首页配置过期 | 互斥锁回源、逻辑过期、热点永不过期+异步刷新 |
| 雪崩 | **大量 key 同时**失效或 Redis 整体不可用 | 批量灌数据时统一过期时间、宕机 | 过期时间随机化、多级缓存、集群高可用、限流降级 |

```bash
# 穿透对策 1：空值缓存（短过期，防被刷穿的同时不长期占位）
SET user:9999 "" EX 60        # DB 查不到时回写空占位

# 雪崩对策：过期时间 = 基础值 + 随机抖动，如 EX 3600 改为 3600 + random(0,600)
```

- 布隆过滤器适合「全量 id 可枚举」的场景（商品、用户），把全部合法 id 预热进去，不存在的直接拦在缓存层之前；代价是有误判率且删除麻烦，用前评估。
- 击穿的互斥锁回源：拿不到锁的请求短暂等待后重试读缓存，不要一起去查 DB；锁要设短过期防回源方宕机死锁。

### 逻辑过期（解决击穿的工程常用法）

value 里存数据 + 逻辑到期时间，缓存本身不设 TTL：读到逻辑已过期时，只放一个请求异步去重建，其余请求先返回旧值。牺牲短暂一致性换可用性，适合商品详情这类能容忍秒级旧数据的场景。

## 2. 缓存一致性

主流方案是 **Cache Aside：先更新 DB，再删除缓存**：

1. 写：更新 DB → 删缓存。下次读自然回源重建。
2. 为什么删而不是更新缓存：并发写时更新缓存容易写回旧值；删除最简单且幂等。
3. 为什么先 DB 后删：先删再更新 DB，中间的读会把旧值回填成缓存，脏的时间更长。

残余不一致窗口仍然存在（删缓存失败、并发读写交错），按业务强度补：

- **延迟双删**：更新 DB 后删一次，延迟几百毫秒再删一次，清掉并发读回填的旧值。延迟时间靠经验，不精确，适合一致性要求中等的场景。
- **删失败重试**：删缓存走消息队列/重试任务，保证最终删掉。
- **订阅 binlog**（如 Canal）：以 DB 变更为准统一失效缓存，与业务代码解耦，系统复杂但最可靠，见《MySQL-binlog》的 CDC 用法。

结论口径：**缓存与 DB 做不到强一致，只能选不一致窗口的大小**。余额、库存这类强一致数据不要以缓存为准做决策，缓存只做展示加速。

## 3. 分布式锁：正确形态

自己实现只记四件套（《Redis》总篇有代码）：`SET key uuid NX PX 超时` 加锁、uuid 标识归属、Lua 比对后解锁、超时要大于业务耗时。生产直接用 Redisson：

```java
RLock lock = redissonClient.getLock("lock:order:1001");
try {
    // waitTime 内抢不到就放弃；leaseTime 传 -1 时启用看门狗自动续期
    if (lock.tryLock(3, -1, TimeUnit.SECONDS)) {
        // 业务逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

### 看门狗（Watchdog）

- Redisson 默认锁超时 30 秒，看门狗每 10 秒检查：业务还没执行完就把锁续到 30 秒，直到业务结束或客户端宕机。
- 前提是 `leaseTime` 不手动指定：一旦自己传了固定租期，看门狗不生效，业务超时了锁照样提前释放。
- 看门狗救不了网络分区和进程假死（GC 长暂停）：暂停期间锁过期、别人拿到锁，本进程恢复后会和对方同时进临界区。强正确性场景要在业务层再加校验（如 DB 唯一约束、版本号），别把锁当唯一防线。

## 4. 锁的常见误用

1. **解锁不校验归属**：直接 `DEL` 会删掉别人的锁（自己的锁已过期、别人新建了同名锁）。必须比对 uuid 或用 Redisson。
2. **锁粒度过大**：一把全局锁串行化所有请求。按业务键细化（`lock:order:{id}`），不同订单互不阻塞。
3. **锁住非临界操作**：把远程调用、复杂计算也放锁里，持有时间不可控。锁内只放必须互斥的最小代码段。
4. **不可重入还递归调用**：同线程重复加同一把普通锁会自己等自己；Redisson 的 `RLock` 是可重入的，手写实现一般不是。
5. **拿锁做强一致裁决**：Redis 主从异步复制下，主节点宕机切换可能丢锁（刚加的锁还没同步到从节点）。秒杀库存、资金类决策要用 DB 事务兜底，锁只做削峰。

## 5. 排障速查

```bash
# 锁 key 还在不在、剩余多久
TTL lock:order:1001
GET lock:order:1001          # 值是 uuid/线程标识，看是谁的锁

# 怀疑缓存被打穿时先看命中率和回源量
INFO stats                   # keyspace_hits / keyspace_misses
```

- 现象「偶发重复执行」先查三件事：锁是否提前过期（业务耗时 vs 租期）、解锁是否删了别人的锁、是否发生了主从切换。

## 6. RedLock 争议与 fencing token

### RedLock 是什么

RedLock 是 Redis 作者提出的跨实例锁：向 5 个独立 Redis 主节点用同一个随机值加锁，拿到多数派才算加锁成功，锁有效期按 TTL 减去加锁耗时与时钟漂移 allowance 计算。Redisson 提供 `RedissonRedLock` 实现。本篇 §3 的看门狗、§4 的误用口径对它同样适用。

### Kleppmann 的质疑（2016，《How to do distributed locking》）

1. **依赖时间假设**：算法成立要求有界网络延迟、有界执行时间、各节点时钟大体同步。时钟跳变、GC 长暂停、进程假死都会打破假设，锁在持有者不知情时过期。
2. **不产生 fencing token**：即使 RedLock 本身实现完美，旧持有者醒来后仍可能误写——因为锁只回答“谁持有”，不回答“这次持有比上次新多少”。
3. **结论“既非鱼也非鸟”**：只做效率锁时 5 节点太重；做正确性锁时又不够安全。Antirez 回应称时间假设在实践中可接受，但“没有单调令牌”这一点没有争议。

### 适用边界

- 只做削峰、去重、防重复提交这类**效率场景**可用 RedLock，代价可接受。
- 资金、库存扣减等**正确性场景**不要只靠 RedLock：用共识系统（如 ZooKeeper/Curator）或 DB 事务、唯一约束兜底；本篇 §4 第 5 条的口径与此一致。

### fencing token：防旧持有者误写的正解

- 机制：锁服务每次发放**严格递增**的令牌；写路径每次携带令牌，存储侧记住已见最大令牌，低于它的写一律拒绝。
- 经典例子：A 持 token 33 后 GC 暂停、锁过期；B 持 token 34 写成功，存储侧记住 34；A 醒来持 33 再写，被拒绝——旧权威永远变不成现权威。
- 两点缺一不可：令牌必须由锁服务或共识系统发放（保证单调），存储侧必须强制比对（保证执行）。Redis 单实例的 uuid 只能标识归属、不能比大小，**不等于** fencing token。

## 7. 锁验证方法论：四项演练与判定标准

本篇 §3 到 §6 讲的是锁应该长什么样；本节讲怎么证明它真的长这样。**验证只在测试／预发布环境做**，不要拿生产流量演练 failover 和拨时钟；生产侧只做只读观测（TTL、复制偏移量、告警）。

### 1. 验证续期真的生效

演练步骤：

1. 用 Redisson 以 `leaseTime = -1`（看门狗开启）加锁，锁 TTL 默认 30 秒；业务任务里 sleep 70 秒，模拟长任务超过 TTL。
2. 任务执行期间每 5 秒执行一次 `TTL lock:xxx`，记录 TTL 变化曲线；同时另起一个客户端尝试抢同一把锁。
3. 对照组：同一任务改用固定 `leaseTime = 30`（看门狗关闭），再跑一次 70 秒任务。

判定标准：

- 通过：看门狗组任务全程 TTL 始终回弹（从未归零），另一客户端始终抢不到锁，任务正常结束；对照组 30 秒后锁释放、他人可抢——两组行为不同，证明续期确实是看门狗在做，不是 TTL 本来就长。
- 失败：看门狗组任务中途 TTL 归零且他人拿到锁（双执行），说明续期没生效，先查是否误传了固定 leaseTime（传了固定租期看门狗不生效，见 §3）。

续期失败告警验证：

1. 对持锁进程发 `kill -STOP <pid>` 模拟假死（看门狗线程同样被冻住），观察锁在 TTL 到期后释放。
2. 检查告警链路：锁过期事件、业务中断日志、监控告警是否在 TTL 的 1 到 2 倍时间内到达。

判定标准：通过是告警准时到达且能定位到具体锁 key；失败是锁丢了却没有任何告警——这比丢锁本身更危险，等于裸奔。

还有一条容易漏的：**续期只续自己的锁**。演练：A 的锁过期后 B 拿到同名锁，A 的看门狗醒来后不应给 B 的锁续期（Redisson 靠线程标识＋uuid 校验续期对象）。判定：B 的锁 TTL 曲线不受 A 的看门狗影响；一旦发现 A 的残留续期动了 B 的锁，就是续期校验实现有问题。

### 2. 验证误删防护

演练步骤：

1. A 以 uuid-A 加锁，TTL 设短（如 5 秒）；让 A 的锁自然过期。
2. B 以 uuid-B 加同名锁成功。
3. A 的业务此时才跑完，执行释放逻辑（Lua 脚本按 uuid-A 比对后删除）。

判定标准：

- 通过：Lua 脚本返回 0、key 未被删除，B 的锁值仍为 uuid-B，B 的业务不受影响。
- 失败：key 被删或值被清空，B 中途失锁——说明释放路径没有按持有者标识校验（大概率是裸 `DEL`，见 §4 第 1 条）。

反面复现（用于证明 Lua 的必要性）：同一演练把释放换成裸 `DEL`，应稳定复现误删。复现不了反而要怀疑：是不是测试里 A、B 根本没跑出“过期后易主”这个时序。

原子性验证：多线程同时对同一把锁发起释放，只有持有者那一路返回 1，其余返回 0，且 key 的最终状态唯一。判定：出现两次返回 1，或 key 状态在并发释放后不一致，说明“先 GET 再 DEL”拆成了两步，中间窗口真实存在。

### 3. 验证主从切换不丢锁

先说清验证目标：**单 Redis 架构下，这项验证的目的不是证明“不丢锁”，而是复现丢锁、量出窗口**。复现成功本身就是有效结论——它告诉你这个架构能不能扛你的业务。

演练步骤（哨兵架构为例，集群架构同理）：

1. 客户端在旧主上 `SET lock:xxx uuid NX EX 30` 成功。
2. 立即 kill 旧主进程（或 `SHUTDOWN`），在复制窗口内触发哨兵 failover，提拔从节点为新主。
3. failover 完成后，在新主上执行 `GET lock:xxx`，并让另一客户端尝试 `SET lock:xxx uuid2 NX EX 30`。
4. 量窗口：演练前后分别执行 `INFO replication`，对比 `master_repl_offset` 与从节点的复制偏移量，估算复制延迟量级。

判定标准：

- 丢锁复现（预期内）：新主上查不到该 key，且另一客户端加锁成功——异步复制窗口内的锁确实丢了。此时结论不是“测试失败”，而是“该业务若不能容忍丢锁，此架构不合格”。
- 架构合格判定：只有当业务明确容忍“failover 窗口内锁丢失”（削峰、去重类效率场景），且窗口量级远小于业务可接受误差时，单 Redis 才算通过；资金、库存类正确性场景在此项上直接判不合格，见分布式锁实现与选型篇的主从异步复制丢锁一节。
- RedLock 版演练：5 节点中 kill 掉 1 到 2 个节点，加锁仍应成功（多数派）；被 kill 的节点重启后，应延迟一段时间（大于锁的最大 TTL）再重新对外授锁，否则它以空锁表复活，会把已授出的锁再授给别人。

### 4. 验证时钟漂移与 fencing 代次

时钟漂移演练（测试环境）：

1. 手动拨快持锁节点的时钟（如 `date -s` 快进 60 秒），观察依赖 TTL 的锁是否提前过期；再拨慢，观察过期是否延迟。
2. 同一演练在 ZooKeeper／etcd 锁上跑一遍作对照（这两类锁不依赖时钟，见分布式锁实现与选型 §6）。

判定标准：通过是漂移量与锁行为的对应关系被记录下来，且业务在漂移下的表现符合预期（靠 fencing 兜底，而不是指望锁本身扛漂移）；失败是漂移后出现双写且没有任何拦截——说明正确性链路上缺了 fencing。

fencing 代次测试用例（令牌由锁服务或共识系统发放、存储侧强制比对，两点缺一不可，机制见 §6）：

| 用例 | 操作 | 判定 |
|---|---|---|
| 正常递增 | A 持 token 34 写 | 通过，存储侧记住 34 |
| 旧代次重放 | A 暂停后醒来，持 token 33 再写 | 必须被拒绝，且有明确拒绝日志或错误码 |
| 并发抢代次 | 两个客户端同时申请新令牌 | 只有一个拿到最新代次，另一个的写被拒绝 |
| 令牌服务故障 | 令牌发放方不可用时写路径发请求 | 必须事先定好 fail-closed（拒绝写）还是 fail-open（放行），且实测行为与定好的口径一致；没定口径就上线，判不合格 |

## 面试与自测

1. Cache Aside 为什么是先更新 DB 再删除缓存，而不是先删缓存或更新缓存？
2. Redisson 看门狗的默认行为和生效前提是什么？它救不了哪两类问题？
3. RedLock 为什么被质疑“既非鱼也非鸟”？fencing token 的机制是什么，为什么 Redis 单实例的 uuid 不等于 fencing token？

### 参考答案

1. 先删再更新 DB 时，中间的读会把旧值回填成缓存，脏的时间更长；先更新 DB 再删缓存，下次读自然回源重建。删而不是更新缓存，是因为并发写时更新缓存容易写回旧值，而删除最简单且幂等。残余不一致窗口仍存在，可按业务强度补延迟双删、删失败重试或订阅 binlog（如 Canal）。
2. 默认锁超时 30 秒，看门狗每 10 秒检查，业务没执行完就把锁续到 30 秒，直到业务结束或客户端宕机。前提是 `leaseTime` 不手动指定：一旦传了固定租期，看门狗不生效，业务超时了锁照样提前释放。它救不了网络分区和进程假死（如 GC 长暂停）：暂停期间锁过期、别人拿到锁，本进程恢复后会和对方同时进临界区，强正确性场景要在业务层再加校验（如 DB 唯一约束、版本号）。
3. RedLock 向 5 个独立 Redis 主节点用同一个随机值加锁，拿到多数派才算成功，锁有效期按 TTL 减去加锁耗时与时钟漂移 allowance 计算。Kleppmann 的质疑是：算法依赖有界网络延迟、有界执行时间、各节点时钟大体同步等时间假设，时钟跳变、GC 长暂停、进程假死都会打破假设；且它不产生 fencing token，旧持有者醒来后仍可能误写。所以只做效率锁时 5 节点太重，做正确性锁时又不够安全。fencing token 的机制是锁服务每次发放严格递增的令牌，写路径每次携带令牌，存储侧记住已见最大令牌、低于它的写一律拒绝，令牌由锁服务或共识系统发放与存储侧强制比对两点缺一不可；Redis 单实例的 uuid 只能标识归属、不能比大小，不等于 fencing token。
