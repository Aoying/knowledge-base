# Redis 集群与哨兵

## 1. 核心概念

单机 Redis 的上限很明确：内存装不下、单核 CPU 处理命令串行、机器挂了就全停。从单机走向高可用/可扩展有三级台阶：

| 形态 | 解决什么 | 不解决什么 |
|---|---|---|
| 主从复制 | 读扩展、数据冗余备份 | 自动故障转移、写扩展、容量 |
| 哨兵（Sentinel） | 在主从之上加自动故障转移 | 容量扩展（数据还是全量一份逻辑上） |
| Cluster 模式 | 数据分片，容量和写吞吐水平扩展 + 自带故障转移 | 多键操作、运维简单度 |

选哪级看瓶颈：**只是怕挂 → 主从 + 哨兵；内存不够/写 QPS 顶不住 → Cluster**。哨兵不是 Cluster 的低配版，两者解决的问题维度不同，不要混为一谈。

## 2. 基础知识

### 主从复制

- 从节点通过 `replicaof` 向主节点发起同步：先全量同步（主节点 fork 出子进程生成 RDB，快照期间的新写命令进复制缓冲区），再持续增量同步命令流。
- 复制是**异步**的：主节点写成功不等从节点确认。主节点宕机时未同步的数据会丢——这是后面脑裂丢数据的根源。
- 读扩展：一主多从分摊读流量，但从节点数据有延迟，**读己之写**场景（刚下单就查订单）必须强制读主或做延迟等待。
- 关键参数：`repl-backlog-size`（增量同步环形缓冲区，太小会导致断线重连时频繁全量同步）、`min-replicas-to-write`（见脑裂一节）。

### 哨兵机制

哨兵是独立进程，专门干三件事：**监控**（定时 PING 所有节点）、**通知**（故障转移后告知客户端新主地址）、**自动故障转移**。

- 主观下线（SDOWN）：单个哨兵认为主节点不可达。
- 客观下线（ODOWN）：超过 `quorum`（法定人数）个哨兵都报告主观下线，判定主节点确实挂了，才触发选举和故障转移。
- 哨兵之间先用 Raft 式选举选出一个领头哨兵，由它执行转移：从从节点中挑一个（按优先级、复制偏移量、runID 综合排序）提升为新主，其余从节点改指向新主，旧主恢复后自动降为从节点。
- 客户端通过哨兵获取当前主地址（Spring Data Redis、Jedis、Lettuce 都支持 Sentinel 模式），应用不要把主节点地址写死。

哨兵数量必须是**奇数且 ≥ 3**，且要部署在不同机器上——哨兵和 Redis 节点全挤在一台机器上，机器一挂全军覆没，高可用形同虚设。

## 3. 进阶知识

### 脑裂与数据丢失

脑裂场景：主节点所在机房网络分区，主节点其实活着但哨兵联系不上，哨兵在另一分区选出新主；老主继续接收客户端写入（客户端还没感知切换）。分区恢复后老主降为从节点，它上面那批「分区期间的写入」被全量同步直接覆盖清掉。

两个层面的解法：

1. **减少发生**：`min-replicas-to-write 1` + `min-replicas-max-lag 10`——主节点发现自己连不上足够从节点时拒绝写入，宁可不可用也不写孤岛数据。这是拿可用性换一致性，金融场景应该开。
2. **接受并补偿**：缓存定位是可丢数据（重要数据落 DB、Redis 只做加速），脑裂丢的是缓存，靠回源重建。Redis 里存的是不可重建的权威数据时，先反问架构：它不该只存在 Redis 里。

### Cluster 模式与哈希槽

Cluster 把键空间切成 **16384 个哈希槽（slot）**：`slot = CRC16(key) % 16384`，每个主节点负责一段槽，槽可以在节点间迁移（扩缩容就是搬槽）。

- **为什么是 16384**：节点间心跳包要携带槽位图，16384 个槽用位图表示是 2KB，节点数上限约 1000 时心跳开销可接受；槽太多心跳包就爆了。
- **哈希标签（hash tag）**：key 写成 `user:{1001}:profile` 时只对 `{}` 内的部分算槽，可以把一组相关 key 钉在同一槽——这是 Cluster 里做多键操作的唯一正道。
- **重定向**：客户端连错节点时，节点返回重定向而不是代为转发：
  - `MOVED`：槽已永久迁到另一节点，客户端应刷新本地槽位缓存，后续直连新节点；
  - `ASK`：槽正在迁移中，这次请求临时去目标节点（先发 `ASKING`），客户端不要更新缓存。
  智能客户端（Lettuce、JedisCluster）会缓存槽位映射，所以 Cluster 扩容后偶发 MOVED 是正常现象，频繁出现才需要查槽位状态。
- **多键限制**：`MGET`、多键事务、`KEYS` 类命令要求所有 key 在同一槽，否则报 `CROSSSLOT`。Lua 脚本同理，脚本里用到的 key 必须同槽。设计 key 时就要用 hash tag 把「需要一起操作」的 key 归组，这是 Cluster 上线前评审的重点。

## 4. 原理剖析

### 全量同步为什么贵

主节点 fork 子进程写 RDB 时用写时复制（COW）：同步期间主节点每修改一个内存页就复制一份，写流量越大、同步越久，额外内存占用越高，极端情况内存翻倍直接 OOM。所以大内存实例（几十 GB）的从节点重建要避开业务高峰，`repl-backlog-size` 要给足（经验值按复制延迟和写速率估算，常见 256MB–1GB），让短暂断线走增量同步（PSYNC）而不是全量。

### Cluster 的故障转移

Cluster 没有哨兵，节点间用 Gossip 协议互探：节点标记某主节点 `PFAIL`（疑似下线），集群多数主节点都报告后标记 `FAIL`，触发该主节点的从节点发起选举（同样是 Raft 式投票，多数派授权），胜出的从节点接管槽位并广播新拓扑。参数 `cluster-node-timeout` 决定判定速度，太小误判、太大切换慢，一般 5–15 秒量级按业务容忍度调。

### 一致性定位

无论哨兵还是 Cluster，Redis 的复制都是异步的，故障转移**必然有丢数据窗口**，官方定位就是 AP（可用性优先）。需要强一致的场景（余额、库存扣减的权威判断）不要拿 Redis 当唯一真相源，用 DB 事务/分布式锁校验兜底，或把关键计数放 DB、Redis 只做前置削峰。

## 5. 实战应用

### 选型对比

| 维度 | 主从 + 哨兵 | Cluster |
|---|---|---|
| 数据容量 | 受单机内存限制（全量数据一份） | 多主分片，总容量 = 各主之和 |
| 写吞吐 | 单主上限 | 多主并行扩展 |
| 故障转移 | 哨兵自动切换，秒级到几十秒 | 内置选举，秒级 |
| 多键/事务/Lua | 完整支持 | 必须同槽（hash tag） |
| 客户端 | 连哨兵取主地址，简单 | 需智能客户端维护槽位缓存 |
| 运维复杂度 | 低，3 哨兵 + 一主多从即可 | 高，最少 3 主 3 从起步，槽迁移要演练 |
| 典型规模 | 数据量 < 单机内存，读多写少 | 数据量大、写并发高、大促型业务 |

结论口径：**数据能装进一台机器、只是要高可用，哨兵足够，别为了「先进」上 Cluster**；数据量奔着几百 GB 去或写 QPS 单主扛不住，再上 Cluster。银行内网项目（ao 的环境）以哨兵居多——数据量可控、运维人力有限、还要过稳定性审查，Cluster 的槽运维成本不划算；互联网大流量缓存层则相反，Cluster 是默认选项。

### 部署要点

- 哨兵、Redis 实例分机部署；哨兵配置里的 `quorum` 一般设为哨兵数过半（如 3 个哨兵设 2）。
- 内存上限 `maxmemory` 必设，配合淘汰策略；Redis 当缓存用 `allkeys-lru/lfu`，当队列/存储用禁止淘汰并靠告警扩容。
- 持久化：缓存场景可关 RDB/AOF 换性能，但要接受重启冷启动冲击；混用部署保持一主一从开 AOF。
- 大 key 和热 key 治理在集群下更重要：一个大 key 只会压垮它所在的那个分片，扩容解决不了。

## 6. 疑难杂症

- **故障转移后客户端还往老主写**：客户端没走哨兵/没有重连刷新拓扑，或连接池里存着旧连接。检查客户端是否用的 Sentinel 模式、故障转移通知（+switch-master）是否被消费，转移演练时抓包验证。
- **从节点频繁全量同步**：先看 `repl-backlog-size` 是否太小和网络抖动，再看主节点内存是否大到快照生成时间过长。`master_repl_offset` 与从节点 offset 差距持续拉大，就是增量追不上的信号。
- **Cluster 偶发 CROSSSLOT 报错**：新上线的多键操作没做 hash tag 归组。逐条排查报错命令的 key 集合，统一加 `{}` 标签，注意加标签会改变槽位，存量数据要迁移或双读过渡。
- **MOVED 报错刷屏**：多半是扩缩容后客户端槽位缓存没刷新，或用了不支持重定向的客户端/代理。重启客户端可临时恢复，根治是升级智能客户端并检查 `cluster_state`。
- **哨兵迟迟不切换**：`down-after-milliseconds` 设得太大、quorum 设得比存活哨兵数还高、或哨兵之间网络不通。逐项核对哨兵日志的 SDOWN/ODOWN 记录定位卡点。
- **切换瞬间批量请求失败**：切换窗口内连接被重置属正常现象，客户端必须配置重试（Lettuce 的拓扑刷新 + 命令重试），业务层对非幂等写要做幂等校验，别把切换窗口的失败当数据错误处理。

## 7. 常见误区

- **哨兵只有 1 个或 2 个**：1 个哨兵自己就是单点；2 个哨兵 quorum 设 2 时挂一个就永远达不成客观下线。至少 3 个、奇数部署。
- **把从节点延迟当不存在**：秒杀、发券这类强一致读打从节点，必然出现「刚写查不到」的客诉。用哨兵不等于读写分离可以不分场景。
- **Cluster 里随手用多 key 命令**：单机时代写惯的 `MSET`、跨 key 事务搬到 Cluster 直接 CROSSSLOT，上线前必须全量扫描多键操作。
- **觉得上了集群就不用管大 key**：分片均衡的是 key 数量不是 key 大小，一个 500MB 的大 key 在哪个分片哪个分片倒霉。
- **用 KEYS 做生产查询**：单机阻塞、Cluster 还要逐节点扫，生产一律用 SCAN 或提前建索引结构。

## 8. 性能优化

- **复制链路优化**：无盘复制（`repl-diskless-sync`）避免大实例落盘 RDB 的 IO 峰值；从节点多时考虑级联复制（从连从）给主节点减压。
- **槽位均衡**：Cluster 扩容后用 `cluster rebalance` 均摊槽位，迁移安排在低峰并限速，迁移中的 ASK 重定向会增加一跳延迟。
- **热 key 打散**：读热点 key 做多副本（如 key 后缀随机分片 + 客户端随机选）或本地缓存兜一层，别让单个分片承接全部热点流量。
- **连接与管道**：客户端用连接池 + pipeline 批量命令；Cluster 下 pipeline 的 key 要按槽分组发送，客户端一般已封装，注意版本支持。
- **监控四件套**：复制延迟（offset 差）、内存碎片率（`mem_fragmentation_ratio` > 1.5 关注）、慢日志、逐分片内存/ops 分布——只监控集群总量会掩盖单分片倾斜。

## 9. 版本差异

- **Redis 5.0**：Cluster 总线与复制优化，Stream 结构落地，哨兵/Cluster 仍是 6.x 之前的主力形态。
- **Redis 6.0**：多线程 IO（命令执行仍单线程）、ACL、客户端缓存；对集群的影响主要在单节点吞吐上限抬高，哨兵切换逻辑无本质变化。
- **Redis 7.x**：多 AOF、函数（Functions）、分片发布订阅（SSUBSCRIBE 按槽分发，解决老版本广播全集群的问题）；从 7.0 起 ACL 选择器、命令元数据等运维能力补齐。新建集群直接上 7.x，不要再部署 5.x。
- **RESP3 与客户端**：新客户端默认协议升级对 Cluster 槽位缓存和重定向处理更完善，老客户端（早期 Jedis）在 MOVED 处理上有过兼容坑，升级时一并核对客户端版本矩阵。

## 10. 槽位、节点数与故障转移定量

本节所有数字均为手算，Python 3 本地复算（见节末“### 复算口径”）。【官方】指 Redis 官方文档 / Cluster spec 的事实，核验日期 2026-11-08；【估算】指在明确写出的简化假设下手算的结果，不是官方数字、不是实测值，换一组假设数字会变。本节不重复原文第 3 节的槽位定义与第 4 节的故障转移流程，只补定量。

### 10.1 槽位分配：3 主与 6 主时每节点多少槽、多少 key

【官方】Redis Cluster 固定 16384 个槽，`HASH_SLOT = CRC16(key) mod 16384`，每个主节点负责一段槽。均分时每节点槽数 = 16384 / 主节点数，16384 除不尽就差 1 个槽——槽数差 1 不是不均衡，是整数除法的余数。

【估算】假设 key 在 16384 个槽上均匀分布（CRC16 分布均匀是 spec 的表述，实际业务 key 是否均匀要看 key 的写法），key 总量取 1,000 万：

| 主节点数 | 每节点槽数 | 每节点 key 占比 | 每节点 key 数（1,000 万总量） |
|---|---|---|---|
| 3 | 5462、5461、5461 | 各约 1/3 | 约 333 万 |
| 6 | 2731、2731、2731、2731、2730、2730 | 各约 1/6 | 约 167 万 |
| 4（对照） | 各 4096 | 各 1/4 | 各 250 万 |

具体槽段（均分、从 0 开始连续切）：3 主是 0–5461、5462–10922、10923–16383；6 主是 0–2730、2731–5461、5462–8192、8193–10923、10924–13653、13654–16383。验算：5462 + 5461 + 5461 = 16384；4 × 2731 + 2 × 2730 = 16384。

两个推论：第一，3 主扩到 6 主，单节点 key 量从约 333 万降到约 167 万，降一半，但前提是均匀分布；第二，槽数只差 1 个槽时 key 量差约 610 个（1,000 万 / 16384 ≈ 610.35 个 key/槽），相对 333 万可以忽略——所以“槽数不均”从来不是 3 主、6 主这种规模的均衡问题，真正的均衡问题在 10.2 节。

### 10.2 哈希标签改变分布的定量影响

【官方】key 里第一个 `{...}` 内的子串才参与算槽，同一标签的 key 落在同一槽。标签把“按整个 key 均匀散列”改成“按标签散列”，标签数就是有效的散列基数。

【估算】同样取总量 1,000 万、均匀时每槽约 610 个 key：

- 极端例子：200 万个 key 只用 10 个不同标签（例如 10 个租户 `{tenant:01}`～`{tenant:10}`），它们只占 10 个槽，每槽 200,000 个 key，是均匀情形下这 200 万个 key 每槽约 122 个的 1638.4 倍。最坏情况下这 10 个槽恰好落在同一个主节点，该节点要多承接 200 万个 key，相当于它均匀基线约 333 万的 60% 增量，而其他节点分不到这批 key 的任何一个。
- 温和例子：300 万个 key 用 100 个不同标签，每槽 30,000 个 key，是均匀每槽约 610 个的 49.2 倍。100 个标签本身在 16384 个槽里大致散开，所以节点间分摊相对均匀，但“单槽 key 量”仍比均匀时高一个数量级——这个槽所在节点的内存和热点压力不会因为“标签多”而消失。
- 极限：所有 key 用同一个标签，全部 key 落在 1 个槽、1 个主节点上，主节点数从 3 加到 300 都没用，扩容对这批 key 的容量和吞吐贡献是 0。

结论口径：标签数决定分布的上限。评估标签方案时不要只数“标签够不够多键操作”，要算“最少标签的 key 量 / 标签数”与“均匀每槽 key 量”的比值；比值超过 10 倍就要先问这批 key 的量级，再决定要不要拆标签。

### 10.3 扩容/缩容：迁移 k 个槽要搬多少 key

迁移成本的估算方法只有一条公式，【估算】假设 key 在槽上均匀分布、迁移期间 key 总量不变：

```text
搬迁 key 数 ≈ key 总量 × k / 16384
```

总量 1,000 万时的换算表：

| 迁移槽数 k | 占全部槽比例 | 约搬多少 key |
|---|---|---|
| 100 | 0.61% | 约 61,035 |
| 1000 | 6.10% | 约 610,352 |
| 2731（约 1 个 6 主节点的量） | 16.67% | 约 1,666,870 |
| 4096（3 主扩 4 主，新节点接的量） | 25% | 2,500,000 |
| 8193（3 主扩 6 主，3 个新节点共接的量） | 50.01% | 约 5,000,610 |

读法：3 主扩 4 主，新节点要接 4096 个槽，约搬走总量的 1/4；3 主扩 6 主，3 个新节点共接 8193 个槽，约搬走总量的一半——扩容搬的不是“增量”，是存量的一大块，所以扩容窗口要按“搬几百万个 key”排期，而不是按“加几台机器”排期。缩容是同一公式反向用：下线 1 个 6 主节点要迁出它负责的约 2731 个槽、约 167 万个 key，分摊到剩下 5 个节点，每节点约多接 546 个槽、约 33 万个 key。

时间换算要另给一个假设，不属于上面公式：【估算】若迁移吞吐按 10,000 个 key/秒计，搬 610,352 个 key 约 61 秒，搬 2,500,000 个 key 约 250 秒（约 4.2 分钟）。吞吐不是官方数字，实际值取决于 key 大小、网络和迁移限速，排期时用实测吞吐代入同一公式重算。

### 10.4 故障转移时间线与写不可用窗口

【官方】`cluster-node-timeout` 是节点被判定为故障前允许不可达的最长时间（毫秒）；主节点不可达超过该值会被其从节点接管；节点连续该时长联系不上多数主节点会停止接受查询。官方 spec 的可用性结论是：多数派一侧在 `NODE_TIMEOUT` 时间加“选主与接管通常 1 或 2 秒”后恢复可用。`redis.conf` 自带示例的默认值是 `cluster-node-timeout 15000`，即 15 秒。

【估算】按下式换算受影响槽段的写不可用窗口（集群侧下限，不含客户端发现拓扑变化、刷新缓存与重试的时间，客户端感知到的窗口只会更长）：

```text
写不可用窗口 ≈ cluster-node-timeout + 选主与接管 1–2 秒
```

| cluster-node-timeout | 写不可用窗口（集群侧） |
|---|---|
| 5000 毫秒（官方扩展示例用的值） | 约 6–7 秒 |
| 15000 毫秒（默认值） | 约 16–17 秒 |
| 30000 毫秒 | 约 31–32 秒 |

时间线（默认值 15 秒）：t = 0 主节点失联 → t ≈ 15 秒多数主节点确认其 FAIL（PFAIL→FAIL）→ t ≈ 16–17 秒从节点选主完成、接管槽位并广播新拓扑。调小 timeout 能缩短窗口，但代价是网络抖动更容易误判下线；调大则反之。原文第 4 节“一般 5–15 秒量级按业务容忍度调”说的就是这笔账。

另两个与时间有关的官方口径：第一，【官方】少数派一侧的主节点在超过 `NODE_TIMEOUT` 联系不上多数派后停止接受写，所以分区期间少数派一侧最多接受 `NODE_TIMEOUT`（默认 15 秒）时间的写，之后不再接受、也不再丢新写——写丢失窗口的上限就是这个值。第二，【官方】从节点是否参与接管受 `cluster-replica-validity-factor`（默认值 10）限制：从节点与主节点断开超过 `node-timeout × factor + repl-ping-replica-period`（默认 repl-ping 周期 10 秒）就不会尝试接管，默认值下是 15 × 10 + 10 = 160 秒。断联超过 160 秒的从节点即使活着也不会自动接管，要等原主节点重新加入才恢复可用。

### 10.5 ASK 与 MOVED 的定量区别与 MOVED 风暴条件

【官方】节点不代为转发请求，只返回重定向：MOVED 表示槽已永久迁到另一节点，客户端应更新槽位缓存；ASK 表示槽正在迁移中，这次请求临时去目标节点（先发 `ASKING`），客户端不要更新缓存。

【估算】按“每条命令 1 次往返（RTT）”计数，正常请求 1 次往返：

| 情形 | 首次请求往返数 | 后续同槽请求往返数 | 是否更新缓存 |
|---|---|---|---|
| 正常（缓存正确） | 1 | 1 | 否 |
| ASK（迁移中） | 2（1 次到源节点拿到 ASK，1 次到目标节点，ASKING 与原命令可同连接流水线发） | 1（下次仍先问源节点，直到迁移完成变 MOVED） | 否 |
| MOVED（已迁完，缓存过期） | 2（只更新该槽映射）或 3（全量刷新 `CLUSTER SLOTS` 再重试） | 1 | 是 |

关键区别不在首次请求的往返数（ASK 与 MOVED 首次都是多 1–2 次往返），在“会不会重复发生”：ASK 只影响迁移中的槽、且每次都要多 1 次往返，迁移完成即消失；MOVED 是一次性成本，缓存刷新后同槽请求恢复 1 次往返。MOVED 风暴的条件就是“缓存一直不刷新”：客户端每次 MOVED 都全量刷新、或根本不缓存槽位映射，风暴就持续；只在首次 MOVED 时刷新一次，风暴只持续一个刷新间隔。

【估算】风暴量级：一次扩容迁走 4096 个槽（占 25%），客户端缓存还是旧的、总请求 20,000 QPS，则约 25% 的请求打到错误节点，即约 5,000 次 MOVED/秒，直到缓存刷新。若每次 MOVED 都触发一次全量 `CLUSTER SLOTS` 拉取，额外开销就是 5,000 次/秒的全量拓扑拉取；若只在首次 MOVED 刷新，额外开销约等于 1 次全量拉取加 5,000 次重试往返。判断指标是 `errorstat_MOVED` 的增速：扩容后短暂冲高后回落是正常刷新，持续高位就是缓存没刷新或用了不支持重定向的客户端。

### 10.6 边界条件

1. **主节点数上限**：【官方】槽总数 16384 是主节点数的理论上限，建议最大值约 1000 个节点。1000 主时每节点平均 16.384 个槽——节点数再往上加，每节点只剩十几个槽，Gossip 与心跳开销先成为瓶颈，扩容收益先见顶。
2. **单槽无人覆盖，全集群停写**：【官方】`cluster-require-full-coverage` 默认 yes，一个槽没人管，整个集群拒绝写。主节点与其全部从节点同时挂掉时，受影响的只是约 1/3（3 主）或约 1/6（6 主）的槽，但停写是全集群的——把该参数设成 no 才能让其余槽继续服务，代价是部分 key 暂时写不进去。
3. **从节点太久没同步就不接管**：见 10.4，默认值下从节点与主节点断联超过 160 秒就放弃自动接管。演练时只 kill 主节点、从节点一直在线，接管一定发生；真实故障里从节点可能早已断联，故障转移时间不是 16–17 秒，而是“等原主节点回来”。
4. **标签归组过度，扩容失效**：见 10.2，全部 key 共用一个标签时所有 key 在 1 个槽上，加主节点对这批 key 的容量与吞吐贡献为 0。出现单槽 key 量超过均匀值 10 倍以上时，先拆标签再谈扩容。
5. **迁移中的多键命令会 TRYAGAIN**：【官方】迁移期间同一槽的 key 可能分处源节点与目标节点，多键命令无法一次答完，返回 TRYAGAIN 要求稍后重试。迁移窗口内多键操作的失败不是偶发，是结构性的；迁移期间对该槽的多键操作要按“会重试”来设计，而不是按“一次成功”来设计。

### 复算口径

- 假设（【估算】）：key 在 16384 个槽上均匀分布；迁移期间 key 总量不变；每条命令 1 次往返，ASKING 与重试命令可同连接流水线发；迁移吞吐 10,000 个 key/秒仅为时间换算示例。以上均不是官方数字、不是实测值。
- 官方事实（【官方】，核验日期 2026-11-08）：16384 个槽与 `CRC16(key) mod 16384`、哈希标签规则、MOVED/ASK 语义、NODE_TIMEOUT 后加 1–2 秒恢复可用、少数派超 NODE_TIMEOUT 停写、`cluster-require-full-coverage` 默认 yes、节点数建议上限约 1000，均见 Redis Cluster spec 与 Scale with Redis Cluster；`cluster-node-timeout` 默认值 15000 毫秒见 `redis.conf` 自带示例，`cluster-replica-validity-factor` 默认值 10 与“5 秒 × 10 = 超过 50 秒不接管”的算例见 Scale with Redis Cluster。
- 来源链接：
  - https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/
  - https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/

```python
TOTAL = 16384
K = 10_000_000  # key 总量假设

def split(n):
    base, rem = divmod(TOTAL, n)
    counts = [base + 1 if i < rem else base for i in range(n)]
    ranges, s = [], 0
    for c in counts:
        ranges.append((s, s + c - 1))
        s += c
    return counts, ranges

print(split(3))   # ([5462, 5461, 5461], [(0, 5461), (5462, 10922), (10923, 16383)])
print(split(6))   # ([2731, 2731, 2731, 2731, 2730, 2730], [(0, 2730), (2731, 5461), (5462, 8192), (8193, 10923), (10924, 13653), (13654, 16383)])
print(split(4))   # ([4096, 4096, 4096, 4096], [(0, 4095), (4096, 8191), (8192, 12287), (12288, 16383)])
print("keys/slot:", K / TOTAL)              # 610.3515625
print("3-master keys/node:", K / 3)          # 3333333.33
print("6-master keys/node:", K / 6)          # 1666666.67
for k in (100, 1000, 2731, 4096, 8193):
    print(f"migrate {k} slots -> {K * k / TOTAL:.0f} keys")
print("hash-tag 2M keys / 10 tags per slot:", 2_000_000 / 10)   # 200000
print("uniform per-slot for 2M keys:", 2_000_000 / TOTAL)      # 122.07
print("ratio:", (2_000_000 / 10) / (2_000_000 / TOTAL))        # 1638.4
print("hash-tag 3M keys / 100 tags per slot:", 3_000_000 / 100)  # 30000
print("ratio vs avg slot:", (3_000_000 / 100) / (K / TOTAL))     # 49.152
for t in (5, 15, 30):
    print(f"timeout {t}s -> failover window {t + 1}-{t + 2}s")
print("replica validity cutoff (s):", 15 * 10 + 10)  # 160
print("MOVED storm at 20000 QPS * 25%:", 20000 * 0.25)  # 5000.0 /s
print("migrate 610352 keys at 10000/s (s):", 610352 / 10000)  # ~61
print("migrate 2500000 keys at 10000/s (s):", 2500000 / 10000)  # 250
print("slots/node at 1000 masters:", TOTAL / 1000)  # 16.384
```

## 实战案例

### 案例一：3 主扩到 6 主，扩容期间 MOVED 报错刷屏

**现象：** 一个 3 主集群共 1,000 万个 key（原文 §10 的估算假设总量），扩到 6 主后，业务侧短时间内收到大量 MOVED 报错，错误率迟迟不回落。

**排查：** 先按 §10.3 的公式算搬迁量：搬迁 key 数 ≈ key 总量 × 迁移槽数 / 16384。3 主扩 6 主，3 个新节点一共要接 8193 个槽（占全部 16384 个槽的 50.01%），约搬 5,000,610 个 key，约占总量的一半（§10.3）。这说明扩容搬的不是增量，而是存量的一大块，排期要按“搬几百万个 key”来排，而不是按“加几台机器”来排（§10.3）。再按 §10.5 判断 MOVED 的性质：MOVED 表示槽已永久迁到另一节点，客户端应刷新本地槽位缓存；ASK 表示槽正在迁移中，这次请求临时去目标节点，客户端不要更新缓存（§10.5）。扩容期间先收到 ASK、迁移完成后才变 MOVED，是正常顺序（§10.5、原文第 11 节参考答案第 7 题）。风暴量级也可以估算：一次扩容迁走 4096 个槽（占 25%），客户端缓存还是旧的、总请求 20,000 QPS，则约 25% 的请求打到错误节点，即约 5,000 次 MOVED/秒，直到缓存刷新（§10.5）。判断指标是 `errorstat_MOVED` 的增速：扩容后短暂冲高后回落是正常刷新，持续高位就是缓存没刷新或用了不支持重定向的客户端（§10.5）。

**结论：** 本案例中 MOVED 短暂冲高后回落属于正常刷新；若持续高位，应检查客户端是否在首次 MOVED 时刷新了槽位缓存、是否每次 MOVED 都触发全量 `CLUSTER SLOTS` 拉取（§10.5）。时间方面，按 §10.3 给出的换算示例（迁移吞吐 10,000 个 key/秒，搬 2,500,000 个 key 约 250 秒），搬约 5,000,610 个 key 的量级约为 500 秒——但该吞吐只是 §10.3 的换算示例、不是官方数字也不是实测值，实际迁移吞吐取决于 key 大小、网络和迁移限速，原文未展开，排期时须用实测吞吐代入同一公式重算（§10.3）。

### 案例二：主节点宕机后写不可用比预期长，从节点迟迟不接管

**现象：** 一个主节点宕机后，它负责的槽段写不可用；过了十几秒仍未恢复，且从节点始终没有接管。

**排查：** 先按 §10.4 的时间线换算写不可用窗口：写不可用窗口 ≈ cluster-node-timeout + 选主与接管 1–2 秒。`cluster-node-timeout` 默认值是 15000 毫秒，即 15 秒（§10.4），默认值下写不可用窗口约 16–17 秒（§10.4）。时间线是：t = 0 主节点失联 → t ≈ 15 秒多数主节点确认其 FAIL（PFAIL→FAIL）→ t ≈ 16–17 秒从节点选主完成、接管槽位并广播新拓扑（§10.4）。若超过这个窗口仍未接管，再查从节点的断联时长：从节点是否参与接管受 `cluster-replica-validity-factor`（默认值 10）限制，从节点与主节点断开超过 `node-timeout × factor + repl-ping-replica-period`（默认 repl-ping 周期 10 秒）就不会尝试接管，默认值下是 15 × 10 + 10 = 160 秒（§10.4）。断联超过 160 秒的从节点即使活着也不会自动接管，要等原主节点重新加入才恢复可用（§10.4、§10.6 第 3 条）。

**结论：** 默认配置下 16–17 秒的写不可用窗口是符合 §10.4 换算的预期行为，不是故障；超过该窗口仍不接管时，应优先核查从节点与主节点的断联时长是否已超过 160 秒（§10.4）。另需注意：§10.4 的 16–17 秒是集群侧下限，不含客户端发现拓扑变化、刷新缓存与重试的时间，客户端感知到的窗口只会更长——客户端侧的具体耗时原文未展开，不作定论（§10.4）。

## 小技巧与冷知识

【小技巧】手动排障先跑 `redis-cli --cluster check 任一节点地址`：它会逐节点核对槽位覆盖、主从关系和节点间是否对拓扑达成一致，输出末尾直接给结论。比逐台 `CLUSTER NODES` 肉眼对槽段快得多，扩缩容、节点下线后第一时间就该跑它，看到 "All nodes agree about slots configuration" 才算拓扑干净。

【小技巧】只想查某一批 key 落在哪个分片，用 `CLUSTER COUNTKEYSINSLOT 槽号` 和 `CLUSTER GETKEYSINSLOT 槽号 数量`：先用 `CLUSTER KEYSLOT key` 算出 key 的槽号，再看这个槽里有多少 key、抽几个样本出来。大 key 排查时先定位它在哪个槽、哪个节点，而不是全集群逐节点扫。

【小技巧】集群端口要开两个：数据端口 6379 之外，集群总线端口默认是数据端口 + 10000（6379 对应 16379），节点间 Gossip、故障检测都走总线。防火墙、安全组只放行 6379 时，客户端能连上、节点间却互相看不见，集群永远组不起来；容器部署时总线端口也要映射出去，不能只映射数据端口。

【小技巧】集群模式下没有多数据库，`SELECT 1` 会直接报错：Cluster 只认 0 号库，从单机迁过来时，代码里按业务分库（SELECT 2、SELECT 3）的写法要先改掉，用 key 前缀区分业务，而不是靠库号。迁移前先全库 grep 一遍 `SELECT` 命令，漏掉一处就是上线后才爆的错。

【小技巧】哨兵的 quorum 达标之前，先用 `SENTINEL CKQUORUM 主名` 验一下：它会告诉你当前能联系上的哨兵数够不够达成客观下线。演练或刚部署完哨兵时跑一次，quorum 设得比存活哨兵数还高、哨兵之间网络不通，都会在这里现形；别等主节点真挂了才发现 quorum 永远凑不够。

【小技巧】哨兵拓扑变了之后跑 `SENTINEL RESET 主名`：它会清掉哨兵对该主节点记录的旧从节点、旧哨兵信息，强制重新发现。主从关系手动调过、节点 IP 换过之后，哨兵还拿着旧拓扑做判断，故障转移就可能选错目标；改完拓扑顺手 RESET 一次，比等下次故障转移时才发现要便宜。

【小技巧】`CLUSTER FAILOVER` 可以在从节点上手动触发一次切换：演练、主节点要下线维护时，先在从节点上执行它，让从节点接管槽位再停老主，比直接 kill 主节点再等自动选举可控。加 `TAKEOVER` 参数会跳过多数派协商直接强制切换，只在“集群已失多数派、别无选择”时用，平时别碰。

【小技巧】从节点不是非升不可，用 `replica-priority 0` 把它排除在选举之外：优先级为 0 的从节点永远不会被选为新主，适合“这台机器配置差、只想让它做读副本”的场景。反过来，配置最好的从节点可以把优先级调小（数字越小越优先），让选举倾向于它；默认所有从节点优先级都是 100，等于随机挑。

【小技巧】`cluster-require-full-coverage` 默认是 yes，一个槽没人管、整个集群就拒绝写：主节点和它的从节点同时挂掉、对应槽段无人覆盖时，集群返回 CLUSTERDOWN，所有写（甚至无关槽的写）都停掉。想让“坏掉的槽段之外还能继续服务”，把它设成 no；但这是拿“部分数据不可用”换“其余部分可用”，设之前先确认业务能不能接受某些 key 暂时写不进去。

【小技巧】扩容搬槽别只看进度，要看 `CLUSTER INFO` 里的 `cluster_slots_fail`：搬槽过程中如果有槽处于迁移中途、两边都没认领，`cluster_slots_fail` 就会大于 0，命中这些槽的请求会失败。`redis-cli --cluster reshard` 跑完后先确认这个值归零、再放量；只看“搬完了”就放量，等于把半截槽段暴露给业务。

【小技巧】调试集群命令时用 `redis-cli -c`：带 `-c` 的客户端收到 MOVED 会自动跟过去重试，不带 `-c` 时 MOVED 就是一条报错原样返回。手动排障、验证槽位分布时用 `-c`，写脚本批量操作时反而不带 `-c`，让 MOVED 原样暴露出来——脚本里看到 MOVED 就知道槽位缓存该刷新了，而不是被客户端悄悄掩盖。

【小技巧】热 key 先找再打散，`redis-cli --hotkeys` 只在 LFU 策略下才工作：它采样的是各 key 的访问频率，依赖 LFU 的频率计数，所以 `maxmemory-policy` 不是 `*lfu` 时它采样不到热 key。集群下热 key 只压垮一个分片，定位到之后用原文第 8 节的“多副本 + 随机选”或本地缓存兜一层，别指望扩容能分摊单个 key 的流量。

【小技巧】容器或 NAT 环境部署集群要配 `cluster-announce-ip` 和 `cluster-announce-port`：节点向外广播的地址默认是它自己看到的内网地址，客户端拿到内网 IP 根本连不上。Docker 里跑 Cluster 时每个节点都要显式宣告外网可达的地址和端口，否则 `CLUSTER NODES` 里全是容器内网 IP，客户端一律 MOVED 到连不上的地址。

【小技巧】想让写操作等从节点确认，用 `WAIT 从节点数 超时毫秒`：`WAIT 1 1000` 会阻塞到至少 1 个从节点确认收到、或 1000 毫秒超时，返回实际确认的从节点数。它是“半同步”的一次性版本，不改配置、只对这次写生效；关键写（如下单、扣库存）之前调一次，代价是一次往返的延迟，换来的是“主挂了、这条写大概率已同步”的确定性。

【冷知识】Redis Cluster 是 2015 年随 Redis 3.0 发布的，哨兵比它早三年：哨兵在 2.6 时代（2012 年）就有了，Cluster 直到 3.0 才稳定可用。所以“哨兵 + 主从”这套打法在生产里沉淀的时间更长，运维经验和客户端支持也更成熟；Cluster 解决的是哨兵解决不了的容量问题，不是哨兵的升级版。

【冷知识】集群总线用的不是 RESP 协议，是独立的二进制协议：节点间 Gossip、故障检测、槽位配置传播都走总线端口，抓包看到的不是人类可读的命令文本。这也是总线端口必须单独放行的原因——它和数据端口是两套东西，混在一个端口上既做不到、也不安全。

【冷知识】集群会自动把从节点“搬”去救没有从节点的主节点：这叫副本迁移（replicas migration），某个主节点丢掉全部从节点后，集群会从拥有多个从节点的主节点那里调一个从节点过去。前提是集群里有多余的从节点可调，且 `cluster-allow-replica-migration` 没被关掉；每个主节点只有一个从节点时无从可调，这就是原文说“最少 3 主 3 从起步”的另一层原因。

【冷知识】16384 是 2 的 14 次方，槽号就是 CRC16 取模：`CRC16(key) % 16384` 里的 16384 不是拍脑袋的数字，2 的幂次让取模可以用位运算完成，也让槽位图正好是 2KB。哈希标签的规则也只认第一个花括号对：`user:{1001}:profile` 和 `{1001}user:profile` 算出的槽一样，因为只看 `{}` 里面的内容；key 里没有花括号就对整个 key 算。

【冷知识】哨兵的故障转移演练有官方的模拟命令：`SENTINEL SIMULATE-FAILURE CRASH-AFTER-ELECTION`（选出领头哨兵后模拟崩溃）和 `CRASH-AFTER-PROMOTION`（提升新主后模拟崩溃），专门用来演练“转移进行到一半、执行者挂了”这种最难复现的场景。演练不用真的 kill 进程，哨兵自己会按指令在指定步骤崩溃。

## 11. 面试与自测

1. 哨兵判定主节点客观下线的流程是什么？quorum 和哨兵选举领头是两回事吗？
2. 脑裂时为什么会丢数据？`min-replicas-to-write` 怎么缓解、代价是什么？
3. Cluster 为什么是 16384 个槽而不是 65536？
4. MOVED 和 ASK 的区别？客户端分别应该怎么处理？
5. Cluster 下要保证 `user` 的 profile、setting、score 三个 key 能做事务，怎么设计 key？
6. 数据量只有 20GB、读 QPS 很高，应该上 Cluster 还是哨兵 + 多从？说明理由。

7. 一个 3 主集群共 1,000 万个 key，要扩到 6 主：3 个新节点一共要接多少槽、大概要搬多少 key？扩容期间客户端可能先收到 ASK 还是 MOVED，为什么？另问：cluster-node-timeout 默认 15 秒时，一个主节点宕机后它负责的槽写不可用窗口大约多长？

### 参考答案

1. 流程是：单个哨兵认为主节点不可达叫主观下线（SDOWN）；超过 quorum（法定人数）个哨兵都报告主观下线，才判定客观下线（ODOWN），触发选举和故障转移。quorum 和哨兵选举领头是两回事：quorum 是判定客观下线的门槛，领头哨兵是哨兵之间再用 Raft 式选举选出一个，由它执行转移（从从节点中按优先级、复制偏移量、runID 综合排序挑新主）。
2. 脑裂丢数据的原因是复制异步：主节点所在机房网络分区后，哨兵在另一分区选出新主，老主其实活着还继续接收客户端写入；分区恢复后老主降为从节点，分区期间的那批写入被全量同步直接覆盖清掉。min-replicas-to-write 1 加 min-replicas-max-lag 10 的缓解方式是：主节点发现自己连不上足够从节点时拒绝写入，宁可不可用也不写孤岛数据；代价就是拿可用性换一致性，金融场景应该开。
3. 因为节点间心跳包要携带槽位图：16384 个槽用位图表示是 2KB，在节点数上限约 1000 时心跳开销可接受；槽太多心跳包就爆了。槽数是心跳开销与分片粒度之间的折中，不是越大越好。
4. MOVED 表示槽已永久迁到另一节点，客户端应刷新本地槽位缓存，后续直连新节点；ASK 表示槽正在迁移中，这次请求临时去目标节点（先发 ASKING），客户端不要更新缓存。智能客户端（Lettuce、JedisCluster）会缓存槽位映射，扩容后偶发 MOVED 是正常现象，频繁出现才需要查槽位状态。
5. 用哈希标签把三个 key 钉在同一槽：user:{1001}:profile、user:{1001}:setting、user:{1001}:score。Cluster 只对花括号内的部分算槽，这样三个 key 落在同一槽，多键事务就不会报 CROSSSLOT；注意加标签会改变槽位，存量数据要迁移或双读过渡。
6. 选哨兵加多从。理由：20GB 装得进单机内存，瓶颈只是高可用和读扩展，哨兵正好解决这两点，运维也简单；Cluster 解决的是容量扩展和写吞吐水平扩展，数据量奔着几百 GB 去或写 QPS 单主扛不住时才上。数据能装进一台机器、只是要高可用时，哨兵足够，别为了先进上 Cluster。

7. 3 个新节点一共要接 8193 个槽（6 主均分时每节点 2731 或 2730 个槽，3 个新节点共 8193 个），按 key 均匀分布估算要搬约 5,000,610 个 key，约占总量的一半（公式：搬迁 key 数 ≈ key 总量 × 迁移槽数 / 16384 = 1,000 万 × 8193 / 16384）。扩容期间先收到 ASK：槽正在迁移中，源节点对已搬走的 key 返回 ASK，客户端先发 ASKING 再到目标节点重试，且不更新缓存；迁移完成后才变 MOVED，客户端刷新缓存直连新节点。故障转移窗口：默认值 15 秒加选主与接管通常 1–2 秒，写不可用窗口约 16–17 秒（集群侧下限，客户端发现与重试的时间另算）。
