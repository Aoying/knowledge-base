# ES-倒排索引与查询

> 本篇讲 ES 搜索的内核：文档进索引时如何被分析成倒排表、查询 DSL 如何命中这张表、结果为什么按那个顺序排。集群、分片、写入调优与运维见汇总篇 [Elasticsearch](数据库/ES/Elasticsearch.md)。

## 倒排索引结构

传统索引是"文档 → 词"（打开一本书看它讲什么），倒排索引反过来建"词 → 文档列表"：

| 词条（term） | 倒排列表（posting list） |
|---|---|
| java | doc1（词频 3，位置 0/5/9）、doc4（词频 1） |
| 编程 | doc1、doc2、doc7 |
| 思想 | doc1、doc3 |

- **词典（term dictionary）**：所有不重复词条的有序集合（Lucene 里用 FST 有限状态转换器压缩存放），查词先二分定位词典，再拿倒排列表。
- **倒排列表**：每个词条对应一串命中记录，不只存文档 ID，还存**词频**（这词在该文档出现几次）和**位置**（第几个词）——词频喂给相关性打分，位置支撑短语查询（match_phrase 要求词挨着出现）。
- 搜索快的原因：查"java 编程"就是取两个倒排列表**求交集**，复杂度只跟命中量走，不扫全表；这也是为什么 ES 能在亿级文档里毫秒返回。
- 代价：倒排表在写入（refresh 成段）时就建好且不可变，查询只是读；更新一篇文档 = 旧文档标记删除 + 整篇重新分析建索引，没有"改一个字段"的便宜操作。

## 分析器链：文档和查询都要过同一道工序

建倒排表前，文本要先被**分析器（analyzer）**处理成词条，三个环节串行：

1. **字符过滤器（char filter）**：预处理原文，如去掉 HTML 标签、`&` 转 `and`。
2. **分词器（tokenizer）**：切词。默认 standard 按空格/标点切并逐词处理；中文整句没有空格，必须换 IK 分词器（`ik_max_word` 细粒度、`ik_smart` 粗粒度），否则整句被当成一个词，搜什么都搜不到。
3. **词元过滤器（token filter）**：逐词加工，如转小写、去停用词（the、的）、加同义词。

关键推论：**查询串也要过分析器**（match 查询会把查询文本用字段的分析器再切一遍）。写入端用 ik_max_word、查询端不一致，或者字段建错分析器，效果就是"明明有这篇文档却搜不到"。排查搜索问题先看 `GET /索引/_analyze` 两边切出来的词是否一致。

## mapping 要点

mapping 是字段的"表结构"，建索引时定清；类型定错改不了，只能 reindex 重建。

- **dynamic**：不写 mapping 时 ES 按第一个文档猜类型（动态映射）。生产别裸奔：字符串会被同时建成 text+keyword 两份、year 可能被猜成字符串，后面全乱。显式写 mapping，或设 `"dynamic": "strict"` 让没声明的字段直接报错。
- **text vs keyword**：text 过分析器、建倒排，做全文搜索；keyword 不分词、整串入索引，做精确匹配/聚合/排序。一个字段两者都要就建多字段：

```json
"title": { "type": "text", "analyzer": "ik_max_word",
           "fields": { "kw": { "type": "keyword" } } }
```

查时用 `title` 搜、用 `title.kw` 聚合排序。选型口诀：要搜 → text；要等值/聚合/排序 → keyword。

字段类型速查（建 mapping 时对号入座）：

| 类型 | 存什么 | 注意 |
|---|---|---|
| long / integer | 整数 | 可能带前导 0 的编号用 keyword，别用数值型 |
| double / scaled_float | 小数 | 钱用 scaled_float（放大成整数存） |
| boolean | true/false | 别拿字符串 "true" 冒充 |
| date | 时间 | format 在 mapping 写全，写入端统一格式 |
| ip / geo_point | IP、经纬度 | 用专有类型才能做 IP 段、地理距离查询 |
| object / nested | 嵌套 JSON | 数组对象要按元素独立检索必须用 nested，普通 object 会把各元素字段揉在一起查错 |

## Query DSL

先分清两种上下文：**query 上下文**算相关性得分、决定排序；**filter 上下文**只判是否命中、不打分、可缓存。精确条件（状态、作者、时间范围）一律放 filter，又快又不污染排序。

- **match**：全文搜索。查询串先过分析器切词，再任一词命中即算中（默认 OR）；要全中改 `"operator": "and"`。短语不许拆用 **match_phrase**（靠倒排列表里的位置判断词是否相邻）。
- **term**：精确匹配，不分词、查询串原样对词条。只对 keyword 字段用；拿 term 查 text 字段必然查不到——text 已被切成多个词，整串对不上任何单个词条，这是新手第一大坑。多值任一命中用 **terms**。
- **bool**：组合容器，四槽——`must`（必须中，算分）、`should`（加分项，算分）、`must_not`（排除，不算分）、`filter`（必须中，不算分）。业务查询的标准骨架是 must 放全文条件、filter 放全部精确条件。
- **range**：范围，`{"range": {"year": {"gte": 2000, "lte": 2020}}}`，对数值和日期都成立。
- **exists**：判断字段存在（有值），清洗数据时常用。

```json
GET /books/_search
{ "query": { "bool": {
    "must":   { "match": { "title": "Java 编程" } },
    "filter": [
      { "term":  { "author": "Bruce Eckel" } },
      { "range": { "year": { "gte": 2000, "lte": 2020 } } }
    ]
} } }
```

- **aggs**（聚合，相当于 GROUP BY）只在此提一句：实战写法（PV/UV、date_histogram）见汇总篇 [Elasticsearch](数据库/ES/Elasticsearch.md)。
- wildcard/regexp 通配查询不走倒排加速，数据量大时近似全扫；能用分词或前缀字段解决的别用。

## 相关性打分 BM25：三个直觉

match 命中的文档按 `_score` 从高到低排，默认打分算法是 BM25，不用背公式，记住三个直觉：

1. **词频饱和（TF）**：一个词在文档里出现越多越相关，但边际递减——出现 10 次不比 5 次相关两倍（对数式饱和，防止长文堆词作弊）。
2. **逆文档频率（IDF）**：词越稀有越值钱。全库都有的词（如"系统"）区分度低、权重小；只在少数文档出现的词一命中就大幅加分。
3. **字段长度归一化**：同样的命中，出现在短标题里比出现在长正文里更相关——短字段词密度高，BM25 按字段平均长度做归一。

推论：term 这类精确查询通常不打分（多在 filter 里）；想调排序先分清是"没命中"（分析/mapping 问题）还是"命中了排得靠后"（打分问题），后者可用 `GET /索引/_explain` 看单篇文档的得分构成，别靠猜。

## 小技巧与冷知识

【小技巧】keyword 字段上的 term 查询是区分大小写的：keyword 不分词也不转小写，`term` 查 `"Java"` 和 `"java"` 是两个词条。想做不区分大小写的精确匹配，给 keyword 字段配一个 lowercase 的 normalizer，写入时统一转小写，查询时也按小写写——比查 text 字段再纠结分词可靠得多。

【小技巧】match_phrase 太死时加 `slop` 松一格：`match_phrase` 默认要求词紧挨着，`"slop": 1` 允许中间插一个词，`"slop": 2` 允许插两个。搜“Java 编程思想”时标题里写的是“Java 高级编程思想”，slop 1 就能命中、slop 0 就查不到；slop 越大召回越高、相关性越低，调的时候从 1 开始试。

【小技巧】match 查询想“大部分词命中就行”用 `minimum_should_match`：默认 match 是 OR、任一词中就算中，`"operator": "and"` 又要求全中；中间地带用 `"minimum_should_match": "75%"`，四个词里中三个就算命中。长查询串（比如整句问题）用百分比档位，比在 OR 和 AND 之间二选一更实用。

【小技巧】keyword 字段超长字符串默认不进索引：keyword 有个 `ignore_above: 256` 的默认值，超过 256 个字符的值会被直接忽略、不建倒排，term 查它永远查不到。长文本描述、URL 这类字段如果要做精确匹配，先把 `ignore_above` 调大；如果本来就不打算精确查，忽略反而是省空间的好事。

【小技巧】bool 查询里 `should` 的“至少命中几个”默认是 0：bool 里只要有 `must` 或 `filter`，`should` 就只是加分项、一个都不中也行；只有当 bool 里只剩 `should` 时，至少要命中一个。写“必须满足 A、B，再加分 C、D”时，C、D 放 should 就够了，不用再套一层 minimum_should_match。

【小技巧】查整串别只依赖 `^$` 式思维，ES 里锚定靠字段类型：match 是全文、term 是精确，两者的边界由字段是 text 还是 keyword 决定，而不是靠查询串里加锚点。想“整串等于”就用 keyword + term，想“包含这些词”就用 text + match，锚点那套是正则的思路，搬到 ES 查询里会走偏。

【小技巧】match 查询可以临时换分析器，不用改 mapping：`match` 里传 `"analyzer": "ik_smart"`，这次查询就按 ik_smart 切词，哪怕字段建的时候用的是 ik_max_word。线上排障时先用这个参数试“换个切法能不能搜到”，确认是分析器问题再决定要不要重建索引，比直接改 mapping 快得多。

【小技巧】深分页别用 `from + size` 硬翻：`from` 越大 ES 要在每个分片上先排好再丢掉前面所有结果，翻到几万条就明显变慢，而且默认 `max_result_window` 是 10000，超过直接报错。翻全量用 `search_after`（带上一页最后一条的排序值接着翻）或 scroll，`from + size` 只留给“前几页点一点”的场景。

【小技巧】返回结果只取需要的字段，用 `_source` 过滤：`"_source": ["title", "author"]` 只回这两个字段，_source 里几十 KB 的正文就不用每次跟着查询结果传回来。列表页、聚合页这种“只要标题和作者”的场景，先收窄 _source 再谈查询优化，网络和序列化开销一下子就下来了。

【小技巧】`exists` 查不到 null，但能查到空字符串：ES 不索引 null 值，字段是 null 时 `exists` 判定为不存在；字段值是 `""` 空字符串时它照常索引、`exists` 判定为存在。清洗“缺字段”数据时用 exists 没错，但“值为空串也算缺失”的口径要自己在写入端统一，别指望 exists 帮你区分。

【小技巧】短语查询依赖倒排列表里的位置信息，关掉就查不了：字段的 `index_options` 默认是 positions，match_phrase 靠它判断词是否相邻；如果为了省空间把它改成 `docs` 或 `freqs`，match_phrase 会直接报错或查不到。省空间和保短语查询只能二选一，标题、摘要这类要短语查的字段别动这个参数。

【小技巧】精确条件放 filter 除了不打分，还能被缓存复用：filter 上下文的结果会进节点查询缓存，同一段 filter（比如“状态=已发布”）第二次查就不用重算。把高频的精确条件（状态、分类、时间段）都收进 filter，既省了打分开销，又让缓存命中率上去；must 里塞精确条件等于白白放弃这层缓存。

【冷知识】词典在 Lucene 里是 FST（有限状态转换器）：所有词条按字典序压进一棵共享前缀的自动机里，`java` 和 `javascript` 的公共前缀只存一份。词条越多、词典越大，但因为前缀共享，内存占用比“每个词条单独存一份字符串”小得多；这也是 ES 内存里常驻一份词典就能快速定位词条的原因。

【冷知识】倒排列表不是明文存的，是压缩过的：Lucene 对 posting list 做差分编码（只存文档 ID 的增量）和 FOR（frame of reference）分块压缩，大列表还配跳表（skip list），定位到第 N 个命中不用从头扫。查“java 编程”求交集时，引擎是拿着两个压缩过的有序列表做归并，跳表让它能直接跳到交集附近的区间。

【冷知识】BM25 的两个参数可以在 mapping 里调：`k1` 控制词频饱和的速度（默认 1.2，越大越接近线性计分），`b` 控制字段长度归一化的强度（默认 0.75，0 表示不归一化、1 表示完全按长度惩罚）。调排序之前先确认是不是打分问题，再用自定义 similarity 小范围试 k1、b，别一上来就改 mapping 全量重建。

【冷知识】IK 的两种模式是索引大小和召回的取舍：`ik_max_word` 把一句话切成最细粒度的所有词，索引更大、召回更高；`ik_smart` 只切粗粒度，索引更小、精度更高。同一份中文内容，max_word 的倒排表天然比 smart 大一截，选哪种要看业务更怕“搜不到”还是更怕“搜出一堆不相关的”。

【冷知识】同义词放索引时展开还是查询时展开，结果一样、代价不同：索引时展开（同义词写进倒排表）查询快但索引变大、改同义词要重建；查询时展开（查询串先扩同义词再查）索引小、改同义词不用重建，但每次查询都要多做一次扩展。词表稳定用索引时，词表常变用查询时，别只看查询速度。

## 面试与自测

1. 倒排列表里除了文档 ID 还存什么？这两样东西分别支撑什么能力？查“java 编程”为什么不用扫全表？
2. 拿 term 查 text 字段为什么必然查不到？中文不装 IK 分词器为什么“明明有这篇文档却搜不到”？
3. BM25 的三个直觉各是什么？精确条件为什么要一律放 filter？调排序前要先分清哪两种情况？

### 参考答案

1. 还存词频（这词在该文档出现几次）和位置（第几个词）：词频喂给相关性打分，位置支撑短语查询（match_phrase 要求词挨着出现）。查“java 编程”就是取两个倒排列表求交集，复杂度只跟命中量走，不扫全表。
2. term 是精确匹配，不分词、查询串原样对词条；text 字段已被切成多个词，整串对不上任何单个词条，所以必然查不到，term 只对 keyword 字段用。中文整句没有空格，默认 standard 分词会把整句当成一个词，必须换 IK 分词器（`ik_max_word` 细粒度、`ik_smart` 粗粒度）；且查询串也要过分析器，写入端与查询端切词不一致同样搜不到，排查先看 `GET /索引/_analyze` 两边切出来的词是否一致。
3. 一是词频饱和：出现越多越相关但边际递减，防止长文堆词作弊；二是逆文档频率：词越稀有越值钱，全库都有的词区分度低；三是字段长度归一化：同样命中出现在短标题里比长正文里更相关。精确条件（状态、作者、时间范围）一律放 filter，只判是否命中、不打分、可缓存，又快又不污染排序。调排序先分清是“没命中”（分析/mapping 问题）还是“命中了排得靠后”（打分问题），后者用 `GET /索引/_explain` 看单篇文档的得分构成，别靠猜。
